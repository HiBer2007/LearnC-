# 第 1 章 标准与实现是两回事

## 1.1 标准不能运行程序

**语言的标准（standard）规定「什么代码是合法的、应该有什么行为」，
但它本身不能运行任何程序。**

真正把代码变成可执行文件的是**编译器**——
编译器就是标准的一个**实现（implementation）**。

```
   C 语言标准（ISO/IEC 9899）
        │
        │  由不同的组织各自实现
        ├──────────────┬──────────────┬──────────────┐
        ▼              ▼              ▼              ▼
      GCC           Clang           MSVC      其他编译器
   （GNU）        （LLVM）        （微软）
```

**这几个都是 C 语言的实现**，都遵循同一份标准，
**但在标准未规定的地方可以自由选择。**

## 1.2 同类概念还有哪些

| 层次 | 标准 | 主要实现 |
|---|---|---|
| C 语言 | ISO/IEC 9899（C17、C23） | GCC、Clang、MSVC |
| C++ 语言 | ISO/IEC 14882（C++17、C++20） | GCC、Clang、MSVC |
| 可执行文件格式 | PE/COFF（Windows）、ELF（Linux） | 各系统自己的加载器 |
| 调试信息格式 | DWARF 是公开标准；PDB 是微软的 | GCC 产 DWARF、MSVC 产 PDB |
| 构建系统 | 无统一标准 | CMake 是事实标准 |

**最后两行值得注意**：
「调试信息格式」与「构建系统」也各有各的实现，
**这解释了本教材为什么用大量篇幅讲工具之间的配套关系**。

> **相关**：调试信息格式必须与调试器匹配，
> 见《01-编译器/02-环境配置.md》第 1.1 节。

## 1.3 一个容易混淆的地方

**「实现」有两个不同的含义，要看语境。**

| 语境 | 含义 | 例子 |
|---|---|---|
| **语言的实现** | 编译器这个程序 | 「GCC 是 C 语言的一种实现」 |
| **代码的实现** | 某个函数的具体做法 | 「`printf` 的实现不在这个文件里」 |

**本文讲的是第一种。**

**第二种含义在阅读代码时很常见**，例如：

> 注释说「不会 delete 旧对象」，而函数的实现里 `new` 了一个新对象。

**遇到「实现」这个词，先看它修饰的是什么。**

# 第 2 章 为什么这件事重要

## 2.1 五类可见的差异

| 差异 | 说明 |
|---|---|
| **命令行参数不同** | `-O2` 与 `/O2` 是两套写法 |
| **扩展语法不同** | GCC 有 `__attribute__`，MSVC 有 `__declspec` |
| **调试信息格式不同** | GCC 产 DWARF，MSVC 产 PDB |
| **默认行为不同** | 比如 `char` 是否有符号、`long` 有多宽 |
| **符号命名不同** | C++ 会对函数名做修饰，C 不做 |

**第一类与第三类在《01-编译器/02-环境配置.md》有详细对照**，
第二类在《01-编译器/03-嵌入式与交叉编译.md》中用到。

## 2.2 一个常见现象的解释

```
   同一份代码，在 A 编译器上正常，换到 B 编译器就出错
   →  多半是碰到了「标准未规定、由实现决定」的地方
```

**这句话是本文的核心结论。**

**它同时给出了排查方向**：
不要先怀疑编译器有 bug，
**先确认代码有没有依赖标准未规定的行为**。

## 2.3 与「可移植性」的关系

**可移植性不是「代码能编过」，而是「代码不依赖实现的选择」。**

| 代码写法 | 可移植性 |
|---|---|
| 用 `int32_t` 而不是 `int` | 好，宽度确定 |
| 假设 `char` 无符号 | 差 |
| 假设 `long` 是 4 字节 | **差**，见第 4.1 节 |
| 用 `sizeof(void*)` 判断指针宽度 | 好 |
| 依赖函数参数的求值顺序 | 差 |

**教材后续各篇凡涉及具体字节数的地方，都标注了实测环境**，
原因就在这里。

# 第 3 章 标准里的三类「自由度」

**C 与 C++ 标准对行为的描述分三档，理解这个区分很有用。**

## 3.1 三档对照

| 类别 | 英文 | 含义 | 例子 |
|---|---|---|---|
| **未定义行为** | Undefined behavior | 标准**不作任何要求**，什么事都可能发生 | 数组越界、有符号整数溢出、解引用空指针 |
| **实现定义行为** | Implementation-defined | 标准要求**选定一种并写进文档**，但不规定选哪种 | `char` 是否有符号、`long` 的宽度 |
| **未指定行为** | Unspecified | 标准给出**若干可能**，不规定用哪个，也不要求写文档 | 函数参数的求值顺序 |

## 3.2 三者的实际差别

| | 能否预测结果 | 是否需要写进文档 | 危险程度 |
|---|---|---|---|
| 未定义行为 | **不能** | 否 | **最高** |
| 实现定义行为 | 能，但要查该实现的文档 | **是** | 中 |
| 未指定行为 | 不能，但每种结果都合法 | 否 | 低 |

**「实现定义行为」是可以查的**——
每种编译器都会在与标准配套的文档里写明自己选了什么。
**「未定义行为」无文档可查，因为标准不要求。**

## 3.3 为什么未定义行为最危险

**编译器可以假设未定义行为不会发生，并据此做优化。**

```c
int f(int x) {
    return x + 1 > x;
}
```

**编译器可以把它直接变成 `return 1;`**，
理由是「有符号溢出是未定义行为，因此 `x + 1` 不会溢出」。
但若调用方传入 `INT_MAX`，实际行为与直觉不符。

**这一类问题的特点是：能编过，行为不确定。**

> **完整说明见《03-构建工具链/05-优化等级.md》第 5.5 节。**

## 3.4 三档在代码里的样子

```c
/* 未定义行为：越界写入，后果不可预测 */
int a[10];
a[15] = 1;

/* 实现定义行为：char 是否有符号由实现决定 */
char c = 200;                  /* 若 char 有符号，这里已经溢出 */

/* 未指定行为：两个参数谁先求值不确定 */
f(g(), h());
```

**第一类必须改，第二类要么改要么查文档，第三类通常可以不管。**

# 第 4 章 实测：自由度怎样表现出来

## 4.1 同一个 `long`，三种宽度

**同一份代码，在两个平台的三种实现下运行**（**实测**）：

| 项目 | MinGW gcc 15.2.0 | MSVC 19.51 | Linux gcc 13.3.0 |
|---|---|---|---|
| 平台 | Windows x64 | Windows x64 | Linux x86-64 |
| `sizeof(char)` | 1 | 1 | 1 |
| `sizeof(short)` | 2 | 2 | 2 |
| `sizeof(int)` | 4 | 4 | 4 |
| **`sizeof(long)`** | **4** | **4** | **8** |
| `sizeof(void *)` | 8 | 8 | 8 |
| `char` 是否有符号 | 有符号 | 有符号 | 有符号 |
| `CHAR_MIN` | -128 | -128 | -128 |
| `INT_MAX` | 2147483647 | 2147483647 | 2147483647 |
| `-8 >> 1` | -4 | -4 | -4 |

**唯一不同的是 `sizeof(long)`。**

```
   Windows x64   4 字节    （叫 LLP64 模型）
   Linux x86-64  8 字节    （叫 LP64 模型）
```

**这是本文最有价值的一个例子**：

| 观察 | 说明 |
|---|---|
| 同样在 Windows，gcc 与 MSVC **一致** | 说明差异不来自编译器品牌 |
| 同样用 gcc，Windows 与 Linux **不一致** | 说明差异来自**目标平台的 ABI** |
| `int` 两边都是 4 | 说明并非所有类型都不确定 |

**ABI（应用二进制接口）规定了类型宽度、结构体对齐、
参数传递方式等一整套约定。**
**同一份源码为目标平台编译，就要遵守该平台的 ABI。**

**实际后果**：

```c
/* 在 Windows 上正确，在 Linux 上会截断 */
long file_size = get_file_size();     /* 假设 long 能装下大于 4 GB 的值 */
printf("%ld\n", file_size);           /* 格式符也要跟着改 */

/* 可移植的写法：用固定宽度类型 */
#include <stdint.h>
int64_t file_size = get_file_size();
printf("%" PRId64 "\n", file_size);
```

**教材中凡出现 `long`，都应注意这一点。**
需要确定宽度时用 `<stdint.h>` 的 `int32_t` / `int64_t`。

## 4.2 函数名的符号修饰

**C++ 支持函数重载，因此要对函数名做修饰（name mangling）**，
把参数类型编码进符号名。

**实测**：同一组函数分别用 C 与 C++ 编译，看符号名。

**C++ 源码**：

```cpp
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }
namespace ns { int f(int) { return 0; } }
```

**`g++` 产生的符号**（**实测**，`nm` 输出）：

```
_Z3addii        ← add(int, int)
_Z3adddd        ← add(double, double)
_ZN2ns1fEi      ← ns::f(int)
```

**读法**：

| 部分 | 含义 |
|---|---|
| `_Z` | 修饰名的起始标记 |
| `3add` | 名字长度 3，名字是 `add` |
| `ii` / `dd` | 参数类型：两个 `int` / 两个 `double` |
| `N2ns1fEi` | `N` 开始嵌套名，`2ns` 是命名空间，`1f` 是函数名，`E` 结束，`i` 是参数 |

**C 源码**：

```c
int add(int a, int b) { return a + b; }
```

**`gcc` 产生的符号**（**实测**）：

```
add             ← 完全没有修饰
```

**这解释了一个实际问题**：

> C 编译器按 `add` 去找符号，而 C++ 编译出的符号叫 `_Z3addii`
> —— **链接失败，报 `undefined reference to 'add'`**。

**解决办法是 `extern "C"`**（**实测**）：

```cpp
extern "C" int add(int a, int b) { return a + b; }
```

**产生的符号**：

```
add             ← 与 C 完全一致
```

**这就是所有 C 库被 C++ 调用时都要包一层 `extern "C"` 的原因。**

> **头文件该怎么写**见《00-写在最初/01-C与C++.md》第 2.4.3 节。

## 4.3 命令行参数与扩展

| 功能 | GCC | MSVC |
|---|---|---|
| 优化二级 | `-O2` | `/O2` |
| 生成调试信息 | `-g` | `/Zi` |
| 警告全开 | `-Wall -Wextra` | `/W4` |
| 指定标准 | `-std=c17` | `/std:c17` |
| 导出符号 | `__attribute__((visibility("default")))` | `__declspec(dllexport)` |
| 禁止内联 | `__attribute__((noinline))` | `__declspec(noinline)` |

**最后两行是「扩展」**：标准里没有这些语法，
但两种实现各自加了功能相近的写法。

**这导致一个常见做法——用宏把两者包起来**：

```c
#if defined(_MSC_VER)
#  define NOINLINE __declspec(noinline)
#else
#  define NOINLINE __attribute__((noinline))
#endif
```

**本教材示例中用到了这个写法**，
见《03-构建工具链/05-优化等级.md》附录 B 的探针代码。

> **`_MSC_VER` 是 MSVC 定义的宏**；GCC 定义 `__GNUC__`，Clang 定义 `__clang__`。
> 靠这些宏可以在源码里区分当前是哪个实现。

# 第 5 章 ABI：二进制层面的约定

## 5.1 它是什么

**ABI 是 Application Binary Interface（应用二进制接口）的缩写。**

标准管的是**源码层面**——什么代码合法、应该有什么行为。
**ABI 管的是二进制层面**——编译出来的东西如何与外界对接。

| 层面 | 管什么 | 由谁规定 |
|---|---|---|
| 语言标准 | 语法、语义、哪些行为未定义 | ISO |
| **ABI** | **类型宽度、结构体布局、参数怎么传、符号怎么命名** | **平台与工具链** |

**两者的关系可以这样理解**：

```
   标准说：这个函数有两个 int 参数
   ABI  说：第一个放 rcx，第二个放 rdx
```

**标准不关心参数放在哪，ABI 必须明确**——
否则两个分别编译的目标文件无法链接在一起。

## 5.2 ABI 包含哪些内容

| 内容 | 说明 | 在哪一节 |
|---|---|---|
| 数据模型 | 各种类型的宽度 | 第 4.1 节、第 5.3 节 |
| 调用约定 | 参数放哪、返回值放哪、谁清理栈 | 第 5.4 节 |
| 结构体布局 | 成员顺序、对齐、填充 | 第 5.5 节 |
| 名字修饰 | 符号在目标文件里长什么样 | 第 5.6 节 |
| 符号可见性 | 哪些符号对链接器可见 | 第 5.7 节 |

**本文第 1.2 节提到的「可执行文件格式」与「调试信息格式」
也属于同一类约定**——它们是平台层面的、标准不管的、
但所有工具必须一致的部分。

## 5.3 数据模型

**最常遇到差异的一项是 `long` 的宽度**（**实测**，见第 4.1 节）：

| 模型 | `int` | `long` | 指针 | 用在 |
|---|---|---|---|---|
| **LLP64** | 4 | **4** | 8 | Windows |
| **LP64** | 4 | **8** | 8 | Linux、macOS |

**名字的读法**：`LLP64` 表示 long 与指针都是 64 位；
`LP64` 表示 long 与指针都是 64 位——**这里的 L 指 long，
两个模型的第一、二个字母含义不同，容易记混**。

**记法**：**Windows 的 `long` 与 `int` 一样宽，Linux 的 `long` 与指针一样宽。**

**实际影响**：跨平台代码里凡用 `long` 装大数或指针差值的地方都要改。

```c
/* 在 Windows 上会截断，在 Linux 上正常 */
long size = get_file_size();

/* 两边都对 */
#include <stdint.h>
int64_t size = get_file_size();
```

## 5.4 调用约定

**调用约定规定了「函数调用的两端如何对接」**——
这是 ABI 里最容易被忽略、但一旦不一致就立刻出错的部分。

**实测**：一个六个参数的函数，在 Windows x64 上编译后的开头：

```asm
mov    %rcx,0x10(%rbp)      ← 第 1 个参数
mov    %rdx,0x18(%rbp)      ← 第 2 个参数
mov    %r8,0x20(%rbp)       ← 第 3 个参数
mov    %r9,0x28(%rbp)       ← 第 4 个参数
...
mov    0x30(%rbp),%rax      ← 第 5 个参数，来自栈
```

**对照表**（Windows x64，**实测**）：

| 参数序号 | 位置 |
|---|---|
| 第 1 个 | `rcx` |
| 第 2 个 | `rdx` |
| 第 3 个 | `r8` |
| 第 4 个 | `r9` |
| 第 5 个起 | 栈 |

**不同平台差别很大**：

| 平台 | 前几个整型参数放哪 |
|---|---|
| **Windows x64** | `rcx` `rdx` `r8` `r9` |
| **Linux x86-64** | `rdi` `rsi` `rdx` `rcx` `r8` `r9`（六个） |

**这就是为什么同一个 `.obj` 不能跨平台使用**——
即使机器指令相同，参数放的地方也不一样。

## 5.5 结构体布局与填充

**ABI 规定了对齐规则，编译器据此插入填充字节。**
**这解释了「为什么结构体的大小不等于成员大小之和」。**

**实测**：

```c
struct A { char c; int i; };            /* 8 字节 */
struct B { int i; char c; };            /* 8 字节 */
struct C { char a; char b; char c; };   /* 3 字节 */
```

| 结构体 | `sizeof` | 成员偏移 |
|---|---|---|
| `A` | **8** | `c` 在 0，`i` 在 4 |
| `B` | **8** | `i` 在 0，`c` 在 4 |
| `C` | **3** | `a` 在 0，`b` 在 1，`c` 在 2 |

**读法**：

| 现象 | 原因 |
|---|---|
| `A` 里 `i` 从偏移 4 开始 | `int` 要求 4 字节对齐，`c` 之后空出 3 字节 |
| `A` 总大小是 8 | 4（`c` + 填充）+ 4（`i`） |
| `B` 也是 8 | 4（`i`）+ 1（`c`）+ **3 字节尾部填充** |
| `C` 只有 3 | 三个 `char` 各需 1 字节对齐，无需填充 |

**`A` 与 `B` 的成员完全相同，只是顺序不同，大小却都是 8**——
但内部布局不同。

**工程含义**：

| 做法 | 理由 |
|---|---|
| **不要按成员逐个序列化结构体** | 填充字节的内容未定义 |
| 需要精确布局时用 `#pragma pack` | 但会降低访问速度 |
| 跨平台传数据用文本或明确的字节序 | 见《01-编译器/03-嵌入式与交叉编译.md》第 4 章 |
| 用 `offsetof` 而不是手算偏移 | 见下例 |

```c
#include <stddef.h>
printf("%d\n", (int)offsetof(struct A, i));   /* 让编译器算，别自己数 */
```

> 原《语言与案例》一篇有专门一节，该篇已移出主线待重建。

## 5.6 名字修饰

**ABI 还规定了符号在目标文件里叫什么名字。**

**这件事对 C 与 C++ 的影响完全不同**：

| 语言 | 是否修饰 | 原因 |
|---|---|---|
| **C** | **不修饰**，函数名就是符号名 | 没有重载 |
| **C++** | **修饰**，把参数类型编码进符号名 | 支持函数重载 |

**完整实测对照见第 4.2 节**，那里给出了
`_Z3addii` 与 `add` 的差别以及 `extern "C"` 的作用。

**本章要补充的是**：**名字修饰是 ABI 的一部分，不是语言标准的一部分。**

**证据**：MSVC 与 GCC 的修饰规则**并不相同**。

| 编译器 | `int add(int, int)` 的符号名 |
|---|---|
| GCC / Clang | `_Z3addii` |
| MSVC | `?add@@YAHHH@Z` |

**两者不通用**，因此 MSVC 编译的目标文件与 GCC 编译的
**不能直接链接在一起**（C 语言的符号除外，因为不修饰）。

## 5.7 符号可见性

**ABI 还决定了哪些符号能被其他目标文件看到。**

| 存储类 | 链接属性 | `nm` 中的大小写 |
|---|---|---|
| 默认（无 `static`） | **外部链接**，全局可见 | 大写 |
| `static` | **内部链接**，只在本文件可见 | **小写** |

**实测对照见第 6 章**，那里给出了完整的 `nm` 输出。

## 5.8 ABI 不一致会发生什么

**最麻烦的是「能编过、能链接、但运行结果错」。**

| 不一致的方面 | 后果 |
|---|---|
| 数据模型不同 | 数值截断或越界读 |
| 调用约定不同 | **参数错位，结果完全错乱** |
| 结构体布局不同 | 读到别的成员 |
| 名字修饰不同 | **链接失败**（能发现，反而好办） |
| 对齐规则不同 | 访问越界或性能下降 |

**前四项的共同点**：编译器不会报错，因为它只看自己这一侧。

**实际会遇到的场景**：

| 场景 | 说明 |
|---|---|
| 混用两套工具链编出的库 | 例如 MinGW 编的 `.a` 配 MSVC 编的程序 |
| 跨平台传二进制数据 | 结构体直接 `memcpy` 到网络或文件 |
| 编译器大版本升级 | 极少见，但某些平台改过 ABI |

**对策**：

| 做法 | 说明 |
|---|---|
| 跨模块接口只传基本类型与指针 | 不传结构体本体 |
| 用固定宽度类型 | `int32_t` 等 |
| 结构体布局用 `static_assert` 锁定 | 布局变了会编译失败 |
| 二进制接口用 `extern "C"` | 避开名字修饰差异 |

# 第 6 章 `extern` 关键字

## 6.1 它管的是链接，不是存储

**初学者常把 `extern` 理解成「声明一个外部变量」，
这只说对了一半。**

**准确的表述**：`extern` 指定**链接属性（linkage）**，
并说明「这是一个声明，不是定义」。

**两个作用要分开看**：

| 作用 | 说明 |
|---|---|
| **指定外部链接** | 这个名字在整个程序里只有一个，可以被别的文件引用 |
| **表示只声明** | 不分配存储空间，不生成代码 |

**下文先讲第一个，再讲第二个。**

## 6.2 `extern` 与 `static` 的对照

**C 与 C++ 有三个层次的链接属性**：

| 属性 | 写法 | 可见范围 |
|---|---|---|
| **外部链接** | 默认，或显式 `extern` | 整个程序（所有目标文件） |
| **内部链接** | `static` | 只在当前源文件 |
| **无链接** | 局部变量 | 只在当前块 |

**实测**：下面这个文件编译后用 `nm` 看符号。

```c
int global_default;              /* 默认：外部链接 */
extern int global_extern;        /* extern：外部链接 */
int global_extern = 1;           /* 这一行才是定义 */
static int global_static;        /* static：内部链接 */
const int global_const = 2;      /* C 中 const 默认仍是外部链接 */

int func_default(void) { return 0; }
extern int func_extern(void) { return 1; }
static int func_static(void) { return 2; }

extern int only_declared(void);  /* 只声明，没有定义 */

int use_all(void) { /* 调用上面这些 */ }
```

**`nm` 输出**（**实测**）：

```
0000000000000000 T func_default        ← 大写 T：外部链接的函数
000000000000000b T func_extern         ← 大写 T
0000000000000016 t func_static         ← 小写 t：内部链接
0000000000000000 R global_const        ← 大写 R：外部链接的只读数据
0000000000000000 B global_default      ← 大写 B：未初始化的全局
0000000000000000 D global_extern       ← 大写 D：已初始化的全局
0000000000000004 b global_static       ← 小写 b：内部链接
                 U only_declared       ← U：只声明，本文件没有定义
0000000000000021 T use_all
```

**读法很直接**：

| 字母 | 含义 |
|---|---|
| **大写** | **外部链接**，别的文件能看到 |
| **小写** | **内部链接**，只有本文件能看到 |
| `U` | 未定义，本文件引用了别处的符号 |

**这就是 `extern` 最核心的效果**：
**它保证这个名字在链接时是全局唯一的。**

## 6.3 声明与定义的区别

**这是 `extern` 的第二个作用，也是最容易出错的地方。**

| 写法 | 是声明还是定义 | 是否分配空间 |
|---|---|---|
| `extern int x;` | **声明** | **否** |
| `int x;` | **定义**（C 中的暂定义） | 是 |
| `int x = 1;` | 定义 | 是 |
| `extern int x = 1;` | **定义**（有初始化就是定义） | 是 |

**最后一行值得记住**：**只要带了初始化，`extern` 也拦不住它是定义。**

**为什么需要区分**：

```
   a.c:  int shared = 42;        ← 定义，分配空间
   b.c:  extern int shared;      ← 声明，告诉编译器「别处有一个」
```

**两个文件编译成两个目标文件，链接器把它们接起来。**

**实测**：`a.c` 定义 `shared` 与 `get()`，`b.c` 用 `extern` 声明后引用：

```
输出: 42 42
```

**如果 `b.c` 写成 `int shared;` 而不是 `extern int shared;`**：
在 C 里这是「暂定义」，可能被合并；**在 C++ 里这是两个定义，
链接时直接报重复符号。**

**所以头文件里声明全局变量时，必须写 `extern`。**

```c
/* mylib.h */
extern int shared;        /* 声明：所有包含它的文件共享同一个 */
```

**如果漏了 `extern`**：每个包含该头文件的 `.c` 都会定义一个 `shared`，
链接时报 `multiple definition`。

## 6.4 `const` 在 C 与 C++ 中的差异

**这是 C 与 C++ 的一处实质区别，而且与 `extern` 直接相关。**

**实测**：同一句话在两种语言里的符号。

```cpp
const int global_const = 2;                  /* C++：默认内部链接 */
extern const int global_const_extern = 3;    /* 显式 extern：外部链接 */
```

**`nm` 输出**（**实测**）：

```
0000000000000000 r _ZL12global_const        ← L 表示 local，内部链接
0000000000000004 R global_const_extern      ← 外部链接
```

**对照表**：

| 语言 | `const int x = 2;` 的链接属性 |
|---|---|
| **C** | **外部链接**（`nm` 显示大写 `R`） |
| **C++** | **内部链接**（`nm` 显示小写 `r`，名字还被修饰成 `_ZL...`） |

**为什么 C++ 这样设计**：
`const` 在 C++ 里常用来定义头文件中的常量
（如 `const int MAX = 100;`）。
若默认外部链接，**每个包含该头文件的源文件都定义一个 `MAX`，
链接时必然冲突**。
**默认内部链接就解决了这个问题**——每个文件各有一份，互不干扰。

**代价是**：若真想让所有文件共享**同一个** `const` 对象
（例如取它的地址做比较），**必须显式加 `extern`**。

**这条差异是《00-写在最初/01-C与C++.md》第 2.3.4 节
「能编过但行为不同」的一例。**

## 6.5 `extern "C"`：语言链接

**前面几节讲的是「链接属性」，`extern "C"` 讲的是「语言链接」。**

**这是两个不同的维度**：

| 写法 | 管什么 |
|---|---|
| `extern int x;` | **链接属性**：外部链接 |
| `extern "C" { ... }` | **语言链接**：用 C 的规则生成符号名 |

**`extern "C"` 的确切效果**：**关掉名字修饰**，
让 C++ 编出的符号名与 C 一致。

**实测对照**（**实测**，见第 4.2 节）：

| 写法 | 符号名 |
|---|---|
| `int add(int, int)`（C++） | `_Z3addii` |
| `extern "C" int add(int, int)` | **`add`** |
| `int add(int, int)`（C 语言） | `add` |

**它不改变函数的调用方式，也不改变参数的传递规则**——
只改符号名。

**因此 `extern "C"` 的典型用途有三个**：

| 用途 | 说明 |
|---|---|
| **C++ 调用 C 库** | 头文件里包一层，让链接器能按 C 的名字找到 |
| **C 调用 C++ 写的库** | 库的作者主动导出 C 接口 |
| **动态库导出** | 让 `dlsym` / `GetProcAddress` 能按名字查到 |

**第三种在插件架构里最常见**，见《01-编译器/03-嵌入式与交叉编译.md》第 7 章
与 `A-教学素材/03-跨平台与编码/plugin_loader.cpp`。

## 6.6 头文件的标准写法

**一个给 C 写的库，头文件必须写成两种语言都能用**：

```c
/* mylib.h */
#ifndef MYLIB_H
#define MYLIB_H

#ifdef __cplusplus
extern "C" {
#endif

extern int shared;                  /* 变量声明也要 extern */
int add(int a, int b);
void process(const char *input);

#ifdef __cplusplus
}
#endif

#endif
```

**逐部分读**：

| 部分 | 作用 |
|---|---|
| `#ifdef __cplusplus` | 只在 C++ 编译时成立（C 编译器不定义这个宏） |
| `extern "C" {` ... `}` | 把这些声明标记为「用 C 的符号名」 |
| 对 C 编译器 | 整个块被跳过，看到的还是普通声明 |
| `extern int shared;` | **变量声明必须带 `extern`**，否则每个包含者都定义一份 |

**实测例证**：`A-教学素材/10-寄存器与位运算/gpio.h` 就是这种结构，
可以打开对照。

## 6.7 常见误用

| 写法 | 问题 | 正确做法 |
|---|---|---|
| 头文件里写 `int shared;` | 每个包含者都定义一份，链接冲突 | `extern int shared;` |
| 在 `.c` 里写 `extern int x = 1;` | 带了初始化，这仍是定义 | 想要定义就直接写 `int x = 1;` |
| 以为 `extern` 会分配空间 | 它不分配 | 定义处才分配 |
| 用 `extern "C"` 包整个 C++ 头文件 | 重载、模板、命名空间无法导出 | 只包需要 C 接口的部分 |
| 以为 `static` 能让函数「更快」 | 它改的是链接属性，与速度无关 | 想内联就交给编译器 |
| C++ 里指望 `const` 全局变量共享 | 默认内部链接，各文件一份 | 显式 `extern const` |

**最后一条要特别注意**：若在头文件里写

```cpp
const int MAX = 100;        // C++：每个文件各有一份
```

**在某个文件里取 `&MAX`，与另一个文件里的 `&MAX` 不是同一个地址。**
若程序依赖这一点（例如把地址当键），行为就会出问题。

# 第 7 章 排查与对策

## 7.1 遇到「换个编译器就出错」怎么查

| 步骤 | 做什么 |
|---|---|
| 1 | 看报错是**编译错误**还是**链接错误** |
| 2 | 编译错误：查是不是用了某个实现的扩展 |
| 3 | 链接错误：查是不是丢了 `extern "C"` |
| 4 | 能编过但行为不同：查类型宽度、对齐、求值顺序 |
| 5 | 打开全部警告（`-Wall -Wextra` 或 `/W4`） |
| 6 | 用 `-fsanitize=undefined` 检查未定义行为（GCC/Clang） |

**第 4 步最难，因为没有任何提示。**
**对策是尽量不要依赖实现的选择**，见第 7.2 节。

## 7.2 写可移植代码的几条做法

| 做法 | 替代 |
|---|---|
| 用 `<stdint.h>` 的 `int32_t` / `int64_t` | 不用 `int` / `long` 表示确定宽度 |
| 用 `sizeof` 计算，而不是写死数字 | 不写 `malloc(4 * n)` |
| 用 `size_t` 表示长度与下标 | 不用 `int` 装数组长度 |
| 用 `extern "C"` 导出 C 接口 | 不指望 C++ 符号名能被 C 找到 |
| 用宏区分编译器的扩展 | 不直接写 `__attribute__` |
| 打开并读完所有警告 | 不忽略「只是警告」 |

## 7.3 与调试的关系

**「实现定义」这件事在调试时也会遇到**：

| 现象 | 原因 |
|---|---|
| 换编译器后断点绑不上 | 调试信息格式不同（DWARF 与 PDB） |
| 换平台后 `long` 显示的值不对 | 宽度不同，调试器按本平台解释 |
| C++ 函数在符号表里名字很怪 | 名字修饰，见第 4.2 节 |

**第二条尤其值得注意**：调试器按**本平台**的类型规则解释内存，
**跨平台调试时看到的类型可能与源平台不同。**

> **跨系统调试的完整说明见《02-调试器/02-跨系统调试.md》。**

## B.2 `extern` 与 `static` 的链接属性

```c
int global_default;              /* 默认：外部链接 */
extern int global_extern;        /* extern：外部链接 */
int global_extern = 1;           /* 定义 */
static int global_static;        /* static：内部链接 */
const int global_const = 2;      /* C 中 const 默认外部链接 */

int func_default(void) { return 0; }
extern int func_extern(void) { return 1; }
static int func_static(void) { return 2; }
extern int only_declared(void);  /* 只声明 */
```

```bash
gcc -std=c17 -c linkage.c -o linkage.o
nm linkage.o
```

**看字母大小写**：大写为外部链接，小写为内部链接，`U` 为未定义。

**C++ 的 `const` 对照**：

```cpp
const int global_const = 2;                  /* 内部链接，符号带 L */
extern const int global_const_extern = 3;    /* 外部链接 */
```

```bash
g++ -c linkage.cpp -o linkage_cpp.o
nm linkage_cpp.o | grep global_const
```

## B.4 结构体布局与填充

```c
#include <stdio.h>
#include <stddef.h>

struct A { char c; int i; };
struct B { int i; char c; };
struct C { char a; char b; char c; };

int main(void) {
    printf("A: sizeof=%d  c@%d  i@%d\n", (int)sizeof(struct A),
           (int)offsetof(struct A, c), (int)offsetof(struct A, i));
    printf("B: sizeof=%d  i@%d  c@%d\n", (int)sizeof(struct B),
           (int)offsetof(struct B, i), (int)offsetof(struct B, c));
    printf("C: sizeof=%d\n", (int)sizeof(struct C));
    return 0;
}
```

**用 `offsetof` 让编译器算偏移，不要自己数。**
