# 第 1 节 标准与实现是两回事

## 1.1 标准不能运行程序

**语言的标准（standard）规定「什么代码是合法的、应该有什么行为」，
但它本身不能运行任何程序。**

真正把代码变成可执行文件的是**编译器**——
编译器就是标准的一个**实现（implementation）**。

`Text`

```text
   C 语言标准（ISO/IEC 9899）
        │
        │  由不同的组织各自实现
        ├──────────────┬──────────────┬──────────────┐
        ▼              ▼              ▼              ▼
      GCC           Clang           MSVC      其他编译器
   （GNU）        （LLVM）        （微软）
```

**这几个都是 C 语言的实现**，都遵循同一份标准，
**但在标准未规定的地方可以自由选择。**

## 1.2 同类概念还有哪些

| 层次 | 标准 | 主要实现 |
|---|---|---|
| C 语言 | ISO/IEC 9899（C17、C23） | GCC、Clang、MSVC |
| C++ 语言 | ISO/IEC 14882（C++17、C++20） | GCC、Clang、MSVC |
| 可执行文件格式 | PE/COFF（Windows）、ELF（Linux） | 各系统自己的加载器 |
| 调试信息格式 | DWARF 是公开标准；PDB 是微软的 | GCC 产 DWARF、MSVC 产 PDB |
| 构建系统 | 无统一标准 | CMake 是事实标准 |

**「调试信息格式」与「构建系统」也是同一类东西**：
它们同样有标准与实现之分。
**这解释了本教材为什么用大量篇幅讲工具之间的配套关系。**

**调试信息格式必须与调试器匹配**，
见《01-编译器/02-环境配置.md》第 1.1 小节。

## 1.3 一个容易混淆的地方

**「实现」有两个不同的含义，要看语境。**

| 语境 | 含义 | 例子 |
|---|---|---|
| **语言的实现** | 编译器这个程序 | 「GCC 是 C 语言的一种实现」 |
| **代码的实现** | 某个函数的具体做法 | 「`printf` 的实现不在这个文件里」 |

**本章节讲的是第一种。**

**第二种含义在阅读代码时很常见**：注释说「不会 delete 旧对象」，
而函数的实现里 `new` 了一个新对象。

**遇到「实现」这个词，先看它修饰的是什么。**

# 第 2 节 为什么这件事重要

## 2.1 五类可见的差异

| 差异 | 说明 |
|---|---|
| **命令行参数不同** | `-O2` 与 `/O2` 是两套写法 |
| **扩展语法不同** | GCC 有 `__attribute__`，MSVC 有 `__declspec` |
| **调试信息格式不同** | GCC 产 DWARF，MSVC 产 PDB |
| **默认行为不同** | 比如 `char` 是否有符号、`long` 有多宽 |
| **符号命名不同** | C++ 会对函数名做修饰，C 不做 |

**第一类与第三类在《01-编译器/02-环境配置.md》有详细对照**，
第二类在《01-编译器/03-嵌入式与交叉编译.md》中用到。

## 2.2 一个常见现象的解释

`Text`

```text
   同一份代码，在 A 编译器上正常，换到 B 编译器就出错
   →  多半是碰到了「标准未规定、由实现决定」的地方
```

**这个结论同时给出了排查方向**：
不要先怀疑编译器有 bug，
**先确认代码有没有依赖标准未规定的行为**。

## 2.3 与「可移植性」的关系

**可移植性不是「代码能编过」，而是「代码不依赖实现的选择」。**

| 代码写法 | 可移植性 |
|---|---|
| 用 `int32_t` 而不是 `int` | 好，宽度确定 |
| 假设 `char` 无符号 | 差 |
| 假设 `long` 是 4 字节 | **差**，见第 4.1 小节 |
| 用 `sizeof(void*)` 判断指针宽度 | 好 |
| 依赖函数参数的求值顺序 | 差 |

**教材后续各章节凡涉及具体字节数的地方，都标注了实测环境**，
原因就在这里。

# 第 3 节 标准里的三类「自由度」

**C 与 C++ 标准对行为的描述分三档**，
差别在于标准对实现提出了什么要求。

## 3.1 三档对照

| 类别 | 英文 | 标准的要求 | 能否预测结果 | 例子 |
|---|---|---|---|---|
| **未定义行为** | Undefined behavior | **不作任何要求**，什么事都可能发生 | **不能** | 数组越界、有符号整数溢出、解引用空指针 |
| **实现定义行为** | Implementation-defined | 要求**选定一种并写进文档**，但不规定选哪种 | 能，但要查该实现的文档 | `char` 是否有符号、`long` 的宽度 |
| **未指定行为** | Unspecified | 给出**若干可能**，不规定用哪个，也不要求写文档 | 不能，但每种结果都合法 | 函数参数的求值顺序 |

**三者的危险程度依次递减**：
未定义行为最高，实现定义行为居中，未指定行为最低。

**「实现定义行为」是可以查的**——
每种编译器都会在与标准配套的文档里写明自己选了什么。
**「未定义行为」无文档可查，因为标准不要求。**

## 3.2 为什么未定义行为最危险

**编译器可以假设未定义行为不会发生，并据此做优化。**

`C`

```c
int f(int x) {
    return x + 1 > x;
}
```

**编译器可以把它直接变成 `return 1;`**，
理由是「有符号溢出是未定义行为，因此 `x + 1` 不会溢出」。
但若调用方传入 `INT_MAX`，实际行为与直觉不符。

**这一类问题的特点是：能编过，行为不确定。**

> [!CAUTION]
> **不要写依赖有符号溢出的代码。**
> 编译器有权假定它不会发生，并据此删掉这类判断。

**完整说明见《03-构建工具链/05-优化等级.md》第 5.5 小节。**

## 3.3 三档在代码里的样子

`C`

```c
/* 未定义行为：越界写入，后果不可预测 */
int a[10];
a[15] = 1;

/* 实现定义行为：char 是否有符号由实现决定 */
char c = 200;                  /* 若 char 有符号，这里已经溢出 */

/* 未指定行为：两个参数谁先求值不确定 */
f(g(), h());
```

**第一类必须改，第二类要么改要么查文档，第三类通常可以不管。**

# 第 4 节 自由度在实际中的表现

## 4.1 同一个 `long`，两种宽度

**同一份代码，在两种平台的三套实现下运行，得到的宽度如下。**

`实测数据`

| 项目 | MinGW gcc 15.2.0 | MSVC 19.51 | Linux gcc 13.3.0 |
|---|---|---|---|
| 平台 | Windows x64 | Windows x64 | Linux x86-64 |
| `sizeof(int)` | 4 | 4 | 4 |
| **`sizeof(long)`** | **4** | **4** | **8** |
| `sizeof(long long)` | 8 | 8 | 8 |
| `sizeof(void *)` | 8 | 8 | 8 |
| `char` 是否有符号 | 有符号 | 有符号 | 有符号 |

**宽度项里只有 `sizeof(long)` 一行不同。**
`CHAR_MIN`、`INT_MAX`、`-8 >> 1` 在三套实现上也完全一致，
**完整的宽度清单与探针源码见附录 B.1。**

`Text`

```text
   Windows x64   4 字节    （叫 LLP64 模型）
   Linux x86-64  8 字节    （叫 LP64 模型）
```

**两个 Windows 实现（gcc 与 MSVC）在这一项上完全一致**，
说明差异不来自编译器品牌；
**同样用 gcc，Windows 与 Linux 不一致**，
说明差异来自**目标平台的 ABI**；
而 `int` 两边都是 4，说明并非所有类型都不确定。

**ABI（应用二进制接口）规定了类型宽度、结构体对齐、
参数传递方式等一整套约定。**
**同一份源码为目标平台编译，就要遵守该平台的 ABI。**

**实际后果**：`long` 能表示的数值范围随平台变化。

`C`

```c
/* 在 Windows 上会截断，在 Linux 上正常 */
long file_size = get_file_size();     /* 假设 long 能装下大于 4 GB 的值 */
printf("%ld\n", file_size);           /* 格式符也要跟着改 */

/* 可移植的写法：用固定宽度类型 */
#include <stdint.h>
int64_t file_size = get_file_size();
printf("%" PRId64 "\n", file_size);
```

**教材中凡出现 `long`，都应注意这一点。**
需要确定宽度时用 `<stdint.h>` 的 `int32_t` / `int64_t`。

## 4.2 函数名的符号修饰

**C++ 支持函数重载，因此要对函数名做修饰（name mangling）**，
把参数类型编码进符号名。

`C++`

```cpp
// mangle.cpp    编译：g++ -c mangle.cpp -o mangle.o，再用 nm mangle.o 看符号
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }
namespace ns { int f(int) { return 0; } }
```

`C`

```c
/* mangle.c    编译：gcc -c mangle.c -o mangle_c.o */
/* 函数体写法与 C++ 相同，符号名不同 */
int add(int a, int b) { return a + b; }
```

`实测数据`
`Text`

```text
# C++（g++ -c mangle.cpp）
_Z3addii        ← add(int, int)
_Z3adddd        ← add(double, double)
_ZN2ns1fEi      ← ns::f(int)

# C（gcc -c mangle.c）
add             ← 完全没有修饰
```

**读法**：

| 部分 | 含义 |
|---|---|
| `_Z` | 修饰名的起始标记 |
| `3add` | 名字长度 3，名字是 `add` |
| `ii` / `dd` | 参数类型：两个 `int` / 两个 `double` |
| `N2ns1fEi` | `N` 开始嵌套名，`2ns` 是命名空间，`1f` 是函数名，`E` 结束，`i` 是参数 |

**这解释了一个实际问题**：C 编译器按 `add` 去找符号，
而 C++ 编译出的符号叫 `_Z3addii`，
**链接失败，报 `undefined reference to 'add'`**。

**解决办法是 `extern "C"`**：

`C++`

```cpp
// extc.cpp    编译：g++ -c extc.cpp -o extc.o
extern "C" int add(int a, int b) { return a + b; }
```

`实测数据`
`Text`

```text
add             ← 与 C 完全一致
```

**这就是所有 C 库被 C++ 调用时都要包一层 `extern "C"` 的原因。**

**头文件该怎么写，见《00-写在最初/01-C与C++.md》第 2.4.3 小节。**

## 4.3 命令行参数与扩展

| 功能 | GCC | MSVC |
|---|---|---|
| 优化二级 | `-O2` | `/O2` |
| 生成调试信息 | `-g` | `/Zi` |
| 警告全开 | `-Wall -Wextra` | `/W4` |
| 指定标准 | `-std=c17` | `/std:c17` |
| 导出符号 | `__attribute__((visibility("default")))` | `__declspec(dllexport)` |
| 禁止内联 | `__attribute__((noinline))` | `__declspec(noinline)` |

**最后两行是「扩展」**：标准里没有这些语法，
但两种实现各自加了功能相近的写法。

**这导致一个常见做法——用宏把两者包起来**：

`C`

```c
#if defined(_MSC_VER)
#  define NOINLINE __declspec(noinline)
#else
#  define NOINLINE __attribute__((noinline))
#endif
```

**本教材示例中用到了这个写法**，
见《03-构建工具链/05-优化等级.md》附录 B 的探针代码。

**`_MSC_VER` 是 MSVC 定义的宏**；GCC 定义 `__GNUC__`，Clang 定义 `__clang__`。
靠这些宏可以在源码里区分当前是哪个实现。

# 第 5 节 ABI：二进制层面的约定

## 5.1 它是什么

**ABI 是 Application Binary Interface（应用二进制接口）的缩写。**

标准管的是**源码层面**——什么代码合法、应该有什么行为。
**ABI 管的是二进制层面**——编译出来的东西如何与外界对接。

| 层面 | 管什么 | 由谁规定 |
|---|---|---|
| 语言标准 | 语法、语义、哪些行为未定义 | ISO |
| **ABI** | **类型宽度、结构体布局、参数怎么传、符号怎么命名** | **平台与工具链** |

**两者的关系可以这样理解**：

`Text`

```text
   标准说：这个函数有两个 int 参数
   ABI  说：第一个放 rcx，第二个放 rdx
```

**标准不关心参数放在哪，ABI 必须明确**——
否则两个分别编译的目标文件无法链接在一起。

## 5.2 ABI 包含哪些内容

| 内容 | 说明 | 在哪一小节 |
|---|---|---|
| 数据模型 | 各种类型的宽度 | 第 4.1、5.3 小节 |
| 调用约定 | 参数放哪、返回值放哪、谁清理栈 | 第 5.4 小节 |
| 结构体布局 | 成员顺序、对齐、填充 | 第 5.5 小节 |
| 名字修饰 | 符号在目标文件里长什么样 | 第 5.6 小节 |
| 符号可见性 | 哪些符号对链接器可见 | 第 5.7 小节 |

**本章节第 1.2 小节提到的「可执行文件格式」与「调试信息格式」
也属于同一类约定**——它们是平台层面的、标准不管的、
但所有工具必须一致的部分。

## 5.3 数据模型

**数据模型规定了各种类型的宽度，其中最常出现差异的一项是 `long`。**

`实测数据`

| 模型 | `short` | `int` | `long` | `long long` | 指针 | 用在 |
|---|---|---|---|---|---|---|
| **LLP64** | 2 | 4 | **4** | 8 | 8 | Windows |
| **LP64** | 2 | 4 | **8** | 8 | 8 | Linux、macOS |

**两行只差 `long` 一列**，其余完全相同。

### 名字怎么读

**数据模型的名字列出的是「哪些类型是 64 位的」**，
字母含义固定：`I` 是 `int`，`L` 是 `long`，`LL` 是 `long long`，
`P` 是指针（pointer），末尾数字是该模型里最宽的那一档位数。

| 模型 | 拆解 | 意思是 |
|---|---|---|
| **LP64** | `L` + `P` + `64` | **`long` 与指针是 64 位** |
| **LLP64** | `LL` + `P` + `64` | **`long long` 与指针是 64 位**，`long` 仍是 32 位 |
| ILP32 | `I` + `L` + `P` + `32` | `int`、`long`、指针都是 32 位（32 位平台） |

**关键在 `LLP64` 里那两个 `L`：它是 `long long` 的缩写，
不是「两个 long」。**

**容易记反的地方**：看到 `LLP64` 有两个 `L`，容易以为「long 是 64 位」。
**实际相反**——正因为 `long` 在 Windows 上不是 64 位，
名字里才要写成 `long long` 来指出真正是 64 位的那一个。

**这正是 Windows 与 Linux 的差别所在**：
`LLP64` 里的 `long` 只有 4 字节，装不下 64 位的值。

**记法**：**Windows 的 `long` 与 `int` 一样宽，Linux 的 `long` 与指针一样宽。**

**实际影响**：跨平台代码里凡用 `long` 装大数或指针差值的地方都要改，
**替换写法见第 4.1 小节。**

## 5.4 调用约定

**调用约定规定了「函数调用的两端如何对接」**——
这是 ABI 里最容易被忽略、但一旦不一致就立刻出错的部分。

`C`

```c
/* call.c    编译：gcc -std=c17 -O0 -c call.c -o call.o
              C 与 C++ 的调用约定相同，写法也相同
              再用 objdump -d --no-show-raw-insn call.o 看 add6 的开头 */
long long add6(long long a, long long b, long long c,
               long long d, long long e, long long f) {
    return a + b + c + d + e + f;
}
```

**Windows x64 下，前四个参数从寄存器取出，第五个开始来自栈**：

`实测数据`
`Assembly`

```asm
mov    %rcx,0x10(%rbp)      ← 第 1 个参数
mov    %rdx,0x18(%rbp)      ← 第 2 个参数
mov    %r8,0x20(%rbp)       ← 第 3 个参数
mov    %r9,0x28(%rbp)       ← 第 4 个参数
...
mov    0x30(%rbp),%rax      ← 第 5 个参数，来自栈
```

**换成 Linux x86-64，规则就不一样**：

| 平台 | 前几个整型参数放哪 |
|---|---|
| **Windows x64** | `rcx` `rdx` `r8` `r9`（四个） |
| **Linux x86-64** | `rdi` `rsi` `rdx` `rcx` `r8` `r9`（六个） |

**这就是为什么同一个 `.obj` 不能跨平台使用**——
即使机器指令相同，参数放的地方也不一样。

## 5.5 结构体布局与填充

**ABI 规定了对齐规则，编译器据此插入填充字节。**
**这解释了「为什么结构体的大小不等于成员大小之和」。**

`实测数据`
`C`

```c
/* layout.c    编译：gcc -std=c23 layout.c -o layout && ./layout
               C 与 C++ 写法相同，<stddef.h> 与 offsetof 两边都能用 */
#include <stdio.h>
#include <stddef.h>

struct A { char c; int i; };            /* c 之后要补 3 字节 */
struct B { int i; char c; };            /* c 之后要补 3 字节尾部填充 */
struct C { char a; char b; char c; };   /* 三个 char，不需要填充 */

int main(void) {
    /* offsetof 由编译器算，不要自己数 */
    printf("A: sizeof=%d c@%d i@%d\n", (int)sizeof(struct A),
           (int)offsetof(struct A, c), (int)offsetof(struct A, i));
    printf("B: sizeof=%d i@%d c@%d\n", (int)sizeof(struct B),
           (int)offsetof(struct B, i), (int)offsetof(struct B, c));
    printf("C: sizeof=%d\n", (int)sizeof(struct C));
    return 0;
}
```

| 结构体 | `sizeof` | 成员偏移 | 填充在哪 |
|---|---|---|---|
| `A` | **8** | `c` 在 0，`i` 在 4 | `c` 之后 3 字节 |
| `B` | **8** | `i` 在 0，`c` 在 4 | `c` 之后 3 字节尾部填充 |
| `C` | **3** | `a` 在 0，`b` 在 1，`c` 在 2 | 无 |

**`A` 与 `B` 的成员完全相同，只是顺序不同，大小都是 8，内部布局却不同**：
`A` 的 `int` 要求 4 字节对齐，`char c` 之后必须空出 3 字节；
`B` 的 `int` 在开头，尾部补 3 字节。
`C` 的三个 `char` 各需 1 字节对齐，大小就是 3。

**工程含义**：

| 做法 | 理由 |
|---|---|
| **不要按成员逐个序列化结构体** | 填充字节的内容未定义 |
| 需要精确布局时用 `#pragma pack` | 但会降低访问速度 |
| 跨平台传数据用文本或明确的字节序 | 见《01-编译器/03-嵌入式与交叉编译.md》第 4 节 |
| 用 `offsetof` 而不是手算偏移 | 布局随 ABI 变化，手算的数字会失效 |

**关于 `#pragma pack` 的对照数据，原《语言与案例》一章中有一节专门讲它，
该章已移出主线，待重建。**

## 5.6 名字修饰

**ABI 还规定了符号在目标文件里叫什么名字。**
C 不做修饰，函数名本身就能唯一标识一个函数；
C++ 支持重载，必须把参数类型编码进符号名。
**完整对照见第 4.2 小节。**

**这里要补充的是：名字修饰是 ABI 的一部分，不是语言标准的一部分。**

**证据是同一组规则在不同实现下并不通用**：
`int add(int, int)` 在 GCC 与 Clang 下是 `_Z3addii`，
在 MSVC 下是 `?add@@YAHHH@Z`。

**两者互不通用**，因此 MSVC 编译的目标文件与 GCC 编译的目标文件
**不能直接链接在一起**（C 语言的符号除外，因为不修饰）。

## 5.7 符号可见性

**ABI 还决定了哪些符号能被其他目标文件看到。**

| 存储类 | 链接属性 | `nm` 中的大小写 |
|---|---|---|
| 默认（无 `static`） | **外部链接**，全局可见 | 大写 |
| `static` | **内部链接**，只在本文件可见 | **小写** |

**对照见第 6.2 小节**，那里给出了完整的 `nm` 输出。

## 5.8 ABI 不一致会发生什么

**最麻烦的是「能编过、能链接、但运行结果错」。**

| 不一致的方面 | 后果 |
|---|---|
| 数据模型不同 | 数值截断或越界读 |
| 调用约定不同 | **参数错位，结果完全错乱** |
| 结构体布局不同 | 读到别的成员 |
| 名字修饰不同 | **链接失败**（能发现，反而好办） |
| 对齐规则不同 | 访问越界或性能下降 |

**前四项的共同点**：编译器不会报错，因为它只看自己这一侧。

**实际会遇到的场景有三类**：混用两套工具链编出的库
（例如 MinGW 编的 `.a` 配 MSVC 编的程序）；
跨平台传二进制数据（结构体直接 `memcpy` 到网络或文件）；
编译器大版本升级（极少见，但某些平台改过 ABI）。

**对策**：

| 做法 | 说明 |
|---|---|
| 跨模块接口只传基本类型与指针 | 不传结构体本体 |
| 用固定宽度类型 | `int32_t` 等 |
| 结构体布局用 `static_assert` 锁定 | 布局变了会编译失败 |
| 二进制接口用 `extern "C"` | 避开名字修饰差异 |

**还有一条与堆有关**：

`待确认`

> **跨模块传递由 `new` 分配的对象时，分配与释放要落在同一个运行时里。**
> 插件与宿主如果各自静态链接了运行库，两侧就是两个堆，
> 在宿主里 `delete` 插件 `new` 出来的对象会出问题。
> 这一条取决于运行库的链接方式（MSVC 的 `/MT` 与 `/MD`），本教材尚未实测。

# 第 6 节 `extern` 关键字

## 6.1 它管的是链接，不是存储

**把 `extern` 理解成「声明一个外部变量」，只说对了一半。**

**准确的表述**：`extern` 指定**链接属性（linkage）**，
并说明「这是一个声明，不是定义」。

**两个作用要分开看**：

| 作用 | 说明 |
|---|---|
| **指定外部链接** | 这个名字在整个程序里只有一个，可以被别的文件引用 |
| **表示只声明** | 不分配存储空间，不生成代码 |

## 6.2 `extern` 与 `static` 的对照

**C 与 C++ 有三个层次的链接属性**：

| 属性 | 写法 | 可见范围 |
|---|---|---|
| **外部链接** | 默认，或显式 `extern` | 整个程序（所有目标文件） |
| **内部链接** | `static` | 只在当前源文件 |
| **无链接** | 局部变量 | 只在当前块 |

`实测数据`
`C`

```c
/* linkage.c    编译：gcc -std=c17 -c linkage.c -o linkage.o
                 再用 nm linkage.o 看符号 */
int global_default;              /* 默认：外部链接 */
extern int global_extern;        /* extern：外部链接 */
int global_extern = 1;           /* 这一行才是定义 */
static int global_static;        /* static：内部链接 */
const int global_const = 2;      /* C 中 const 默认仍是外部链接 */

int func_default(void) { return 0; }
extern int func_extern(void) { return 1; }
static int func_static(void) { return 2; }

extern int only_declared(void);  /* 只声明，没有定义 */

int use_all(void) { return func_default(); }
```

`实测数据`
`Text`

```text
0000000000000000 T func_default        ← 大写 T：外部链接的函数
000000000000000b T func_extern         ← 大写 T
0000000000000016 t func_static         ← 小写 t：内部链接
0000000000000000 R global_const        ← 大写 R：外部链接的只读数据
0000000000000000 B global_default      ← 大写 B：未初始化的全局
0000000000000000 D global_extern       ← 大写 D：已初始化的全局
0000000000000004 b global_static       ← 小写 b：内部链接
                 U only_declared       ← U：只声明，本文件没有定义
0000000000000021 T use_all
```

**`nm` 的字母直接用大小写区分链接属性**：大写是外部链接，别的文件能看到；
小写是内部链接，只有本文件能看到；
`U` 表示未定义，本文件引用了别处的符号。

**这就是 `extern` 最核心的效果**：
**它保证这个名字在链接时是全局唯一的。**

## 6.3 声明与定义的区别

**这是 `extern` 的第二个作用，也是最容易出错的地方。**

| 写法 | 是声明还是定义 | 是否分配空间 |
|---|---|---|
| `extern int x;` | **声明** | **否** |
| `int x;` | **定义**（C 中的暂定义） | 是 |
| `int x = 1;` | 定义 | 是 |
| `extern int x = 1;` | **定义**（有初始化就是定义） | 是 |

**只要带了初始化，`extern` 也拦不住它是定义。**

**为什么需要区分**：

`Text`

```text
   a.c:  int shared = 42;        ← 定义，分配空间
   b.c:  extern int shared;      ← 声明，告诉编译器「别处有一个」
```

**两个文件编译成两个目标文件，链接器把它们接起来，
完整数据见附录 B.6。**

**如果 `b.c` 写成 `int shared;` 而不是 `extern int shared;`**：
在 C 里这是「暂定义」，可能被合并；**在 C++ 里这是两个定义，
链接时直接报重复符号。**

**所以头文件里声明全局变量时，必须写 `extern`。**

`C`

```c
/* mylib.h */
extern int shared;        /* 声明：所有包含它的文件共享同一个 */
```

**如果漏了 `extern`**：每个包含该头文件的 `.c` 都会定义一个 `shared`，
链接时报 `multiple definition`。

## 6.4 `const` 在 C 与 C++ 中的差异

**这是 C 与 C++ 的一处实质区别，与 `extern` 直接相关。**

`C`

```c
/* const_linkage.c    编译：gcc -c const_linkage.c -o const_linkage_c.o
                       再用 nm const_linkage_c.o 看符号 */
const int global_const = 2;      /* C：默认仍是外部链接 */
```

`C++`

```cpp
// const_linkage.cpp    编译：g++ -c const_linkage.cpp -o const_linkage_cpp.o
const int global_const = 2;                  /* C++：默认内部链接 */
extern const int global_const_extern = 3;    /* 显式 extern：外部链接 */
```

`实测数据`
`Text`

```text
# C（gcc -c const_linkage.c）
0000000000000000 R global_const             ← 大写 R：外部链接

# C++（g++ -c const_linkage.cpp）
0000000000000000 r _ZL12global_const        ← 小写 r，L 表示 local，内部链接
0000000000000004 R global_const_extern      ← 大写 R：外部链接
```

> [!IMPORTANT]
> **同一句 `const int x = 2;`，C 里是外部链接，C++ 里是内部链接。**
> C++ 下名字还被修饰成 `_ZL...`，其中的 `L` 表示 local。

**为什么 C++ 这样设计**：
`const` 在 C++ 里常用来定义头文件中的常量
（如 `const int MAX = 100;`）。
若默认外部链接，**每个包含该头文件的源文件都定义一个 `MAX`，
链接时必然冲突**。
**默认内部链接就解决了这个问题**——每个文件各有一份，互不干扰。

**代价是**：若真想让所有文件共享**同一个** `const` 对象
（例如取它的地址做比较），**必须显式加 `extern`**。

**这条差异是《00-写在最初/01-C与C++.md》第 2.3.4 小节
「能编过但行为不同」的一例。**

## 6.5 `extern "C"`：语言链接

**前面几节讲的是「链接属性」，`extern "C"` 讲的是「语言链接」。**

**这是两个不同的维度**：

| 写法 | 管什么 |
|---|---|
| `extern int x;` | **链接属性**：外部链接 |
| `extern "C" { ... }` | **语言链接**：用 C 的规则生成符号名 |

**`extern "C"` 的确切效果**：**关掉名字修饰**，
让 C++ 编出的符号名与 C 一致。
**符号名的对照见第 4.2 小节**：
`int add(int, int)` 在 C++ 里是 `_Z3addii`，
加上 `extern "C"` 之后是 `add`，与 C 编出来的一致。

**它不改变函数的调用方式，也不改变参数的传递规则**——
只改符号名。

**因此 `extern "C"` 的典型用途有三个**：

| 用途 | 说明 |
|---|---|
| **C++ 调用 C 库** | 头文件里包一层，让链接器能按 C 的名字找到 |
| **C 调用 C++ 写的库** | 库的作者主动导出 C 接口 |
| **动态库导出** | 让 `dlsym` / `GetProcAddress` 能按名字查到 |

**第三种在插件架构里最常见**，跨平台加载的代码见《02-调试器/02-跨系统调试.md》第 1.5 小节，
原文副本在 `A-教学素材/01-编译器/跨平台与编码/plugin_loader.cpp`。

**插件把「按名字取函数」用成了一套协议**。真实项目里的导出分成两层
（`modules/NeoCore/src/plugin_loader.cpp` 第 183 至 199 行，**下面是节选**）：

`C++`

```cpp
    void* handle = LOAD_LIBRARY(dllPath.c_str());
    if (!handle) return false;

    auto createFunc = reinterpret_cast<CreateParserFunc>(
        GET_PROC(handle, "CreateParser"));
    if (!createFunc) {
        FREE_LIBRARY(handle);
        return false;
    }

    // 插件日志注入 (可选): 插件导出 SetPluginLogSink 则注入宿主 sink,
    // 否则插件内 PluginLog 回退 CLogger (default_logger 跨模块)
    static LoggerLogSink pluginLogSink;
    if (auto setSink = reinterpret_cast<void (*)(ILogSink*)>(
            GET_PROC(handle, "SetPluginLogSink"))) {
        setSink(&pluginLogSink);
    }
```

| 导出函数 | 缺失时的处理 |
|---|---|
| 创建对象的工厂函数 `CreateParser`（必需） | 拒绝加载这个插件，并释放已经拿到的库句柄 |
| 注入日志接收器的 `SetPluginLogSink`（可选） | 退回默认行为，不当作错误 |

**按名字取回来的只是一个地址**，必须换成正确的函数指针类型才能调用。
`CreateParserFunc` 的类型别名写在 `modules/NeoCore/include/IConfigParser.h` 第 68 行：

`C++`

```cpp
using CreateParserFunc = IConfigParser* (*)();   /* 无参数，返回 IConfigParser* */
```

**类型写错不会有编译错误**：`reinterpret_cast` 到任何函数指针类型都合法，
两边对不上要到调用时才以「跳到错误的地址」的形式暴露出来。

**跨模块传递对象时还有一条约定**，见第 5.8 小节。

## 6.6 头文件的标准写法

**一个给 C 写的库，头文件必须写成两种语言都能用**：

`C`

```c
/* mylib.h */
#ifndef MYLIB_H
#define MYLIB_H

#ifdef __cplusplus
extern "C" {
#endif

extern int shared;                  /* 变量声明也要 extern */
int add(int a, int b);
void process(const char *input);

#ifdef __cplusplus
}
#endif

#endif
```

**`#ifdef __cplusplus` 只在 C++ 编译时成立**（C 编译器不定义这个宏），
因此 C 编译器会把整个 `extern "C" { }` 块跳过，看到的还是普通声明。
**`extern int shared;` 里的 `extern` 不能省**，否则每个包含者都定义一份。

**`A-教学素材/01-编译器/嵌入式/寄存器与位运算/gpio.h` 就是这种结构**，可以打开对照。

## 6.7 常见误用

| 写法 | 问题 | 正确做法 |
|---|---|---|
| 头文件里写 `int shared;` | 每个包含者都定义一份，链接冲突 | `extern int shared;` |
| 在 `.c` 里写 `extern int x = 1;` | 带了初始化，这仍是定义 | 想要定义就直接写 `int x = 1;` |
| 以为 `extern` 会分配空间 | 它不分配 | 定义处才分配 |
| 用 `extern "C"` 包整个 C++ 头文件 | 重载、模板、命名空间无法导出 | 只包需要 C 接口的部分 |
| 以为 `static` 能让函数「更快」 | 它改的是链接属性，与速度无关 | 想内联就交给编译器 |
| C++ 里指望 `const` 全局变量共享 | 默认内部链接，各文件一份 | 显式 `extern const` |

**在头文件里写 `const int MAX = 100;` 就会遇到这种情况**：

`C++`

```cpp
// max.h    随包含它的源文件一起编译
const int MAX = 100;        // C++：每个包含它的文件各有一份
```

**在某个文件里取 `&MAX`，与另一个文件里的 `&MAX` 不是同一个地址。**
若程序依赖这一点（例如把地址当键），行为就会出问题。

# 第 7 节 排查与对策

## 7.1 遇到「换个编译器就出错」怎么查

| 步骤 | 做什么 |
|---|---|
| 1 | 看报错是**编译错误**还是**链接错误** |
| 2 | 编译错误：查是不是用了某个实现的扩展 |
| 3 | 链接错误：查是不是丢了 `extern "C"` |
| 4 | 能编过但行为不同：查类型宽度、对齐、求值顺序 |
| 5 | 打开全部警告（`-Wall -Wextra` 或 `/W4`） |
| 6 | 用 `-fsanitize=undefined` 检查未定义行为（GCC/Clang） |

**第 4 步最难，因为没有任何提示。**
**对策是尽量不要依赖实现的选择**，见第 7.2 小节。

## 7.2 写可移植代码的几条做法

| 做法 | 替代 |
|---|---|
| 用 `<stdint.h>` 的 `int32_t` / `int64_t` | 不用 `int` / `long` 表示确定宽度 |
| 用 `sizeof` 计算，而不是写死数字 | 不写 `malloc(4 * n)` |
| 用 `size_t` 表示长度与下标 | 不用 `int` 装数组长度 |
| 用 `extern "C"` 导出 C 接口 | 不指望 C++ 符号名能被 C 找到 |
| 用宏区分编译器的扩展 | 不直接写 `__attribute__` |
| 打开并读完所有警告 | 不忽略「只是警告」 |

## 7.3 与调试的关系

**「实现定义」这件事在调试时也会遇到**：

| 现象 | 原因 |
|---|---|
| 换编译器后断点绑不上 | 调试信息格式不同（DWARF 与 PDB） |
| 换平台后 `long` 显示的值不对 | 宽度不同，调试器按本平台解释 |
| C++ 函数在符号表里名字很怪 | 名字修饰，见第 4.2 小节 |

**调试器按本平台的类型规则解释内存**，
**跨平台调试时看到的类型可能与源平台不同。**

**跨系统调试的完整说明见《02-调试器/02-跨系统调试.md》。**

# 第 8 节 术语表

| 术语 | 英文 | 含义 |
|---|---|---|
| 标准 | Standard | 规定语言语法与语义的规范性文件 |
| 实现 | Implementation | 标准的具体落实者，即编译器 |
| 未定义行为 | Undefined behavior | 标准不作要求，任何结果都可能 |
| 实现定义行为 | Implementation-defined behavior | 由具体实现选定，且必须写进文档 |
| 未指定行为 | Unspecified behavior | 标准给出若干可能，不规定用哪个 |
| **ABI** | Application Binary Interface | 类型宽度、对齐、调用约定、符号命名等二进制层面的约定 |
| 数据模型 | Data model | 规定各类型宽度的方案，如 LLP64 / LP64 |
| 调用约定 | Calling convention | 参数与返回值放在哪、由谁清理栈 |
| 对齐 | Alignment | 成员地址必须是其宽度的整数倍 |
| **填充** | Padding | 为满足对齐而插入的无意义字节 |
| **链接属性** | Linkage | 一个名字可否被其他目标文件看到 |
| **外部链接** | External linkage | 整个程序可见，`nm` 显示为大写 |
| **内部链接** | Internal linkage | 只在当前源文件可见，`nm` 显示为小写 |
| **声明** | Declaration | 告诉编译器「有这么个东西」，不分配空间 |
| **定义** | Definition | 真正分配空间或生成代码 |
| **`extern`** | — | 指定外部链接；用在变量上时表示「这是声明」 |
| LLP64 | — | Windows 的模型：**`long long` 与指针**是 64 位，`long` 只有 4 字节 |
| LP64 | — | Linux/macOS 的模型：**`long` 与指针**是 64 位 |
| 名字修饰 | Name mangling | C++ 把参数类型编码进符号名的机制 |
| `extern "C"` | — | 关闭名字修饰，使 C 与 C++ 能互相链接 |
| 扩展 | Extension | 某个实现自行增加的、标准里没有的语法 |

## B.1 类型宽度探针

`C`

```c
/* probe.c    编译：gcc -std=c17 probe.c -o probe
               C 与 C++ 写法相同 */
#include <stdio.h>
#include <limits.h>

int main(void) {
    printf("sizeof(char)  : %d\n", (int)sizeof(char));
    printf("sizeof(short) : %d\n", (int)sizeof(short));
    printf("sizeof(int)   : %d\n", (int)sizeof(int));
    printf("sizeof(long)  : %d\n", (int)sizeof(long));
    printf("sizeof(long long) : %d\n", (int)sizeof(long long));
    printf("sizeof(void*) : %d\n", (int)sizeof(void *));
    printf("char 有符号   : %s\n", (char)-1 < 0 ? "是" : "否");
    printf("CHAR_MIN      : %d\n", CHAR_MIN);
    printf("INT_MAX       : %d\n", INT_MAX);
    printf("-8 >> 1       : %d\n", -8 >> 1);
    return 0;
}
```

**在三个环境分别编译运行**：

`Bash`

```bash
# Windows + MinGW
gcc -std=c17 probe.c -o probe_gcc.exe

# Windows + MSVC（在 x64 Native Tools 命令提示符中）
cl /nologo /source-charset:utf-8 /execution-charset:gbk probe.c

# Linux
gcc -std=c17 probe.c -o probe_linux && ./probe_linux
```

| `sizeof(long long)` | 8 | 8 | 8 |

| `char` 是否有符号 | 有符号 | 有符号 | 有符号 |

## B.2 `extern` 与 `static` 的链接属性

`C`

```c
/* linkage.c    编译：gcc -std=c17 -c linkage.c -o linkage.o */
int global_default;              /* 默认：外部链接 */
extern int global_extern;        /* extern：外部链接 */
int global_extern = 1;           /* 定义 */
static int global_static;        /* static：内部链接 */
const int global_const = 2;      /* C 中 const 默认外部链接 */

int func_default(void) { return 0; }
extern int func_extern(void) { return 1; }
static int func_static(void) { return 2; }
extern int only_declared(void);  /* 只声明 */
```

`Bash`

```bash
gcc -std=c17 -c linkage.c -o linkage.o
nm linkage.o
```

**看字母大小写**：大写为外部链接，小写为内部链接，`U` 为未定义。

**C++ 的 `const` 对照**：

`C++`

```cpp
// const_linkage.cpp    编译：g++ -c const_linkage.cpp -o const_linkage_cpp.o
const int global_const = 2;                  /* 内部链接，符号带 L */
extern const int global_const_extern = 3;    /* 外部链接 */
```

`Bash`

```bash
g++ -c const_linkage.cpp -o const_linkage_cpp.o
nm const_linkage_cpp.o | grep global_const
```

## B.4 结构体布局与填充

`C`

```c
/* layout.c    编译：gcc -std=c23 layout.c -o layout && ./layout */
#include <stdio.h>
#include <stddef.h>

struct A { char c; int i; };
struct B { int i; char c; };
struct C { char a; char b; char c; };

int main(void) {
    printf("A: sizeof=%d  c@%d  i@%d\n", (int)sizeof(struct A),
           (int)offsetof(struct A, c), (int)offsetof(struct A, i));
    printf("B: sizeof=%d  i@%d  c@%d\n", (int)sizeof(struct B),
           (int)offsetof(struct B, i), (int)offsetof(struct B, c));
    printf("C: sizeof=%d\n", (int)sizeof(struct C));
    return 0;
}
```

**用 `offsetof` 让编译器算偏移，不要自己数。**

## B.6 `extern` 声明与定义的两文件对照

`C`

```c
/* a.c    编译：gcc -std=c17 a.c b.c -o ab && ./ab */

`C`

/* b.c */
#include <stdio.h>

}
```
