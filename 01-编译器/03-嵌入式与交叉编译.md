# 第 1 节 从 C 到 .hex：完整的编译链路

## 1.1 与桌面程序的区别

对比《01-编译器/01-编译与链接.md》第 2 节讲的四阶段：

| 阶段 | 桌面（Windows/MinGW） | 嵌入式（ARM/GCC） |
|---|---|---|
| 预处理 | `gcc -E` | 相同 |
| 编译 | `gcc -S` | `arm-none-eabi-gcc -S` |
| 汇编 | `gcc -c` | 相同 |
| 链接 | 用默认链接脚本 | **必须提供自己的 `.ld`** |
| 启动代码 | 由运行库提供 | **必须提供 `startup_*.s`** |
| 产物 | `.exe` | `.elf` → **再转成 `.hex` / `.bin`** |

**最后两行是关键差异**：桌面程序有操作系统接手，
单片机裸机什么都没有，**一切都要自己给**。

## 1.2 一个 CubeMX 工程包含什么

`信息显示驱动` 是一个完整的 STM32F103 + CMake + GCC 工程：

| 文件 / 目录 | 行数 | 作用 | 谁生成 |
|---|---|---|---|
| `Driver.ioc` | 134 | **工程配置**（引脚、时钟、外设） | CubeMX |
| `CMakeLists.txt` | 91 | 顶层构建脚本 | CubeMX |
| `cmake/gcc-arm-none-eabi.cmake` | 43 | **工具链描述** | CubeMX |
| `cmake/stm32cubemx/CMakeLists.txt` | 92 | 源文件清单 | CubeMX |
| `STM32F103XX_FLASH.ld` | 249 | **链接脚本** | CubeMX |
| `startup_stm32f103xe.s` | 470 | **启动文件** | ST |
| `Core/Src/main.c` | 184 | 主程序 | CubeMX + 用户 |
| `Core/Src/sysmem.c` | 87 | **堆内存管理** | CubeMX |
| `Core/Src/syscalls.c` | 244 | 系统调用桩 | CubeMX |
| `Core/Src/stm32f1xx_it.c` | 223 | **中断服务函数** | CubeMX |
| `Core/Src/gpio.c` `dac.c` `usart.c` | 各约 100 | 外设初始化 | CubeMX |
| `Drivers/` | — | HAL 驱动与 CMSIS | ST / ARM |

## 1.3 工具链描述

`cmake/gcc-arm-none-eabi.cmake`（**原文**，逐段讲解）：

`CMake`

```cmake
set(CMAKE_SYSTEM_NAME               Generic)
set(CMAKE_SYSTEM_PROCESSOR          arm)
```

**`Generic` 表示「没有操作系统」**。这告诉 CMake：
不要去找 Linux 的头文件、不要生成动态库、不要假设有 `main` 之外的运行环境。

`CMake`

```cmake
set(TOOLCHAIN_PREFIX                arm-none-eabi-)

set(CMAKE_C_COMPILER                ${TOOLCHAIN_PREFIX}gcc)
set(CMAKE_ASM_COMPILER              ${CMAKE_C_COMPILER})
set(CMAKE_CXX_COMPILER              ${TOOLCHAIN_PREFIX}g++)
set(CMAKE_LINKER                    ${TOOLCHAIN_PREFIX}g++)
set(CMAKE_OBJCOPY                   ${TOOLCHAIN_PREFIX}objcopy)
set(CMAKE_SIZE                      ${TOOLCHAIN_PREFIX}size)
```

**`arm-none-eabi-` 是交叉编译器的前缀**：

| 部分 | 含义 |
|---|---|
| `arm` | 目标架构是 ARM |
| `none` | 没有操作系统（裸机） |
| `eabi` | 使用 ARM 的嵌入式应用二进制接口 |

**它在 x86 的电脑上运行，生成的是 ARM 芯片能执行的代码。**
这就是《01-编译器/01-编译与链接.md》第 5.1 节「决定二：翻译成哪个平台的机器码」的实物。

`CMake`

```cmake
set(CMAKE_EXECUTABLE_SUFFIX_ASM     ".elf")
set(CMAKE_EXECUTABLE_SUFFIX_C       ".elf")
```

**把可执行文件的扩展名改成 `.elf`**——嵌入式不是 `.exe`。

`CMake`

```cmake
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)
```

**这一行解决一个实际问题**：CMake 配置阶段会试着编译一个测试程序来探测编译器。
但裸机程序**链接不起来**（没有启动代码、没有链接脚本）。
把它设为 `STATIC_LIBRARY` 后，CMake 只编译不链接，探测就能通过。
**这是工具链为特定场景做的妥协**，属于常见的工程实践。

`CMake`

```cmake
set(TARGET_FLAGS "-mcpu=cortex-m3 ")

set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} ${TARGET_FLAGS}")
set(CMAKE_ASM_FLAGS "${CMAKE_C_FLAGS} -x assembler-with-cpp -MMD -MP")
set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} -Wall -fdata-sections -ffunction-sections")
```

| 参数 | 含义 |
|---|---|
| `-mcpu=cortex-m3` | 目标 CPU 是 Cortex-M3（F103 的内核） |
| `-x assembler-with-cpp` | 汇编文件也要过预处理器（这样 `.s` 里能用 `#include`） |
| `-fdata-sections` `-ffunction-sections` | **每个函数/变量各占一个段** |

**最后一项是为链接期的垃圾回收做准备**，见第 1.4 小节。

`CMake`

```cmake
set(CMAKE_C_FLAGS_DEBUG "-O0 -g3")
set(CMAKE_C_FLAGS_RELEASE "-Os -g0")
```

**Debug 用 `-O0 -g3`，Release 用 `-Os -g0`**：

| 配置 | 优化 | 调试信息 | 说明 |
|---|---|---|---|
| Debug | `-O0` | `-g3`（最详细） | 便于调试 |
| Release | **`-Os`（优化体积）** | 无 | 单片机 Flash 小，优先省空间 |

> [!WARNING]
> Release 用的是 `-Os` 而不是 `-O2`：单片机上**体积比速度更重要**
> （Flash 只有 256 KB）。这与桌面上习惯用 `-O2` 是不同的取舍。
>
> `-O0` 与优化版的行为差异在嵌入式里同样存在，
> 见《01-编译器/01-编译与链接.md》第 6.2 小节。

## 1.4 链接脚本是怎样被传入的

同文件末尾（**原文**）：

`CMake`

```cmake
set(CMAKE_EXE_LINKER_FLAGS "${TARGET_FLAGS}")
set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} -T \"${CMAKE_SOURCE_DIR}/STM32F103XX_FLASH.ld\"")
set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} --specs=nano.specs")
set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} -Wl,-Map=${CMAKE_PROJECT_NAME}.map -Wl,--gc-sections")
set(CMAKE_EXE_LINKER_FLAGS "${CMAKE_EXE_LINKER_FLAGS} -Wl,--print-memory-usage")
```

| 参数 | 作用 |
|---|---|
| **`-T 文件`** | **指定链接脚本**——这就是第 2.1 小节那个 `.ld` 被用上的地方 |
| `--specs=nano.specs` | 使用精简版 C 库（体积小） |
| `-Wl,-Map=...` | 生成 `.map` 文件（内存占用清单） |
| **`-Wl,--gc-sections`** | **回收没人引用的段** |
| `-Wl,--print-memory-usage` | 链接后打印 Flash/RAM 占用 |

### `--gc-sections` 与链接脚本的关系

**这两处必须配合理解**：

`Text`

```text
编译期：-ffunction-sections -fdata-sections
        → 每个函数、每个变量各占独立的一段

链接期：--gc-sections
        → 把「没有任何地方引用」的段整个删掉

链接脚本：KEEP(*(.isr_vector))
        → 但这一段必须保留，哪怕没人显式引用
```

**为什么要 `KEEP`**：中断向量表**不被任何 C 与 C++ 代码引用**——
它是给硬件读的（CPU 上电时直接从那里取栈顶和入口地址）。
链接器不知道这件事，会认为它是垃圾而删除。

**删掉的后果**：程序烧进去后**根本跑不起来**，因为 CPU 取到的是空白。

> [!IMPORTANT]
> **链接脚本里的一个关键字，决定程序能否启动。**
> 而它的必要性，只有在看到 `--gc-sections` 之后才真正能理解。

## 1.5 生成 hex 与 bin

`CMakeLists.txt` 中（**原文**，节选）：

`CMake`

```cmake
if(CMAKE_OBJCOPY)
    add_custom_command(TARGET ${CMAKE_PROJECT_NAME} POST_BUILD
        COMMAND ${CMAKE_OBJCOPY} -O ihex
                $<TARGET_FILE:${CMAKE_PROJECT_NAME}> ${CMAKE_PROJECT_NAME}.hex
        COMMAND ${CMAKE_OBJCOPY} -O binary -S
                $<TARGET_FILE:${CMAKE_PROJECT_NAME}> ${CMAKE_PROJECT_NAME}.bin
        COMMAND ${CMAKE_SIZE} $<TARGET_FILE:${CMAKE_PROJECT_NAME}>
        COMMENT "Generating ${CMAKE_PROJECT_NAME}.hex / ${CMAKE_PROJECT_NAME}.bin"
        VERBATIM
    )
endif()
```

**为什么要多这一步**：链接产物 `.elf` 里含有调试信息、符号表等，
是给**调试器**看的；而烧录器需要的是纯粹的**存储映像**。

| 格式 | 内容 | 用途 |
|---|---|---|
| `.elf` | 机器码 + 符号表 + 调试信息 + 段信息 | 调试 |
| `.hex` | 纯十六进制文本，**每行带地址** | 烧录 |
| `.bin` | 纯二进制，**不含地址信息** | 烧录 / OTA 升级 |

**`.hex` 与 `.bin` 的区别**：
`.hex` 是**文本**，烧录器从每行的地址字段知道往哪写；
`.bin` 是**纯二进制**，烧录时必须由工具另外指定起始地址。

# 第 2 节 链接脚本：内存的地图

## 2.1 真实代码

`STM32F103XX_FLASH.ld` 第 52-77 行（**原文**）：

`Linker Script`

```ld
/* Entry Point */
ENTRY(Reset_Handler)

/* Specify the memory areas */
MEMORY
{
RAM (xrw)      : ORIGIN = 0x20000000, LENGTH = 48K
FLASH (rx)      : ORIGIN = 0x8000000, LENGTH = 256K
}

/* Highest address of the user mode stack */
_estack = ORIGIN(RAM) + LENGTH(RAM);    /* end of RAM */
/* Generate a link error if heap and stack don't fit into RAM */
_Min_Heap_Size = 0x200;      /* required amount of heap  */
_Min_Stack_Size = 0x400; /* required amount of stack */

/* Define output sections */
SECTIONS
{
  /* The startup code goes first into FLASH */
  .isr_vector :
  {
    . = ALIGN(4);
    KEEP(*(.isr_vector)) /* Startup code */
    . = ALIGN(4);
  } >FLASH
```

> 文件头含完整的 BSD-3-Clause 声明与
> `COPYRIGHT(c) 2025 STMicroelectronics`，此处略去。

## 2.2 逐项讲解

### 要点一：`MEMORY` 块是「芯片的地址地图」

`Text`

```text
RAM    : 0x20000000, 48K      ← 可读写，变量放这里
FLASH  : 0x08000000, 256K     ← 只读可执行，代码放这里
```

**这些地址不是随便写的**，而是芯片设计时定死的。
STM32F103 的 Flash 就从 `0x08000000` 开始，RAM 从 `0x20000000` 开始。

**对照桌面程序**：桌面程序运行在虚拟地址空间里，
链接器可以用 `0x400000` 之类的地址；而单片机**没有 MMU**，
代码直接跑在物理地址上，因此地址完全由芯片决定。

**对照同系列的不同型号**：
另一个 CubeMX 工程的 `STM32F407XX_FLASH.ld` 里是这样的：

`Linker Script`

```ld
RAM (xrw)      : ORIGIN = 0x20000000, LENGTH = 128K
CCMRAM (xrw)   : ORIGIN = 0x10000000, LENGTH = 64K
FLASH (rx)     : ORIGIN = 0x8000000, LENGTH = 1024K
```

**起始地址相同，容量不同**——因为 F407 是更高端的型号。
**换芯片时，链接脚本是必须改的地方之一。**

这句话在真板上验证过：给 F103**xC**（RAM 48 KB / flash 256 KB）写的脚本，
原样用在 F103**C8**（20 KB / 64 KB）上，链接器一句话都不说，烧进去之后复位即进 `HardFault`，
连 `main` 都进不去。命令与现场见第 9.6 小节。

### 要点二：`_estack` 为什么必须是 RAM 的最高地址

`_estack` 是脚本算出来的常量，值等于「RAM 起点 + RAM 长度」，也就是这块芯片 RAM 的最高地址。
Cortex-M 复位时硬件把它装进 `MSP`，栈从那里向下生长——**改 `MEMORY` 里的 `LENGTH`，改的就是栈顶**。

**它由链接脚本定义、由启动文件引用**：`.ld` 给出 `_estack` 的值，
`.s` 把向量表的第 0 项写成 `.word _estack`，两处必须配套。

> [!IMPORTANT]
> `LENGTH` 要写自己芯片的真实容量。写大了链接器不会报错，
> 只会把栈指针放到不存在的内存上，复位后第一次压栈就越界，见第 9.6 小节。

复位行为的完整时序见《07-更底层/07-链接脚本与启动代码.md》第 3.1 小节，
`MEMORY` 与 `_estack` 的逐行解释见《07-更底层/07-链接脚本与启动代码.md》第 2.2 小节。

### 要点三：`KEEP` 与 `--gc-sections` 的配合

`KEEP(*(.isr_vector))` 的作用与必要性见第 1.4 小节。
**删掉它不会有任何警告**，链接照常成功，只是向量表被当作无人引用的段回收，
芯片取不到入口。真板上的实测见《07-更底层/07-链接脚本与启动代码.md》第 5.1 小节，
空片复位的现场见第 9.4 小节。

### 要点四：栈与堆的大小是「链接期预留」

`Linker Script`

```ld
_Min_Heap_Size = 0x200;      /* 512 字节 */
_Min_Stack_Size = 0x400;     /* 1 KB */
```

名字里的 **`Min`** 很关键：这只是**最小值**，链接器会据此检查
「RAM 装得下吗」；但**运行期没有任何机制看守它**。

**F407 工程里这两个值各是 8 KB，比这里大得多**，
因为 F103 只有 48 KB RAM，**留不出那么多**。

**第 9 节那块 C8 板子的 RAM 只有 20 KB**，同样的预留值占比更大；
换型号时这两个数与 `LENGTH` 要一起看。

**栈用超了会怎样**？见第 5 节。

### 要点五：段（`SECTIONS`）与内存布局

`SECTIONS` 把各输入文件里的段拼成输出段，再指定每个输出段进 FLASH 还是 RAM。
段名与《01-编译器/01-编译与链接.md》第 2.4 小节 `nm` 输出里的标记一一对应。
其中 `.data` 与 `.bss` 只差一条：**前者的初值装在 Flash 里，变量本身在 RAM 里**；
后者的初值就是 0，不占镜像空间。

> [!IMPORTANT]
> 因此启动代码必须做两件事：把 `.data` 的初值从 Flash 搬到 RAM、把 `.bss` 清零。
> 搬运循环的写法、`AT>` 与 VMA/LMA 的关系见《07-更底层/07-链接脚本与启动代码.md》第 2.6 小节。

# 第 3 节 启动文件：`main` 之前发生了什么

## 3.1 真实代码

`startup_stm32f103xe.s` 是 ST 提供的启动文件，属于工程里**不必自己写、也不该改**的那部分。
入口是 `Reset_Handler`（**原文**，节选）：

`Assembly`

```asm
  .section  .text.Reset_Handler
  .weak  Reset_Handler
  .type  Reset_Handler, %function
Reset_Handler:

/* Call the clock system initialization function.*/
    bl  SystemInit
```

> 该文件头标注 `@author MCD Application Team`，
> 属于 ST 提供的启动模板，随 HAL 包以 BSD-3-Clause 分发。

**从这条 `bl` 往下，文件里依次还有四段**：把 `.data` 从 flash 搬到 RAM 的循环、
把 `.bss` 清零的循环、`bl __libc_init_array`、`bl main`。
它们的逐条讲解见《07-更底层/07-链接脚本与启动代码.md》第 3 节，
本节只给每段做什么、以及工程上要留意的地方。

## 3.2 复位之后的五步

从复位到 `main`，一共五步。逐条讲解见《07-更底层/07-链接脚本与启动代码.md》第 3 节，
对应的小节如下：

| 顺序 | 做什么 | 小节 |
|---|---|---|
| 1 | 硬件把向量表第 0 项装进 `MSP`，跳转到第 1 项 | 3.1 |
| 2 | `bl SystemInit`：配置时钟树 | 3.2 |
| 3 | 把 `.data` 从 flash 搬到 RAM | 3.3 |
| 4 | 把 `.bss` 清零 | 3.4 |
| 5 | `bl __libc_init_array`、`bl main` | 3.5、3.6 |

> [!IMPORTANT]
> `Reset_Handler` 里**没有设置栈指针的语句**：第 1 步由硬件完成，
> 栈指针取自向量表的第 0 项，见第 3.4 小节。

**第 2 步必须在 `main` 之前完成**，否则后面所有的延时与串口波特率都是错的。
这块板子上读到的时钟源仍是 **HSI 8 MHz**（`RCC_CFGR = 0x00000000`），
把周期数折算成时间时按第 9.1 小节的数字算。

**第 5 步是 C++ 全局对象能在 `main` 之前构造好的原因**：
`__libc_init_array` 遍历构造数组，逐个调用构造函数；纯 C 程序里它无事可做，
C++ 程序里它不可省。

本工程的工具链文件里另有 `-fno-threadsafe-statics`、`-fno-exceptions`、
`-fno-rtti`，说明该工程按「受限的 C++」子集使用，这是嵌入式常见做法。

## 3.3 与桌面程序的对应

桌面程序里这些事由 **C 运行库的启动代码**（`crt0` / `crt1`）完成，
你从来不用写，甚至不知道它存在。

**桌面程序里 `main` 也不是第一个被执行的函数。**
在它之前同样有「设置栈、初始化运行库、调用全局构造函数」这些步骤，
只不过那些代码是编译器附带的，**而单片机上你必须自己提供**。

两边的分工与差异见《07-更底层/07-链接脚本与启动代码.md》第 4 节。

## 3.4 向量表

同文件中的向量表开头（**原文**，节选）：

`Assembly`

```asm
   .section  .isr_vector,"a",%progbits
  .type  g_pfnVectors, %object
g_pfnVectors:
  .word  _estack
  .word  Reset_Handler
  .word  NMI_Handler
  .word  HardFault_Handler
```

**这是一张函数地址表**：第 0 项是栈顶（不是函数），第 1 项是复位入口，第 3 项是 `HardFault`。
发生中断时，CPU 用「中断号 × 4」作为偏移去表里取地址，然后跳过去。

**表放在哪里由链接脚本决定**：它必须占据 flash 的第一个字节，
并且不能被 `--gc-sections` 收走——原因见《07-更底层/07-链接脚本与启动代码.md》第 2.4 小节，
收走之后的实测后果见《07-更底层/07-链接脚本与启动代码.md》第 5.1 小节。
`HardFault` 的处理办法见第 6.2 小节。

# 第 4 节 寄存器、位运算与 `volatile`

## 4.1 寄存器是什么

单片机的外设（GPIO、串口、定时器）都由**寄存器**控制。
每个寄存器就是内存里的一个固定地址，读写它就等于操作硬件。

**这让「指针」这个概念有了具体对象**：寄存器就是「某个地址上的一个 `uint32_t`」。

## 4.2 从整数地址到指针

CMSIS 的设备头文件里（**原文**，宏定义形式）：

`C`

```c
#define PERIPH_BASE           0x40000000UL
#define APB2PERIPH_BASE       (PERIPH_BASE + 0x00010000UL)
#define GPIOA_BASE            (APB2PERIPH_BASE + 0x00000800UL)
#define GPIOA                 ((GPIO_TypeDef *) GPIOA_BASE)
```

**逐层展开**：

`Text`

```text
PERIPH_BASE     = 0x40000000
APB2PERIPH_BASE = 0x40000000 + 0x00010000 = 0x40010000
GPIOA_BASE      = 0x40010000 + 0x00000800 = 0x40010800
GPIOA           = (GPIO_TypeDef *) 0x40010800
                   ↑ 把这个整数地址强行解释成一个结构体指针
```

**`GPIOA->ODR` 这一句代码，编译后就是「访问地址 0x4001080C」**。
没有操作系统介入，没有虚拟内存映射——**指针直接指向硬件**。

**如果一个指针的值是 `0x40010800`，解引用它会怎样**？
会读到一个 `GPIO_TypeDef` 结构体，而那个结构体的每个字段
都对应一个真实的硬件寄存器。**这就是内存映射 I/O。**

> [!WARNING]
> 具体偏移值随芯片型号不同，不要背下来，
> 用之前打开自己芯片的头文件确认。

## 4.3 `BSRR`：为什么要专门设计一个寄存器

HAL 库中的写引脚函数（**原文**，`stm32f1xx_hal_gpio.c`）：

`C`

```c
void HAL_GPIO_WritePin(GPIO_TypeDef *GPIOx, uint16_t GPIO_Pin, GPIO_PinState PinState)
{
  /* Check the parameters */
  assert_param(IS_GPIO_PIN(GPIO_Pin));
  assert_param(IS_GPIO_PIN_ACTION(PinState));

  if (PinState != GPIO_PIN_RESET)
  {
    GPIOx->BSRR = GPIO_Pin;
  }
  else
  {
    GPIOx->BSRR = (uint32_t)GPIO_Pin << 16u;
  }
}
```

**`BSRR` 的低 16 位置 1，高 16 位清 0**，而且**写它不影响其他位**：

`Text`

```text
BSRR = |  清 0 位（高 16）  |  置 1 位（低 16）  |
         bit31 ... bit16      bit15 ... bit0
```

因此：
- `BSRR = pin` → 把 `pin` 置 1，其他引脚不动
- `BSRR = pin << 16` → 把 `pin` 清 0，其他引脚不动

**为什么这样设计**：如果改用「读 `ODR` → 改一位 → 写回」的方式，中间会有个间隙。
**如果此时发生了中断，而中断里也操作同一个端口，那一位就会被写错。**

`BSRR` 把「读改写」合并成一次写操作，**硬件层面保证原子性**。

> [!IMPORTANT]
> 这是一个说明**硬件设计如何简化软件**的例子。
> 对照 `HAL_GPIO_TogglePin`（它必须先读 `ODR` 再写 `BSRR`）——
> 那个函数**不是**原子的，在中断环境里需要额外保护。

## 4.4 位运算：置位与清位的固定套路

配置寄存器时的写法：

`C`

```c
tmpreg &= ~pinmask;              /* 清位：按位与上掩码的反 */
tmpreg |= (mode << pos);         /* 置位：按位或上移位后的值 */
GPIOx->CRL = tmpreg;             /* 整体写回 */
```

**这是「读—改—写」模式的固定套路**：

`Text`

```text
读出现值 → 清除要改的位 → 写入新值 → 整体写回
```

**为什么要「整体写回」而不是逐位写**：因为硬件寄存器通常不支持位寻址，
你只能一次写 32 位。如果直接 `GPIOx->CRL = newvalue`，
其他引脚的配置就被覆盖了。

**顺序不能反**：先 `|=` 再 `&= ~`，新写入的值会被紧接着清掉。

**「配置 PA5」时的掩码是这样算出来的**：

`Text`

```text
pinpos  = 5
pos     = 5 << 2 = 20          （每个引脚占 4 位）
pinmask = 0x0F << 20 = 0x00F00000
```

> [!WARNING]
> F1 系列的 `CRL`/`CRH` 每 4 位描述一个引脚；
> F4 系列改成了 `MODER`/`OTYPER`/`OSPEEDR`/`PUPDR` 四个寄存器，每个引脚各占 2 位。
> **这是寄存器设计随芯片演进的实例**，对照时应打开对应型号的头文件。

## 4.5 `volatile`：一个后果很严重的例子

### 4.5.1 问题

CMSIS 的核心头文件 `core_cm3.h` 里（**原文**）：

`C`

```c
#define     __I     volatile const       /*!< Defines 'read only' permissions */
#define     __O     volatile             /*!< Defines 'write only' permissions */
#define     __IO    volatile             /*!< Defines 'read / write' permissions */
```

**每个寄存器成员都被标成 `volatile`。为什么？**

### 4.5.2 不加 `volatile` 会怎样

写两个函数，一个用普通变量，一个用 `volatile` 变量，都做「等待标志位置位」。

`实测数据`
`C`

```c
/* volatile_flag.c    编译：gcc -std=c23 -O0 -S volatile_flag.c -o O0.s */
/*                    再编一次：gcc -std=c23 -O2 -S volatile_flag.c -o O2.s */
int flag_normal = 0;                    /* 普通变量 */
volatile int flag_volatile = 0;         /* 每次访问都要真的读写内存 */

/* 等待标志位置位 */
int wait_normal(void)   { while (flag_normal == 0) { }   return 1; }
int wait_volatile(void) { while (flag_volatile == 0) { } return 1; }
```

`-O2` 下两者的差别就是结论本身（完整输出见附录 D）：

`实测数据`
`Assembly`

```asm
wait_normal:                          wait_volatile:
	movl	flag_normal(%rip), %eax         .L6:
	testl	%eax, %eax                        movl	flag_volatile(%rip), %eax
	je	.L3                                 testl	%eax, %eax
	movl	$1, %eax                          je	.L6
	ret                                     movl	$1, %eax
.L3:                                        ret
	jmp	.L3
```

**`wait_normal` 只读了一次内存**，随后在 `.L3` 原地跳转，**再也不读**。
编译器的推理是「循环体里没有任何东西会修改这个变量」，这在普通变量的前提下完全正确，
但它不知道硬件会改。**`wait_volatile` 每次循环都重新读内存**，因此能感知到变化。

`-O0` 下两者的汇编一样，因此这类缺陷只在优化过的版本里出现。
真板上的同一个现象更直接：程序在循环里等一个标志，调试器把那个地址改成 1 之后，
带 `volatile` 的版本跳出了循环，去掉 `volatile` 的版本完全没有反应，`pc` 仍停在循环里——
源码、命令与两边的结果见《07-更底层/03-寄存器、位与 volatile.md》第 2.3 小节。

### 4.5.3 四个要点

**要点一：`volatile` 的含义是「每次访问都要真的去内存读/写」**

它不是「让变量变得线程安全」，也不是「禁止优化」，
而是**告诉编译器：这个值可能在你不知道的时候改变**。

**要点二：不加 `volatile` 的后果是「程序永远卡在等待里」**

而这个缺陷**在 `-O0` 下不会出现**，因为不优化时编译器不推理。

**本工程的 Release 配置用的是 `-Os`（同样是优化）**，
因此这类问题**只在发布版出现**，详见
《01-编译器/01-编译与链接.md》第 6.3 小节。

**要点三：`volatile` 不能替代同步原语**

它管得住编译器的优化，管不住中断与主循环之间的竞争，管不住 CPU 的访问顺序，
也给不了一次操作的原子性。四类问题的逐条分析与真板实测见
《07-更底层/03-寄存器、位与 volatile.md》第 2.8 小节与第 3 节。

`volatile` 常被当成一个万用的开关，上列四类问题它一个也解决不了。

**要点四：中断里改的变量必须是 `volatile`**

`C`

```c
/* tick.c */
#include <stdint.h>

volatile uint32_t g_tick_count = 0;      /* 在 SysTick 中断里递增 */

void SysTick_Handler(void)
{
    g_tick_count++;                      /* 中断服务函数修改它 */
}

int main(void)
{
    while (g_tick_count < 1000) { }      /* 主循环等待：没有 volatile 就会死循环 */
    return 0;
}
```

**这是嵌入式里最常见的 `volatile` 使用场景**，
完整清单（哪些地方必须写、哪些地方写了也没用）见
《07-更底层/03-寄存器、位与 volatile.md》第 2.7 小节。

# 第 5 节 内存布局：栈与堆在单片机上

## 5.1 一张图

`Core/Src/sysmem.c` 的注释里就画着这张图（**原文**）：

`C`

```c
/**
 * @verbatim
 * ############################################################################
 * #  .data  #  .bss  #       newlib heap       #          MSP stack          #
 * #         #        #                         # Reserved by _Min_Stack_Size #
 * ############################################################################
 * ^-- RAM start      ^-- _end                             _estack, RAM end --^
 * @endverbatim
 */
```

**这张图是理解嵌入式内存的关键**：

`Text`

```text
低地址                                                          高地址
  ┌────────┬────────┬──────────────────────┬──────────────────────┐
  │ .data  │ .bss   │      堆（heap）       │    栈（stack）        │
  │        │        │      →  向上增长      │  ←  向下增长          │
  └────────┴────────┴──────────────────────┴──────────────────────┘
  ↑                                              ↑
  RAM 起点                                     RAM 终点 = _estack
                    ↑
                  堆栈在这里相遇 = 溢出
```

**这张图说明了三件事**：

1. `.data` 和 `.bss` 在**最前面**（低地址），因为它们是静态分配的
2. **堆向上长，栈向下长**，中间是空地
3. 两者相遇就是**堆栈冲突**，通常表现为「栈溢出踩坏了堆」

## 5.2 `_sbrk`：堆的边界检查

`Core/Src/sysmem.c`（**原文**，CubeMX 生成）：

`C`

```c
void *_sbrk(ptrdiff_t incr)
{
  extern uint8_t _end; /* Symbol defined in the linker script */
  extern uint8_t _estack; /* Symbol defined in the linker script */
  extern uint32_t _Min_Stack_Size; /* Symbol defined in the linker script */
  const uint32_t stack_limit = (uint32_t)&_estack - (uint32_t)&_Min_Stack_Size;
  const uint8_t *max_heap = (uint8_t *)stack_limit;
  uint8_t *prev_heap_end;

  /* Initialize heap end at first call */
  if (NULL == __sbrk_heap_end)
  {
    __sbrk_heap_end = &_end;
  }

  /* Protect heap from growing into the reserved MSP stack */
  if (__sbrk_heap_end + incr > max_heap)
  {
    errno = ENOMEM;
    return (void *)-1;
  }

  prev_heap_end = __sbrk_heap_end;
  __sbrk_heap_end += incr;

  return (void *)prev_heap_end;
}
```

> 文件头标注 `@author Generated by STM32CubeMX`。

### 5.2.1 `malloc` 最终调用的是 `_sbrk`

`malloc` 只是内存分配器，它向「系统」要内存时调用的就是这个 `_sbrk`。
在桌面上 `_sbrk` 由操作系统实现（背后是虚拟内存），
**在裸机上必须自己写**，CubeMX 替你生成了这一份。

**在 `_sbrk` 里加一句打印，然后调用 `malloc`**，
就能观察每次分配时 `__sbrk_heap_end` 的变化。

### 5.2.2 三个符号都来自链接脚本

`C`

```c
extern uint8_t _end;              /* .bss 的终点 → 堆的起点 */
extern uint8_t _estack;           /* RAM 终点 → 栈的起点 */
extern uint32_t _Min_Stack_Size;  /* 栈的保留大小 */
```

**这三个符号在第 2.1 小节的 `.ld` 文件里都能找到**：

`Linker Script`

```ld
_estack = ORIGIN(RAM) + LENGTH(RAM);
_Min_Heap_Size = 0x200;
_Min_Stack_Size = 0x400;
```

> [!IMPORTANT]
> `sysmem.c` 与 `.ld` 之间是**跨文件的约定**。
> **有些符号来自链接脚本，不在任何 `.c` 里。**
> C 文件并不是自足的。

### 5.2.3 堆有守卫，栈没有

`C`

```c
if (__sbrk_heap_end + incr > max_heap)      /* 堆：会检查 */
{
    errno = ENOMEM;
    return (void *)-1;                      /* 返回失败，malloc 返回 NULL */
}
```

堆越界会**返回失败**，调用方可以处理。

**但栈没有任何保护**：

`Text`

```text
栈溢出时 → 直接踩掉堆或其他变量 → 行为完全不可预测
```

> [!CAUTION]
> **栈溢出是嵌入式开发中一类经典故障的根源。**
> 它不会报错，只会让某个不相干的变量莫名其妙地改变。

### 5.2.4 注释里已经提示了怎么办

`文档`

> "NOTE: If the MSP stack, at any point during execution, grows larger than the
> reserved size, please increase the `_Min_Stack_Size`."
>
> —— `Core/Src/sysmem.c` 原文件注释

**即：把链接脚本里的 `_Min_Stack_Size` 调大。**
但这只是「扩大保留区」，**并不构成真正的保护**：
它只影响堆的上限，栈本身仍然可以越过它。

### 5.2.5 栈溢出的典型表现

| 表现 | 原因 |
|---|---|
| 某个不相关的变量突然变了 | 栈长过来踩到了它 |
| `malloc` 返回的指针指向垃圾 | 栈踩坏了堆的元数据 |
| 进 `HardFault_Handler` | 踩到了不该踩的地方 |
| 递归深了就死机 | 每层递归都占栈帧 |

**排查手段**：

1. 把 `_Min_Stack_Size` 调大试试（如果问题消失，就是栈溢出）
2. 在栈的低地址端填上特征值（如 `0xDEADBEEF`），运行一段时间后检查被冲掉了多少
3. 避免在大函数里定义大数组（`int buf[1000]` 就是 4 KB 栈）

> [!WARNING]
> `int buf[1000];` 写成一个**局部变量**时占的是栈，
> 写成**全局变量**时占的是 `.bss`。这一个字的差别，
> **在本工程里就是 48 KB RAM 中 4 KB 的差距**，
> 而 `_Min_Stack_Size` 默认只留了 1 KB。

# 第 6 节 中断服务函数

## 6.1 真实代码

`Core/Src/stm32f1xx_it.c`（**原文**，CubeMX 生成）：

`C`

```c
/**
  * @brief This function handles Non maskable interrupt.
  */
void NMI_Handler(void)
{
  /* USER CODE BEGIN NonMaskableInt_IRQn 0 */

  /* USER CODE END NonMaskableInt_IRQn 0 */
  /* USER CODE BEGIN NonMaskableInt_IRQn 1 */
   while (1)
  {
  }
  /* USER CODE END NonMaskableInt_IRQn 1 */
}

/**
  * @brief This function handles Hard fault interrupt.
  */
void HardFault_Handler(void)
{
  /* USER CODE BEGIN HardFault_IRQn 0 */

  /* USER CODE END HardFault_IRQn 0 */
  while (1)
  {
    /* USER CODE BEGIN W1_HardFault_IRQn 0 */
    /* USER CODE END W1_HardFault_IRQn 0 */
  }
}
```

## 6.2 逐项讲解

### 6.2.1 CubeMX 只给骨架，`while(1)` 是占位

每个异常处理函数里都是 `while (1) { }`，即**死循环**。

**这是有意为之的**：CubeMX 不知道你希望程序在出错时做什么，
所以给一个「停下来」的默认行为，同时用 `USER CODE` 区块留出位置让你填。

> [!IMPORTANT]
> **默认行为要保守。**
> 出错时**停下来**比**继续跑**安全得多，继续跑可能损坏硬件。

### 6.2.2 `HardFault_Handler` 是调试的第一站

**`HardFault` 是 ARM Cortex-M 的「兜底异常」**：
当发生了处理器无法归类为其他异常的错误（非法访问、非对齐访问、
除零、跳转到非法地址等），都会进这里。

**几种可用的做法**：

| 做法 | 效果 |
|---|---|
| 在 `while(1)` 处下断点 | 出故障时能停住，看调用栈 |
| 在里面点亮一个 LED | 无调试器时也能知道「出错了」 |
| 读取故障状态寄存器 | 知道**是哪一类**故障 |

**故障状态寄存器**（在 `USER CODE` 区块里添加）：

`C`

```c
void HardFault_Handler(void)
{
  volatile uint32_t cfsr  = SCB->CFSR;    /* 可配置故障状态 */
  volatile uint32_t hfsr  = SCB->HFSR;    /* 硬故障状态 */
  volatile uint32_t mmfar = SCB->MMFAR;   /* 出错的内存地址 */
  volatile uint32_t bfar  = SCB->BFAR;    /* 出错的总线地址 */
  (void)cfsr; (void)hfsr; (void)mmfar; (void)bfar;

  while (1) { }
}
```

**在调试器里查看这几个变量的值**，就能判断故障类型：

| 寄存器 | 含义 |
|---|---|
| `CFSR` | 具体是哪一类故障（非对齐、除零、非法状态……） |
| `HFSR` | 是否由其他故障升级而来 |
| `MMFAR` / `BFAR` | **出错的地址**，这一项最有用 |

**故意写一句 `*(volatile uint32_t *)0x12345678 = 1;`**，
就能看到程序进 `HardFault_Handler`；再读 `BFAR`，
**它会告诉你刚才访问的是哪个非法地址**。

> [!IMPORTANT]
> 这与《02-调试器/01-原理与使用.md》第 10 节讲的崩溃排查是同一件事，
> 只是桌面上有操作系统帮忙产生转储文件，而单片机上全靠自己读寄存器。

### 6.2.3 ISR 的三条戒律

| 戒律 | 原因 |
|---|---|
| **要短** | 中断期间同级中断被阻塞；太长会丢事件 |
| **不能阻塞** | ISR 里不能 `sleep`、不能等信号量，它没有「其他线程」可让 |
| **共享变量必须 `volatile`** | 主循环里的编译器不知道 ISR 会改它 |

### 6.2.4 `USER CODE` 区块是 CubeMX 的约定

注意这些标记：

`C`

```c
  /* USER CODE BEGIN HardFault_IRQn 0 */
  ...你的代码写在这里...
  /* USER CODE END HardFault_IRQn 0 */
```

**CubeMX 重新生成代码时，只会保留这些区块内的内容**，
区块之外的一律覆盖。详见第 7 节。

# 第 7 节 CubeMX 工程的工作方式

## 7.1 `.ioc` 文件是什么

每个工程根目录都有一个 `.ioc` 文件（本工程为 `Driver.ioc`）。
它是 **CubeMX 的工程描述文件**，记录了：

| 内容 | 说明 |
|---|---|
| 芯片型号 | 决定链接脚本里的内存大小 |
| 引脚分配 | 哪个引脚做什么用 |
| 时钟树配置 | 系统频率、各总线分频 |
| 外设使能 | 开了哪些 GPIO / USART / DAC |
| 中断优先级 | NVIC 配置 |

**用 CubeMX 打开 `.ioc`，就能看到图形化的配置界面。**

> [!IMPORTANT]
> `.ioc` 是**工程的唯一真相来源**。
> `Core/` 下的那些 `.c` 文件都是从它生成的，**改配置不如改 `.ioc`**。
> 只有在 `USER CODE` 区块里加逻辑是例外。

## 7.2 `USER CODE` 区块的规则

**只有这些区块内的内容会在重新生成时被保留**：

`C`

```c
/* USER CODE BEGIN 0 */
    这里的内容会保留
/* USER CODE END 0 */

    这里的内容会被覆盖
```

**区块是成对出现的**，`BEGIN` 与 `END` 之间的内容才算数。

### 常见的区块名

| 区块名 | 出现位置 | 用途 |
|---|---|---|
| `USER CODE BEGIN Includes` | 文件头部 | 加自己的 `#include` |
| `USER CODE BEGIN PV` | Private Variables | 加自己的全局变量 |
| `USER CODE BEGIN 0` | 各文件的通用区 | 加自己的函数 |
| `USER CODE BEGIN 2` | `main.c` 的初始化之后 | 加自己的初始化代码 |
| `USER CODE BEGIN WHILE` | `main.c` 的主循环内 | 加主循环逻辑 |
| `USER CODE BEGIN 4` | `stm32f1xx_it.c` | 加自己的中断处理 |

**编号（0/1/2/3/4）表示在文件中的位置**，与功能无关。

## 7.3 与 VS Code 重写 `tasks.json` 的相似之处

| 场景 | 谁在重写文件 | 保留什么 |
|---|---|---|
| CubeMX 重新生成代码 | CubeMX | `USER CODE` 区块 |
| **VS Code 追加调试配置** | **VS Code** | **不保留注释** |
| CMake 重新配置 | CMake | `CMakeCache.txt` 之外的用户改动 |

**共同点**：**有些工具会重写你的文件，你必须知道它保留什么。**

《01-编译器/02-环境配置.md》第 9.7 小节记录过一个真实情况：
VS Code 在追加自动生成的调试配置时，**把 `tasks.json` 里的注释全删了**。
这与 CubeMX 覆盖 `USER CODE` 之外的内容是同一类问题。

> [!TIP]
> 手工写的代码放进工具认可的区块；
> 工具的配置文件改动前先备份；
> 改动之前先确认文件头有没有 `@author Generated by ...`。

## 7.4 怎么判断一个文件是不是生成的

**看文件头**。本工程里三种都有：

| 文件头标注 | 含义 | 能否手改 |
|---|---|---|
| `@author Generated by STM32CubeMX` | CubeMX 生成 | **只在 `USER CODE` 区块内改** |
| `@author MCD Application Team` | ST 提供 | 一般不改 |
| 无标注或你自己的标注 | 用户代码 | 可以改 |

**这解释了为什么本工程里 `Core/Src/main.c` 有 `USER CODE` 区块，
而 `startup_stm32f103xe.s` 没有**：后者是 ST 的固定模板，
重新生成不会覆盖它，但改错了会出问题。

# 第 9 节 真板：烧录与调试

前面八节的代码都来自别人的工程。这一节换成一块真实存在的板子：
**STM32F103C8 最小系统板 + CMSIS-DAP 调试器**，从接线走到看见程序的输出。
下面的命令、输出与数字都是在这块板子上实测得到的。

## 9.1 板子、调试器与接线

`实测数据`

| 项 | 值 |
|---|---|
| 芯片 | STM32F103C8（中容量 F103，Cortex-M3 r1p1） |
| flash | **64 KiB**，起始 `0x08000000` |
| RAM | **20 KiB**，起始 `0x20000000`，栈顶 `0x20005000` |
| 板上器件 | **只有 MCU 与晶振**（另有 SWD 排针）：没有 LED、没有串口、没有传感器 |
| 调试器 | CMSIS-DAP，FW 1.2.0，Serial `6D656D6F7279` |
| 内核标识 | `DPIDR = 0x1ba01477`，6 个断点 / 4 个观察点 |
| 时钟源 | `RCC_CFGR = 0x00000000` → SWS = 00 → **HSI 8 MHz**，1 周期 = 125 ns |

**SWD 只需要四根线**：3V3、GND、SWDIO、SWCLK。

`Text`

```text
     调试器（CMSIS-DAP）                        板子（STM32F103C8）

     ┌──────────────┐                          ┌──────────────┐
     │  3V3     ────┼──────────────────────────┼──── 3V3      │
     │  GND     ────┼──────────────────────────┼──── GND      │
     │  SWDIO   ────┼──────────────────────────┼──── SWDIO    │
     │  SWCLK   ────┼──────────────────────────┼──── SWCLK    │
     └──────────────┘                          └──────────────┘
```

**板上焊了晶振，但实测时 HSE 没有开**（`RCC_CR = 0x00005C83`），
系统跑在复位默认的 HSI 8 MHz 上。凡是要把周期数折算成时间的地方，
都按 **1 周期 = 125 ns** 计算。

> [!WARNING]
> **这块板子没有 LED，也没有串口。**
> 判断程序有没有跑起来，不能靠点灯，也不能靠 `printf`。
> 可用的只有两条通道：调试器读内存（第 9.3 小节）与 semihosting 输出（第 9.5 小节）。

## 9.2 先确认连得上：识别芯片

第一步不是烧写，而是让调试器把芯片认出来。OpenOCD 的两个 `-f` 各给一份配置：
一份描述调试器（`interface/cmsis-dap.cfg`），一份描述目标芯片（`target/stm32f1x.cfg`）；
`-c` 里的命令按出现顺序执行。

`实测数据`
`PowerShell`

```powershell
# 识别：init 初始化调试器与目标，reset halt 复位后立刻停住，flash probe 0 读回 flash 描述
& "<OpenOCD>\bin\openocd.exe" -s "<OpenOCD>\share\openocd\scripts" `
  -f interface/cmsis-dap.cfg -f target/stm32f1x.cfg `
  -c "init" -c "reset halt" -c "flash probe 0"
```

`-s` 指向 OpenOCD 自带的 `scripts` 目录。识别结果里关键的三行：

`实测数据`
`Text`

```text
DBGMCU_IDCODE = 0x20036410      → device id 0x410，中容量 F103
flash size    = 64 KiB
DPIDR         = 0x1ba01477      → Cortex-M3 r1p1，6 断点 / 4 观察点
```

**三个值各回答一个问题**：

| 值 | 回答什么 |
|---|---|
| `DBGMCU_IDCODE` 的低 12 位，`0x410` | 芯片是谁——中容量 F103，与 `target/stm32f1x.cfg` 对得上 |
| `flash size = 64 KiB` | flash 有多大——改链接脚本里的 `LENGTH` 时以它为准（第 9.6 小节） |
| `DPIDR = 0x1ba01477` | 内核是谁——Cortex-M3 r1p1，决定可用的指令与断点数量 |

**这三行读不出来就不用往下走**：先查接线与供电，再查调试器是不是被别的进程占着（第 9.7 小节）。

## 9.3 擦除、烧写与校验

程序先用交叉编译器编成 `.elf`。这块板子的编译命令与第 1 节讲的链路一致，
只是不引入 CubeMX 那一套 HAL：

`Bash`

```bash
# 交叉编译（WSL Ubuntu，arm-none-eabi-gcc 13.2.1）
# 工作目录里有 STM32F103C8_FLASH.ld 与 startup_stm32f103xe.s
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -g -nostartfiles --specs=nosys.specs \
  -T STM32F103C8_FLASH.ld startup_stm32f103xe.s 程序.c -o 程序.elf
```

`-nostartfiles` 表示不用工具链自带的启动代码，入口由 `startup_stm32f103xe.s` 提供；
`--specs=nosys.specs` 提供空的系统调用桩——裸机上没有操作系统可以调用。
这两项与第 1.4 小节那份 `cmake` 文件里的取舍是同一件事。

烧写、运行、读回内存可以用一条 OpenOCD 命令做完：

`实测数据`
`PowerShell`

```powershell
# 烧写 + 复位运行 + 读回内存（路径一律用正斜杠，理由见第 9.7 小节）
& "<OpenOCD>\bin\openocd.exe" -s "<OpenOCD>\share\openocd\scripts" `
  -f interface/cmsis-dap.cfg -f target/stm32f1x.cfg `
  -c "init" -c "reset halt" -c "arm semihosting enable" `
  -c "flash write_image erase <工作区>/程序.elf" `
  -c "reset run" -c "sleep 2000" -c "halt" `
  -c "mdw 0x20000000 8" -c "shutdown"
```

**烧写只有一条命令**：`flash write_image erase` 先擦后写，写完自动校验一遍。
想单独再校验一次时用 `verify_image`。实测的耗时如下：

`实测数据`

| 操作 | 数字 |
|---|---|
| `flash write_image erase` 写入 1540 字节（含校验） | **0.20 s**（约 7.5 KiB/s） |
| 再 `verify_image` 同样的 1540 字节 | **0.09 s**（约 16.5 KiB/s） |

`待确认`

按 7.5 KiB/s 折算，写满 64 KiB 大约需要十几秒；本教材没有实测过满片写入。

**不必先整片擦除**：`flash write_image erase` 会擦掉涉及到的扇区。
需要整片擦除（`stm32f1x mass_erase 0`）的场合只有两个：交付前清空，
或者要看第 9.4 小节那种空片现场。

**只写 flash 主区，不碰 option bytes 与读保护**：烧写落在 `0x08000000` 起的主区；
option bytes 区在 `0x1FFFF800`，能正常读出内容，说明读保护位（RDP）没有被置上。

`待确认`

读保护一旦置上，调试访问会被拒绝，恢复要整片擦除并重新解锁；本教材没有实测这一状态，
操作时避开它。

## 9.4 空片复位是什么现场

整片擦除之后，flash 里全是 `0xFF`；擦除成功时 OpenOCD 打一行 `stm32x mass erase complete`。

`实测数据`
`PowerShell`

```powershell
# 整片擦除；复位后的 pc / sp 用 reg 读，flash 开头用 mdw 读，见下面两行输出
& "<OpenOCD>\bin\openocd.exe" -s "<OpenOCD>\share\openocd\scripts" `
  -f interface/cmsis-dap.cfg -f target/stm32f1x.cfg `
  -c "init" -c "stm32f1x mass_erase 0" -c "shutdown"
```

`实测数据`
`Text`

```text
0x08000000: ffffffff ffffffff ffffffff ffffffff     ← 全片擦净
复位后：pc = 0xfffffffe   sp = 0xfffffffc
```

向量表被擦掉了，硬件照样从 flash 开头取那两个数：两个 `0xFFFFFFFF` 的最低两位被忽略，
于是 `MSP = 0xFFFFFFFC`、`PC = 0xFFFFFFFE`，取不到有效指令，处理器直接进 `HardFault`。

**这是排查「程序没烧进去」最快的判据**：复位后 `pc` 是 `0xfffffffe`，说明 flash 还是空的。
向量表为什么必须放在 flash 最前面，见《07-更底层/07-链接脚本与启动代码.md》第 2.4 小节；
这里的现场与「`KEEP` 被去掉」是同一副，见《07-更底层/07-链接脚本与启动代码.md》第 5.1 小节。

## 9.5 程序怎么「打印」：semihosting

板上没有串口，**程序的输出只有一条通道**：ARM 为调试留的 semihosting。
约定是 `r0` 放功能号、`r1` 放参数，`bkpt 0xAB` 陷入调试器，由 OpenOCD 把内容转发到自己的控制台。
功能号 `0x04` 是 `SYS_WRITE0`：把 `r1` 指向的、以 0 结尾的字符串写出去。

`C`

```c
/* sh_puts.c    Cortex-M 的最小输出通道：semihosting 的 SYS_WRITE0

   编译（WSL Ubuntu，arm-none-eabi-gcc 13.2.1）：
     arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -g -nostartfiles --specs=nosys.specs \
       -T STM32F103C8_FLASH.ld startup_stm32f103xe.s sh_puts.c -o sh_puts.elf

   运行（Windows，openocd 0.12.0）：会话里必须有 -c "arm semihosting enable"，
   否则 bkpt 0xAB 只是一条断点指令，看不到任何输出：
     openocd -f interface/cmsis-dap.cfg -f target/stm32f1x.cfg \
       -c "init" -c "reset halt" -c "arm semihosting enable" \
       -c "flash write_image erase <工作区>/sh_puts.elf" -c "reset run" -c "shutdown" */
#include <stdint.h>

/* semihosting 的调用约定：r0 = 功能号，r1 = 参数，bkpt 0xAB 陷入调试器。
   两个寄存器变量必须与 asm 的约束对上：r0 写成 "+r"，编译器才知道它被改过；
   漏掉约束时优化器会以为 r0 里还是 4，把它换成别的寄存器。 */
static void sh_puts(const char *s)
{
    register uint32_t r0 __asm__("r0") = 4;               /* 功能号 0x04：SYS_WRITE0 */
    register uint32_t r1 __asm__("r1") = (uint32_t)s;     /* 参数：字符串地址 */
    __asm__ volatile ("bkpt 0xAB" : "+r"(r0) : "r"(r1) : "memory");
}

int main(void)
{
    sh_puts("hello from STM32F103C8\n");
    for (;;) { }        /* 裸机上 main 不返回 */
}
```

**三处必须同时成立，缺一处就看不到输出**：

| 位置 | 要做的事 |
|---|---|
| 程序 | `bkpt 0xAB`，`r0` 放功能号、`r1` 放参数 |
| OpenOCD 会话 | 加 `-c "arm semihosting enable"` |
| 看输出的地方 | **OpenOCD 自己的控制台**，不是另一个窗口 |

> [!WARNING]
> **寄存器变量不写进 asm 的操作数，会被优化器改坏。**
> 上面 `sh_puts()` 里 `"+r"(r0)` 这一处不能省：省掉它，编译器不知道 `bkpt` 会用到 `r0`，
> `-O2` 下会把它换成别的值，症状是 OpenOCD 报 `Unsupported SemiHosting SWI`。

**裸机上没有 `printf`**：newlib 的 `printf` 需要 `_write` 之类的系统调用桩，
桩没接上时它返回 0 且什么都不输出。要打印数字就手写十进制与十六进制转换；
完整的一份（含主机侧回退到 `fputs`，同一份源码在 PC 上也能编）见
《07-更底层/03-寄存器、位与 volatile.md》第 2.4 小节。

## 9.6 跑不起来的案例：链接脚本的内存大小

素材里的 `STM32F103XX_FLASH.ld` 是给 **F103xC**（RAM 48 KB、flash 256 KB）写的，
这块板子是 **C8**（RAM 20 KB、flash 64 KB）。把它原样拿来编 C8 的程序，
**链接器一句话都不说**：

`实测数据`
`Bash`

```bash
# 两个脚本只差 MEMORY 里那两个数
grep -n "LENGTH" STM32F103C8_FLASH.ld
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -nostartfiles --specs=nosys.specs \
  -T STM32F103XX_FLASH.ld startup_stm32f103xe.s boot.c -o probe_xc.elf
arm-none-eabi-nm probe_xc.elf | grep _estack
```

`实测数据`
`Text`

```text
RAM    (xrw)    : ORIGIN = 0x20000000,   LENGTH = 20K
FLASH (rx)      : ORIGIN = 0x8000000, LENGTH = 64K

2000c000 R _estack
```

`_estack` 算出来是 `0x2000C000`，比这块芯片 RAM 的顶端 `0x20005000` 高出 28 KB。
把它烧进板子，复位之后的表现：

`实测数据`

| 项 | 用错脚本（RAM 48K） | 把 `LENGTH` 改成 20K |
|---|---|---|
| `_estack` | `0x2000C000`，超出真实 RAM | `0x20005000` |
| 复位后现场 | `current mode: Handler HardFault`，`pc = 0x08000314` | 正常进 `main` |
| 结果 | 第一次压栈就越界，连 `main` 都进不去 | `.data` / `.bss` 检查全部通过 |

**这不是「结果不对」，而是「根本跑不起来」**：`MSP` 指向芯片上不存在的一段地址，
从复位到第一次压栈之间的任何一步写栈都会让总线报错，处理器转进 `HardFault`；
而进入 `HardFault` 同样要压栈，于是在故障里循环。

拿到一个别的型号的工程时，按这三步核对：

| 步骤 | 做什么 |
|---|---|
| 1 | 确认芯片型号：`.ioc` 里的型号，或 `flash probe 0` 读回的 `device id` |
| 2 | 改 `MEMORY` 的两行：长度按芯片手册或 `flash size` 的读数写 |
| 3 | 核对栈顶：`arm-none-eabi-nm` 看 `_estack`，应正好等于 RAM 顶端 |

> [!CAUTION]
> 链接脚本里的 `LENGTH` 是「这块芯片有多少」，不是「这个程序要多少」。
> **写小了对不上，链接器会报溢出；写大了它不报错**，只会把栈指针放到不存在的内存上。
> 因此这一条只有真板能证明：QEMU 的近似板 RAM 更大，什么毛病都看不出来。

诊断思路的完整分析见《07-更底层/07-链接脚本与启动代码.md》第 5.5 小节。

## 9.7 两条纪律

**一、`-c` 参数里的路径一律用正斜杠。**

OpenOCD 的 `-c` 按 Tcl 规则解析，反斜杠是转义符。把路径写成 `C:\work\app.elf` 时，
`\w`、`\a` 会被当成转义序列吃掉，报出来的错与「文件不存在」相同，
排查时会一直往路径写错的方向找。写成 `C:/work/app.elf` 就没有这个问题。

> [!WARNING]
> 编译在 WSL 里做、烧写在 Windows 侧做时，交给 OpenOCD 的必须是 Windows 侧看得见的那条路径，
> 而且其中的反斜杠要换成正斜杠——这两件事要一起检查。

**二、调试器同一时刻只能被一个进程占用。**

板子只有一块，SWD 链路只有一条。上一个 OpenOCD 没有退出时再起一个，
两个会话会互相打断，表现是其中一方报错或者会话中途失效。
排查连接问题时，第一步是确认没有别的 OpenOCD 或 IDE 调试会话还开着。

# 附录 D 复现本章节的 `volatile` 实测

**环境**：`gcc` 15.2.0（MinGW-w64），Windows x64。以下命令在源码所在目录下执行。

## D.1 源码

`C`

```c
/* volatile_flag.c    编译：gcc -std=c23 -O0 -S volatile_flag.c -o O0.s */
/*                    再编一次：gcc -std=c23 -O2 -S volatile_flag.c -o O2.s */
int flag_normal = 0;                    /* 普通变量 */
volatile int flag_volatile = 0;         /* 每次访问都要真的读写内存 */

/* 等待标志位置位 */
int wait_normal(void)   { while (flag_normal == 0) { }   return 1; }
int wait_volatile(void) { while (flag_volatile == 0) { } return 1; }
```

**C 与 C++ 写法相同**：这段代码可以原样用 `g++ -std=c++17 -S` 编译。

## D.2 两条编译命令

`Bash`

```bash
gcc -std=c23 -O0 -S volatile_flag.c -o O0.s
gcc -std=c23 -O2 -S volatile_flag.c -o O2.s
```

## D.3 `-O0` 的完整输出

`Assembly`

```asm
wait_normal:
	nop
.L2:
	movl	flag_normal(%rip), %eax
	testl	%eax, %eax
	je	.L2

wait_volatile:
	nop
.L5:
	movl	flag_volatile(%rip), %eax
	testl	%eax, %eax
	je	.L5
```

**两者都是「读内存 → 判断 → 跳回」，行为一致。**

## D.4 `-O2` 的完整输出

`Assembly`

```asm
wait_normal:
	movl	flag_normal(%rip), %eax
	testl	%eax, %eax
	je	.L3
	movl	$1, %eax
	ret
.L3:
	jmp	.L3

wait_volatile:
.L6:
	movl	flag_volatile(%rip), %eax
	testl	%eax, %eax
	je	.L6
	movl	$1, %eax
	ret
```

**`wait_normal` 在 `.L3` 处原地跳转，不再读内存；
`wait_volatile` 每次循环都重新读内存。**
