# 第 1 章 基本概念

配置调试环境时遇到的多数困惑，源于对以下五个概念的关系不清楚。

| 概念 | 定义 | 示例 |
|---|---|---|
| **编译器** | 将源代码转换为可执行文件的程序 | `gcc`、`g++`、`cl.exe`（MSVC） |
| **调试信息** | 编译时写入可执行文件的辅助数据，用于建立机器码与源码的对应关系 | GCC 的 **DWARF**、MSVC 的 **PDB** |
| **调试器** | 实际执行调试动作的程序 | **GDB**、**LLDB**、**VS2022 调试引擎** |
| **调试适配器** | 将 VS Code 的通用调试指令翻译为目标调试器的指令 | `cppdbg`、`cppvsdbg`、`lldb` |
| **VS Code 扩展** | 提供调试适配器的插件 | C/C++ 扩展、CodeLLDB |

## 1.1 核心约束：调试信息格式必须匹配

调试器只能识别与自身兼容的调试信息格式：

| 编译器 | 调试信息格式 | GDB | LLDB | VS2022 调试引擎 |
|---|---|---|---|---|
| `gcc` / `g++` | DWARF | 支持 | **支持** | 不支持 |
| `cl.exe` | PDB | 不支持 | **支持** | 支持 |

由此得出两点结论：

1. **编译器决定了可用的调试器**。使用 GCC 编译，则必须用 GDB 或 LLDB 调试；
   使用 MSVC 编译，则必须用 VS2022 调试引擎或 LLDB 调试。两者不可混用。
2. **LLDB 是例外**，它同时支持 DWARF 与 PDB（**实测**）。
   这意味着 CodeLLDB 扩展可以同时承担两条路线的调试工作。

## 1.2 核心约束：Windows 中文路径对 GDB 的限制

**这一节的内容决定了你在本项目中的调试器选择，建议在开始配置前先读完。**

在路径包含中文的 Windows 工程中，**GDB（`cppdbg`）无法启动调试**。这与配置是否正确无关，
是 GDB 自身的限制。

### 原因

GDB 在 Windows 上通过 **MI 协议**接收文件名时，期望的是 **ANSI 代码页**
（中文系统为 936 / GBK）编码的字节，而 VS Code 发送的是 **UTF-8** 字节。
两者不一致时，GDB 无法打开该文件。

实测对照（通过 MI 协议发送 `-file-exec-and-symbols`，与 VS Code 的行为一致）：

| 送入 MI 的路径 | 结果 |
|---|---|
| 纯英文路径 | 成功 |
| 中文路径，UTF-8 字节（**即 VS Code 的行为**） | **失败** |
| 中文路径，GBK / ANSI 字节 | 成功 |

### 影响范围

| 对象 | 是否受影响 |
|---|---|
| **可执行文件路径**（`program` 字段） | **受影响**。调试完全无法启动 |
| **源码路径**（断点位置） | **不受影响**。VS Code 发送的 UTF-8 源码路径恰好是 GDB 所能接受的（**实测**） |

因此判断标准很简单：**工程路径中只要含有任何一段中文，GDB 路线就用不了。**

> **注意**：这只影响可执行文件所在的路径。若把构建产物输出到全英文路径，
> 而源码仍留在中文路径，GDB 是可以正常工作的（**实测**）。

### 三种调试器在含中文路径下的实际表现

| 调试器 | 调试类型 | 中文路径下 | 说明 |
|---|---|---|---|
| **VS2022 调试引擎** | `cppvsdbg` | **可用**（**实测**） | 微软自研引擎，原生使用 Unicode 路径，不经过 MI 协议 |
| **LLDB**（CodeLLDB） | `lldb` | **可用**（**实测**） | 断点命中、中文内容显示均正常 |
| **GDB** | `cppdbg` | **不可用** | 本节的限制 |

### 无法通过配置解决

下列方法均已验证**无效**，不必再尝试：

| 尝试的方法 | 结果 |
|---|---|
| `set host-charset UTF-8` / `CP936` / `GBK` | 无效 |
| `set charset UTF-8` / `set target-charset UTF-8` | 无效 |
| 改用正斜杠、反斜杠或混合分隔符 | 无效（三种均失败） |
| 8.3 短路径（如 `K:\C6D3CF~1`） | 依赖系统是否启用短名，本机未启用，不可用 |
| 修改 cpptools 的设置项 | 其全部设置项中**没有**任何编码相关项 |
| 修改 `cppdbg` 的配置字段 | 其 40 个字段中**没有**任何编码相关字段 |

字符集转换发生在 MI 协议的解析层，不受上述任何设置控制。

详细的排查步骤见第 9 章第 13 节。

## 1.3 本文覆盖的两种开发形式

| 形式 | 适用场景 | 构建方式 | 调试配置要点 |
|---|---|---|---|
| **单文件** | 语法练习、算法验证、课程作业 | 直接调用编译器 | 使用 `${file}` 等变量，配置对任意文件生效 |

# 第 3 章 从零搭建

## 开始之前：PATH 是什么，怎么配置

**本章的每一步安装完成后，都需要把程序加入 PATH。** 这里先把它讲清楚，后面不再重复。

### 什么是 PATH

PATH 是 Windows 的一个**环境变量**，内容是一串用分号隔开的目录。
当你在命令行输入 `gcc` 时，系统会依次到 PATH 里的每个目录中查找 `gcc.exe`；
找到就运行，全都没找到就报「不是内部或外部命令」。

**一个类比**：PATH 相当于系统的一份「常用程序地址簿」。
把程序所在目录写进这份地址簿，之后在任何位置都能直接用程序名调用它，
不必每次输入完整路径。

### 为什么本文强调 PATH

本工作区的配置文件**一律直接使用程序名**，而不是写死安装路径：

```jsonc
"command": "cmake"        // 直接调用 PATH 中的程序
                          // 而不是写死成 "<CMake>\\bin\\cmake.exe"
```

这样做的目的是**让配置文件可以直接复制到别的计算机使用**。
代价是要求这些程序已经在 PATH 中——文件名对了，但系统找不到它，任务就会失败。

### 查看当前的 PATH

在 PowerShell 中执行：

```powershell
# 查看完整 PATH（分号分隔，内容较长）
$env:PATH

# 逐行显示，便于阅读
$env:PATH -split ';' | Where-Object { $_ }
```

### 确认某个程序是否已在 PATH 中

```powershell
foreach ($t in 'gcc','g++','gdb','cmake','ninja','pwsh') {
  $c = Get-Command $t -ErrorAction SilentlyContinue
  "{0,-8} {1}" -f $t, $(if ($c) { $c.Source } else { '（不在 PATH 中）' })
}
```

输出中能看到完整路径，即表示该程序已在 PATH 中；
显示「不在 PATH 中」则需要进行下一步。

### 如何把程序加入 PATH

#### 方法一：图形界面（推荐给初学者）

1. 按 `Win + R`，输入 `sysdm.cpl`，回车
2. 切换到「高级」选项卡，点击「环境变量」
3. 在上方「用户变量」中找到 `Path`，双击
4. 点击「新建」，填入程序所在的**目录**（不是 exe 文件的完整路径）
5. 逐级点击「确定」关闭所有对话框

> **注意**：填的应当是**目录**。例如要使用 `<MinGW>\bin\gcc.exe`，
> 应填入 `<MinGW>\bin`，而不是 exe 本身的路径。

#### 方法二：PowerShell 命令

```powershell
# 把 <目录> 换成实际目录，例如 C:\mingw64\bin
$dir = '<目录>'

# 读取当前用户的 PATH，追加新目录（不重复添加）
$old = [Environment]::GetEnvironmentVariable('PATH', 'User')
if ($old -notlike "*$dir*") {
    [Environment]::SetEnvironmentVariable('PATH', "$old;$dir", 'User')
    "已添加：$dir"
} else {
    "已存在，未重复添加：$dir"
}
```

> **说明**：上面的写法修改的是**用户级** PATH，**不需要管理员权限**。
> 若改为 `'Machine'` 则是机器级 PATH，需要以管理员身份运行 PowerShell。
> 两者效果相同，用户级更容易撤销。

### 关键：修改 PATH 后必须重启

**PATH 的修改不会影响已经打开的进程。** 已经运行的终端、VS Code
都持有启动时的那份 PATH 副本，因此：

| 需要做 | 原因 |
|---|---|
| 关闭并重新打开 PowerShell 窗口 | 让它读到新的 PATH |
| **完全重启 VS Code** | 同上；这是「刚装完程序但 VS Code 找不到」的最常见原因 |

> **实测现象**：安装 CMake 后立刻在已打开的 VS Code 中按 F5，
> 任务会报找不到 `cmake`；完全重启 VS Code 后即恢复正常。
> 本工作区曾因此问题排查过一轮。

### PATH 相关问题的排查顺序

出现「找不到 xxx」时，按下列顺序检查：

1. **该程序是否真的安装了？** 去安装目录看看 exe 是否存在
2. **它在不在 PATH 中？** 用上面「确认某个程序是否已在 PATH 中」的命令
3. **加了 PATH 但没生效？** 重启终端与 VS Code
4. **仍然不行？** 检查 PATH 中填的**是目录还是文件**、有没有多余空格或引号
5. **终极手段**：在配置中临时写完整路径验证一下，确认不是别的问题

> **说明**：本文的示例配置**故意不写完整路径**，以保持可移植性。
> 若你的环境确实不便配置 PATH，也可以把 `"command": "cmake"`
> 改回完整路径——这样配置就只适用于你自己的机器了，但能立刻工作。

### 常见错误

| 错误写法 | 问题 |
|---|---|
| `C:\mingw64\bin\gcc.exe` | 填了文件而不是目录 |
| `"C:\mingw64\bin"` | 多了一对引号（图形界面中会自动处理，命令行中不要加） |
| `C:\mingw64\bin;` | 末尾多一个分号（虽不影响使用，但不规范） |
| 目录已失效 | 程序被移动或卸载后，PATH 中的记录不会自动清除 |

## 步骤 1 安装 PowerShell 7

**必需项。**

**本步骤应当优先完成。** 后续全部命令行操作，以及 VS Code 的构建任务脚本，
均以 PowerShell 7（`pwsh`）为准。

### 1.1 为什么使用 PowerShell 7

Windows 自带的两个命令行工具在实际使用中均存在明确限制：

| 工具 | 限制 |
|---|---|
| **`cmd.exe`** | 按"当前代码页"逐字节解析批处理文件，UTF-8 编码的中文注释会被误读为控制字符。其参数转义规则与 VS Code 的任务传参机制不兼容，会直接导致任务启动失败（实测案例见第 9 章第 4 节） |
| **Windows PowerShell 5.1**（`powershell.exe`） | 读取无 BOM 的 UTF-8 脚本文件时按 ANSI 代码页解析，中文内容会变为乱码 |

PowerShell 7 的对应优势：

- 默认以 UTF-8 读写脚本文件与输出
- 参数转义规则明确，与 VS Code 的任务传参机制兼容
- 跨平台，同一份 `.ps1` 脚本可在 Windows、Linux、macOS 上运行
- 处于积极维护状态；`cmd.exe` 与 Windows PowerShell 5.1 已仅为维护
- 是当前工具链与自动化脚本的主要目标环境

> **说明**：以上并非风格偏好。本工作区在搭建过程中，因 `cmd.exe` 的上述两点问题

## 步骤 2 安装编译器（MinGW-w64）

**按需项。** 若你只打算使用 MSVC 路线（即只用 Visual Studio 的编译器），
可以跳过本步骤，直接安装 Visual Studio（见步骤 4 末尾的说明）。

不过建议同时安装两套工具链：GDB 路线配置轻量、跨平台，且与多数公开教程一致。

### 2.1 安装

从 [winlibs.com](https://winlibs.com/) 下载
**UCRT + POSIX threads + SEH** 组合的 x86_64 版本，
解压至一个**全英文、无空格**的目录，例如 `C:\mingw64`。

该目录即前文所说的 `<MinGW>`。

> **说明**：本工作区使用 winlibs 的打包版，因为它免安装、解压即用，
> 且 UCRT 运行时与 Windows 自带的一致。也可选用 MSYS2 或 w64devkit，
> 只要其中包含 `gcc`、`g++`、`gdb` 三者即可。

### 2.2 加入 PATH

把 `<MinGW>\bin` 加入 PATH（方法见本章开头）。这是**必须**的一步，
否则后续所有 `gcc` / `g++` / `gdb` 命令都会提示找不到。

### 2.3 验证

**重新打开一个 PowerShell 窗口**（让新的 PATH 生效），然后执行：

```powershell
gcc --version
g++ --version
gdb --version
```

预期输出形如 `gcc (MinGW-W64 ...)`、`g++ (...)`、`GNU gdb (GDB) ...` 的版本信息。
本文以 gcc 15.2.0 与 gdb 16.3 编写（**实测**），但**版本号不必一致**。

若提示找不到命令，回到本章开头的「PATH 相关问题的排查顺序」。

### 2.4 如何找到实际路径

安装完成后，用这条命令直接问出路径，不必自己回忆解压到了哪里：

```powershell
(Get-Command gcc).Source        # 例如 C:\mingw64\bin\gcc.exe
(Get-Command gdb).Source
```

把结果去掉末尾的 `\bin\gcc.exe` 部分，剩下的就是 `<MinGW>`。

> **说明**：建议使用纯英文路径的原因见第 9 章第 1 节。
> 中文路径不影响调试功能本身，但会引入若干无谓的排查成本。

## 步骤 3 安装 CMake 与 Ninja

**按需项。** 只有需要构建 CMake 工程时才必须。
**只调试单个 `.c` / `.cpp` 文件的话，可以完全跳过本步骤**——
本工作区的单文件配置已改为不依赖 CMake。

### 3.1 CMake


### 3.2 Ninja（可选）

Ninja 是 CMake 的一种构建后端。**不安装也能用**——CMake 可以改用

## 步骤 6 编写 `tasks.json`

`launch.json` 中的 `preLaunchTask` 将引用此处定义的任务名，
**两处的名称必须完全一致**。

关键要求：编译参数中必须包含 `-g`（GCC）或 `/Zi`（MSVC）。
缺少该参数则不会生成调试信息，调试器打开后无法定位源码。

```jsonc
{
  "version": "2.0.0",
  "tasks": [
    // 准备输出目录（编译器不会自动创建目录）
    // 使用 cmake -E make_directory 而非 cmd /c mkdir：
    // 前者参数为单一值，不受 VS Code 参数转义规则影响，且幂等。
    {
      "label": "准备: 创建输出目录",
      "type": "process",
      "command": "cmake",
      "args": ["-E", "make_directory", "${workspaceFolder}\\build\\gcc"],
      "problemMatcher": [],
      "presentation": { "reveal": "silent", "panel": "shared", "close": true }
    },

    // 单文件：gcc 编译
    // 注意 -o 的输出路径必须全部使用【反斜杠】，原因见第 9 章第 5 节。
    // 字符集参数用于避免中文输出乱码，原因见第 9 章第 6 节。
    {
      "label": "构建: 单文件 (gcc)",
      "type": "process",
      "command": "gcc",
      "args": [
        "-std=gnu17", "-g", "-O0", "-Wall", "-Wextra",
        "-finput-charset=UTF-8", "-fexec-charset=GBK",
        "${file}",
        "-o", "${workspaceFolder}\\build\\gcc\\${fileBasenameNoExtension}.exe"
      ],
      "options": { "cwd": "${fileDirname}" },
      "dependsOn": ["准备: 创建输出目录"],
      "problemMatcher": "$gcc",
      "presentation": { "reveal": "silent", "panel": "shared", "clear": true }
    },

    // CMake：配置 + 编译（用 dependsOn 串联）
    // 直接调用 PATH 中的 cmake，不写死安装路径
    {
      "label": "CMake: 配置 (MinGW)",
      "type": "process",
      "command": "cmake",
      "args": ["--preset", "mingw-gdb"],
      "options": { "cwd": "${workspaceFolder}" },
      "problemMatcher": [],
      "presentation": { "reveal": "silent", "panel": "shared", "clear": true }
    },
    {
      "label": "CMake: 编译 (MinGW)",
      "type": "process",
      "command": "cmake",
      "args": ["--build", "--preset", "mingw-gdb"],
      "options": { "cwd": "${workspaceFolder}" },
      "problemMatcher": "$gcc",
      "presentation": { "reveal": "silent", "panel": "shared", "clear": true }
    },
    {
      "label": "构建: CMake 工程 (MinGW)",
      "dependsOrder": "sequence",
      "dependsOn": ["CMake: 配置 (MinGW)", "CMake: 编译 (MinGW)"],
      "problemMatcher": []
    }
  ]
}
```

编写要点：

| 要点 | 说明 |
|---|---|
| 使用 `"type": "process"` | 相比 `"type": "shell"`，不经过 shell 解析，参数不会被引号规则破坏 |
| `options.env.PATH` 兜底 | 避免"刚安装 CMake 但尚未重启 VS Code"导致找不到 `cmake` |
| 任务 `label` | 可包含中文、空格与括号，但必须与 `launch.json` 的 `preLaunchTask` 完全一致 |
| 创建目录 | **不要**使用 `cmd /c "if not exist ... mkdir ..."`，原因见下 |
| `-o` 输出路径 | **必须使用反斜杠**（JSON 中写作 `\\`）。路径含中文时，正斜杠会导致 `ld.exe` 报 `cannot open output file`，见第 9 章第 5 节 |

> **注意**：创建目录任务不要写成 `cmd.exe /d /c "if not exist \"...\" mkdir \"...\""`。
> VS Code 的 `process` 任务按 MSVCRT 规则为参数加引号，参数内部的 `"` 会被转义为 `\"`，
> 而 `cmd.exe` 不识别该转义，将报错
> `The filename, directory name, or volume label syntax is incorrect.` 并导致任务失败。
> 使用 `cmake -E make_directory` 可避免此问题，且该命令在目录已存在时同样返回 0。（**实测**）

## 步骤 7 编写 `launch.json`

> **说明**：`launch.json` 并非必需。VS Code 与 C/C++ 扩展支持在无此文件的情况下
> 生成调试配置。若希望避免手工编写，请先阅读第 6 章。

最小可用示例：

```jsonc
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "GDB · 单文件",
      "type": "cppdbg",
      "request": "launch",
      "program": "${workspaceFolder}/build/gcc/${fileBasenameNoExtension}.exe",
      "args": [],
      "cwd": "${fileDirname}",
      "MIMode": "gdb",
      "externalConsole": false,
      "preLaunchTask": "构建: 单文件 (gcc)"
    }
  ]
}
```

其中五个核心字段的作用：

| 字段 | 作用 |
|---|---|
| `type` | 指定调试适配器：`cppdbg` / `cppvsdbg` / `lldb` |
| `request` | `launch` 表示启动新进程；`attach` 表示附加到已有进程 |
| `program` | 待调试的可执行文件路径 |
| `miDebuggerPath` | **`cppdbg` 专用**：`gdb.exe` 的路径；省略则在 PATH 中查找 |
| `preLaunchTask` | 调试前执行的构建任务名，须与 `tasks.json` 中的 `label` 一致 |

常用变量：

| 变量 | 含义 |
|---|---|
| `${file}` | 当前打开文件的完整路径 |
| `${fileBasenameNoExtension}` | 当前文件名（不含扩展名） |
| `${fileDirname}` | 当前文件所在目录 |
| `${workspaceFolder}` | 工作区根目录 |

使用这些变量后，同一份配置对任意文件均成立，无需为每个新文件修改配置。

字段的完整说明见第 5 章。

## 步骤 8 编写 `settings.json`

```jsonc
{
  // 默认智能感知按 GCC 解析。
  // compilerPath 可以省略，cpptools 会自动探测；填了则更明确。
  "C_Cpp.default.compilerPath": "<MinGW>/bin\\gcc.exe",
  "C_Cpp.default.intelliSenseMode": "windows-gcc-x64",
  "C_Cpp.default.cStandard": "c17",

  // CMake Tools
  // cmakePath 写 "cmake" 即表示使用 PATH 中的 cmake，
  // 无需填写安装路径，换台机器也能直接用。
  "cmake.useCMakePresets": "auto",
  "cmake.cmakePath": "cmake",
  "cmake.configureOnOpen": false,
  "cmake.buildBeforeRun": false,

  // 文件与编码
  "files.encoding": "utf8",
  "files.associations": { "*.h": "c" }
}
```

> **说明**：`cmake.cmakePath` 写为绝对路径，是为了在尚未重启 VS Code 时也能正常工作。
> 重启后改为 `"cmake"` 效果相同。

## 步骤 9 编写 `c_cpp_properties.json`

该文件仅影响**代码补全、跳转与波浪线提示**，不影响编译与调试。

```jsonc
{
  "version": 4,
  "configurations": [
    {
      "name": "MinGW-GCC-x64",
      "compilerPath": "<MinGW>/bin/gcc.exe",
      "cStandard": "c17",
      "intelliSenseMode": "windows-gcc-x64",
      "includePath": ["${workspaceFolder}/**"],
      "compileCommands": "${workspaceFolder}/build/mingw/compile_commands.json"
    },
    {
      "name": "MSVC-x64",
      // 该路径包含工具集版本号，Visual Studio 升级后需同步修改
      "compilerPath": "<VS>/VC/Tools/MSVC/<版本号>/bin/Hostx64/x64/cl.exe",
      "cStandard": "c17",
      "intelliSenseMode": "windows-msvc-x64",
      "includePath": ["${workspaceFolder}/**"]
    }
  ]
}
```

> **注意**：`compileCommands` 指向的文件**仅由 Ninja 与 Makefile 生成器产出**。
> Visual Studio 生成器**不会**生成 `compile_commands.json`（**实测**）。
> 因此 MSVC 配置中不应包含该字段。

切换使用哪套配置：`Ctrl+Shift+P` → `C/C++: Select IntelliSense Configuration`。

## 步骤 10 验证

按 `F5` 能停在断点上即表示配置成功。更严格的验证方式如下（不依赖 VS Code 界面）：

```powershell
# 1. 编译（C 用 gcc，C++ 改为 g++）
gcc -g -O0 hello.c -o build\gcc\hello.exe

# 2. 用 gdb 批处理方式验证断点（写入脚本文件以避免命令行引号问题）
@'
set pagination off
break main
run
print 1+1
quit
'@ | Set-Content "$env:TEMP\v.gdb" -Encoding UTF8

gdb --batch -x "$env:TEMP\v.gdb" build\gcc\hello.exe
```

预期输出包含断点命中信息与 `$1 = 2`。若通过，则说明工具链工作正常，
后续问题均属于 VS Code 配置层面。

# 第 5 章 `launch.json` 字段详解

本章逐一说明 `launch.json` 中调试配置的各个字段。
字段清单来源于各扩展 `package.json` 中 `contributes.debuggers` 的定义（**实测**），
而非推测。

三个调试适配器各自支持的字段数量如下：

| 调试适配器 | 所属扩展 | launch 字段数 | attach 字段数 |
|---|---|---|---|
| `cppdbg` | ms-vscode.cpptools | 40 | 22 |
| `cppvsdbg` | ms-vscode.cpptools | 17 | 8 |
| `lldb` | vadimcn.vscode-lldb（CodeLLDB） | 26 | — |

> **说明**：同时使用多个适配器时，`type` 决定哪些字段有效。
> 例如 `miDebuggerPath` 属于 `cppdbg`，写入 `cppvsdbg` 配置不会生效，也不会报错。

## 5.1 所有适配器通用字段

这些字段由 VS Code 本身处理，不属于任何调试适配器。

| 字段 | 类型 | 作用 |
|---|---|---|
| `name` | string | 配置名称，显示在 F5 的下拉列表中。同一文件内不可重复 |
| `type` | string | 调试适配器：`cppdbg`、`cppvsdbg` 或 `lldb` |
| `request` | string | `launch` 启动新进程；`attach` 附加到已有进程 |
| `preLaunchTask` | string | 调试前执行的构建任务名，须与 `tasks.json` 的 `label` 完全一致 |
| `postDebugTask` | string | 调试结束后执行的任务 |
| `presentation` | object | 调试会话在界面中的呈现方式（分组、顺序等） |
| `internalConsoleOptions` | string | 内部控制台的行为：`neverOpen`、`openOnSessionStart`、`openOnFirstSessionStart` |
| `serverReadyAction` | object | 调试目标启动后自动在浏览器打开 URL（Web 场景使用） |
| `windows` / `linux` / `osx` | object | 按操作系统覆盖上述任何字段，实现一份配置跨平台 |

**跨平台写法示例**：

```jsonc
{
  "name": "C/C++ · 跨平台",
  "type": "cppdbg",
  "request": "launch",
  "program": "${workspaceFolder}/build/app",
  "windows": {
    "program": "${workspaceFolder}/build/app.exe",
    "MIMode": "gdb",
    "externalConsole": false
  },
  "linux": {
    "MIMode": "gdb"
  },
  "osx": {
    "MIMode": "lldb"
  }
}
```

## 5.2 目标程序与运行环境

三个适配器均支持。

| 字段 | 类型 | 作用 | 备注 |
|---|---|---|---|
| `program` | string | 待调试的可执行文件路径 | **必需**。调试器据此加载符号 |
| `args` | array | 传给程序的命令行参数 | `["arg1", "arg2"]` |
| `cwd` | string | 程序的工作目录 | 影响程序中的相对路径 |
| `environment` | array | 追加的环境变量 | 格式为 `[{ "name": "...", "value": "..." }]` |
| `envFile` | string | 从文件读取环境变量 | 文件格式为 `KEY=VALUE`，`#` 为注释 |
| `stopAtEntry` | boolean | 是否在 `main` 入口处暂停 | 仅 `launch` 有效；默认 `false` |
| `externalConsole` | boolean | 是否使用独立控制台窗口 | `false` 使用 VS Code 集成终端 |
| `logging` | object | 日志输出配置，见 5.9 | |

> **注意**：`environment` 的格式是 `[{ "name": "X", "value": "Y" }]`，
> **不是** `[{ "X": "Y" }]`。格式错误不会报错，环境变量会静默不生效。

## 5.3 GDB / LLDB 连接配置（`cppdbg` 专用）

| 字段 | 类型 | 作用 |
|---|---|---|
| `MIMode` | string | 目标调试器类型：`gdb` 或 `lldb` |
| `miDebuggerPath` | string | 调试器可执行文件路径。省略则在 PATH 中查找 |
| `miDebuggerArgs` | array | 传给调试器本身的附加参数 |
| `stopAtConnect` | boolean | 连接后是否立即暂停（`attach` 场景） |
| `avoidWindowsConsoleRedirection` | boolean | 置 `true` 可禁用 Windows 下集成终端的控制台重定向 |

## 5.4 GDB / LLDB 命令定制（`cppdbg` 专用）

| 字段 | 类型 | 作用 |
|---|---|---|
| `setupCommands` | array | 调试器启动后、程序运行前执行的命令序列 |
| `customLaunchSetupCommands` | array | **替换**默认的启动命令序列（用于附加等特殊场景） |
| `launchCompleteCommand` | string | 启动完成后执行的命令：`exec-run`、`exec-continue` 或 `None` |

`setupCommands` 中每个元素的格式为
`{ "text": "命令", "description": "说明", "ignoreFailures": true|false }`。

**`setupCommands` 的典型用途：**

```jsonc
"setupCommands": [
  // 1. 启用整齐打印（对 MI 输出生效）
  { "description": "为 MI 输出启用整齐打印",
    "text": "-enable-pretty-printing", "ignoreFailures": true },

  // 2. 让 GDB 能显示 C++ 标准库容器内容（详见下方说明）
  { "description": "将 libstdc++ 的 pretty-printer 加入 Python 搜索路径",
    "text": "python import sys, glob, os, gdb; sys.path += glob.glob(os.path.join(os.path.dirname(os.path.dirname(gdb.PYTHONDIR)), 'gcc-*', 'python'))",
    "ignoreFailures": true },
  { "description": "注册 libstdc++ pretty-printer",
    "text": "python import libstdcxx.v6",
    "ignoreFailures": true },

  // 3. 关闭分页，避免输出停在 --More--
  { "description": "关闭分页", "text": "set pagination off", "ignoreFailures": true }
]
```

> **关于 `-enable-pretty-printing` 的重要说明**（**实测**）
>
> 公开资料常称"加上 `-enable-pretty-printing` 即可让 `std::vector` 整齐显示"。
> 该说法**不完整**。此命令的作用是"允许 MI 输出使用 pretty-printer"，
> 而 **MinGW 版 GDB 通常未将 libstdc++ 的 printer 脚本放入默认搜索路径**，
> 此时没有 printer 可供使用，该命令不产生任何效果。
>
> 实测对比（MI 协议输出，即 VS Code 实际接收的数据）：
>
> | 配置 | VS Code 收到的值 |
> |---|---|
> | 仅 `-enable-pretty-printing` | `value="{...}"`，界面显示为不可读的可展开节点 |
> | 加上上述两条 `python` 命令 | `value="std::vector of length 5, capacity 5"`，并带 `displayhint="string"` |
>
> printer 脚本的实际位置为 `<MinGW>\share\gcc-<版本>\python\libstdcxx\v6\printers.py`。
> 配置中使用 `glob` 匹配版本号，GCC 升级后无需修改。
> 路径不存在时该命令会报错，但 `ignoreFailures: true` 会使其被忽略，不影响调试。

## 5.5 源码与符号路径映射

| 字段 | 类型 | 适用 | 作用 |
|---|---|---|---|
| `sourceFileMap` | object | `cppdbg`、`cppvsdbg` | 将调试信息中的编译期路径映射到本地路径 |
| `additionalSOLibSearchPath` | string | `cppdbg` | GDB/LLDB 查找 `.so` 文件的路径，分号分隔 |
| `symbolLoadInfo` | object | `cppdbg` | 控制共享库符号的加载策略 |
| `symbolSearchPath` | string | `cppvsdbg` | 查找 `.pdb` 文件的路径，分号分隔 |
| `symbolOptions` | object | `cppvsdbg` | 符号服务器、缓存目录、模块过滤等 |
| `requireExactSource` | boolean | `cppvsdbg` | 要求源码与 PDB 完全一致才允许调试 |
| `debuginfod` | object | `cppdbg` | 从 debuginfod 服务器自动下载符号（主要用于 Linux） |

`sourceFileMap` 的典型用途是容器或远程调试时路径不一致：

```jsonc
"sourceFileMap": { "/mnt/c": "C:\\" }
```

`symbolOptions` 的完整形式：

```jsonc
"symbolOptions": {
  "searchPaths": ["C:\\src\\MyProject\\bin\\debug", "https://my-symbols-server"],
  "searchMicrosoftSymbolServer": true,
  "cachePath": "%TEMP%\\symcache",
  "moduleFilter": {
    "mode": "loadAllButExcluded",
    "excludedModules": ["DoNotLookForThisOne*.dll"]
  }
}
```

## 5.6 VS2022 调试器专用字段（`cppvsdbg`）

| 字段 | 类型 | 作用 |
|---|---|---|
| `console` | string | 程序控制台类型：`internalConsole`、`integratedTerminal`、`externalTerminal` |
| `symbolSearchPath` | string | 查找 `.pdb` 的路径 |
| `requireExactSource` | boolean | 要求源码与 PDB 完全一致 |
| `symbolOptions` | object | 符号服务器与模块过滤 |
| `visualizerFile` | string | `.natvis` 文件路径，用于自定义对象的显示方式 |
| `dumpPath` | string | Windows 内存转储文件路径（用于事后调试） |
| `enableDebugHeap` | boolean | 启用调试堆，辅助检测内存问题 |
| `envFile` | string | 从文件读取环境变量 |

> **说明**：`visualizerFile` 与 `envFile` 为 `cppdbg` 与 `cppvsdbg` **共有**。
> `showDisplayString` 则**仅属于 `cppdbg`**，写入 `cppvsdbg` 配置不会生效。

`cppvsdbg` 使用 `console` 而非 `externalConsole` 控制程序输入输出：

```jsonc
"console": "integratedTerminal"
```

## 5.7 附加到进程与远程调试

| 字段 | 类型 | 适用 | 作用 |
|---|---|---|---|
| `processId` | number/string | `cppdbg`、`cppvsdbg` | 目标进程 ID，默认 `${command:pickProcess}` 弹出选择列表 |
| `pid` | number/string | `lldb`（CodeLLDB） | 同上，但字段名为 `pid` |
| `program` | string | `attach` 场景 | 用于加载符号，附加时通常仍需指定 |
| `miDebuggerServerAddress` | string | `cppdbg` | gdbserver 地址，如 `localhost:1234` |
| `debugServerPath` | string | `cppdbg` | 由 VS Code 启动的调试服务器程序路径 |
| `debugServerArgs` | string | `cppdbg` | 调试服务器的参数 |
| `serverStarted` | string | `cppdbg` | 判定服务器已启动的输出匹配模式（支持正则） |
| `serverLaunchTimeout` | number | `cppdbg` | 等待服务器启动的超时时间（毫秒），默认 10000 |
| `filterStdout` / `filterStderr` | boolean | `cppdbg` | 是否搜索并记录服务器的标准输出/错误 |
| `pipeTransport` | object | `cppdbg` | 通过管道传输调试协议（容器、跨机调试） |
| `hardwareBreakpoints` | object | `cppdbg` | 远程目标的硬件断点控制，如 `{ "require": true, "limit": 6 }` |

**附加到进程的最小配置：**

```jsonc
{
  "name": "GDB · 附加到进程",
  "type": "cppdbg",
  "request": "attach",
  "program": "${workspaceFolder}/build/gcc/app.exe",
  "MIMode": "gdb",
  "processId": "${command:pickProcess}"
}
```

> **注意**：MinGW/Cygwin 下的 GDB **无法中断正在运行的进程**（**文档**）。
> 程序启动后，在 VS Code 中执行"暂停"不会生效；需要在程序自身的终端中按 `Ctrl+C`。

## 5.8 转储文件调试

| 字段 | 类型 | 适用 | 作用 |
|---|---|---|---|
| `coreDumpPath` | string | `cppdbg` | 核心转储文件路径 |
| `dumpPath` | string | `cppvsdbg` | Windows 内存转储文件路径 |

> **注意**：**MinGW 下不支持 core dump 调试**（**文档**）。
> 该功能仅在 Linux 与 macOS 上可用。Windows 上的内存转储应使用 `cppvsdbg` 与 `dumpPath`。

## 5.9 日志配置

`logging` 对象用于排查调试器本身的问题，三个适配器均支持。

| 子字段 | 默认值 | 作用 |
|---|---|---|
| `exceptions` | `true` | 是否将异常信息输出到调试控制台 |
| `moduleLoad` | `true` | 是否输出模块加载事件 |
| `programOutput` | `true` | 是否输出程序的标准输出 |
| `engineLogging` | `false` | 是否输出调试引擎的诊断日志 |
| `trace` | `false` | 是否输出适配器与调试器之间的命令交互 |
| `traceResponse` | `false` | 是否同时输出命令的响应 |

排查"调试器行为异常"时，将 `trace` 设为 `true` 可看到完整的协议交互过程。

## 5.10 CodeLLDB 字段对照（`lldb`）

CodeLLDB 的字段命名与 `cpptools` 不同，混用会导致字段静默失效。

| 含义 | `cpptools`（`cppdbg`） | CodeLLDB（`lldb`） |
|---|---|---|
| 入口暂停 | `stopAtEntry` | **`stopOnEntry`** |
| 终端类型 | `externalConsole` | **`terminal`**（兼容别名 `console`） |
| 源码映射 | `sourceFileMap`（对象） | **`sourceMap`**（路径对数组） |
| 启动命令 | `setupCommands` | **`initCommands`** / `preRunCommands` |
| 调试器路径 | `miDebuggerPath` | 无此字段（自带 LLDB） |
| 环境变量 | `environment`（对象数组） | **`env`** |
| 附加进程 | `processId` | **`pid`** |
| 参数 | `args` | `args`（相同） |
| 工作目录 | `cwd` | `cwd`（相同） |
| 程序路径 | `program` | `program`（相同） |

CodeLLDB 的**命令钩子**分阶段执行，粒度比 `cppdbg` 更细：

| 字段 | 执行时机 |
|---|---|
| `initCommands` | 调试器启动时（此时调试目标尚未创建） |
| `targetCreateCommands` | 创建调试目标时 |
| `processCreateCommands` | 创建调试进程时 |
| `preRunCommands` | 目标启动或附加之前 |
| `postRunCommands` | 目标启动或附加之后 |
| `preTerminateCommands` | 终止或断开之前 |
| `exitCommands` | 调试会话结束后 |

其他 CodeLLDB 专有字段：

| 字段 | 作用 |
|---|---|
| `relativePathBase` | 解析相对源码路径的基准目录，默认 `${workspaceFolder}` |
| `sourceLanguages` | 启用语言特定功能的源码语言列表 |
| `expressions` | 表达式求值器的默认类型 |
| `breakpointMode` | 源码断点的设置方式 |
| `reverseDebugging` | 启用反向调试（需要调试后端支持） |
| `gracefulShutdown` | 请求终止时向目标发送的信号或执行的 LLDB 命令 |
| `stdio` | 标准输入输出的去向（可重定向到文件） |
| `noDebug` | 仅运行不调试 |
| `cargo` | Rust 的 Cargo 调用参数 |

# 第 6 章 从扩展提供的模板快速起步

手工编写 `launch.json` 容易出错。实际上，**多数场景并不需要手工编写**。
本章介绍四条由浅入深的起步路径。

## 6.1 路径概览

| 路径 | 是否需要 `launch.json` | 适用场景 |
|---|---|---|
| 一、F5 动态生成 | 不需要，且不落盘 | 调试当前打开的单个文件 |
| 二、编辑器播放按钮 | 不需要，且不落盘 | 同上，操作更直观 |
| 三、让 VS Code 生成文件 | 自动生成 | 需要在此基础上修改 |
| 四、CMake Tools 状态栏 | 不需要 | CMake 工程调试指定目标 |
| 五、使用扩展配置片段 | 自动插入 | 需要特定字段组合 |

> **说明**：C/C++ 扩展支持"动态调试配置"机制。官方文档的表述为：
> *"When you debug with the play button or F5, the C++ extension creates a
> dynamic debug configuration on the fly."*
> 即在使用播放按钮或 F5 时，扩展会即时生成调试配置，无需 `launch.json`。

## 6.2 路径一：按 F5 动态生成

1. 在**没有** `launch.json` 的工作区中打开一个 `.c` 或 `.cpp` 文件，使其成为活动编辑器；
2. 按 `F5`；
3. 在弹出的"选择调试配置"列表中选择 `C++ (GDB/LLDB)` 或 `C++ (Windows)`；
4. 若列表中要求选择编译器，选择对应的 `gcc.exe` / `g++.exe` / `cl.exe`。

扩展会自动生成 `tasks.json`（使用其专有的 `cppbuild` 任务类型），
而调试配置在每次调试时即时生成，不写入文件。

> **注意**：一旦工作区中**已存在** `launch.json`，播放按钮与 F5 将**优先使用该文件**，
> 不再走动态生成。官方文档的表述为：
> *"From now on, the play button and F5 will read from your launch.json file."*
> 若需恢复动态生成行为，可临时重命名 `.vscode/launch.json`。

## 6.3 路径二：使用编辑器播放按钮

前置条件：设置项 `C_Cpp.debugShortcut` 为 `true`（默认值即为 `true`）。

1. 打开 `.c` 或 `.cpp` 文件，使其成为活动编辑器；
2. 点击编辑器**右上角的播放按钮**（其旁的下拉箭头可在"运行"与"调试"间切换）；
3. 首次使用时选择编译器，此后播放按钮会记住该选择。

该路径与路径一使用相同的动态配置机制。

## 6.4 路径三：让 VS Code 生成 `launch.json` 文件

当需要生成一份可编辑的配置文件时：

**方法一**：在无 `launch.json` 时按 `F5`，选择环境后 VS Code 会创建该文件。

**方法二**：点击播放按钮旁的下拉箭头 → **Add Debug Configuration** → 选择编译器。

生成的配置中，`program` 默认为
`${fileDirname}\${fileBasenameNoExtension}.exe`，
`miDebuggerPath` 会自动填入检测到的 GDB 路径。

> **说明**：`cpptools` **不提供 `configurationSnippets`**（**实测**，其 `package.json` 中无此项）。
> 因此"添加配置"下拉列表中**不会**出现 C++ 模板。
> C++ 的自动生成走的是上述"检测编译器 + 动态配置"机制，与其他语言不同。
> 这一点容易引起误解，属正常现象。

## 6.5 路径四：CMake Tools 状态栏（推荐用于 CMake 工程）

已安装 CMake Tools 时，调试 CMake 工程**无需任何 `launch.json`**：

1. 在状态栏点击 **Set Launch/Debug Target**，选择要调试的目标；
2. 点击 **Debug** 按钮。

CMake Tools 会自动判断应使用的调试器（GCC 工具链使用 `cppdbg`，
MSVC 工具链使用 `cppvsdbg`）并生成配置。

相关命令及其在界面中的名称：

| 命令 ID | 界面名称 |
|---|---|
| `cmake.selectLaunchTarget` | Set Launch/Debug Target |
| `cmake.setBuildTargetSameAsLaunchTarget` | 使构建目标与调试目标保持一致 |
| `cmake.debugTarget` | Debug |
| `cmake.launchTarget` | Run Without Debugging |

**定制自动生成的配置**：使用 `settings.json` 中的 `cmake.debugConfig`，无需修改 `launch.json`。
其官方说明为：

> When `type` is specified, the auto-detected debugger configuration is skipped and only a
> minimal base configuration (program, cwd, name) is generated from the target. All other
> properties are applied from this setting, allowing full control over the debug launch
> configuration for any debug adapter.

即：指定 `type` 后，自动检测的配置被跳过，仅从目标生成 `program`、`cwd`、`name` 三项，
其余属性全部来自该设置项，从而可对任意调试适配器实现完全控制。

> **注意**：不要将 `CMake Tools` 提供的 `cmake` 调试类型误认为用于调试 C/C++ 程序。
> 该类型用于调试 **CMake 自身**，其三个配置片段分别为：
> `CMake: Configure`（调试 CMake 配置过程）、`CMake: Script`（调试 CMake 脚本）、
> `CMake: External`（连接外部 CMake 调用）。
> 对应命令为 `cmake.configureWithDebugger` 等。为程序编写 `"type": "cmake"` 是错误的。

## 6.6 路径五：使用扩展提供的配置片段

在 `launch.json` 中点击右下角的 **Add Configuration** 按钮，
会列出各扩展贡献的配置片段（`configurationSnippets`）。选择后自动插入到
`configurations` 数组中，字段名由扩展保证正确。

本机已安装扩展提供的片段：

| 扩展 | 片段名 | 用途 |
|---|---|---|
| CMake Tools | CMake: Configure | 调试 CMake 配置过程 |
| CMake Tools | CMake: Script | 调试 CMake 脚本 |
| CMake Tools | CMake: External | 连接外部 CMake 调用 |
| CodeLLDB | CodeLLDB: Launch | 启动目标程序 |
| CodeLLDB | CodeLLDB: Attach to Process | 附加到进程 |
| CodeLLDB | CodeLLDB: Launch Custom | 使用自定义命令启动 |

> **说明**：`cpptools` 未提供任何配置片段，因此 C/C++ 模板不会出现在此列表中。
> 如需该扩展的配置，请使用第 7 章的模板，或采用 6.4 的生成方法。

## 6.7 何时必须手工编写

| 需求 | 是否需要手工编写 |
|---|---|
| 调试当前打开的文件 | 否（路径一、二） |
| 调试 CMake 工程的某个目标 | 否（路径四） |
| 传递命令行参数 | 是，或使用 `cmake.debugConfig` |
| 设置环境变量 | 是 |
| 附加到运行中的进程 | 是 |
| 维护多套可切换的配置 | 是 |
| 一份配置支持多个操作系统 | 是 |
| 远程调试 | 是 |

## T3 MSVC 单文件构建的完整处理（vcvars 问题）（**实测**）

`cppvsdbg` 调试本身不需要 `vcvars`，但**编译**需要：`cl.exe` 依赖
`INCLUDE` 与 `LIB` 环境变量。

使用 `.cmd` 批处理存在两个问题：

1. `cmd.exe` 按当前代码页逐字节解析批处理文件，中文注释可能被误读为控制字符；
2. `/Fo:"...\dir\"` 结尾的 `\"` 会被 CRT 参数解析器视为转义引号，
   导致其后的源文件参数被一并吞掉，`cl` 报 `D8003 缺少源文件名`。

因此改用 PowerShell 脚本。`.vscode/tools/build-msvc.ps1` 的核心部分：

```powershell
param(
    [Parameter(Mandatory=$true)][string]$Source,
    [Parameter(Mandatory=$true)][string]$Output
)
$ErrorActionPreference = 'Stop'

# 1. 定位 Visual Studio（优先 VS2022）
$vswhere = Join-Path ${env:ProgramFiles(x86)} 'Microsoft Visual Studio\Installer\vswhere.exe'
$usable = @(& $vswhere -products '*' -property installationPath 2>$null |
            Where-Object { $_ -and (Test-Path (Join-Path $_ 'VC\Auxiliary\Build\vcvars64.bat')) })
$preferred = @($usable | Where-Object { $_ -match '\\2022\\Community$' })
if ($preferred.Count -eq 0) { $preferred = @($usable | Where-Object { $_ -match '\\2022\\' }) }
$vs = if ($preferred.Count) { $preferred[0] } else { $usable[0] }

# 2. 将 vcvars64.bat 的环境变量导入当前进程
$vcvars = Join-Path $vs 'VC\Auxiliary\Build\vcvars64.bat'
& cmd.exe /d /c "call `"$vcvars`" >nul 2>&1 && set" | ForEach-Object {
    $i = $_.IndexOf('=')
    if ($i -gt 0) { Set-Item -Path "Env:$($_.Substring(0,$i))" -Value $_.Substring($i+1) -ErrorAction SilentlyContinue }
}

# 3. 编译：路径全部换为正斜杠，避开 CRT 转义问题
$src = (Resolve-Path -LiteralPath $Source).Path -replace '\\','/'
$out = [System.IO.Path]::GetFullPath($Output) -replace '\\','/'
$dir = ((Split-Path -Parent $out) -replace '\\','/').TrimEnd('/') + '/'
New-Item -ItemType Directory -Force -Path (Split-Path -Parent $out) | Out-Null

Push-Location (Split-Path -Parent $out)   # 使 cl 生成的 vc140.pdb 落在输出目录
# /source-charset:utf-8     源码按 UTF-8 读取
# /execution-charset:gbk    字符串常量按 GBK 写入 exe，避免中文输出乱码
#                           （不能用 /utf-8，它会把执行字符集也设为 UTF-8）
& cl.exe /nologo /std:c17 /source-charset:utf-8 /execution-charset:gbk /Zi /Od /W3 `
         "/Fe:$out" "/Fo:$dir" $src
$rc = $LASTEXITCODE
Pop-Location
exit $rc
```

对应的 `tasks.json` 任务：

```jsonc
{
  "label": "构建: 单文件 (MSVC)",
  "type": "process",
  "command": "pwsh",
  "args": ["-NoProfile", "-ExecutionPolicy", "Bypass",
    "-File", "${workspaceFolder}\\.vscode\\tools\\build-msvc.ps1",
    "-Source", "${file}",
    "-Output", "${workspaceFolder}\\build\\msvc\\${fileBasenameNoExtension}.exe"],
  "options": { "cwd": "${fileDirname}" },
  "problemMatcher": "$msCompile",
  "presentation": { "reveal": "silent", "panel": "shared", "clear": true }
}
```

> **说明**：使用 `pwsh`（PowerShell 7）而非 `powershell`（Windows PowerShell 5.1）的原因：
> 后者读取无 BOM 的 UTF-8 脚本文件时按 ANSI 解析，中文注释会变成乱码甚至引发错误。
> PowerShell 7 默认使用 UTF-8。

```jsonc
  // 转储文件对应的那个 exe（用于匹配符号）
  "program": "${workspaceFolder}\\build\\msvc\\app.exe",
  // 要分析的转储文件
  "dumpPath": "${workspaceFolder}\\crash.dmp",
  "cwd": "${workspaceFolder}",
  // 若 pdb 不在 exe 旁边，在此指定搜索路径，分号分隔
  "symbolSearchPath": "${workspaceFolder}\\build\\msvc"
}
```

打开后即可查看调用堆栈、切换栈帧、查看各层变量，与正常调试相同。

> **注意**：`dumpPath` **仅属于 `cppvsdbg`**。`cppdbg`（GDB）不支持该字段，
> 因为 GDB 无法读取 Windows 的小型转储格式。

> **重要限制**：转储分析**需要 PDB 符号**，因此应当使用 **MSVC 编译**（`/Zi`）。
> 用 MinGW 的 gcc（`-g`，产出 DWARF）编译的程序，其转储只能显示出
> 「模块名 + 偏移」，无法还原函数名与源码行号（**实测**）。
> 完整的对照数据与生成转储的方法见《02-调试器/01-原理与使用.md》第 10.5 节。

## 8.6 查询扩展提供了哪些调试器

最可靠的方法是直接读取扩展的 `package.json`：

```powershell
Get-ChildItem "$env:USERPROFILE\.vscode\extensions" -Directory | ForEach-Object {
  $pj = Join-Path $_.FullName 'package.json'
  if (Test-Path $pj) {
    $j = Get-Content $pj -Raw -Encoding UTF8 | ConvertFrom-Json
    foreach ($d in $j.contributes.debuggers) {
      "{0,-24} type={1,-16} {2}" -f $j.name, $d.type, $d.label

```

> cpptools 中 `debuggers[0]` 是 `cppdbg`（40 个 launch 字段），
> `debuggers[1]` 才是 `cppvsdbg`（17 个）。
> 按下标取值会导致 `cppvsdbg` 的配置被 `cppdbg` 的 schema 校验，失去校验意义。

```powershell
# 正确做法：按 type 取值
$cpp = Get-Content "$env:USERPROFILE\.vscode\extensions\ms-vscode.cpptools-*\package.json" -Raw | ConvertFrom-Json
foreach ($d in $cpp.contributes.debuggers) {
  "--- {0} （{1} 个 launch 字段） ---" -f $d.type, $d.configurationAttributes.launch.properties.PSObject.Properties.Name.Count
  $d.configurationAttributes.launch.properties.PSObject.Properties.Name | Sort-Object
}
```

另一种方法是在"运行和调试"面板点击齿轮图标，**由扩展自行生成配置**。
这是发布者保证正确的途径，对文档不完整的扩展尤为适用。

## 8.7 选型建议

**首要判断条件：工程路径是否含中文。** 该条件会直接排除掉 GDB 路线。

| 使用场景 | 建议方案 |
|---|---|
| **工程路径含中文** | **不可用 `cppdbg`**。改用 `cppvsdbg` 或 CodeLLDB |

# 第 9 章 故障排查

## 9.1 中文路径下 GDB 报 `No such file or directory`（**实测**）

```
warning: 2  <工作区>\xxx.c: No such file or directory
```

**原因**：`chcp 65001` 只改变**控制台**代码页，不影响进程的 **ANSI 代码页**
（`GetACP()` 由系统区域设置决定，固定为 936）。MinGW 的 `fopen` 使用 ANSI 代码页，
而 gcc 将 UTF-8 编码的路径写入了 DWARF，两者不一致。

**影响范围**（**实测**结论）：

| 功能 | 是否受影响 |
|---|---|
| 断点命中 | 正常 |
| 单步、变量查看、调用堆栈 | 正常 |
| 源码显示与高亮 | 正常（由 VS Code 自行读取文件） |
| GDB 自身的 `list` 命令 | 受影响 |

**实际不影响调试的原因**：VS Code 通过 GDB 的 **MI 接口**通信，
MI 会以 **UTF-8 正确返回绝对路径**（**实测**，见 `fullname` 字段），
源码由 VS Code 读取。仅 GDB 自身的命令行功能受影响。

**规避方式**：改用 CodeLLDB（LLDB 无此问题，**实测**），或将工程置于纯英文路径。

## 9.2 CMake 4.x 报 `Compatibility with CMake < 3.5 has been removed`（**实测**）

```
CMake Error at CMakeLists.txt:1 (cmake_minimum_required):
  Compatibility with CMake < 3.5 has been removed from CMake.
  Or, add -DCMAKE_POLICY_VERSION_MINIMUM=3.5 to try configuring anyway.
```

两种解决方法：

```powershell
# 方法一：临时兼容（不改动他人代码）
# 注意：等号后的部分必须整体加引号。
# 不加引号时 PowerShell 会将其拆分为 "-D...=3" 与 ".5" 两个参数，
# CMake 将报 Invalid CMAKE_POLICY_VERSION_MINIMUM value "3"。
cmake -S . -B build "-DCMAKE_POLICY_VERSION_MINIMUM=3.5"

# 或使用环境变量（无需处理引号）
$env:CMAKE_POLICY_VERSION_MINIMUM = "3.5"
cmake -S . -B build
Remove-Item Env:\CMAKE_POLICY_VERSION_MINIMUM
```

```cmake
# 方法二：修改一行（推荐长期使用）
cmake_minimum_required(VERSION 3.16)
```

> **补充说明**：直接执行 `cmake -S . -B build` 而**不使用 `-G` 指定生成器**时，
> CMake 4.4.3 会自动选择**最新版本的 Visual Studio**（本机为 VS2026 BuildTools），
> 而非 VS2022。本工作区的预设均显式指定了生成器，不受此影响。

## 9.3 按 F5 提示找不到 `cmake` / `ninja`（**实测**）

**先重启 VS Code。** 新安装的软件需要 VS Code 重新读取 PATH
（其环境变量为启动时的快照）。

若重启后仍然找不到，说明该程序确实不在 PATH 中，
请按第 3 章「PATH 的说明与配置」一节把它加入 PATH。

> **说明**：本工作区的配置一律**直接调用 PATH 中的程序**（`"command": "cmake"`），
> 不写死安装路径。这样换一台机器也能直接使用，但前提是这些程序已在 PATH 中。
> 这是有意为之的取舍：用「一次性配置 PATH」换取配置文件的便携性。

## 9.4 任务启动失败，报 `The filename, directory name, or volume label syntax is incorrect.`

该错误由创建目录任务引起。若任务写作：

```jsonc
{
  "type": "process",
  "command": "cmd.exe",
  "args": ["/d", "/c", "if not exist \"${workspaceFolder}\\build\" mkdir \"${workspaceFolder}\\build\""]
}
```

则 VS Code 会按 MSVCRT 规则处理参数：为含空格的参数加引号，并将内部的 `"`
转义为 `\"`。而 `cmd.exe` 不识别该转义方式，因而报错（**实测**）。

**解决**：改用 PowerShell 的 .NET 方法建目录。它的参数是单个字符串，
不涉及引号转义，且幂等（目录已存在时同样成功）：

```jsonc
{
  "label": "准备: 创建输出目录",
  "type": "process",
  "command": "pwsh",
  "args": [
    "-NoProfile",
    "-NonInteractive",
    "-Command",
    "[System.IO.Directory]::CreateDirectory('${workspaceFolder}\\build\\gcc') | Out-Null"
  ],
  "problemMatcher": []
}
```

> **说明**：也可以使用 `cmake -E make_directory`，它同样只接受单一参数且幂等。
> 但那样会让「只做单文件调试」的人也被迫安装 CMake，
> 因此本工作区统一采用 PowerShell 方案——PowerShell 7 本就是本工作区的必需项。

## 9.5 gcc 报 `cannot open output file ...: No such file or directory`（**实测**）

即使输出目录确实已经存在，`gcc` 仍可能报此错误：

```
ld.exe: cannot open output file K:\...\01-c-single-file/build/gcc/main.exe: No such file or directory
```

**原因**：当路径中包含非 ASCII 字符（如中文目录名）时，`gcc` 的 `-o` 输出路径
**不能使用正斜杠，也不能混用分隔符**。MinGW 的 `ld.exe` 在处理此类路径时无法正确解析。

实测对照（同一工程，仅分隔符不同）：

| 路径字符 | 分隔符 | 结果 |
|---|---|---|
| 纯英文 | 全反斜杠 | 成功 |
| 纯英文 | 全正斜杠 | 成功 |
| 纯英文 | 混合 | 成功 |
| **含中文** | **全反斜杠** | **成功** |
| 含中文 | 全正斜杠 | 失败 |
| 含中文 | 混合 | 失败 |

**解决方法**：`tasks.json` 中 `-o` 的输出路径全部使用反斜杠。
反斜杠在 JSON 中需转义为 `\\`：

```jsonc
"args": [
  "-std=gnu17", "-g", "-O0", "-Wall", "-Wextra",
  "${file}",
  "-o", "${workspaceFolder}\\build\\gcc\\${fileBasenameNoExtension}.exe"
]
```

> **说明**：以下位置**不受**此问题影响，可继续使用正斜杠：
>
> | 位置 | 原因 |
> |---|---|
> | `launch.json` 的 `program` 字段 | VS Code 与 GDB 均能正确处理三种分隔符（**实测**） |
> | `cmake -E make_directory` 的参数 | CMake 自行规范化路径 |
> | `CMakePresets.json` 的 `binaryDir` | 由 CMake 内部解析 |
> | `c_cpp_properties.json` 的 `compileCommands` | 由 VS Code 读取 |
>
> 仅 `gcc` / `g++` 的 `-o` 参数需要遵守此规则。

## 9.6 程序输出的中文显示为乱码（**实测**）

### 现象

程序中的中文通过 `printf` / `cout` 输出后，显示为下列形态：

```
鏋勯€犲璞″垪琛?
灏忔槑  78
```

### 原理

MinGW 的 gcc 与 MSVC 的 cl.exe **默认都把字符串常量按 UTF-8 写入 exe**，
而中文 Windows 的控制台默认按 **CP936（GBK）** 解释收到的字节流。
两边编码不一致，于是显示为乱码。

实测的字节对照（源文件为 UTF-8，系统 ANSI 代码页为 936）：

| 编译器 | 编译选项 | 汉字 `中` 的字节 | 在 CP936 控制台的显示 |
|---|---|---|---|
| **gcc** | 默认（无字符集参数） | `e4 b8 ad`（UTF-8） | 乱码 |
| gcc | `-fexec-charset=GBK` | `d6 d0`（GBK） | `中` |
| gcc | `-fexec-charset=UTF-8` | `e4 b8 ad`（UTF-8） | 乱码 |
| **cl.exe** | `/utf-8` | `e4 b8 ad`（UTF-8） | 乱码 |
| cl.exe | `/execution-charset:gbk` | `d6 d0`（GBK） | `中` |

两种编译器的默认行为一致，均需显式指定执行字符集。

### 解决方法

核心原则：**源码按 UTF-8 读取，字符串常量按 GBK 写入 exe。**

**GCC / G++**，在编译参数中加入：

```
-finput-charset=UTF-8 -fexec-charset=GBK
```

**MSVC cl.exe**，将原来的 `/utf-8` 替换为：

```
/source-charset:utf-8 /execution-charset:gbk
```

> **注意**：`/utf-8` 是 `/source-charset:utf-8` 与 `/execution-charset:utf-8` 的合并写法，
> 它把**执行**字符集也设成了 UTF-8，因此在中文控制台下同样会乱码。
> 需要拆开书写，只把源码字符集设为 UTF-8。

**CMake 工程**在 `CMakeLists.txt` 中设置：

```cmake
if(MSVC)
    target_compile_options(app PRIVATE /source-charset:utf-8 /execution-charset:gbk /W4)
else()
    target_compile_options(app PRIVATE -g -Wall -Wextra
                                -finput-charset=UTF-8 -fexec-charset=GBK)
endif()
```

本工作区的 4 个examples均已按上述方式配置。

### 备选方案：改用 UTF-8 控制台

若希望程序保持输出 UTF-8 字节（例如输出需重定向到文件，或需与 Linux 共享），
则应改为让控制台按 UTF-8 解释：

```powershell
chcp 65001
```

该方式有三点限制：

- 只对**当前控制台窗口**生效，关闭后失效
- 对 VS Code 的**调试控制台**无效（它不是控制台窗口）
- 每次新建终端都需重新执行

> **说明**：两种方案只能择一，不可混用。
> 若程序按 GBK 输出而控制台设为 65001，乱码会以另一种形态出现。
> 查询当前控制台代码页：执行 `chcp`，输出形如 `活动代码页: 936`。

### 判断依据

| 现象 | 说明程序输出的是 | 应采用 |
|---|---|---|
| 「看起来像汉字但完全不对」的字符，如 `涓枃` | UTF-8 字节，显示端按 GBK 解码 | 修改编译选项，或改控制台为 65001 |
| 十六进制序列，如 `xe4xb8xad` | UTF-8 字节，显示端未作解码 | 改用自带解码的显示端（如集成终端） |
| 大量 `�`（替换字符） | 字节序列**不是合法的 UTF-8** | 显示端按 UTF-8 解码，但源数据是 GBK |
| 提示找不到文件，但路径看起来正常 | 传给 API 的路径**编码已损坏** | 见下面的真实案例 |

### 真实案例：编码在传递途中被弄坏

上面都是「显示」层面的乱码。还有一种更麻烦的情况：
**乱码发生在数据传递途中，程序因此找不到文件。**

某个真实项目里，两个模块都要「用运行时加载 DLL」，
**它们用了不同的写法，一对一错**。

**正确的写法**（`plugin_loader.cpp`）：

```cpp
int len = MultiByteToWideChar(CP_UTF8, 0, path.c_str(), -1, nullptr, 0);
std::wstring wpath(len, L'\0');
MultiByteToWideChar(CP_UTF8, 0, path.c_str(), -1, &wpath[0], len);
void* handle = (void*)LoadLibraryW(wpath.c_str());
```

**错误的写法**（`pointer_downloader.cpp`）：

```cpp
std::wstring widePath(dllPath.begin(), dllPath.end());   // 逐字节加宽
handle = LoadLibraryW(widePath.c_str());
```

后者把每个 `char` **按数值原样**转成一个 `wchar_t`。
对 ASCII 字符这恰好是对的，**对任何非 ASCII 字符都是错的**。

**实测对比**（路径含「插件」二字，UTF-8 下是 `E6 8F 92 E4 BB B6` 六个字节）：

```
错误写法:  [FFE6][FF8F][FF92][FFE4][FFBB][FFB6]     6 个字节 → 6 个乱码
正确写法:  [63D2][4EF6]                              6 个字节 → 「插件」2 个汉字
```

**错误的写法下，只要路径里有中文，`LoadLibraryW` 就一定失败。**

### 与本节的联系

这是**同一个根源的第三种表现**：

| 场景 | 谁给了什么 | 谁怎么解释 |
|---|---|---|
| 控制台乱码 | gcc 写 UTF-8 字面量 | 控制台按 GBK 显示 |
| GDB 打不开中文路径 | VS Code 发 UTF-8 | GDB 按 ANSI（936） |
| 本节这个案例 | 程序给逐字节加宽的串 | 系统按 Unicode 码点 |

**三次都是「编码是一份约定，双方必须一致」。**

> **完整分析**见 【待补：01-编译器/05-语法.md】；
> 该案例所在的工程与授权说明见《版权与许可说明.md》。

## 9.7 报 `Program path ... is missing or invalid`，但文件确实存在

### 现象

```
Unable to start debugging. Program path
'K:\...\02-cpp-single-file\main.exe' is missing or invalid.

GDB failed with message: K:\...\02-cpp-single-file\main.exe: No such file or directory.
```

而该文件经检查确实存在。

### 首要排查方向：确认按 F5 时选中的是哪一条配置

**判断方法：看报错路径中的产物位置。**

本文配置的各示例，产物位置是固定的：

| 示例 | GDB 路线产物 | VS2022 路线产物 |
|---|---|---|
| 01 / 02（单文件） | `build\gcc\<文件名>.exe` | `build\msvc\<文件名>.exe` |
| 03 / 04（CMake） | `build\mingw\bin\app.exe` | `build\msvc\bin\Debug\app.exe` |

**若报错路径形如 `<工程目录>\main.exe`（缺少 `build\gcc\` 这一层），
则说明选中的不是本文配置的条目，而是 VS Code 自动生成的配置。**

### 自动生成的配置从何而来

在"运行和调试"面板点击 **播放按钮**（编辑器右上角的三角形图标），或首次按 F5 时选择了
`C/C++: g++ 生成和调试活动文件` 一类的条目，C/C++ 扩展会即时创建
一份调试配置与一个构建任务。

自动生成的内容有四个特征：

| 特征 | 说明 |
|---|---|
| 产物直接放在源码旁边 | 路径为 `${fileDirname}\${fileBasenameNoExtension}.exe` |
| 任务类型为 `cppbuild` | 而非本文所用的 `process` |
| 工作目录被设为编译器所在目录 | 例如 `"cwd": "C:/mingw64/bin"` |
| 被标记为默认构建任务 | `"group": { "kind": "build", "isDefault": true }` |

**另一个副作用**：VS Code 在追加该任务时会**重写整个 `tasks.json`**，
重新缩进并**删除其中的全部注释**。因此该文件中的注释若消失，即说明发生过此事。

### 处理方法

**第一步：删除自动生成的任务。** 打开 `.vscode/tasks.json`，
删除 `"type": "cppbuild"` 的那个任务对象，注意同时处理它前面的逗号。

**第二步：确认 F5 下拉列表中的条目。** 应当只出现本文配置的名称：

| 示例 | 应有的配置名称 |
|---|---|
| 01 | `GDB · 调试当前 .c 文件`、`VS2022 · 调试当前 .c 文件` |
| 02 | `GDB · 调试当前 .cpp 文件`、`VS2022 · 调试当前 .cpp 文件` |
| 03 / 04 | `GDB · CMake 工程 (MinGW)`、`VS2022 · CMake 工程 (MSVC)` |

若列表中仍有 `C/C++: g++.exe 生成和调试活动文件` 之类的条目，
说明自动生成的内容尚未清除。

**第三步：清理多余的产物。** 自动生成的 exe 位于源码旁边，
与本文的 `build\` 目录结构不同，可自行删除。

> **说明**：完成本文的配置后，**不要使用编辑器右上角的播放按钮**，
> 该按钮走的是自动生成路径。请一律使用 `F5`，并在弹出的列表中选择上表中的条目。

### 若确认使用的就是本文的配置

按下列顺序检查：

1. `program` 字段的路径与实际产物位置是否一致（对照上文表格）；
2. `preLaunchTask` 的名称与 `tasks.json` 中的 `label` 是否字字相同（见 9.8 节）；
3. 构建任务是否真的成功执行过——在命令面板执行 `Tasks: Run Task`，
   手动运行对应的构建任务，观察终端输出；
4. `settings.json` 中是否设置了 `"debug.onTaskErrors": "showErrors"`。
   该设置可避免"构建失败但仍启动调试"的情况。

## 9.8 F5 报"找不到任务 xxx"

`launch.json` 的 `preLaunchTask` 与 `tasks.json` 的 `label` 必须完全一致，
包括空格、中文与括号。建议采用复制粘贴的方式填写。

## 9.9 断点显示为空心灰点，提示"未绑定断点"

表示可执行文件中没有对应的调试信息。依次检查：

1. 编译是否包含 `-g`（GCC）或 `/Zi`（MSVC）？
2. `program` 指向的是否为**刚编译出的**可执行文件？（路径错误会调试到旧文件）
3. 编译器与调试器是否匹配？（GCC 产物不能配合 `cppvsdbg`）

## 9.10 断点停在声明行时，变量显示为无关数值

此为正常现象，而非故障。例如：

```c
int arr[N] = {10, 20, 30};   /* 断点位于此行 */
```

停住时查看 `arr` 会看到一组无关数值，或提示
`Cannot access memory at address ...`。原因是**该行尚未执行**：
断点停在"即将执行"的位置，初始化表达式还未运行（**实测**）。

**处理方法**：将断点设在下一行；或在停住后按一次 `F10`（单步跳过），
使初始化完成后查看变量。

`std::vector<Student> list = {...}` 等带构造函数的声明同理。

## 9.11 程序中的 `scanf` 无法输入

- `cppdbg`：设置 `"externalConsole": false`（使用集成终端）
- `cppvsdbg`：设置 `"console": "integratedTerminal"`

## 9.12 在根工作区调试 CMake 示例时链接失败

现象为 `undefined reference to ...`。原因是打开方式不正确：
VS Code 只识别工作区根目录的 `.vscode`。
`B-examples\03-CMake-C\src\main.c` 这类文件在上层工作区打开时，
会使用上层（单文件）配置，将其当作单文件单独编译，
而该文件调用了同工程其他源文件中的函数，因而链接失败。

**处理方法**：使用`文件 → 打开文件夹`单独打开对应的示例目录。

## 9.13 GDB 路线完全无法启动调试（**实测**）

### 现象

按 `F5` 选择 GDB 配置后，可能出现下列任一情况：

| 现象 | 说明 |
|---|---|
| 提示 `Program path '...' is missing or invalid`，但该文件确实存在 | 最常见 |
| 弹出"选择要终止的调试会话"列表，但**列表为空**，随后没有任何反应 | 会话卡在启动状态 |
| 调试会话一直停留在启动中，既不报错也不继续 | 同上 |
| GDB 报 `...: No such file or directory` | 与第一条等价 |

### 快速判定

查看报错中的路径。**只要路径中含有中文，本节就是原因**，无需继续排查配置。

对照实验可确认这一判断——在命令行中直接运行程序通常是正常的：

```powershell
# 命令行方式下 GDB 可以正常打开中文路径的可执行文件
gdb --batch -ex "break main" -ex run "K:\...\中文目录\build\gcc\main.exe"
```

**命令行能成功、VS Code 却失败，这正是本节所述问题的典型特征。**
原因在于：命令行方式由 Windows 传入参数（走 Unicode 转换），
而 VS Code 通过 MI 协议以 UTF-8 字节发送路径，两者路径解析机制不同。

### 原因与影响范围

完整的原理、实测数据与影响范围见**第 1 章第 2 节**。要点如下：

- GDB 经 MI 协议接收文件名时期望 ANSI 代码页（936）字节，VS Code 发送 UTF-8，两者不一致
- **可执行文件路径受影响**（调试无法启动）
- **源码路径不受影响**（断点可以正常设置）
- 该问题**无法通过任何配置项解决**

### 处理方法

按可行性从高到低排列：

| 方法 | 需要的改动 |
|---|---|
| **改用 VS2022 路线**（`cppvsdbg`） | 无需改动文件，直接按 F5 选择该配置。**本工作区已验证可用** |
| **改用 CodeLLDB**（`lldb`） | 安装扩展后追加配置。**本工作区已验证可用** |
| **仅将构建产物输出到全英文路径** | 修改 `tasks.json` 的输出路径与 `launch.json` 的 `program`。源码可留在中文路径 |
| **将整个工程移至全英文路径** | 例如 `D:\cpp-course\`。最彻底，但需要迁移 |

> **说明**：前两种方法不需要移动任何文件，只改配置。

### 关于"让 VS Code 自动生成配置"

使用编辑器右上角的播放按钮、或选择 `C/C++: g++ 生成和调试活动文件` 一类的条目，
会让扩展自动生成一套配置与构建任务。**这一做法无法解决本问题**：
自动生成的产物仍然位于中文路径下（`${fileDirname}\${fileBasenameNoExtension}.exe`），
GDB 同样加载不了。

「生成了 exe 文件」与「能够调试」是两件事。
