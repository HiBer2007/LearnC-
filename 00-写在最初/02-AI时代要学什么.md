**这套教材不讲速成，也不打算让人背下多少条语法。**
它真正想回答的是一件更要紧的事：当机器已经能写代码、能查资料、
能把一句中文变成一段可以编译的程序时，一个人还剩下什么是必须自己会的。

**答案不在语言本身，在语言背后。**
一个东西放在哪里、一次调用背后发生了什么、一个数字写错为什么会让整台机器停住——
这些知识不因为有人工智能而失效，反而因为生成变得廉价，而变得更值钱。

**这一篇写给开始之前的人，也写给学了几年、忽然发现自己记不住也背不完的人。**
它不教任何语法，只把方向摆正：什么可以交出去，什么必须留下，时间该花在哪里。

# 第 1 节 已经交出去的三件事

## 1.1 记忆

**曾经，记住是本事。**

记住一个函数的参数顺序，记住一个类型的宽度，记住几条容易混淆的规则。
这些记忆在面试里能换分，在日常里能换速度，于是被反复训练，
甚至被当成「基础扎实」的同义词。

**现在它们是检索问题，不是记忆问题。**

一个能读资料的工具，可以在很短的时间里给出比任何人记得都准的答案，
而且不会记混、不会想当然、不会因为三个月没用就忘掉。
记忆的边际价值，正在以肉眼可见的速度下降。

**但有一件事要说清楚：查得到，不等于看得懂。**
一个人如果不知道某个规则背后的道理，那么查到的每一条他都只能照抄；
一旦两条规则冲突，他就没有能力判断该信哪一个。
**被替代的是记忆，不是理解。**

## 1.2 翻译

**「把想法翻成代码」曾经是这项工作的主体。**

把一句需求翻成一段逻辑，把一张流程图翻成若干个函数，
把一份接口说明翻成一组类型定义。
熟练的人翻得快，不熟练的人翻得慢，差别就体现在这里。

**这类翻译正在被大量接管。**

给定清楚的输入、输出与约束，得到一段能编译的代码，已经不算难事。
尤其在重复而琐碎的地方，机器写得比人快，也比人耐烦。

**可是翻译的前提是「说清楚」。**
而真正耗费时间的从来不是翻译，是**先说清楚**：
到底要什么、什么情况算失败、规模有多大、谁来用它。
这些问题没有人能替你回答，因为答案取决于你处在什么位置。

## 1.3 样板

**样板是另一种形式的记忆。**

一类程序该怎么起手，一种结构该怎么组织，一个模块该怎么分层。
这些模式反复出现，写法大同小异，改动的只有名字与细节。

**它们是最先被交出去的部分**，而且交得很干净：
形状固定、对错容易判断、与具体处境关系不大。

**值得留意的是：样板被接管之后，剩下的工作反而更难了。**
留下的是判断该用哪一种、判断眼前的约束与常见的例子差在哪里、
判断现成的东西能不能直接放在这里。
**容易被替代的先被替代，剩下的部分因此显得更突出。**

## 1.4 为什么这三件事的价值在下降

**因为它们都属于同一类事：答案已经写在某处，而且对错容易判断。**

| 这类事的特征 | 结果 |
|---|---|
| 答案已经存在 | 检索比记忆便宜 |
| 对错容易判断 | 生成之后立刻能检查 |
| 与具体处境关系不大 | 换一个场合照样成立 |

**反过来看，凡是「取决于你的处境」的事，都不在这张名单上。**
你的条件是什么、你的读者是谁、你能承受多少代价——
这些别人不知道，工具也不知道。

**分界线就在这里。**

# 第 2 节 没有交出去的四件事

## 2.1 判断：知道要什么

**工具可以回答任何被问清楚的问题，但它不负责决定该问什么。**

一件事该做到什么程度，取决于谁来用、用多久、出错的代价由谁承担。
一个方案该激进还是保守，取决于团队、时间与余地。
**这些选择没有标准答案，只有取舍**，而取舍的依据来自你所处的位置。

**判断力不是天生的，它来自见过的系统足够多**——
见过做得好的，也见过做得糟的，并且知道它们各自的代价落在哪里。
这就是为什么「为什么」比「怎么做」更值得花时间。

## 2.2 验证：知道对不对

**这是最容易被低估的一件事。**

一段东西读起来通顺、命名合理、说明得体，
它是不是对的？**这个问题只能由试过它的人回答。**

**更麻烦的是，错的地方往往不在显眼处。**
有些错误成立的条件很苛刻：要在特定的优化下、在特定的硬件上、
在特定的时序里才会露出来。这样的错误读一百遍也读不出来，
**只有在真实条件下跑一遍，并且知道该看什么，才会现形。**

**验证的能力包含三件事**：
知道该看什么、知道怎么看、知道看到的东西意味着什么。

## 2.3 组合：把零件拼成系统

**单独一个零件对不对容易判断，把许多零件拼在一起还正确，是另一回事。**

选项与运行时的关系、版本与头文件的关系、
几个人同时改了什么、错误在哪一层被接住、
哪些东西只在某一刻存在过——
**系统的性质不在任何一个零件里，而在零件之间。**

**组合能力最直接的体现是排错。**
别人那里能跑，你这里不行；
昨天还好，加一行记录就不行；
一种配置正常，另一种崩掉。
这些问题不会有现成的答案，因为你面对的是一个**只有你手上这一份**的系统。

## 2.4 负责：出错时站在那里的人

**工具不承担责任。**

它不会因为出了事故而难受，不会因为看错了条件而需要向人解释，
也不会在下一次设计时记得上一次的教训。
**署名、交付、维护、承担后果，这些动作只能由人完成。**

责任不是一句口号，它会反过来影响技术选择：
需要长久维护的东西，人会倾向于写得更朴素、更容易被下一个人看懂；
只有自己能看懂的聪明写法，代价往往在很久之后由别人支付。

## 2.5 一条分界

把前两节合起来看，分界很清楚：

`Text`

```text
        可以交出去的                      必须留下的
   ┌────────────────────┐          ┌────────────────────┐
   │  事实、规则、写法  │          │  判断、验证、组合  │
   │  常见的模式        │          │  边界、取舍、责任  │
   │  有唯一正确答案    │          │  取决于你的处境    │
   └────────────────────┘          └────────────────────┘
            正在被接管                       正在变值钱
```

**这条分界不是永久的**，它每年都在往左挪一点。
**但挪动的方式是「右边的一部分变成左边」，而不是「右边消失」。**
今天需要判断的事，明天可能变成有标准答案的事；
而今天还没有人能判断的事，明天依然要有人去判断。

**方向因此变得清楚：往右边站。**

# 第 3 节 为什么会这样

## 3.1 它擅长的是「像」而不是「是」

**这类工具做的事，是根据已有的材料推断接下来最可能出现的样子。**

这个机制在「像」这个维度上非常强：
它见过的例子足够多，因此知道一类东西通常长什么样、
名字一般怎么起、说明一般写在哪儿、常见的做法有哪几种。

**它给出的是「最可能的」，不是「在你这里成立的」。**
这两件事大多数时候重合，所以它看起来非常准；
而在不重合的时候，它依然会用同样确定的语气说出来。

## 3.2 流畅与正确之间没有等号

**流畅是一种观感，正确是一种事实。**

一段东西读起来合理，可能是因为它符合我们对这类东西的印象，
而不是因为它在这个条件下真的能工作。
**印象来自过去见过的样子，条件只属于眼前这一份。**

**因此有一句判断标准值得记住**：
**凡是「不试就不知道」的结论，都必须试。**

## 3.3 谁有权签发「正确」

**在一台具体的机器上跑出来的结果，是唯一有权签发「正确」的东西。**

不是说明，因为说明可能对应另一个版本；
不是经验，因为经验可能来自另一个环境；
更不是「说得通」，因为说得通只是最低标准。

**这也是这套教材把「可复现」看得比「讲得漂亮」重的原因。**
读者不必相信作者，照着做一遍就行。
**在生成变得廉价之后，这件事的重要性只增不减**——
因为生成越快，验证越成为瓶颈。

# 第 4 节 于是要学什么

## 4.1 机制：东西是怎么运转的

**机制是判断的地基。**

不知道一层东西是怎么被处理的，就无法判断它在另一种条件下是否还成立；
不知道一个报错从哪里来，就无法判断该往哪个方向找。
**机制类的知识有一个好处：它不常变。**
说法会增补，工具会更新，而「东西是怎么运转的」这件事十年二十年不动。

## 4.2 组合：零件怎么拼成一个能跑的系统

**组合能力要靠完整的工程练，不能靠零散的片段。**

一个能跑起来的东西至少要包含：
怎么建、依赖谁、东西放哪、编成什么样，
以及一条从源材料到成品的可重复路径。
**看一遍不算会，自己搭一遍才算。**

## 4.3 证据：怎么验证一句话

**这是最希望被带走的一项能力。**

它由四个动作组成：

| 动作 | 做法 |
|---|---|
| **限定条件** | 说清楚在什么平台、什么版本、什么配置下成立 |
| **给出步骤** | 让人能照着做，而不是只给结论 |
| **贴出结果** | 真实结果，包括错误原文，不改写 |
| **写明边界** | 什么情况下这个结论不成立 |

**这四步看起来笨，但它是把「印象」变成「知识」的唯一办法。**
只记住结论的人，换一个环境就会失效；
记住「怎么验证」的人，换到哪里都能重新确认一遍。

## 4.4 提问：把愿望写成可执行的问题

**提问的质量，直接决定答案的质量。**

「这样做有没有问题」几乎无法回答；
「在这种条件下，这样做会不会出现那种现象」则是可以回答的。
**把愿望变成问题，需要知道系统由哪些部分组成、
哪些部分可能出错、怎样描述一个可以被观察到的现象。**
这三样正好是前面三节的内容，它们在这里汇合。

# 第 5 节 这套教材为什么是这样写的

## 5.1 只写跑得起来的东西

**保留在正文里的每个实例都是完整的、可以自己跑一遍的**，
而不是读起来轻松、读完却不知道从何下手的片段。
**能跑的东西才谈得上验证。**

## 5.2 把不确定标出来

**教材里不会用含糊的词把不清楚的地方盖过去。**

每个结论都标出依据：做过的、引自资料的、还没验证的，
以及**随环境而变、给不出统一答案的**。
**读者看到「做过的」可以放心照着做，看到「还没验证的」知道自己要留心。**

**这套标注不只是给读者看的，也是给作者的约束。**
写下一个数字之前必须先做一遍，这个要求会强迫人把话说实。

## 5.3 讲为什么，不只讲怎么做

**「怎么做」会被检索替代，「为什么」不会。**

知道了为什么，遇到没有人写过的情形才推得下去。
**与之配套的是：数据与结论分开摆**——
支撑论述必须用到的留在正文，只是佐证的移到别处。
判断标准只有一句：**把它删掉，这段论述还成立吗。**

## 5.4 留一半给读者

**教材提供骨架，读的人补上实现。**

理由很朴素：**读懂的东西与写出来的东西之间，隔着一道必须自己跨过去的门。**
这道门跨过去之后，地图就换了——
原来记住的变成了工具，原来模糊的变成了判断，
原来「能跑」的东西开始要求「在约束下正确」。

# 第 6 节 与 AI 共事

## 6.1 当检索器与草稿机

**这是它最擅长的位置。**

查一个用法、问一个方向、把重复的部分写出来、
把一份说明翻译成可以用的形状、解释一段别人写的东西。
这些事情它做得又快又稳，**省下来的时间正好用在判断与验证上。**

**用得好的标志是：你越来越清楚哪些事不必自己动手，也越来越清楚哪些事必须自己动手。**

## 6.2 验证权留在自己手里

**生成是它的强项，验证是它的短板。**

一段东西读起来通顺，并不构成「在你这里成立」的证据。
**凡是不试就不知道的结论，都必须试**——这句话对人和对工具同样有效。

**这套教材的仓库里带了一份写给 AI 的说明**，
它规定用 AI 打开这个工作区时应当遵守什么：
只依据仓库里的内容作答、不许用外部知识补全这里没写的东西、
不许把标着「还没验证」或「随环境而变」的内容说成确定的。
**这套规则不是限制，而是把「验证权在自己手里」写成可执行的约定。**

## 6.3 提问的质量决定答案的质量

**同一个工具，问得好与问得差，得到的东西差得很远。**

一个好的提问通常包含四件事：
**条件**（在什么环境下）、
**现象**（看到的原文，不是转述）、
**期望**（本来想让它怎么样）、
**已知**（已经排除过哪些可能）。

**这四件事与要求「做过的结论」时必须交代的内容几乎一样**，
因为它们服务的是同一个目的：**让别人能重现你说的问题。**

## 6.4 什么时候不要用它

**有三种场合，先自己想。**

| 场合 | 为什么 |
|---|---|
| **第一次学一个机制** | 先自己推一遍，再对照答案，才知道自己错在哪一步 |
| **需要留下判断依据时** | 依据必须来自你自己验证过的东西，否则出了问题无法解释 |
| **涉及不可逆的操作时** | 动手之前要知道会发生什么 |

**这不是拒绝工具，而是安排顺序。**
工具在「我推完了，来对一下」这个位置上，价值最大。

# 第 7 节 写在开始之前

## 7.1 从会背到会判断

**一个人学编程的路径，正在从「积累知识」变成「积累判断」。**

积累知识的时代，差距来自谁记得多；
积累判断的时代，差距来自谁见过的系统更多、
知道更多的代价、并且能在没有标准答案的时候做出选择。

**判断不能凭空长出来。**
它需要真实的条件、真实的失败、真实的约束，
需要为了一个「明明应该能跑」的问题翻来覆去，
需要在把东西送出去之后发现它一动不动，然后顺着线索找回那个被忽略的细节。

## 7.2 把时间花在哪

**把时间花在不会被替代的地方。**

| 少花一点时间 | 多花一点时间 |
|---|---|
| 记住用法与参数 | 弄清一个机制为什么这样设计 |
| 抄一个能跑的样板 | 自己搭一遍，看每一处在起什么作用 |
| 记住结论 | 记住结论的**边界**——它在什么条件下不成立 |
| 追求看起来聪明 | 追求能被下一个人看懂 |
| 问「这样对吗」 | 问「在什么条件下它会不对」 |

**这些选择短期看不出差别，长期会把两个人分到完全不同的位置。**

## 7.3 速查

| 状态 | 什么时候用 | 怎么办 |
|---|---|---|
| 已经交出去 | 记忆、翻译、样板 | 查得到就行，不必背 |
| 必须留下 | 判断、验证、组合、负责 | 靠真实的事情积累 |
| 学习方向 | 机制、组合、证据、提问 | 前者为后者铺路 |
| 验证四步 | 限定条件、给出步骤、贴出结果、写明边界 | 对人对己都适用 |
| 与 AI 共事的底线 | **生成可以外包，验证不能** | 顺序：先自己想，再来对 |

**上面这些话，现在读一遍就够了，不必记住。**

那时你会发现，这一篇并没有讲什么新的道理，
