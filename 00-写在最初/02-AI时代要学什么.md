**这套教材不讲速成，也不打算让人背下多少条语法。**
它想回答的是一件更要紧的事：当机器已经能写代码、能查文档、能把一段中文翻成一段可编译的程序时，
一个人还剩下什么是必须自己会的。

**答案不在语言本身，在语言背后的东西。**
一个变量放在内存的哪一段、一次函数调用为什么要压栈、一个链接脚本写错一个数字为什么程序会在复位后立刻停住——
这些知识不因为有人工智能而失效，反而因为生成代码变得廉价，而变得更值钱。

**这一篇写给开始之前的人，也写给学了几年、忽然发现自己记不住也背不完的人。**
它不教任何语法，只把方向摆正：什么该交出去，什么必须留下，时间应该花在哪里。

# 第 1 节 已经交出去的三件事

## 1.1 记忆

**曾经，记住是本事。**

记住 `printf` 的格式串有哪些转换说明，记住 `std::vector` 有几个构造函数，
记住结构体对齐的几条规则，记住某个函数返回的是指针还是引用。
这些记忆在面试里能换分，在工作里能换来速度。

**现在它们是检索问题，不是记忆问题。**

一个能读文档的工具，可以在半秒里给出比任何人记得都准的答案，
而且它不会记错，不会把 `%lf` 和 `%f` 混起来，不会把 `size_t` 说成 `unsigned int`。
记忆的边际价值，正在以肉眼可见的速度下降。

**但有一件事必须说清楚：查得到，不等于看得懂。**
一个人如果不知道「对齐」是什么，那么查到的每一条规则他都只能照抄；
一旦两个规则冲突，他就没有能力判断该信哪一个。
**记忆被替代了，理解没有。**

## 1.2 翻译

**「把需求翻译成代码」曾经是这项工作的主体。**

把一句「按销售额从高到低排一下」翻译成排序调用，
把一个流程图翻译成若干个函数，
把一份接口文档翻译成一组结构体定义。
熟练的人做得快，不熟练的人做得慢，差别在这里。

**这类翻译正在被大量接管。**

给定清楚的输入、输出与约束，生成一段能编译的代码，已经是相当稳定的事。
尤其在样板密集的地方——配置解析、字符串处理、序列化、命令行的参数表——
机器写得比人快，也比人耐烦。

**但翻译的前提是「说清楚」。**
而实际工作中，最耗时间的从来不是翻译，是**先说清楚**：
到底按哪一列排、相等的时候怎么办、数据量有多大、失败时是报错还是跳过。
这些问题没有人替你回答，因为答案取决于你要什么。

## 1.3 样板

**样板代码是另一种形式的记忆。**

一个 CMake 工程该怎么开头，一个类该有哪几个特殊成员函数，
一个日志模块该怎么包装，一个状态机该怎么起手。
这些模式反复出现，写法大同小异。

**它们是最先被外包出去的部分**，而且外包得很干净：
模式固定、对错容易验证、与具体业务关系不大。

**值得留意的是：样板被替代之后，剩下的工作反而更难了。**
留下的是判断「该用哪一种样板」、
判断「这个项目的约束和教科书上的例子差在哪里」、
以及判断「这段生成的代码能不能放在这里」。
**容易被替代的部分先被替代，剩下的部分因此显得更突出。**

## 1.4 为什么这三件事的价值在下降

**一句话：它们都是「有唯一正确答案、且答案可以被检索到」的事。**

| 这类事的特征 | 结果 |
|---|---|
| 答案已经写在某处 | 检索比记忆便宜 |
| 对错容易验证 | 生成之后立刻能检查 |
| 与具体处境关系不大 | 换一个项目也照样成立 |

**反过来看，凡是「答案取决于你的处境」的事，都不在这个名单上。**
你的板子是哪一款、你的编译器是哪个版本、你的数据有多少条、你的读者是谁——
这些东西别人不知道，工具也不知道，只有你知道。

**分界线就在这里。**

# 第 2 节 没有交出去的四件事

## 2.1 判断：知道要什么

**工具可以回答任何被问清楚的问题，但它不负责决定该问什么。**

一个函数是该返回错误码还是抛异常，取决于调用方是谁、失败的频率有多高、
上游有没有人接得住。一个接口该收窄还是放宽，取决于谁会用它、以后会不会改。
一个模块该不该拆，取决于团队的规模与变更的节奏。

**这些决定没有标准答案，只有取舍**，而取舍的依据来自你的处境。
写成文档、讲给同事听、出了问题自己承担——**这是判断，不是检索。**

**判断力是怎么来的**：见过足够多做得好的系统，也见过足够多做得糟的系统，
并且知道它们各自的代价落在哪里。这就是为什么本教材把「为什么」看得比「怎么做」重。

## 2.2 验证：知道对不对

**这是最容易被低估的一件事。**

一段生成的代码，读起来通顺、命名合理、注释得体、编译通过。
它是不是对的？**这个问题只能由跑过它的人回答。**

本教材里有三个例子，它们都「看起来对」：

| 例子 | 看起来怎样 | 实际上怎样 | 在哪 |
|---|---|---|---|
| 少写一个 `volatile` | 循环读一个标志位，逻辑清楚 | 编译器把读优化掉，**内存里标志位已经变了，程序却永远停在原地** | 《06-更底层/03-寄存器、位与 volatile.md》 |
| `_sbrk` 少一句边界检查 | 堆分配照常工作 | 分配到 RAM 之外仍返回成功，**真板上以总线故障收场** | 《06-更底层/11-系统调用：程序与内核的边界.md》 |
| 链接脚本里的内存大小抄错 | 链接成功，没有一条警告 | 栈顶被算到 RAM 之外，**复位后第一条指令就进 HardFault** | 《06-更底层/07-链接脚本与启动代码.md》 |

**这三处没有一处能靠「读一遍」发现。**
它们共同的特点是：**错的不是文字，是文字与真实机器之间的关系。**

**验证的能力包含三件事**：
知道该量什么、知道怎么量、知道量出来的数字意味着什么。
本教材里那些 `实测数据`，标的就是这三件事都做过的地方。

## 2.3 组合：把零件拼成系统

**单独一个函数的对错容易判断，把一百个函数拼在一起还正确，是另一回事。**

编译选项与运行时的关系、库的版本与头文件的关系、
线程之间共享了什么、异常穿过哪一层被接住、
内存的哪一段在启动时被搬过、哪一段只在链接脚本里出现过一次——
**系统的性质不在任何一个零件里，而在零件之间。**

**组合能力最直接的体现是排错。**
一个程序在别人机器上跑得起来，在你这里不行；
昨天还能跑，加了一行日志就不行；
Debug 版正常，Release 版崩。
这些问题不会有现成的答案，因为你面对的是一个**只有你手上这一份**的系统。

## 2.4 负责：出错时站在那里的人

**工具不承担责任。**

它不会因为线上出了事故而难受，不会因为看错了一个约束而需要向人解释，
也不会在下一次设计时记得这次的教训。
**署名、交付、维护、承担后果——这些动作只能由人完成。**

责任不是一句口号，它会反过来影响技术选择：
一个需要长期维护的模块，你会倾向于选更朴素、更容易被下一个人看懂的写法；
一段只有你能看懂的聪明代码，代价会在两年后由别人支付。

**这也是本教材为什么坚持把限制写出来。**
一个结论在什么条件下成立、在什么条件下失效，比结论本身更重要，
因为**接手的人需要知道边界在哪里。**

## 2.5 一条分界：可检索的与需要负责的

把第 1 节与第 2 节合起来看，分界很清楚：

`Text`

```text
        可检索的                          需要负责的
   ┌────────────────────┐          ┌────────────────────┐
   │  事实、语法、API   │          │  判断、验证、组合  │
   │  常见写法、样板    │          │  边界、取舍、责任  │
   │  有唯一正确答案    │          │  取决于你的处境    │
   └────────────────────┘          └────────────────────┘
            正在被接管                       正在变值钱
```

**这条分界不是永久的**，它每年都在往右挪一点。
**但挪动的方式是「右边的一部分变成左边」，而不是「右边消失」。**
今天需要判断的事，明天可能变成有标准答案的事；
而今天还没有人能判断的事，明天依然要有人去判断。

**学习的方向因此变得清楚：往右边站。**

# 第 3 节 为什么会这样

## 3.1 它擅长的是「像」而不是「是」

**语言模型做的事，是根据已有的文本推断接下来最可能出现的文本。**

这个机制在「像」这个维度上非常强：
它见过海量的代码，因此知道一段 C 代码通常长什么样、
知道命名一般怎么起、知道注释一般写在哪儿、
知道一个问题通常的解法有哪几种。

**它给出的答案是「最可能的」，不是「在你的机器上成立的」。**
这两件事在大多数时候重合，所以它看起来非常准；
而在不重合的时候，它依然会用同样确定的语气说出来。

**这一点与本教材的做法正好相反。**
本教材要求每个技术结论都标出依据：跑过的标 `实测数据`，
引自资料的标 `文档`，没验证的标 `待确认`，
随环境而变的写明**存疑**。
**标依据的成本很高，但它换来的东西是：读者知道哪一句话可以信到什么程度。**

## 3.2 流畅与正确之间没有等号

**流畅是一种观感，正确是一种事实。**

一段代码读起来合理，可能是因为它符合我们对这类代码的印象，
而不是因为它在这个环境里真的能工作。
第 2.2 小节那三个例子，都属于「读起来合理、跑起来不对」。

**更麻烦的是，错误往往不在显眼的地方。**

一段少写 `volatile` 的轮询代码，编译没有任何警告，
逻辑读起来完全正确，静态检查也挑不出毛病——
**因为它的错误要到「编译器优化之后、硬件真的在另一个上下文里改这个变量」时才成立。**
这类问题不能靠读，只能靠**在真实条件下跑，并且知道该看什么**。

**因此有一句判断标准值得记住**：
**凡是「不跑就不知道」的结论，都必须跑。**

## 3.3 谁有权签发「正确」

**在一台具体机器上跑出来的输出，是唯一有权签发「正确」的东西。**

不是文档，因为文档可能对应另一个版本；
不是经验，因为经验可能来自另一个平台；
更不是「说得通」，因为说得通是最低标准。

**这也是本教材把「可复现」看得比「讲得漂亮」重的原因。**
每个保留在正文里的实例都写成完整单文件，
首行注释给出编译与运行命令，
结论下面贴着这些命令的真实输出。
**读者不必相信作者，照着敲一遍就行。**

**这套做法在有人工智能之后，重要性只增不减。**
因为生成的成本下降了，**验证就成了瓶颈**。
一个系统里，能被快速生成的代码越多，能被快速验证的代码就越值钱。

# 第 4 节 于是要学什么

## 4.1 机制：东西是怎么运转的

**机制是判断的地基。**

不知道编译器会做哪些优化，就无法判断一段代码在 `-O2` 下是否还成立；
不知道链接器怎么分配地址，就无法判断一个「内存不够」的报错从哪来；
不知道函数调用时寄存器和栈各自承担什么，就无法判断一段内联汇编是否安全。

**这部分内容分布在本教材的三个位置**：

| 讲什么 | 在哪 |
|---|---|
| 从源码到可执行文件这条链条 | `01-编译器` 板块 |
| 出错时怎么看现场 | `02-调试器` 板块 |
| 地址、对齐、`volatile`、ABI、链接脚本、系统调用、并发与内存序 | `06-更底层` 板块 |

**这些内容的特点是：不常改。**
一门语言的语法会增补，一个库的接口会变化，
而「栈向低地址增长」「结构体要按最宽成员对齐」「中断里改的变量主循环可能看不见」这些事，
十年二十年不动。

## 4.2 组合：零件怎么拼成一个能跑的系统

**组合能力要靠完整的工程练，不能靠零散的片段。**

一个能跑起来的工程至少包含：
构建描述（怎么编）、依赖管理（用谁的东西）、
目录结构（东西放在哪）、配置（编成什么样）、
以及一条从源码到产物的可重复路径。
**本教材的练习模板只给骨架，配置留给自己写**，
原因就在这里：**看一遍不算会，配一遍才算。**

| 讲什么 | 在哪 |
|---|---|
| 构建工具链、执行器、包管理、符号、优化等级 | `03-构建工具链` 板块 |
| 一个完整示例工程长什么样 | `B-examples/` |
| 分阶段的练习模板 | `C-templates/` |

## 4.3 证据：怎么验证一句话

**这是本教材反复演示、也最希望被带走的一项能力。**

它由四个动作组成：

| 动作 | 做法 |
|---|---|
| **限定条件** | 说清楚在哪个平台、哪个编译器、哪个版本、哪一级优化下成立 |
| **给出命令** | 让人能照着敲，而不是只给结论 |
| **贴出输出** | 真实输出，包括报错原文，不改写 |
| **写明边界** | 什么情况下这个结论不成立 |

**这四步看起来笨，但它是把「印象」变成「知识」的唯一办法。**
一个人如果只记住结论，换一个环境就会失效；
记住的是「怎么验证」，换到哪里都能重新确认一遍。

**本教材对不确定的东西有三种处理方式，值得作为习惯带走**：

| 状态 | 含义 | 写作时怎么写 |
|---|---|---|
| `实测数据` | 跑过，输出可复现 | 标记 + 真实输出 |
| `待确认` | 尚未验证，但原则上可验证 | 标记 + 卡在哪一步 |
| **存疑** | 随环境而变，给不出统一结论 | 写明变的是什么、为什么定不下来 |

**第三种最容易被忽略。** 很多问题的答案取决于读者装了什么扩展、用了哪个版本，
作者在自己的机器上跑通，不代表读者能用。
**把这些写成「存疑」而不是「已验证」，是一种诚实，也是一种能力。**

## 4.4 提问：把愿望写成可执行的问题

**提问的质量，直接决定答案的质量**，这一点在有人工智能之后尤其明显。

「这段代码有 bug 吗」是一个几乎无法回答的问题。
「在 `-O2` 下，这个循环读到的标志位会不会被优化掉」是一个可以回答的问题。

**把愿望变成问题，需要三样东西**：
知道系统由哪些部分组成（机制）、
知道哪些部分可能出错（经验）、
知道怎么描述一个可验证的现象（证据）。
**这三样正好是前面三节的内容——它们在这里汇合。**

# 第 5 节 这本教材为什么这样写

## 5.1 只写跑得起来的东西

**保留在正文里的每个实例都是完整单文件**：
有 `#include`、有 `int main`、首行注释写明编译与运行命令。
**代码块要么是完整的，要么明确标注「（下面是节选）」，不留没有交代的碎片。**

**理由很实在**：碎片读起来轻松，但读完仍然不知道该怎么动手；
完整文件读起来费劲，但抄下来就能跑，跑完就有一份自己的输出。
**能跑的东西才谈得上验证。**

## 5.2 把不确定标出来

**教材里不会出现「通常」「一般来说」这类含糊词，也不会用流畅的语气掩盖空洞。**

每个技术结论都带依据标注；没验证的明说没验证；
随环境而变的写清为什么给不出统一答案。
**读者看到 `实测数据` 时，可以放心照着做；
看到「待确认」时，知道自己要留心。**

**这套标注不只是给读者看的，也是写给作者的约束。**
写下一个数字之前必须先跑一遍，
这个要求会强迫人把话说实——**这是本教材最重要的规矩。**

## 5.3 讲为什么，不只讲怎么做

**「怎么做」会被检索替代，「为什么」不会。**

因此每一处结论都尽量给到机制层：
为什么寄存器要用 `volatile` 修饰的指针访问、
为什么 `.data` 段要在启动时从 flash 搬到 RAM、
为什么两个线程同时加一最后不等于加二。
**知道了为什么，遇到没人写过的情形才推得下去。**

**与之配套的是：数据与结论分开摆。**
支撑讲解必须用到的数据留在正文；
只是佐证的、与论证无关的清单，移到附录或素材目录。
**判断标准一句话：把这组数据删掉，这段讲解还成立吗。**

## 5.4 留给你动手的那一半

**教材提供骨架，读的人补上实现。**

`C-templates/` 里的练习模板大多分阶段：
第一阶段只留下要填的位置，后面几个阶段逐步加约束，
最后一阶段给出参考做法。
**这样安排的原因是：读懂的代码与写出来的代码，隔着一道必须自己跨过去的门。**

**这道门跨过去之后，地图就换了。**
原来记住的东西变成了工具，原来模糊的东西变成了判断，
原来「能编译」的东西开始要求「在约束下正确」。

# 第 6 节 与 AI 共事

## 6.1 把它当检索器与草稿机

**这是它最擅长的位置。**

查一个函数签名、问一个报错的大致方向、
让它把一段重复的样板写出来、
让它把一份接口文档翻译成结构体定义、
让它解释一段别人写的代码在做什么。
这些事情它做得又快又稳，**省下来的时间正好用在判断与验证上。**

**用得好的标志是：你越来越清楚哪些问题不必自己动手，
也越来越清楚哪些问题必须自己动手。**

## 6.2 验证权留在自己手里

**生成是它的强项，验证是它的短板。**

一个句子读起来通顺，一段代码看起来合理，
并不构成「在你的机器上成立」的证据。
**凡是「不跑就不知道」的结论，都必须跑**——
这句话对人和对机器同样有效。

**本仓库里有一份 `AGENTS.md`**，它规定用 AI 打开这个工作区时应当遵守什么：
只依据仓库内文档作答，不许用外部知识补全教材没写的内容，
不许把标了 `待确认` 或写明「存疑」的内容说成确定的，
引用必须落到《路径》第 N 节。
**这套规则不是限制，而是把「验证权在自己手里」这句原则写成了可执行的约定。**

## 6.3 提问的质量决定答案的质量

**同一个工具，问得好与问得差，得到的东西差得很远。**

一个好的提问通常包含四件事：
**环境**（平台、编译器、版本、优化等级）、
**现象**（看到的原文，不是转述）、
**期望**（本来想让它做什么）、
**已知**（已经排除过哪些可能）。

**这四件事与本教材要求 `实测数据` 时必须交代的内容几乎一样**，
因为它们服务的是同一个目的：**让别人（或别的工具）能复现你说的问题。**

## 6.4 什么时候不要用它

**有三种场合，先自己想。**

| 场合 | 为什么 |
|---|---|
| **第一次学一个机制** | 先自己推一遍，再对照答案，才知道自己错在哪一步；直接看答案会把「看懂」误当成「会」 |
| **需要留下判断依据时** | 依据必须来自你自己验证过的东西，否则出了问题无法解释 |
| **涉及真实设备的操作** | 烧写、擦除、改配置这类动作不可逆，动手前要知道会发生什么 |

**这不是拒绝工具，而是安排顺序。**
工具在「我推完了，来对一下」这个位置上，价值最大。

# 第 7 节 写在开始之前

## 7.1 从会背到会判断

**一个人学编程的路径，正在从「积累知识」变成「积累判断」。**

积累知识的时代，差距来自谁记得多；
积累判断的时代，差距来自谁见过更多的系统、知道更多的代价、
并且能在没有标准答案的时候做出选择。

**判断不能凭空长出来。**
它需要真实的机器、真实的报错、真实的约束，
需要在深夜为了一个「明明应该能跑」的问题翻出汇编，
需要在把程序烧进板子之后发现它一动不动，然后顺着线索找到那个被优化掉的读操作。

**本教材里每一条 `实测数据`，背后都是这样一段时间。**

## 7.2 把时间花在哪

**把时间花在不会被替代的地方。**

| 少花一点时间 | 多花一点时间 |
|---|---|
| 背 API 与参数表 | 弄清一个机制为什么这样设计 |
| 抄一个能跑的样板 | 自己配一遍，看每一行配置在起作用什么 |
| 记住结论 | 记住结论的**边界**——它在什么条件下不成立 |
| 追求代码看起来聪明 | 追求代码能被下一个人看懂 |
| 问「这段代码对吗」 | 问「在什么条件下它会不对」 |

**这些选择短期看不出差别，长期会把两个人分到完全不同的位置。**

## 7.3 速查表

| 状态 | 什么时候用 | 写作时的写法 |
|---|---|---|
| 已经交出去 | 记忆、翻译、样板 | 查得到就行，不必背 |
| 必须留下 | 判断、验证、组合、负责 | 靠真实项目积累 |
| 学习方向 | 机制、组合、证据、提问 | 本教材四个板块分别对应 |
| 验证四步 | 限定条件、给出命令、贴出输出、写明边界 | 本教材对每个结论的要求 |
| 不确定的三种处理 | `待确认`、**存疑**、`实测数据` | 不许含糊带过 |
| 与 AI 共事的底线 | **生成可以外包，验证不能** | `AGENTS.md` 是这条原则的落地 |
