要在一百万个整数里回答十万次「这个数在不在」，同一份数据可以有四种摆法：
不排序直接从头找、排好序用二分、放进 `std::map`、放进 `std::unordered_map`。
四份程序做的事完全一样，答案完全一样，**实测的耗时相差约三个数量级**。
变的不是数据，也不是需求，只是数据怎么摆、找的时候按什么线索走。

这类问题在写代码时到处都是。通讯录要按名字查，也要按首字母列出全部；
任务调度要每次取出最紧急的那一件；文件系统要在一次磁盘读取里定位到成千上万个键。
每一个需求都在追问同一件事：**这些数据该按什么形状摆起来。**
形状选对了，操作就便宜；形状选错了，再快的机器也救不回来。

**结构不是目标，是需求留下的形状。**
先把需求问清楚——谁在什么时候、要对数据做什么、各做多少次——
再让形状从需求里长出来，不背结构的名字，也不把结构当成「高级」的象征。

# 第 1 节 结构由需求决定

## 1.1 同一个问题，四种摆法

把需求写清楚是这样：有一百万个整数，要回答十万次「某个数在不在里面」，
其中大约一半的问题答案是在。

这份需求里有一个容易被忽略、但决定一切的问法：**「在不在」**。
它只要求一个是非答案，不要求顺序，不要求取出这个数，也不要求范围。
下面四份程序都满足它，区别只在于数据怎么摆。

`C++`

```cpp
/* four_ways.cpp    编译：g++ -std=c++17 -O2 four_ways.cpp -o four_ways
 * 同一份数据、同一个需求（某数在不在）的四种摆法，各计时一次 */
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <map>
#include <random>
#include <unordered_map>
#include <vector>

// 计时小工具：把一段代码跑一次，返回毫秒
template <class F>
static double time_ms(F&& f) {
    const auto t0 = std::chrono::steady_clock::now();
    f();
    const auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

int main() {
    constexpr int N = 1000000;          // 一百万个键
    constexpr int Q = 100000;           // 十万次查询
    std::mt19937 rng(12345);

    std::vector<int> keys(N);
    for (int i = 0; i < N; ++i) keys[i] = i * 2;      // 递增，天然有序

    std::vector<int> unsorted = keys;                 // 摆法一：打乱后不排序
    std::shuffle(unsorted.begin(), unsorted.end(), rng);

    std::map<int, int> omap;                          // 摆法三：平衡搜索树
    std::unordered_map<int, int> umap;                // 摆法四：哈希表
    for (int k : keys) { omap[k] = k; umap[k] = k; }

    std::vector<int> queries(Q);                      // 查询里一半左右能命中
    for (int& q : queries) q = rng() % (N * 2);

    volatile long long hits = 0;                      // 让编译器不敢把结果删掉

    const double t_lin = time_ms([&] {                // 摆法一：线性查找
        long long h = 0;
        for (int q : queries)
            h += std::find(unsorted.begin(), unsorted.end(), q) != unsorted.end();
        hits += h;
    });
    const double t_bin = time_ms([&] {                // 摆法二：有序 + 二分
        long long h = 0;
        for (int q : queries) h += std::binary_search(keys.begin(), keys.end(), q);
        hits += h;
    });
    const double t_map = time_ms([&] {                // 摆法三：树里找
        long long h = 0;
        for (int q : queries) h += omap.find(q) != omap.end();
        hits += h;
    });
    const double t_umap = time_ms([&] {               // 摆法四：哈希里找
        long long h = 0;
        for (int q : queries) h += umap.find(q) != umap.end();
        hits += h;
    });

    std::printf("N=%d 个元素，%d 次查找（一半命中）\n", N, Q);
    std::printf("%-34s %10.3f ms\n", "无序 vector + std::find", t_lin);
    std::printf("%-34s %10.3f ms\n", "有序 vector + binary_search", t_bin);
    std::printf("%-34s %10.3f ms\n", "std::map::find", t_map);
    std::printf("%-34s %10.3f ms\n", "std::unordered_map::find", t_umap);
    std::printf("（命中计数 %lld，防止被优化掉）\n", static_cast<long long>(hits));
    return 0;
}
```

`实测数据`
`Text`

```text
N=1000000 个元素，100000 次查找（一半命中）
无序 vector + std::find            9285.467 ms
有序 vector + binary_search           9.347 ms
std::map::find                         45.911 ms
std::unordered_map::find                2.998 ms
（命中计数 200368，防止被优化掉）
```

**四份程序做的事完全一样，耗时却从 9285.467 ms 到 2.998 ms，相差约 3000 倍。**
同一条查询语句、同一个编译器、同一台机器，差别只在数据怎么摆：
连续内存排不排序、树按不按大小组织、表按不按哈希值分桶。

> [!IMPORTANT]
> **结构的作用是把某类操作的代价压下来，代价则转移到别处。**
> 无序数组的「在不在」要一次一次比，但插入新元素最便宜；
> 有序数组的二分只要约 20 次比较就能排除一百万个数，
> 但每插入一个数都要把后面所有元素挪一格；
> 树和哈希表把插入变便宜了，代价是每个元素都要多存指针或桶位。
> **没有哪一种摆法全面胜出，只有哪一种更适合这份需求。**

## 1.2 需求决定形状

把上面那句话落到具体动作上：**先问需求，形状就定了。**

| 需求里的关键动作 | 频率 | 它逼出来的形状 |
|---|---|---|
| 按下标取第 i 个 | 极多 | 一块连续内存，地址能算出来 |
| 在中间插入、删除 | 极多 | 元素之间用指针连起来，插入时只改指针 |
| 按值查在不在 | 极多 | 另建一张能快速定位的表（有序或哈希） |
| 按范围取一批 | 多 | 有序，且能取前驱与后继 |
| 只在一端进出 | 极多 | 只要一端，别的口都封上 |
| 每次取最小 | 极多 | 只维护「最小在上面」这一个不变式，不必全序 |
| 数据大到内存装不下 | —— | 一次读一页，把树压矮 |

**这张表从左往右读**：左边是动作与它的频率，右边是这个动作逼出来的形状。
反过来读——先记住「堆」这个名字，再去找什么场合能用它——就会变成背名词。

## 1.3 名字是结果，不是起点

初学时常听到的一串名词是：链表、栈、队列、哈希表、二叉树、红黑树、B+ 树、trie、并查集。
它们都是**结果**：某个具体需求反复出现之后，有人把解法固定下来，起了个名字。

举一个例子。需求是「数据存在磁盘上，一次读只能读一页（比如 4 KiB），
要在这堆数据里按键查，而且要能按范围顺序取」。
先从最朴素的做法开始：用一棵二叉搜索树。每个节点存一个键，
树高约等于 `log2(n)`；一亿条数据要跳约 27 次。
可这 27 次是 27 次磁盘读取——每次都等一次寻道，代价无法接受。

于是有人问：**能不能让每个节点多存几个键、多分几个叉？**
一次读一页，就把一页塞满：一个节点存几百个键、分出几百个叉。
树高立刻从 27 掉到 3 到 4 层，三次磁盘读取就够。
**这就是 B 树与 B+ 树。它不是先发明出来再找用途，而是这一页的大小逼出来的。**

同一件事在本板块会出现很多次：

| 需求卡在哪 | 需求逼出的结构 |
|---|---|
| 一块内存装不下、要重新分配 | 连续存储的分段增长（`A-01`） |
| 插入要搬动后面所有元素 | 链式存储（`A-02`） |
| 朴素搜索树在有序输入下退化成链表 | 平衡（`A-07`） |
| 树太深、一次只能读一页 | 多路树（`A-08`） |
| 关系不是层次，而是任意相连 | 图的两种存法（`A-10`） |

> [!NOTE]
> **问清楚「要做什么、做多少次」，结构就是从这两个问题的答案里推出来的，
> 不是从名词表里挑出来的。**

# 第 2 节 三类存储模型

数据摆在内存里，只有三种基本摆法：**挤在一起、用指针连起来、另存一张表指向它。**
所有常见的结构都是这三类的组合或变体。

## 2.1 连续：一整块内存

一次向系统要一块内存，把所有元素按顺序排进去。第 `i` 个元素的地址由起始地址算出来，
不需要任何查找。

`Text`

```text
  一块连续的内存（每个格子 4 字节）：

    ┌────┬────┬────┬────┬────┬────┐
    │ 7  │ 1  │ 9  │ 3  │ 5  │ 8  │      第 i 个元素在 base + i × 4
    └────┴────┴────┴────┴────┴────┘
     base  +4   +8   +12  +16  +20
      ↑
      整块由容器持有，用完一次性还回去
```

**特点**：按下标取元素是 `O(1)`，而且只要一次乘加；一整块内存连着读，
硬件的一次读取能把后面若干个元素一起带进缓存，遍历极快。

**代价**：中间插入或删除一个元素，后面全部要挪一格，是 `O(n)`；
元素个数超出容量时，要另找一块更大的内存，把全部元素搬过去。
`A-01` 会给出这两件事的实测数据。

## 2.2 链式：节点用指针相连

每个元素单独占一小块内存，块里除了数据还存着「下一个在哪」。

`Text`

```text
  ┌───────────┐     ┌───────────┐     ┌───────────┐
  │ 7 │下一个 ┼────►│ 1 │下一个 ┼────►│ 9 │下一个 ┼────► 空
  └───────────┘     └───────────┘     └───────────┘
    一块一块向系统要，位置互不相邻

双向链表（`list`）的每一块再多存一个「上一个在哪」，
因此既能往回走，插入与删除时也不必先知道前一个是谁。
```

**特点**：只要手里已经拿着某个位置，在它旁边插入或删除只需改几个指针，是 `O(1)`，
而且不需要挪动任何元素；插入的元素也不会让别的元素换地址。

**代价**：按下标取第 `i` 个元素要从头一个一个跳过去，是 `O(n)`；
每个元素都要多付一个或两个指针的空间；元素散落在堆上，
遍历时缓存帮不上忙。`A-02` 会用实测把这三笔代价摆出来。

## 2.3 索引：另存一张表

数据本身不动，另外维护一张表，表里记着「去哪里找」。查找先查表，再按表里的线索取数据。

`Text`

```text
   ┌──────────────┐              ┌──────────┬──────────────┐
   │  键 42  ...  │◄─────────────┤  42      │指向 42 的条目│
   ├──────────────┤              ├──────────┼──────────────┤
   │  键 7   ...  │◄─────────────┤   7      │指向 7 的条目 │
   ├──────────────┤              ├──────────┼──────────────┤
   │  键 91  ...  │◄─────────────┤  91      │指向 91 的条目│
   └──────────────┘              └──────────┴──────────────┘
   ↑ 数据区（位置任意）            ↑ 索引表（另存一张，按键组织）

   索引表怎么组织，决定了查找有多快：
   排好序 → 二分或树；按哈希值分桶 → 直接定位
```

**特点**：把「按什么查」和「数据怎么存」分开。
索引表可以有各种组织方式——排序数组、搜索树、哈希桶——
每一种都在「查找快」「插入便宜」「能按范围取」之间做不同的取舍。

**代价**：多一张表的空间，写入时要同时维护数据与索引；
索引表自己也可能需要重新组织（排序数组的插入要挪、哈希表的桶满了要再哈希）。

## 2.4 三种模型会叠在一起用

三类模型不是三选一，真实的容器经常是两层甚至三层的组合：

| 你用的东西 | 拆开看是哪几层 |
|---|---|
| `std::vector` | 连续 + 一块容量计数 |
| `std::list` | 链式 |
| `std::map` | 索引（树） + 每个节点一块独立内存（链式的分配方式） |
| `std::unordered_map` | 索引（桶数组，连续） + 每个桶挂一条链（链式） |
| 数据库的索引 | 索引（B+ 树） + 数据按页存放（连续） |
| 图的邻接表 | 索引（每个顶点一条边表） + 每条边表是连续或链式 |

**看懂一个容器，就是看懂它由哪几层拼起来、每层各付出什么代价。**
这也是后面每一章的做法：先把模型画出来，再看接口，最后测量代价。

|---|---|---|---|---|---|
| **连续**（`vector`） | `O(1)` | `O(n)`（要挪后面） | `O(n)`；排好序后 `O(log n)` | 约 0 到几个字节 | **最快**（1.24 ms） |
| **链式**（`list`） | `O(n)` | **`O(1)`**（改指针） | `O(n)` | **一个或两个指针**（24 字节/元素） | 慢（68.03 ms，约 55 倍） |
| **索引**（`map`） | 不支持 | `O(log n)` | `O(log n)` | 节点链接与平衡信息（40 字节/元素） | 中 |
| **索引**（`unordered_map`） | 不支持 | 平均 `O(1)` | **平均 `O(1)`** | 节点 + 桶数组（43.26 字节/元素） | 中 |

**最后一行「头部插入」的数字最能说明问题**：一百万个元素依次往头部插，
`vector` 花了 34742.979 ms，`list` 花了 41.435 ms，相差约 840 倍。
但如果**换个做法**——先 `push_back` 再一次性 `reverse`——同一份连续存储只花 1.957 ms，
比链表还快 21 倍。

> [!IMPORTANT]
> **这份数据里最该记住的不是「链表快」或「数组快」，而是「访问模式决定谁快」。**
> 链表赢在「位置已知时的插入」，输在「遍历」与「按下标取」；
> 连续存储输在「中间插入」，赢在别的一切。
> 而「先攒后翻」这种做法能同时拿到两边的好处，说明**结构选对之后，用法还能再省一截**。

# 第 3 节 从需求到代价：本板块的推进路线

## 3.1 五个阶段各回答什么

本板块的每一章都按同一条路线推进。**顺序不能换**：先有需求，才谈得上模型；
模型定下来，接口才有意义；接口定下来，实现才有目标；实现写完，代价才有得测。

`Mermaid`

```mermaid
flowchart LR
    A["需求<br/>谁要做什么、各做多少次"] --> B["模型<br/>数据按什么形状摆"]
    B --> C["接口<br/>对外给出哪些操作"]
    C --> D["实现<br/>这些操作怎么做出来"]
    D --> E["代价<br/>时间、内存、分配次数"]
    E -.->|"不够用就换模型"| B
```

| 阶段 | 回答的问题 | 判断「做完了」的标准 |
|---|---|---|
| **需求** | 谁要对数据做什么？每个动作各做多少次？数据有多大？ | 能写出具体次数，例如「一百万条，十万次查询，一半命中」 |
| **模型** | 数据按什么形状摆？靠什么线索定位？ | 能画出图，能说清每个元素额外付多少空间 |
| **接口** | 对外提供哪些操作？每个操作的语义与前提是什么？ | 能写出调用方的代码，且不关心内部怎么实现 |
| **实现** | 这些操作各自怎么做出来？改了哪些内部状态？ | 能跑，且边界情况（空容器、满了、重复键）都交代过 |
| **代价** | 每个操作的时间与空间是多少？最坏情况是什么？ | **有本机跑出来的数字**，不是「应该很快」 |

**这条路线也是本板块与「背结论」的分界线。**
只记住「`map` 查找是 `O(log n)`」是结论，属于最后一格；
知道它为什么是 `O(log n)`、为什么插入要旋转、为什么每个元素要付 40 字节，
才是走完了整条路线。

## 3.2 五阶段走完第 1 节的例子

用 1.1 的查询需求把五个阶段各填一次，整条路线就落地了。

| 阶段 | 这份需求下的答案 |
|---|---|
| **需求** | 一百万个整数；十万次「在不在」，约一半命中；数据建好之后不再增删 |
| **模型** | 四种候选：无序连续、有序连续、平衡搜索树、哈希表 |
| **接口** | `std::find`（返回迭代器）、`std::binary_search`（返回 `bool`）、`find`（返回迭代器，比到 `end()` 表示没有）、`unordered_map::find`（同上） |
| **实现** | 逐个比较；每次砍掉一半区间；沿树往下走；算出哈希值直接跳到某个桶 |
| **代价** | 9285.467 / 9.347 / 45.911 / 2.998 ms（见第 1.1 小节） |

**关键在接口那一格**：四种摆法的接口几乎一样，
调用方写起来都是「拿一个键，问在不在」。
接口一样而代价差三个数量级，这正是「结构藏在接口后面」的意思——
用错结构，代码照样编译、功能测试照样通过，只有在真实规模上才暴露：
这份数据里就是九秒与三毫秒的差别。编译器与单元测试都不会提醒一个字。


`C++`

```cpp
/* one_demand_four_interfaces.cpp
 * 编译：g++ -std=c++17 -O2 one_demand_four_interfaces.cpp -o one_demand_four_interfaces
 * 同一句「在不在」，四种接口的写法：调用方看起来差不多，背后完全不同 */
#include <algorithm>
#include <cstdio>
#include <map>
#include <set>
#include <unordered_map>
#include <unordered_set>
#include <vector>

int main() {
    const std::vector<int> sorted_keys{1, 3, 5, 7, 9};        // 有序连续
    const std::vector<int> raw_keys{5, 1, 9, 3, 7};            // 无序连续
    const std::set<int> tree_keys{1, 3, 5, 7, 9};              // 树
    const std::unordered_set<int> hash_keys{1, 3, 5, 7, 9};    // 哈希

    const int q = 7;

    const bool a = std::find(raw_keys.begin(), raw_keys.end(), q) != raw_keys.end();
    const bool b = std::binary_search(sorted_keys.begin(), sorted_keys.end(), q);
    const bool c = tree_keys.find(q) != tree_keys.end();
    const bool d = hash_keys.find(q) != hash_keys.end();

    std::printf("无序连续：%d\n", a);
    std::printf("有序连续：%d\n", b);
    std::printf("树      ：%d\n", c);
    std::printf("哈希    ：%d\n", d);
    return 0;
}
```

`实测数据`
`Text`

```text
无序连续：1
有序连续：1
树      ：1
哈希    ：1
```

**四个答案一样，四份代码的语义也一样，差别只在数据怎么摆。**
所以选结构这件事不会在编译期报错，也不会在功能测试里露馅，
只会在一百万条数据、十万次查询的时候变成九秒与三毫秒的差别。

## 3.3 代价只能测，不能猜

「这个操作大概是 `O(log n)`」是分析，不是数据。
真正写进代码做取舍时，常数因子、缓存、分配次数往往比量级更管用——
一百万个元素的 `O(log n)` 查找是 20 次比较，
而一次内存分配本身就可能比 20 次比较贵。

测量代价时有三条纪律，违反了会得到看似合理、实则无意义的数字。
下面三条都有本机的实测支持。

**纪律一：算出来的结果要有人用。** 优化器会把没人读的计算整段删掉。

`C++`

```cpp
/* elide_result.cpp    编译：g++ -std=c++17 -O2 elide_result.cpp -o elide_result
 * 同一段求和，一处结果没人读，一处把结果读出来 */
#include <chrono>
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> v(1000000, 1);
    volatile long long sink = 0;                 // volatile：写入是「可观察的」

    const auto t0 = std::chrono::steady_clock::now();
    for (int r = 0; r < 200; ++r) {
        long long s = 0;
        for (int x : v) s += x;                  // s 从来没人读
    }
    const auto t1 = std::chrono::steady_clock::now();

    const auto t2 = std::chrono::steady_clock::now();
    for (int r = 0; r < 200; ++r) {
        long long s = 0;
        for (int x : v) s += x;
        sink += s;                               // 结果被读出来
    }
    const auto t3 = std::chrono::steady_clock::now();

    auto ms = [](auto a, auto b) {
        return std::chrono::duration<double, std::milli>(b - a).count();
    };
    std::printf("200 轮遍历 100 万个 int，结果没人读  %10.3f ms\n", ms(t0, t1));
    std::printf("200 轮遍历 100 万个 int，结果读出来  %10.3f ms\n", ms(t2, t3));
    std::printf("（sink=%lld）\n", static_cast<long long>(sink));
    return 0;
}
```

`实测数据`
`Text`

```text
200 轮遍历 100 万个 int，结果没人读       0.000 ms
200 轮遍历 100 万个 int，结果读出来      19.584 ms
```

**优化器把两亿次加法整段删掉了，测出来是 0.000 ms。**
反过来，也不必为此到处加屏障：把结果读到 `volatile` 变量里、
或者返回给调用方，编译器就不会删掉它。

`待确认`

「优化器会把没人读的容器整个删掉」这个说法在本机没有复现：
用替换 `operator new` 计数时，八种「没人读」的写法在 `-O2` 与 `-O0` 下分配次数完全一致；
改成用耗时观察一亿个 `int` 的 `vector` 与一百万个节点的 `list`，
加屏障与不加屏障两组数字交错，看不出系统性差异。
真正会被删掉的是**没人读的计算结果**，而不是分配本身。
两份探针的源码与真实输出见附录 A.1；
这一条的成立范围随编译器与优化级别而变，读者应以自己的编译器实测为准。

**纪律二：不要把「看起来像在测」的写法当成证据。**
下面这份程序想比较同一个 `std::distance` 在两种容器上的代价。

`C++`

```cpp
/* distance_cost.cpp    编译：g++ -std=c++17 -O2 distance_cost.cpp -o distance_cost
 * 编译（对照）：g++ -std=c++17 -O0 distance_cost.cpp -o distance_cost_O0
 * 同一个 std::distance/std::advance，在 vector 与 list 上的代价
 * 带 -O0 的构建是为了看「没有优化时」这两步各要多久，两行输出要对照着读 */
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <iterator>
#include <list>
#include <vector>

template <class C>
static void clobber(C& c) { asm volatile("" : : "r"(&c) : "memory"); }

template <class F>
static double best_ms(int rounds, F&& f) {
    double best = 1e300;
    for (int i = 0; i < rounds; ++i) {
        const auto t0 = std::chrono::steady_clock::now();
        f();
        const auto t1 = std::chrono::steady_clock::now();
        best = std::min(best, std::chrono::duration<double, std::milli>(t1 - t0).count());
    }
    return best;
}

int main() {
    constexpr int N = 1000000;
    std::vector<int> v(N, 1);
    std::list<int> l(N, 1);
    volatile long long sink = 0;

    const double d_vec = best_ms(5, [&] {
        long long s = 0;
        for (int r = 0; r < 1000; ++r) { clobber(v); s += std::distance(v.begin(), v.end()); }
        sink += s;
    });
    const double d_lst = best_ms(5, [&] {
        long long s = 0;
        for (int r = 0; r < 100; ++r) { clobber(l); s += std::distance(l.begin(), l.end()); }
        sink += s;
    });
    std::printf("100 万元素\n");
    std::printf("  vector：1000 次 std::distance(begin,end)  %12.3f ms\n", d_vec);
    std::printf("  list  ：100 次  std::distance(begin,end)  %12.3f ms\n", d_lst);

    const double a_vec = best_ms(5, [&] {
        long long s = 0;
        for (int r = 0; r < 100000; ++r) { auto it = v.begin(); std::advance(it, 999999); s += *it; }
        sink += s;
    });
    const double a_lst = best_ms(5, [&] {
        long long s = 0;
        for (int r = 0; r < 10; ++r) { auto it = l.begin(); std::advance(it, 999999); s += *it; }
        sink += s;
    });
    std::printf("\n  vector：10 万次 std::advance(it,999999)  %12.3f ms\n", a_vec);
    std::printf("  list  ：10 次   std::advance(it,999999)  %12.3f ms\n", a_lst);
    std::printf("（sink=%lld）\n", static_cast<long long>(sink));
    return 0;
}
```

同一个程序、同一批数据编成两份，先后跑出来的结果如下。`-O2` 的结果：

`实测数据`
`Text`

```text
100 万元素
  vector：1000 次 std::distance(begin,end)         0.000 ms
  list  ：100 次  std::distance(begin,end)         0.000 ms

  vector：10 万次 std::advance(it,999999)         0.000 ms
  list  ：10 次   std::advance(it,999999)        38.667 ms
```

`-O0`（同一份源码，不优化）的结果：

`实测数据`
`Text`

```text
100 万元素
  vector：1000 次 std::distance(begin,end)         0.002 ms
  list  ：100 次  std::distance(begin,end)       409.667 ms

  vector：10 万次 std::advance(it,999999)         0.208 ms
  list  ：10 次   std::advance(it,999999)        39.248 ms
```

**链表上从头走一百万步、走一百次，按同一台机器上链表遍历的实测速度
（一百万个节点，每元素约 3.8 ns，见 `A-02` 的附录）折算该是 380 ms 上下，
`-O2` 下却测出 0.000 ms，而同一份程序换成 `-O0` 编译就是 409.667 ms。**
两个数印证了同一件事：计时区间没有漏掉这 100 次调用，而是**编译器把它们换掉了**。

原因是这套标准库给 `list` 迭代器写了一条专用重载：只有当编译器能证明
「这段区间就是整条链」时（`l.begin()` 与 `l.end()` 这一对），
它才不数节点，直接返回节点头里记着的元素个数——这一步于是真的成了 `O(1)`。
`-O0` 下编译器不做这种判定，捷径用不上，只能一步一步数，因此回到 409.667 ms，
与按遍历速度折算的 380 ms 吻合。

**这条捷径换一套标准库、或者把区间换成子区间就不成立**，那时它就是实打实的 `O(n)`。
同一份程序里 `std::advance` 的 `-O2` 与 `-O0` 数字接近（38.667 与 39.248 ms），
说明编译器没有把它换掉：链表上跳 999999 步，每次约 **3.9 ms**。

> [!WARNING]
> **想测 A 的代价，测到的却可能是优化后的 B。**
> 怀疑某个循环被优化掉时，把它拆成「数据规模由运行期决定」（例如从命令行参数读进来），
> 或者让目标位置真的依赖运行期取值；两者选一，通常就露出来了。

**纪律三：规模太小，一遍测出来是 0。**
时钟的分辨率有限，一次只跑几千个元素，测到的就是 0.000。

`C++`

```cpp
/* small_scale.cpp    编译：g++ -std=c++17 -O2 small_scale.cpp -o small_scale
 * 同一个遍历：只做一遍测出 0，做够轮数才有数 */
#include <chrono>
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> small(1000, 1);
    volatile long long sink = 0;

    const auto t0 = std::chrono::steady_clock::now();
    { long long s = 0; for (int x : small) s += x; sink += s; }
    const auto t1 = std::chrono::steady_clock::now();

    const auto t2 = std::chrono::steady_clock::now();
    for (int r = 0; r < 100000; ++r) { long long s = 0; for (int x : small) s += x; sink += s; }
    const auto t3 = std::chrono::steady_clock::now();

    auto ms = [](auto a, auto b) {
        return std::chrono::duration<double, std::milli>(b - a).count();
    };
    const double once = ms(t2, t3) / 100000.0;
    std::printf("1000 个 int 只遍历一遍       %10.3f ms\n", ms(t0, t1));
    std::printf("同样的遍历做 10 万遍         %10.3f ms（折算一遍 %.6f ms）\n",
                ms(t2, t3), once);
    std::printf("（sink=%lld）\n", static_cast<long long>(sink));
    return 0;
}
```

`实测数据`
`Text`

```text
同样的遍历做 10 万遍                     9.933 ms（折算一遍 0.000099 ms）
```

**小规模那一行不能单独作为耗时证据**：一千个 `int` 只遍历一遍，
本机几次运行分别落在 0.000 与 0.001 ms 上——这个量级已经贴着时钟分辨率，
读数会随运行漂移。**能站住的数字是「做 10 万遍共 9.933 ms」**，
折算下来一遍约 0.000099 ms。

> [!TIP]
> **测小规模的正确做法是反过来定轮数**：先定一个总工作量（例如总共访问十亿个元素），
> 再让轮数等于总量除以规模。本板块后面测「每元素纳秒数」时用的就是这个办法，
> 从一千个元素到一千万个元素都用同一套基准，数据才可比。

## 3.4 先问访问模式，再谈结构

走到这里，选结构的判据可以写成一句话：**先数一数每种操作各做多少次。**
做得多、又做得慢的那个操作，决定了该选什么形状。

| 你的代码里最主要的是什么 | 先考虑 | 理由 |
|---|---|---|
| 按下标随机访问、末尾追加 | `std::vector` | 连续内存，随机访问 `O(1)`，遍历最快 |
| 遍历一遍做统计 | `std::vector` | 缓存友好，比链式快一个量级 |
| 在已知位置频繁插入删除 | `std::list` | `O(1)` 改指针，元素不搬 |
| 按键查、还要有序与范围 | `std::map` / `std::set` | 有序，`O(log n)`，能取前驱后继 |
| 按键查、只求平均最快 | `std::unordered_map` | 平均 `O(1)` |
| 只在一端进出 | `std::stack` / `std::queue` | 语义清楚，别人一眼看懂 |
| 每次取最小 | `std::priority_queue` | 只维护「最小在上面」 |
| 数据大到内存装不下 | 多路树（`A-08`） | 一次读一页，把树压矮 |

**这张表只是入口，不是答案。** 每一章都会给出该结构更细的判据与代价，
末尾的 `END-怎么选容器与结构` 会把它们合成一张可按需求查的表。

# 第 4 节 与相邻板块的边界

数据结构不是孤立的一门东西，它夹在语言机制与底层硬件之间。
说清楚边界，读的时候才知道哪一层该找谁。

## 4.1 算法只是解法

**本板块解决的是「数据怎么摆」，算法解决的是「事情怎么做」，两者常常一起出现，但不是同一件事。**
同一个「找最小的 k 个数」，换一种摆法就换一种做法，能写出好几种组合；
反过来，同一个做法在不同摆法上代价也不同。

本教材把算法部分放在 `08-一些散落的算法`（尚未编写），
那里放的内容是：递归总结、查找与排序的策略、分治、贪心与动态规划、
字符串匹配、扫描与状态机、随机与采样。

> [!IMPORTANT]
> **算法部分的细节在 `【待补：08-一些散落的算法/】`，尚未编写，不影响读本板块。**
> 结构与用它的算法是强关联的——`splice`、`lower_bound`、堆的上浮下沉
> 这些操作本身就是结构接口的一部分，**它们留在本板块，与结构一起讲**；
> 而排序策略、分治、动态规划这类跨结构通用的解法，归 `08`。

# 术语表

| 术语 | 含义 |
|---|---|
| **连续存储** | 所有元素挤在一块内存里，按固定偏移排列；第 `i` 个元素的地址可以直接算出来 |
| **链式存储** | 每个元素单独占一块内存，块内存着相邻元素的位置，靠指针串起来 |
| **索引存储** | 数据之外另存一张表，表里记着去哪里找；表的组织方式决定查找快慢 |
| **节点** | 链式存储里「一块内存」的称呼，通常包含数据与一个或两个指针 |
| **哨兵节点** | 不存数据、只用来简化边界判断的节点；双向链表常有一个 |
| **随机访问** | 能用下标直接跳到第 `i` 个元素，代价与 `i` 无关 |
| **摊还代价** | 单次操作偶尔很贵（例如扩容），把这一次的代价分摊到很多次操作上算出来的平均值 |
| **迭代器** | 容器与算法之间的接口：算法只认迭代器，不认容器 |
| **失效** | 容器的结构变化之后，原来拿到的迭代器、指针或引用不再可用 |
| **负载因子** | 哈希表里「已存元素数 ÷ 桶数」，超过阈值就要加桶并重新分布 |
| **退化** | 结构失去原有的性质，例如有序插入让搜索树变成一条链，查找从 `O(log n)` 掉到 `O(n)` |
| **`O(...)`** | 复杂度记号，表示代价随规模增长的量级，不表示具体快慢 |

## A.1 两个计数探针

「优化器会不会把没人读的容器删掉」这件事，用两份探针各测一次：
一份数分配次数（精确、可复现），一份看耗时（看有没有系统性差异）。

`C++`

```cpp
/* elide_container.cpp
 * 编译：g++ -std=c++17 -O2 elide_container.cpp -o elide_container
 * 哪些「没人读」的容器会被优化器整段删掉：逐个变体试 */
#include <cstdio>
#include <cstdlib>
#include <forward_list>
#include <list>
#include <new>
#include <vector>

static long long g_calls = 0;
static long long g_bytes = 0;

void* operator new(std::size_t n) {
    ++g_calls;
    g_bytes += static_cast<long long>(n);
    void* p = std::malloc(n ? n : 1);
    if (!p) throw std::bad_alloc();
    return p;
}
void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }

static void reset() { g_calls = 0; g_bytes = 0; }
static void report(const char* what) {
    std::printf("  %-46s 分配 %4lld 次，共 %8lld 字节\n", what, g_calls, g_bytes);
}

int main() {
    constexpr int N = 1000;

    reset();
    { std::list<int> c; for (int i = 0; i < N; ++i) c.push_back(i); }
    report("list，没人读");

    reset();
    { std::forward_list<int> c; for (int i = 0; i < N; ++i) c.push_front(i); }
    report("forward_list，没人读");

    reset();
    { std::vector<int> c; for (int i = 0; i < N; ++i) c.push_back(i); }
    report("vector，没人读");

    reset();
    { std::vector<int> c(N, 1); }
    report("vector(N,1)，没人读");

    reset();
    { std::list<int> c; for (int i = 0; i < N; ++i) c.push_back(i);
      std::printf("  %-46s 分配 %4lld 次，共 %8lld 字节（读了 size）\n",
                  "list，读一下 size()", g_calls, g_bytes); }

    reset();
    { std::list<int> c; for (int i = 0; i < N; ++i) c.push_back(i);
      std::printf("  %-46s 分配 %4lld 次，共 %8lld 字节（读了 front）\n",
                  "list，读一下 front()", g_calls, g_bytes); }

    reset();
    { std::list<int> c; for (int i = 0; i < N; ++i) c.push_back(i);
      asm volatile("" : : "r"(&c) : "memory");
      report("list，加 asm 屏障"); }

    reset();
    { std::forward_list<int> c; for (int i = 0; i < N; ++i) c.push_front(i);
      asm volatile("" : : "r"(&c) : "memory");
      report("forward_list，加 asm 屏障"); }
    return 0;
}
```

`实测数据`
`Text`

```text
  list，没人读                               分配 1000 次，共    24000 字节
  forward_list，没人读                       分配 1000 次，共    16000 字节
  vector，没人读                             分配   11 次，共     8188 字节
  vector(N,1)，没人读                        分配    1 次，共     4000 字节
  list，读一下 size()                        分配 1000 次，共    24000 字节（读了 size）
  list，读一下 front()                       分配 1000 次，共    24000 字节（读了 front）
  list，加 asm 屏障                          分配 1000 次，共    24000 字节
  forward_list，加 asm 屏障                  分配 1000 次，共    16000 字节
```

**八种写法在 `-O2` 与 `-O0` 下的输出完全一致。**
优化器没有删掉容器——原因是这些程序替换了全局 `operator new`，
它是一个可替换函数，编译器不能假设调用它没有副作用。

`C++`

```cpp
/* elide_time.cpp
 * 编译：g++ -std=c++17 -O2 elide_time.cpp -o elide_time
 * 「没人读的容器」是否会被删掉：用默认 operator new，改从耗时上看 */
#include <chrono>
#include <cstdio>
#include <list>
#include <vector>

template <class C>
static void clobber(C& c) {
    asm volatile("" : : "r"(&c) : "memory");
}

static double ms(std::chrono::steady_clock::time_point a,
                 std::chrono::steady_clock::time_point b) {
    return std::chrono::duration<double, std::milli>(b - a).count();
}

int main() {
    const auto t0 = std::chrono::steady_clock::now();
    { std::vector<int> v(100000000, 1); }
    const auto t1 = std::chrono::steady_clock::now();

    const auto t2 = std::chrono::steady_clock::now();
    { std::vector<int> v(100000000, 1); clobber(v); }
    const auto t3 = std::chrono::steady_clock::now();

    const auto t4 = std::chrono::steady_clock::now();
    { std::list<int> l(1000000, 1); }
    const auto t5 = std::chrono::steady_clock::now();

    const auto t6 = std::chrono::steady_clock::now();
    { std::list<int> l(1000000, 1); clobber(l); }
    const auto t7 = std::chrono::steady_clock::now();

    std::printf("一亿个 int 的 vector，没人读：   %10.3f ms\n", ms(t0, t1));
    std::printf("同样一段代码，加 asm 屏障：      %10.3f ms\n", ms(t2, t3));
    std::printf("100 万个节点的 list，没人读：    %10.3f ms\n", ms(t4, t5));
    std::printf("同样一段代码，加 asm 屏障：      %10.3f ms\n", ms(t6, t7));
    return 0;
}
```

`实测数据`
`Text`

```text

同样一段代码，加 asm 屏障：         102.657 ms
100 万个节点的 list，没人读：        51.903 ms
同样一段代码，加 asm 屏障：          54.751 ms
```

`实测数据`
`Text`

```text
一亿个 int 的 vector，没人读：       89.224 ms
同样一段代码，加 asm 屏障：          82.157 ms
100 万个节点的 list，没人读：        41.830 ms
同样一段代码，加 asm 屏障：          40.345 ms
```

**两组数字交错，看不出「不加屏障就更快」的系统性差异。**
真正会被删掉的是**没人读的计算结果**（第 3.3 小节纪律一里那个 0.000 ms），
而不是分配本身。这两份探针的结论只在本机这套编译器与优化级别上成立。

**计时数字每次重跑都会浮动。** 同一份 `four_ways.cpp` 连跑三次，
线性查找在 9275 到 11463 ms 之间，`std::map::find` 在 54.703 到 62.670 ms 之间，
`std::unordered_map::find` 在 3.492 到 4.816 ms 之间；
`elide_time.cpp` 连跑三次，四行分别落在 82.4 到 104.8 ms、82.2 到 105.0 ms、
41.8 到 69.8 ms、40.3 到 57.5 ms 之间。
**结论（相差三个数量级、加不加屏障看不出系统差异）不受影响，逐位数字不必对齐。**
