# 高阶数据结构

**一个结构之所以存在，是因为有一类问题非它不可。**

按下标随机访问要快，于是有了连续存储；在已知位置频繁插入和删除，于是有了链式存储；
按键查得快、还要能按范围取，于是有了搜索树；只求查得快、不在乎顺序，于是有了哈希表；
数据大到内存装不下、一次只能读一页，于是有了多路树。

树与图也一样。它们不是「更高级」的东西，而是两个具体需求的形状：
**树是「数据之间有层次」这件事的形状，图是「数据之间有任意关系」这件事的形状。**
先有需求，再有模型；模型定下来，接口才有得谈；接口定下来，实现才有得写；
写完还要回头量一次代价，看这个模型到底值不值。

> [!IMPORTANT]
> **本板块的目标是讲清楚为什么。** 每个结构都从「它要解决什么问题」推出来，
> 推进路线固定为 **需求 → 模型 → 接口 → 实现 → 代价**：
> 从一行朴素代码的痛点起步，走到一个能用的模型，再把模型写成接口与实现，
> 最后用实测数据说明它赢在哪、输在哪。**不讲「高大上」，只讲取舍。**

## 一、本板块覆盖的核心问题

按「要解决的问题」排，不按结构的名气排。**每一个结构都是从左边这一列推出来的。**

| 要解决的问题 | 引出的模型 | 在哪一章 |
|---|---|---|
| 按下标随机访问要 O(1)，元素个数运行时才知道 | 连续存储：`array`、`vector` | `A-01` |
| 在已知位置频繁插入删除，元素不能搬来搬去 | 链式存储：`list`、`forward_list` | `A-02` |
| 既要按键有序，又要按范围取、取前驱后继 | 平衡搜索树：`map`、`set` | `A-03`、`A-07` |
| 只按键查，不在乎顺序，只求平均最快 | 哈希表：`unordered_map`、`unordered_set` | `A-04` |
| 只在一端进出，或每次都取当前最小的 | `stack`、`queue`、堆与 `priority_queue` | `A-05` |
| 容器要能交给通用算法用，还不损失效率 | 迭代器与范围 | `A-06` |
| 朴素搜索树会退化成链表，查询从 O(log n) 掉到 O(n) | 平衡：旋转与不变式 | `A-07` |
| 数据在磁盘上，一次读一页，二叉树太深 | 多路树：B 树与 B+ 树 | `A-08` |
| 按前缀找、按前缀统计 | trie 与它的变体 | `A-09` |
| 关系本身要存下来（谁连着谁、怎么走） | 图的两种存法 | `A-10` |
| 反复问区间和、反复做区间加 | 前缀和、差分、稀疏表 | `A-11` |
| 反复合并集合、反复判连通 | 不相交集合：并查集 | `A-12` |
| 容器的内存从哪来、谁在分配 | 分配器 | `A-13` |

**这张表里没有「红黑树」「B+ 树」这样的起点。** 它们都出现在右边两列，
左边那一列才是起点——先有问题，再有结构。

## 七、本板块的约定

- **结论必标依据**：`` `实测数据` ``（本机真跑，输出可复现）、`` `文档` ``（引标准草案或官方资料并给章节号）、`` `待确认` ``（合理推断但未验证）；随环境而变的写明**存疑**。
- **数据一律来自实测**：本书的数据在本机跑出来，环境是 Windows 11 + g++ 15.2.0（MinGW-w64），编译命令写在每个程序的首行注释里。**换一套标准库，数字会变**——涉及实现差异的地方会给出两套标准库的对照。
- **代码块上方标语言**（`` `C++` `` / `` `C` `` / `` `Text` `` / `` `Bash` `` / `` `Mermaid` ``）；凡出现代码的块，要么是完整单文件，要么明确标「（下面是节选）」。
- **不写本机路径**，用 `<MinGW>`、`<工作区>` 这类占位符。
- **每个结构都留一句「什么时候别用它」**：讲一个结构的长处时，同一节里要交代它的短处，否则读者会拿它去套所有场合。
