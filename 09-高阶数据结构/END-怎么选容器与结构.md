整个板块讲了十几章结构，每一章都从「要解决什么问题」开始。
到了收口的地方，问题反过来问：**手上有一个需求，该用哪一个。**
这一章给一张按需求反查的表、三类常见的误选、以及两条边界——
**什么时候值得自己写，什么时候不要自己写。**

选结构这件事有一个容易忽略的前提：**需求里最常做的那件事，
决定了该用哪个结构**，而不是「哪个结构更高级」。
`A-10` 实测过同一张图问两种问题的差距：稀疏图上邻接表取邻居比邻接矩阵快 1197 倍，
而矩阵查一条边只要 9 到 11 纳秒——**同一个图，问法不同，答案就不同。**

本章的数字全部来自 `A` 段并注明出处，不新造实测数据。

# 第 1 节 按需求反查的表

## 1.1 先问三个问题

| 问题 | 为什么先问它 |
|---|---|
| **最常做的是哪件事**：按位置取、按值找、按顺序取、还是取最值 | 它决定结构的形状（连续、哈希、有序、堆） |
| **数据会不会变**：只读、只加不改、随时增删 | 「会变」会让一部分结构直接出局（见 `A-11` 第 1.1 小节） |
| **规模有多大** | 小规模时复杂度差异可以忽略，常数与内存才是主要开销 |

## 1.2 表

| 你要什么 | 用哪个 | 代价在哪 | 出处 |
|---|---|---|---|
| 按下标随机访问 | `vector`／`array` | 中间插入要搬移 | 《09-高阶数据结构/A-01-连续存储：array 与 vector.md》第 2、3 节 |
| 频繁在两端进出 | `deque` | 中间插入比 `vector` 贵 | 《09-高阶数据结构/A-02-链式存储：list 与 forward_list.md》第 5.2 小节 |
| 频繁在中间插入删除，且位置已拿到 | `list` | 每元素 24 字节、遍历慢 | 《09-高阶数据结构/A-02-链式存储：list 与 forward_list.md》第 5 节 |
| 按值快速查找、不需要有序 | `unordered_map`／`unordered_set` | 哈希质量决定一切 | 《09-高阶数据结构/A-04-按哈希定位：unordered_map.md》第 5.3 小节 |
| 按值查找且需要有序（范围、前后继） | `map`／`set` | 每元素 40 字节、常数更大 | 《09-高阶数据结构/A-03-索引存储：map、set 与有序.md》第 5 节 |
| 反复取最大／最小 | `priority_queue` | 只能看堆顶，不能按序遍历 | 《09-高阶数据结构/A-05-后进先出、先进先出与优先级：stack、queue 与堆.md》第 4 节 |
| 后进先出／先进先出 | `stack`／`queue` | 取决于底层容器 | 《09-高阶数据结构/A-05-后进先出、先进先出与优先级：stack、queue 与堆.md》第 2、3 节 |
| 按键的前缀找 | trie | 每字符一个节点，内存换速度 | 《09-高阶数据结构/A-09-树（三）：按前缀找——trie 与它的变体.md》第 4 节 |
| 数据在磁盘上、要少读几趟 | B+ 树 | 实现复杂，节点要按页对齐 | 《09-高阶数据结构/A-08-树（二）：数据在磁盘上——B 树与 B+ 树.md》第 3 节 |
| 反复问同一个区间 | 前缀和／稀疏表／差分 | 建表成本有回本点 | 《09-高阶数据结构/A-11-区间查询：前缀和、差分与稀疏表.md》第 5.2 小节 |
| 只问连通性、边会并不会删 | 并查集 | 不能删边、不能给路径 | 《09-高阶数据结构/A-12-不相交集合：只要连通性.md》第 5 节 |
| 要遍历邻居 | 邻接表 | 查边要扫一个数组 | 《09-高阶数据结构/A-10-图：关系怎么存.md》第 5.2 小节 |
| 要反复判断两点是否相连 | 邻接矩阵 | 内存是 `V²`，遍历邻居是 `O(V)` | 《09-高阶数据结构/A-10-图：关系怎么存.md》第 5.3 小节 |

> [!IMPORTANT]
> **表的读法是「从需求那一列往下找」，不是「从结构那一列往上挑」。**
> 结构只有配上需求才有优劣：`list` 在「位置已知的中间插入」上是常数时间，
> 在「按位置取第 n 个」上是 `O(n)`——同一份实测数据，换个问法结论就反过来。

## 1.3 几条容易记混的对照

| 对照 | 结论 | 出处 |
|---|---|---|
| `vector` 与 `deque` 在头部插入 | `deque` 是 `O(1)`，`vector` 要整体搬移（实测差三个数量级） | 《09-高阶数据结构/A-02-链式存储：list 与 forward_list.md》第 5.2 小节 |
| `map` 与 `unordered_map` | 有序换哈希：`map` 保序、`unordered_map` 更快但无序 | 《09-高阶数据结构/A-04-按哈希定位：unordered_map.md》第 5.3 小节 |
| `list` 与 `vector` 的遍历 | 连续存储快得多（实测差约 30 倍） | 《09-高阶数据结构/A-02-链式存储：list 与 forward_list.md》第 5.4 小节 |
| 堆与「每次维持有序」 | 堆快几十倍；与「收齐再排一次」同一档 | 《09-高阶数据结构/A-05-后进先出、先进先出与优先级：stack、queue 与堆.md》第 5.1 小节 |
| 前缀和与每次现算 | 查询快一个数量级，但回本点在一千到一万次之间 | 《09-高阶数据结构/A-11-区间查询：前缀和、差分与稀疏表.md》第 5.2 小节 |

# 第 2 节 三类常见误选

## 2.1 用链表当默认容器

**症状**：`list` 用得很顺，但程序越来越慢。

`A-02` 实测过：每元素堆字节 `list` 24、`vector` 4；
遍历一百万个元素 `list` 38.86 毫秒、`vector` 1.30 毫秒。
**链表只在「位置已拿到且频繁在中间增删」时赢**，
而多数程序里最常做的却是遍历与按下标访问。

| 改法 | 说明 |
|---|---|
| 先换成 `vector` 量一遍 | 多数场合直接变快，且内存降下来 |
| 真的需要中间插入 | 先问「位置是不是已经拿到」；要先找位置的话，链表不省查找 |
| 需要迭代器稳定 | 那是 `list` 的正当理由（`A-02` 第 4 节） |

## 2.2 用有序容器做只需要查找的事

**症状**：用 `map` 只为了「按键找值」，从来不做范围查询、不按序遍历。

`A-03` 实测过每元素 40 字节、`map<int,int>` 对象本身 48 字节；
`A-04` 的 `unordered_map` 每元素 34 到 43 字节但常数更小。
**只要不需要「有序」带来的能力（范围、前后继、按序输出），
哈希表通常是更好的默认选择**——前提是哈希函数合格。

## 2.3 建了索引却不用

**症状**：为了「查得快」建了哈希表，但每次查询之前先遍历一遍原数组。

**这类错误的共同点是把「结构」当成目的**：
结构只有在被**反复使用**时才回本。
`A-11` 的回本点实测就是这个道理——查询次数少于一千次时，
从头算反而更快。

| 判据 | 做法 |
|---|---|
| 这个结构会被用多少次 | 少于回本点就别建 |
| 每次用它省下多少 | 省的是 `O(n)` 还是 `O(log n)` |
| 建它的代价 | 建表时间 + 内存 |

> [!WARNING]
> **「先建个索引」不是无条件的优化。**
> 建表要时间、要内存，而且**只在反复使用时才回本**。
> 判据只有一句话：**把建表成本除以每次省下的时间，看够不够查那么多次。**

# 第 3 节 什么时候自己写

| 情况 | 说明 |
|---|---|
| 标准容器缺一个操作 | 例如「按值快速删除 + 保序」这种组合 |
| 有特殊的分配需求 | 内存池、共享内存、固定地址（`A-13` 会讲分配器） |
| 需要把结构放到特殊内存 | 内存映射文件、嵌入式设备的固定缓冲区 |
| 要把某个结构当教学或调试工具 | 画出来看它怎么长——这也是 `B` 段的目的 |
| 需要在结构里附带额外信息 | 例如每个节点带一个时间戳 |

**自己写之前先确认三件事**：

1. **标准容器真的做不到吗**（多数「做不到」用组合就能解决）；
2. **测试怎么写**（随机测 + 不变式校验，见 `B-04` 第 5 节）；
3. **异常安全与所有权怎么处理**（`B-01` 第 4 节、`B-02` 第 3 节）。

# 第 4 节 什么时候不要自己写

| 情况 | 为什么 |
|---|---|
| 标准容器已经满足需求 | 它们被无数程序磨过，边界情况处理得比手写周全 |
| 只是「想试试」 | 先在沙盘里试，不要放进生产代码 |
| 团队里没人维护得了 | 自己写的结构是一份长期负债 |
| 需要的是性能而结构没换 | 先测再改，《09-高阶数据结构/A-00-导读：数据结构是问题的形状.md》第 3.3 小节给过纪律 |

> [!CAUTION]
> **手写容器最容易出错的三处**（`B` 段各章都给了清单）：
> **异常安全**（搬到一半抛了怎么办）、**所有权**（谁负责释放）、
> **迭代器失效**（哪些操作让哪些迭代器作废）。
> 这三处在标准容器里已经被处理好了，自己写就要自己担。

# 第 5 节 一条收口的原则

整个板块反复出现同一个句式：**需求决定形状**。

| 需求里的那句话 | 推出什么形状 |
|---|---|
| 「按编号取第几个」 | 连续存储 |
| 「插到中间」 | 链式存储，或留空隙 |
| 「按值找」 | 哈希 |
| 「按大小顺序取」 | 有序树 |
| 「总是要最大的」 | 堆 |
| 「反复问同一个区间」 | 预先算好一部分结果 |
| 「只问通不通」 | 丢掉路径，只留连通性 |

**结构不是目标，它是需求压出来的形状。**
判断一个结构合不合适，只需要问两句：
**它最擅长回答哪个问题，而我的程序最常问的是不是那个问题。**

> [!NOTE]
> 这一章收成三句话：
> **按需求反查，不要按「哪个高级」挑；
> 三类常见误选（拿链表当默认、拿有序容器做纯查找、建了索引不用）
> 的共同点是「结构没配上需求」；
> 自己写只在标准容器真的做不到、或有特殊分配需求时才值得，
> 而手写要担起异常安全、所有权、迭代器失效这三件事。**

# 术语表

| 术语 | 含义 |
|---|---|
| **随机访问** | 按下标直接取，`O(1)` |
| **摊还** | 把偶发的高代价分摊到多次操作上平均计算 |
| **回本点** | 建结构的成本被后续操作省下的时间追平所需的次数 |
| **负载因子** | 哈希表里 `size / bucket_count` |
| **不变式** | 结构必须始终成立的性质；手写时用它做校验 |
| **异常安全** | 抛异常之后容器仍然可用、内容可预期 |
