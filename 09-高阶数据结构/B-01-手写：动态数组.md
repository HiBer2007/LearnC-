# 第 1 节 三指针布局与不变式

`A-01` 测过：`sizeof(std::vector<int>)` 是 24 字节，即三个指针。

`C++`

（下面是节选：只给数据成员与不变式，完整类见配套实例）

```cpp
template <class T>
class Vector {
    T* begin_ = nullptr;        // 元素区起点
    T* end_   = nullptr;        // 元素区终点（size 的位置）
    T* cap_   = nullptr;        // 缓冲区终点（capacity 的位置）
public:
    std::size_t size() const { return static_cast<std::size_t>(end_ - begin_); }
    std::size_t capacity() const { return static_cast<std::size_t>(cap_ - begin_); }
};
```

**必须始终成立的三条不变式**：

| 不变式 | 破了会怎样 |
|---|---|
| `begin_ <= end_ <= cap_` | 指针运算失去意义，`size()` 算出负数 |
| `[begin_, end_)` 里全是活对象 | 析构时会漏掉或多析构 |
| `[end_, cap_)` 是未构造的原始内存 | 对它做 `delete` 或赋值是未定义行为 |

**第三条最容易被忽略**：缓冲区里的元素与缓冲区本身是两回事。
缓冲区是一块原始内存（`operator new` 或分配器给的），
元素是在这块内存上构造出来的对象。
**分配与构造分开，是手写容器的第一课。**

# 第 2 节 增长策略

## 2.1 为什么不能每次只加一个

每次插入都只多要一格，就要每次扩容、每次搬走全部元素：
`n` 次插入是 `O(n²)`。**成倍增长把这个代价摊平到 `O(1)`**：
扩容次数是 `log n` 量级，搬移总量是 `2n` 量级。

## 2.2 几倍：1.5 还是 2

`实测数据`
`Text`

```text
libstdc++：25 次扩容，共搬走 16777215 个元素，末尾余量 40.4%
MSVC     ：41 次扩容，共搬走 23917332 个元素，末尾余量 16.4%
```

（数字与程序见《09-高阶数据结构/A-01-连续存储：array 与 vector.md》第 3.2 小节。）

| 倍数 | 扩容次数 | 搬移总量 | 末尾余量 | 内存能重用吗 |
|---|---|---|---|---|
| 2 | 少 | 约 `2n` | **最多 50%** | **通常不能**：新块总是比「已释放的块加起来」大 |
| 1.5 | 略多 | 约 `3n` | 约 33% | **通常能**：释放的块加起来够放下新块 |

**选 1.5 的理由是内存重用**：按 2 倍增长时，新块的大小永远大于
此前释放的所有块之和，因此那块内存还回去也没人能接着用；
按 1.5 倍增长时，攒几次释放的块就能拼出新块要的大小。
**选 2 的理由是算术简单**（乘 2 就是左移），而且搬移次数更少。

> [!IMPORTANT]
> **倍数没有唯一正确答案，但有一条硬底线：必须大于 1 且成倍。**
> 小于 1.5 会让搬移总量涨得很快（1.1 倍时约 `11n`），
> 等于 1 就是每插一次搬一次。**先定一个常数，再在注释里写明为什么选它。**

## 2.3 扩容时不要忘记的三件事

1. **先要新内存，成功了再搬**——顺序反了会在失败时丢掉原数据；
2. **搬的是元素，不是字节**（除非元素可以按字节搬，见第 3 节）；
3. **搬完要销毁旧元素、释放旧缓冲区**，而不是 `delete[]` 旧指针（见第 7 节）。

# 第 3 节 搬迁：拷贝还是移动

扩容要把旧元素搬到新缓冲区。**用移动构造还是拷贝构造，取决于元素类型**。

`C++`

（下面是节选：搬迁的核心判断）

```cpp
// 只有当移动构造不抛异常时，才敢用移动——理由见第 4 节
if constexpr (std::is_nothrow_move_constructible_v<T>) {
    for (T& x : old_range) new (dst++) T(std::move(x));   // 移动
} else {
    for (const T& x : old_range) new (dst++) T(x);        // 退回复制
}
```

| 元素的移动构造 | 搬迁方式 | 结果 |
|---|---|---|
| `noexcept` | 移动 | 快，且旧元素处于「有效但未指定」的状态 |
| 可能抛异常 | **退回复制** | 慢，但旧元素保持原样 |

`A-01` 测过这一条的实际影响：给一个「移动构造会抛」的类型，
`vector` 会退回拷贝，扩容耗时应声上涨。

> [!WARNING]
> **给自定义类型写移动构造时，记得标 `noexcept`。**
> 不标不等于会抛，但标准库与手写容器都会**当成会抛**处理，
> 于是悄悄退回复制——性能掉了，编译器一句提示都没有。

# 第 4 节 异常安全

## 4.1 问题长什么样

扩容搬到第 7 个元素时，第 7 个元素的拷贝构造抛了异常。此时：

- 新缓冲区里有 6 个构造好的元素；
- 旧缓冲区里的元素**一个都没动**（如果用的是拷贝）；
- 旧缓冲区还在，还没释放。

**必须做到「异常抛出去之后，容器仍然可用，且内容与操作前一致」。**
这就是强异常安全保证。

## 4.2 怎么做到

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 1 | 先分配新缓冲区 | 失败时容器原封不动 |
| 2 | 搬元素（拷贝，或 `noexcept` 的移动） | 抛了就把新缓冲区里已构造的析构掉、释放内存 |
| 3 | **全部搬完之后**才改三个指针 | 指针一改，旧数据就找不回来了 |
| 4 | 销毁旧元素、释放旧缓冲区 | 这一步不能再抛 |

`C++`

（下面是节选：异常安全的骨架）

```cpp
T* fresh = alloc_.allocate(new_cap);          // 1. 可能抛 bad_alloc，此时什么都没变
std::size_t built = 0;
try {
    for (; built < size(); ++built)           // 2. 可能抛
        new (fresh + built) T(std::move_if_noexcept(begin_[built]));
} catch (...) {
    for (std::size_t i = 0; i < built; ++i) fresh[i].~T();   // 把已构造的收拾掉
    alloc_.deallocate(fresh, new_cap);
    throw;                                     // 容器状态与操作前一致
}
for (std::size_t i = 0; i < size(); ++i) begin_[i].~T();
alloc_.deallocate(begin_, capacity());         // 3、4. 到这里才动自己的指针
begin_ = fresh; end_ = fresh + built; cap_ = fresh + new_cap;
```

> [!CAUTION]
> **用移动搬迁时，「异常安全」与「性能」是冲突的。**
> 移动搬到一半抛异常，旧元素已经被搬空了，**强保证做不到了**——
> 这正是第 3 节那条规则（不抛才敢移动）的来路。
> 想同时要两者，只能让移动构造保证不抛。

# 第 5 节 `reserve` 与 `shrink_to_fit`

| 接口 | 做什么 | 承诺 |
|---|---|---|
| `reserve(n)` | 把容量至少提到 `n` | **只增不减**；`n` 小于当前容量时什么都不做 |
| `shrink_to_fit()` | 请求把容量降到 `size()` | **非强制**：实现可以不理它 |
| `resize(n)` | 改变元素个数（多出来的默认构造） | 会真的构造或析构元素 |
| `clear()` | 元素个数归零 | **不释放内存** |

**`shrink_to_fit` 是请求，不是命令**——标准给的是「可以」而不是「必须」。
自己写的时候也一样：写成请求语义，调用方才不会依赖它一定成功。

> [!TIP]
> **知道规模时先 `reserve`**：省掉十几次「要新内存 + 搬走全部元素」。
> `A-01` 用替换 `operator new` 的办法数过这件事：
> 预留之后分配次数从十几次降到一次。

# 第 6 节 迭代器失效从哪来

`A-06` 给过一张总表，这里只讲**手写时该怎么想**：

| 操作 | 失效范围 | 手写时的对应动作 |
|---|---|---|
| 扩容 | **全部** | 三个指针全变了，任何旧迭代器都作废 |
| 插入（不扩容） | 插入点**之后** | 后面的元素整体后移了 |
| 删除 | 删除点**及之后** | 后面的元素整体前移了 |
| 只读 | 不失效 | —— |

**手写时最容易漏的是「插入点之后」**：不扩容时元素没有搬家，
但插入点之后的元素位置全变了。返回新迭代器（`insert` 的标准做法）
就是为了让调用方拿到有效的位置。

> [!WARNING]
> **`reserve` 之后再插入，并不能保证迭代器不失效**——
> 它只是保证不扩容；在中间插入仍然会让后面的迭代器失效。

# 第 7 节 最小分配器接口要点

手写容器不必直接用 `new`／`delete`，而是走分配器，
这样才能让调用方换成内存池或统计器（`A-13` 会完整讲）。

| 接口 | 做什么 | 要点 |
|---|---|---|
| `allocate(n)` | 要 `n` 个元素的原始内存 | **只给内存，不构造对象** |
| `deallocate(p, n)` | 还内存 | **`n` 必须等于当初 `allocate` 的值** |
| `construct(p, args...)` | 在 `p` 上构造 | C++17 起由 `allocator_traits` 代劳 |
| `destroy(p)` | 析构 | 同上 |

**三条容易写错的地方**：

1. **原始内存不是数组**：用 `alloc_.allocate(n)` 拿到的内存，
   要用 `alloc_.deallocate(p, n)` 还，**不能配 `delete[]`**；
2. **构造与析构要配对**：分配器只给内存，元素的生命周期由容器自己管；
3. **`deallocate` 的 `n` 不能省**：有些分配器要靠它判断该还给哪个空闲链表
   （`A-13` 会给一个「忽略 `n` 就出错」的例子）。

# 第 8 节 常见陷阱清单

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| 扩容倍数写成 1.1 | 搬移总量涨到约 `11n` | 取 1.5 或 2，并写明理由 |
| 移动构造不标 `noexcept` | 悄悄退回复制 | 不抛就标上 |
| 先改指针再搬元素 | 抛异常后数据全丢 | 全部搬完再改指针 |
| 用 `delete[]` 释放分配器的内存 | 未定义行为 | 用 `deallocate` |
| 忘了析构旧元素 | 泄漏资源（文件、锁、内存） | 搬完逐个析构 |
| 插入后继续用旧迭代器 | 读到错位的数据 | 用返回的新迭代器 |
| `clear()` 以为会释放内存 | 内存一直占着 | 要释放就 `shrink_to_fit` 或交换 |
| 认为 `shrink_to_fit` 一定成功 | 依赖了非强制的行为 | 当成请求 |

> [!NOTE]
> 这一章收成三句话：
> **手写动态数组的第一课是「分配与构造分开」——缓冲区是原始内存，元素是构造出来的对象；
> 第二课是增长倍数（1.5 换内存重用、2 换搬移次数），它决定摊还代价；
> 第三课是异常安全：先把新东西备齐、再动自己的指针，中间抛了就把新东西收拾干净。**

# 术语表

| 术语 | 含义 |
|---|---|
| **容量** | 缓冲区能装多少个元素 |
| **摊还** | 把偶发的高代价分摊到多次操作上平均计算 |
| **搬迁** | 扩容时把元素从旧缓冲区搬到新缓冲区 |
| **原始内存** | 只分配、未构造对象的一块内存 |
| **强异常安全** | 抛异常后容器状态与操作前完全一致 |
| **`noexcept` 移动** | 承诺不抛异常的移动构造；容器据此决定是否敢移动 |
| **分配器** | 把「要内存」与「构造对象」分开的接口 |
