同一份数据换个哈希函数，查找从 1.571 毫秒变成 21807.775 毫秒。
自己写一个哈希表，难处就在那条结论背后的三个决定：
**桶里怎么放冲突的元素**、**什么时候加桶**、**删除怎么处理**。
再加一条与哈希函数本身有关的要求——它必须与判等谓词一致。

# 第 1 节 两半结构

`A-04` 的实测给过桶数的增长：1 → 13 → 29 → 59 → 127 → …，
负载因子始终维持在 0.5 上下，一百万个键最后有 351061 个桶。

`Text`

```text
   ┌────────┬────────┬────────┬────────┬────────┐
   │ 桶 0   │ 桶 1   │ 桶 2   │ 桶 3   │ 桶 4   │   桶数组：一段连续内存
   └───┬────┴────────┴───┬────┴────────┴───┬────┘
       │                 │                 │
       ▼                 ▼                 ▼
   ┌────────┐        ┌────────┐        ┌────────┐   ┌────────┐
   │ 键 16  │        │ 键  9  │        │ 键  2  │──►│ 键 42  │   桶里：一条链
   └────────┘        └────────┘        └────────┘   └────────┘
```

| 两半 | 由谁决定 | 写的时候注意 |
|---|---|---|
| 桶数组 | 桶数 | 是一段连续内存，扩容就是 `B-01` 那套搬迁 |
| 桶里的东西 | 冲突处理方式 | 链地址法是一条链，开放寻址是「往后找空位」 |

**查找三步**：算哈希 → 对桶数取余得桶号 → 在桶里找。
前两步是常数，第三步的代价取决于桶里有多少元素。

# 第 2 节 链地址法与开放寻址

| | 链地址法 | 开放寻址 |
|---|---|---|
| 冲突了怎么办 | 挂到同一个桶的链上 | **按探测序列找下一个空位** |
| 每个元素的开销 | 一个节点（指针 + 元素） | **没有额外开销**，都放在桶数组里 |
| 负载因子能到多少 | 可以超过 1 | **必须小于 1**，通常压在 0.7 以下 |
| 删除 | 直接摘掉链上的节点 | **不能直接删**，要留墓碑（见第 6 节） |
| 缓存友好度 | 差（节点散落） | 好（都在数组里） |
| 迭代器稳定性 | 节点不搬家，稳定 | 元素在数组里，扩容就全失效 |

**怎么选**：

| 情形 | 选择 |
|---|---|
| 元素较大、或需要稳定的引用 | 链地址法 |
| 元素小（`int`、指针）、追求速度与省内存 | 开放寻址 |
| 删除很频繁 | 链地址法（开放寻址的墓碑会越积越多） |
| 要按桶遍历、或要 `bucket_count()` 这类接口 | 链地址法 |

> [!IMPORTANT]
> **两种做法的取舍点只有一个：把「冲突」的代价放在哪里。**
> 链地址法把它放在**额外的节点**上（内存换简单）；
> 开放寻址把它放在**探测**上（时间换内存，且删除变复杂）。

# 第 3 节 桶数与负载因子

## 3.1 三个数

| 名字 | 定义 | `A-04` 实测 |
|---|---|---|
| 桶数 | 有多少个桶 | 一百万个键时 351061 |
| 负载因子 | `size / bucket_count` | 全程维持在 0.49 上下 |
| 最大负载因子 | 允许的上限 | 1.000（本机实现） |

## 3.2 什么时候加桶

**在插入之前判断「插进去会不会超过上限」**，超了就先把桶数翻倍再插。
`A-04` 的实测里，加桶发生在第 1、14、30、60、128、258… 个元素上——
**桶数大致翻倍**，因此一百万个元素只加了十几次桶。

`C++`

（下面是节选：插入时的判断）

```cpp
if (size_ + 1 > static_cast<std::size_t>(bucket_count_ * max_load_factor_))
    rehash(bucket_count_ * 2);          // 先加桶，再插
insert_without_check(key, value);
```

| 做法 | 结果 |
|---|---|
| 插入前判断 | 负载因子始终不超上限，最坏情况可预测 |
| 插入后判断 | 会短暂超限，桶里的链更长 |

**桶数取素数还是 2 的幂**：取 2 的幂时「对桶数取余」可以写成按位与，
速度更快；取素数时分布更均匀。**本机实现走的是素数路线**（13、29、59…），
这也是它每次加桶都要重新算一遍的原因之一。

# 第 4 节 再哈希

再哈希 = **换一个更大的桶数组，把所有元素按新的桶数重新放一遍**。

`C++`

（下面是节选：再哈希的骨架）

```cpp
void rehash(std::size_t new_count) {
    std::vector<Node*> fresh(new_count, nullptr);
    for (Node* head : buckets_) {          // 遍历旧桶
        while (head) {
            Node* next = head->next;       // 先记住，再挪
            const std::size_t idx = hash_(head->key) % new_count;
            head->next = fresh[idx];       // 头插进新桶
            fresh[idx] = head;
            head = next;
        }
    }
    buckets_.swap(fresh);                  // 旧桶数组在这里析构
    bucket_count_ = new_count;
}
```

**注意三件事**：

1. **节点本身不重新分配**，只是换了挂在哪条链上——
   这正是 `A-04` 实测里「再哈希之后指针与引用仍然有效」的原因；
2. **迭代器会失效**（它记的是「哪个桶 + 桶里的位置」，桶变了就作废）；
3. **每个元素都要重算一次哈希**，因此再哈希是 `O(n)`，
   摊到每次插入上是常数——这就是「平均 `O(1)`」里那个「平均」的来路。

> [!TIP]
> **知道要放多少个键时先 `reserve`。** `A-04` 实测过：
> `reserve(200000)` 之后插满二十万个元素，**一次桶都没加**。
> 省下的不是一次搬移，而是十几次「全部元素重算哈希」。

# 第 5 节 哈希函数的要求

## 5.1 两条硬要求

| 要求 | 说明 |
|---|---|
| **与判等一致** | 任何两个被判为相等的键，哈希值必须相同 |
| **分布均匀** | 不同的键要尽量落到不同的桶里 |

违反第一条的后果，`A-04` 演示过：相等谓词只看 `x`、哈希看 `x` 与 `y` 时，
`{1,2}` 与 `{1,3}` 都插了进去，而按谓词它们本该是同一个键。
**这是未定义行为，容器不会检查。**

## 5.2 坏哈希有多坏

`实测数据`
`Text`

```text
N=100000 个键（都是 10 的倍数），100000 次查找
                 默认哈希 只看末四位 全部一个桶
查找（毫秒）        1.571     3966.114      21807.775
  最长的桶长度：默认 1，只看末四位 12500，全部一个桶 100000
```

（数字与程序见《09-高阶数据结构/A-04-按哈希定位：unordered_map.md》第 5.3 小节。）

**同一份数据、同一个容器、同一个查找语句，只换哈希函数，慢了将近一万四千倍。**
写哈希函数时最常犯的两个错都在那组数据里：
**只用键的一部分**（末四位）、**让所有键算出同一个值**。

> [!CAUTION]
> **不要把几个字段简单相加当哈希值。**
> 字段有规律时（例如都是 10 的倍数），相加的结果同样有规律，
> 于是键成串地挤进少数几个桶——实测中这已经足以让查找慢两千多倍。

# 第 6 节 删除

## 6.1 链地址法：摘节点

`C++`

（下面是节选：删一个键）

```cpp
bool erase(const Key& key) {
    const std::size_t idx = hash_(key) % bucket_count_;
    Node** link = &buckets_[idx];          // 指向「指向当前节点的那个指针」
    while (*link) {
        if (equal_((*link)->key, key)) {
            Node* dead = *link;
            *link = dead->next;            // 让前驱跳过它
            destroy_node(dead);
            --size_;
            return true;
        }
        link = &(*link)->next;
    }
    return false;
}
```

**用「指向指针的指针」可以省掉「前驱是不是空」的特判**——
删的是头节点还是中间节点，代码一样。

## 6.2 开放寻址：墓碑

开放寻址里不能把位置直接清空，否则**探测序列会断**：
后面来找同一个键的探测会以为「这里没被占过」，于是提前停下、找不到。

| 标记 | 含义 | 查找时 | 插入时 |
|---|---|---|---|
| 空 | 从来没被占过 | **停下**（后面不可能有） | 可以放这里 |
| 占用 | 有元素 | 比较 | 不能放 |
| **墓碑** | 曾经有、已删除 | **继续往后找** | **可以放这里** |

**墓碑积多了，变慢的不是「找不到的查找」，而是插入。**

`实测数据`

| 同一张表，占用改成墓碑之后 | 探测步数 |
|---|---|
| 查一个不在表里的键 | **678 对 678（完全不变）** |
| 各插 300 个新键（一张留 700 个墓碑、一张清干净） | **765 对 393** |

（数字与程序见《B-examples/09-data-structures/03-hash-mini/》的 README 与 `app_cli` 输出。）

**为什么「找不到」不变**：线性探测本来就要一格一格走过那些位置，
占用变成墓碑，**走过的格数还是那些**——既不会让查找提前停下，也不会让它变长。
**真正变的是插入**：插入要绕过墓碑才能找到空槽，
而且**负载因子把墓碑算在内**，表会更早触发扩容。
因此开放寻址的表要定期**重整**（把墓碑清掉、元素重新排一遍）。

同一个示例还给出一组对照：留墓碑的那张表仍能找到 300 个键，
把删除位置**直接清空**的那张只找到 193 个——**这组对照说明墓碑不能省**。

> [!WARNING]
> **墓碑是开放寻址最容易漏的一环。**
> 直接把删除的位置标成「空」，会让「找得到」变成「找不到」——
> 而且只在删过元素之后才复现，测试里很容易漏掉。

# 第 7 节 常见陷阱清单

配套模板把墓碑的处理拆成两处：**墓碑的判断写在探测循环里**（阶段 1 要写的那一段），
**置墓碑写在删除里**（阶段 3）——**两者是两处代码，不是同一处**。

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| 哈希与判等不一致 | 未定义行为：找得到又找不到 | 两个一起写、一起测 |
| 只用键的一部分算哈希 | 分布退化，慢几千倍 | 让键的每一位都参与 |
| 桶数不涨 | 链越挂越长，退化成链表 | 超过负载因子上限就加桶 |
| 忘了「先加桶再插」 | 短暂超限，最坏情况变差 | 插入前判断 |
| 再哈希时重新分配节点 | 指针与引用失效（本可避免） | 只改链，不搬节点 |
| 开放寻址直接清空删除位 | 探测序列断掉，找不到 | 留墓碑 |
| 墓碑从不重整 | 查找越来越慢 | 到一定比例就重整 |
| 以为 `reserve` 是必须的 | 不预留只是慢，不会错 | 知道规模时预留，性能更好 |

> [!NOTE]
> 这一章收成三句话：
> **哈希表 = 桶数组 + 冲突处理，前者照动态数组写、后者二选一；
> 加桶的时机与哈希函数的质量决定它是 `O(1)` 还是 `O(n)`——
> 实测中换一个坏哈希就慢了一万四千倍；
> 删除是最容易写错的一环：链地址法要摘节点，开放寻址要留墓碑。**

|---|---|
