# 配置步骤 · 05-oop/02-cpp-inheritance（继承与多态）

本模板是**分阶段的整体演练**：成品是一套图形类体系（抽象基类 + 两个派生类 + 工厂），
外加三个驱动——命令行版 `app_cli.exe`、Win32 界面版 `app_gui_win32.exe` 与 Qt 界面版 `app_gui_qt.exe`（默认不构建）。
每个阶段结束时两个程序都能编译、能运行。怎么复制模板、怎么打开、遇到问题查哪里，
见 [`../../README.md`](../../README.md)，本文件不重复。

---

## 成品形态

做完 4 个阶段之后，这套图形类体系具备：

| 能力 | 由哪一阶段提供 |
|---|---|
| 抽象基类 `Shape` 只留接口，`Circle` 与 `Rect` 各自实现面积与周长 | 阶段 1 |
| 同一个 `describe()` 调用点上，不同派生对象打印不同结果（动态绑定） | 阶段 1 |
| 通过基类指针 `delete` 时，派生类与基类的析构函数都按顺序被调用 | 阶段 2 |
| 工厂 `make_shape` 按名字造对象，名字不认识时返回 `nullptr` | 阶段 3 |
| 一组基类指针的遍历与汇总（总面积、逐个描述） | 阶段 3 |
| 运行期判断「这个图形到底是不是圆」，指针版判空、引用版抛 `std::bad_cast` | 阶段 4 |

命令行版按阶段打印验收数据；界面版把同一组对象画在窗口上，横条长度就是面积。

## 阶段 1 · 虚函数：面积与周长

**要做什么**（都在 `src/shape.cpp`）

- 1-1 `Circle::area()`：圆周率 × 半径²
- 1-2 `Circle::perimeter()`：2 × 圆周率 × 半径
- 1-3 `Rect::area()`：宽 × 高
- 1-4 `Rect::perimeter()`：2 ×（宽 + 高）

**验收标准**

`Text`

```text
=== 阶段 1：面积与周长 ===
  circle  面积 = 12.5664，周长 = 12.5664
  rect    面积 = 12.0000，周长 = 14.0000
  只有 Circle 有的操作：半径 = 2
  只有 Rect 有的操作：是正方形吗 = 否
  live = 2
  析构 Rect(3 x 4)
  析构 Shape(rect)
  析构 Circle(半径 2)
  析构 Shape(circle)
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 面积全是 `0.0000` | 虚函数还是占位版本 |
| 圆的面积是 `12.0000` | 用了 3 当圆周率，或者把半径当直径算了 |
| 局部对象析构顺序反了 | 析构顺序与构造顺序相反：`rect` 后构造，先析构 |

实验：把 `Circle::area()` 的签名改成 `double area(int) const`，编译器会立刻报
`error: 'double Circle::area(int) const' marked 'override' but does not override`。
这正是 `override` 的作用——签名写错时不用等到运行期才发现，见《配置步骤》上文引的章节。

## 阶段 2 · 虚析构

**要做什么**

- 2-1 在 `include/shape.hpp` 里给 `~Shape()` 加上 `virtual`
- 2-2 给 `~Circle()` 加 `override`，函数体打印 `析构 Circle(半径 …)`
- 2-3 给 `~Rect()` 加 `override`，函数体打印 `析构 Rect(… x …)`

**验收标准**

`Text`

```text
=== 阶段 2：通过基类指针删除对象 ===
  delete 之前：live = 1
  析构 Circle(半径 1.5)
  析构 Shape(circle)
  delete 之后：live = 0
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 只有 `析构 Shape(circle)` 一行 | `~Shape()` 还不是虚函数。骨架本来就是这一行，做完 2-1 才会多出派生类那一行 |
| 构建时仍有 `-Wdelete-non-virtual-dtor` 警告 | 同上，警告会随 `virtual` 一起消失 |
| `live` 没有回到 0 | 析构函数里的 `--live_count_` 被删掉了 |

对照实验（做完之后再做一次）：把 `virtual` 去掉，重新构建并运行，
阶段 2 只剩基类那一行，警告也回来了。`virtual` 一加上，两者同时恢复。

## 阶段 3 · 工厂与多态遍历

**要做什么**

- 3-1 实现 `make_shape`：`"circle"` → `new Circle(a)`，`"rect"` → `new Rect(a, b)`，其它返回 `nullptr`

**验收标准**

`Text`

```text
=== 阶段 3：工厂与多态遍历 ===
  造出 4 个图形，1 个名字不认识
  circle  面积 = 12.5664，周长 = 12.5664
  rect    面积 = 12.0000，周长 = 14.0000
  circle  面积 = 3.1416，周长 = 6.2832
  rect    面积 = 4.0000，周长 = 8.0000
  总面积 = 31.7080
  live = 4
  析构 Circle(半径 2)
  析构 Shape(circle)
  析构 Rect(3 x 4)
  析构 Shape(rect)
  析构 Circle(半径 1)
  析构 Shape(circle)
  析构 Rect(2 x 2)
  析构 Shape(rect)
  清理后 live = 0
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `造出 0 个图形，5 个名字不认识` | `make_shape` 还是占位版本 |
| `1 个名字不认识` 变成别的数字 | 字符串比较写错了。比较 C 字符串要用 `std::strcmp`，不能用 `==` |
| `triangle` 也造出了对象 | 分支缺少兜底，最后应当 `return nullptr` |
| 总面积是 `19.7080` 一类 | 少算了一个图形，或某个面积公式不对 |

## 阶段 4 · `dynamic_cast`

**要做什么**

- 4-1 `as_circle`：用 `dynamic_cast<const Circle *>(s)`，转不过去得到 `nullptr`
- 4-2 `count_circles`：遍历数组统计圆的个数
- 4-3 `as_circle_ref`：用 `dynamic_cast<const Circle &>(s)`，失败时它自己抛 `std::bad_cast`

**验收标准**

`Text`

```text
=== 阶段 4：dynamic_cast ===
  图形总数 = 3，其中圆 = 2
  第一个是圆吗：是
    它的半径 = 2
  引用版：成功，半径 = 2
  对矩形用引用版：捕获到 std::bad_cast
  析构 Circle(半径 2)
  析构 Shape(circle)
  析构 Rect(3 x 4)
  析构 Shape(rect)
  析构 Circle(半径 1)
  析构 Shape(circle)
  清理后 live = 0
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `其中圆 = 0` | `as_circle` 还是返回 `nullptr`，或者 `count_circles` 没有调用它 |
| `第一个是圆吗：否` | `dynamic_cast` 的目标类型写错，注意要转成 `const Circle *` |
| 程序在引用版那一行崩溃 | 引用版没有捕获异常。引用版失败时抛 `std::bad_cast`，必须用 `try` / `catch (const std::bad_cast &)` 捕获 |
| 编译报 `source type is not polymorphic` | `Shape` 里没有虚函数。类型信息挂在虚函数表旁边，没有虚函数的类无法做 `dynamic_cast` |

> [!IMPORTANT]
> 指针版失败得到空指针，用之前必须判空；引用版失败抛 `std::bad_cast`，
> 只适合「确定成功」的场合。这一条来自 N4659 §8.2.7/9，
> 完整引用见《05-类与面向对象/08-多态：重载、虚函数与它们的分工.md》第 8.2 小节。

## 界面部分怎么用

界面版是同一个核心模块的第二个驱动，有 Win32 与 Qt 两份实现，业务逻辑都只在 `core` 里。

### 两份界面：Win32 与 Qt

同一个窗口有两份实现，业务逻辑都只在 `core` 里，两份界面只负责调用它：

| 文件 | 界面库 | 产物 | 默认是否构建 |
|---|---|---|---|
| `src/main_gui_win32.cpp` | Win32 API + GDI | `app_gui_win32.exe` | 构建（零第三方依赖） |
| `src/main_gui_qt.cpp` | Qt Widgets | `app_gui_qt.exe` | **不构建**，需要显式打开 |

两份界面里的 TODO 是**同一批**，编号也一致（界面连接 1、2a、2b……）。
**做一份即可**，另一份留作对照：同一件事在消息映射里怎么写、在信号槽里怎么写。

**Qt 版怎么打开**

Qt 版用的是**官方安装器的动态版 Qt**，配置时指向那一套 Qt 的**套件目录**：

`PowerShell`

```powershell
# 套件目录要指到编译器那一层，例如 <Qt>/6.11.1/mingw_64
cmake --preset mingw-gdb -DWITH_QT=ON -DQT_ROOT=<Qt 的套件目录>
cmake --build --preset mingw-gdb
build\mingw\bin\app_gui_qt.exe
```

- `WITH_QT` 默认为 `OFF`：没有 Qt 时，`core`、`app_cli` 与 `app_gui_win32` 照常构建；
- Qt 的位置也可以放在环境变量 `QT_ROOT` 里，此时配置命令不必再写 `-DQT_ROOT`；
- 定位 Qt 与工具链匹配检查都交给仓库根目录 `工具/获取依赖/qt-dynamic.cmake`，
  **工程里不写死任何本机路径**；
- 模板若已被复制到仓库之外，Qt 版需要自行 `find_package(Qt6 COMPONENTS Widgets REQUIRED)`。

**运行时怎么部署**

构建完成后会自动调用 `windeployqt`，把 Qt 的 DLL 与 `platforms\qwindows.dll` 拷到 exe 旁边，
随后再把编这个 exe 的那套 MinGW 运行时 DLL 拷过去：

`Text`

```text
Qt6Core.dll  Qt6Gui.dll  Qt6Widgets.dll  platforms\qwindows.dll
libgcc_s_seh-1.dll  libstdc++-6.dll  libwinpthread-1.dll
```

- 后三个是 **MinGW 运行时**。Qt 自己的 DLL 也依赖它们，因此必须与 exe 放在一起，
  而且**必须与编译器同源**——不同 GCC 版本的 `libstdc++-6.dll` 混用会出怪问题；
- 工程同时给 Qt 目标加了 `-static-libgcc -static-libstdc++`：exe 本身不再依赖
  `libgcc_s_seh-1.dll` 与 `libstdc++-6.dll`，但 Qt 的 DLL 仍然需要，所以照拷；
- 目标机器仍需要对应的编译器运行库：MSVC 构建要装 Visual C++ 运行库；
  MinGW 构建的这三个 DLL 已经拷在 exe 旁边；
- **判据：把 exe 连同这些 DLL 拷到一个没有 Qt、`PATH` 里也没有 Qt 与 MinGW 的目录，
  双击能起窗口，才算部署完成。**
- 部署产物全部落在 `build\` 里，已被仓库 `.gitignore` 覆盖，**不要提交 DLL**。

> [!TIP]
> 只练语言部分时保持 `WITH_QT=OFF`，用 Win32 版或命令行版即可，不必装 Qt。

**怎么跑**

`PowerShell`

```powershell
cmake --build --preset mingw-gdb
build\mingw\bin\app_gui_win32.exe
```

在 VS Code 里调试它时，`program` 指向 `build/mingw/bin/app_gui_win32.exe`
（MSVC 生成器则是 `build/msvc/bin/Debug/app_gui_win32.exe`）。
