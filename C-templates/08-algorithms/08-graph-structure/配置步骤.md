# 配置步骤 · 08-algorithms/08-graph-structure（图上的结构性问题）

本模板是**分阶段的整体演练**：把「图上的结构性问题」拆成四个阶段。
四个阶段的算法都长在同一趟深度优先搜索或同一次入度消减上，
因此每一阶段只留一处空：留空的地方都是那一步最关键的判断。

四个阶段分别是：拓扑排序里取出一个点之后怎么改邻居的入度、什么时候把邻居入队；
Tarjan 里 `low` 的两条更新规则；割点的判定（桥的判定已经给出）；
Kruskal 里取出下一条边之后怎么用并查集判断、加不加、什么时候收工。

本模板的参考答案不给，判据就是本文件里逐字给出的输出与自查表。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

## 阶段 1 · 拓扑排序的入度更新

**要做什么**（在 `src/graphalgo.cpp` 里，TODO 阶段 1-1，`kahn_toposort`）

模板里的有向图有 9 个点、12 条边，其中 0→1→2→0 与 5→6→5 是两个环。
把它里面 2→1 与 6→5 这两条回边去掉，就得到同一批点上的无环图（10 条边）。
两张图都要跑一遍：一张有解，一张有环。

`Text`

```text
有向图（9 个点、12 条边）的出边表：

  点 0：1、2、3、5        点 5：6
  点 1：2                 点 6：4、5
  点 2：1、3              点 7：8
  点 3：4                 点 8：无
  点 4：无

无环图＝上面这张表去掉 2→1 与 6→5 两条边，剩 10 条。
```

**已给出的部分**：入度数组的初始化（数一遍每条边指向谁）、队列、
入度为 0 的点按编号升序先进队列、结果的存放。
**留空的**：从队列取出一个点之后要做什么——它的每条出边让谁的入度减一、
减到什么时候才把那个点放进队列，以及两个计数器 `decrements` 与 `enqueued`。
取点的循环本身也在这里，`head` 已经声明好了。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 1: Kahn topological sort ===
acyclic graph vertices          : 9
acyclic graph edges             : 10
cyclic graph vertices           : 9
cyclic graph edges              : 12
-- acyclic graph --
topological order               : 0 7 1 5 8 2 6 3 4
order length                    : 9
enqueue order                   : 0 7 1 5 8 2 6 3 4
indegree decrements             : 10
vertices with indegree left     : 0
those vertices                  : (none)
has cycle                       : no
-- cyclic graph --
topological order               : (none)
order length                    : 0
enqueue order                   : 0 7 8
indegree decrements             : 5
vertices with indegree left     : 6
those vertices                  : 1 2 3 4 5 6
has cycle                       : yes
```

**判据是四列一起看**，不只是拓扑序本身：

| 列 | 无环图 | 有环图 | 说明 |
|---|---|---|---|
| `topological order` | `0 7 1 5 8 2 6 3 4` | `(none)` | 有环时收尾会把排不满的结果清空 |
| `order length` | `9` | `0` | 无环图排出来的点数必须等于点数 |
| `enqueue order` | 与拓扑序相同 | `0 7 8` | 有环图只有三个点进过队列，另六个进不去 |
| `indegree decrements` | `10` | `5` | 无环图每个点都出过队，每条边恰好被处理一次，因此等于边数 |
| `vertices with indegree left` | `0` | `6` | 无环图收工时入度全为 0；有环图剩下 1、2、3、4、5、6 互相等着 |

拓扑序为什么是 `0 7 1 5 8 2 6 3 4` 而不是从小到大的 `0 1 2 3 4 5 6 7 8`：
队列是先进先出，初始进入的是 0 与 7 两个入度为 0 的点；
取出 0 之后，1 与 5 的入度归零，排在 7 后面进场。
`enqueue order` 与 `topological order` 在先进先出队列下必然相同，
两行一起打印是为了让有环图那一段说得清：有环时拓扑序列被清空了，
`enqueue order` 仍然留下「谁进过队列」这个线索。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 两张图的 `has cycle` 都是 `yes`，`enqueue order` 只有 `0 7` | 入度从来没有被减过，占位实现还在那一步 |
| 无环图的 `indegree decrements` 停在 `5`（实测） | 只处理了初始队列里的两个点，取点的循环没有继续往下走 |
| 无环图的 `topological order` 是 `7 8 0 5 6 1 2 3 4`（实测） | 队列被写成了后进先出：次序仍然是一个合法拓扑序，但与判据不同 |
| `enqueue order` 比 `topological order` 短 | 有入度没归零的点被提前放进了队列，收尾时被当成有环 |
| 无环图报 `has cycle` 是 `yes` | 收尾那一句判的是「排出来的点数等于点数」，排不满只可能是入度的账没算平 |
| `decrements` 比 10 大 | 同一条边被处理了两次，或者计数器写在取点的循环里而不是出边的循环里 |

> [!TIP]
> 拓扑序不唯一，同一张图可以有多个合法次序。本模板判的是**由先进先出队列
> 与邻接表次序共同定下来的那一个**，因此换一种队列就换一个答案。
> 想确认自己写的是不是「次序合法但对不上判据」，数一下 `decrements`：
> 它是 10 而次序不同，说明入度的账是平的，只是取点的顺序换了。

## 阶段 2 · Tarjan 的 `low` 更新

**要做什么**（TODO 阶段 2-1，`tarjan_dfs`）

`dfn` 是每个点第一次被访问到的时刻，`low` 是「从这一点出发，沿着树边往下走、
最多再走一条非树边，能回到的最早时刻」。`low` 与 `dfn` 相等时，
这个点就是它所在强连通分量的根，从栈顶弹到它为止就是一个分量。

**已给出的部分**：`dfn` 与 `low` 的分配、栈、`in_stack` 标记、
弹栈与分量收集、对每个未访问点各起一趟 DFS 的驱动。
**留空的**：`low` 的两条更新规则，在邻居循环的两处留空里
——一处管「子树回来了」，另一处管「边指向一个还在栈里的点」。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 2: Tarjan strong components ===
vertices                        : 9
edges                           : 12
component count                 : 7
sum of component sizes          : 9
largest component size          : 2
single-vertex components        : 5
component 1 (size 1)            : 4
component 2 (size 1)            : 3
component 3 (size 2)            : 1 2
component 4 (size 2)            : 5 6
component 5 (size 1)            : 0
component 6 (size 1)            : 8
component 7 (size 1)            : 7
dfn                             : 1 2 3 4 5 6 7 8 9
low                             : 1 2 2 4 5 6 6 8 9
scc matches reachability        : yes
```

分量的次序是**弹出次序**，也就是缩点图的一个逆拓扑序：
4、3 与 1 2 先收，5 6 次之，0 最后收，8 与 7 来自第二趟 DFS。
每个分量内部按编号升序打印，因此 `1 2` 与 `5 6` 谁先谁后不靠运气。

**判据在 `component count` 与 `low` 这两行上**：

| 看什么 | 应当是 | 说明 |
|---|---|---|
| `component count` | `7` | 12 条边、9 个点，但只有两个环，因此只有两个分量大于 1 |
| `sum of component sizes` | `9` | 每个点恰好属于一个分量 |
| `low` | `1 2 2 4 5 6 6 8 9` | 点 2 与点 6 的 `low` 比自己的 `dfn` 小，它们靠环里的回边绕了上去 |
| `dfn` 与 `low` 相等的点 | 0、1、3、4、5、7、8，共 7 个 | 正好是 7 个分量的根，与 `component count` 对上 |
| `scc matches reachability` | `yes` | 按定义验过：分量内部两两可达，不同分量之间不互相可达 |

点 6 有一条边指向点 4，而点 4 在第一趟 DFS 里早就收完、已经不在栈里。
这条边不算退路，`low[6]` 因此停在 6 而不是被拉到 5 上——
它是这一阶段最容易写错的一处，也是能分辨出对错的那一处。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `component count` 是 9、每个分量都是单点 | 两条更新都没写，`low` 一直等于 `dfn` |
| `component count` 是 6，且出现 `0 5 6` 这样的大小 3 的分量（实测） | 回边那一处没判「还在不在栈里」，指向已收完分量的边也被当成了退路 |
| `scc matches reachability` 是 `no` | 分量不满足定义，按上一行与下一行找是哪一处 `low` 拉错了 |
| 分量个数对了，某个分量的成员是 `2 1` | 收集时没有对成员排序，打印出来就成了入栈次序 |
| 程序在弹栈时读到空栈 | 弹栈循环的终止条件写错：要一路弹到当前点为止 |
| `low` 里有 0 | `low` 的初值是 `dfn`，被改成了从 0 开始的下标；0 是「还没访问」的标记 |

> [!IMPORTANT]
> **`low` 的两条规则都在把当前点的 `low` 往更早的序号上拉，依据却不同。**
> 子树那一条看子树的 `low`，回边那一条看对面那个点的 `dfn`。
> 还有第三类边，它既不是树边也不是退路：对面那个点访问过、已经不在栈里，
> 属于另一个早就收完的分量，这一类不能让 `low` 动。
> 本图上点 6 有一条边指向点 4，漏掉这一类，分量个数会从 7 掉到 6，
> 点 0、5、6 会被并成一个分量。

## 阶段 3 · 割点与桥

**要做什么**（TODO 阶段 3-1，`find_cut_vertices`）

删掉一个点会让剩下的图断开，这个点就是**割点**；删掉一条边会让剩下的图断开，
这条边就是**桥**。两者都由同一趟 DFS 上的 `dfn` 与 `low` 判出来。

无向带权图有 8 个点、11 条边，按权从小到大是 0-1(1)、1-2(2)、0-2(3)、3-4(4)、
6-7(5)、4-5(6)、5-6(7)、2-3(8)、0-3(9)、4-6(10)、1-3(11)。
这一阶段只用到它的形状，权留到阶段 4 用。

**已给出的部分**：DFS 骨架、`dfn` 与 `low` 的分配、回边的处理、
**桥的判定收集**、割点的去重与排序、两个暴力验证函数。
**留空的**：割点的判定——子树绕不绕得回当前点，以及当前点是这趟 DFS 的起点时按什么判。

> [!WARNING]
> **桥的判定已经写在留空处的正上方，它透露了「拿 `low` 与 `dfn` 比大小」这个形状。**
> 因此这一阶段的难点不在形状上，而在两件事：比较符取哪一个方向，
> 以及起点为什么要单独处理（起点没有祖先，上面那条路走不通）。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 3: cut vertices and bridges ===
vertices                        : 8
edges                           : 11
cut vertices                    : 3 4 6
cut vertex count                : 3
bridges                         : (3,4) (6,7)
bridge count                    : 2
dfn                             : 1 2 3 4 5 6 7 8
low                             : 1 1 1 1 5 5 5 8
cut vertices by brute force     : 3 4 6
bridges by brute force          : (3,4) (6,7)
cut vertices match              : yes
bridges match                   : yes
```

**判据是与暴力验证两行 `match` 都为 `yes`**：

| 看什么 | 应当是 | 说明 |
|---|---|---|
| `cut vertices` | `3 4 6` | 删掉 3 断开两块，删掉 4 断开右边的一摞，删掉 6 让 7 落单 |
| `bridges` | `(3,4) (6,7)` | `low[4]` 是 5、`dfn[3]` 是 4，前者大；`low[7]` 是 8、`dfn[6]` 是 7，同样如此 |
| `cut vertices match` | `yes` | 与逐个删点试出来的集合一致 |
| `bridges match` | `yes` | 与逐条删边试出来的集合一致 |
| `dfn` | `1 2 3 4 5 6 7 8` | DFS 从 0 出发一路走成一条链，因此序号就是访问次序 |
| `low` | `1 1 1 1 5 5 5 8` | 0、1、2、3 互相有回边，4、5、6 只有彼此 |

`cut vertices by brute force` 与 `bridges by brute force` 是给出的：
前者逐个删点、看剩下的图从编号最小的点出发能走到几个点，
后者逐条删边、看剩下的图还连不连通。两者都不懂 Tarjan，只按定义做，
因此它们给出的集合可以当作标准答案。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `cut vertices` 是 `0 3 4 6`，比暴力验证多一个 0（实测） | 起点也用了非起点那条规则：起点没有祖先可绕，只能靠孩子的个数说话 |
| `cut vertices` 是 `3 6`，比暴力验证少一个 4（实测） | 把桥的判定直接搬给了割点：桥用的是严格大于，割点的等号方向不同 |
| `cut vertices` 里有重复的编号 | 收尾的去重被删掉了；一个割点可能被多个孩子各判出来一次（本图上每个点只有一个孩子，因此这一步不改结果，但它不能少） |
| `bridges match` 是 `no` | 收进结果时没有按 `(小, 大)` 归一，`(4,3)` 与 `(3,4)` 会被当成两条 |
| `cut vertices match` 是 `no`，两边看着一样 | 一边升序、一边没排序：集合相同而序列不同，比较是按序列比的 |
| 程序在 `dfn` 为 0 的点上递归 | 回边那一支也要走 `continue`，否则访问过的点会被当成没访问过再进去一次 |

> [!CAUTION]
> 无向图在 `to_unweighted` 里每条边加了两个方向，因此邻接表里每一项都出现两次。
> **暴力删边时只看 `u` 小于 `v` 的那一次**，否则同一条边会被删两遍、
> 报出来的桥也会重复一份。

## 阶段 4 · Kruskal 的并查集接入

**要做什么**（TODO 阶段 4-1，`kruskal`）

Kruskal 的做法是：把边按权从小到大排好，一条一条取出来，
两端还不在同一棵树上的就收下，已经连通的就放弃；
收够「点数减一」条就停手，剩下的边连取都不用取。

**已给出的部分**：边表、按权排序、一条一条取出的遍历骨架、
`considered` 的计数，以及**完整的并查集**（`find` 带路径压缩、`unite` 按大小合并）。
**留空的**：取出下一条边之后怎么判断两端是否已经连通、加不加、
两个计数器 `skipped` 与 `total_weight` 怎么办，以及什么时候收工。

阶段 3 与阶段 4 用的是同一张无向带权图，权两两不同，因此最小生成树唯一。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 4: Kruskal and the disjoint set ===
vertices                        : 8
edges in the table              : 11
edges considered                : 8
edges never considered          : 3
edges chosen                    : 7
edges skipped                   : 1
chosen equals vertices - 1      : yes
total weight                    : 33
sets left                       : 1
chosen edges, in the order they were added:
  0-1 w=1
  1-2 w=2
  3-4 w=4
  6-7 w=5
  4-5 w=6
  5-6 w=7
  2-3 w=8
```

**判据在「取了几条、选了几条、跳过几条」这三个数上**：

| 看什么 | 应当是 | 说明 |
|---|---|---|
| `edges considered` | `8` | 7 条选完就凑够 7 条边，第 9 条起不必再取 |
| `edges never considered` | `3` | 0-3(9)、4-6(10)、1-3(11) 三条没有被取出来 |
| `edges chosen` | `7` | 8 个点的树正好 7 条边 |
| `edges skipped` | `1` | 第 3 条 0-2(3) 的两端早已连通，它成环，被放弃 |
| `chosen equals vertices - 1` | `yes` | 边数满足「点数减一」，树长满了 |
| `total weight` | `33` | 1+2+4+5+6+7+8 |
| `sets left` | `1` | 收工时全部点在一棵树上 |

选中的次序就是权从小到大的次序：权是 1、2、3、4、5、6、7、8 的八条里，
权为 3 的那条被跳过，其余七条依次把 8 个点连成一棵。
剩下的三条如果继续取，都会被跳过（所有点已经在一棵树上），
判据里 `edges considered` 这一行因此能直接反映有没有提前收工。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `edges chosen` 是 0、`sets left` 是 8 | 占位实现还在，一条也没选 |
| `edges considered` 是 11、`edges never considered` 是 0、`edges skipped` 是 4，而边集与总权都对（实测） | 少了收工那一步：树长满之后还在往下取，结果对但账目对不上 |
| `total weight` 大于 33 | 成环的边也被收了进去 |
| `chosen equals vertices - 1` 是 `no` 而 `sets left` 是 1 | 选多了：连通性已经满足，边数却超过点数减一 |
| `sets left` 大于 1 | 图被当成不连通的：`unite` 没有真的把两棵树合起来，或者有的边被漏看 |
| 合并时读坏下标 | 并查集初始化的点数要与图的点数一致，点的编号在 0 到 7 之间 |

> [!TIP]
> 并查集是给出的，不要改它。要接的是两件事：**怎么问「两端在不在同一棵树上」**，
> 以及**什么时候停**。这两件事写对了，`considered` 与 `skipped` 自然对得上；
> 只把边集写对而不管这两个数，判据里两行就会露出来。

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| 编译报 `'kahn_toposort' was not declared in this scope` | `graphalgo.hpp` 里的 `namespace galgo` 没有对上，或者头文件被改动过 |
| 运行结果里出现中文 | 判据行一律 ASCII，中文只写在注释里；检查自己加进去的打印 |
| 同一份源码重跑数字不同 | 本模板的图写死在源码里，没有随机数与时间种子；出现这种情况说明图的数据被改过 |
| `-Wall` 报 `unused variable` 或 `set but not used` | 占位实现里带 `(void)` 的那几行没有随 TODO 一起删掉 |
| 某个阶段做完之后别的阶段输出也变了 | 四个阶段互不相干，各用各的图；检查是不是改到了公共的图数据或 `main_cli.cpp` |
| 改了 `main_cli.cpp` 让输出好看 | 它打印的是验收判据，不要为了让数字对上而改它 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
