# 配置步骤 · 08-algorithms/02-memo-divide-backtrack（记忆化、分治与回溯）

本模板是**分阶段的整体演练**：记忆化、分治、回溯看着是三套写法，
它们共用同一棵递归树，区别只在「哪些子问题被重复展开」与「哪一步做完要退回去」。
四个阶段依次把缓存读写、合并段、选择与撤销补上，最后用同一组计数把三者摆在一起看。

本模板的参考答案不给，判据就是本文件里逐字给出的输出与自查表。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

## 阶段 1 · 记忆化的缓存读与写

**要做什么**（在 `src/memo.cpp` 里，`fib_memo` 上的两处 TODO）

- 1-1 读缓存：进函数先看这一格是算好的值还是「还没算过」的标记，算好的直接交出去
- 1-2 写缓存：基线那一支与递归算完那一支，都要把结果记回缓存

**验收标准**

`Text`

```text
=== Stage 1: memoization, cache read and write ===
fib_naive(25)                   : 75025
fib_naive(25) calls             : 242785
fib_naive(25) depth max         : 25
fib_naive(30) calls             : 2692537
fib_memo(25)                    : 75025
fib_memo(25) calls              : 49
fib_memo(25) hits               : 23
fib_memo(25) depth max          : 25
fib_memo(30)                    : 832040
fib_memo(30) calls              : 59
fib_memo(30) hits               : 28
```

**判据在 `calls` 与 `hits` 上**：`fib_naive(25)` 展开了 242785 个节点，
`fib_memo(25)` 只进了 49 次函数，其中 23 次是直接命中缓存的。
`fib(30)` 的对比更明显：2692537 对 59。

| 怎么看这三个数 | 说明 |
|---|---|
| `fib_memo(25)` 是 0 | 占位实现还在 |
| `calls` 还是 242785 | 读缓存没有生效：进了函数没查缓存就往下展开 |
| `calls` 是 26 而 `hits` 是 23 | 读与写都写了，但顺序反了：命中判断放在了递归之后 |
| `hits` 是 0 而 `calls` 明显小了 | 只写了缓存没写命中判断，或者命中时忘了把 `hits` 加一 |
| `fib_memo(30)` 是错的而 `fib_memo(25)` 是对的 | 缓存建小了：`make_cache(n)` 的长度是 n+1，别的地方用 n |
| `fib_memo(0)` 之类的调用返回 -1 | 「还没算过」的标记与真实结果撞了；fib 的值不是负数，-1 才安全 |

> [!TIP]
> **记忆化的判据不是「变快了」，而是「调用次数降下来了」。**
> 耗时随机器与优化等级变，调用次数只随算法变，重跑逐位相同，适合当验收标准。

## 阶段 2 · 分治的合并段

**要做什么**（TODO 阶段 2-1，`cross_sum`）

分治的骨架已经给出：区间对半拆，分别递归，再把「跨越中点」的那一段并进来。
合并段由两截拼成——一截以 `mid-1` 结尾向左延伸，一截从 `mid` 开始向右延伸，
两截都必须非空。

**验收标准**

`Text`

```text
=== Stage 2: divide and conquer, the merge step ===
data A                          : 2 -3 4 -1 -2 1 5 -3
A, linear                       : 7
A, divide and conquer           : 7
A, dc calls                     : 15
A, dc scan iterations           : 24
data B (all negative)           : -5 -2 -9 -1 -7
B, linear                       : -1
B, divide and conquer           : -1
B, dc calls                     : 9
B, dc scan iterations           : 12
data C (fixed random)           : 15 -14 -13 17 -11 -18 -17 10 18 -7 -9 19 5 -18 -8 -19 -3 11 20 -9 -17 -18 -6 5 -19 -2 6 18 1 9 -4 15
C, linear                       : 45
C, divide and conquer           : 45
C, dc calls                     : 63
C, dc scan iterations           : 160
```

**三组数据的结果都必须与线性版逐位相同**。
A 组的 7 来自 `4 + (-1) + (-2) + 1 + 5`，它正好跨越中点，是本阶段的关键用例：
合并段写错时 A 组会给出 5（只取右半的最大和），一眼就能看出来。
B 组全是负数，答案是 -1——**合并段的初值如果取 0，这一组会给出 0**。

`dc calls` 与 `dc scan iterations` 是分治的两笔代价：
递归节点数（区间对半拆，8 个元素是 15 个节点）与合并时扫过的元素个数。
`dc calls` 在 n=8 时是 15、n=32 时是 63，都等于 2n-1。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `A` 组是 0 | 占位实现还在 |
| `A` 组是 5 | 只算了右半，合并段没写 |
| `B` 组是 0 | 合并段的初值取成了 0，全负数时返回了一个「空的段」 |
| `C` 组与线性版差一点 | 两截里有一截可以为空；两截都必须至少含一个元素 |
| 结果偏大 | 合并时把左右两半的最大和也加进来了：合并段只算「跨越中点」的那一条 |
| `dc scan iterations` 是 0 | 合并段没有真的去扫，或者计数没加 |

## 阶段 3 · 回溯的选择与撤销

**要做什么**（`queen_place` 与 `queen_remove` 各一处 TODO）

搜索的主干、可行性检查与节点计数都已经给出。两处留空的是**选择与撤销**：
选中一格就把列、主对角线、副对角线三个标记立起来，回溯返回前再把它们放回去。
三个位置的下标换算在已给出的 `queen_can_place` 里，照着它写。

**验收标准**

`Text`

```text
=== Stage 3: backtracking, choose and undo ===
n_queens(6)                     : 4
n_queens(6) nodes               : 153
n_queens(6) pruned              : 742
n_queens(7)                     : 40
n_queens(7) nodes               : 552
n_queens(7) pruned              : 3033
```

**判据是三个数一起看**：解数（6 皇后 4 个、7 皇后 40 个）、
搜索树节点数（153、552）、被剪掉的候选数（742、3033）。
节点数比「不剪枝的 55987 与 960800」小两三个数量级，剪枝省下的工作量就在这里。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 解数还是 46656 / 823543 | 两处 TODO 都没填，一次剪枝也没发生 |
| 解数比 4 少很多 | 「选择」写了但「撤销」没写：标记只立不清，越往后冲突越多 |
| 解数比 4 大 | 「撤销」把不该清的也清了，同一行里出现了两个皇后 |
| 解数比 4 小 | 三个标记只立了两个，冲突判定过严 |
| 解数对但 `pruned` 是 0 | 剪枝计数没加，或 `queen_can_place` 被改动了 |
| 第二次跑 `n_queens` 时结果变了 | 棋盘状态没有在 `n_queens` 里重新初始化，或者上一轮残留的标记没清干净 |

> [!CAUTION]
> **撤销必须与选择严格配对，且顺序相反。**
> 少清一个标记，出错的位置与真正的原因会隔很远：错误在当前分支，
> 报出来的却是后面某个完全无关的分支。这类错误只能靠「选择与撤销成对出现」这条纪律避免。

## 阶段 4 · 同一棵递归树，三种用法

**要做什么**（TODO 阶段 4-1，`count_distinct_calls`）

前三个阶段各算了一笔账。这一阶段把账并到一起：
朴素递归展开了多少个节点、记忆化进了多少次函数、其中**参数互不相同的**有多少个。
最后一件事不用展开树——参数只会在 0 到 n 之间取值，数一遍取值范围就够了。

**验收标准**

`Text`

```text
=== Stage 4: the same recursion tree, three uses ===
fib(25), naive tree nodes       : 242785
fib(25), memo calls             : 49
fib(25), memo hits              : 23
fib(25), cache filled cells     : 26
fib(25), distinct subproblems   : 26
fib(30), naive tree nodes       : 2692537
fib(30), memo calls             : 59
fib(30), cache filled cells     : 31
fib(30), distinct subproblems   : 31
```

**判据是 `distinct subproblems` 与 `cache filled cells` 必须相等**：
两者都在数同一件事——**被真正算过（不是命中）的子问题有几个**。
25 是 26 个、30 是 31 个，正好是 n+1。

这三行放在一起就是记忆化的全部依据：
树上有 242785 个节点，而参数互不相同的只有 26 个，
省下来的 242785 - 49 次调用全部来自「同一个参数不再展开第二遍」。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `distinct subproblems` 是 0 | 占位实现还在 |
| 它等于 `memo calls` | 数成了「一共进了几次函数」，那是阶段 1 已经数过的 |
| 它与 `cache filled cells` 差 1 | 少算了参数 0；`fib(0)` 也是一次实实在在的计算 |
| 它等于 `naive tree nodes` | 数成了递归树的节点数 |

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| 编译报 `'std::vector' has not been declared` | `memo.hpp` 里的 `#include <vector>` 被删了 |
| `fib_naive(30)` 要跑很久 | 正常，它是 2692537 次调用；本模板只用它作对照，不要拿它当实现 |
| 阶段 3 骨架跑得慢 | 占位实现不做剪枝，7 皇后要搜 960800 个节点；这是骨架的正常状态 |
| 结果重跑不一致 | 本模板的数据全部写死或由固定种子生成，出现这种情况说明改动了 `main_cli.cpp` |
| `-Wall` 报 `unused parameter` | 占位实现里 `(void)` 那几行没有随 TODO 一起删掉 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
