# 配置步骤 · 08-algorithms/05-sort-compare（比较排序的三种策略）

本模板是**分阶段的整体演练**：把「比较排序」拆成四个阶段，
从归并的合并段写起，再写快排的 Lomuto 分区，然后补上三数取中，
最后写堆排序的下沉。四个阶段结束时程序都能构建、能跑出可对照的输出。

这个模板与别处的不同在计数器：三个排序函数都收一个 `Stats &`，
每一次比较走 `less_key`，每一次交换或搬移走 `swap_items` 与 `move_item`，
因此「谁比较得多、谁搬得多」不是估计出来的，而是程序打印出来的两个数。
三种策略共用同一份数据、同一套计数规则，数字之间才可以横向比。

数据全都写死在源码里：32 个元素里只有 4 把键（同一把键分成好几片，用来判稳定性）、
1024 个固定种子的伪随机元素、128 个已经升序的元素（用来把退化情形逼出来）。
没有读文件，也没有拿时间当种子，重跑逐位相同。

本模板的参考答案不给，判据就是本文件里逐字给出的输出与自查表。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

计数器只有两个函数会动：`less_key` 每调用一次 `compares` 加一；
`swap_items` 记两次搬移，`move_item` 记一次搬移。一次交换算两次搬移，
因为两个元素各自换了个位置。三个排序函数都收一个 `Stats &`，
`depth` 与 `depth_max` 由 `DepthGuard` 维护——它在构造时记一层、析构时退回来，
因此不必在每条返回路径上手工加减。

判据工具也已经给出：`is_sorted` 查键是否非降，`stable_ok` 先查有序、
再查同一把键的原始下标是否升序，`reference_order` 给出稳定排序唯一可能的那个结果，
`std_sort_compares` 用 `std::sort` 排同一个序列并返回它调了多少次比较函数。

**判据落在三组数上**。

`input keys` 与 `merge: sorted keys` 两行把「成片重复」摊开给人看：
键 0 原本占着开头 3 格与第 17 位起 4 格，排完之后并成一段 7 个。
`stable` 那一行验的是这 7 个的原始下标仍然升序，也就是原来在前面的那一片仍然在前面。

`compares` 与 `moves` 两个数都能手算核对：32 个元素要并 5 层
（1 并 2、2 并 4、4 并 8、8 并 16、16 并 32），每层每个元素被搬两次
（写进缓冲区、再搬回来），因此 `moves` 是 32 乘 5 乘 2，正好 320。
`compares` 是「决定拿哪一边」的总次数，93 比逐层最坏情况小，
原因是有相等键时总有一边先拿完，剩下那一段不再比较。

`same as reference` 那一行比 `stable` 更严：它把结果与按「键、原始下标」排出来的
唯一序列逐项比。稳定排序的结果只有这一个可能。
`bottom-up` 的两个数与递归版逐位相同，因为 1024 与 32 都是 2 的幂，
两种分法切出来的合并区间完全一样。

> [!IMPORTANT]
> **稳定性只由合并段里的一句判断决定**：两边一样大时先拿左边那一个。
> 这一句同时决定了 `compares` 的值——反过来写，比较次数会变，`stable` 也会变成 `no`。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `merge: sorted` 是 `no` | 占位实现还在，合并段整段没做 |
| `merge: stable` 是 `no` 而 `sorted` 是 `yes` | 相等时先拿了右边那一个；把「右是否小于左」反过来写成「左是否小于右」就会这样 |
| `compares` 比 93 大不少 | 有一段先拿完之后还在继续比较，比如用哨兵把两段都扫到底 |
| `moves` 是 160 而不是 320 | 只记了写进缓冲区的那一半，整段搬回数组那一步没走 `move_item` |
| `bottom-up: compares` 与递归版差几个 | 段长翻倍的边界写错了：末尾只剩一段时也去合并，或者右邻不足一整段时按整段算 |
| `bottom-up: same as reference` 是 `no` | 自底向上那一版还没有真正跑起来（占位实现什么都不做） |
| `depth max` 不是 6 | 二分骨架被改过；这个数只跟规模有关，32 个元素是 6 层 |

## 阶段 2 · Lomuto 分区

**要做什么**（在 `src/sortcmp.cpp` 里，TODO 阶段 2-1，`partition_lomuto`）

方案已经定死：Lomuto 分区，枢轴取区间最后一个元素 `a[hi - 1]`，返回它排好之后落在的下标。
定死方案是为了让固定输入下的交换次数唯一，判据才有意义。
递归骨架与两处计数都已经给出。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 2: Lomuto partition, pivot is the last element ===
32 items, only 4 distinct keys:
last-element pivot: sorted      : yes
last-element pivot: stable      : no
last-element pivot: compares    : 158
last-element pivot: moves       : 144
last-element pivot: depth max   : 10
1024 items, keys 0..4095, seed 12345:
last-element pivot: compares    : 11416
last-element pivot: moves       : 13020
last-element pivot: depth max   : 23
std::sort: compares             : 12018
```

**判据落在三个数上**。

`compares` 与枢轴落在哪一格无关：Lomuto 固定扫区间里除枢轴以外的每一个元素，
每扫一个记一次比较。因此 32 个元素那一组是 158，凡是照方案写的实现都会得到这个数。

`moves` 是交换次数的两倍（`swap_items` 记两次）。144 对应 72 次交换。
这里有一条容易吃亏的约定：两个下标相同时也照样记两次，写成
「下标不同才换」会让这个数偏小，三种策略的搬移次数就不再是同一把尺子量的了。

`depth max` 是 10（32 个元素）与 23（1024 个元素）。
它与 `std::sort` 的对照也一并给出：11416 对 12018，快排的比较次数略少于 `std::sort`。

> [!NOTE]
> `stable` 那一行是 `no`。快排不是稳定的：分区里的交换会把相等键的原始次序打乱。
> 这一行在阶段 2 不是判据（快排本来就不必稳定），它回答的是另一个问题——
> 为什么归并排完之后同一个输入能保持原次序，而快排不能。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `sorted` 是 `no` | 占位实现还在，它永远返回区间开头 |
| `compares` 比 158 小 | 分区里漏扫了元素；Lomuto 扫的是区间里除枢轴以外的每一个 |
| `compares` 比 158 大 | 枢轴自己也拿去比了，它不参与那一轮扫描 |
| `moves` 比 144 小，其余都对 | 两个下标相同时跳过了 `swap_items`；本模板约定照记两次 |
| `moves` 与 144 差得远 | 「小于枢轴」判成了「不大于枢轴」，与枢轴相等的元素也被换到了前面 |
| `depth max` 是 32 或 1024 | 分区没有把区间切小（返回值就是区间端点），递归退化成一条链 |
| `stable` 是 `yes` | 一次交换都没做，分区没有生效 |

```text
median-of-three: sorted         : yes
1024 items, keys 0..4095, seed 12345:
last-element pivot: compares    : 11416
last-element pivot: depth max   : 23
median-of-three: compares       : 11773
median-of-three: depth max      : 16
median-of-three: sorted         : yes
```

**这一节是本模板最有价值的地方**：同一份已经升序的输入，两种取枢轴的做法差出一个数量级。

8128 可以手算核对：末元素枢轴在升序输入上每次都把区间切成
「除枢轴以外全部留在左边」，长度一次只减一，于是比较次数是
127 加 126 一直加到 1，正好 8128，递归深度就是 128。
三数取中在同样的输入上每次取到的正好是区间正中间那个位置的值，区间对半劈开，
比较次数降到 841，深度降到 8。

1024 个伪随机元素那一组给出的是另一面：`median-of-three` 的比较次数
反而比 `last-element pivot` 多一点（11773 对 11416），
因为它每次都要固定花 3 次比较去选枢轴；换来的是深度从 23 降到 16。
**平均情况与最坏情况是两把不同的尺子**，这一段把两把尺子摆在了同一张输出上。

> [!CAUTION]
> 末元素枢轴遇到已经升序的输入会退化成深度等于区间长度的递归。
> 本模板只用了 128 个元素（128 层还撑得住），把规模放大到几十万，
> 栈就会被压穿。这正是三数取中要解决的问题之一。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `median-of-three: compares` 是 0 | 占位实现还在，它永远返回第一个候选 |
| `compares` 是 834 而不是 841 | 有分支只记了 2 次比较；契约要求无论数据怎么排都恰好 3 次 |
| `depth max` 是 128 | 返回的不是中间那个候选，退化还在 |
| `last-element pivot: sorted` 是 `yes` 而 `compares` 是 0 | 骨架状态的假过关：输入本来就升序，占位实现什么都没做。这一行必须与 `compares` 一起看 |
| `median-of-three: compares` 比 `last-element pivot` 还大、深度也没降 | 分区那一处还是占位实现，两组数字比的是同一个空壳 |
| 程序在很短的小区间上崩掉 | 区间长度很小时三个候选的下标会重复，返回值必须仍然是这三个下标之一 |

> [!TIP]
> 想看清三数取中的收益，把阶段 3 的两组数各抄一行到纸上：
> 升序那一组是「比较次数差 9.7 倍、深度差 16 倍」，
> 随机那一组是「比较次数略多、深度更浅」。两种输入给出的结论不一样。

## 阶段 4 · 堆排序的下沉

**要做什么**（在 `src/sortcmp.cpp` 里，TODO 阶段 4-1，`sift_down`）

建堆循环与「堆顶换到末尾、堆缩小一格」的循环都已经给出，
留空的是下沉本身：每一层先看两个孩子里谁的键更大，再拿它与当前节点比，
孩子更大就换下去。注意形参里的 `n` 是「堆里还剩几个元素」，不是数组长度。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 4: heap sort, sift down ===
32 items, only 4 distinct keys:
heap: sorted                    : yes
heap: stable                    : no
heap: compares                  : 204
heap: moves                     : 216
1024 items, keys 0..4095, seed 12345:
heap: compares                  : 17295
heap: moves                     : 18658
heap: depth max                 : 0
std::sort: compares             : 12018
```

**判据落在三个数上**。

`depth max` 是 0：三种策略里只有堆排序不吃栈帧，它是三个循环套出来的。

`compares` 是 204（32 个元素）与 17295（1024 个元素），是三种策略里最高的。
每一层要两次比较：一次挑出较大的孩子，一次拿它与父亲比。与 `std::sort` 的
12018 相比，同规模的随机数据上堆排序多花了四成以上的比较。

`moves` 是 216 与 18658，都是偶数——堆排序只有交换，没有别的搬移方式。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `sorted` 是 `no` | 占位实现还在，堆建不起来 |
| `compares` 是 0 而 `moves` 不是 0 | 骨架状态：给定的那两个循环还在换位，下沉一处未填 |
| `compares` 比 204 小不少 | 挑孩子与比父亲这两次比较只做了一次；两个孩子都在时必须先挑出大的 |
| `moves` 是奇数 | 少记了一次搬移；堆排序只走 `swap_items`，每次记两次 |
| 排完之后只剩最后一个元素不对 | 堆缩小的边界给错了：`sift_down` 拿到的 `n` 是堆里剩下的元素个数，不是数组长度 |
| `depth max` 不是 0 | 堆排序没有递归；出现非零深度说明实现里调用了别的排序 |

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| 所有 `compares` 都是 0 | 比较没有走 `less_key`，而是在自己写的分支里直接比了键 |
| 结果是对的，所有 `moves` 都是 0 | 搬移没有走 `swap_items` 与 `move_item` |
| 编译报 `'less_key' was not declared in this scope` | 接口在 `namespace sc` 里；检查 `sortcmp.hpp` 有没有被改动 |
| 同一份源码重跑数字不同 | 本模板没有拿时间当种子的随机数；出现这种情况说明改动了 `main_cli.cpp` 或数据生成 |
| `-Wall` 报 `unused parameter` | 占位实现里带 `(void)` 的那几行没有随 TODO 一起删掉 |
| `std::sort: compares` 换一套标准库就变 | 这一行由标准库的实现决定，本文件记的是本机 g++ 16.2.0 上 libstdc++ 的值；其余各行都是本模板自己数出来的，以本机重跑的输出为准 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
