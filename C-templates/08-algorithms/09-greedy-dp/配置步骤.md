# 配置步骤 · 08-algorithms/09-greedy-dp（贪心与动态规划）

本模板是**分阶段的整体演练**：把「贪心与动态规划」这一件事拆成四个阶段。
先从区间调度看贪心策略怎么选，再用 0/1 背包看贪心错在哪里，
然后把二维表的转移写出来，最后把二维表压成一行、看清容量维度为什么必须反着走。
四个阶段结束时程序都能构建、能跑出可对照的输出。

四个阶段共用同一份写死的数据：区间七条，物品九件，背包容量二十。
数据全部写在 `src/main_cli.cpp` 里，没有随机数、没有时间种子、不读文件，
同一份源码重跑逐位相同。排序器在同键时一律用原始下标收尾，
因此换个算法库实现也不会改变输出。

本模板的参考答案不给，判据就是本文件里逐字给出的输出与自查表。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

## 阶段 1 · 区间调度：那个被维护的量

**要做什么**（在 `src/greedydp.cpp` 里，TODO 阶段 1-1，`interval_schedule`）

七条区间，要选出尽量多互不重叠的，返回它们的原始下标。
函数开头已经把区间按右端点升序排好，循环骨架也写好了，
循环体里缺的是「这一条收不收」与「收下之后留下什么」。

判断依据的是这一条与上一条收下的区间在位置上的关系；
留给下一条的那个量是一个数——是这一条的哪一端，由读者判断。
它在循环开始前要有一个初值，使得第一条区间一定收得下。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 1: which order, and what to keep ===
intervals (lo, hi):
  [0] [1, 100)
  [1] [2, 12)
  [2] [12, 22)
  [3] [11, 13)
  [4] [22, 27)
  [5] [27, 32)
  [6] [32, 37)
schedule count                  : 5
schedule indices                : 1 2 4 5 6
wrong: by left end, count       : 1
wrong: by left end, indices     : 0
wrong: by length, count         : 4
wrong: by length, indices       : 3 4 5 6
```

**判据是前两行**：`schedule count` 是 5，`schedule indices` 是 `1 2 4 5 6`。
下标是**原始下标**，不是排序之后的位置——两者在这份数据里不一样，
区间 0 排在最前面，区间 3 排在第三位，认错了就会打印出一串顺序怪异的数。

后四行是已经给出的两个错误策略，用来对照：

| 策略 | 个数 | 为什么少 |
|---|---|---|
| 按右端点升序（本阶段要写的） | 5 | 结束得早的区间留下最多的时间给后面 |
| 按左端点升序（已给出） | 1 | 区间 0 的 `[1, 100)` 开始最早，收下它之后全被挡住 |
| 按区间长度升序（已给出） | 4 | 最短的 `[11, 13)` 挡掉了 `[2, 12)` 与 `[12, 22)` 两条 |

`[11, 13)` 与 `[12, 22)` 是端点相接之后再错开的关系，这个例子说明
「单位时间收益最高」不等于「总收益最高」——贪心的正确性要靠换法证明，不靠直觉。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `schedule count` 是 0 | 占位实现还在，循环体里什么都没做；或者那个量的初值取得太大，第一条就被挡下了 |
| `schedule count` 是 7，`indices` 是 `1 3 2 4 5 6 0` | 收下之后没有更新那个量，后面每一条都通过了判断 |
| `schedule count` 是 6，`indices` 是 `1 3 2 4 5 6` | 维护的是这一条区间的左端点，不是右端点；收下的区间之间有重叠 |
| `schedule count` 是 3，`indices` 是 `1 4 6` | 比较用了严格大于，端点相接的两条被判成了重叠 |
| `indices` 是 `0 2 3 4 5` | 收下时记住了排序后的位置，没有用 `index` |
| 编译报 `unused variable` | 自己声明的那个量没有在循环里读它 |

> [!TIP]
> **比 5 大的个数一定是错的。** 七条区间里最多挑得出 5 条互不重叠的，
> 报出 6 或 7 说明收下的那些之间彼此重叠，判断本身没有起作用。
> 这一点比「个数偏小」更好用：偏小可能是次序没选对，偏大只能是判断写错了。

> [!IMPORTANT]
> **贪心能不能用，取决于「换掉其中一步会不会变差」。**
> 区间调度能换：结束最早的那条与最优解的第一条互换之后，剩下的可选区间只会更多。
> 0/1 背包不能换，下一阶段给出的是一个具体的、能算出差多少的反例。

## 阶段 2 · 单位价值贪心与它的反例

**要做什么**（TODO 阶段 2-1，`greedy_knapsack`）

九件物品，容量二十。函数开头已经按单位价值从高到低排好，
收下之后的记账（价值、重量、原始下标、剩余容量）也已经写好。
循环体里缺的是一个判断：这一件收不收，以及收不下的时候停下来还是跳过去。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 2: greedy by unit value, and where it fails ===
items (weight, value):
  [0] w=4 v=9
  [1] w=9 v=19
  [2] w=9 v=19
  [3] w=11 v=22
  [4] w=5 v=6
  [5] w=7 v=8
  [6] w=3 v=3
  [7] w=2 v=2
  [8] w=6 v=6
capacity                        : 20
greedy value                    : 36
greedy weight                   : 20
greedy taken                    : 0 1 4 7
best by brute force             : 41
greedy short by                 : 5
```

**判据是 `greedy value` 与 `greedy short by` 这两个数，它们要一起看**：
贪心拿到 36，穷举出来的真正最优值是 41，差 5。
只看 36 说明不了什么，36 与 41 并排摆着才是这一阶段的结论。

这组数据是这样凑出来的：物品 0（`w=4 v=9`）的单位价值最高，贪心先收它，
剩 16；物品 1（`w=9 v=19`）收得下，剩 7；此时物品 2 与物品 3 都塞不进去了，
只能拿 `w=5 v=6` 与 `w=2 v=2` 把容量填满，价值停在 36。
而真正的最优解是物品 1 与物品 3：重量 9 加 11 正好是 20，价值 19 加 22 是 41。

`greedy weight` 是 20，说明贪心把容量用光了——**用光容量不等于拿到最优值**。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `greedy value` 是 94、`taken` 是九件全收 | 占位实现还在，没有判断容量够不够 |
| `greedy short by` 是负数 | 同上：收下的总重量 56 超过了容量 20 |
| `greedy value` 是 28、`taken` 是 `0 1`、`short by` 是 13 | 收不下的时候用了 `break`：物品 2 塞不进剩 7，后面的也一并跳过了 |
| `greedy value` 是 36 而 `taken` 不是 `0 1 4 7` | 下标记成了排序后的位置，或者记账那几行被改过 |
| `best by brute force` 不是 41 | `main_cli.cpp` 被改动过；它是验收程序，不需要改 |

> [!TIP]
> 想知道贪心到底差多少，先要有一个「真正的最优值」当尺子。
> 本模板给的尺子是穷举所有子集，九件物品只要 512 次尝试，几毫秒就跑完。
> 尺子越简单越可信——它是拿来验 DP 的，不是拿来替 DP 的。

## 阶段 3 · 二维表：状态定义与转移

**要做什么**（TODO 阶段 3-1，`knapsack_dp`）

`dp[i][c]` 表示只考虑前 `i` 件物品、容量为 `c` 时的最大价值。
第 0 行的初值与填表的双重循环都已经写好，
走完之后的回溯也已经写好，缺的是循环体里那一格的转移。

第 `i` 件物品有两个前途：不收它，答案落在少一件、同容量的那一格；
收它，就要先从容量里腾出它的重量，再看腾出来的那一格。
两个前途取更好的那个写进这一格，重量超过容量时就只剩一个前途。
两个格子的行号与列号分别是什么，是这一步的关键。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 3: the two-dim table and its transition ===
items                           : 9
capacity                        : 20
dp best                         : 41
dp cells filled                 : 210
dp chosen                       : 1 3
dp best equals brute force      : yes
```

**判据是四行一起看**：`dp best` 是 41，与阶段 2 那把尺子对上了；
`dp chosen` 是 `1 3`，与 41 这个值的来历一致（`w=9 v=19` 与 `w=11 v=22`）；
`dp best equals brute force` 是 `yes`。
`dp cells filled` 是 210，它是结构量：`(9 + 1) × (20 + 1)`，第 0 行加九行，每行二十一格。

`dp chosen` 由已经给出的回溯得到：从右下角往回走，
这一格如果与「不收这一件」的那一格相等，说明这一件没进最优解。
因此这一列能把「值对了但表填错了」的情况抓出来——
值碰巧相同而表里的数不成体系时，回溯走出来的下标序列会对不上。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `dp best` 是 0、`dp chosen` 是 `(none)` | 占位实现还在，内层循环没有给任何一格赋值 |
| `dp best` 是 45、`dp chosen` 是 `0` | 「收它」那一支用了这一行而不是上一行的格子，同一件物品被反复收下 |
| `dp best` 是 41 而 `dp chosen` 是 `(none)` | 转移写对了，但回溯读的行号与转移里写的不是同一套 |
| 程序在回溯处崩溃或读到越界 | 收下之后减重量时列号越过了 0；转移没有拦住「重量大于容量」这一支 |
| `dp cells filled` 不是 210 | 双重循环的边界或计数那两行被改过 |

> [!CAUTION]
> 回溯是**已经给出的代码**，它假定转移写的是标准形式。
> 如果转移里的两个前途取反了（把「不收」写成「收」），
> 回溯会在容量为负的格子上继续往下走。转移写完之后先看 `dp best` 是不是 41，
> 再看 `dp chosen`，两步分开查比一起查容易定位。

## 阶段 4 · 滚动数组：用哪一行、往哪边走

**要做什么**（TODO 阶段 4-1，`knapsack_rolling`）

二维表有 `(n + 1) × (capacity + 1)` 格，而算每一行只用得上上一行。
一维数组只有一行，它同时扮演「上一件物品那一行」与「这一件物品这一行」，
因此内层容量维的方向成了关键：走的方向决定每一格读到的到底是谁。

函数里已经给出了数组、初值、外层循环，也给出了一个正序遍历容量的对照版本。
缺的是内层循环本身：从哪一格开始、到哪一格停、每次走几格。

**验收标准**

`实测数据`
`Text`

```text
=== Stage 4: rolling array, which row and which way ===
two-dim best                    : 41
two-dim cells                   : 210
rolling best                    : 41
rolling array cells             : 21
rolling same as two-dim         : yes
unbounded (forward) best        : 45
unbounded differs from 0/1      : yes
```

**判据是三个数并排**：`rolling best` 是 41，与 `two-dim best` 逐位相同；
`rolling array cells` 是 21，二维版是 210，正好是它的十分之一；
`unbounded (forward) best` 是 45，比 41 大。

三个数读法是：前两个相同，说明压掉一维没有改变答案；
第三个数不同，说明方向确实在起作用——正序遍历容量时，
每一格读到的是这一件物品刚改过的格子，于是物品 0（`w=4 v=9`，单位价值最高）
被反复收下五次，重量 20、价值 45。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `rolling best` 是 0 | 占位实现还在，内层循环没有写 |
| `rolling best` 是 45、`same as two-dim` 是 `no` | 方向反了，滚动版变成了完全背包版，与给出的对照版得到同一个数 |
| `rolling best` 是 41 而 `same as two-dim` 是 `no` | 阶段 3 的二维版出了问题，两边算的不是同一件事 |
| `rolling array cells` 不是 21 | 数组开成了二维，或者长度写成 `capacity`（少了容量为 0 的那一格） |
| 程序越界读到别的内存 | 内层循环的下界用了 0 而不是物品本身的重量，`c - w` 变成了负数 |

> [!IMPORTANT]
> **方向不是习惯问题，是「这一格该读谁」的问题。**
> 反着走时，下标更小的格子还没被这一件物品碰过，读到的是上一件物品留下的结果；
> 正着走时，下标更小的格子刚刚被改过，读到的是这一件物品自己的结果。
> 一个方向是 0/1 背包，另一个方向是完全背包，代码只差一个自增与一个自减。

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| 编译报 `'interval_schedule' was not declared in this scope` | `greedydp.hpp` 里的 `namespace gdp` 没有对上，或者 `main_cli.cpp` 被改动过 |
| 一组数字全对，另一组全是 0 | 四个阶段是各自独立的函数，只做了其中一两个 |
| 同一份源码重跑数字不同 | 本模板没有随机数、没有时间种子，出现这种情况说明改动了 `main_cli.cpp` 或数据表 |
| `-Wall` 报 `unused parameter` 或 `unused variable` | 占位实现里带 `(void)` 的那几行没有随 TODO 一起删掉；自己声明的量没有在循环里读它 |
| 输出的数字带负号 | `greedy short by` 在骨架状态是负数，属于正常现象；填完阶段 2 之后它是 5 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
| 改了数据表之后判据对不上 | 判据与本文件里的数据是一套；换数据要连带把本文件的输出一起换掉 |
