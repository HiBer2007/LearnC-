# 配置步骤 · 08-algorithms/06-sort-noncompare（不比较也能排：计数与基数）

本模板是**分阶段的整体演练**：把「不比较也能排」这一件事拆成四个阶段，从计数排序的计数写起，
再把前缀和读成每一块的起点、把元素回填出去，然后按位分配完成基数排序，
最后用同一套桶分配、只改一个扫描方向，跑出稳定与不稳定两种结果。
四个阶段结束时程序都能构建、能跑出可对照的输出。

四个阶段一共 5 处 TODO，全在 `src/sortnc.cpp` 里：阶段 1 一处，阶段 2 两处，
阶段 3 与阶段 4 各一处。每一处上面写明要做什么，下面给出填完之后应当看到的数；
`src/main_cli.cpp` 按阶段把这些数打印出来，逐行对得上才算做完。

本模板的参考答案不给，判据就是本文件里逐字给出的输出与自查表。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

排序的元素是 `Item`：一个键，加上它在原始数组里的**下标**。下标一路跟着元素走，
排完之后按「键相等」分组把下标打印出来，相等键的先后有没有被打乱一眼就能看见。

数据写死在 `src/main_cli.cpp` 里：第一组 40 个元素，只有 5 个不同的键（0、4、9、13、15），
每个键各出现 8 次，而且同样的键常常连着一片；第二组 24 个元素，最大值 900，
让基数排序走满三轮。**成片重复的键是稳定性判据的前提**：每个键只出现一次的话，
「相等键的原始下标」这一列就永远是升序，判据形同虚设。

两个计数器的口径固定，与你在代码里怎么写那一行无关。

| 计数器 | 记什么 |
|---|---|
| `writes` | 写入次数：每把一个值写进数组的一个格子，加一。写计数桶的格子、把元素放进桶、把元素写回数组都算；读不算 |
| `bucket_ops` | 桶操作次数：每让一个元素与桶打一次交道，加一。把一个元素分配进桶算一次，从桶里取回落点或取回元素也算一次 |

桶自身的整理——计数数组清零、求前缀和、抄桶的大小——不计入这两个数：
那几步是准备，没有元素在动。

## 阶段 1 · 计数：把每个键的个数记下来

**要做什么**（在 `src/sortnc.cpp` 里，TODO 阶段 1-1，`count_keys`）

`counts` 的声明与清零、`counts_size` 个格子与键的一一对应关系都已经给出。
这一阶段补两件事：先把 `n` 个键验一遍，有一个落在计数数组管不到的范围就返回 `false`，
此时一个格子也不许动；再把每个键的个数记到它该去的格子里。

**验收标准**

`Text`

```text
=== Stage 1: counting the keys ===
data (40 items)                     : 13 13 13 0 0 9 9 13 4 4 15 0 9 15 15 4 13 0 9 4 15 15 0 0 13 9 4 15 9 0 4 13 9 4 15 13 0 4 9 15
distinct keys                       : 5
key range                           : 0..15
counts (16 cells, one per key)      : 8 0 0 0 8 0 0 0 0 8 0 0 0 8 0 8
counts total                        : 40
count_keys, returned                : accepted
count_keys, writes                  : 40
count_keys, bucket ops              : 40
bad key 16, returned                : rejected
bad key 16, counts untouched        : yes
bad key -1, returned                : rejected
bad key -1, counts untouched        : yes
```

**判据有三处，缺一处都不算做完。**

| 看哪一行 | 应当是什么 | 为什么 |
|---|---|---|
| `counts (16 cells, one per key)` | `8 0 0 0 8 0 0 0 0 8 0 0 0 8 0 8` | 只有 5 个格子非零，与数据里的 5 个键一一对应；每个非零值都是 8 |
| `counts total` | `40` | 计数是元素的另一种数法，合计必须等于元素个数 |
| `count_keys, writes` 与 `bucket ops` | `40` 与 `40` | 40 个元素各改写一个格子、各进一次桶 |
| `bad key 16` 与 `bad key -1` 两行 | 都是 `rejected`，且 `untouched` 都是 `yes` | 范围校验在动计数数组之前做完 |

越界那两行是同一个判据的两半：`rejected` 只说明返回了 `false`，
`counts untouched` 才说明你没有一边验一边记。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 16 个格子全是 0 | 占位实现还在，计数那一段没写 |
| 只有第 0 个格子非零 | 记数时用的不是键；格子由键决定，不是由位置决定 |
| `counts total` 不是 40 | 有元素被记了两次，或者漏了；合计必须等于元素个数 |
| 越界那两行报 `accepted` | 范围没验；越界写 `counts[k]` 是缓冲区越界 |
| 报 `rejected` 但 `counts untouched` 是 `no` | 边验边记；先走一趟只验不动，第二趟才动手 |
| `writes` 是 80 | 把「读一格再写一格」记成了两次；口径是「改写一个格子算一次」 |
| 编译报 `unused variable` | 占位那几行 `(void)` 没有随 TODO 一起删掉 |

> [!CAUTION]
> **键是数据给的，不是常量。** `counts[key]` 在 `key` 超出 `0..counts_size-1` 时
> 写的是缓冲区外面的内存，属于未定义行为：可能悄悄改坏别的变量，也可能当场崩。
> 范围校验必须排在第一次写之前。

## 阶段 2 · 每一块的起点，以及回填

**要做什么**（TODO 阶段 2-1 在 `block_starts`，TODO 阶段 2-2 在 `count_sort`）

前缀和已经由 `prefix_sum` 求出：`counts[k]` 是「键不大于 `k` 的元素共有几个」。
阶段 2-1 把这句话读成每一块的起点；阶段 2-2 按落点把 `a` 里的元素搬进 `out`。
回填时要定下两件事：一个元素的落点怎么从前缀和里读出来，以及按什么次序取 `a` 里的元素。
第二件事决定稳定性——键的序列看不出它，相等键的原始下标看得出来。

**验收标准**

`Text`

```text

count_keys, returned                : accepted
counts after prefix sum             : 8 8 8 8 16 16 16 16 16 24 24 24 24 32 32 40
starts of each key's block          : 0 8 8 8 8 16 16 16 16 16 24 24 24 24 32 32
count_sort, sorted keys             : 0 0 0 0 0 0 0 0 4 4 4 4 4 4 4 4 9 9 9 9 9 9 9 9 13 13 13 13 13 13 13 13 15 15 15 15 15 15 15 15
count_sort, returned                : accepted
count_sort, sorted by key           : yes
count_sort, same as stable sort     : yes
count_sort, stable (equal keys)     : yes
key 0 indices (in out)              : 3 4 11 17 22 23 29 36
key 4 indices (in out)              : 8 9 15 19 26 30 33 37
key 9 indices (in out)              : 5 6 12 18 25 28 32 38
key 13 indices (in out)             : 0 1 2 7 16 24 31 35
key 15 indices (in out)             : 10 13 14 20 21 27 34 39
count_sort, writes                  : 120
count_sort, bucket ops              : 80
```

`starts` 那 16 个数是阶段 2-1 的判据：`0 8 8 8 8 16 16 16 16 16 24 24 24 24 32 32`。
键 0 那一块从 0 开始，最后一块（键 15）从 32 开始——而 32 加上 8 正好是元素总数 40，
每一块的起点与上一块的终点接得上。**不查这一行也能做对阶段 2-2**，
但 `starts` 与 `counts` 的对应关系正是回填要用的那把钥匙。

阶段 2-2 的判据有两层：

| 层次 | 看哪一行 | 应当是什么 |
|---|---|---|
| 排好了 | `count_sort, sorted by key` | `yes`：0 八个、4 八个、9 八个、13 八个、15 八个 |
| 而且稳定 | `key N indices (in out)` 五行 | 每一个键的下标都严格递增：`3 4 11 17 22 23 29 36` 等 |
| 与标准库一致 | `count_sort, same as stable sort` | `yes`：键与原始下标逐位相同 |

最后一层最严：`same_items` 连原始下标一起比，键对了而相等键的先后错了，照样报 `no`。

`writes` 是 120、`bucket ops` 是 80，拆开是：

| 计数器 | 构成 | 合计 |
|---|---|---|
| `writes` | 40（计数：每个元素把它的格子改写一次）+ 80（回填：每个元素改写一次桶里的落点，再写进输出数组一次） | 120 |
| `bucket_ops` | 40（计数：每个元素进一次桶）+ 40（回填：每个元素从桶里取回一个落点） | 80 |

两个计数器记的是元素级的动作，与具体写法无关：改写一格记一次写入，过一个桶记一次桶操作。
若你另开一个游标数组来接落点，被改写的格子数就与这里不同，那一列会对不上——
**算法对不对看前面几行**：键序列、每个键的原始下标序列、与 `std::stable_sort` 的逐位比较。

> [!IMPORTANT]
> **稳定性不是回填的副产物，它是取元素次序的直接后果。**
> 同一个前缀和，从前往后取元素与从后往前取元素，
> 得到的两份结果键的序列一模一样，相等键的先后却正好相反。
> 阶段 4 会把这一条单独拎出来对照。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `starts` 全是 0 | 占位实现还在，阶段 2-1 没写 |
| `starts` 比正确值大一些 | 起点写成了终点：`counts[k]` 是「不大于 `k` 的个数」，不是这一块的起点 |
| `sorted by key` 是 `no` | 落点算错了，或者放的时候用错了键 |
| `sorted by key` 是 `yes` 而 `stable` 是 `no` | 回填时取元素的次序反了：同一个块里后放的压在了前面 |
| `same as stable sort` 是 `no` 而前面几行都是 `yes` | 拿着 `key N indices` 与验收输出逐行对，一眼能看出是哪一个键的开始错位 |
| `writes` 是 80 | 回填时桶里那一次改写没记：搬一个元素要写两处 |
| 程序在回填处崩溃 | 落点算成了负数或者超出 `out` 的长度；`counts[key]` 用之前先确认它大于 0 |

## 阶段 3 · 按位分配：一轮一位

**要做什么**（TODO 阶段 3-1，`radix_sort`）

轮数（最大值的十进制位数）、取位函数、每轮的 10 个桶、各桶大小的抄录、
按桶号接回工作副本这四件事都已经给出。补的是分配那一段：
把工作副本里的每个元素按当前位放进它该去的桶里。
桶号由这一位上的数字决定，而**同一个桶里攒下来的次序取决于你扫描的方向**——
LSD 基数排序的立足点是「上一轮排好的次序不能被这一轮打乱」，方向不是随便挑的。

**验收标准**

`Text`

```text
=== Stage 3: distributing by digit ===
40 items, max key                   : 15
40 items, rounds                    : 2
round 1, bucket sizes (digit 0..9)  : 8 0 0 8 8 8 0 0 0 8
round 2, bucket sizes (digit 0..9)  : 24 16 0 0 0 0 0 0 0 0
40 items, sorted keys               : 0 0 0 0 0 0 0 0 4 4 4 4 4 4 4 4 9 9 9 9 9 9 9 9 13 13 13 13 13 13 13 13 15 15 15 15 15 15 15 15
40 items, returned                  : accepted
40 items, sorted by key             : yes
40 items, same as stable sort       : yes
40 items, stable (equal keys)       : yes
40 items, key 0 indices             : 3 4 11 17 22 23 29 36
40 items, writes                    : 200
40 items, bucket ops                : 160
--- second data set ---
24 items, max key                   : 900
24 items, rounds                    : 3
24 items, keys                      : 314 7 7 900 0 314 900 900 42 7 0 314 42 42 900 7 314 0 42 900 7 314 0 42
round 1, bucket sizes (digit 0..9)  : 9 0 5 0 5 0 0 5 0 0
round 2, bucket sizes (digit 0..9)  : 14 5 0 0 5 0 0 0 0 0
round 3, bucket sizes (digit 0..9)  : 14 0 0 5 0 0 0 0 0 5
24 items, sorted keys               : 0 0 0 0 7 7 7 7 7 42 42 42 42 42 314 314 314 314 314 900 900 900 900 900
24 items, returned                  : accepted
24 items, sorted by key             : yes
24 items, same as stable sort       : yes
24 items, stable (equal keys)       : yes
24 items, writes                    : 168
24 items, bucket ops                : 144
```

逐轮的桶大小是这一阶段独有的结构量：它把「分配」这一步单独暴露出来，
而排序结果对不对要等所有轮走完才知道。第一组第一轮按个位分，
键 0、4、9、13、15 的个位分别是 0、4、9、3、5，于是桶 0、3、4、5、9 各有 8 个；
第二轮按十位分，0、4、9 的十位是 0，13、15 的十位是 1，于是只剩两个非零桶。
每一轮 10 个桶加起来都等于元素个数，这是分配没有漏也没有重的判据。

`writes` 与 `bucket_ops` 的拆开方式：

| 数据 | `writes` | `bucket_ops` |
|---|---|---|
| 40 个元素、2 轮 | 2 × (40 分配进桶 + 40 接回工作副本) + 40 最后拷进 `out` = 200 | 2 × (40 分配进桶 + 40 从桶取回) = 160 |
| 24 个元素、3 轮 | 3 × (24 + 24) + 24 = 168 | 3 × (24 + 24) = 144 |

两个数都随「元素个数 × 轮数」增长，而轮数由最大值有几位十进制数字决定——
这正是基数排序的代价所在，也是它不适合键的位数很长的场合的原因。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `sorted keys` 就是输入本身的次序 | 分配那一段还没写（占位实现），桶里一个元素也没有 |
| 逐轮桶大小全是 0 | 同上 |
| `sorted by key` 是 `yes` 而 `same as stable sort` 是 `no` | 扫描方向反了：桶里攒下来的次序被翻掉，LSD 的立足点就没了 |
| 桶大小加起来不等于元素个数 | 有的元素分进了两个桶，或者被漏掉 |
| 只有前几轮对、最后一轮不对 | 轮数写死了；轮数由最大值的位数决定，最大值变了就要跟着变 |
| `writes` 是 160 | 最后拷进 `out` 的那 40 次没有记 |
| 编译报 `unused variable 'exp'` | 占位那一行 `(void)exp;` 没有随 TODO 一起删掉 |

> [!TIP]
> 方向有没有扫反，看 `same as stable sort` 那一行最快。
> 基数排序的每一轮都要求稳定，其中一轮扫反了，最终结果迟早对不上；
> 而对不上的地方往往离出错的那一轮很远，因此不要靠肉眼看键的序列。

## 阶段 4 · 扫描方向决定稳定性

**要做什么**（TODO 阶段 4-1，`distribute_stable`）

与阶段 3 的分配是同一件事，差别有两处：桶变成 16 个（按整个键分），
而且要跑两遍——一遍从前往后扫描输入，一遍从后往前。
分配与写回都在留空处，两次调用除那一个 `bool` 之外必须一模一样：
两遍结果的差别只能来自扫描方向，否则这个实验说明不了任何问题。

**验收标准**

`Text`

```text
=== Stage 4: the scan direction decides stability ===
--- scan forward ---
sorted keys                         : 0 0 0 0 0 0 0 0 4 4 4 4 4 4 4 4 9 9 9 9 9 9 9 9 13 13 13 13 13 13 13 13 15 15 15 15 15 15 15 15
sorted by key                       : yes
same as stable sort                 : yes
stable (equal keys keep order)      : yes
key 0 indices                       : 3 4 11 17 22 23 29 36
key 15 indices                      : 10 13 14 20 21 27 34 39
writes                              : 80
bucket ops                          : 80
--- scan backward ---
sorted keys                         : 0 0 0 0 0 0 0 0 4 4 4 4 4 4 4 4 9 9 9 9 9 9 9 9 13 13 13 13 13 13 13 13 15 15 15 15 15 15 15 15
sorted by key                       : yes
same as stable sort                 : no
stable (equal keys keep order)      : no
key 0 indices                       : 36 29 23 22 17 11 4 3
key 15 indices                      : 39 34 27 21 20 14 13 10
writes                              : 80
bucket ops                          : 80
```

**两种方向都要打印出来对照，判据也在这两段的差别里。**

| 看哪一行 | 从前往后 | 从后往前 |
|---|---|---|
| `sorted keys` | 排好的 | 一样 |
| `sorted by key` | `yes` | 一样是 `yes` |
| `key 0 indices` | `3 4 11 17 22 23 29 36` | `36 29 23 22 17 11 4 3` |
| `stable (equal keys keep order)` | `yes` | `no` |
| `same as stable sort` | `yes` | `no` |
| `writes` 与 `bucket ops` | `80` 与 `80` | 一样 |

两段的 `sorted keys` 一行不差：**按键是否排好，完全看不出稳定性丢了**。
从后往前那一次，每个键的下标恰好是升序的倒过来——桶内按扫描到的次序追加，
扫描反过来，桶里的次序自然反过来，写回时再按桶号顺序接出去，
同一个键的元素就整段倒了个个儿。

两个计数器两次相同（各 80：40 放进桶、40 写回 `out`，桶操作同理），
说明方向不改变代价，只改变次序。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 两种方向都是 `stable` | 除扫描方向之外还改了别的：从后往前时改成往桶头插，或者写回时倒着取，把方向的影响抵消了 |
| 两种方向都不 `stable` | 写回时从每个桶的末尾取；往末尾追加就要从桶头取 |
| 从前往后那一次不是升序 | 追加与写回没有配套，同上 |
| 两次的 `writes` 不一样 | 两条分支不等长；两次只允许差扫描方向 |
| `key 15 indices` 是 `(none)` | `out` 一个元素也没放（占位实现还在） |
| `sorted by key` 是 `no` | 桶号算错了：这一阶段按整个键分，不是按某一位分 |

> [!NOTE]
> **四个阶段合起来是同一件事的四层。** 计数排序把键变成下标，
> 用它数出每个键有几个（阶段 1）；前缀和把个数变成落点，回填把元素放到落点上（阶段 2）；
> 键的位数多起来时，一位一位地排，每一轮都要求上一轮的次序不被破坏（阶段 3）；
> 而「破坏」与「不破坏」之间，隔着的往往只是一个扫描方向（阶段 4）。
> 代价也随之换了个地方：不再是比较次数，而是写入次数与桶操作次数。

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| 编译报 `'count_keys' was not declared in this scope` | 命名空间 `snc` 没有对上，或者 `include/sortnc.hpp` 被改动过 |
| 编译报 `unused variable 'exp'` | 阶段 3 占位那一行 `(void)exp;` 还留着，随 TODO 一起删掉 |
| 编译报 `unused parameter` | 某处占位实现的 `(void)x;` 少了一行，而那个形参确实没用到 |
| 越界那两行变成 `accepted` | 范围校验没写；越界写计数桶是缓冲区越界 |
| `counts untouched` 是 `no` | 校验与计数写在了同一趟里；先把 `n` 个键验完再动手 |
| `sorted by key` 是 `yes` 但 `same as stable sort` 是 `no` | 稳定性丢了，两处的次序问题都查一遍：计数排序查取元素的次序，基数排序查扫描方向 |
| 结果里出现负数或特别大的数 | 落点或桶号算错，写到了数组外面；先用小的数据跑，再逐步放大 |
| 同一份源码重跑数字不同 | 本模板四个阶段都是确定性的，数据写死、没有随机数；出现这种情况说明改动了 `main_cli.cpp` |
| 输出的中文变成乱码 | 判据行全是 ASCII；出现乱码说明判据行被改过 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
