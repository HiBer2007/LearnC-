## 阶段 1 · 递归三件套：基线、推进、合并

**要做什么**（在 `src/recursion.cpp` 里，`sum_first` 上的三处 TODO）

一个递归函数由三块组成：**什么时候不再往下走**（基线）、
**把问题交给规模更小的自己**（推进）、
**把这一层的结果与子问题的结果合起来**（合并）。
`sum_first` 求的是数组前 `n` 项之和，三处 TODO 分别对应这三块。

**验收标准**

`Text`

```text
=== Stage 1: base case, step, combine ===
array                           : 1 2 3 4 5 6 7 8
sum_first(n=0)                  : 0
sum_first(n=0) calls            : 1
sum_first(n=1)                  : 1
sum_first(n=8)                  : 36
sum_first(n=8) calls            : 9
sum_first(n=8) depth max        : 9
sum_first(n=2048)               : 2098176
sum_first(n=2048) calls         : 2049
sum_first(n=2048) depth max     : 2049
```

**判据在 calls 与 depth max 这两列上，而不只在和上**：
`n=8` 时 `calls` 是 9、`depth_max` 也是 9，`n=2048` 时两个都是 2049。
`calls` 比 `n` 多一，是因为「前 0 项之和」那一次也要进函数一次（它就是基线那一次）。

| 怎么看这两个数 | 说明 |
|---|---|
| `calls` 恒等于 1 | 没有推进，函数每次都在基线处直接返回 |
| `calls` 等于 `n` 而不是 `n+1` | 基线写成了「`n` 等于 1 时返回第一个元素」，少了一层 |
| `depth_max` 比 `calls` 小很多 | 推进的规模没有真的变小，出现了分叉；本函数是一条链，两者必然相等 |
| 程序在 `n=2048` 处崩溃 | 基线条件永远不成立，递归一直往下走 |

> [!TIP]
> 想看清一条链式的递归，把 `depth_max` 与 `calls` 一起打印最快：
> 两个数相等就是链，两个数差得远就是树。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `sum_first(n=8)` 是 0 | 占位实现还在，三处 TODO 一处未填 |
| 答案比 36 小，差值正好是 1 | 基线写成了「`n` 小于 2 时返回 0」，把 `a[0]` 漏掉了；基线只该管 `n` 等于 0 |
| 答案比 36 大 | 合并时把留下来的那个元素加了两次 |
| `calls` 是 8 而不是 9 | 基线那一次没有进函数，或者计数只在递归分支里加 |
| `calls` 明显大于 n+1 | 推进没有把规模真的减到 `n-1`，出现了分叉 |
| 编译报 `control reaches end of non-void function` | 三块只写了基线，推进与合并还空着，`return` 不见了 |
| `-Wall` 报变量未使用 | 占位实现里那几行 `(void)` 没有随 TODO 一起删掉 |

## 阶段 2 · 递归树有多少个节点

**要做什么**（TODO 阶段 2-1，`fib_tree_nodes`）

`fib_naive` 是已经给出的：`n` 小于 2 时直接返回，否则把两个更小的自己加起来。
每进入一次函数就在递归树上多一个节点，`calls` 数出来的就是节点数。
阶段 2 的任务是**不展开**这棵树，只把节点数递推出来。

**验收标准**

`Text`

```text
=== Stage 2: how big is the recursion tree ===
fib_naive(5)                    : 5
fib_naive(5) calls              : 15
fib_naive(10) calls             : 177
fib_naive(20) calls             : 21891
fib_naive(20) depth max         : 20
fib_tree_nodes(5)               : 15
fib_tree_nodes(10)              : 177
fib_tree_nodes(20)              : 21891
fib(4) tree:
fib(4)
  fib(3)
    fib(2)
      fib(1)
      fib(0)
    fib(1)
  fib(2)
    fib(1)
    fib(0)
fib(4) tree drawn, lines        : 9
fib_naive(4) calls              : 9
```

**判据是三列对齐**：`fib_tree_nodes(n)` 必须与 `fib_naive(n) calls` 逐位相同，
而 `fib_tree_draw(4)` 画出来的行数（9）也必须与 `fib_naive(4) calls` 相同。
`fib_tree_draw` 是已经给出的，它把递归树按缩进画出来，行数就是节点数。

`fib(20)` 的 21891 与 `fib(10)` 的 177 差了 123 倍，而 `n` 只翻了一倍——
这正是递归树上「同一个子问题被反复展开」的样子，
下一章的记忆化要解决的就是它。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 三行都是 0 | 占位实现还在 |
| `fib_tree_nodes(5)` 是 5 | 返回的是 `fib(n)` 的值，不是树的节点数 |
| `fib_tree_nodes(10)` 是 11 | 只数了一条链：左右两棵子树只递归了一边 |
| `fib_tree_nodes(20)` 变成一个很大的负数 | 真的去展开了 `fib(20)`，或者返回值用了 `int` 而溢出 |
| 与 `fib_naive(n) calls` 差 1 | 基线那一层的节点没有算进去；`n` 小于 2 时树只有一个节点 |

## 阶段 3 · 尾递归，以及它的真相

**要做什么**（TODO 阶段 3-1，`sum_loop`）

`sum_tail` 是已经给出的尾递归版：累加器 `acc` 一路传下去，最后一步只剩把 `acc` 返回。
阶段 3 把它改写成循环。**改写之后不该再消耗栈帧**，
这一点由 `depth max` 那一列直接体现——它必须是 0。
每走一轮让 `c.iterations` 加一，验收程序要读这个数。

**验收标准**

`Text`

```text
=== Stage 3: tail recursion, and what it really is ===
sum_tail(n=8)                   : 36
sum_tail(n=8) calls             : 9
sum_tail(n=8) depth max         : 9
sum_tail(n=2048)                : 2098176
sum_tail(n=2048) calls          : 2049
sum_tail(n=2048) depth max      : 2049
sum_loop(n=8)                   : 36
sum_loop(n=8) iterations        : 8
sum_loop(n=8) depth max         : 0
sum_loop(n=2048)                : 2098176
sum_loop(n=2048) iterations     : 2048
sum_loop(n=2048) depth max      : 0
```

前三行是已经给出的尾递归版：`depth max` 等于 2049，**与 `calls` 一样大**。
尾递归在 C++ 里并没有变成循环，栈帧一层不少。
后三行是循环版：`iterations` 等于 `n`，`depth max` 是 0。

| 怎么看这两个数 | 说明 |
|---|---|
| `sum_tail` 的 `depth max` 等于 `calls` | 尾递归没有被消除，这是本阶段的结论本身 |
| `sum_loop` 的 `depth max` 不是 0 | 循环体里又调用了自己（写成了递归），或者仍在调用 `sum_tail` |
| `sum_loop` 的 `iterations` 是 `n+1` | 循环条件写成了「先减再判」，多走了一轮空转 |
| `sum_loop` 的 `iterations` 是 0 而答案对 | 答案是别的路径算出来的；检查 `iterations` 自增写在不在循环里 |

> [!IMPORTANT]
> **尾递归消除是语言实现的选择，不是语言的规定。**
> Scheme 要求实现必须做，C 与 C++ 都不要求。
> 因此不能靠「写成尾递归」来保证不吃栈帧；要保证，就自己写成循环或显式栈。

## 阶段 4 · 显式栈替掉函数调用栈

**要做什么**（TODO 阶段 4-1，`hanoi_stack`）

汉诺塔的递归版已经给出。阶段 4 用一个自己维护的栈得到同一串移动。
栈里放两种「待办的事」：还要再拆的「把 k 个盘子从某柱搬到某柱」，
以及拆到底的「第 k 个盘子走一步」。

**验收标准**

`Text`

```text
=== Stage 4: recursion with an explicit stack ===
hanoi_recursive(3) moves        : 7
hanoi_stack(3) moves            : 7
hanoi(3) same                   : yes
hanoi_recursive(10) moves       : 1023
hanoi_stack(10) moves           : 1023
hanoi(10) same                  : yes
hanoi_recursive(16) moves       : 65535
hanoi_stack(16) moves           : 65535
hanoi(16) same                  : yes
hanoi(3), recursive moves:
  disk 1: A -> C
  disk 2: A -> B
  disk 1: C -> B
  disk 3: A -> C
  disk 1: B -> A
  disk 2: B -> C
  disk 1: A -> C
hanoi(3), stack moves:
  disk 1: A -> C
  disk 2: A -> B
  disk 1: C -> B
  disk 3: A -> C
  disk 1: B -> A
  disk 2: B -> C
  disk 1: A -> C
```

**判据是 `same` 那一列的三个 `yes`**，以及最后两段移动序列逐行相同。
`same_moves` 是已经给出的，它连长度带每一项都比较，不只看步数：
步数相同而次序不同，一样会报 `no`。

`hanoi(n)` 的步数是 2 的 n 次方减一（3 步、1023 步、65535 步），
这一列也一并验了「栈里的每一件事恰好被弹出一次」。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `hanoi_stack` 步数是 0 | 占位实现还在 |
| 步数对而 `same` 是 `no` | 压栈的次序反了：栈是后进先出，**先执行的要最后压** |
| `hanoi(3)` 是 `yes`、`hanoi(10)` 是 `no` | 只处理了「一步移动」，没有处理「还要再拆」的那一种待办，浅的层级碰巧对上 |
| 程序崩溃或死循环 | 弹出的待办没有改变状态就又压了回去，或者 `n` 等于 0 的待办没有丢掉 |
| 移动序列里盘子编号乱序 | 盘子编号没有跟着待办一起走，而是另外算了 |

> [!CAUTION]
> `std::vector` 既是容器也能当栈用，但**取引用之后不要再用它压栈**：
> `push_back` 可能让缓冲区重新分配，先前取到的引用会指向已经释放的内存，
> 之后每一次读写都是未定义行为。先按值取一份，或者用下标访问。

| 运行到 `n=2048` 时崩溃 | 递归没有基线，栈被压穿；先只跑 `n=8` 确认基线生效 |
| 输出的数字带负号 | 用了 `int` 累加，`2098176` 还没溢出，再大的规模就会；计数与和都用 `long long` |
| 同一份源码重跑数字不同 | 本模板的四个阶段全是确定性的，没有随机数，出现这种情况说明改动了 `main_cli.cpp` |
| `-Wall` 报 `unused parameter` | 占位实现带 `(void)` 的那几行没有随 TODO 一起删掉 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
