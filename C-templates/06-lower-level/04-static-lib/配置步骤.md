# 配置步骤 · 06-lower-level/04-static-lib（静态库与符号）

本模板是**分阶段的整体演练**：成品是一个传感器模块——库里有一份自带的采样算法，
外部的「驱动」可以顶替它。同一份 `src/main_cli.c` 编出两个可执行文件：
`app_default` 走库里的算法，`app_override` 走驱动那一份。
四道练习分别落在**内部链接**、**静态库的成员粒度**、**库怎么发现外部实现**、
**强定义覆盖**这四件事上。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

---

## 成品形态

做完这 4 个阶段之后：

| 能力 | 由哪一阶段提供 |
|---|---|
| 两个翻译单元里各有一个同名的内部函数，链接器不报重复定义 | 阶段 1 |
| 静态库的成员按需被拉进可执行文件；看懂「库必须放在引用者之后」 | 阶段 2 |
| 库里找不到外部实现时，用自己的默认算法（通道 0 读到 1） | 阶段 3 |
| 外部驱动给出强定义后，读到的值换一套（通道 0 读到 7） | 阶段 4 |

判定覆盖成功的标准不是「链接没报错」，而是**两个可执行文件打印的值不一样**。

## 阶段 1 · 内部链接

**要做什么**（都在 `core/sensor.c`）

- 1-1 `strip_channel`：合法通道（0 到 `SENSOR_CHANNELS - 1`）原样返回，越界返回 -1。
  它已经是 `static` 的，**保持不动**：`drivers/driver_fast.c` 里有一个同名同签名的函数，
  那个也是 `static`，两个内部符号在同一个可执行文件里互不干扰
- 1-2 `sensor_check_channel`：返回 `strip_channel(ch)`

**验收标准**

`Text`

```text
=== Stage 1: channel check (internal linkage) ===
  check(0)  = 0
  check(2)  = 2
  check(9)  = -1   (expect -1)
  check(-1) = -1   (expect -1)
```

同一份可执行文件里有**两个同名的局部符号**，链接器不报重复定义：

`实测数据`
`Text`

```text
$ nm build/mingw/bin/app_override.exe | findstr strip_channel
00000001400015e0 t strip_channel      ← 来自 drivers/driver_fast.c
0000000140001440 t strip_channel      ← 来自 core/sensor.c
```

小写 `t` 表示内部链接（local）。改成外部链接（把 `static` 去掉）就会撞车：

`实测数据`
`Text`

```text
$ gcc build/exp/main.o build/exp/sensor_nostatic.o ... build/exp/driver_nostatic.o -o a.exe
<工具链>/ld.exe: build/exp/driver_nostatic.o:(.text+0x0): multiple definition of `strip_channel';
                build/exp/sensor_nostatic.o:(.text+0x0): first defined here
collect2.exe: error: ld returned 1 exit status
```

（上面抹掉了工具链的绝对路径，其余原样。）

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `check(9) = 9` | 没有做范围检查，直接返回了入参 | 1-1 |
| `check(-1) = -1` 但 `check(9) = 9` | 只判了下界：`ch < 0` 要写成 `ch < 0 \|\| ch >= SENSOR_CHANNELS` | 1-1 |
| `check(0) = -1000` | `sensor_check_channel` 还是占位实现，没调用 `strip_channel` | 1-2 |
| 链接报 `multiple definition of 'strip_channel'` | 两处里的某一处 `static` 被去掉了 | 两个文件各自的 1-1、4-1 |
| `nm` 里只有一个小写 `t strip_channel` | 驱动那一份没进链接（`app_default` 本来就不链驱动；要看 `app_override`） | 看 `app_override.exe` |
| 编译报 `'strip_channel' defined but not used` | 写了内部函数却没有调用它 | 让 `sensor_check_channel` 调用它 |

## 阶段 2 · 静态库的成员粒度与顺序

**要做什么**

- 2-1 `core/sensor_extra.c` 里的 `sensor_version`：返回 100
- 2-2 用 `nm` 看 `libsensor_core.a` 里有几个成员、各导出什么符号
- 2-3 用命令行手动链接两次，把库放在引用者**之后**与**之前**，对照结果

**验收标准**

`Text`

```text
=== Stage 2: the second member of the static library ===
  version() = 100   (expect 100)
```

静态库的三个成员各自独立，导出符号一目了然：

`实测数据`
`Text`

```text
$ nm build/mingw/lib/libsensor_core.a
sensor.c.obj:
000000000000001f T sensor_check_channel
000000000000003a T sensor_read
                 U sensor_sample_default
                 w sensor_sample_hook
0000000000000000 t strip_channel

sensor_extra.c.obj:
0000000000000000 T sensor_version

sensor_default.c.obj:
0000000000000000 T sensor_sample_default
```

（上面每个成员里那些 `.debug_*`、`.pdata` 一类行已省略，只留了与本题相关的符号。）

库的顺序可以自己动手撞一次：把三个 `.o` 打进一个 `libsensor_core.a`，
再分别用两种顺序链接（`main.o` 引用库里的符号）。

`实测数据`
`Text`

```text
$ gcc -Lbuild/exp build/exp/main.o -lsensor_core -o order_ok.exe      ← 库在引用者之后
（链接成功）

$ gcc -Lbuild/exp -lsensor_core build/exp/main.o -o order_bad.exe     ← 库在引用者之前
<工具链>/ld.exe: build/exp/main.o:main_cli.c:(.text+0x22): undefined reference to `sensor_check_channel'
<工具链>/ld.exe: build/exp/main.o:main_cli.c:(.text+0x98): undefined reference to `sensor_version'
<工具链>/ld.exe: build/exp/main.o:main_cli.c:(.text+0xcb): undefined reference to `sensor_read'
collect2.exe: error: ld returned 1 exit status
```

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `version() = -1` | 占位实现还在 | 2-1 |
| `nm` 的库里看不到 `sensor_extra.c.obj` | 那个文件没加进 `sensor_core` 目标 | `CMakeLists.txt` 的 `add_library(sensor_core ...)` |
| `nm` 在可执行文件里找不到 `sensor_version` | 没有人引用它，这个成员就没被拉进来——这正是成员粒度的意思 | 不用改；`main_cli.c` 里有调用，所以它会在 |
| 手动链接时把库放前面，报的错与你预期不同 | 报错只会列出**第一个**遇到的未定义符号，后面的要往下翻 | 看完整的报错列表 |
| `nm` 报 `file format not recognized` | 把 `.a` 当成可执行文件去 `nm` 了；对库要用 `nm <库名>`，它会按成员分组打印 | 命令写法 |

> [!IMPORTANT]
> **静态库的抽取单位是目标文件，不是符号。** 只要有一个被引用的符号落在某个成员里，
> 整个成员都会被拉进可执行文件。这也是为什么「把无关代码丢进同一个 `.c`」会让体积变大。

## 阶段 3 · 库自带的默认算法

**要做什么**

- 3-1 `core/sensor_default.c` 里的 `sensor_sample_default`：返回 `ch * 10 + 1`
- 3-2 读一遍 `core/sensor.c` 上方那段注释：库是**怎么发现**外部实现的
  （GCC 系用弱引用、MSVC 用 `/alternatename`），并想清楚 `SENSOR_HAS_HOOK()` 为 0 时走哪条路

**验收标准**

`Text`

```text
=== Stage 3/4: default algorithm or external driver ===
  read(0) = 1
  read(1) = 11
  read(2) = 21
  read(3) = 31
```

同一个程序换 `app_override` 跑，这四行会变成 `7 / 107 / 207 / 307`（阶段 4 的结果）。

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| 四行全是 `-1` | 通道检查没过（阶段 1 没做完），或者默认算法返回了负数 | 先回阶段 1，再看 3-1 |
| `read(0) = 0` | 写成了 `ch * 10`，丢了那个 `+ 1` | 3-1 |
| 两个可执行文件打印的值一样 | `app_override` 没有把驱动链进去，或者驱动还没实现 | 阶段 4 |
| MSVC 下报 `unresolved external symbol sensor_sample_hook` | `/alternatename` 那一行没生效：它只加在 `app_default` 上 | `CMakeLists.txt` 的 `if(MSVC)` 分支 |
| MinGW 下报 `undefined reference to 'sensor_sample_hook'` | 弱引用被写成了普通声明（少了 `__attribute__((weak))`），而库里没有这个定义 | `core/sensor.c` 顶部的声明 |

## 阶段 4 · 强定义覆盖

**要做什么**

- 4-1 `drivers/driver_fast.c` 里的 `strip_channel`（`static`）：合法通道原样返回，越界返回 -1
- 4-2 同一个文件里的 `sensor_sample_hook`：先用本文件的 `strip_channel` 检查通道号，
  合法就返回 `ch * 100 + 7`，越界返回 -1
- 4-3 重新构建，分别跑两个可执行文件，再用 `nm` 看符号类型的变化

**验收标准**

`Text`

```text
$ build\mingw\bin\app_default.exe
=== Stage 3/4: default algorithm or external driver ===
  read(0) = 1
  read(1) = 11
  read(2) = 21
  read(3) = 31

$ build\mingw\bin\app_override.exe
=== Stage 3/4: default algorithm or external driver ===
  read(0) = 7
  read(1) = 107
  read(2) = 207
  read(3) = 307
```

符号表里的差别就在这里：

`实测数据`
`Text`

```text
$ nm build/mingw/bin/app_default.exe | findstr "sensor_sample_hook strip_channel"
                 U sensor_sample_hook      ← 未定义：弱引用的地址是 0，走库里的默认算法
0000000140001580 t strip_channel

$ nm build/mingw/bin/app_override.exe | findstr "sensor_sample_hook strip_channel"
000000014000145f T sensor_sample_hook      ← 强定义在场
00000001400015e0 t strip_channel           ← 驱动那一份
0000000140001440 t strip_channel           ← 库那一份
```

**覆盖失败是一个静默的错**：把驱动从链接里去掉，程序照跑，只是值换了一套，
链接器与运行时都不报任何错。

`实测数据`
`Text`

```text
$ cmake --preset mingw-gdb -DWITH_DRIVER=OFF
-- WITH_DRIVER=OFF：app_override 不再链接 drivers/driver_fast.c
$ cmake --build --preset mingw-gdb
$ build\mingw\bin\app_override.exe
  read(0) = 1
  read(1) = 11
  read(2) = 21
  read(3) = 31
```

`app_override` 打印的与 `app_default` 一模一样，**没有任何提示**。
真板上对应的现象是「中断服务程序被默认实现顶替、中断进来却什么都没做」，
见《06-更底层/06-符号与链接属性.md》第 4.3 小节。

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `app_override` 还是 `1 / 11 / 21 / 31` | 驱动没进链接（`WITH_DRIVER` 被关过），或者钩子返回的是占位值 | 重新配置 `-DWITH_DRIVER=ON`；4-2 |
| `app_override` 打印 `-1` | 本文件的 `strip_channel` 还是占位实现（返回 -2000） | 4-1 |
| `app_default` 也变成 `7 / 107 / ...` | 驱动被链进了两个目标：检查 `target_link_libraries` | `CMakeLists.txt` |
| `nm` 里 `sensor_sample_hook` 是 `U` 而程序却打出了驱动的值 | 看错了可执行文件 | 核对 `nm` 的路径 |
| 编译报 `'strip_channel' defined but not used` | 4-1 实现了却没在 4-2 里调用 | 4-2 里先调 `strip_channel` |
| 把驱动换成静态库之后 `app_override` 又变回默认值 | 弱引用不会把静态库的成员拉出来，符号仍然是 `U`（实测） | 把驱动做成对象库，或直接编进目标文件 |

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| `undefined reference to 'sensor_sample_hook'`（MinGW） | PE 目标上**弱定义不能满足未定义引用**（实测：`__attribute__((weak)) int f(void){...}` 单独给出，链接仍然是未定义）。本模板因此用的是**弱引用 + 外部强定义**：库里声明 `extern int sensor_sample_hook(int) __attribute__((weak));`，没人定义时地址为 0 |
| `nm` 里驱动明明定义了，符号还是 `U` | 弱引用**不会**让链接器去静态库里抽成员。把驱动做成对象库（`add_library(... OBJECT ...)`）或直接编进目标文件 |
| MSVC 报 `unresolved external symbol _sensor_sample_hook` | MSVC 没有弱引用：靠 `/alternatename:sensor_sample_hook=sensor_sample_hook_default` 兜底，检查这一行是否加在了 `app_default` 上 |
| MSVC 报 `LNK2005: sensor_sample_hook already defined` | 默认实现与驱动同时定义了同一个名字。默认实现在 MSVC 下要叫 `sensor_sample_hook_default` |
| 链接报 `multiple definition of 'strip_channel'`（MSVC 是 `LNK2005`） | 两个翻译单元里的同名函数都成了外部链接 | 至少保留一个 `static` |
| 库放在引用者之前，报一堆 `undefined reference` | 静态库按命令行顺序扫描，只解决「扫描到它时已经出现的未定义符号」 | 把库放到引用者之后 |
| 改了 `.c` 但输出没变 | 构建目录里的旧产物还在：删掉 `build\` 再配置一次 |
