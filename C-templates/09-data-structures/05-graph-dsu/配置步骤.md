# 配置步骤 · 09-data-structures/05-graph-dsu（手写图与并查集）

本模板是**分阶段的整体演练**：把图的三种存法与并查集各写一遍。
4 个阶段依次补上「邻接表的遍历接口」「矩阵与边表的遍历接口」「路径压缩」「按大小合并」，
每个阶段结束时程序都能构建、能跑出可对照的输出。

这个模板把 `A-10` 与 `A-12` 的「怎么写」收在一处——两者都是「关系的表示」，
差别只在于保留多少信息：图保留全部关系，并查集只保留连通性。

本模板的参考答案不给，判据就是本文件里逐字给出的输出与自查表。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

## 阶段 1 · 邻接表的遍历接口

**要做什么**（在 `include/graph.hpp` 里，TODO 阶段 1-1）

`AdjList::for_each_neighbor(v, f)`：把 `v` 的每个邻居交给 `f`。

**验收标准**

`Text`

```text
from the edge table (the judge)
neighbors of 3                  : [1 2 4]
neighbors of 4                  : [3 5 6]
bfs distances from 0            : [0 1 1 2 3 4 4 -1]
adjacency list
neighbors of 3                  : [1 2 4]
neighbors of 4                  : [3 5 6]
bfs distances from 0            : [0 1 1 2 3 4 4 -1]
dfs order from 0                : [0 2 3 4 6 5 1]
adjacency list matches table    : yes
bitmap matrix matches table     : no
edge list matches table         : no
```

这张图是 8 个点、8 条边，另有孤点 7，因此距离数组的最后一个元素是 `-1`。
`dfs order` 与邻居的**顺序**有关（深度优先把邻居依次压栈），
本机的邻接表恰好与矩阵给出同一个顺序，但这是输入顺序凑巧，不要当成规律。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 邻居列表是空的 | 占位实现还在：一个邻居都没报 |
| `bfs distances` 只有起点是 0，其余全是 -1 | 同上；也可能是接口没有被调用（检查 `for_each_neighbor` 的形参名有没有写错） |
| 少了一个邻居 | 无向图两个方向都要存：`add_edge` 里两个方向各 push 一次 |
| 距离数组里出现了 -1 而边表里连得通 | 孤点之外还有 -1，说明某个邻居没有被报出来 |
| `dfs order` 长度不到 8 | 孤点 7 到不了是对的（只有 7 个点），若还少就是漏了邻居 |

## 阶段 2 · 位图矩阵与边表的遍历接口

**要做什么**（TODO 阶段 2-1、2-2）

- 矩阵：扫一遍这一行，`get(v, u)` 为真就把 `u` 交给 `f`；
- 边表：把每条边过一遍，一端是 `v` 就把另一端交给 `f`（无向边只存了一份，两个方向都要看）。

**验收标准**

`Text`

```text
bitmap matrix
neighbors of 3                  : [1 2 4]
neighbors of 4                  : [3 5 6]
bfs distances from 0            : [0 1 1 2 3 4 4 -1]
dfs order from 0                : [0 2 3 4 6 5 1]
edge list
neighbors of 3                  : [1 2 4]
neighbors of 4                  : [3 5 6]
bfs distances from 0            : [0 1 1 2 3 4 4 -1]
dfs order from 0                : [0 2 3 4 6 5 1]
bitmap matrix matches table     : yes
edge list matches table         : yes
edges in the graph              : 8
adjacency list slots            : 16
bitmap matrix words             : 2
```

最后三行是这张小图上的资源账：8 条无向边在邻接表里占 16 个位置；
8 个点的位图矩阵占 2 个 64 位字（16 字节）。
**点少边密时矩阵更省，点多边稀时反过来**——这正是 `B-05` 第 2 节那张表的来路。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 矩阵的邻居是空的 | 占位实现还在 |
| 边表的邻居只报了一半 | 无向边只存了一份：`e.from == v` 与 `e.to == v` 两种都要处理 |
| 矩阵报了重复的邻居 | 无向图两个位置都置了位，扫行时一个 `u` 只会被报一次，不会重复；出现重复说明 `add_edge` 被调了两次 |
| 矩阵与边表的结果互不相同 | 有一种存法的 `add_edge` 少写了：矩阵要双边置位，边表只存一份 |
| `bitmap matrix words` 与预期不符 | 这个数由构造时的位数定死，`n*n/64+1`；改图不会影响它 |

## 阶段 3 · 路径压缩

**要做什么**（在 `src/disjoint_set.cpp` 里，TODO 阶段 3-1）

`find` 的第一趟已经写好了：顺着父指针走到根。要补的是第二趟：
把路上经过的每个节点直接挂到根上，这样下次问它们就是一步。

**验收标准**

`Text`

```text
=== Stage 3: path compression in find ===
nodes in the chain              : 2000
max height before find          : 1999
find(0), first pass             : 1999
find(0), second pass            : 1
root of every node              : 1999
distinct roots                  : 1
```

验收程序用测试工具 `link_raw` 手工搭一条 2000 个节点的长链（`0 → 1 → … → 1999`），
然后问两次 `find(0)`：第一次要走 1999 步，第二次只要 1 步。

`实测数据`
`Text`

```text
g++ 16.2.0，本机，2000 个节点的链：
  不做压缩：第一次 1999 步，第二次 1999 步
  做了压缩：第一次 1999 步，第二次 1 步
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 第二次仍然是 1999 步 | 占位实现还在：找到了根就返回，没有压平 |
| 第二次是 1 步但 `root of every node` 变了 | 压缩时把某个节点的父指针指向了错的根 |
| 程序卡死或读到坏指针 | 改父指针之前没有先记住下一个节点，改完就找不到路了 |
| `distinct roots` 不是 1 | 压缩不该改变集合的个数，检查是不是把某个根也改了 |
| `size of the set` 变小了 | 压缩不改变集合大小；`size_` 只在根上有意义，压缩时不要动它 |

> [!CAUTION]
> **改指针之前先记住下一个。** 这与链表删除是同一条纪律：
> 一旦把当前节点的父指针改成根，原来那条「往上走」的路就断了。

## 阶段 4 · 按大小合并

**要做什么**（TODO 阶段 4-1）

`unite` 现在的实现是「谁先来谁当根」。要补的是一句比较：
**让小的那棵挂到大的下面**。大小分别记在两个根上（`size_[ra]` 与 `size_[rb]`）。

**验收标准**

`Text`

```text
=== Stage 4: union by size ===
unions                          : 1999
steps while uniting             : 1997
max height                      : 1
distinct roots                  : 1
same(0, 1999)                   : yes
size of the set                 : 2000
steps for 2000 finds            : 1999
```

验收程序按「总是把新点并到老树上」的顺序合并 2000 个点——这个顺序专门欺负
「谁先来谁当根」：不比较大小的实现会长成一条 1999 层高的链，而按大小合并会把它压成星形。

`实测数据`
`Text`

```text
g++ 16.2.0，本机，2000 个点、1999 次合并：
  不按大小合并：最大树高 1999，随后 2000 次查找共走 1999999 步（压缩已开时是 1999 步）
  按大小合并  ：最大树高 1，合并过程本身走 1997 步，随后 2000 次查找共走 1999 步
```

**注意 `steps while uniting` 这一行**：不比较大小时它是 0，按大小合并反而是 1997。
这不是缺点，而是这笔优化本来的样子——**先花几步把树压平，省下的是后面每一次查找**。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `max height` 还是 1999 | 占位实现还在：把 `rb` 直接挂到 `ra` 下面，不看两棵树各有多大 |
| 最大树高降下来了，但 `size of the set` 不对 | 合并之后忘了把大小加到新的根上 |
| `distinct roots` 不是 1 | 两个点本来就在同一集合时应当直接返回，重复合并会把棵数算错 |
| `same(0, 1999)` 是 no | 合并没有真正接上，或者 `find` 的压缩写错了 |
| 按大小合并之后树高仍然很大 | 比较的是节点自己的 `size_`（非根上是陈旧值），要先求根再比 |

> [!IMPORTANT]
> **两处优化各只有几行，但漏掉任一处都会付出代价。**
> `A-12` 测过这两处优化各自单独用、一起用、都不用四种组合；
> 本模板测的是同一件事的另外两个角度：**查找步数**与**树高**。

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| 编译报 `for_each_neighbor` 找不到 | 它是成员模板，定义必须写在使用点可见的地方（本模板都写在头文件里） |
| 编译报 lambda 不能转换成 `F` | 形参写成 `F &f` 时不能接临时 lambda；按值收 `F f` 即可 |
| 三种存法结果不同 | 无向图的三个方向没对齐：邻接表两个方向各存一次、矩阵两个位置都置位、边表只存一份但取邻居看两端 |
| 并查集漏掉按大小合并 | 树退化成链，`steps for 2000 finds` 会到百万量级 |
| 并查集漏掉路径压缩 | 同一条长路每问一次走一次，第二次不会变快 |
| 拿 `size_of` 读非根的 `size_` | 那个值是陈旧的；先 `find` 求根，再读根上的大小 |
| 图的遍历用递归写深度优先 | 链状图上递归深度等于点数，会爆栈；`traverse.hpp` 用的是显式栈 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
