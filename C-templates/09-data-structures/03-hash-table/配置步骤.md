# 配置步骤 · 09-data-structures/03-hash-table（手写哈希表）

本模板是**分阶段的整体演练**：用开放寻址（线性探测）把哈希表自己写一遍。
4 个阶段依次补上「探测」「再哈希」「墓碑式删除」「加桶时机」，
每个阶段结束时程序都能构建，并给出可对照的输出。

本模板的参考答案不给，判据就是本文件里逐字给出的输出与自查表。
复制模板、打开工程与遇到问题时的查找方式见 [`../../README.md`](../../README.md)，本文件不重复。

## 阶段 1 · 探测：三种状态各自的走法

**要做什么**（在 `include/hash_table.hpp` 里，TODO 阶段 1-1）

写 `probe(table, key, found)`：找到时返回桶号并把 `found` 置 `true`；
没找到时返回「该放进哪个桶」。要探测的表由参数给进来——再哈希要拿新表当参数，
所以不能写死用 `slots_`。读桶请用已经给好的 `at(table, i)`，它顺便记探测步数。

| 遇到 | 查找时 | 插入时 |
|---|---|---|
| 空（`Empty`） | 停下，后面不可能有 | 可以放这里 |
| 占用（`Occupied`） | 比较键，相等就是找到 | 不能放 |
| **墓碑（`Tombstone`）** | **继续往后找** | 不能放 |

**验收标准**

`Text`

```text
=== Stage 1: probe, three states ===
inserted                : 5
check                   : ok
buckets                 : 8
find 30                 : hit, value 300
find 999                : miss
string key "alpha"      : hit, value 7
```

插进去的是键 0、10、20、30、40，值分别是键的十倍；
`find 30` 命中并给出 300，没插过的 999 落空。
最后一行换成字符串键，说明探测与键的类型无关。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `check : occupied slots differ from size()` | 每次都写在同一个桶上（占位实现就是这样）；起点算错了，或者没有往后挪 |
| 所有查找都 `miss` | 只写了「往后挪」而没有比较键，或者比较用错了相等的判断 |
| `find 999` 命中 | 找到空位时没有停下，把空桶里的默认值当成了结果 |
| 程序卡死 | 探测没有绕回 0 号桶（`i = i + 1` 一直加到越界），或者桶数为 0 时取了余 |
| 插入 8 个以上就失败 | 一圈走完都没有空位，而阶段 4 的加桶还没做——这是正常的，见阶段 4 |

> [!IMPORTANT]
> **墓碑这一支现在就要写上。** 它只影响「删过元素之后」的行为，
> 因此要到阶段 3 才看得出来，但分支本身长在探测里。

## 阶段 2 · 再哈希：换一张表，重新放一遍

**要做什么**（TODO 阶段 2-1）

`rehash(new_count)`：建一张 `new_count` 个空桶的新表，把每个**占用**的桶按新桶数
重新探测一次放进去，然后换过来。墓碑不搬，`tombstones_` 归零——这就是「定期重整」。

**验收标准**

`Text`

```text
=== Stage 2: rehash rebuilds the table ===
before rehash, buckets  : 8
before rehash, size     : 5
after rehash, buckets   : 16
after rehash, size      : 5
after rehash, check     : ok
keys found after rehash : 5
```

`实测数据`
`Text`

```text
g++ 16.2.0，本机：
  显式 rehash(16)：桶数 8 → 16，5 个键全部仍然找得到
  阶段 3 做完之后再跑：erase 留下的 1 个墓碑在 rehash 之后归零
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `after rehash, buckets : 8` | 占位实现还在，什么都没做 |
| 桶数变了但 `keys found` 少了 | 放元素时用的还是旧表（或者起点仍按旧桶数取余）；探测要把新表当参数传进去 |
| `check` 报不一致 | 只换了桶数组，`size_` 或 `tombstones_` 没跟上 |
| 墓碑数不减 | 把墓碑也搬了过去；墓碑不搬，重整就是清掉它们的机会 |
| 元素被搬坏了 | 搬的是键与值，不是节点本身；本模板的桶里直接放键值，赋值即可 |

> [!TIP]
> **再哈希的代价是 `O(n)`**，摊到每次插入上是常数——这就是「平均 `O(1)`」里
> 那个「平均」的根据。知道要放多少个键时先预留，省下的不是一次搬移，
> 而是十几次「全部元素重算哈希」。

## 阶段 3 · 删除：置墓碑，不是清空

**要做什么**（TODO 阶段 3-1）

`erase(key)`：找到就把它那个桶标成墓碑、元素个数减一、墓碑数加一；找不到返回 `false`。

**验收标准**

`Text`

```text
=== Stage 3: erase leaves a tombstone ===
two keys in one bucket  : 2 and 4
erase the earlier key   : 1
after erase, size       : 1
after erase, tombstones : 1
after erase, check      : ok
find the later key      : hit, value 400
erase it a second time  : 0
tombstones after rehash : 0
```

验收程序先找出**两个落在同一个桶上**的键（本机是 2 与 4），
先插后一个、再插前一个，于是后一个的探测要经过前一个的槽位。
删掉前一个之后，后一个**仍然找得到**——这就是墓碑存在的全部理由。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `erase the earlier key : 0` | 没有真正删（占位实现就是这样），或者探测没找到它 |
| `tombstones : 0` 而 `size` 减了 | 标成了空位而不是墓碑：**下一个测试就是它** |
| `find the later key : miss` | 最典型的一处：删除标成了空位，探测提前停下。改标墓碑即可 |
| `check` 报墓碑数不符 | `tombstones_` 没有跟着加，或者加在了别处 |
| 重复删返回 1 | 第二次探测竟然又找到了：第一次删的时候只减了计数、没改状态 |
| `tombstones after rehash` 不是 0 | 阶段 2 的再哈希把墓碑也搬了过去 |

> [!CAUTION]
> **墓碑是开放寻址最容易漏的一环。** 直接把删除的位置标成「空」，
> 会让「找得到」变成「找不到」，而且只在删过元素之后才复现，
> 测试里很容易漏掉。墓碑越积越多还会让查找变慢，因此表要定期重整。

## 阶段 4 · 加桶的时机

**要做什么**（TODO 阶段 4-1）

在插入**之前**判断「插进去会不会超过上限」，超了就翻倍加桶。
判断里要把墓碑也算进去：`size_ + tombstones_ + 1` 才是这次插入之后一共要占的桶数。
限额已经给定：`kMaxLoadFactor` 是 0.7。

**验收标准**

`Text`

```text
=== Stage 4: when to add buckets ===
inserted                : 200
bucket sequence         : [8 16 32 64 128 256 512]
bucket changes          : 6
buckets                 : 512
load factor             : 0.3906
check                   : ok
200 lookups, default hash: 200 hits, 262 probe steps
200 lookups, all-zero hash: 200 hits, 20100 probe steps
longest cluster, default: 7
longest cluster, all-zero: 200
```

前七行是加桶时机：200 个键、6 次加桶，负载因子始终不超过 0.7。

后四行是同一个容器、同一批键、同一批查找，**只换哈希函数**：

`实测数据`
`Text`

```text
g++ 16.2.0，本机，200 个键、200 次查找：
  默认哈希    262 步探测，最长的一段连续非空桶 7
  全零哈希    20100 步探测，最长的一段连续非空桶 200

同一份数据、同一个容器、同一个查找语句，只换哈希函数，探测步数差 76 倍。
```

全零哈希的每个键都算成 0，于是所有元素挤在一段里，退化成一次线性扫描。
这正是《09-高阶数据结构/B-03-手写：哈希表.md》第 5.2 小节那张表的缩小版。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `inserted : 8`、`buckets : 8`、`load factor : 1.0000` | 占位实现从不加桶：表满了以后 `insert` 只能返回 `false` |
| `bucket sequence` 有几百项 | 写成了「每次加一格」；加桶是 `O(n)` 的重排，不能每次都来一遍 |
| `bucket changes` 远大于 6 | 倍数太小。差一点没关系（判据是量级），但翻倍是最简单的取法 |
| `load factor` 超过 0.7 | 判断写在了插入之后，或者忘了算墓碑 |
| `200 lookups, default hash` 的步数接近 all-zero | 哈希函数退化了；检查 `DefaultHash<int>` 有没有被改动 |
| `longest cluster` 一直等于桶数 | 所有键落在一段里，同上 |

> [!IMPORTANT]
> **哈希表快不快，一半看哈希函数，一半看加桶时机。**
> 实测里换一个坏哈希就慢了几十倍；而桶数不涨，链会越挂越长，退化成链表。

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| 编译报 `hash_` 不能调用 | `probe` 是 `const` 成员函数，哈希函数对象的 `operator()` 也要是 `const`（本模板已经是） |
| 编译报 `Slot` 没有默认构造 | 桶里的 `K key{}` 要求键可默认构造；本模板用 `int` 与 `std::string`，都满足 |
| 运行时报除零 | 桶数为 0 时取了余。`probe` 里要单独处理空表 |
| 插入一批键之后有元素找不到 | 探测没有绕回 0 号桶，或者删除标成了空位 |
| `probe steps` 一直是 0 | 探测里直接写了 `table[i]` 而不是用 `at(table, i)`，步数没被记上 |
| 换成自己的哈希函数后结果全变 | 哈希与判等必须成对（见《09-高阶数据结构/B-03-手写：哈希表.md》第 5.1 小节）：换成大小写不敏感的哈希，判等也要跟着改 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
