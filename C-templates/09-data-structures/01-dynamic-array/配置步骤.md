# 配置步骤 · 09-data-structures/01-dynamic-array（手写动态数组）

本模板是**分阶段的整体演练**：把 `vector` 那块连续内存自己管一遍。
5 个阶段依次补上「容量够时的追加」「扩容的收尾」「搬迁」「扩容策略」「异常安全」，
每个阶段结束时程序都能构建，并给出可对照的输出。

本模板的参考答案不给，判据就是本文件里逐字给出的输出与自查表。
复制模板、打开工程与遇到问题时的查找方式见 [`../../README.md`](../../README.md)，本文件不重复。

## 阶段 1 · 容量够时的追加

**要做什么**（在 `include/dynarray.hpp` 里，TODO 阶段 1-1）

`end_` 与 `cap_` 之间是**未构造的原始内存**。容量够的时候，把新元素放在 `end_` 指着的那一格上，
构造成功再让 `end_` 前进一格。

**验收标准**

`Text`

```text
=== Stage 1: append while capacity lasts ===
size = 4   capacity = 4   grow_calls = 0
values          : [1 2 3 4]
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `size = 2`，内容还是 `[1 2]` | 占位实现还在，函数体里什么都没做 |
| `size = 4` 但内容是 `[1 2 0 0]` | 只把 `end_` 前移了，没有在那一格上构造对象 |
| 程序在这两行之前就崩溃 | `end_` 前移写在了构造之前，或者写成了对未构造内存赋值 |
| `grow_calls` 不是 0 | 走到了扩容路径，检查 `push_back` 里的判断条件是不是 `end_ != cap_` |

> [!TIP]
> 构造与移动的顺序可以这样记：**先在新格子上构造对象，再让指针指向它**。
> 顺序反过来，下一次追加就会把上一个「还没有对象」的格子当成对象用。

## 阶段 2 · 扩容的收尾

**要做什么**（TODO 阶段 2-1）

新缓冲区已经备好、元素也已经搬完（由阶段 3 完成），现在做四件事，顺序不能换：

1. 把这一次要加的元素放进新缓冲区；
2. 改 `begin_`、`end_`、`cap_`；
3. 逐个析构旧缓冲区里的元素；
4. 按**旧的容量**把旧缓冲区还回去。

**验收标准**

`Text`

```text
=== Stage 2: finish the grow ===
size            : 8
capacity        : 8
grow_calls      : 8
relocations     : 8
allocs          : 8
deallocs        : 8
values          : [0 0 0 0 0 0 0 70]
```

`values` 这一行里只有最后一个是这次加进去的，前七个都是 0——**这是对的**：
搬迁（阶段 3）还没做，元素的值在扩容时丢掉了。阶段 3 做完之后这一行会变成
`[0 10 20 30 40 50 60 70]`。

`grow_calls = 8` 也是本阶段应有的样子：扩容策略（阶段 4）还没做，占位实现每次只加一格，
因此 8 次追加扩容 8 次。阶段 4 做完之后这两个数都会下降。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `size` 还是 0 | 占位实现还在，三个指针没有换过 |
| `deallocs` 是 0 | 旧缓冲区没有还回去；每次扩容漏一块内存 |
| `deallocs` 比 `allocs` 少很多 | 同上，只是漏得少一些 |
| 程序在后面的阶段里读到乱码或崩溃 | 旧缓冲区与新缓冲区写反了：先改了指针，又按新指针去释放，等于把正在用的那块内存还了回去 |
| `capacity` 是 0 而 `size` 是 8 | 指针换了但 `cap_` 没跟着换，容量算错 |

> [!CAUTION]
> **必须「全部搬完之后」才改三个指针。** 指针一改，旧缓冲区就再也找不到了：
> 它上面还留着旧元素没析构、内存没归还，而这些地址只存在于刚覆盖掉的那两个变量里。

## 阶段 3 · 搬迁：拷贝还是移动

**要做什么**（TODO 阶段 3-1）

把旧缓冲区 `[begin_, end_)` 里的 `n` 个元素搬到 `fresh` 上。`fresh` 是未构造的原始内存，
因此要逐个构造。用移动还是拷贝，取决于元素的移动构造会不会抛：

| 元素的移动构造 | 搬迁方式 | 结果 |
|---|---|---|
| `noexcept` | 移动 | 快；旧元素处于「有效但未指定」的状态 |
| 可能抛异常 | **退回复制** | 慢；旧元素保持原样，阶段 5 要的强保证才有得谈 |

`std::move_if_noexcept`（`<utility>` 里）就是完成这个判断的工具。
本模板给的两个类型各占一边：`Tracked` 的移动带 `noexcept`，`SlowTracked` 不带。

**验收标准**

`Text`

```text
=== Stage 3: relocate (move or copy) ===
Tracked     : size = 8   moves = 28   copies = 8
Tracked     : values = [0 10 20 30 40 50 60 70]
SlowTracked : size = 8   moves = 0   copies = 36
SlowTracked : values = [0 10 20 30 40 50 60 70]
```

`实测数据`
`Text`

```text
g++ 16.2.0，本机，8 次 push_back：
  阶段 4 还没做（占位实现每次只加一格，一共搬了 28 个元素）：
      Tracked moves = 28、copies = 8      SlowTracked moves = 0、copies = 36
  阶段 4 做完（取 2 倍增长，一共搬了 7 个元素）：
      Tracked moves = 7、copies = 8       SlowTracked moves = 0、copies = 15

两边的 copies 里各有 8 次来自 push_back 传参时的那一次拷贝，剩下都是搬迁。
搬迁次数随扩容倍数变，因此判据是**关系**：Tracked 的 moves 大于 0，
SlowTracked 的 moves 等于 0 而 copies 更大。
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 内容是 `[0 0 0 0 0 0 0 70]` | 占位实现还在：它默认构造了 `n` 个空对象，元素原来的值全部丢失 |
| `Tracked` 那一行 `moves = 0` | 写成了无条件拷贝；`Tracked` 的移动带 `noexcept`，应当用移动 |
| `SlowTracked` 那一行 `moves` 不是 0 | 写成了无条件移动；它的移动构造没标 `noexcept`，应当退回复制 |
| `moves` 与 `copies` 与上面差几个数 | 扩容倍数与上面的不同：倍数越大，搬迁次数越少。判据是**关系**：`Tracked` 的 `moves` 大于 0，`SlowTracked` 的 `moves` 等于 0 而 `copies` 更大 |
| 编译报 `is_nothrow_move_constructible_v` 未定义 | 少了 `#include <type_traits>`；用 `std::move_if_noexcept` 则只需要 `<utility>` |

## 阶段 4 · 扩容策略

**要做什么**（TODO 阶段 4-1）

给「这一次要申请多少格」定一个策略。要求是成倍增长，并且给容量为 0 的第一次留一个下限。

**验收标准**

`Text`

```text
=== Stage 4: growth policy ===
size              : 1000
capacity          : 1024
grow_calls        : 11
relocated_elements: 1023
allocs            : 11
deallocs          : 11
sequence 0..999   : ok
```

`实测数据`
`Text`

```text
g++ 16.2.0，本机按 2 倍增长、1000 次 push_back：
  扩容 11 次（容量 1、2、4、…、1024），搬走 1023 个元素，分配与释放各 11 次

同一份程序在阶段 4 之前的占位实现（每次只加一格）：
  扩容 1000 次，搬走 499500 个元素
```

判断标准是**量级**，不是具体的数：扩容次数应当落在「十几次」，搬移总量与它同量级。
取 1.5 倍时扩容次数会多一些、搬移总量也更大，那是允许的取舍（见《09-高阶数据结构/B-01-手写：动态数组.md》第 2.2 小节）。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `grow_calls` 接近 1000，`relocated_elements` 接近 500000 | 占位实现还在：每次只加一格，搬移总量是 `n²/2` 量级 |
| `capacity = 0` 或程序卡死 | 第一次扩容的倍数算出来仍是 0，容量永远涨不起来；给一个至少 1 格的下限 |
| `grow_calls` 是 1 | 只扩容一次就够 1000 个元素，说明倍数是 1000 以上，余量过大 |
| `sequence 0..999 : wrong` | 内容与追加顺序对不上，回到阶段 3 检查搬迁 |
| `allocs` 比 `deallocs` 大 | 有缓冲区没还回去 |

> [!IMPORTANT]
> **倍数没有唯一正确答案，硬底线只有一条：必须大于 1 且成倍。**
> 定下常数之后，在代码里写一行注释说明为什么选它——这句注释是这份练习的一部分。

## 阶段 5 · 异常安全：搬到一半抛了怎么办

**要做什么**（TODO 阶段 5-1）

`relocate` 搬到一半，第 k 个元素的拷贝构造抛了。此时的状态是：

- 新缓冲区里有 `built` 个构造好的元素；
- 旧缓冲区一个都没动（用的是拷贝，不是移动）；
- 旧缓冲区还在，还是容器的家。

`catch` 里要做两件事：把新缓冲区里**已经构造好的那几个**析构掉、把新缓冲区还回去，
然后把异常继续往外抛。做完之后，容器的 `size`、`capacity`、内容与调用 `push_back` 之前完全一样。

验收程序的做法是往类型里注入一次构造失败：`tracked_set_throw_after(2)` 让第 3 次
拷贝或移动构造抛异常（前两次正常）。

**验收标准**

`Text`

```text
=== Stage 5: exception safety on grow ===
caught            : yes
content unchanged : yes
live before/after : 3 / 3
buffer returned   : yes
```

`content unchanged` 与 `live before/after` 这两行是真正的判据：
`caught = yes` 只说明有异常经过，不代表容器已经恢复原状。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `live before/after : 3 / 5` | `catch` 没有析构新缓冲区里已经构造好的元素，它们成了没有主人的对象 |
| `live before/after : 3 / 7` | 连阶段 3 也没做（占位实现默认构造了 3 个，加上新元素共 4 个） |
| `buffer returned : no` | 新缓冲区没有还回去，每次失败漏一块内存 |
| `content unchanged : no` | 搬迁用了无条件移动：抛之前已经有两个旧元素被搬空，强保证做不到。退回复制就没有这个问题 |
| `caught : no` | 搬迁一步都没走成，或者 `catch` 把异常吞掉了 |
| 编译报 `built was not declared` | `built` 声明在了 `try` 里面；`catch` 要读它，得声明在 `try` 外面 |

> [!CAUTION]
> **用移动搬迁时，「异常安全」与「性能」是冲突的。**
> 移动搬到一半抛异常，旧元素已经被搬空，强保证做不到了。
> 这正是「不抛才敢移动」那条规则的根据：想同时要性能与强保证，只能让移动构造保证不抛。

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| 编译报 `placement new` 相关错误 | 少了 `#include <new>`；放置构造的声明在那个头文件里 |
| 运行时报 `double free` 或堆损坏 | 同一个缓冲区被释放了两次，常见于「改了指针又按新指针释放」或者拷贝构造里没有接管而是共享 |
| `TrackedCounters::live` 一直是正数不归零 | 有元素没有析构。每次扩容都要把旧缓冲区里的 `n` 个元素逐个析构 |
| 换成 `SlowTracked` 之后 `-Wall` 报 `-Wexceptions` | 在 `noexcept` 函数里调用了可能抛的表达式；本模板里没有 `noexcept` 标记的搬迁函数，检查是否自行添加了一个 |
| MSVC 下中文注释导致 `C4819` | 工程的 `CMakeLists.txt` 已经给 `core` 与 `app_cli` 加了 `/utf-8` |
| `cmake --preset msvc` 找不到生成器 | 若未安装 Visual Studio 生成工具，用 MinGW 路线即可 |
