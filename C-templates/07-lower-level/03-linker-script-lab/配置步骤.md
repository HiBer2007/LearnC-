# 配置步骤 · 07-lower-level/03-linker-script-lab（链接脚本实验）

本模板是**分阶段的排错演练**：给你的链接脚本**能链接、但跑不起来**。
程序本身没有问题（启动文件是真实的，应用只打印几行字），问题都在脚本里，
一共两处。要用的工具是 `arm-none-eabi-objdump`、`objcopy` 与 QEMU：
先用段表与 `.bin` 体积找出可疑处，再用「能不能跑出输出」验证修好了没有。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

> [!IMPORTANT]
> **本模板里的 `STM32F103C8_FLASH.ld` 不是 ST 的原版文件。**
> 它保留了原始的版权头，但做了两件事：把内存容量换成本板（C8：flash 64 KiB / RAM 20 KiB），
> 并**有意留下两处缺陷**。原版脚本见 `A-教学素材/01-编译器/嵌入式/链接脚本与启动/`。

---

## 成品形态

两个阶段各修一处，修完之后：

| 能力 | 由哪一阶段提供 |
|---|---|
| 段表里能看到 `.isr_vector` 落在 `0x08000000`，QEMU 里能跑出程序的输出 | 阶段 2 |
| `.data` 的装载地址在 flash、运行地址在 RAM，`.bin` 从 384 MiB 回到 1 KB 级 | 阶段 3 |

判定「跑起来了」的标准不是「链接没报错」，而是**QEMU 里出现程序打印的七行字**。

## 第 0 步 · 构建与运行

**交叉编译路线**（在 WSL 的 Ubuntu 里执行；模板目录下直接跑脚本）

`PowerShell`

```powershell
wsl -d Ubuntu -e bash build.sh
```

脚本里做的事，逐条写全如下（`-T` 后面就是那个要修的脚本名）：

`Bash`

```bash
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -g -nostartfiles --specs=nosys.specs \
  -fdata-sections -ffunction-sections \
  -Wl,--gc-sections -Wl,-Map=build/app.map \
  -T STM32F103C8_FLASH.ld startup_stm32f103xe.s app/main.c -o build/app.elf
arm-none-eabi-objdump -h build/app.elf
arm-none-eabi-objcopy -O binary build/app.elf build/app.bin
qemu-system-arm -M netduinoplus2 -kernel build/app.elf -nographic \
  -semihosting-config enable=on,target=native
```

`-fdata-sections -ffunction-sections` 与 `-Wl,--gc-sections` 三个参数照抄 CubeMX 生成的
`gcc-arm-none-eabi.cmake`。**它们与链接脚本里的 `KEEP` 直接相关**，先弄清这三个参数做什么，
再去看脚本。

- [ ] 骨架状态（两处都没修）输出如下：段表里 `.isr_vector` 的大小是 0，
      `.bin` 有 402,653,188 字节，QEMU 里**一个字都没有打印**，直接以 Lockup 中止

> 涉及具体外设（USART、GPIO、定时器）的结论不能拿它当依据。

## 阶段 1 · 看清现象：能链接，跑不起来

**要做什么**

- 1-1 跑一遍 `build.sh`，把五段输出都看一遍（链接、段表、flash 起始内容、`.bin` 体积、QEMU）
- 1-2 在段表里找 `.isr_vector`：它的 `Size` 是 `00000000`，而 `VMA` 写着 `08000000`
- 1-3 在 `build/app.map` 里搜 `Reset_Handler`，确认代码本身**在**（问题不是没编进去）
- 1-4 用一句话写下你的判断：为什么 `0x08000000` 那里没有向量表

**验收标准**

`Text`

```text
  0 .isr_vector   00000000  08000000  08000000  00002004  2**0
                  CONTENTS
  1 .text         000001c8  08000000  08000000  00001000  2**2
                  CONTENTS, ALLOC, LOAD, READONLY, CODE
```

`.text` 的起始地址也是 `08000000`：**向量表本该占住的位置被代码顶上来了**。
再对照本文档「第 0 步」里那段 QEMU 输出，第一行程序输出都没有。

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `.isr_vector` 一行都没有 | 链接脚本里这个输出段整段被删掉了 | 补回 `.isr_vector` 输出段，再回来看大小 |
| `.isr_vector` 大小不为 0，但 QEMU 还是没输出 | 问题不在向量表：先看 `.text` 的地址是不是 `08000000`，再看别的缺陷 | 阶段 3 |
| `.bin` 只有几 KB，QEMU 也没输出 | 两处缺陷的严重程度不同，先解决「没有输出」这一处 | 阶段 2 |
| 链接就失败了，报 `region RAM overflowed` | `MEMORY` 里的容量被改得比实际代码还小 | 对照本板：flash 64 KiB、RAM 20 KiB |
| `objdump` 报 `File format not recognized` | 看的是 `.bin` 而不是 `.elf`：`objdump -h` 要作用在 `.elf` 上 | 改回 `build/app.elf` |

## 阶段 2 · 缺陷一：向量表被链接器回收

**要做什么**

- 2-1 打开 `STM32F103C8_FLASH.ld`，找到输出段 `.isr_vector`
- 2-2 想清楚一件事：启动文件里的 `.isr_vector` 段**没有任何代码引用它**，
  而链接参数里有 `-Wl,--gc-sections`；链接器凭什么保留它
- 2-3 把该加的关键字加上（只有一个：让这个段成为回收的根），重新跑 `build.sh`

**验收标准**

段表里向量表回到 flash 起始处，大小是 `0x1e4`（468 字节，与向量表项数对应）：

`Text`

```text
  0 .isr_vector   000001e4  08000000  08000000  00001000  2**0
                  CONTENTS, ALLOC, LOAD, READONLY, DATA
  1 .text         000001cc  080001e4  080001e4  000011e4  2**2
                  CONTENTS, ALLOC, LOAD, READONLY, CODE
  2 .rodata       00000110  080003b0  080003b0  000013b0  2**2
                  CONTENTS, ALLOC, LOAD, READONLY, DATA
```

flash 起始处的两个双字也对得上：`0x20005000` 是栈顶（RAM 顶端），
`0x08000235` 是复位入口（最低位为 1，表示 Thumb 态）：

`Text`

```text
Contents of section .isr_vector:
 8000000 00500020 35020008 7d020008 7d020008  .P. 5...}...}...
```

QEMU 里出现程序的输出：

`Text`

```text
linker-script-lab: Reset_Handler ran, we are in main
g_from_data = 0x1234abcd  (expect 0x1234abcd)
g_from_bss  = 0x00000000  (expect 0x00000000)
g_another_bss = 0x00000000  (expect 0x00000000)
_sidata = 0x20000000  (flash: 0x0800....)
_sdata  = 0x20000000  (RAM:   0x2000....)
_ebss   = 0x2000000c
done
qemu-system-arm: terminating on signal 15 from pid 424 (timeout)
（退出码 124：0 = 程序自己结束；124 = 超时被杀；134 = QEMU 因非法状态自己中止）
```

程序的最后一行 `done` 之后是一个 `for (;;)`，因此超时被杀（退出码 124）是正常的。

**注意 `_sidata` 那一行**：它现在是 `0x20000000`，与 `_sdata` **一样**。
`.data` 的初值本该在 flash 里，现在却说自己也在 RAM——这是第二处缺陷的现场。

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `.isr_vector` 有大小，但 QEMU 还是没输出 | 向量表被放到了别的位置：`.text` 的 VMA 不是 `080001e4` | 检查 `.isr_vector` 输出段是不是排在 `.text` 前面 |
| 第一项是 `00000000` 而不是 `20005000` | 栈顶符号 `_estack` 没算对：`ORIGIN(RAM) + LENGTH(RAM)` 两项之一被改过 | `MEMORY` 段与 `_estack` |
| 第二项最低位是 0 | 入口符号写成了数据符号，或者 `ENTRY` 那一句被改过 | 脚本开头的 `ENTRY(Reset_Handler)` |
| QEMU 打印两行就停了 | `_sidata` 与 `_sdata` 相等时拷贝是空操作；如果初值确实错了，先去阶段 3 | 阶段 3 |
| 加了关键字之后链接报语法错 | 关键字要写在 `*(.isr_vector)` 的**外面**：`KEEP(*(.isr_vector))` | 同处 |

## 阶段 3 · 缺陷二：`.data` 的装载地址

**要做什么**

- 3-1 看段表里 `.data` 的 `VMA` 与 `LMA` 两栏，再看程序打印的 `_sidata` 与 `_sdata`
- 3-2 想清楚 `_sidata = LOADADDR(.data)` 这一句的期望值：它在 flash 里，应当是 `0x0800....`
- 3-3 把 `.data` 输出段该有的那半句补上，重新跑 `build.sh`，看 `.bin` 体积的变化

**验收标准**

`.bin` 从 402,653,188 字节（384 MiB）回到 1220 字节：

`Text`

```text
=== 4. 转成烧写用的 .bin，看体积
    1220 字节
```

程序打印的两个地址分开了：装载地址在 flash，运行地址在 RAM：

`Text`

```text
_sidata = 0x080004c0  (flash: 0x0800....)
_sdata  = 0x20000000  (RAM:   0x2000....)
_ebss   = 0x2000000c
```

`.data` 里的 `g_from_data` 仍然是 `0x1234abcd`——现在这个值是 `Reset_Handler`
**从 flash 搬进 RAM** 的，而不是「碰巧早就在 RAM 里」。

`实测数据`
`Text`

```text
同一份源码，两处缺陷各修一步之后的三个数字：

  只修向量表      .bin = 402,653,188 字节    _sidata = 0x20000000   程序能跑，输出齐全
  两处都修好      .bin = 1,220 字节          _sidata = 0x080004c0   程序能跑，输出齐全
```

**为什么差这么多字节**：少了 `AT>`，`.data` 的 LMA 与 VMA 相同，都在 `0x20000000`；
`objcopy -O binary` 会从 `0x08000000` 一路填到 `0x20000000` 再往后，
中间那 384 MiB 的空洞全部变成 0 填进文件。这样的 `.bin` 既没法烧，也没有意义。

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `.bin` 还是 402,653,188 字节 | `.data` 输出段结尾没有那半句，或者写到 `.tdata` 上了 | `.data` 的 `} >RAM` 后面 |
| `.bin` 变成几 MB，不是 1 KB 级 | 还有别的段把 LMA 放在了 RAM | 逐个看段表的 `LMA` 栏，凡在 `0x2000....` 的都要查 |
| `_sidata` 是 `0x080004c0` 但程序跑不起来 | 向量表那一处又坏了：回去阶段 2 | 阶段 2 |
| 程序打印的 `g_from_data` 不是 `0x1234abcd` | `Reset_Handler` 的拷贝被跳过，或者 `_sidata` 指错 | 对照《07-更底层/07-链接脚本与启动代码.md》第 3.3 小节 |
| `.bin` 体积正常但烧进板子不跑 | 烧写地址不对：`.bin` 要从 `0x08000000` 烧起 | 见《01-编译器/03-嵌入式与交叉编译.md》章节 |

> [!WARNING]
> **`AT>` 只说了一件事：这个段的初值放在哪个地址。**
> 少了它，链接器会把「运行地址」当成「装载地址」，链接不报错、QEMU 里甚至能跑
> （因为 ELF 装载器把数据段直接放进了 RAM），**只有在烧写与真板上才暴露**。
> 这一类缺陷靠「跑一次」是发现不了的，要看段表的 `LMA` 栏。

## 阶段 4 · 五个符号与真板对照（可选）

**要做什么**

- 4-1 用 `arm-none-eabi-nm` 找出链接脚本定义的那几个符号，与程序打印的值对上：
  `_sidata`、`_sdata`、`_edata`、`_sbss`、`_ebss`
- 4-2 把 `MEMORY` 里 RAM 的 `LENGTH` 改成 `48K`（素材里那份 F103xC 脚本的值），
  重新编译并运行 QEMU，看现象；再改回 `20K`
- 4-3 有板子的话，走下面的真板路径，把同一份 `.elf` 烧进去复测

**验收标准**

`Text`

```text
$ arm-none-eabi-nm build/app.elf | grep -E "_sidata|_sdata|_edata|_sbss|_ebss"
2000000c B _ebss
20000004 D _edata
20000004 B _sbss
20000000 D _sdata
080004c0 A _sidata
```

`_sidata` 的类型是 `A`（absolute，表示它只是一个算出来的常数，不属于任何段），
`_sdata`/`_edata` 是 `D`（在 `.data` 里），`_sbss`/`_ebss` 是 `B`（在 `.bss` 里）。
**`_sidata` 在 `0x0800....`、`_sdata` 在 `0x2000....`**，两者分属 flash 与 RAM，
这就是 `AT>` 那一句的成果。

`LENGTH` 改成 `48K` 之后：栈顶从 `0x20005000` 变成 `0x2000C000`，
**超出了这块板子的 20 KiB RAM**。QEMU 的 `netduinoplus2` 有 128 KiB RAM，
因此它这里跑得起来；真板上则是复位后立刻 HardFault。

`实测数据`
`Text`

```text
真板（STM32F103C8，RAM 20 KiB）上把 RAM 长度照抄成 48K：

  用错脚本（48K）    _estack = 0x2000C000（超出 20 KiB RAM）
                     复位后 current mode: Handler HardFault，pc = 0x08000314
                     第一次压栈就越界，任何测试都跑不起来
  改成 20K           _estack = 0x20005000，.data / .bss 检查全部通过
```

数据来自真板，完整现场见《07-更底层/07-链接脚本与启动代码.md》第 5.5 小节。

**真板路径（可选，需要开发板与调试器）**

`PowerShell`

```powershell
& "<OpenOCD>\bin\openocd.exe" -s "<OpenOCD>\share\openocd\scripts" `
  -f interface/cmsis-dap.cfg -f target/stm32f1x.cfg `
  -c "init" -c "reset halt" -c "arm semihosting enable" `
  -c "flash write_image erase C:/path/build/app.elf" -c "reset run" -c "sleep 2000" -c "halt" `
  -c "shutdown"
```

程序里的打印走 semihosting，`arm semihosting enable` 之后 OpenOCD 会把输出打在自己的控制台上。

> [!CAUTION]
> **只用 `flash write_image erase` 写 flash 主区。** 不要执行 mass erase，
> 不要碰 option bytes，也不要去改读保护位——那几项一旦写错，
> 芯片会读不出来，需要用调试器专门解锁。

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `nm` 里找不到 `_sidata` | 那一句 `_sidata = LOADADDR(.data);` 被删了 | 补回到 `.data` 输出段之前 |
| `_edata` 与 `_sdata` 相等 | `.data` 里没有任何带初值的对象：程序被优化掉了，或者全局变量都成了 `const` | 看 `app/main.c` 里的两个全局量 |
| 真板上复位后进 HardFault | 先怀疑内存容量：`_estack` 是否超过 RAM 顶端 | `MEMORY` 里的 `LENGTH` |
| 真板上打印不出字 | semihosting 需要调试器开着 `arm semihosting enable`；最小板上没有串口 | 上面那条 OpenOCD 命令 |
| 改回 20K 之后 `region RAM overflowed` | 代码与数据加起来超过 20 KiB：把 `.bin` 体积与 `size` 的输出对照一下 | 减代码或换板子 |

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| QEMU 报 `unsupported machine type` | 机型名写错：本模板用 `netduinoplus2` |
| QEMU 报 `Lockup: can't escalate 3 to HardFault` | 复位向量无效（向量表被回收或被挤走）。不是程序逻辑问题，先看段表 |
| `region FLASH overflowed` / `region RAM overflowed` | `MEMORY` 里的容量与实际不符（本板：flash 64 KiB、RAM 20 KiB） |
| `.bin` 体积是几百 MB | 某个段的 LMA 落在了 RAM 段里：检查每个输出段结尾的 `AT>` |
| `arm-none-eabi-gcc: command not found` | 交叉工具链没装或不在 `PATH` 里；装法见《01-编译器/03-嵌入式与交叉编译.md》章节 |
| 段表里 `.ARM.extab` 大小为 0 是正常的 | 这个工程没有异常展开表（C 代码、`nosys` 规格），空段不影响 |
| `objcopy` 报 `Unable to recognise the format` | 输入给成了 `.bin`；`objcopy` 的输入必须是 `.elf` |
| 改了脚本但输出没变 | 构建目录里的旧产物还在：删掉 `build/` 再跑一遍 |

## 完成后可做的延伸
