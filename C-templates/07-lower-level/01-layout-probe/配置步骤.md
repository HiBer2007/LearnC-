# 配置步骤 · 07-lower-level/01-layout-probe（布局探针）

本模板是**分阶段的整体演练**：成品是一个命令行程序，把「一个对象落在哪一段」与
「一个结构体在内存里怎么摆」这两件事打印出来，再用两次运行的对照说明
哪些地址是链接期定死的、哪些是加载期给的。整个模板只有 C 源码，不涉及界面。
怎么复制模板、怎么打开、遇到问题查哪里，见 [`../../README.md`](../../README.md)，本文件不重复。

---

## 成品形态

做完这 4 个阶段之后，`app_cli.exe` 具备下面这些能力：

| 能力 | 由哪一阶段提供 |
|---|---|
| 报出六类对象（代码、只读数据、有初值数据、无初值数据、栈、堆）的地址 | 阶段 1 |
| 算出段与段的间距，并说明哪些数字两次运行不变 | 阶段 2 |
| 报出三种排布的结构体的大小、对齐与成员偏移 | 阶段 3 |
| 用一组自检确认对齐规则真的成立，并读一次非对齐的字 | 阶段 4 |

## 阶段 1 · 六类对象的地址

**要做什么**（都在 `src/layout_probe.c`）

- 1-1 `lp_probe_addresses`：给 7 个探测点填上 `name`、`kind`、`addr` 三栏。
  顺序照素材来：`lp_code_anchor`（text）、`lp_g_rodata` 与 `lp_g_msg`（rodata）、
  `lp_g_data`（data）、`lp_g_bss`（bss），再在函数内部现取一个自动变量（stack）
  与一次 `malloc` 的返回值（heap）。填满 7 条返回 7；容量不够返回 -1

**验收标准**

`Text`

```text
=== Stage 1: object addresses ===
  name           kind     address
  lp_code_anchor text     0x00007ff637d621b0
  lp_g_rodata    rodata   0x00007ff637d6b470
  lp_g_msg       rodata   0x00007ff637d6b478
  lp_g_data      data     0x00007ff637d6a000
  lp_g_bss       bss      0x00007ff637d6e030
  local          stack    0x00000052ea9ff5cc
  malloc         heap     0x000001d3fc372480
```

地址本身每次运行都会变（栈与堆每次都不同，模块基址也可能变），
**要核对的是「哪个名字落在哪个段」**。

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `returned -1` | 占位实现还在，函数里没有任何 `out[n] = ...` | `src/layout_probe.c` 的 1-1 |
| 只报出 5 条，缺栈与堆 | 只填了素材里的全局对象，忘了在函数内部取自动变量与 `malloc` 的地址 | 同上，栈用 `&局部变量`，堆用 `malloc` 的返回值 |
| 堆那一条每次都是 `0x0000000000000000` | `malloc` 失败时没有处理，或者把 `malloc` 的返回值当成 `int` 存了 | 用 `uintptr_t` 接地址 |
| `lp_g_rodata` 与 `lp_g_data` 的段名写反 | 段名是照着直觉填的；要用 `const` 与初始化判断，报告要真实 | 对照《07-更底层/01-对象在哪里：栈、堆与静态区.md》第 1.1 小节 |
| 编译报 `cast to pointer from integer of different size` | 把地址存进了 `int` 或 `unsigned` | 结构体里那一栏是 `uintptr_t` |

把程序打印的地址与 `nm` 的映像内偏移对上，是这个阶段真正的收获：

`实测数据`
`Text`

```text
$ size build/mingw/bin/app_cli.exe
   text    data     bss     dec     hex filename
  41568     288    2976   44832    af20 build/mingw/bin/app_cli.exe

$ nm build/mingw/bin/app_cli.exe | findstr "lp_g_ lp_code_anchor"
00000001400021b0 T lp_code_anchor
000000014000e030 B lp_g_bss
000000014000a000 D lp_g_data
000000014000b478 R lp_g_msg
000000014000b470 R lp_g_rodata
```

`T` 是代码段、`R` 是只读数据、`D` 是有初值数据、`B` 是无初值数据，
小写字母表示内部链接。`nm` 里的地址是**映像内偏移**，
程序打印的是**运行地址**，两者相差一个加载基址（这一段实测里是 `0x7ff6...` 减去 `0x140000000`）。

## 阶段 2 · 段间距与两次运行的差别

**要做什么**

- 2-1 `lp_section_gap`：在已经采到的样本里找第一段名等于 `from`、`to` 的两条，
  返回两者地址之差。段名用 `strcmp` 比，任一段找不到返回 0
- 2-2 `lp_address_delta`：返回两个地址的距离。实参可能是两个互不相关的对象，
  先转 `uintptr_t` 再相减

**验收标准**

`Text`

```text
=== Stage 2: section gaps ===
  text     -> rodata   : +37568
  rodata   -> data     : -5232
  data     -> bss      : +16432
  bss      -> heap     : -1000324016
  delta(bss, data) = +16432
  delta(text, data) = -32336
```

`bss -> heap` 这一项**没有意义**：堆是另一块内存区，与映像里的段不在同一段地址空间。
那一条留着是为了看一个现象——只要两栏都有值，函数就会算出一个数，它不保证这个数有意义。

**两次运行的对照**（同一份产物，连着跑两次）

`实测数据`
`Text`

```text
                第一次                          第二次
lp_code_anchor  0x00007ff637d621b0  text        0x00007ff637d621b0  text
lp_g_rodata     0x00007ff637d6b470  rodata      0x00007ff637d6b470  rodata
lp_g_data       0x00007ff637d6a000  data        0x00007ff637d6a000  data
lp_g_bss        0x00007ff637d6e030  bss         0x00007ff637d6e030  bss
local           0x00000052ea9ff5cc  stack       0x00000073aadff8fc  stack
malloc          0x000001d3fc372480  heap        0x0000024e4cf22480  heap

段间距（两次相同）：
  text -> rodata : +37568     rodata -> data : -5232     data -> bss : +16432
```

`text`、`rodata`、`data`、`bss` 两次一模一样，`stack` 与 `heap` 每次都变，
而**段与段的距离两次相同**。这三句话就是这个阶段的结论。

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| 间距全是 0 | 阶段 1 没做完（样本是空的），或者段名拼错了大小写 | 先回阶段 1；段名是小写的 `text`/`rodata`/`data`/`bss` |
| `text -> rodata` 是负数、`data -> bss` 也是负数 | 用指针直接相减，而不是先转 `uintptr_t` | 2-2 |
| 换个构建类型（Debug 换 Release）后间距变了 | 正常：优化改了代码大小，段的位置跟着动 | 不用改 |
| `delta(bss, data)` 与 `data -> bss` 对不上 | 一个用的是段里第一条样本，一个用的是指定对象 | 不用改，两处口径本来就不同 |
| 加了 `-O2` 之后 `stack` 那一条不见了 | 优化把那个自动变量放进了寄存器，`&local` 仍应有效 | 1-1 里给变量加 `volatile` 再看 |

## 阶段 3 · 三种排布的结构体

**要做什么**（都在 `src/shapes.c`）

- 3-1 `lp_describe_shapes`：把 `LpPlain`、`LpPacked`、`LpAligned` 三种排布各填一条，
  返回 3。大小用 `sizeof`、对齐用 `_Alignof`、偏移用 `offsetof`。
  `LpAligned` 没有那四个成员，四个偏移栏填 `(size_t)-1`（驱动会打印成 `--`）

**验收标准**

`Text`

```text
=== Stage 3: struct layout ===
  name        size  align    tag  value  flags   kind
  LpPlain       12      4      0      4      8     10
  LpPacked       8      1      0      1      5      7
  LpAligned     32     16     --     --     --     --
```

`实测数据`
`Text`

```text
LpPlain    自然对齐：tag 0、填充 3 字节、value 4、flags 8、kind 10、尾部再填 1 → 12
LpPacked   紧凑排布：tag 0、value 1、flags 5、kind 7 → 大小 8（省 4 字节）
LpAligned  整体 16 对齐：block 0 到 15、tail 16、尾部填到 32 → 大小 32
```

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| `LpPlain` 的 `value` 偏移写成 1 | 照着 `LpPacked` 填的：`LpPlain` 里 `uint32_t` 要对齐到 4 | 3-1，用 `offsetof` 取，不要手写 |
| `LpPlain` 大小写成 11 | 漏了尾部填充：结构体大小要对齐到它的对齐值 | 3-1 |
| `LpPacked` 大小写成 12 | `#pragma pack(push, 1)` 没生效：头文件里的 `push`/`pop` 被改过 | 不要改 `include/shapes.h` |
| `LpAligned` 的对齐是 8 而不是 16 | `_Alignas(16)` 写成了 `_Alignas(8)`，或者改用了 `#pragma pack` 包裹 | 3-1，读一遍 `include/shapes.h` |
| 编译报 `offsetof` 未定义 | 少了 `#include <stddef.h>`（`layout_probe.h` 里有，自己新建文件时要带上） | `src/shapes.c` 的包含区 |

> [!WARNING]
> **紧凑排布不是免费的。** 省下的是内存，付出的是访问代价：
> 在 Cortex-M3 上实测，`packed` 结构体字段的一次访问是 10 个周期，
> 而自然对齐的 32 位访问是 8 个周期；如果落成逐字节拼接则是 18 个周期。
> 那一组数字与原因见《07-更底层/02-对齐、填充与缓存.md》第 1.2 小节与第 2.3 小节。

## 阶段 4 · 对齐自检

**要做什么**

- 4-1 `lp_align_check`：把三项自检的结果写进 `buf`，返回写出的字符数。
  三项分别是：一个 `LpAligned` 局部变量的地址对 16 取余是不是 0；
  一个 `uint32_t` 局部变量的地址对 4 取余是不是 0；
  从一个**非对齐**地址（`raw + 1`）读一个 `uint32_t`，与对齐读比较是否一致。
  最后写一行统计。格式照抄下面的验收标准，三行内容与统计必须一致

**验收标准**

`Text`

```text
=== Stage 4: alignment self-check ===
align  : LpAligned 局部变量 地址 % 16 = 0
align  : uint32_t 局部变量 地址 % 4 = 0
read   : raw+1 读到 0x11223344，与对齐读一致
check  : 3 项通过，0 项失败
```

**怎么自查**

| 你看到的 | 说明 | 改哪里 |
|---|---|---|
| 只有 `(TODO 4-1: ...)` 一行 | 占位实现还在 | `src/shapes.c` 的 4-1 |
| `LpAligned 局部变量 地址 % 16 = 8` | 局部变量没有被过对齐：把它声明成了别的类型，或者用的是 `malloc` 拿的内存 | 声明成 `LpAligned` 类型的局部变量 |
| `raw+1` 读到 `0x22334400` 一类错位的值 | 搬字节时用了 `memcpy` 之外的写法，或者源地址也错了 | 用 `memcpy` 搬进 `raw + 1`，再用 `memcpy` 读回来 |
| 最后一行是 `3 项通过，0 项失败` 但前面有 `不一致` | 统计那一段的计数写反了 | 4-1 的计数逻辑 |
| 程序在 `raw+1` 那一句崩溃 | 把 `unsigned char *` 强转成 `uint32_t *` 再解引用，且地址没有对齐 | 用 `memcpy` 读写，别用强制转换 |

> [!IMPORTANT]
> **在 x86-64 上，非对齐的 32 位访问不报错**，这一项自检在本机一定通过。
> 换到别的架构上未必：Cortex-M3 允许单字非对齐访问，但 `LDM`/`STM` 这类多字访问要求对齐；
> 有些架构会直接触发异常。**报「通过」不等于这段代码可以移植**，
> 它只说明在本机这条路径上硬件没有拦住。硬件这一层的完整讲法见
> 《07-更底层/02-对齐、填充与缓存.md》第 1 节。

## 常见错误与排查

| 现象 | 原因与做法 |
|---|---|
| `cmake --preset msvc` 报 `Compatibility with CMake < 3.5 has been removed` | 预设文件被改过。本模板的 `CMakePresets.json` 里 `cmakeMinimumRequired` 是 3.21 |
| 编译报 `expected specifier-qualifier-list before 'alignas'` | 在 C17 模式下 `alignas` 只是 `<stdalign.h>` 里的宏，不是关键字。本模板用的是 `_Alignas`，C23 起才可以直接写 `alignas` |
| 打印地址时 MSVC 报 `/W4` 警告 C4311（指针截断） | 用了 `%p` 之外的格式，或把 64 位指针塞进 `int`。统一用 `uintptr_t` 接地址、`%016llx` 打印 |
| `warning: cast from pointer to integer of different size` | 同上，用 `uintptr_t` |
| 两次运行所有地址都一样 | 系统关掉了 ASLR，或者程序被固定基址加载。此时栈与堆仍应变化；若真的都不变，把观察点放在「段间距不变」这一条上 |
