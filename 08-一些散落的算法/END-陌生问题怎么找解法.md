前面十几章讲的都是「已知这类问题，该用哪个解法」。真实的情形常常反过来：
先拿到一段需求，读完之后不知道它属于哪一类，也不知道该翻哪一章。

这一章给的就是这个动作的顺序：**先分类、再降规模、再找相似结构。**
三步里没有一步需要灵感，都是可以按着做的。
分类回答「这是找、是排、是判、还是构造」；降规模把「一次处理全部」换成「一次只看一个」，
用它逼出两样东西——**状态是什么、子问题重不重复**；找相似结构是翻一张按问题特征排的表。

最后一步是收口：什么时候该停手，不要自己写。
这一条与「怎么找解法」是一体两面——**多数陌生问题已经有现成答案，
判断它属于哪一类，有一半的目的正是为了找到那个现成答案在哪。**

# 第 E.1 节 先分类

## E.1.1 四类问题

拿到一段需求，先把它归到四类里的一类。分类的依据不是「答案是什么形式」，
而是**问题要求你交出什么**。

| 类 | 要求交出什么 | 典型的问法 | 解法从哪里来 |
|---|---|---|---|
| **找** | 一个或一组满足条件的对象 | 在不在、第几个、最大的是哪个、满足条件的有几个 | 顺序扫描、二分、哈希、堆 |
| **排** | 一个次序 | 按什么顺序输出、谁排在前面 | 比较排序、不比较的排序 |
| **判** | 是或否，或者一个划分 | 有没有环、通不通、能不能拆成两块 | 图上的结构算法、并查集、拓扑排序 |
| **构造** | 一个完整的答案对象 | 给出一种方案、给出最短的那条、给出一个排列 | 贪心、动态规划、搜索、回溯 |

四类的解法族差别很大，分类错了后面全错。最容易混的是「找」与「判」：

| 需求里的话 | 是哪一类 | 为什么 |
|---|---|---|
| 「这两个点之间有没有路」 | **判** | 只要求是或否，不要求给出路径 |
| 「这两个点之间最短的路是哪条」 | **找**（找一条路径） | 要交出路径本身 |
| 「这张图里有没有环」 | **判** | 是或否 |
| 「把这张图排成一个没有环的次序」 | **构造** | 要交出一个次序 |
| 「所有任务能不能排完」 | **判** | 是或否，等价于问有没有环 |
| 「给出一个可行的排法」 | **构造** | 要交出一个次序 |

上面三组对照指向同一个结论：**同一个场景，问法差一个词，解法就换一族。**
判往往比找便宜——只要一个划分、不要路径，可以丢掉大量信息，
这正是《09-高阶数据结构/A-12-不相交集合：只要连通性.md》第 1 节讲的那条界线。

## E.1.2 分类之后立刻问的三个问题

| 问题 | 它决定什么 |
|---|---|
| **要交出的答案是「一个」还是「全部」** | 「一个」往往能用贪心或一次扫描；「全部」通常要枚举或计数 |
| **答案要不要可解释**（要不要给出路径、过程、依据） | 要，就不能丢掉中间信息；不要，就可以只留结论 |
| **有没有「最优」这个字** | 有最优，就要问「局部最优能不能推出全局最优」（贪心）或「有没有最优子结构」（动态规划） |

第三个问题最容易被跳过。需求里出现「最少」「最短」「最大」时，
先不要想算法，先问一句：**每一步都取当下最好的，最后会不会就是最好的？**
会，就是贪心；不会，就要看子问题重不重复。

## E.1.3 一句问法

分类可以压缩成一句话：**「我最后要交出去的那个东西，是一个数、一个次序、一个划分，还是一个对象？」**

- 一个数（在不在、有几个、最短多长）→ 找或判，多半可以用计数、二分、一次扫描；
- 一个次序 → 排，先问数据长什么样，再选比较排序还是不比较的排序；
- 一个划分 → 判，图上那几种结构算法多半直接可用；
- 一个对象（一条路径、一种方案、一个排列）→ 构造，走贪心、动态规划或搜索。

# 第 E.2 节 再降规模

## E.2.1 降到 1 个、2 个、3 个

分类之后仍然想不出解法时，把规模降下来手算一遍。降规模不是比喻，是真的把输入写小：

| 降到 | 做什么 | 能看到什么 |
|---|---|---|
| 1 个元素 | 答案是什么，边界在哪 | 基线条件（递归的出口往往就在这里） |
| 2 个元素 | 两个元素之间要不要比较、按什么比较 | 比较的依据是什么 |
| 3 个元素 | 多出来的第三个元素怎么并进去 | 递推的方向：是并入、是分半、还是重新开始 |
| 加一个「什么都不选」的选项 | 空输入、零代价 | 状态里要不要有「还没开始」这一档 |

第三行是关键。从 2 个到 3 个的那一步，往往就是整个解法：
如果第三个元素只是「并到已有的答案上」，那是一个递推；
如果它要求「把前两个的答案合起来」，那是分治；
如果它要求「在前面所有位置里挑一个最好的接上去」，那是动态规划。

## E.2.2 降规模暴露的两件事

**第一件是状态。** 手算时你会发现自己在纸上记着一些东西：
前面见过的最小值、上一个位置的下标、当前攒了多少。
**纸上记着的东西，就是解法里的状态。**

| 手算时纸上记的 | 状态是什么 | 解法往哪走 |
|---|---|---|
| 只记「当前这个」 | 一个变量 | 一次扫描 |
| 记「到目前为止的最优」 | 一个变量，但要定义清楚「到目前为止」 | 贪心 |
| 记「每个位置各自的最优」 | 一张表 | 动态规划 |
| 记「还没配对的那些」 | 一个栈或队列 | 栈、队列、广度优先 |
| 什么都不用记，只记「第几层」 | 一个计数器 | 状态机 |

**第二件是子问题重不重复。** 把手算的过程画成一棵树，
看有没有两个分支在算同一件事：

`Text`

```text
   算 f(5) 时如果要 f(4) 与 f(3)：

                  f(5)
                 ╱    ╲
              f(4)    f(3)      ← 同一个 f(3) 出现两次
             ╱   ╲      │
          f(3)   f(2)  f(2)     ← f(2) 出现三次
           │      │     │
          f(2)   f(1)  f(1)

   同一层里出现重复的结点，说明子问题重复：
   把算过的结果存起来（记忆化），或者自底向上填表（动态规划）。

   如果每个结点都只出现一次（每次分半、两半不相交），
   那就是分治：算完两半合起来即可，不需要存表。
```

## E.2.3 降规模之后仍然想不出来

如果 1 个、2 个、3 个都手算过，还是看不出递推，按顺序做下面三件事：

| 做法 | 说明 |
|---|---|
| **换一个「状态」的定义** | 同一题换一种状态定义，转移会跟着变简单或变复杂，见《08-一些散落的算法/09-贪心与动态规划.md》第 9.3 节那张三种定义的对照 |
| **换一个方向** | 从前往后想不出，就从后往前；从小的往大的想不出，就从大的往小的 |
| **把「求最优值」换成「判定一个值行不行」** | 判定的问题通常更容易，二分答案可以把它换回来 |

第二条在图上特别常见：正着走不通，把边的方向反过来往往就通了——
强连通分量的 Kosaraju 算法就是靠反图上再走一遍，见《08-一些散落的算法/08-图上的结构性问题.md》第 8.3 节。

# 第 E.3 节 再找相似结构

下面这张表按**需求里出现的特征**排，不按算法名排。
读法是从「问题特征」那一列往下找，找到最接近的一行，
再看「先试什么」，最后按「在哪一章」去翻详细讲法。

## E.3.2 几条容易记混的对照

| 对照 | 判据 | 出处 |
|---|---|---|
| 二分与哈希 | 需不需要顺序、会不会变、内存够不够 | 《08-一些散落的算法/04-查找：从线性到索引.md》 |

| KMP 与滚动哈希 | 查一个模式还是查一批等长模式 | `《08-一些散落的算法/10-字符串匹配.md》` |
| 递归与状态机 | 深度由谁决定：调用栈还是自己的变量 | `《08-一些散落的算法/11-扫描与状态机.md》` |

## E.3.3 表之外的三种情况

表覆盖不到的情形有三类，各有各的处理：

| 情形 | 处理 |
|---|---|
| 需求里同时出现两个特征 | 先做那个能把规模降下来的；两个都要做时，看哪个的结果是另一个的输入 |
| 特征对不上任何一行 | 回到 E.1 重新分类，多半是分类分错了 |
| 需求本身在变 | 停手，先把需求问清楚，见 E.4 |

## E.4.2 问题属于别的领域

| 领域 | 归哪 |
|---|---|

| 图形、图像、几何 | 计算几何与图形学专门资料 |
| 压缩、加密、校验 | 各自的标准与库；**不要自己发明**，见下 |
| 机器学习的训练与推理 | 专门框架 |

> [!CAUTION]
> **压缩、加密、校验这三类不要自己写。**
> 它们的正确性不是「跑通了就算」，而是要挡住刻意构造的输入；
> 自己写的实现看不出问题，却会在安全边界上失守。
> 这三类一律用经过审计的库。

## E.4.3 需求本身没定

第三种情形最费时间，也最常见：**要解的题目本身还没定下来。**

| 症状 | 表现 | 该做什么 |
|---|---|---|
| 规模没说 | 「要快」但不说多少条数据 | 先问规模：一千条和十亿条是两个问题 |
| 数据会不会变没说 | 只说「要能查」，不说增删 | 先问访问模式：只读、只加、随时增删 |
| 边界没说 | 不说输入为空、超长、非法时怎么办 | 先把边界列出来，它们往往就是测试用例 |
| 「最优」的标准没说 | 要最快、最省内存、还是最短代码 | 先问优化目标，三个目标常常冲突 |

这一节的判断可以压成一句：**写不出解法时，先确认是不是把问题问错了。**
需求里最常做的那件事决定了该用哪个解法，而「最常做的那件事」通常需要问出来。

## E.4.4 一条收口的原则

整个板块反复出现同一个顺序：**先分类，再定状态，最后才谈算法。**

| 走到哪一步 | 该问的话 |
|---|---|
| 分类 | 我最后要交出去的是一个数、一个次序、一个划分，还是一个对象 |
| 降规模 | 手算 1 个、2 个、3 个时，我在纸上记着什么 |
| 找结构 | 那个「记着的东西」是不是就是状态；子问题重不重复 |
| 落实现 | 现成的东西有没有；复杂度够不够；边界挡住了没有 |
| 收尾 | 代价测过没有；回本点算过没有 |

> [!NOTE]
> 这一章收成三句话：
> **分类决定解法族，降规模逼出状态，反查表给出先试什么；
> 三步都不需要灵感，都可以按着做；
> 而多数陌生问题已经有现成答案，找它的前提是先把它归对类。**
> 选结构的另一半在《09-高阶数据结构/END-怎么选容器与结构.md》，
> 两张表连着用才算把一个问题走完。

# 术语表

| 术语 | 含义 |
|---|---|
| **分类** | 判断问题要交出的东西是数、次序、划分还是对象 |
| **降规模** | 把输入缩小到手算得动的规模，用它逼出状态与递推 |
| **状态** | 手算时纸上记着的那几样东西，对应解法里要保存的变量 |
| **子问题重复** | 递归树里同一个结点出现多次；重复就记忆化或填表 |
| **交换论证** | 证明贪心成立的办法：把最优解的第一步换成贪心的选择，解不变差 |
| **回本点** | 预先算好的成本被后续操作省下的时间追平所需的次数 |
| **反查表** | 按需求特征排的表，从需求那一列往下找 |
