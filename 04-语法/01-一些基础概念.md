# 第 1 节 语法糖

## 1.1 一句话定义

> [!IMPORTANT]
> **语法糖是同一件事的另一种写法。**
> **底层机制完全相同，只是写法不同。**

**关键词是「同一件事」。**

| 说法 | 对不对 |
|---|---|
| 「语法糖是一种更好用的写法」 | 不完整，漏了「同一件事」 |
| 「语法糖是**同一机制**的另一种写法」 | **对** |

**它不增加语言的能力**：
凡是能用糖写出来的，**不用糖也能写出来**，只是麻烦一些。

## 1.2 为什么叫「糖」

**因为它对代码的作用，与糖对食物的作用类似：让人更愿意吃，但不增加营养。**

| | 糖的作用 |
|---|---|
| **对写代码的人** | 写起来短、读起来顺 |
| **对编译器** | **没有影响**——糖在读入源码时就化掉了 |
| **对生成的机器码** | **没有影响** |

**第三条是关键，它把语法糖与「优化」区分开**：

| | 语法糖 | 优化 |
|---|---|---|
| 改变什么 | **写法** | **生成的代码** |
| 谁在做 | 语言设计者 | 编译器 |
| 关掉它会怎样 | 只得写得更长 | 程序变慢 |

## 1.3 糖纸下面是什么

**每一颗糖都有一个「糖纸下面」的写法，叫它的展开形式。**

`Text`

```
   糖            糖纸下面
   a[i]    ───►  *(a + i)
   T&      ───►  传参用的指针
   int(x)  ───►  一次类型转换
```

**理解一颗糖，就是知道它展开成什么。**

> [!TIP]
> **读到一个陌生写法时，先试着自己展开它。**
> 展开得出来，说明你理解它；展开不出来，再去查规则也不迟。

## 1.4 怎么识别

**判断一个写法是不是糖，看三件事**：

| 判据 | 是糖的表现 |
|---|---|
| **能不能换一种写法表达同一件事** | 能，而且换完效果完全相同 |
| **它有没有对应的机器指令** | **没有**——编译器展开成别的指令 |
| **它有没有引入新的运行期开销** | **没有** |

**前两条合起来，等于一句话**：

> **把源码里的糖换掉，生成的机器码不变。**

**这条判据可以直接验证**：把两种写法各编一次，看汇编是否相同。

### 一个完整的例子：`a[i]`

**`a[i]` 是糖，它展开成 `*(a + i)`。**

`实测数据`
`C`

```c
/* subscript.c    编译：gcc -std=c23 -S subscript.c -o subscript.s */
/* 用下标与用指针访问同一个元素，对照生成的汇编 */

int by_subscript(const int *a, int i) {
    return a[i];                /* 糖 */
}

int by_pointer(const int *a, int i) {
    return *(a + i);            /* 糖纸下面 */
}
```

**两个函数生成的指令序列逐条相同**：

`Assembly`

```asm
movl  24(%rbp), %eax        /* 取出 i */
cltq                        /* 符号扩展到 64 位 */
leaq  0(,%rax,4), %rdx      /* 乘以 4 —— 每个 int 占 4 字节 */
movq  16(%rbp), %rax        /* 取出数组首地址 a */
addq  %rdx, %rax            /* 首地址 + i*4 —— 这就是 a + i */
```

**看第三行与第五行**：`a[i]` 里那个方括号**什么也没做**，
编译器算的是「首地址 ＋ i × 元素大小」，与手写 `*(a + i)` 完全一样。

> [!IMPORTANT]
> **下标运算符本身不是「访问数组」这件事，它只是指针加法的糖。**
> 后面讲数组为什么会「退化」、为什么不能整体赋值，
> 都要回到这一条上。

## 1.5 会遇到的糖

**下面这些糖会在后续章节里陆续出现。**

| 糖 | 糖纸下面 | 在哪一节 |
|---|---|---|
| **类型别名** `typedef` / `using` | 编译期替换，编译后什么都不剩 | `02-数据类型与类型系统` 第 4 节 |
| **`a[i]`** | `*(a + i)` | 本节、`07-数组、指针与引用` |
| **数组** | 「数据存储」用的指针 | `07-数组、指针与引用` |
| **引用 `T&`** | 「函数传参」用的指针 | `07-数组、指针与引用` |
| **`int(x)`** | 一次类型转换，不是函数调用 | `02` 第 5 节、`03-表达式与运算符` |
| **范围 `for`** | 展开成 `begin()` / `end()` 的迭代器循环 | `05-控制流语句` |
| **运算符重载** | 一次函数调用 | 【待补：05-类与面向对象/】 |
| **lambda** | 一个带 `operator()` 的类的对象 | 【待补：05-类与面向对象/】 |

**其中前五条本节已经能说明，后三条留到对应章节展开。**

### 两组实测证据

**第一组：别名在编译后不留痕迹。**

`实测数据`
`C`

```c
/* alias_same.c    编译：gcc -std=c23 -S alias_same.c -o alias_same.s */
typedef int myint;

int with_alias(void)    { myint a = 1; return a + 1; }   /* 用别名 */
int without_alias(void) { int   a = 1; return a + 1; }   /* 不用别名 */
```

**两个函数的指令序列逐条相同。**

**第二组：有些写法看着像函数调用，实际不是。**

`实测数据`
`C++`

```cpp
// no_call.cpp
// 编译：g++ -std=c++17 -O0 -S no_call.cpp -o no_call.s
int use_sizeof(void)        { return (int)sizeof(int); }  /* sizeof 是运算符 */
int use_cast_c(double d)    { return (int)d; }            /* C 风格转换 */
int use_cast_func(double d) { return int(d); }            /* 函数样式的转换 */
```

**三个函数里的函数调用指令都是 0 条**，
`sizeof`、`(int)d`、`int(d)` **都不是函数调用**。

**作为对照，下面这一类会产生真实的函数调用**：

`实测数据`
`C++`

```cpp
// has_call.cpp
// 编译：g++ -std=c++17 -O0 -S has_call.cpp -o has_call.s
struct V { int x; };
V operator+(V a, V b) { V r; r.x = a.x + b.x; return r; }

int add_fn(int a, int b) { return a + b; }

int use_class_operator(V a, V b) { V c = a + b; return c.x; }  /* 一条 call */
int use_function(int a, int b)   { return add_fn(a, b); }      /* 一条 call */
```

**类类型的 `a + b` 会产生一条函数调用指令**，
调用的符号名是修饰过的 `operator+`。

> [!NOTE]
> **糖与糖不一样。**
> 前几颗糖（别名、下标、转换）**编译后彻底消失**；
> 运算符重载与 lambda **会留下一个真实的函数调用**。
> 它们仍是糖——**写法与机制不是一回事**——
> 但代价不同，用之前要知道。

## 1.6 为什么要专门讲它

### 不理解糖，就只能背特例

**拿数组举例。初学者常遇到这几个「怪现象」**：

| 现象 | 死记的结论 |
|---|---|
| 数组名能传给指针参数 | 「数组就是指针」 |
| 可 `sizeof(arr)` 拿到的又不止是指针大小 | 「但 sizeof 的时候不是」 |
| 数组不能整体赋值 | 「数组不能赋值」 |
| `&arr` 与 `arr` 值相同、类型不同 | 「记住就行」 |

**这四条互相矛盾，只能各背各的。**

**换成糖的视角**：

`Text`

```
   数组本身            一块连续的内存，有确定的长度与首地址
   数组名在表达式里     退化成指向首元素的指针
   a[i]                就是 *(a + i)
```

**四条现象全部变成推论**：

| 现象 | 由什么推出 |
|---|---|
| 能传给指针参数 | 它退化成指针了 |
| `sizeof(arr)` 是整块大小 | `sizeof` 不触发退化，它要的是类型 |
| 不能整体赋值 | 退化之后只剩一个地址，没有「一整块」可赋 |
| `&arr` 类型不同 | 退化发生与否，决定取到的是不是整块 |

> [!IMPORTANT]
> **糖不是「简写」那么简单，它决定了这个语法点有哪些性质。**
> **知道糖纸下面是什么，性质就是推出来的，不是背下来的。**

### 两条通用做法

**第一条：遇到「为什么它这么怪」时，先找糖。**

`Text`

```
   一个语法点的行为看着不合常理
        ↓
   问：它是不是某个更基础东西的糖
        ↓
   是 → 那个更基础的东西有什么性质，糖就继承什么性质
```

**第二条：别把糖当成能力。**

> [!CAUTION]
> **糖不提供底层机制没有的能力。**
> 把 `UserId` 与 `OrderId` 都定义成 `int` 的别名，
> **编译器不会拦住你把其中一个传给需要另一个的函数**——
> 糖化掉之后，两者都是 `int`。

**这一条在 `14-奇技淫巧与优化` 里会反复用到**：
那一章的写法常常是「利用糖化之后的真实行为」，
**不知道糖纸下面是什么，就会写出看着对、实际错的东西**。

# 第 2 节 缩进与换行

**写代码时最随意的是排版，最容易看错的也是排版。**

## 2.1 排版不改变程序

**同一段程序，下面三种写法在编译器眼里是同一件事。**

`实测数据`
`C`

```c
/* format_normal.c    编译：gcc -std=c23 format_normal.c -o format_normal */
#include <stdio.h>

int main(void)
{
    int a = 1;
    int b = 2;
    if (a < b)
    {
        printf("%d\n", a + b);
    }
    return 0;
}
```

**第二种把整段压成一行**：

`C`

```c
/* format_flat.c    编译：gcc -std=c23 format_flat.c -o format_flat */
#include <stdio.h>
int main(void){int a=1;int b=2;if(a<b){printf("%d\n",a+b);}return 0;}
```

**第三种把制表符与空格混着用**（下面缩进里既有 Tab 也有空格）：

`C`

```c
/* format_tabs.c    编译：gcc -std=c23 format_tabs.c -o format_tabs */
#include <stdio.h>
int main(void)
{
	int a  = 1;		/* 这一行用制表符缩进 */
        int b = 2;	/* 这一行用空格缩进 */
	if (a < b)
	{
		printf("%d\n", a + b);
	}
  return 0;
}
```

**三份源码生成的目标文件，`.text` 段逐字节相同**：

`实测数据`

| 检查 | 结果 |
|---|---|
| 机器码（`.text` 段） | **三份完全相同** |
| 目标文件整体 | 只差 7 个字节，是符号表里记录的源文件名 |
| 运行结果 | 都是 `3` |

**结论：排版只在「分开两个记号」这件事上有意义。**

`文档`

> "Blanks, horizontal and vertical tabs, newlines, formfeeds, and comments
> (collectively, "white space"), as described below, are ignored except as
> they serve to separate tokens."
>
> —— N4659 §5.6/1

**到语法分析这一步，空白已经被丢掉了**：

`文档`

> "White-space characters separating tokens are no longer significant.
> Each preprocessing token is converted into a token."
>
> —— N3220 §5.1.1.2 第 7 阶段

## 2.2 缩进会骗人

**编译器不看缩进，所以缩进可以「撒谎」。**
最典型的一处是悬空 `else`：

`实测数据`
`C`

```c
/* dangling_else.c    编译：gcc -std=c23 dangling_else.c -o dangling_else */
#include <stdio.h>

int main(void) {
    int a = 1, b = 0;

    if (a)
        if (b)
            printf("内层 if 成立\n");
        else
            printf("else 跟的是内层 if\n");   /* 缩进看着像外层，实际不是 */
    return 0;
}
```

**运行结果是「else 跟的是内层 if」。**
把那个 `else` 缩进到与第一个 `if` 对齐，程序的行为一点不变。

**`else` 与哪个 `if` 配对由文法决定**（就近配对），缩进说了不算。

> [!TIP]
> **给 `if`、`else`、`for`、`while` 一律加大括号。**
> 有了括号，配对关系由括号决定，排版就只管好不好看。
> 循环体漏写大括号的例子见《04-语法/05-控制流语句.md》第 3.8 小节。

## 2.3 换行在四处确实有意义

**换行也是空白的一种，但在下面四个地方它不是「可忽略的空白」。**

| 场合 | 换行起什么作用 |
|---|---|
| `//` 注释 | **结束注释**，注释到行尾为止 |
| 预处理指令 | **结束指令**，`#define` 的宏体到行尾为止 |
| 字符串字面量 | **不允许出现在里面**（未经转义时） |
| 反斜杠之后 | **被删掉**，两个物理行拼成一个逻辑行 |

### 一、`//` 注释到行尾为止

`实测数据`
`C`

```c
/* comment_eol.c    编译：gcc -std=c23 comment_eol.c -o comment_eol */
#include <stdio.h>

int main(void) {
    int b = 2;   // 从这里到行尾都是注释 printf("这一行不会输出\n");
    printf("b = %d\n", b);
    return 0;
}
```

**输出只有 `b = 2` 一行**：写在 `//` 后面的那条 `printf` 属于注释。

`文档`

> "The characters // introduce a comment that includes all multibyte characters
> up to, but not including, the next new-line character."
>
> —— N3220 §6.4.9/2

### 二、预处理指令到行尾为止

**`#define` 的宏体在第一个换行处结束**，因此多行的宏要靠反斜杠续行：

`文档`

> "The last token in the sequence is the first new-line character that follows
> the first token in the sequence. A new-line character ends the preprocessing
> directive even if it occurs within what would otherwise be an invocation of
> a function-like macro."
>
> —— N3220 §6.10.1/2

`实测数据`
`C`

```c
/* define_ok.c    编译：gcc -std=c23 define_ok.c -o define_ok */
#include <stdio.h>

#define SUM 1 + \
            2               /* 反斜杠把两个物理行拼成一个逻辑行 */

int main(void) {
    printf("SUM = %d\n", SUM);
    return 0;
}
```

**少了那个反斜杠就编不过**：

`实测数据`
`C`

```c
/* define_bad.c    编译：gcc -std=c23 define_bad.c -o define_bad （失败）
 * gcc 报错：error: expected identifier or '(' before numeric constant
 */
#include <stdio.h>

#define SUM 1 +
            2               /* 没有反斜杠：宏体只有「1 +」 */

int main(void) {
    printf("SUM = %d\n", SUM);
    return 0;
}
```

**宏体只到第一行为止**，于是第二行的 `2` 成了文件作用域里的一条独立语句。
宏的其余规则见《04-语法/13-预处理器.md》第 2 节。

### 三、反斜杠续行：把换行「取消」

**反斜杠紧挨着换行时，这一对字符会被删掉**，两个物理行合成一个逻辑行：

`文档`

> "Each instance of a backslash character (\) immediately followed by a
> new-line character is deleted, splicing physical source lines to form
> logical source lines."
>
> —— N3220 §5.1.1.2 第 2 阶段

**这一步发生在「识别注释」之前**，因此 `//` 行末尾的反斜杠会把下一行也吞进注释：

`实测数据`
`C`

```c
/* comment_splice.c    编译：gcc -std=c23 -Wall comment_splice.c -o comment_splice
 * gcc 输出：warning: multi-line comment [-Wcomment]
 */
#include <stdio.h>

int main(void) {
    int a = 1;
    // 这一行末尾有一个反斜杠，注释会延续到下一行 \
    a = 99;
    printf("a = %d\n", a);
    return 0;
}
```

**输出是 `a = 1`**：`a = 99;` 已经被并进上一行的注释里。

**顺序是这条现象的成因**：先拼接（第 2 阶段），再识别注释（第 3 阶段）。
若反过来先识别注释，注释到本行末尾就结束了，也就吞不掉下一行。

`文档`

> "Implementations must behave as if these separate phases occur, although in
> practice different phases might be folded together."
>
> —— N4659 §5.2 脚注 12

> [!WARNING]
> **不要用反斜杠给 `//` 注释续行。**
> 要写多行注释用 `/* */`，它的结束靠 `*/`，不靠换行。

### 四、字符串字面量不能跨行

`实测数据`
`C`

```c
/* string_newline.c    编译：gcc -std=c23 string_newline.c -o string_newline （失败）
 * gcc 报错：error: missing terminating " character
 */
#include <stdio.h>

int main(void) {
    printf("这一行没有结束
            引号在下一行才出现\n");
    return 0;
}
```

**字符串字面量里不允许出现未转义的换行**：

`文档`

> "s-char: any member of the source character set except the double-quote ",
> backslash \, or new-line character"
>
> —— N3220 §6.4.5

**要写长字符串，把它拆成几个相邻的字面量**，编译器会在翻译阶段把它们接起来：

`文档`

> "Adjacent string literal tokens are concatenated."
>
> —— N3220 §5.1.1.2 第 6 阶段

`C`

```c
printf("这是一段很长的文字，"
       "可以分成几行来写。\n");
```

## 2.4 空白什么时候必须有

**两个记号挨在一起时，可能被读成一个记号**，这时空白不可省。

`文档`

> "Otherwise, the next preprocessing token is the longest sequence of
> characters that could constitute a preprocessing token, even if that would
> cause further lexical analysis to fail."
>
> —— N4659 §5.4/3.3

**这条规则叫最长匹配**：切记号时总是尽量往长了切。

`实测数据`
`C`

```c
/* plusplus.c    编译：gcc -std=c23 plusplus.c -o plusplus */
#include <stdio.h>

int main(void) {
    int a = 1, b = 2;
    printf("a+++b = %d\n", a+++b);      /* 最长匹配：a++ + b */
    printf("之后 a = %d\n", a);
    printf("a + ++b = %d\n", a + ++b);  /* 加上空格是这个意思 */
    return 0;
}
```

`Text`

```text
a+++b = 3
之后 a = 2
a + ++b = 5
```

**`a+++b` 被切成 `a++`、`+`、`b` 三个记号**，因为切第一个记号时取了最长的 `a++`。
**减号同理**：`a---b` 是 `(a--) - b`，实测得 `-1`。

**标准里的例子更极端**：`x+++++y` 被切成 `x ++ ++ + y`，
于是它违反自增运算符的约束——`x++` 的结果不能再自增。

**少写一个空格，后果可以很严重**（`/` 与 `*` 贴在一起就是注释开头）：

`实测数据`
`C`

```c
/* comment_ok.c    编译：gcc -std=c23 comment_ok.c -o comment_ok */
#include <stdio.h>

int main(void) {
    int a = 6, b = 2;
    int *p = &b;
    int c = a / *p;     /* 除号与解引用之间必须留空格 */
    printf("c = %d\n", c);
    return 0;
}
```

**写成 `a/*p` 就成了注释**：

`实测数据`
`C`

```c
/* comment_trap.c    编译：gcc -std=c23 comment_trap.c -o comment_trap （失败）
 * gcc 报错：error: expected ',' or ';' before 'printf'
 */
#include <stdio.h>

int main(void) {
    int a = 6, b = 2;
    int *p = &b;
    int c = a/*p;               /* 本意是 a / *p，少写空格就变成了注释开始 */
    printf("%d\n", c);
    return 0;
}
```

**报错却指在下一行的 `printf` 上**：这一行从 `/*` 起不再是代码，
`int c = a` 后面直接接上了下一行。

> [!IMPORTANT]
> **该有空格的地方不要省。**
> `a / *p`、`a + ++b`、`int x` 里的空格都不是装饰：
> **没有空格时，记号的切法可能与预期不同。**

## 2.5 与 Python 的对照

**换一门语言，缩进与换行的地位就变了。**

| | C 与 C++ | Python |
|---|---|---|
| 什么决定块结构 | **`{}`** | **缩进** |
| 什么结束一条语句 | **`;`** | **换行** |
| 缩进的作用 | 只影响阅读 | **语法的一部分** |
| 语句能随便换行吗 | **能**（记号之间可以放任意空白） | **不能**，除非在括号内或加 `\` |
| 制表符与空格混用 | 无所谓 | **报 `TabError`** |
| 一行写多条语句 | 本来就是这么写的 | 可以，用 `;` 分隔，但不常用 |

**Python 对换行的要求**：

`实测数据`
`Python`

```python
# newline_bad.py    运行：python newline_bad.py
total = 1 +
        2
print(total)
```

`Text`

```text
  File "newline_bad.py", line 1
    total = 1 +
               ^
SyntaxError: invalid syntax
```

**把换行挪到括号里面就合法**：

`实测数据`
`Python`

```python
# newline_ok.py    运行：python newline_ok.py
total = (1 +
         2)
print(total)
```

**输出是 `3`。**

**缩进在 Python 里是语法**，多一个空格就是错误；在 C 里多一个空格毫无影响。

`实测数据`
`Text`

```text
indent_bad.py     IndentationError: unexpected indent
tab_mix.py        TabError: inconsistent use of tabs and spaces in indentation
```

**完整源码见附录 A.6 与 A.7。**

> [!CAUTION]
> **从 Python 过来时，要改掉两个习惯**：
> **用缩进表达块结构**（C 里必须写 `{}`）、
> **用换行结束语句**（C 里必须写 `;`）。
> 缩进写错在 Python 里会报错，在 C 里会静默地按另一种意思执行。

## 2.6 排版仍然重要

> [!TIP]
> **编译器不在乎缩进，读代码的人在乎。**
> 同一份代码换一种排法，读起来的难易程度可以差很远。
> **排版是给人看的**——正因为编译器不管，它才完全取决于写代码的人是否用心。

# 术语表

| 术语 | 英文 | 含义 |
|---|---|---|
| 语法糖 | Syntactic sugar | 同一底层机制的另一种写法 |
| 展开 | Desugaring | 把糖替换成它对应的基础写法 |
| 退化 | Decay | 数组名在表达式中变成指向首元素的指针 |
| 记号 | Token | 词法分析切出的最小单位，空白只用来分隔它 |
| 最长匹配 | Maximal munch | 切记号时总是取能构成记号的最长字符序列 |
| 物理行 / 逻辑行 | Physical line / Logical line | 拼接前的一行 / 反斜杠续行拼接后的一行 |
| 续行 | Line splicing | 反斜杠紧挨换行时两者被删除，两个物理行拼成一个逻辑行 |
