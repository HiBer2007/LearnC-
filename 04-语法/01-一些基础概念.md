# 第 1 节 语法糖

## 1.1 一句话定义

> [!IMPORTANT]
> **语法糖是同一件事的另一种写法。**
> **底层机制完全相同，只是写法不同。**

**关键词是「同一件事」。**

| 说法 | 对不对 |
|---|---|
| 「语法糖是一种更好用的写法」 | 不完整，漏了「同一件事」 |
| 「语法糖是**同一机制**的另一种写法」 | **对** |

**它不增加语言的能力**：
凡是能用糖写出来的，**不用糖也能写出来**，只是麻烦一些。

## 1.2 为什么叫「糖」

**因为它对代码的作用，与糖对食物的作用类似：让人更愿意吃，但不增加营养。**

| | 糖的作用 |
|---|---|
| **对写代码的人** | 写起来短、读起来顺 |
| **对编译器** | **没有影响**——糖在读入源码时就化掉了 |
| **对生成的机器码** | **没有影响** |

**第三条是关键，它把语法糖与「优化」区分开**：

| | 语法糖 | 优化 |
|---|---|---|
| 改变什么 | **写法** | **生成的代码** |
| 谁在做 | 语言设计者 | 编译器 |
| 关掉它会怎样 | 只得写得更长 | 程序变慢 |

## 1.3 糖纸下面是什么

**每一颗糖都有一个「糖纸下面」的写法，叫它的展开形式。**

<small style="color:gray">text</small>

```
   糖            糖纸下面
   a[i]    ───►  *(a + i)
   T&      ───►  传参用的指针
   int(x)  ───►  一次类型转换
```

**理解一颗糖，就是知道它展开成什么。**

> [!TIP]
> **读到一个陌生写法时，先试着自己展开它。**
> 展开得出来，说明你理解它；展开不出来，再去查规则也不迟。

## 1.4 怎么识别

**判断一个写法是不是糖，看三件事**：

| 判据 | 是糖的表现 |
|---|---|
| **能不能换一种写法表达同一件事** | 能，而且换完效果完全相同 |
| **它有没有对应的机器指令** | **没有**——编译器展开成别的指令 |
| **它有没有引入新的运行期开销** | **没有** |

**前两条合起来，等于一句话**：

> **把源码里的糖换掉，生成的机器码不变。**

**这条判据可以直接验证**：把两种写法各编一次，看汇编是否相同。

### 一个完整的例子：`a[i]`

**`a[i]` 是糖，它展开成 `*(a + i)`。**

<small style="color:gray">实测数据</small>
<small style="color:gray">c</small>

```c
/* subscript.c    编译：gcc -std=c23 -S subscript.c -o subscript.s */
/* 用下标与用指针访问同一个元素，对照生成的汇编 */

int by_subscript(const int *a, int i) {
    return a[i];                /* 糖 */
}

int by_pointer(const int *a, int i) {
    return *(a + i);            /* 糖纸下面 */
}
```

**两个函数生成的指令序列逐条相同**：

<small style="color:gray">asm</small>

```asm
movl  24(%rbp), %eax        /* 取出 i */
cltq                        /* 符号扩展到 64 位 */
leaq  0(,%rax,4), %rdx      /* 乘以 4 —— 每个 int 占 4 字节 */
movq  16(%rbp), %rax        /* 取出数组首地址 a */
addq  %rdx, %rax            /* 首地址 + i*4 —— 这就是 a + i */
```

**看第三行与第五行**：`a[i]` 里那个方括号**什么也没做**，
编译器算的是「首地址 ＋ i × 元素大小」，与手写 `*(a + i)` 完全一样。

> [!IMPORTANT]
> **下标运算符本身不是「访问数组」这件事，它只是指针加法的糖。**
> 后面讲数组为什么会「退化」、为什么不能整体赋值，
> 都要回到这一条上。

## 1.5 会遇到的糖

**下面这些糖会在后续章节里陆续出现。**

| 糖 | 糖纸下面 | 在哪一节 |
|---|---|---|
| **类型别名** `typedef` / `using` | 编译期替换，编译后什么都不剩 | `02-数据类型与类型系统` 第 4 节 |
| **`a[i]`** | `*(a + i)` | 本节、`07-数组、指针与引用` |
| **数组** | 「数据存储」用的指针 | `07-数组、指针与引用` |
| **引用 `T&`** | 「函数传参」用的指针 | `07-数组、指针与引用` |
| **`int(x)`** | 一次类型转换，不是函数调用 | `02` 第 5 节、`03-表达式与运算符` |
| **范围 `for`** | 展开成 `begin()` / `end()` 的迭代器循环 | `05-控制流语句` |
| **运算符重载** | 一次函数调用 | 【待补：05-类与面向对象/】 |
| **lambda** | 一个带 `operator()` 的类的对象 | 【待补：05-类与面向对象/】 |

**其中前五条本节已经能说明，后三条留到对应章节展开。**

### 两组实测证据

**第一组：别名在编译后不留痕迹。**

<small style="color:gray">实测数据</small>
<small style="color:gray">c</small>

```c
/* alias_same.c    编译：gcc -std=c23 -S alias_same.c -o alias_same.s */
typedef int myint;

int with_alias(void)    { myint a = 1; return a + 1; }   /* 用别名 */
int without_alias(void) { int   a = 1; return a + 1; }   /* 不用别名 */
```

**两个函数的指令序列逐条相同。**

**第二组：有些写法看着像函数调用，实际不是。**

<small style="color:gray">实测数据</small>
<small style="color:gray">cpp</small>

```cpp
// no_call.cpp
// 编译：g++ -std=c++17 -O0 -S no_call.cpp -o no_call.s
int use_sizeof(void)        { return (int)sizeof(int); }  /* sizeof 是运算符 */
int use_cast_c(double d)    { return (int)d; }            /* C 风格转换 */
int use_cast_func(double d) { return int(d); }            /* 函数样式的转换 */
```

**三个函数里的函数调用指令都是 0 条**，
`sizeof`、`(int)d`、`int(d)` **都不是函数调用**。

**作为对照，下面这一类会产生真实的函数调用**：

<small style="color:gray">实测数据</small>
<small style="color:gray">cpp</small>

```cpp
// has_call.cpp
// 编译：g++ -std=c++17 -O0 -S has_call.cpp -o has_call.s
struct V { int x; };
V operator+(V a, V b) { V r; r.x = a.x + b.x; return r; }

int add_fn(int a, int b) { return a + b; }

int use_class_operator(V a, V b) { V c = a + b; return c.x; }  /* 一条 call */
int use_function(int a, int b)   { return add_fn(a, b); }      /* 一条 call */
```

**类类型的 `a + b` 会产生一条函数调用指令**，
调用的符号名是修饰过的 `operator+`。

> [!NOTE]
> **糖与糖不一样。**
> 前几颗糖（别名、下标、转换）**编译后彻底消失**；
> 运算符重载与 lambda **会留下一个真实的函数调用**。
> 它们仍是糖——**写法与机制不是一回事**——
> 但代价不同，用之前要知道。

## 1.6 为什么要专门讲它

### 不理解糖，就只能背特例

**拿数组举例。初学者常遇到这几个「怪现象」**：

| 现象 | 死记的结论 |
|---|---|
| 数组名能传给指针参数 | 「数组就是指针」 |
| 可 `sizeof(arr)` 拿到的又不止是指针大小 | 「但 sizeof 的时候不是」 |
| 数组不能整体赋值 | 「数组不能赋值」 |
| `&arr` 与 `arr` 值相同、类型不同 | 「记住就行」 |

**这四条互相矛盾，只能各背各的。**

**换成糖的视角**：

<small style="color:gray">text</small>

```
   数组本身            一块连续的内存，有确定的长度与首地址
   数组名在表达式里     退化成指向首元素的指针
   a[i]                就是 *(a + i)
```

**四条现象全部变成推论**：

| 现象 | 由什么推出 |
|---|---|
| 能传给指针参数 | 它退化成指针了 |
| `sizeof(arr)` 是整块大小 | `sizeof` 不触发退化，它要的是类型 |
| 不能整体赋值 | 退化之后只剩一个地址，没有「一整块」可赋 |
| `&arr` 类型不同 | 退化发生与否，决定取到的是不是整块 |

> [!IMPORTANT]
> **糖不是「简写」那么简单，它决定了这个语法点有哪些性质。**
> **知道糖纸下面是什么，性质就是推出来的，不是背下来的。**

### 两条通用做法

**第一条：遇到「为什么它这么怪」时，先找糖。**

<small style="color:gray">text</small>

```
   一个语法点的行为看着不合常理
        ↓
   问：它是不是某个更基础东西的糖
        ↓
   是 → 那个更基础的东西有什么性质，糖就继承什么性质
```

**第二条：别把糖当成能力。**

> [!CAUTION]
> **糖不提供底层机制没有的能力。**
> 把 `UserId` 与 `OrderId` 都定义成 `int` 的别名，
> **编译器不会拦住你把其中一个传给需要另一个的函数**——
> 糖化掉之后，两者都是 `int`。

**这一条在 `14-奇技淫巧与优化` 里会反复用到**：
那一章的写法常常是「利用糖化之后的真实行为」，
**不知道糖纸下面是什么，就会写出看着对、实际错的东西**。

# 术语表

| 术语 | 英文 | 含义 |
|---|---|---|
| 语法糖 | Syntactic sugar | 同一底层机制的另一种写法 |
| 展开 | Desugaring | 把糖替换成它对应的基础写法 |
| 退化 | Decay | 数组名在表达式中变成指向首元素的指针 |
