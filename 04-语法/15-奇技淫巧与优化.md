# 第 1 节 这些手法为什么存在

**它们大多来自某个特定的年代或场景。**

| 年代 | 当时的处境 |
|---|---|
| 编译器很笨 | 不会自动做强度削减、循环展开 |
| 内存按 KB 算 | 每字节都要省 |
| CPU 慢且指令集少 | 一条移位比一次乘法快得多 |
| 没有标准库 | 什么都得手写 |

**今天的情况变了**：

| 变化 | 后果 |
|---|---|
| 优化器成熟 | 多数「手写优化」它自己就会做 |
| 内存按 GB 算 | 省下的几字节没有意义 |
| 乘法与移位一样快 | 强度削减的价值大幅下降 |
| 标准库完善 | 手写实现通常不如标准库 |

> [!IMPORTANT]
> **判断一个技巧今天还需不需要，办法是实测**——
> **写两版，看汇编是否相同。**
> 相同就说明编译器已经做了这件事，手写版只剩「更难读」这一个后果。

**本章下面每一节都做了这个对照。**

# 第 2 节 手写移位代替乘除法

## 2.1 它解决什么问题

**在优化器不成熟的年代，`x * 8` 真的会被编成一条乘法指令**，
而乘法在早期 CPU 上要花好几个周期。写成 `x << 3` 就能省下这些周期。

## 2.2 今天还需不需要

`C`

```c
/* shift_vs_mul.c    编译：gcc -std=c23 -O2 -S shift_vs_mul.c -o shift_vs_mul.s */
int by_shift(int x) { return x << 3; }
int by_mul(int x)   { return x * 8; }
```

**`-O2` 下两个函数的汇编**

`实测数据`
`Text`

```text
by_shift: leal 0(,%rcx,8), %eax | ret
by_mul  : leal 0(,%rcx,8), %eax | ret
逐条相同: 是
```

**不只是 `-O2`，连 `-O0`（不优化）下编译器也已经换掉了**：

`实测数据`
`Text`

```text
-O0 下 int mul_by_8(int x) { return x * 8; }
→ sall $3, %eax          （移位指令）

-O0 下 int mul_by_7(int x) { return x * 7; }
→ movl %eax, %edx
  sall $3, %edx
  subl %eax, %edx        （x*8 - x，比乘法快）

-O0 下 int div_by_8(int x) { return x / 8; }
→ leal 7(%rax), %edx
  testl %eax, %eax
  cmovs %edx, %eax       （补上负数向零取整的修正）
  sarl $3, %eax
```

**`x / 8` 被换成了「加 7、按符号选、算术右移」三步**——
这是带符号除法向零取整所必需的修正。

> [!IMPORTANT]
> **「用移位代替乘除」这件事编译器已经做完了，而且在 `-O0` 下就做了。**
> 手写 `x << 3` 的唯一效果是让读代码的人多花一秒确认「这里为什么不用乘法」。

## 2.3 什么时候不该用

| 情形 | 理由 |
|---|---|
| 几乎全部情形 | 编译器已经做了 |
| 想表达「乘以 8」 | 写 `x * 8` 更直接 |
| 想表达「位操作」 | 那时移位才是本意，不算技巧 |

> [!TIP]
> **唯一还值得写移位的地方，是它本来就是位操作**——
> 取某几位、置标志位、拼装字节。
> **那时用移位不是「优化」，而是「这件事本身就是移位的语义」。**

# 第 3 节 用单字节类型装普通整数

## 3.1 它解决什么问题

**省内存。** 一个结构体里有十个计数器，每个都用 `int` 要 40 字节，
用 `int8_t` 只要 10 字节（实际还要看填充，见
《04-语法/09-结构体、联合体与 enum.md》第 1.5 小节）。

**在内存按 KB 算的年代，这个差别很实在。**

## 3.2 它带来的意外

`C`

```c
/* int8_arith.c    编译：gcc -std=c23 int8_arith.c -o int8_arith */
#include <stdio.h>
#include <stdint.h>

int main(void) {
    int8_t a = 100, b = 100;

    printf("int8_t 相加: %d\n", a + b);          /* 看起来应该溢出 */
    printf("sizeof(a + b) = %zu\n", sizeof(a + b));
    printf("sizeof(a)     = %zu\n", sizeof(a));

    int8_t s = a + b;                            /* 结果装回 int8_t */
    printf("装回 int8_t: %d\n", s);
    return 0;
}
```

`实测数据`
`Text`

```text
int8_t 相加: 200
sizeof(a + b) = 4
sizeof(a)     = 1
装回 int8_t: -56
```

**三件事同时看出来了**：

**第一，`a + b` 得到 200，没有溢出。**
因为 `int8_t` 在参与运算时被**提升**成了 `int`。

**第二，`sizeof(a + b)` 是 4**，不是 1。这就是提升的证据。

**第三，把 200 装回 `int8_t` 才溢出**，得到 `-56`。

> [!WARNING]
> **小整数类型只在「存储」时省空间，一旦参与运算就变回 `int`。**
> 因此「用 `int8_t` 让运算变快」是不成立的——
> **它反而可能更慢**，因为每次运算后要截断回 8 位。

## 3.3 什么时候不该用

| 情形 | 用什么 |
|---|---|
| 循环变量、计数器 | **`int`**——它本来就是寄存器宽度 |
| 结构体里的大批标志 | `int8_t` / `bool`，**省的是存储** |
| 需要精确宽度的场合（协议、硬件） | `int8_t` / `uint16_t` 等，**这时它是语义需要** |
| 数组里的大批小数值 | `int8_t`，缓存友好 |

> [!TIP]
> **判断标准**：**用它是因为「存储布局需要」，还是因为「以为它更快」？**
> 前者对，后者错。

# 第 4 节 用联合体做类型双关

## 4.1 它解决什么问题

**把一个 `float` 按 `unsigned int` 看**，以取出它的位模式。

**用途**：浮点数的位级分析、协议里按字节收发、哈希。

## 4.2 它和 `memcpy` 一样

`C`

```c
/* pun.c    编译：gcc -std=c23 -O2 -S pun.c -o pun.s */
#include <string.h>

union Pun { float f; unsigned int u; };

unsigned int by_union(float x) {
    union Pun p;
    p.f = x;
    return p.u;                 /* 读的不是最后写入的成员 */
}

unsigned int by_memcpy(float x) {
    unsigned int r;
    memcpy(&r, &x, sizeof r);   /* 按字节复制 */
    return r;
}
```

`实测数据`
`Text`

```text
union  : 0x3F800000
memcpy : 0x3F800000
-O2 下两者汇编相同: 是
```

**两个函数得到同样的位模式，汇编也逐条相同。**

## 4.3 代价

| 代价 | 说明 |
|---|---|
| **读非最后写入的成员是未定义行为** | C++ 明确规定；C 里是常见做法但不属可移植代码 |
| 依赖字节序 | 换平台结果不同 |
| 依赖对齐 | 某些平台上会崩 |
| 优化器可能不按你想的做 | 严格别名规则允许它假设两个成员互不相关 |

> [!CAUTION]
> **`memcpy` 才是标准认可的写法，而且它没有代价。**
> 上例实测两者汇编相同——
> 既然一样快，就没有理由选那个「未定义」的。

**标准写法**：

`C`

```c
unsigned int by_memcpy(float x) {
    unsigned int r;
    memcpy(&r, &x, sizeof r);   /* 标准保证，且被优化成一条 mov */
    return r;
}
```

## 4.4 什么时候不该用

| 情形 | 用什么 |
|---|---|
| 想取出浮点的位模式 | **`memcpy`** |
| 想在几种类型间共用存储（节省空间） | 联合体**可以**，但要保证「写哪个读哪个」 |
| 想做序列化 | 逐字节写，或 `memcpy` 到字节数组 |

# 第 5 节 跳转表

## 5.1 它解决什么问题

**用函数指针数组代替 `switch`**，让「按编号选一个操作」不用写分支链。

**它的价值不在于快**——`switch` 通常也被编译成跳转表。
**价值在于「可扩展」**：加一个操作只需要在表里加一项。

## 5.2 跳转表的实际表现

`C`

```c
/* jump_table.c    编译：gcc -std=c23 jump_table.c -o jump_table */
#include <stdio.h>

int op_add(int a, int b) { return a + b; }
int op_sub(int a, int b) { return a - b; }
int op_mul(int a, int b) { return a * b; }

/* 用函数指针数组当跳转表 */
static int (*const table[])(int, int) = { op_add, op_sub, op_mul };

int by_table(int op, int a, int b) {
    if (op < 0 || op > 2) return -1;
    return table[op](a, b);
}

int by_switch(int op, int a, int b) {
    switch (op) {
        case 0: return a + b;
        case 1: return a - b;
        case 2: return a * b;
        default: return -1;
    }
}

int main(void) {
    for (int i = 0; i < 3; i++)
        printf("%d %d | ", by_table(i, 10, 3), by_switch(i, 10, 3));
    printf("\n");
    return 0;
}
```

**两种写法的输出相同**：`13 13 | 7 7 | 30 30 |`。

## 5.3 代价

| 代价 | 说明 |
|---|---|
| **范围检查必须自己写** | `switch` 的 `default` 是自动的，数组下标越界不是 |
| 间接调用妨碍内联 | 编译器不知道会调到哪个函数 |
| 调试时看不出调用关系 | 断点要打在具体函数上 |
| 函数签名必须统一 | 参数个数与类型都被固定 |

> [!WARNING]
> **跳转表最大的风险是「忘了检查下标」。**
> `table[op]` 里 `op` 越界时，读的是数组外的地址，
> 然后跳过去执行——这是可被利用的安全问题。
> **`switch` 天然有 `default`，跳转表没有。**

## 5.4 什么时候不该用

| 情形 | 用什么 |
|---|---|
| 分支少（三五个） | **`switch`**，更直白 |
| 各分支的参数不同 | `switch`（跳转表要求签名统一） |
| 需要内联优化 | `switch` |
| **分支多、且会持续增加** | **跳转表**，加一项只改一行 |

# 第 6 节 位运算技巧

## 6.1 它解决什么问题

**位级操作本来就没有更高级的表达方式**，
因此这一类里有些**不算技巧，而是本意**。

**但有一类确实是技巧**：用位运算实现原本要循环或分支才能做的事。

## 6.2 手写 popcount 与内建函数

**算一个整数里有几个二进制 1。**

`C`

```c
/* popcount.c    编译：gcc -std=c23 -O2 -S popcount.c -o popcount.s */
#include <stdint.h>

int manual(uint32_t x) {
    int n = 0;
    while (x) { n += x & 1; x >>= 1; }
    return n;
}

int builtin(uint32_t x) { return __builtin_popcount(x); }
```

**两者结果相同（都是 16），`-O2` 下的汇编**

`实测数据`
`Text`

```text
manual  ：11 条指令，含一个循环
    xorl  %eax, %eax
    testl %ecx, %ecx
    je    .L1
  .L3:
    movl  %ecx, %edx
    andl  $1, %edx
    addl  %edx, %eax
    shrl  %ecx
    ...

builtin ：5 条指令
    subq  $40, %rsp
    movl  %ecx, %ecx
    call  __popcountdi2
    addq  $40, %rsp
    ret
```

> [!IMPORTANT]
> **编译器认识 `__builtin_popcount`，会换成它自己选的实现。**
> 手写循环虽然也不慢，但**编译器更清楚目标 CPU 有没有 `popcnt` 指令**——
> 有就直接用一条指令，没有就调库函数。
> **手写版永远只能是一个循环。**

## 6.3 哪些位运算不算技巧

**下面这些是「本意」，不是「优化」**：

`C`

```c
x & 0xFF            /* 取低 8 位 */
x | (1u << n)       /* 置第 n 位 */
x & ~(1u << n)      /* 清第 n 位 */
(x >> n) & 1u       /* 读第 n 位 */
x ^= y              /* 按位翻转 */
```

**它们在硬件寄存器操作里是唯一写法**，
做法见《01-编译器/03-嵌入式与交叉编译.md》第 4.3 小节。

## 6.4 什么时候不该用

| 情形 | 用什么 |
|---|---|
| 算有几个 1 | **`__builtin_popcount`** |
| 找最高位 / 最低位 | `__builtin_clz` / `__builtin_ctz` |
| 判断是不是 2 的幂 | `(x & (x-1)) == 0`，这个够简单，可以用 |
| 位掩码、寄存器操作 | **位运算就是本意**，直接用 |
| 手写的「无分支」小技巧 | 先实测，编译器往往已经做了 |

> [!CAUTION]
> **不要为了「无分支」而写难懂的表达。**
> 现代 CPU 的分支预测很准，而编译器比你更懂目标平台。
> **读不懂的代码带来的维护成本，远大于省下的几个周期。**

# 第 7 节 强制内联与分支提示

## 7.1 C 的 `inline` 不是「请内联」

**这是最容易误解的一处。**

`C`

```c
inline        int f(void) { return 1; }     /* 定义 */
extern inline int f(void) { return 1; }     /* 外部链接的定义 */
static inline int f(void) { return 1; }     /* 内部链接的定义 */
```

**`nm` 看符号表**

`实测数据`
`Text`

```text
inline int f(void)        →  U f            （未定义）
extern inline int f(void) →  T f            （外部链接）
static inline int f(void) →  t f            （内部链接）
int f(void)               →  T f            （普通函数）
```

**第一行是关键**：单独写 `inline` 时，**符号表里是 `U`（未定义）**。

> [!IMPORTANT]
> **C 里 `inline` 管的是「要不要生成函数体」，不是「要不要内联」。**
> 单独写 `inline` 表示「这是一个内联定义」——
> 编译器**可以不生成它的独立函数体**，
> 因此别的文件找不到这个符号（`U`）。
>
> **要生成函数体，得配 `extern`；要只在本文件用，配 `static`。**

**「要不要内联」由编译器自己决定**，与写不写 `inline` 无关。

**C++ 的规则不同**：`inline` 函数在所有翻译单元里是同一个实体，
因此可以放心写在头文件里（见《04-语法/14-预处理器.md》第 3.3 小节）。

## 7.2 强制内联

**GCC 与 Clang 提供一个属性**：

`C`

```c
__attribute__((always_inline)) inline int forced(int x) { return x + 1; }
```

**MSVC 上是 `__forceinline`。**

**`-O0` 下 `always_inline` 仍然会内联**（数据见附录 A.9）。

**代价**：

| 代价 | 说明 |
|---|---|
| 代码膨胀 | 每个调用点都展开一份，指令缓存压力大 |
| 不可移植 | GCC 与 MSVC 的写法不同 |
| 妨碍调试 | 断点打不进去 |
| 可能更慢 | 膨胀之后指令缓存装不下 |

> [!WARNING]
> **`always_inline` 是「我知道得比编译器清楚」的声明。**
> 大多数时候这个判断是错的——**编译器能看到调用点的上下文，
> 而你写这个属性时看不到**。

## 7.3 分支提示

`C`

```c
if (__builtin_expect(x > 0, 1)) { ... }     /* 告诉编译器「通常成立」 */
```

**加与不加，`-O2` 下的汇编逐条相同。**

`实测数据`
`Text`

```text
加提示: xorl %eax, %eax | testl %ecx, %ecx | setg %al | ret
不加  : xorl %eax, %eax | testl %ecx, %ecx | setg %al | ret
```

**原因**：这个例子里没有分支——编译器把它变成了 `setg`（条件置位），
提示自然无从发挥作用。

> [!TIP]
> **分支提示只在「真的有分支、且预测确实困难」时才有意义。**
> 判断办法只有一个：**实测**。
> 在 `perf` 之类的工具下对比，而不是凭感觉加。

## 7.4 什么时候不该用

| 情形 | 做法 |
|---|---|
| 想让小函数内联 | **把函数定义放进头文件**，让编译器看得见 |
| 想开优化 | **改编译选项**（`-O2`），而不是改源码 |
| 想加分支提示 | 先实测；没有改善就去掉 |
| 需要跨编译器 | 别用属性，或者用宏包一层 |

> [!IMPORTANT]
> **优化应该在编译选项层面做，不应该在源码里做。**
> 源码里写死优化意图，会让代码难以移植、难以调试，
> 而且换个编译器就失效。
> **先把 `-O2` 打开，再看还有没有热点。**

# 第 8 节 一张总表

`实测数据`

| 技巧 | 今天还需要吗 | 实测结论 |
|---|---|---|
| 移位代替乘除 | **不需要** | `-O0` 下编译器就已经换掉了 |
| `int8_t` 让运算更快 | **反了** | 运算时提升成 `int`，装回时还要截断 |
| 联合体类型双关 | **用 `memcpy`** | 两者汇编相同，`memcpy` 是标准写法 |
| 跳转表代替 `switch` | **看场合** | 分支多且会增长时值得，但要自己检查下标 |
| 手写 popcount | **用内建函数** | 编译器更清楚目标 CPU 有没有 `popcnt` |
| 位掩码、寄存器操作 | **是语义，不是技巧** | 没有更高级的表达方式 |
| `inline` 请求内联 | **误解** | C 里它管的是要不要生成函数体 |
| `always_inline` | **少用** | 编译器看得比你多 |
| `__builtin_expect` | **先实测** | 简单情形下汇编完全相同 |

> [!IMPORTANT]
> **判断一个技巧今天还需不需要，唯一的办法是实测。**
> **写两版、看汇编、比一下。**
> 相同就说明编译器已经做了——**这时保留手写版只剩下缺点。**
>
> **这一条比本章列出的任何具体技巧都重要。**

> [!IMPORTANT]
> **不要和编译器比谁更懂你的代码。**
> **除非你已经能独立开发出一个 GCC，**
> **否则在「怎么把这段代码变快」这件事上，编译器只会比你更聪明。**

## A.9 `always_inline` 在 `-O0` 下也内联

`C`

```c
/* always_inline.c */
__attribute__((always_inline)) static inline int add_forced(int a, int b) {
    return a + b;                   /* 强制内联 */
}

static inline int add_plain(int a, int b) {
    return a + b;                   /* 只是建议内联 */
}

int call_forced(int x) { return add_forced(x, 1); }
int call_plain(int x)  { return add_plain(x, 1); }
```

`Bash`

```bash
gcc -std=c23 -O0 -S always_inline.c -o always_inline_O0.s
gcc -std=c23 -O2 -S always_inline.c -o always_inline_O2.s
```

`实测数据`

| 函数（`-O0`） | 指令数 | 其中 `call` |
|---|---|---|
| `call_forced` | 13 | **0** |
| `call_plain` | 11 | **1** |
| `add_plain` | 9 | 0 |

**同在 `-O0` 下**：加了 `always_inline` 的调用点里没有 `call`，
函数体被直接展开；没加的那个仍是一条 `call add_plain`。
**`add_forced` 甚至没有单独生成**——它只以展开的形式存在。

`实测数据`

| 函数（`-O2`） | 指令数 | 其中 `call` |
|---|---|---|
| `call_forced` | 2 | **0** |
| `call_plain` | 2 | **0** |

**`-O2` 下两者完全相同**（都是 `leal 1(%rcx), %eax` 加 `ret`）：
**优化一开，不写属性也一样内联**。
