# 第 1 节 教程的意义是辅助理解

## 1.1 一份「这是什么」的清单有什么问题

**先看一份常见的语法清单**：

`Text`

```text
· const 表示常量，不能修改
· static 表示静态，有三种用法
· 数组名是指针，但不能修改
· 引用必须初始化，且不能重新绑定
· sizeof 是运算符不是函数
```

**这些话都对，但把它们背下来，仍然不会用。**

**问题在于这一层只回答「是什么」，不回答「为什么」**：

| 只有结论 | 缺的那一问 |
|---|---|
| `const` 表示常量 | 为什么需要它？不用它会怎样？ |
| `static` 有三种用法 | 三种用法为什么共用一个关键字？ |
| 数组名是指针 | 那为什么 `sizeof` 又不一样？ |
| 引用不能重新绑定 | 为什么？它和指针差在哪？ |
| `sizeof` 是运算符 | 是函数又怎样？ |

**「是函数又怎样」这一问尤其典型**——
它看着像冷知识，但底下藏着一件实事：**运算符没有函数调用的开销，
也不要求参数类型一致**。这就是为什么 `sizeof(arr)` 能拿到整个数组的大小，
而任何形式的函数都做不到。

**不知道这一层，那条「冷知识」就永远只是冷知识。**

## 1.2 两种学习方式的差别

`Text`

```text
   路线甲：收集结论
      学一条 → 记住 → 学下一条 → 记住 → ……
      遇到新问题 → 在记忆里找见过的写法
                  找不到就卡住

   路线乙：理解意图
      遇到一条 → 问它解决什么问题 → 理解 → 下一条
      遇到新问题 → 从意图推导出写法
                  没见过的组合也能应付
```

**两条路线在前期的差别不大**，路线甲甚至更快——
背结论比想问题轻松。

**差别在遇到没见过的组合时显现**：

| 场景 | 路线甲 | 路线乙 |
|---|---|---|
| 写出书上的例子 | 会 | 会 |
| 改一改书上例子 | 大多会 | 会 |
| 组合两个学过的点 | **容易卡住** | 会 |
| 遇到从没见过的需求 | **只能去搜** | 能推 |
| 判断一种写法好不好 | 不会，只能说「书上这么写」 | 会 |

## 1.3 本教材打算怎么做

**结论该给还是要给，但每条结论都要能回答「为什么」。**

具体到写法上：

| 做法 | 说明 |
|---|---|
| **先讲它解决什么问题** | 再讲它长什么样 |
| **给能跑的最小例子** | 不给伪代码 |
| **点出反例** | 不用它会出什么事 |
| **说清代价** | 每个特性都有代价，没有白得的好处 |
| **凡有差异，必问意图** | 见第四节 |

**一句话**：

> [!IMPORTANT]
> **教程的意义是辅助理解。**
> **如果一份讲解去掉「为什么」之后还能完整保留，那它就不是讲解，是索引。**

# 第 2 节 学语言是理解设计者的意图

## 2.1 语法不是任意规定

**初学者容易把语法当成「规定」**——
像是有人凭空定了一堆规矩，读者只能遵守。

**每一条语法都在解决一个具体问题。** 举几个例子：

| 语法 | 它解决的问题 |
|---|---|
| `const` | 让「这个值不该被改」**由编译器保证**，而不是靠注释约定 |
| 引用 `T&` | 传参时既要避免拷贝，又不想写 `*p` 与 `&x` 的噪音 |
| `static` 局部变量 | 要一个「函数私有、但活得比函数调用长」的变量 |
| `enum` | 要一组有名字的整数，且不希望它们互相干扰 |
| **反重包含**（防止同一个头文件被重复包含） | 同一个头文件被包含两次时，让第二次的内容不生效 |

> 表里的「反重包含」：头文件可能被间接包含多次，
若不加防护，同一个头文件的内容会重复展开，导致重复定义。
**通常的写法是用条件编译把整个头文件包起来**，
写法见《04-语法/13-预处理器.md》第 3.2 小节。

> [!IMPORTANT]
> **每一条语法都是「某个问题」的答案。
> 知道了问题，答案就好记；不知道问题，答案就只能背。**

## 2.2 从翻译机器到架构设计

**只会背结论的人，做的是「翻译」**：
把需求翻译成自己见过的写法。

`Text`

```text
   需求  →  [在记忆里搜索相似写法]  → 代码
```

**这条路的天花板很低**：

| 阶段 | 能力 | 上限 |
|---|---|---|
| 翻译机器 | 见过就能写 | 见过的组合 |
| **理解意图** | **能判断该用什么** | **没见过的需求也能应付** |

**区别在能不能按需取用**：

**理解意图的人，工具箱是敞开的**——
他不需要回忆「这个场景书上是怎么写的」，
他知道每个工具解决什么问题，因此能**当场挑一个合适的**。

**进一步**：拿到一个复杂需求时，能把它拆成若干个
「已知问题」，然后各配一个合适的语法工具。
**这就是架构设计在做的事。**

## 2.3 「理解」的标志是什么

**判断是否理解，有三个可自检的标准**：

| 标准 | 具体表现 |
|---|---|
| **能说出它解决什么问题** | 不是「它能做什么」，是「没有它的时候怎么办」 |
| **能说出它的代价** | 每个特性都有代价，说不出代价就是没懂 |
| **能推导出没见过的用法** | 给你一个新场景，能判断该不该用它 |

**第三条最硬**。举一个真实的自检题：

> `static` 用在**函数内部**的变量上、用在**全局变量**上、
> 用在**类成员函数**上，三者的含义看起来毫不相干。
> **它们为什么共用一个关键字？**

**能回答这个问题，说明理解了「存储期与链接」这条线；
不能回答，说明三个 `static` 是分三次背下来的。**

**本章节不给答案**——答案见《04-语法/10-作用域、生存期与链接.md》第 6 节。

# 第 3 节 本教材依据的版本

## 3.1 什么是「C/C++ 版本」

**这两门语言都有国际标准，标准在持续修订，每一版叫一个「版本」。**

`Text`

```text
   C 语言       ISO/IEC 9899
                 ├── C89 / C90      1990
                 ├── C99            1999
                 ├── C11            2011
                 ├── C17            2018
                 └── C23            2024   ← 本教材采用

   C++ 语言     ISO/IEC 14882
                 ├── C++98 / C++03  1998 / 2003
                 ├── C++11          2011
                 ├── C++14          2014
                 ├── C++17          2017   ← 本教材采用
                 ├── C++20          2020
                 └── C++23          2023
```

**几个要点**：

| 要点 | 说明 |
|---|---|
| **版本号是年份** | 指的是标准发布的年份，不是编译器版本 |
| **新版本向后兼容** | 通常旧代码在新标准下照常编译 |
| **不是所有编译器都支持最新版** | 因此选版本时要看编译器 |
| **写法可能受版本影响** | 同一个特性在不同版本里行为可能不同 |

**「C++17」这个词有两个可能的意思，要分清**：

| 说法 | 意思 |
|---|---|
| 「C++17 标准」 | ISO 发布的那份文件（ISO/IEC 14882:2017） |
| 「用 C++17 编译」 | 让编译器按那份标准的规则来处理你的代码 |

**本章节与后续各章节说的是后者。**

**「标准」与「实现」的分工**是一个独立题目，
见《01-编译器/00-语言的实现.md》第 1 节。
那里还讲了标准留给实现的三类自由度，
与本章节第 3.4 小节「看到更新的写法怎么办」直接相关。

## 3.2 采用的标准

| 语言 | 标准 | 为什么选它 |
|---|---|---|
| **C++** | **C++17** | 已被广泛验证、主流采用、主流编译器推荐 |
| **C** | **C23** | 最新已发布标准；`gcc` 的默认就是它 |

**为什么 C 不选与 C++17 同年的 C17**：

| 理由 | 说明 |
|---|---|
| 编译器默认 | `gcc` 不指定参数时**直接用 C23**，读者照抄命令就能对上 |
| **拉近了与 C++ 的距离** | C23 补进了大量 C++ 早已有的写法，**合讲更顺** |
| 避免教完就过时 | C17 已在被替换的过程中 |

**更新的特性也会涉及**，但凡超出这两个版本的写法，
**都会明确标注是哪个版本引入的**。

## 3.3 怎么查自己的编译器用哪个版本

**编译器有「默认标准」与「指定标准」两回事。**
查法是让编译器把内置的宏打印出来，看标准版本宏的取值。

`实测数据`

| 命令 | 宏的值 | 对应标准 |
|---|---|---|
| `gcc -dM -E - < 空文件` | `__STDC_VERSION__ = 202311L` | **C23** |
| `gcc -std=c17 -dM -E - < 空文件` | `__STDC_VERSION__ = 201710L` | C17 |
| `g++ -dM -E -x c++ - < 空文件` | `__cplusplus = 201703L` | **C++17** |
| `g++ -std=c++20 -dM -E -x c++ - < 空文件` | `__cplusplus = 202002L` | C++20 |

**两条对读者有利的结论**：

> [!IMPORTANT]
> **`g++` 的默认标准就是 C++17，`gcc` 的默认就是 C23。**
> **也就是说，不写任何 `-std=` 参数，拿到的正好是本教材采用的两个基准。**

**写代码时可以自己断言版本**（C++17 起可用）：

`C++`

```cpp
/* version_assert.cpp    编译：g++ -std=c++17 version_assert.cpp -o version_assert */
static_assert(__cplusplus >= 201703L, "本文件需要 C++17 或更新");

int main() { return 0; }
```

**完整环境清单**见仓库根目录 `README.md` 的「实测环境」一节；
上面这张表的复现命令见附录 A.1。

## 3.4 看到更新的写法怎么办

**在别处看到 C++20、C++23 甚至 C++26 的写法时**：

| 步骤 | 做什么 |
|---|---|
| 1 | **先确认它是哪个版本引入的**——查手册，不凭印象 |
| 2 | 看自己的编译器支持不支持 |
| 3 | **搞清楚它解决了什么问题**——这一步不能跳 |
| 4 | 若项目基准是 C++17，**不要单独使用**；要升级就整个项目一起升 |

**第 3 步不能跳**：新特性同样是「某个问题的答案」，
知道它解决什么问题，才知道该不该用。

# 第 4 节 C 与 C++ 合讲，因此盯住差异

## 4.1 为什么可以合讲

**C++ 以 C 为基础，语法上高度兼容**——
两者共用的部分占多数，分开讲会大量重复。

**完整说明见《00-写在最初/01-C与C++.md》第 2 节**，
那里讲了「C++ 是 C 的不严格意义上的超集」这句话的准确含义。

**C23 新增的一批构造，写法与 C++ 几乎一致**：

`实测数据`

| 构造 | C23 | C++17 |
|---|---|---|
| `nullptr` | 通过 | 通过 |
| `constexpr` | 通过 | 通过 |
| `bool` / `true` / `false` | 通过 | 通过 |
| `static_assert` | 通过 | 通过 |

**两者都通过，这部分合讲没有障碍**——
`auto x = 42;`、`0b1010`、`1'000'000`、`[[nodiscard]]` 同样两边都通过，
完整的对照表与探针源码见附录 A.2。

## 4.2 为什么示例大量用 C 写

**本板块的示例以 C 为主**，这不是因为 C 更重要，而是四个具体原因。

**一、两门语言共用的部分占多数，一份 C 示例两边都能读。**
C++ 以 C 为基础，运算符、控制流、函数、指针、数组、结构体、字符串、
作用域、预处理器这些规则两门一致或几乎一致。
**反过来不成立**：C 读者读不懂类、引用、模板与异常。
**因此同一段讲解，用 C 写能同时服务两类读者。**

**二、C 更贴近底层，讲「到底发生了什么」时对应关系最干净。**
C 的每个构造几乎都能直接落到机器指令与内存布局上。
本板块大量用「看汇编」来证明结论——**C 代码的汇编与源码几乎一一对应**，
读者一眼能看出哪条指令来自哪一行。
C++ 的高级特性会带来构造、析构、异常处理表、静态初始化等额外产物，
**同样一件事的汇编会长得多，反而看不清主线。**

**三、C++ 的高级特性会引入额外代码，这会干扰对语法本身的观察。**
同一个「装两个 `int` 的结构」加一个使用它的函数：

`实测数据`
`C`

```c
/* point_c.c    编译：gcc -std=c23 -c point_c.c -o point_c.o
 * 完整源码与命令见附录 A.5。
 */
struct Point { int x, y; };             /* 只是数据 */

struct Point g = {1, 2};                /* 全局对象：静态初始化，不需要代码 */

int use(void) {
    struct Point p = {3, 4};            /* 就地初始化 */
    return p.x + p.y;
}

int main(void) { return use(); }
```

`实测数据`
`C++`

```cpp
/* point_cpp.cpp    编译：g++ -std=c++17 -c point_cpp.cpp -o point_cpp.o */
struct Point {
    int x, y;
    Point(int a, int b) : x(a), y(b) {}     /* 构造函数 */
    ~Point() {}                             /* 析构函数 */
};

Point g(1, 2);                          /* 全局对象：main 之前要先构造 */

int use() {
    Point p(3, 4);                      /* 每次调用都要构造与析构 */
    return p.x + p.y;
}

int main() { return use(); }
```

`实测数据`

| 目标文件里的东西 | C | C++ |
|---|---|---|
| `.text`（代码） | 64 字节 | 208 字节，另加构造函数 48、析构函数 16 |
| 全局对象 `g` 放在 | `.data`（16 字节，静态初始化） | `.bss`（16 字节）+ `.ctors`（8 字节） |
| `main` 之前要跑的代码 | **没有** | `_GLOBAL__sub_I_g` |
| 符号名 | `g`、`use`、`main` | `_Z3usev`、`_ZN5PointC1Eii`、`_ZN5PointD1Ev`、`main` |
| `.xdata` + `.pdata`（异常与栈展开表） | 48 字节 | 160 字节 |

**多出来的东西不是语法造成的**，而是「类有构造与析构」这个语义的必然结果。
**讲语法时，这些额外产物只会挡住视线。**

**四、读懂 C 代码本身就是目标。**
操作系统内核、驱动、嵌入式固件、大量基础库都是 C 写的，
**读得懂 C 才读得懂这些代码。**

> [!IMPORTANT]
> **示例用 C 写，讲的是两门语言共用的那部分规则。**
> **凡是 C++ 独有的写法，正文会明确标出**（类、引用、模板、异常、
> `constexpr`、标准库等），需要时给 C 与 C++ 两版对照。

## 4.3 差异是意图的分叉点

**但确实存在差异。** 同一件事在两边的结果不同：

`实测数据`

| 构造 | C23 | C++17 |
|---|---|---|
| 指定初始化器**乱序** | 通过 | **失败** |
| `typeof` | 通过 | **失败** |
| `_Generic` | 通过 | **失败** |
| 复合字面量 `&(struct S){ .a = 1 }` | 通过 | **失败** |
| 变长数组 `int a[n]` | 通过 | 通过**但仅作扩展** |

**VLA 这一条**：《00-写在最初/01-C与C++.md》第 2.3.3 小节已列此项，
那里标注的是「标准不支持，GCC 作为扩展提供」。
**这里可以更进一步**：默认能编过，加 `-pedantic-errors` 即失败。

**初学者看到这张表，反应通常是「记住就行」：C 有这些，C++ 没有。**

**本章节要说的正好相反**：

> [!IMPORTANT]
> **每一处差异都是一条线索，指向设计者的一次选择。**
> **顺着线索问下去，得到的是理解；停在表面前，得到的是一张要背的清单。**

## 4.4 三问法

**本教材处理每一处 C/C++ 差异时，都要回答三个问题：**

| 问 | 要求 |
|---|---|
| **一、差异是什么** | 给出可复现的对照 |
| **二、为什么要分岔** | 指出背后的设计意图 |
| **三、因此该怎么理解** | 把差异归到某条原则上，而不是当成特例 |

**只答第一问是罗列。答到第二问才是讲解。**

**这三问在后续各章节里都会用到。**

## 4.5 实例：一个字面量，两个类型

**按三问法走一遍。**

#### 第一问：差异是什么

**同一份代码分别用 `gcc` 与 `g++` 编译，结果不同。**

`实测数据`
`C`

```c
/* char_literal.c    编译：gcc -std=c23 char_literal.c -o char_literal */
#include <stdio.h>

int main(void) {
    /* 在 C 里，字符字面量的类型是 int */
    printf("C    : sizeof('a') = %d\n", (int)sizeof('a'));
    return 0;
}
```

`C++`

```cpp
/* char_literal.cpp    编译：g++ -std=c++17 char_literal.cpp -o char_literal */
#include <cstdio>

int main() {
    /* 在 C++ 里，字符字面量的类型是 char */
    std::printf("C++  : sizeof('a') = %d\n", (int)sizeof('a'));
    return 0;
}
```

**运行结果**：

`Text`

```text
C    : sizeof('a') = 4      /* 'a' 的类型是 int */
C++  : sizeof('a') = 1      /* 'a' 的类型是 char */
```

**在 C 里，`'a'` 和 `97` 是同一个类型；在 C++ 里不是。**

**这不是冷知识，它会改变重载决议的结果**：

`实测数据`
`C++`

```cpp
/* overload_char.cpp    编译：g++ -std=c++17 overload_char.cpp -o overload_char */
#include <cstdio>

void f(int)  { std::printf("f(int)\n"); }
void f(char) { std::printf("f(char)\n"); }

int main() {
    f('a');        /* 走到 f(char) */
    f(97);         /* 走到 f(int) */
    f((char)97);   /* 走到 f(char) */
    return 0;
}
```

`Text`

```text
f(char)
f(int)
f(char)
```

**`f('a')` 走到了 `f(char)`**——如果 `'a'` 是 `int`，这里会走到 `f(int)`。

#### 第二问：为什么要分岔

**因为 C++ 要支持函数重载。**

**假如 `'a'` 沿用 C 的规定是 `int`**：

| 后果 | 说明 |
|---|---|
| `f('a')` 与 `f(97)` 无法区分 | 两者参数类型相同，重载决议无从下手 |
| 调用会「悄悄走错」 | 不会报错，但可能走到你不期望的那一个 |
| 或者干脆编译失败 | 编译器认为歧义 |

**所以 C++ 必须让字符字面量的类型与 `int` 分开。**
**它回头改了一个从 C 继承来的老细节，只为了让新能力站得住。**

#### 第三问：因此该怎么理解

**这条差异属于一个更大的模式**：

> [!IMPORTANT]
> **C++ 在引入新能力时，会回头修正 C 里那些与新能力冲突的细节。**

**同类的情形还有**：

| 差异 | 同样的动机 |
|---|---|
| 函数声明 `f()` 在 C 里表示「参数不限」，C++ 里表示「无参」 | 重载要求参数类型确定 |
| `void*` 在 C 里可隐式转换，C++ 里不行 | 类型安全 |
| `const` 全局量在 C 里默认外部链接，C++ 里默认内部链接 | 让 `const int MAX = 100;` 能安全写进头文件 |

**看到这类差异时，问题不该是「记住哪一个」，
而该是「C++ 想干什么，才不得不改它」。**

**这几处的完整分析**见《04-语法/02-数据类型与类型系统.md》第 6 节
与《04-语法/10-作用域、生存期与链接.md》第 5 节。

# 第 5 节 怎么用这套讲解

> [!TIP]
> **这一节是操作手册**——前四节回答「为什么这样学」，这一节回答「具体怎么读」。
> **它比前面任何一节都用得多**，尤其 5.1 与 5.5；
> 不按它们说的方法读，后面各章节的编排会显得没有道理。
> **读到第一个「看不懂」的地方时，回来重看这一节。**

## 5.1 语法是一张网

**语法点不是排成一列的清单，而是一张相互搭接的网。**

`Text`

```text
   重载 ────── 类型转换
     │            │
     │        字面量的类型
     │            │
   名字修饰 ─── 链接 ─── static ─── 存储期
                              │
                          作用域
```

#### 网不是编排选择，是语法的固有性质

**先接受一个事实：语法点的依赖关系里有环。**

**举一个真实存在的环**：

`Text`

```text
   讲清「引用有什么用」  ──需要先懂──▶  函数怎么传参
        ▲                                      │
        │                                      │
        └── 讲清「函数传参的效率」需要先懂 ──────┘
```

**引用是为函数传参而设计的**——避免拷贝、免去 `*p` 与 `&x` 的噪音。
**但要说明白「为什么需要引用」，又必须先讲清参数传递有哪几种方式。**

**这个环不是本教材编排得不好，而是语法本身如此。**

**任何按线性顺序讲的教材都会撞上它，处理方式无非三种**：

| 处理方式 | 结果 |
|---|---|
| 假装没有环，硬按顺序讲 | 读者在第一个环处卡住，且不知道为什么卡 |
| 把互相依赖的点全塞进同一个章节 | 那个章节长得读不完，而且仍然有环 |
| **允许「先知道名字，后理解含义」** | **本教材采用** |

#### 解法：两轮读法

**本教材把「理解」拆成两轮，而不是要求一次到位**：

| 轮次 | 目标 | 允许暂时不理解 |
|---|---|---|
| **第一轮** | 知道**有这么个东西**、它大致解决什么问题 | 细节、边界、原理、例外 |
| **第二轮** | 理解**为什么这样设计**、什么时候该用、代价是什么 | —— |

**落到写法上，就是那条约定**：

> [!IMPORTANT]
> **术语第一次出现时给一句话定义，并当场指向详解章节。**

**两者缺一不可**：

| 只有跳转标记 | 只有一句话定义 |
|---|---|
| 读者当场卡住，不知道那是什么 | 读者以为已经讲完了，不知道后面还有 |
| 无法继续往下读 | 回头补的线索断了 |

**这条约定与《AGENTS.md》里「不写空引用」的规定是同一件事**——
它不是格式要求，**而是为了打通这张网上的环**。

**因此你在读到 `【待补：…】` 或一句轻量的括号说明时，
正确的反应不是跳过，而是「记下位置，继续读，回头补」。**

#### 章节开头与末尾的两组链接

**因此本套讲解的每一章节都带两组链接**：

| 位置 | 内容 |
|---|---|
| **章节开头** | 「本章节在这张网的什么位置」——前置节点与本章节引出的节点 |
| **章节末尾** | 「相邻节点」——与本章节互相依赖的其他章节 |

**《04-语法/README.md》里有一张总图**，画的是这张网。

#### 具体怎么用

**章节开头那张「网中的位置」不是装饰，它有实际用处。** 三种读法：

| 你的情况 | 怎么做 |
|---|---|
| **顺读**（从第一个章节往下看） | 扫一眼「前置」，**缺哪个就先补哪个**，不要硬撑 |
| **跳读**（只查某一个点） | 看「前置」够不够；不够就先读前置，**否则这一段会读不懂** |
| **卡住了** | 回到开头的定位表，**多半是某个前置节点没读** |

**末尾的「相邻节点」是反向用的**：
读完一个章节后想知道「接下来该看什么」，看那里。

**举一个实际的例子**：

`Text`

```text
   你在 07-数组、指针与引用 里读「数组名会退化成指针」，发现看不懂
        ↓
   回看 07 的「前置」：02-数据类型与类型系统、03-表达式与运算符
        ↓
   再回看 02 的「前置」，发现「左值/右值」是在 03 里讲的
        ↓
   先补 03 的对应小节，再回来读 07
```

**这不是绕路。** 语法本来就是网状的，
**顺着节点走比硬啃一个孤立段落快得多。**

## 5.2 标注与提示块约定

**标注以行内代码单独成行，写在对应的表格或代码块正上方**：

| 标注 | 含义 |
|---|---|
| `实测数据` | 在实际环境中执行并验证过，输出可复现 |
| `文档` | 来源于官方文档、标准或权威资料，后接英文原文引用与出处 |
| `待确认` | 有合理推断但未验证，或依赖外部条件 |

**本套讲解尽量给出可复现的数据**——一个能跑的例子比一段描述更有说服力。

**正文里的提示块按用途分五级，颜色固定**：

| 用途 | 写法 |
|---|---|
| 结论、要点、本质概括 | `> [!IMPORTANT]` |
| 小结、回顾 | `> [!NOTE]` |
| 提示、做法建议、经验 | `> [!TIP]` |
| 警告、可能出错 | `> [!WARNING]` |
| 严重后果（数据损坏、未定义行为、安全） | `> [!CAUTION]` |

## 5.3 关于标准原文

**本教材以 ISO 标准为严格参考，但不把标准原文当作讲解主线。**

| 场合 | 用法 |
|---|---|
| 需要精确界定某个概念 | 引原文，标明出处 |
| 有常见误解需要纠正 | 用原文说明标准实际怎么写的 |
| **其余场合** | **以直通本质的讲解与可运行的演示为主** |

**理由**：标准是为实现者写的，不是为学习者写的。
它追求无歧义，因此写法上高度克制，直接读会很吃力。
**先用直白的方式讲明白，再回头看标准，那时才读得进去。**

## A.2 两个标准都接受的构造

`C`

```c
/* shared.c    编译：gcc -std=c23 -c shared.c -o shared_c.o
                或   g++ -std=c++17 -x c++ -c shared.c -o shared_cpp.o
   C 与 C++ 写法相同 */
#include <stddef.h>

constexpr int max_len = 100;
bool flag = true;
```

**两条编译命令都通过。**

## A.3 只有 C23 接受的构造

`C`

```c
/* conly.c    编译：gcc -std=c23 -c conly.c -o conly_c.o     通过
                或   g++ -std=c++17 -x c++ -c conly.c        失败 */
struct S { int a; int b; };

struct S s = { .b = 2, .a = 1 };            /* 指定初始化器乱序 */
typeof(int) t = 1;                          /* typeof */
int g = _Generic(1, int: 1, default: 0);    /* _Generic */
struct S *p = &(struct S){ .a = 1 };        /* 复合字面量 */
```

**C++17 下四条全部失败**，报错依次是
「designator order ... does not match declaration order」、
「expected constructor, destructor, or type conversion before 't'」、
「`_Generic` was not declared in this scope」、
「taking address of rvalue」。

## A.5 同一个结构，C 与 C++ 的目标文件差多少

`C`

```c
/* point_c.c */
struct Point { int x, y; };             /* 只是数据 */

struct Point g = {1, 2};                /* 全局对象：静态初始化，不需要代码 */

int use(void) {
    struct Point p = {3, 4};            /* 就地初始化 */
    return p.x + p.y;
}

int main(void) { return use(); }
```

`C++`

```cpp
/* point_cpp.cpp */
struct Point {
    int x, y;
    Point(int a, int b) : x(a), y(b) {}     /* 构造函数 */
    ~Point() {}                             /* 析构函数 */
};

Point g(1, 2);                          /* 全局对象：main 之前要先构造 */

int use() {
    Point p(3, 4);                      /* 每次调用都要构造与析构 */
    return p.x + p.y;
}

int main() { return use(); }
```

`Bash`

```bash
gcc -std=c23 -c point_c.c -o point_c.o
g++ -std=c++17 -c point_cpp.cpp -o point_cpp.o
objdump -h point_c.o        # 段表：.text .data 与异常表
objdump -h point_cpp.o      # 多出 .ctors 与构造函数、析构函数的独立段
nm point_c.o                # D g / T use / T main
nm point_cpp.o              # B g / _Z3usev / _ZN5PointC1Eii / _ZN5PointD1Ev / T main
                            # 另有 _GLOBAL__sub_I_g（main 之前运行的构造代码）
```

`实测数据`

| 目标文件里的东西 | `point_c.o` | `point_cpp.o` |
|---|---|---|
| `.text` | 64 字节 | 208 字节 |
| 构造函数 | 无 | 48 字节（独立段） |
| 析构函数 | 无 | 16 字节（独立段） |
| 全局对象 `g` | `.data`，16 字节 | `.bss`，16 字节 |
| 静态初始化 | 不需要 | `.ctors`，8 字节 |
| `main` 之前的初始化函数 | 无 | `_GLOBAL__sub_I_g` |
| `.xdata` + `.pdata` | 48 字节 | 160 字节 |

**`main` 是唯一没被修饰的名字**：C++ 里函数名会被修饰成 `_Z3usev` 这样的形式，
而 `main` 保持原样——运行环境要按这个名字找到入口。
