上一章回答的是「对象在哪一段内存里」，这一章接着问第二个问题：**它落在那个段里的哪个地址上**。
这个问题的答案不只影响空间，还直接影响速度：一个 4 字节的整数放在 4 的倍数上，
硬件一条指令就能搬走；放在奇数地址上，在 x86-64 上要多花一点时间，
在只有字节访问能力的机器上要拆成四条字节指令拼起来。

结构体的布局是这件事最常见的现场。编译器为了让每个成员落在合适的位置上，
会往里塞一些谁也没写的字节——标准里叫**无名填充**，
它们是「同一个结构体在两个目标上大小不同」的直接原因。
把填充去掉的办法有两种（`#pragma pack` 与 `__attribute__((packed))`），
代价是把对齐的负担从编译器转嫁给了运行期。

到有缓存的机器上，这一层还会多出一个问题：**数据在缓存里还是内存里**。
两个线程各改各的变量却因为落在同一条缓存行上而互相拖慢（伪共享），
DMA 搬完数据却发现 CPU 看到的是缓存里的旧值（缓存一致性），
都是同一个机制的两面。本章用 STM32F103C8 做对照面：**Cortex-M3 没有缓存**，
这些麻烦一个都没有，代价是每一次取指都要等 flash。

# 第 1 节 为什么硬件要求对齐

## 1.1 一次访存落到总线上是什么样

内存不是「一个字节一个字节」被访问的。总线按字（word）搬运：
32 位总线上一次搬 4 字节，而且这 4 字节的起始地址必须是 4 的倍数。
一个 `uint32_t` 如果落在 `0x20000001`，硬件面前有两条路：
要么不支持（直接报错），要么拆成两次访问再拼起来（慢）。

标准对这一点的态度是**不规定**，只承认「有对齐要求」这件事：

`文档`

> "Complete object types have alignment requirements which place restrictions on the addresses
> at which objects of that type may be allocated. An alignment is an implementation-defined integer
> value representing the number of bytes between successive addresses at which a given object can be
> allocated. An object type imposes an alignment requirement on every object of that type:
> stricter alignment can be requested using the alignas keyword."
>
> —— N3220 §6.2.8/1

「implementation-defined」这四个字意味着：**对齐是多少、不对齐会怎样，都不由语言决定**，
由 ABI 与硬件决定。三种常见硬件的态度差别很大：

`实测数据`

| 目标 | 非对齐的单字访问 | 编译器生成的指令 | 在真板／主机上的表现 |
|---|---|---|---|
| x86-64 | 硬件允许 | `movl 1(%rcx), %eax` | 正常，代价在跨越缓存行时 |
| Cortex-M3／M4 | 单字 `LDR`/`STR` 允许 | `ldr r0, [r0, #1]  @ unaligned` | **9 周期**，不触发故障 |
| Cortex-M0／M0+ 与多字访问 | 不允许 | 4 条 `ldrb` + 3 条 `orr` | 需 `待确认`（手头只有 Cortex-M3 的板子） |

Cortex-M3 那一行是在真板上测出来的：把一个 `buf + 1` 当地址读一个 `uint32_t`，
用掉 9 个周期，程序没有进 HardFault。**但这不代表可以随便写**：
换到 Cortex-M0、或者让编译器把几次访问合并成 `LDM`/`STM`（多字访问要求对齐），
同一份源码的后果就不同了。

> [!CAUTION]
> **「我的机器上能跑」不是对齐问题的判据。** 非对齐访问在 x86-64 与 Cortex-M3/M4 上
> 不报错，在 Cortex-M0、某些 DSP、以及把访问合并成多字指令时就会出错。
> 编译器给出的 `-Waddress-of-packed-member` 警告值得当错误处理（第 2.5 小节）。

## 1.2 真板上测到的代价

`对齐` 这个词在书里出现太多次，容易让人以为它只是「规范要求」。
它在真板上是可以直接数出周期数的。下面这张表来自 STM32F103C8
（Cortex-M3、HSI 8 MHz，1 周期 = 125 ns），用 SysTick 数内核周期：

`实测数据`

| 操作 | 周期数 | 折合时间 | 说明 |
|---|---|---|---|
| 对齐的 32 位访问（`uint32_t`） | **8** | 1.00 µs | 编译器一条 `ldr` 完成 |
| 同一个字**逐字节**拼起来 | **18** | 2.25 µs | 4 条 `ldrb` 加 3 条 `orr`，**2.25 倍** |
| `packed` 结构体的字段 | **10** | 1.25 µs | 编译器改成非对齐单字访问 |
| **非对齐**的 32 位访问（`buf + 1`） | **9** | 1.125 µs | M3 允许单字非对齐，不触发故障 |
| `volatile` 读一次 RAM 变量 | 6 | 0.75 µs | 对照组：一次普通读 |
| `volatile` 读一次外设寄存器 | 9 | 1.125 µs | 对照组：外设总线上的一次读 |

**8 与 18 之间就是「对齐」的价钱**：同一个 4 字节的值，
对齐访问一条指令拿走，逐字节访问要四条读加三次移位合并。
2.25 倍这个数字在 8 MHz 的芯片上就是 1 µs 与 2.25 µs 的差别——
在一个 1 kHz 的控制循环里，这是 0.1% 与 0.225% 的 CPU 时间。

**`packed` 结构体只慢了 2 个周期**（10 对 8），因为 Cortex-M3 的硬件允许非对齐单字访问，
编译器直接生成了一条带 `@ unaligned` 注释的 `ldr`：

`实测数据`
`Assembly`

```asm
read_normal:                          read_packed:
	ldr	r0, [r0, #4]                    ldr	r0, [r0, #1]	@ unaligned
	bx	lr                              bx	lr
```

**换一台不允许非对齐的机器，同一份源码就变成七条指令。**
第 2.3 小节用同一份 `packed_cost.c` 把三种目标的产物并排贴出来。

## 1.3 x86-64 上的代价藏在哪

x86-64 上做同样的对照，会看到一个「没有差别」的结果：

`实测数据`
`Assembly`

```asm
read_normal:                          read_packed:
	movl	4(%rcx), %eax                   movl	1(%rcx), %eax
	ret                                     ret

write_normal:                         write_packed:
	movl	%edx, 4(%rcx)                   movl	%edx, 1(%rcx)
	ret                                     ret
```

**指令条数完全相同**：x86-64 的硬件直接支持非对齐访问，
编译器不需要为 `packed` 生成特殊代码。那代价在哪？

- **跨越缓存行时**：一个 4 字节的读如果横跨两条 64 字节缓存行，
  硬件要访问两个缓存行，代价明显上升（第 3 节会量缓存行）；
- **跨越页边界时**：极端情况下会触发两次地址翻译；
- **被编译器合并成向量指令时**：`-O2` 下若把多个成员的访问合并成一条 `movups`，
  非对齐的影响会重新出现（`movups` 本身就是为非对齐准备的，代价仍在硬件里）。

**结论：x86-64 上的对齐问题以「性能抖动」的形式出现，不以「崩溃」的形式出现**；
而 Cortex-M0 一类目标上它以「指令数翻几倍」的形式出现。
两边都要靠同一件事避免：**让数据落在它该在的地址上**。

## 1.4 小结

> [!NOTE]
> 对齐要求来自硬件：总线按字搬运，地址必须是字长的整数倍。
> 标准只写「对齐由实现定义」，实际值由 ABI 与芯片决定。
> 不对齐的后果分三档：x86-64 与 Cortex-M3/M4 允许（代价藏在缓存行与时钟周期里），
> Cortex-M0 一类目标拆成字节指令（真板上测到 2.25 倍），
> 多字访问（`LDM`/`STM`）在所有 ARM 上都要求对齐。

# 第 2 节 结构体里发生了什么

## 2.1 一张 `sizeof`／`offsetof` 表

同样四个字段，四种排法，大小从 14 到 64 都有。先看 x86-64 上的真值。

`C`

```c
/* layout.c   编译：gcc -std=c23 -O2 layout.c -o layout.exe
   运行：layout.exe                                                          */
#include <stdio.h>
#include <stddef.h>
#include <stdalign.h>

struct Plain {          /* 编译器按自然对齐排：每个成员落在自己大小的整数倍上 */
    char   a;
    int    b;
    char   c;
    double d;
};

#pragma pack(push, 1)
struct Pack1 {          /* MSVC 与 GCC 都认的写法 */
    char   a;
    int    b;
    char   c;
    double d;
};
#pragma pack(pop)

struct __attribute__((packed)) AttrPack {   /* GCC 专有的写法 */
    char   a;
    int    b;
    char   c;
    double d;
};

struct Aligned64 {      /* 提高对齐：整个对象按 64 字节对齐 */
    alignas(64) int x;
};

int main(void)
{
    printf("sizeof(struct Plain)     = %2zu  对齐 %2zu\n", sizeof(struct Plain),     alignof(struct Plain));
    printf("sizeof(struct Pack1)     = %2zu  对齐 %2zu\n", sizeof(struct Pack1),     alignof(struct Pack1));
    printf("sizeof(struct AttrPack)  = %2zu  对齐 %2zu\n", sizeof(struct AttrPack),  alignof(struct AttrPack));
    printf("sizeof(struct Aligned64) = %2zu  对齐 %2zu\n", sizeof(struct Aligned64), alignof(struct Aligned64));
    printf("\n字段偏移（字节）：\n");
    printf("%-16s %-8s %-8s %-8s %-8s\n", "结构体", "a", "b", "c", "d");
    printf("%-16s %-8zu %-8zu %-8zu %-8zu\n", "struct Plain",
           offsetof(struct Plain, a), offsetof(struct Plain, b),
           offsetof(struct Plain, c), offsetof(struct Plain, d));
    printf("%-16s %-8zu %-8zu %-8zu %-8zu\n", "struct Pack1",
           offsetof(struct Pack1, a), offsetof(struct Pack1, b),
           offsetof(struct Pack1, c), offsetof(struct Pack1, d));
    printf("%-16s %-8zu %-8zu %-8zu %-8zu\n", "struct AttrPack",
           offsetof(struct AttrPack, a), offsetof(struct AttrPack, b),
           offsetof(struct AttrPack, c), offsetof(struct AttrPack, d));

    printf("\nPlain 在内存里的字节（char a='A'  int b=0x11223344  char c='B'  double d=1.0）：\n");
    struct Plain p = { 'A', 0x11223344, 'B', 1.0 };
    const unsigned char *q = (const unsigned char *)&p;
    for (size_t i = 0; i < sizeof p; ++i) printf("%02x ", q[i]);
    printf("\n偏移 0=char  4=int  8=char  16=double：1..3、9..15 是填充\n");
    return 0;
}
```

`实测数据`
`Text`

```text
sizeof(struct Plain)     = 24  对齐  8
sizeof(struct Pack1)     = 14  对齐  1
sizeof(struct AttrPack)  = 14  对齐  1
sizeof(struct Aligned64) = 64  对齐 64

字段偏移（字节）：
结构体        a        b        c        d
struct Plain     0        4        8        16
struct Pack1     0        1        5        6
struct AttrPack  0        1        5        6

Plain 在内存里的字节（char a='A'  int b=0x11223344  char c='B'  double d=1.0）：
41 00 00 00 44 33 22 11 42 dd 4a ab f8 7f 00 00 00 00 00 00 00 00 f0 3f
```

四个字段一共 1 + 4 + 1 + 8 = 14 字节，自然排法占 24 字节——
**多出来的 10 字节全是填充**：

| 位置 | 字节 | 是什么 |
|---|---|---|
| 偏移 0 | `41` | `a = 'A'` |
| 偏移 1–3 | `00 00 00` | **填充**：让 `b` 落在 4 的倍数上 |
| 偏移 4–7 | `44 33 22 11` | `b = 0x11223344`（小端：低位在前） |
| 偏移 8 | `42` | `c = 'B'` |
| 偏移 9–15 | `dd 4a ab f8 7f 00 00` | **填充**：让 `d` 落在 8 的倍数上 |
| 偏移 16–23 | `00 00 00 00 00 00 f0 3f` | `d = 1.0` 的 IEEE 754 位模式 |

**注意偏移 9 到 15 那几个字节的内容**：`dd 4a ab f8 7f 00 00` 看起来像一个地址的低半截。
填充字节的值标准没有规定，编译器也不保证它们是 0——
第 2.6 小节会看到，把这 24 字节整体写给文件时，这几个字节会一起被写出去。

## 2.2 同一张表在 Cortex-M 上

同一份布局规则换个目标会不会变？把结构体换掉、打印函数换成 semihosting，
在 Cortex-M3 上跑一遍：

`C`

```c
/* layout_arm.c   交叉编译（Cortex-M3）：arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -c layout_arm.c -o layout_arm.o
   完整构建与运行（在 WSL 的 Ubuntu 里）：
     arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -nostartfiles --specs=nosys.specs \
       -T STM32F103C8_FLASH.ld startup_stm32f103xe.s layout_arm.c -o layout_arm.elf
     qemu-system-arm -M netduinoplus2 -kernel layout_arm.elf -nographic \
       -semihosting-config enable=on,target=native */
#include <stdint.h>
#include <stddef.h>
#include <stdalign.h>

struct Plain { char a; int b; char c; double d; };
#pragma pack(push, 1)
struct Pack1 { char a; int b; char c; double d; };
#pragma pack(pop)
struct __attribute__((packed)) AttrPack { char a; int b; char c; double d; };
struct Aligned64 { alignas(64) int x; };

static void sh_puts(const char *s)
{
#if defined(__arm__)
    register uint32_t r0 __asm__("r0") = 0x04u;
    register const char *r1 __asm__("r1") = s;
    __asm__ volatile ("bkpt 0xAB" : : "r"(r0), "r"(r1) : "memory");
#else
    (void)s;
#endif
}
static void sh_dec(uint32_t v)
{
    char b[12]; int i = 11; b[i--] = '\0';
    if (!v) b[i--] = '0';
    while (v) { b[i--] = (char)('0' + v % 10u); v /= 10u; }
    sh_puts(&b[i + 1]);
}
static void row(const char *name, uint32_t sz, uint32_t al,
                uint32_t oa, uint32_t ob, uint32_t oc, uint32_t od)
{
    sh_puts(name); sh_puts(" sizeof="); sh_dec(sz); sh_puts(" align="); sh_dec(al);
    sh_puts(" off="); sh_dec(oa); sh_puts(","); sh_dec(ob);
    sh_puts(","); sh_dec(oc); sh_puts(","); sh_dec(od);
    sh_puts("\r\n");
}

void SystemInit(void) { }
void _init(void) { }

int main(void)
{
    row("Plain   ", sizeof(struct Plain), alignof(struct Plain),
        offsetof(struct Plain, a), offsetof(struct Plain, b),
        offsetof(struct Plain, c), offsetof(struct Plain, d));
    row("Pack1   ", sizeof(struct Pack1), alignof(struct Pack1),
        offsetof(struct Pack1, a), offsetof(struct Pack1, b),
        offsetof(struct Pack1, c), offsetof(struct Pack1, d));
    row("AttrPack", sizeof(struct AttrPack), alignof(struct AttrPack),
        offsetof(struct AttrPack, a), offsetof(struct AttrPack, b),
        offsetof(struct AttrPack, c), offsetof(struct AttrPack, d));
    row("Aligned64", sizeof(struct Aligned64), alignof(struct Aligned64), 0, 0, 0, 0);
    for (;;) { }
}
```

`实测数据`
`Text`

```text
$ qemu-system-arm -M netduinoplus2 -kernel layout_arm.elf -nographic \
    -semihosting-config enable=on,target=native
Plain    sizeof=24 align=8 off=0,4,8,16
Pack1    sizeof=14 align=1 off=0,1,5,6
AttrPack sizeof=14 align=1 off=0,1,5,6
Aligned64 sizeof=64 align=64 off=0,0,0,0
```

**四行数字与 x86-64 上的完全一致**。这不是巧合：
32 位与 64 位 ARM 的 AAPCS 和 x86-64 的两套 ABI，对这几种基本类型给出的宽度与对齐相同
（`char` 1/1、`int` 4/4、`double` 8/8），于是填充的位置也一样。
**换一个 ABI 就可能不一样**：比如某个平台上 `double` 是 4 字节对齐，
`d` 的偏移就会从 16 变成 12，`sizeof` 从 24 变成 20。
写线格式的程序不能依赖这张表碰巧一致。
## 2.3 `packed` 的访问代价

上一节的周期数差（8 对 10）来自指令本身。把这件事看清楚的程序只有十行：

`C`

```c
/* packed_cost.c   编译（只看汇编）：gcc -std=c23 -O2 -S packed_cost.c -o packed_x86.s
   交叉编译（Cortex-M3）：arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 \
                          -S packed_cost.c -o packed_m3.s
   交叉编译（Cortex-M0）：arm-none-eabi-gcc -mcpu=cortex-m0 -mthumb -O2 \
                          -S packed_cost.c -o packed_m0.s                        */
#include <stdint.h>

struct Normal { uint8_t tag; uint32_t value; uint8_t flag; };

#pragma pack(push, 1)
struct Packed { uint8_t tag; uint32_t value; uint8_t flag; };
#pragma pack(pop)

uint32_t read_normal(const struct Normal *p) { return p->value; }
uint32_t read_packed(const struct Packed *p) { return p->value; }

void write_normal(struct Normal *p, uint32_t v) { p->value = v; }
void write_packed(struct Packed *p, uint32_t v) { p->value = v; }
```

`struct Normal` 里 `value` 的偏移是 4（对齐），`struct Packed` 里是 1。
两种 `packed` 写法（`#pragma pack` 与 `__attribute__((packed))`）在这里的产物相同，
本节只留一种。

`实测数据`
`Assembly`

```asm
; ① Cortex-M3，默认（允许非对齐单字访问）：一条 ldr
read_packed:
	ldr	r0, [r0, #1]	@ unaligned
	bx	lr

; ② 同一颗 M3，加 -mno-unaligned-access：4 条 ldrb + 3 条 orr
read_packed:
	ldrb	r3, [r0, #1]
	ldrb	r1, [r0, #2]
	ldrb	r2, [r0, #3]
	orr	r3, r3, r1, lsl #8
	ldrb	r0, [r0, #4]
	orr	r3, r3, r2, lsl #16
	orr	r0, r3, r0, lsl #24
	bx	lr

; ③ Cortex-M0（硬件没有非对齐访问）：同样拆成字节
read_packed:
	ldrb	r2, [r0, #2]
	ldrb	r3, [r0, #1]
	lsls	r2, r2, #8
	orrs	r2, r3
	ldrb	r3, [r0, #3]
	ldrb	r0, [r0, #4]
	lsls	r3, r3, #16
	orrs	r3, r2
	lsls	r0, r0, #24
	orrs	r0, r3
```

**同一份 C 代码、同一个编译器，因为目标不同，指令数从 2 条变成 9 条。**
这就是「对齐的代价」在编译器这一侧的样子：它不由源码决定，由目标决定。

`实测数据`

| 目标与选项 | `read_packed` 的指令数 | 真板上的周期数 |
|---|---|---|
| Cortex-M3（默认） | 2（一条非对齐 `ldr`） | 10 |
| Cortex-M3（`-mno-unaligned-access`） | 9 | 与「逐字节拼」同档（真板测到 18） |
| Cortex-M0 | 12 | `待确认`（手头只有 Cortex-M3 的板子） |
| x86-64 | 2（一条 `movl`，与对齐时相同） | 代价藏在跨缓存行时 |

**x86-64 那一行值得单独记住**：`packed` 在那里的指令与对齐版本完全一样，
代价既不在指令数上，也不在「崩不崩」上，而是在缓存与地址翻译那一层。
第 3 节会量缓存行，到时能看到代价从哪冒出来。

## 2.4 写错了会怎样（一）：取 `packed` 成员的地址

`packed` 有一个隐蔽得多的用法错误：不是直接读成员，而是**取成员的地址传出去**。
一旦取地址，编译器就无法在访问点做「非对齐单字读」的优化，只能生成一个
`uint32_t *`，而那个指针指向的地址很可能不满足 `uint32_t` 的对齐要求。

`C`

```c
/* packaddr.c   编译：gcc -std=c23 -O2 -Wall -c packaddr.c -o packaddr.o
   （只编译不链接：这是编译期警告，与运行无关） */
#include <stdint.h>

struct __attribute__((packed)) P { uint8_t tag; uint32_t value; };

uint32_t load(const uint32_t *p) { return *p; }

uint32_t bad(struct P *s) { return load(&s->value); }   /* 取 packed 成员的地址 */
```

GCC 与 Clang 都会在这里给出警告，而且是**默认就开**的：

`实测数据`
`Text`

```text
$ arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -Wall -c packaddr.c -o packaddr.o
packaddr.c: In function 'bad':
packaddr.c:5:41: warning: taking address of packed member of 'struct P' may result in an unaligned pointer value [-Waddress-of-packed-member]
    5 | uint32_t bad(struct P *s) { return load(&s->value); }
      |                                         ^~~~~~~~~
```

**这条警告在 Cortex-M3 上可能什么也不发生**（硬件允许非对齐），
在 Cortex-M0 上会让那次间接访问被拆成字节访问（慢但不崩），
在把该指针交给 DMA 或 `memcpy` 时会变成真故障：
`memcpy` 与 DMA 都倾向于按字搬运，而字访问要求对齐。
**「警告默认开着」意味着编译器认为这是常见错误**，值得当错误处理：

`Bash`

```bash
# 把它升级成错误，避免漏过
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -Werror=address-of-packed-member -c packaddr.c
```

正确的做法是**按值取出来再用**，或者给结构体加回对齐：

`C`

```c
/* packaddr_fix.c   编译：gcc -std=c23 -O2 -Wall -c packaddr_fix.c -o packaddr_fix.o */
#include <stdint.h>

struct __attribute__((packed)) P { uint8_t tag; uint32_t value; };

/* 写法一：把值复制出来（多一次赋值，换来一个对齐的局部变量） */
uint32_t good_copy(const struct P *s) { uint32_t v = s->value; return v; }

/* 写法二：把字段本身声明成对齐的（-Wpadded 也不再抱怨） */
struct Q { uint8_t tag; uint32_t value __attribute__((aligned(4))); } __attribute__((packed));
```

## 2.5 写错了会怎样（二）：把结构体当线格式

第二个坑更常见：**把结构体的内存直接写成文件或发到网络上**。
上一节的 24 字节里有 10 个字节是填充，其中 7 个字节的值没有规定。
下面这份程序把同一个记录按两种排法各写一份。

`C`

```c
/* wire.c   编译：gcc -std=c23 -O2 wire.c -o wire.exe
   运行：wire.exe                                                          */
#include <stdio.h>
#include <stdint.h>
#include <stddef.h>

struct Record {          /* 自然的排法 */
    uint8_t  kind;
    uint32_t id;
    uint8_t  flag;
    double   value;
};

#pragma pack(push, 1)
struct WireRecord {      /* 逐字节紧凑，用来当线格式 */
    uint8_t  kind;
    uint32_t id;
    uint8_t  flag;
    double   value;
};
#pragma pack(pop)

static void dump(const char *name, const void *p, size_t n)
{
    const unsigned char *b = (const unsigned char *)p;
    printf("%-10s %2zu 字节：", name, n);
    for (size_t i = 0; i < n; ++i) printf("%02x ", b[i]);
    printf("\n");
}

int main(void)
{
    struct Record     r = { 1, 0x0000ABCDu, 1, 6.25 };
    struct WireRecord w = { 1, 0x0000ABCDu, 1, 6.25 };

    FILE *f1 = fopen("record_natural.bin", "wb");
    fwrite(&r, sizeof r, 1, f1); fclose(f1);
    FILE *f2 = fopen("record_packed.bin", "wb");
    fwrite(&w, sizeof w, 1, f2); fclose(f2);

    dump("自然排法", &r, sizeof r);
    dump("packed", &w, sizeof w);
    printf("\n两个文件的长度：自然 %zu，packed %zu\n", sizeof r, sizeof w);
    printf("kind/id/flag/value 的偏移：自然 %zu/%zu/%zu/%zu，packed %zu/%zu/%zu/%zu\n",
           offsetof(struct Record, kind), offsetof(struct Record, id),
           offsetof(struct Record, flag), offsetof(struct Record, value),
           offsetof(struct WireRecord, kind), offsetof(struct WireRecord, id),
           offsetof(struct WireRecord, flag), offsetof(struct WireRecord, value));
    return 0;
}
```

`实测数据`
`Text`

```text
自然排法 24 字节：01 00 00 00 cd ab 00 00 01 dd 4a ab f8 7f 00 00 00 00 00 00 00 00 19 40
packed     14 字节：01 cd ab 00 00 01 00 00 00 00 00 00 19 40

两个文件的长度：自然 24，packed 14
kind/id/flag/value 的偏移：自然 0/4/8/16，packed 0/1/5/6
```

三个问题一次暴露：

1. **长度不同**：24 与 14，差 10 字节。写入方与读取方只要一方用了自然排法，
   整个文件就错位；
2. **里面有未初始化的字节**：自然排法里偏移 9–15 那 7 个字节是 `dd 4a ab f8 7f 00 00`，
   既不是 `kind` 也不是 `id`，是内存里的残留内容。**把它写进文件或发到网络就是信息泄露**，
   而且每次运行可能不同；
3. **布局依赖 ABI**：自然排法的偏移 `0/4/8/16` 是这套 ABI 的结果，
   换一套 ABI（比如 `double` 只要求 4 字节对齐）就变成 `0/4/8/12`，长度变成 20。

**线格式要么显式按字节序列化，要么整体 `packed` 并固定字节序**——
`packed` 只解决对齐填出来的空洞，不解决字节序（那是
《06-更底层/04-字节序与数据表示.md》章节的主题）。
配套练习 [C-templates/06-lower-level/01-layout-probe/](../C-templates/06-lower-level/01-layout-probe/)
就是让你把这张表在三个目标上各打一遍，看看哪几行会变。

## 2.6 `alignas`：把对齐提高一档

前面的例子都在「减少」对齐，`alignas` 是反方向：**要求更严的对齐**。
`struct Aligned64` 的 `sizeof` 是 64，因为整个对象被要求落在 64 的倍数上。
标准里这条要求的措辞是「stricter alignment can be requested using the alignas keyword」
（N3220 §6.2.8/1）。为什么要提高对齐？因为**缓存行**。

`实测数据`

| 结构体 | `sizeof` | 对齐 | 常见用途 |
|---|---|---|---|
| `struct Plain` | 24 | 8 | 普通数据 |
| `struct Pack1` / `AttrPack` | 14 | 1 | 线格式、通信帧 |
| `struct Aligned64` | 64 | 64 | 让对象独占一条缓存行（第 3 节） |
| `max_align_t`（x86-64） | 32 | 16 | `malloc` 保证的对齐上限 |

**对齐提高的代价是空间**：`Aligned64` 里只有一个 `int`，却占了 64 字节。
在有缓存的机器上这个交换经常划算（避免伪共享）；在没有缓存的单片机上
它纯粹是浪费 SRAM——**同一个关键字在两个世界里价值相反**。

## 2.7 小结

> [!NOTE]
> 结构体的大小 = 各成员大小之和 + 填充。填充的规则是「每个成员落在自己对齐要求的倍数上」，
> 结构体本身的大小再向上取齐到最大成员的对齐。`#pragma pack(1)` 与
> `__attribute__((packed))` 把对齐要求降到 1，代价是访问要拆成字节或多一次非对齐访问
> （真板上 8 → 10 → 18 周期三档）。取 `packed` 成员的地址会让对齐要求无法保证，
> 编译器默认给出 `-Waddress-of-packed-member` 警告。

# 第 3 节 缓存行与伪共享

## 3.1 缓存行有多大

缓存不是按字节搬运的，它按**缓存行**（cache line）整条搬运。
行有多大由 CPU 决定，可以问出来：

`C++`

```cpp
// cacheline.cpp   编译：g++ -std=c++17 -O2 cacheline.cpp -o cacheline.exe
// 运行：cacheline.exe
#include <cstdio>
#include <cstdint>
#include <cstdlib>
#include <chrono>

// CPUID 叶子 1：EBX[15:8] 是 CLFLUSH 行大小 / 8
// CPUID 叶子 4：EBX[11:0] 是（一致性行大小 - 1）
static void cpuid_line(unsigned &clflush_bytes, unsigned &coherency_bytes)
{
#if defined(__x86_64__) || defined(__i386__)
    unsigned a, b, c, d;
    __asm__ volatile("cpuid" : "=a"(a), "=b"(b), "=c"(c), "=d"(d) : "a"(1), "c"(0));
    clflush_bytes = ((b >> 8) & 0xFFu) * 8u;
    __asm__ volatile("cpuid" : "=a"(a), "=b"(b), "=c"(c), "=d"(d) : "a"(4), "c"(0));
    coherency_bytes = (b & 0xFFFu) + 1u;
#else
    clflush_bytes = coherency_bytes = 0;
#endif
}

// 按固定步长把整个数组读一遍，返回「每次访问平均多少纳秒」
static double scan_ns(size_t stride, size_t bytes)
{
    unsigned char *buf = (unsigned char *)std::malloc(bytes + 64);
    for (size_t i = 0; i < bytes; ++i) buf[i] = (unsigned char)i;
    volatile unsigned long long sum = 0;
    auto t0 = std::chrono::steady_clock::now();
    for (int rep = 0; rep < 200; ++rep)
        for (size_t i = 0; i < bytes; i += stride) sum += buf[i];
    auto t1 = std::chrono::steady_clock::now();
    std::free(buf);
    double ns = std::chrono::duration<double, std::nano>(t1 - t0).count();
    return ns / (double)(200 * (bytes / stride));
}

int main()
{
    unsigned clflush = 0, coherency = 0;
    cpuid_line(clflush, coherency);
    std::printf("CPUID 叶子 1 的 CLFLUSH 行大小 = %u 字节\n", clflush);
    std::printf("CPUID 叶子 4 的一致性行大小   = %u 字节\n", coherency);

    std::printf("\n步长扫描（4 MiB 数组，每次访问的平均耗时）：\n");
    const size_t N = size_t(1) << 22;
    for (size_t stride = 1; stride <= 256; stride *= 2)
        std::printf("  步长 %3zu 字节：%7.2f ns\n", stride, scan_ns(stride, N));
    std::printf("\n步长超过 64（一个缓存行的宽度）以后，每次访问都要新取一行\n");
    return 0;
}
```

`Text`

```text

CPUID 叶子 4 的一致性行大小   = 64 字节
```

超过 64 以后每次访问都要新取一行，耗时升到 1 ns 量级。
**`alignas(64)` 里的 64 不是随便挑的**，它来自这里。

两次运行的台阶位置一致（都在 64 字节），但 128 字节以上的绝对值不稳定：
4 MiB 的数组已经超出末级缓存，硬件预取与内存页行为都会掺进来。
**这类微基准只适合用来看「台阶在哪」，不适合拿来当绝对性能指标。**

## 3.2 伪共享：两个线程各改各的，却互相拖慢

缓存行带来一个反直觉的后果：**两个线程访问不同的变量，只要这两个变量在同一条缓存行上，
它们就会互相干扰**。原因是缓存一致性协议以行为单位：
一个核要写自己那个变量，就必须先把整条行独占，另一个核手里的同一行随即失效。
下一轮反过来。行在两个核之间来回搬，这叫**伪共享**（false sharing）。

`C++`

```cpp
// false_share.cpp   编译：g++ -std=c++17 -O2 false_share.cpp -o false_share.exe
// 运行：false_share.exe
//
// 六个配置：相邻/分开 两种排布，各自在「钉在不同物理核」「钉在同一物理核的两个
// 超线程」「不钉」三种调度下各跑一次。钉核是为了排除调度抖动：不钉时两个线程
// 可能被放到同一个物理核的两个超线程上。
#include <cstdio>
#include <thread>
#include <chrono>
#include <cstdint>
#ifdef _WIN32
#include <windows.h>
#endif

static const long long N = 50000000;      // 每个线程的循环次数

struct Adjacent {                          // 两个计数器挨在一起，必在同一缓存行
    volatile long long a;
    volatile long long b;
};

struct Padded {                            // 各自独占一条缓存行
    alignas(64) volatile long long a;
    alignas(64) volatile long long b;
};

#ifdef _WIN32
static void pin_this_thread(unsigned long long cpu_mask)
{
    SetThreadAffinityMask(GetCurrentThread(), (DWORD_PTR)cpu_mask);
}
#else
static void pin_this_thread(unsigned long long) { }
#endif

// mask 为 0 表示不钉核
template <typename T>
static double run_one(T &p, unsigned long long mask1, unsigned long long mask2)
{
    p.a = 0; p.b = 0;
    auto t0 = std::chrono::steady_clock::now();
    std::thread t1([&p, mask1] {
        if (mask1) pin_this_thread(mask1);
        for (long long i = 0; i < N; ++i) p.a = p.a + 1;
    });
    std::thread t2([&p, mask2] {
        if (mask2) pin_this_thread(mask2);
        for (long long i = 0; i < N; ++i) p.b = p.b + 1;
    });
    t1.join(); t2.join();
    auto t1e = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1e - t0).count();
}

static void report(const char *what, const char *how, double ms, long long a, long long b)
{
    std::printf("%-10s %-22s %8.1f ms   （a=%lld b=%lld）\n", what, how, ms, a, b);
}

int main()
{
    Adjacent adj{};
    Padded   pad{};
    std::printf("每个线程把自增 %lld 次写回内存（volatile，编译器不能省掉）\n\n", N);

    // 逻辑 CPU 0 与 2 属于两个不同的物理核；0 与 1 是同一个物理核的两个超线程
    double a_cross = run_one(adj, 1ull << 0, 1ull << 2);
    double p_cross = run_one(pad, 1ull << 0, 1ull << 2);
    double a_smt   = run_one(adj, 1ull << 0, 1ull << 1);
    double p_smt   = run_one(pad, 1ull << 0, 1ull << 1);
    double a_free  = run_one(adj, 0, 0);
    double p_free  = run_one(pad, 0, 0);

    std::printf("--- 两个线程钉在两个物理核上（CPU0 与 CPU2）---\n");
    report("相邻", "不同物理核", a_cross, adj.a, adj.b);
    report("分开", "不同物理核", p_cross, pad.a, pad.b);
    std::printf("--- 两个线程钉在同一个物理核的两个超线程上（CPU0 与 CPU1）---\n");
    report("相邻", "同一核的两个超线程", a_smt, adj.a, adj.b);
    report("分开", "同一核的两个超线程", p_smt, pad.a, pad.b);
    std::printf("--- 不钉核，交给调度器 ---\n");
    report("相邻", "不钉核", a_free, adj.a, adj.b);
    report("分开", "不钉核", p_free, pad.a, pad.b);

    std::printf("\n结构体大小：Adjacent = %zu 字节，Padded = %zu 字节\n",
                sizeof(Adjacent), sizeof(Padded));
    std::printf("相邻/分开 的倍数：不同物理核 %.2f，同核超线程 %.2f，不钉核 %.2f\n",
                a_cross / p_cross, a_smt / p_smt, a_free / p_free);
    return 0;
}
```

```text
复验时同一份程序的第二次运行（同一台机器，只隔了几分钟）：

相邻     不同物理核            11.0 ms        分开     不同物理核             9.3 ms
相邻     同一核的两个超线程     88.4 ms        分开     同一核的两个超线程     19.4 ms
相邻     不钉核                10.8 ms        分开     不钉核                 8.7 ms

相邻/分开 的倍数：不同物理核 1.18，同核超线程 4.55，不钉核 1.25
```

**两次运行的绝对值差了一倍**（同一核超线程：18.3 与 11.0 ms），
这在这类微基准里是常态：CPU 频率、后台负载、线程落点都会影响绝对值。
**稳定的是比例**：同核超线程那一组两次都是 3.7 与 4.6 倍。

三条结论都在这两张表里：

- **相邻的 `a` 与 `b` 让两个线程慢了**：同核超线程那一组是 **3.7 与 4.6 倍**；
  不同物理核那一组只慢 1.2–1.5 倍；
- **不钉核时差别很小**（0.94 与 1.25 倍）：调度器可能把两个线程放在同一个物理核上，
  超线程共享 L1 缓存，缓存行的所有权没有在核间来回搬——
  **这也解释了为什么「我本地跑不出伪共享」是一件很常见的事**；
- **代价来自结构体的排布，不是来自代码**：两段线程函数完全相同，
  只差 `alignas(64)`，结构体从 16 字节变成 128 字节。

**换一种访问模式，代价会大得多。** 两个线程各有自己的计数器，
但每次都读一下对方的（一个写者、多个读者，仍然没有数据竞争）。
对照程序与上一份同源，只换循环体：`p.a = p.a + 1`、
`p.a = p.a + 1; sink += p.b;`、`p.a.fetch_add(1, std::memory_order_relaxed)`，
两个线程分别钉在 CPU0 与 CPU1（同核超线程）或 CPU0 与 CPU2（不同物理核）。

`实测数据`
`Text`

```text
N = 50000000，单位 ms（同一台机器，两种排布都加 alignas(64) 隔开）

第 1 轮
  各写各的（分开 64 字节）  CPU0/CPU2      22.8    CPU0/CPU1      20.3
  互相读（每次读对方的）    CPU0/CPU2     193.4    CPU0/CPU1     150.0
  原子自增（同一缓存行）    CPU0/CPU2     713.7    CPU0/CPU1     389.8
第 2 轮
  各写各的（分开 64 字节）  CPU0/CPU2      24.6    CPU0/CPU1      19.5
  互相读（每次读对方的）    CPU0/CPU2     251.0    CPU0/CPU1     160.1
  原子自增（同一缓存行）    CPU0/CPU2     719.2    CPU0/CPU1     393.7
```

**互相读让耗时涨到 8 倍左右，原子自增涨到 20 到 30 倍。**
原子那一行是极端情况：`fetch_add` 每次都要独占整条缓存行，
两个核轮流拿到它，每一次都要一次核间往返。
原子操作本身的用法在《07-标准库/B-10-内存与并发的基础设施.md》第 5 节，
这里只取它的性能含义：**同一缓存行上的高频写是现代多核上最贵的操作之一**。

## 3.3 怎么避免伪共享

三条路，按代价从低到高：

1. **让每个线程的数据独占一条缓存行**。C++17 给了标准里的常数：

   `文档`

   > "inline constexpr size_t hardware_destructive_interference_size = implementation-defined ;
   > ... This number is the minimum recommended offset between two concurrently-accessed objects
   > to avoid additional performance degradation due to contention introduced by the implementation.
   > It shall be at least alignof(max_align_t)."
   >
   > —— N4659 §21.6.5

   标准里的例子正是本节的场景：

   `C++`

   ```cpp
   // keep_apart.cpp   编译（只看语法）：g++ -std=c++17 -O2 -c keep_apart.cpp -o keep_apart.o   （下面是节选）
   #include <atomic>
   #include <new>

   struct keep_apart {
       alignas(std::hardware_destructive_interference_size) std::atomic<int> cat;
       alignas(std::hardware_destructive_interference_size) std::atomic<int> dog;
   };
   ```

   在 x86-64 的 GCC 上这个常量是 64，与上一小节测到的一致。
   **在没有缓存的 Cortex-M3 上，这个关键字没有任何意义**——
   它不会让代码变慢，只是白占 SRAM。

2. **改数据布局，让每个线程的数据来自不同的缓存行**：
   把「一组计数器」改写成「每个线程一个结构体，结构体内部再聚合」，
   这在统计类代码里比 `alignas` 更自然。

3. **减少写共享**：把每个线程的结果先累加到本地，最后再汇总一次。
   这一条不依赖缓存行的大小，因此在换了 CPU 之后仍然有效。

## 3.4 小结

> [!NOTE]
> 缓存以 64 字节的行（本机测到的值）为单位搬运。两个线程写同一行里的不同变量时，
> 行的所有权在核间来回搬，性能可以差 3 到 8 倍；把变量按行隔开就恢复正常。
> `alignas(64)` 与 C++17 的 `hardware_destructive_interference_size` 是标准里的工具，
> 但它们只在有缓存的机器上有意义——Cortex-M3 上没有缓存，这个关键字换来的是纯粹的浪费。

# 第 4 节 DMA 与缓存一致性

## 4.1 问题现场

有缓存的机器上，CPU 写一个变量时**不一定写进内存**：写操作先进缓存，
被改过的缓存行标记为「脏」，等到某次替换时才写回内存。
这条规则本身没问题，直到另一个「不经过缓存的主」也来访问同一块内存——
**DMA 控制器**正是这样的主：它在外设与内存之间直接搬数据，不经过 CPU 的缓存。

`Text`

```text
        ┌──────────┐         ┌──────────────┐
        │   CPU    │◄───────►│  D-Cache     │   ← CPU 看到的世界
        └──────────┘         └──────┬───────┘
                                     │ 脏行不一定已经写回
                                     ▼
                              ┌──────────────┐
                              │    SRAM      │   ← DMA 看到的世界
                              └──────┬───────┘
                                     ▲
        ┌──────────┐                 │
        │   DMA    │─────────────────┘            ← 直接读写内存，绕过缓存
        └──────────┘
```

两个方向都会出错：

| 方向 | 现象 | 原因 |
|---|---|---|
| CPU 写 → DMA 读 | DMA 搬走的是**旧数据** | CPU 的新值还在缓存里，没写回内存 |
| DMA 写 → CPU 读 | CPU 读到的是**旧数据** | 缓存里留着这一行的旧副本，DMA 改的是内存 |

**这和 `volatile` 是两件事**。`volatile` 让编译器每次都真的发出访问指令，
但那条指令到达的是缓存；DMA 绕过缓存，两者在总线上看到的内容可以不同。
`volatile` 管的是编译器，缓存一致性管的是硬件。

## 4.2 两种修法

**修法一：在同步点手工维护缓存。** 顺序不能颠倒：

`C`

```c
/* cache_sync.c   缓存维护的调用顺序（下面是节选：完整的 DMA 例程随芯片厂商提供）
   只编译：gcc -std=c23 -c cache_sync.c -o cache_sync.o */
#include <stdint.h>

/* 下面几个是厂商库与工程里的函数，这里只给声明，用来标出调用顺序 */
void fill_tx_buffer(void *buf, uint32_t len);
void start_dma_tx(void *buf, uint32_t len);
void start_dma_rx(void *buf, uint32_t len);
int  wait_dma_done(void);
void consume_rx_buffer(void *buf, uint32_t len);
void SCB_CleanDCache_by_Addr(uint32_t *addr, int32_t dsize);
void SCB_InvalidateDCache_by_Addr(uint32_t *addr, int32_t dsize);

/* 发送方向：CPU 准备数据 → DMA 读出。先写回，再启动 */
void tx_path(void *tx, uint32_t len)
{
    fill_tx_buffer(tx, len);
    SCB_CleanDCache_by_Addr((uint32_t *)tx, (int32_t)len);   /* 写回：内存拿到最新值 */
    start_dma_tx(tx, len);
}

/* 接收方向：DMA 写入 → CPU 读取。先作废，再读 */
void rx_path(void *rx, uint32_t len)
{
    start_dma_rx(rx, len);
    wait_dma_done();
    SCB_InvalidateDCache_by_Addr((uint32_t *)rx, (int32_t)len);   /* 作废：丢掉旧副本 */
    consume_rx_buffer(rx, len);
}
```

`待确认`

> `SCB_CleanDCache_by_Addr` 与 `SCB_InvalidateDCache_by_Addr` 是 CMSIS 里
> Cortex-M7 头文件提供的函数名。本机没有 M7 的工程，这两个名字未在本地核对；
> 有些厂商库用 `L1C_CleanDCacheByAddr` 之类的名字，**用之前查自己那颗芯片的头文件**。

**修法二：让这块内存根本不进缓存。** 通过 MPU 把 DMA 缓冲区所在的区域配成
non-cacheable 或 write-through，CPU 与 DMA 看到的就始终是同一份数据，
不需要任何维护调用（代价是 CPU 访问这块内存变慢）。
两种修法可以混用：小缓冲区用维护调用，频繁搬的大缓冲区用 MPU 配置。

还有一条与硬件无关的经验：**别让 CPU 与 DMA 同时在同一个缓冲区上工作**。
双缓冲（一个在搬、一个在处理）把同步点减少到「切换的那一次」，
既省掉大部分缓存维护，也让代码更容易验证。

## 4.3 F103 的对照面：没有缓存，就没有一致性问题

STM32F103C8 是 Cortex-M3。**M3 没有数据缓存，也没有指令缓存**
（只有 flash 侧的预取缓冲），因此：

- **DMA 缓冲区不需要任何缓存维护**：CPU 写进 SRAM 就是写进 SRAM；
- **不存在「缓存里的旧值」**：每一次读都真的到总线上；
- **时序非常可预测**：真板上测到的中断延迟（从置起挂起位到执行 ISR 第一条指令）
  是 **21 个周期**，触发 64 次，**最小值与最大值完全相同**。
  没有缓存与乱序执行带来的抖动，数字才能稳定到这个程度。

代价在另一个地方：**每一次取指都要等 flash**，
所以 M3 有 flash 等待周期与预取缓冲这些机制来补。
换句话说，无缓存并非「更好」，只是把「缓存一致性」这个复杂度
换成了「执行速度」这个复杂度——**哪一边更容易出错，取决于你的程序在做什么**。

`实测数据`

| 项 | 有缓存的目标（如 Cortex-M7） | STM32F103C8（Cortex-M3，无缓存） |
|---|---|---|
| DMA 前后要不要维护缓存 | 要（clean / invalidate） | 不要 |
| 忘记维护的后果 | DMA 搬到旧数据或 CPU 读到旧数据 | 无此问题 |
| 中断延迟的稳定性 | 受缓存命中与否影响 | 真板上 64 次测量 min = max = 21 周期 |
| 代价 | 缓存维护代码与 MPU 配置 | 每次取指都要等 flash |

> [!CAUTION]
> **`volatile` 不能替代缓存维护。** 在 Cortex-M7 这类有 D-Cache 的芯片上，
> 给 DMA 缓冲区加 `volatile` 只解决了「编译器每次都发出访问」这一半问题，
> 「硬件看到的是哪一份数据」那一半要靠在正确的同步点 clean/invalidate。
> 反过来，在 F103 上没有缓存，写了 clean/invalidate 也只是空操作，
> 移植代码时不要因为「在 F103 上没问题」就把这些调用删掉。

## 4.4 小结

> [!NOTE]
> 缓存一致性问题来自「两个主共享一块内存」：CPU 经过缓存，DMA 不经过。
> 有缓存的芯片要在同步点做写回与作废，或者用 MPU 把缓冲区配成非缓存。
> Cortex-M3 没有缓存，这一整类问题都不存在，代价是取指要等 flash；
> 也正因为没有缓存，真板上的周期数才能稳定到 min = max。

# 第 5 节 速查表

`实测数据`

| 常用件 | 一句话用途 | 典型坑 |
|---|---|---|
| `alignof(T)` / `offsetof(S, m)` | 量对齐要求与成员偏移 | 拿一张表去推断另一套 ABI |
| `alignas(N)` | 提高对齐（对象落在 N 的倍数上） | 无缓存的目标上纯粹浪费 SRAM |
| `#pragma pack(push, 1)` | 跨编译器都认的打包写法 | 忘了配对的 `pop`，影响后面所有结构体 |
| `__attribute__((packed))` | GCC／Clang 专有的打包写法 | MSVC 不认，跨编译器要包一层宏 |
| `-Waddress-of-packed-member` | 抓「取 packed 成员地址」 | 默认只是警告，要 `-Werror=` 才拦住 |
| `-Wpadded` | 报告编译器在哪里插了填充 | 只在 GCC 上有，且会刷屏 |
| `-fpack-struct` | 全局打包（不建议） | 影响所有结构体，包括库头文件里的 |
| IEEE 754 位模式 | 解释浮点数据里的字节 | 类型双关读浮点（见第 4 章） |
| CPUID 叶子 1/4 | 问出缓存行大小（本机 64 字节） | 只在 x86 上有 |
| 步长扫描 | 用耗时曲线验证缓存行大小 | 数组要明显大于末级缓存 |
| `alignas(64)` 计数器 | 避免伪共享 | 只在多核且有缓存时有用 |
| `hardware_destructive_interference_size` | 标准里的缓存行建议值（C++17） | `implementation-defined`，跨平台可能不同 |
| 钉核（亲和性） | 复现伪共享：必须让两个线程真并行 | 不钉核时看不到差别，容易误判 |
| `SCB_CleanDCache_by_Addr` | 启动 DMA 前把脏行写回 | 名字随厂商库变，用前查头文件 |
| `SCB_InvalidateDCache_by_Addr` | DMA 完成后丢掉旧副本 | 顺序颠倒：先读后作废，读到的还是旧值 |
| MPU 非缓存区域 | 让 DMA 缓冲区不进缓存 | 区域边界与大小要按 MPU 的对齐规则设 |
| Cortex-M3 无缓存 | DMA 不需要缓存维护 | 别把「F103 上没问题」推广到 M7 |
