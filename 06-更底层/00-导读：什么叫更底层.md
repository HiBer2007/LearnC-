写应用的人迟早会遇到这样几个问题：程序链接时报 `undefined reference`，而那个符号明明写了；
换一台机器重新编译，同一个结构体的大小就变了；在轮询里加一行 `printf` 调试，bug 却自己消失了。
写嵌入式的人遇到的问题更直接：程序根本没进 `main`、中断里改过的变量主循环看不见、
`.data` 里明明初始化成 `0x1234ABCD` 的全局量读出来是别的数。这些问题都不在语法层面，
翻语言教程也找不到答案——**它们发生在语言之下**。

`01-编译器/00-语言的实现.md` 第 1 节把「标准与实现是两回事」这件事讲清楚了：
标准规定的是**哪些写法是合法的、行为是什么**，而**具体怎么落地**交给实现。
本板块接着往下走一层，看的就是「实现」这一侧里最靠近硬的那部分：
一个变量落在哪个地址上、参数进哪个寄存器、结构体里填了几个字节、
上电以后第一条指令取在哪、外设寄存器为什么必须用 `volatile` 访问。
**这一层的规矩不是语言标准定的**：有的由 ABI 定，有的由芯片定，有的由你手上那块板子的内存大小定。

因此本板块的每条原理都要落到硬件上：讲 ABI 就把参数寄存器和反汇编贴出来，
讲内存布局就把真板上的地址与段表贴出来，讲对齐就把真板上量到的周期数贴出来。
**每个结论都标出处**——`实测` 的数据来自本机编译运行与一块 STM32F103C8 真板，
`文档` 的引用给标准草案的章节号，没验证过的写 `待确认`。
读法上建议**按需查**：这套东西不是靠顺序读记下来的，而是遇到症状时知道该翻哪一节。

# 第 1 节 「更底层」指哪一层

## 1.1 同一份源码，三套 ABI

先看一件最容易被忽略的事：**同一台机器、同一个编译器、同样合法的源码，
换一个目标（甚至只换操作系统）就得到不同的类型宽度**。
下面这份程序不做别的事，只用编译期断言把各类型的宽度写死，
哪一条不成立，编译就直接失败。

`C`

```c
/* abi_sizes.c   编译：gcc -std=c23 -c abi_sizes.c -o abi_sizes.o
   （同一份断言，三个目标：编译得过就说明宽度一致；这个文件没有 main，只编译不链接）
   Linux：    gcc -std=c2x -c abi_sizes.c -o abi_sizes.o
   Cortex-M： arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -c abi_sizes.c -o abi_sizes.o */
#include <stddef.h>
#include <stdint.h>

_Static_assert(sizeof(char) == 1,           "char is not 1 byte");
_Static_assert(sizeof(short) == 2,          "short is not 2 bytes");
_Static_assert(sizeof(int) == 4,            "int is not 4 bytes");
_Static_assert(sizeof(long) == 4,           "long is not 4 bytes");
_Static_assert(sizeof(long long) == 8,      "long long is not 8 bytes");
_Static_assert(sizeof(void *) == 8,         "pointer is not 8 bytes");
_Static_assert(sizeof(size_t) == 8,         "size_t is not 8 bytes");
_Static_assert(_Alignof(double) == 8,       "double alignment is not 8");
_Static_assert(_Alignof(max_align_t) == 16, "max_align_t alignment is not 16");
```

在三个目标上分别编译，结果是三份不同的答卷。

`实测数据`
`Text`

```text
Windows x86-64（gcc 15.2.0）：九条断言全部成立

Linux x86-64（WSL Ubuntu，gcc 13.3.0）：
abi_sizes.c:11:1: error: static assertion failed: "long is not 4 bytes"
   11 | _Static_assert(sizeof(long) == 4,           "long is not 4 bytes");

Cortex-M3（arm-none-eabi-gcc 13.2.1）：
abi_sizes.c:13:1: error: static assertion failed: "pointer is not 8 bytes"
abi_sizes.c:14:1: error: static assertion failed: "size_t is not 8 bytes"
abi_sizes.c:16:1: error: static assertion failed: "max_align_t alignment is not 16"
```

**Windows 与 Linux 都是 x86-64，指令集完全一样，`long` 却一个是 4 字节、一个是 8 字节。**
这不是编译器随意，而是两套 ABI 各自的规定：Windows 的 LLP64 模型里 `long` 保持 32 位，
Linux 的 LP64 模型里 `long` 与指针同宽。Cortex-M 那边则是 32 位机：
指针与 `size_t` 都是 4 字节，`max_align_t` 的对齐是 8 而不是 16。

**这就是本板块要讲的那一层。** 三份答卷都不是标准规定的，
把源码从头读到尾也推不出 `sizeof(long)` 是几——它是 ABI 规定的，
而 ABI 由「谁在什么机器上怎么调用」决定。第 5 章会把这条线走完：
参数进哪个寄存器、返回值放哪、结构体按值传递时怎么摊开，
Windows x64、System V AMD64、ARM AAPCS 各有一份答案。

## 1.2 从源码到硬件：四层

「更底层」不是一个模糊的方向，它指一条具体的链路。一行 `static int g = 1;`
要变成 RAM 里那个值为 1 的字，中间经过四层，每一层有自己的规矩和负责人。

`Text`

```text
┌──────────────────────────────────────────────────────────────────────┐
│ ① 语言标准（N3220 / N4659）                                          │
│    规定：哪些写法合法、行为是什么、哪些地方「由实现定义」            │
│    负责人：ISO C / C++ 委员会        你的代码在这一层是可移植的      │
├──────────────────────────────────────────────────────────────────────┤
│ ② 编译器与优化器                                                     │
│    决定：要不要把这个变量放进寄存器、展开几层循环、函数内联不内联    │
│    负责人：GCC / Clang / MSVC        这一层决定了你能看到什么汇编    │
├──────────────────────────────────────────────────────────────────────┤
│ ③ ABI 与链接器                                                       │
│    决定：类型的宽度与对齐、参数进哪个寄存器、符号叫什么名字、         │
│          各个段摆在哪一段内存里、`.data` 的初值从哪拷到哪            │
│    负责人：平台 ABI（x86-64 System V / Windows x64 / AAPCS）＋链接脚本│
├──────────────────────────────────────────────────────────────────────┤
│ ④ 硬件与芯片                                                         │
│    决定：地址空间怎么划分、访问没对齐会怎样、写外设寄存器有什么副作用、│
│          有没有缓存、缓存与 DMA 之间谁维护一致                       │
│    负责人：芯片与板子                这一层没有「可移植」可言        │
└──────────────────────────────────────────────────────────────────────┘
```

**本板块讲第 ③、④ 两层**，并且在讲第 ③ 层时尽量用第 ④ 层的证据：
段表要落在真实地址上，反汇编要来自真实产物，周期数要在真实芯片上数。

四层之间最容易出错的接缝是 ③ 与 ④ 之间。举一个本板块反复用到的例子：
**「一个变量在哪里」这个问题，在桌面程序和裸机上答案完全不同。**
在 Windows 上，`g` 的地址是虚拟地址，由操作系统的加载器决定，
每次运行还可能变（第 1 章会量出来）；在单片机上，`g` 的地址由链接脚本写死，
不运行就看得出来，上电后由 `Reset_Handler` 把初值从 flash 搬过去。
同一个 `static int g = 1;`，两条完全不同的落地路径。

## 1.3 标准留白的地方，谁填上

标准不是没考虑到这些事，而是**有意留白**，把决定权交给实现。
下面这张表把第 ③、④ 两层的常见留白列在一起——
它们的共同点是：标准说了「由实现定义」或干脆没说，而**芯片手册与 ABI 文档说了**。

| 标准留白的地方 | 标准怎么说 | 谁填上 | 讲在哪 |
|---|---|---|---|
| 各类型的宽度 | 只给最小值与相对秩，不写固定字节数 | ABI（LP64 / LLP64 / ILP32） | 第 5 章 |
| 对象的对齐要求 | 「实现定义的整数值」 | ABI 与硬件 | 第 2 章 |
| 结构体里的填充字节 | 「允许有无名的填充」 | ABI | 第 2 章 |
| 参数怎么传、返回值放哪 | 完全不管 | ABI（System V / Windows x64 / AAPCS） | 第 5 章 |
| 名字在符号表里长什么样 | 完全不管 | ABI 与名字修饰规则 | 第 5、6 章 |
| 一个符号是强是弱、能不能被覆盖 | 只说外部链接与内部链接 | 链接器（ELF 的 `weak`） | 第 6 章 |
| 代码与数据放在内存的哪里 | 完全不管 | 链接脚本与操作系统加载器 | 第 1、7 章 |
| 越界访问会发生什么 | 未定义行为 | 硬件：MMU 有保护、裸机没有 | 第 1 章 |
| 多线程与中断下的可见性 | 只谈抽象机器上的顺序 | 硬件内存模型与屏障 | 第 10 章 |

标准文本本身写得很直白。下面是 C23 草案里关于对齐的一段：

`文档`

> "Complete object types have alignment requirements which place restrictions on the addresses
> at which objects of that type may be allocated. An alignment is an implementation-defined integer
> value representing the number of bytes between successive addresses at which a given object can be
> allocated. An object type imposes an alignment requirement on every object of that type:
> stricter alignment can be requested using the alignas keyword."
>
> —— N3220 §6.2.8/1

「implementation-defined integer value」这六个字就是留白：
对齐到底是多少，标准不说，去问 ABI 和你那颗芯片。
同一节里还有一句限定了填充能出现在哪：

`文档`

> "There may be unnamed padding within a structure object, but not at its beginning."
>
> —— N3220 §6.7.3.2/17
>
> "There may be unnamed padding at the end of a structure or union."
>
> —— N3220 §6.7.3.2/19

**「可以有无名填充」加上「对齐由实现定」，两条合起来就解释了
为什么同一个结构体在两个目标上大小不同**——第 2 章会把这张 `sizeof`/`offsetof` 表
在 x86-64 与 Cortex-M 上各打印一份，再讲填充带来的访问代价。

## 1.4 「更底层」不等于「更难」

需要先说清一点：下到这一层不是为了炫技，而是为了**解释现象**与**避开静默错误**。
绝大多数程序一辈子不需要关心 `.data` 在哪、参数进哪个寄存器；
但只要出现下面三类情形之一，这一层就绕不过去。

| 情形 | 为什么绕不过去 |
|---|---|
| 换编译器、换平台、换优化等级后行为变了 | 变的往往正是 ABI 与优化器负责的那部分（第 2、5 章） |
| 程序在桌面上好好的，烧进单片机就不动 | 裸机没有操作系统兜底：栈溢出没人拦、越界访问没人报（第 1、3 章） |
| 偶发、难复现、加一行打印就好 | 优化器把不该省的访问省了、缓存与 DMA 不一致、缺屏障（第 2、3、10 章） |

反过来说，**这一层里没用的东西也不要碰**：能写成标准 C 与 C++ 的地方就写成标准写法，
把 `__attribute__`、寄存器地址、链接脚本这些留给真正需要它们的那几行。
第 12 章会专门讲怎么把编译器扩展隔离起来，第 13 章给一张「什么时候该下来」的决策表。

> [!NOTE]
> **小结**：「更底层」指的是语言标准之下的第 ③、④ 两层——ABI 与链接器一层，硬件与芯片一层。
> 这两层的规矩不由标准定：类型宽度、对齐、填充、传参、符号名、段的位置由 ABI 与链接脚本定，
> 地址空间、非对齐访问的后果、缓存一致性由芯片定。标准在这些地方只写「由实现定义」，
> 然后留下足够的空白让实现去填。

# 第 2 节 两类读者，两条线

## 2.1 写应用的人：症状在工具输出里

写应用的人遇到这条线上的问题时，看到的通常不是硬件现象，而是**工具的一条输出**：
链接器说符号未定义、调试器说变量被优化掉了、程序在 Release 下崩而在 Debug 下不崩、
换个编译器告警一大堆。

对这类读者，本板块的目标是**把工具输出翻译成机制**：

| 你看到的 | 底下发生的事 | 在哪一章 |
|---|---|---|
| `undefined reference to 'foo'` | 符号没定义，或定义了但名字被修饰过、链接顺序不对 | 第 5、6 章 |
| `multiple definition of 'x'` | 两个目标文件都给了强定义 | 第 6 章 |
| 结构体大小和预期差几个字节 | ABI 往里加了填充 | 第 2 章 |
| Release 下行为和 Debug 不同 | 优化器利用了「这段代码有未定义行为」 | 第 12 章 |
| 多线程计数偶尔少几次 | 读-改-写不是原子的 | 第 10 章 |
| `nm` 里符号一大堆看不懂 | 符号表按链接属性分类，字母有含义 | 第 6 章 |

## 2.2 写嵌入式的人：症状在板子上

写嵌入式的人看到的现象更直接，也更难查：程序不进 `main`、中断里改的变量主循环看不见、
上电后外设没反应、DMA 搬进来的数据和内存里的对不上、加个 `volatile` 就好了。

这条线的入口是**硬件事实**，而不是工具输出：

| 你看到的现象 | 底下的机制 | 在哪一章 |
|---|---|---|
| 复位后立刻进 HardFault | 栈顶指向了不存在的内存（链接脚本写错） | 第 7 章 |
| 轮询循环永远出不来 | 少了 `volatile`，编译器把读操作优化掉了 | 第 3 章 |
| 中断改了标志位，主循环看不见 | 变量没写 `volatile`，编译器把它缓存在寄存器里 | 第 3、10 章 |
| 中断与主循环共用的计数器少了几次 | 读-改-写被中断打断，`volatile` 不保证原子 | 第 10 章 |
| 全局变量莫名变了 | 栈溢出压到了 `.data`，裸机上没人拦 | 第 1 章 |
| DMA 收到的数据是旧的 | 缓冲区在缓存里没写回（有缓存的芯片才有） | 第 2 章 |
| 结构体塞进通信帧对不上 | 对齐填充把布局撑开了，需要按字节打包 | 第 2 章 |
| 板子上 `printf` 一个字都不打 | 没有内核接管 `_write`，桩函数返回 -1 | 第 11 章 |

# 第 3 节 工具箱一览

## 3.1 六个工具，各看一层

这一节把本板块常用的六件工具逐个拆开。它们看的是同一份产物的不同侧面，
**先用哪件取决于你想问什么**：

| 工具 | 它看什么 | 一句话用途 | 常见前缀 |
|---|---|---|---|
| `nm` | 符号表 | 有哪些符号、各是什么链接属性、地址在哪 | `arm-none-eabi-nm` |
| `size` | 段的大小 | `.text`/`.data`/`.bss` 各占多少字节 | `arm-none-eabi-size` |
| `objdump` | 段表与机器码 | 段摆在哪、反汇编是什么指令 | `arm-none-eabi-objdump` |
| `readelf` | ELF 的结构 | 文件类型、入口、段表、符号表的原始形态 | `arm-none-eabi-readelf` |
| `map` | 链接器的工作日志 | 每个符号与每个段最终落在哪、为什么 | 加 `-Wl,-Map=` |
| `dumpbin` | PE 的结构 | Windows 侧的 `readelf`，看头部与导出表 | MSVC 自带 |

**两条纪律**，后面每一小节都会用到：

- **工具看的是产物，不是源码。** 同一个源文件换个优化等级，
  `nm` 里可能少几个符号、`objdump` 里可能整段循环都不见了。
  拿工具输出下结论之前，先确认你看的是哪一次编译的产物。
- **交叉编译侧的工具要带前缀。** `nm` 看不了 ARM 的 ELF（格式能读，
  但符号名与地址的含义要按目标机理解），用 `arm-none-eabi-nm` 这一组。
  工具链装在 WSL 里，命令形如 `wsl -d Ubuntu -e arm-none-eabi-nm ...`。

## 3.2 `nm`：符号表

符号表是链接器的工作台账。先准备一个每种链接属性都占一个的源文件。

`C`

```c
/* syms.c   编译：gcc -std=c23 -O0 -c syms.c -o syms.o   （只编译不链接）
   各种链接属性各来一个，用来看 nm 的字母；链接：gcc -std=c23 -O0 syms.c -o syms.exe */
#include <stdio.h>

int         g_init   = 42;            /* 有初值的全局：.data，外部链接 */
int         g_uninit;                 /* 无初值的全局：.bss，外部链接 */
const int   g_const  = 7;             /* 常量：只读数据 */
static int  s_static = 5;             /* 内部链接 */

void exported_fn(void) { g_uninit = g_init + s_static; }   /* 外部链接的函数 */
static void local_fn(void) { }                             /* 内部链接的函数 */

int main(void)
{
    printf("%d %d %p\n", g_const, s_static, (void *)&local_fn);
    exported_fn();
    return 0;
}
```

只编译不链接，得到的 `.o` 里所有符号都还在：

`实测数据`
`Text`

```text
$ nm syms.o
0000000000000000 b .bss
0000000000000000 d .data
0000000000000000 p .pdata
0000000000000000 r .rdata
0000000000000000 t .text
                 U __main
                 U __mingw_printf
0000000000000000 T exported_fn
0000000000000000 R g_const
0000000000000000 D g_init
0000000000000000 B g_uninit
000000000000001b t local_fn
0000000000000022 T main
0000000000000004 d s_static
```

**第一个字母是符号的类别，大小写是链接属性**：大写表示外部链接（别的目标文件能引用），
小写表示内部链接（只有本文件可见）。两者是正交的，因此同一类符号有大小写两个字母。

| 字母 | 含义 | 落在哪 | 本例子里的 |
|---|---|---|---|
| `T` / `t` | 代码（text） | `.text` | `exported_fn`（T）、`local_fn`（t） |
| `D` / `d` | 有初值的数据 | `.data` | `g_init`（D）、`s_static`（d） |
| `B` / `b` | 无初值的数据 | `.bss` | `g_uninit`（B） |
| `R` / `r` | 只读数据 | `.rodata` | `g_const`（R） |
| `U` | 未定义，需要别人提供 | 链接期解决 | `__mingw_printf` |
| `A` | 绝对地址，链接时不再重定位 | — | 链接脚本里的 `_estack` |
| `W` / `w` | 弱符号（weak） | — | 启动文件里那些可被覆盖的中断处理函数 |
| `I` | 间接符号（GNU 扩展） | `.idata` | 动态库函数的导入桩 `__imp_...` |
| `N` | 调试符号 | — | 用 `-g` 编译才有 |

链接成可执行文件之后再 `nm` 一次，符号会多出好几百个——**C 运行库被静态链进来了**：

`实测数据`
`Text`

```text
$ nm syms.exe | grep -E "printf|g_init|g_uninit|g_const|s_static|exported_fn|local_fn"
000000014000e2d8 I __imp_fprintf
000000014000e328 I __imp_vfprintf
00000001400025e0 T __mingw_printf
0000000140001440 T exported_fn
0000000140008330 T fprintf
000000014000a000 R g_const
0000000140009000 D g_init
000000014000d030 B g_uninit
000000014000145b t local_fn
0000000140009004 d s_static
0000000140008380 T vfprintf
```

三点直接读得出来：

- **地址齐了**：`.o` 里所有符号地址都是 0（还没分配），链接之后每个符号都有真实地址；
- **段分开了**：`g_const` 在 `0x14000a000`（只读段），`g_init` 在 `0x140009000`（可写数据段），
  `g_uninit` 在 `0x14000d030`（`.bss`），三者在不同页上——这是权限划分的物理基础；
- **`s_static` 还在，但变成了小写 `d`**：内部链接的符号不会消失，
  只是链接器不允许别的目标文件引用它。想连名字都不留，那是 `strip` 的工作。

## 3.3 `size`：三个数

`size` 把段归成三类，输出朴素但信息量大。用下面这个程序对比两个优化等级。

`C`

```c
/* sizes.c   编译：gcc -std=c23 -O2 sizes.c -o sizes.exe   （同一份源码，两个优化等级） */
#include <stdio.h>

static int helper(int x) { return x * 3 + 1; }   /* -O2 下会被内联并折叠 */

int main(void)
{
    int sum = 0;
    for (int i = 0; i < 10; ++i) sum += helper(i);
    printf("%d\n", sum);
    return 0;
}
```

`实测数据`
`Text`

```text
$ ls -l sizes_O0.exe sizes_O2.exe
sizes_O0.exe  80387 字节
sizes_O2.exe  79875 字节

$ size sizes_O0.exe sizes_O2.exe
   text	   data	    bss	    dec	    hex	filename
  36248	    272	   2944	  39464	   9a28	sizes_O0.exe
  36144	    272	   2944	  39360	   99c0	sizes_O2.exe
```

**三列的含义**：

| 列 | 含义 | 运行时在哪 | 占文件空间吗 |
|---|---|---|---|
| `text` | 代码与只读数据 | 只读内存 | 占 |
| `data` | 有初值的可写数据 | 可写内存 | 占（初值要在文件里存一份） |
| `bss` | 无初值的可写数据 | 可写内存 | **不占**，只记长度 |

`.bss` 不占文件空间这件事在段表里看得最清楚：

`实测数据`
`Text`

```text
$ objdump -h sizes_O2.exe | sed -n '4,20p'
Idx Name          Size      VMA               LMA               File off  Algn
  0 .text         000073c0  0000000140001000  0000000140001000  00000600  2**4
  1 .data         00000100  0000000140009000  0000000140009000  00007a00  2**4
  2 .rdata        00000998  000000014000a000  000000014000a000  00007c00  2**4
  3 .pdata        00000480  000000014000b000  000000014000b000  00008600  2**2
  4 .xdata        00000430  000000014000c000  000000014000c000  00008c00  2**2
  5 .bss          00000b80  000000014000d000  000000014000d000  00000000  2**4
```

`.bss` 那一行的 `File off` 是 `00000000`：它在文件里没有内容，运行时由加载器（或裸机上的启动代码）
按长度清零。同一件事在 ELF 侧写得更直白——段的类型从 `PROGBITS` 变成 `NOBITS`：

`实测数据`
`Text`

```text
$ readelf -S sizes_lin_O2 | grep -E "\[ *[0-9]+\] \.(text|data|bss|rodata) "
  [16] .text             PROGBITS         0000000000001060  00001060
  [18] .rodata           PROGBITS         0000000000002000  00002000
  [25] .data             PROGBITS         0000000000004000  00003000
  [26] .bss              NOBITS           0000000000004010  00003010
```

**换到 Cortex-M 上，这三列就是 flash 与 RAM 的账本。** 同一份计算代码交叉编译成目标文件：

`实测数据`
`Text`

```text
$ arm-none-eabi-size sum_O0.o sum_O2.o sum_Os.o
   text	   data	    bss	    dec	    hex	filename
     90	      0	      0	     90	     5a	sum_O0.o
     40	      0	      0	     40	     28	sum_O2.o
     28	      0	      0	     28	     1c	sum_Os.o
```

`-O0` 的 90 字节到 `-Os` 的 28 字节，**同一份源码的代码量差了 3 倍多**。
这就是「体积」这件事在嵌入式侧的分量：flash 只有 64 KiB，
而且**代码量只跟编译选项和目标机有关，跟源文件行数没关系**。

## 3.4 `objdump`：段表与机器码

`objdump -h` 给出段表（上一小节用过），`objdump -d` 给出反汇编。
两者合起来回答「这段代码最终变成了什么」。看同一段循环在两个优化等级下的区别：

`实测数据`
`Text`

```text
$ objdump -d --disassemble=main sizes_O0.exe | sed -n '20,30p'
0000000140001455 <main>:
   140001455:	55                   	push   %rbp
   140001456:	48 89 e5             	mov    %rsp,%rbp
   140001459:	48 83 ec 30          	sub    $0x30,%rsp
   14000145d:	e8 0e 01 00 00       	call   140001570 <__main>
   140001462:	c7 45 fc 00 00 00 00 	movl   $0x0,-0x4(%rbp)
   140001469:	c7 45 f8 00 00 00 00 	movl   $0x0,-0x8(%rbp)
   140001470:	eb 11                	jmp    140001483 <main+0x2e>

$ objdump -d --disassemble=main sizes_O2.exe | sed -n '6,14p'
0000000140008380 <main>:
   140008380:	48 83 ec 28          	sub    $0x28,%rsp
   140008384:	e8 77 91 ff ff       	call   140001500 <__main>
   140008389:	ba 91 00 00 00       	mov    $0x91,%edx
   14000838e:	48 8d 0d 6b 1c 00 00 	lea    0x1c6b(%rip),%rcx        # 14000a000 <.rdata>
   140008395:	e8 c6 a1 ff ff       	call   140002560 <__mingw_printf>
   14000839a:	31 c0                	xor    %eax,%eax
   14000839c:	48 83 c4 28          	add    $0x28,%rsp
   1400083a0:	c3                   	ret
```

`-O0` 版本里有循环、有栈上的 `sum`（`-0x4(%rbp)`）、有跳转；
`-O2` 版本里**循环没了**：`mov $0x91,%edx` 直接把结果 145（`0x91`）当常数传给了 `printf`。
十次循环、十次函数调用，在编译器眼里是可以在编译期算完的。

**这条观察是后面好几章的起点**：既然编译器能在编译期把「读内存」这个动作取消，
那么当那个地址上挂的不是内存而是外设寄存器时，取消它就是致命的（第 3 章）；
既然它能把结果算成常数，那么当代码里有未定义行为时，它的推理就可以走向任何方向（第 12 章）。

## 3.5 `readelf` 与 `dumpbin`：两种容器

可执行文件是容器。Linux 与裸机用 ELF，Windows 用 PE。
容器的头部写明了「这是什么机器、从哪开始执行、有多少段」。

`实测数据`
`Text`

```text
$ arm-none-eabi-readelf -h addr.elf
ELF Header:
  Magic:   7f 45 4c 46 01 01 01 00 00 00 00 00 00 00 00 00
  Class:                             ELF32
  Data:                              2's complement, little endian
  OS/ABI:                            UNIX - System V
  Type:                              EXEC (Executable file)
  Machine:                           ARM
  Entry point address:               0x80014c9
  Start of program headers:          52 (bytes into file)
  Number of program headers:         3
  Number of section headers:         27
```

`实测数据`
`Text`

```text
$ dumpbin /headers sizes_O2.exe | findstr /C:"machine" /C:"subsystem" /C:"entry point" /C:"size of image"
            8664 machine (x64)
            13F0 entry point (00000001400013F0)
           19000 size of image
               3 subsystem (Windows CUI)
```

两边语义一一对应：`Machine` 对 `machine`、`Entry point address` 对 `entry point`、
`Type: EXEC` 对 `subsystem (Windows CUI)`。ARM 的入口 `0x80014c9` 低位是 1，
表示进入时处于 Thumb 态（第 5 章会讲这个最低位的含义）。

`dumpbin` 还能回答一个 ELF 侧不常问的问题：**栈和堆预留了多大**。

`实测数据`
`Text`

```text
$ dumpbin /headers stack_overflow.exe | findstr /C:"stack reserve" /C:"stack commit"
200000 size of stack reserve
1000 size of stack commit
```

`0x200000` 就是 2 MiB——这是 PE 头部里的「栈预留大小」，
第 1 章讲栈溢出时要用这个数去算能递归多少层。

**格式不匹配时工具不会猜，会直接报错**：

`实测数据`
`Text`

```text
$ readelf -h sizes_O2.exe
readelf: Error: Not an ELF file - it has the wrong magic bytes at the start
$ $LASTEXITCODE        # 上面这条命令在 PowerShell 里的退出码
1
```

这条报错值得记住：**`readelf` 只能看 ELF，`dumpbin` 只能看 PE**。
在 Windows 上装 MinGW 就有了 ELF 工具，但编译出来的是 PE，
所以 `readelf` 对 `.exe` 一律无效——不是工具坏了，是文件格式不对。
反过来，`objdump -h` 与 `nm` 两种格式都认，看的就是它们各自内部解析出来的段与符号。

## 3.6 `map`：链接器的工作记录

前面几个工具看的都是产物，`map` 看的是**过程**：
哪个符号进了哪个段、每段最终落在哪个地址区间、库里的哪个成员被拉进来了。
链接时加一个开关就有：

`Bash`

```bash
# 链接时生成 map 文件（GCC 与 Clang 都认）
gcc -std=c23 -O2 sizes.c -o sizes_map.exe -Wl,-Map=sizes.map
```

交叉编译的链接脚本配 map 文件，能一眼看出内存是怎么切开的：

`实测数据`
`Text`

```text
$ grep -A4 "^Memory Configuration" addr.map
Name             Origin             Length             Attributes
RAM              0x20000000         0x00005000         xrw
FLASH            0x08000000         0x00010000         xr
*default*        0x00000000         0xffffffff

$ grep -E "^\.(isr_vector|text|rodata|data|bss) " addr.map
.isr_vector     0x08000000      0x1e4
.text           0x080001e4     0x1588
.rodata         0x0800176c      0x220
.data           0x20000000      0x54c load address 0x0800198c
.bss            0x2000054c      0x1d0 load address 0x08001ed8
```

**`RAM` 是 20 KiB、`FLASH` 是 64 KiB**，这就是这块板子上内存的全部；
`.data` 那一行最值得看：运行地址（VMA）是 `0x20000000`，
**装载地址（LMA）却是 `0x0800198c`——在 flash 里**。
初值必须先躺在 flash 里，上电后才有人把它搬到 RAM。
`load address` 这四个字就是第 7 章要讲的 `AT>` 与 `Reset_Handler` 的入口。

## 3.7 同一套工具看 Cortex-M

换目标机只换工具前缀，看的字段完全一样。

| 想看什么 | x86-64（Windows / Linux） | Cortex-M（WSL 里的交叉工具链） |
|---|---|---|
| 符号表 | `nm` | `arm-none-eabi-nm` |
| 段大小 | `size` | `arm-none-eabi-size` |
| 段表与反汇编 | `objdump -h` / `-d` | `arm-none-eabi-objdump -h` / `-d` |
| ELF 结构 | `readelf` | `arm-none-eabi-readelf` |
| 链接过程 | `-Wl,-Map=` | 同样，写进 `-Wl,-Map=` |

现场看一次 Cortex-M 的符号表，注意地址区间：

`实测数据`
`Text`

```text
$ arm-none-eabi-nm -n addr.elf | grep -E " (_sidata|_sdata|_edata|_sbss\|_ebss|_estack|g_data|main)$"
080003f4 T main
0800198c A _sidata
20000000 D _sdata
20000000 D g_data
2000054c D _edata
2000054c B _sbss
2000071c B _ebss
20005000 R _estack
```

**地址分成两簇**：`0x0800_xxxx` 是 flash（代码与常量），`0x2000_xxxx` 是 RAM（变量）。
`main` 在 flash 里、`g_data` 在 RAM 里、`_estack` 在 RAM 顶端，
这不是约好的，是链接脚本与芯片内存映射共同决定的。第 1 章会把这两簇地址展开讲。

## 3.8 两处不易察觉的静默陷阱

**第一处：`strip` 之后 `nm` 不报错，只是「没有符号」。**
发布版常把符号表删掉以减小体积，之后再用 `nm` 查东西就什么也看不到：

`实测数据`
`Text`

```text
$ strip syms_stripped.exe
$ nm syms_stripped.exe
nm: syms_stripped.exe: no symbols
$ $LASTEXITCODE        # 退出码是 0：命令成功，只是没有符号
0
```

**退出码是 0**——这是它容易误导人的地方：命令成功了，输出是空的。
所以脚本里用 `nm` 的结果做判断时要先确认符号表还在，
或者干脆保留一份带符号的产物专门用来查问题（第 6 章会讲符号与 `strip` 的关系）。

**第二处：拿文件大小当代码大小。** 同一份 `sizes.c`，三个目标：

`实测数据`
`Text`

```text
Windows x86-64（PE，静态链接 CRT）：sizes_O0.exe 80387 字节，sizes_O2.exe 79875 字节
Linux x86-64（ELF，动态链接 libc）：sizes_lin_O0 15992 字节，sizes_lin_O2 15968 字节
Cortex-M3（目标文件）：sum_O0.o 的 .text 90 字节，sum_Os.o 的 .text 28 字节
```

**同样是 `-O0` 到 `-O2`，桌面 PE 只缩了 512 字节，Cortex-M 的代码段缩了 55%。**
前者的文件大小主要由运行库的固定开销决定，后者才是真正的代码量。
**比较体积时必须固定三件事：同一套工具链、同一个目标、同一个优化等级**，
否则比出来的差值说明不了任何问题。

## 4.4 本板块的三条约定

- **结论必标依据**：`实测`（真跑过，命令随程序给出）、`文档`（引标准或官方资料原文与章节号）、

- **实测的两条腿**：应用侧的结论来自本机的 `gcc`/`g++`（Windows 15.2.0）与 WSL 的 `gcc`（13.3.0）；

- **汇编只到「认得」这一层**：看出「循环里还有没有那条 `ldr`」比逐条读懂指令更重要。

# 第 6 节 速查表

`实测数据`

| 常用件 | 一句话用途 | 典型坑 |
|---|---|---|
| `nm` | 列符号：字母看类别，大小写看链接属性 | `strip` 过后输出为空、退出码仍是 0 |
| `nm -u` | 只看未定义符号，链接报错前先查这里 | 未定义符号来自库时，`-u` 也看不见库内部 |
| `size` | 三个数：`.text`/`.data`/`.bss` | 拿它比两个不同目标机或不同工具链的体积 |
| `size -A` | 按段名细看，PE 上还能看到 `.idata`/`.tls` | 列出的段在不同平台名字不同 |
| `objdump -h` | 段表：VMA/LMA/文件偏移/对齐 | 把 LMA 当成运行地址（`.data` 的 LMA 在 flash 里） |
| `objdump -d` | 反汇编，确认某条访存还在不在 | 看 `-O0` 的产物去推断 `-O2` 的行为 |
| `readelf -h/-S` | ELF 的头部与段表，`NOBITS` 就是不占文件 | 对 PE 文件用 `readelf`，直接报 magic 错 |
| `dumpbin /headers` | PE 的头部、栈与堆预留、导出表 | 只在 MSVC 环境里有，MinGW 侧要用 `objdump` |
| `-Wl,-Map=xxx.map` | 链接过程日志：段与符号的最终落点 | 不开这个开关，链接期的问题只能靠猜 |
| `arm-none-eabi-*` | 交叉工具链的同一套工具 | 用主机侧 `nm` 看 ARM 产物，地址含义会对不上 |
| semihosting | 裸机上不接串口就能打印 | 要 `bkpt 0xAB` 加 `SYS_WRITE0`，且 QEMU 侧要开 `-semihosting-config` |
| `-Wl,-Map` 里的 `load address` | `.data` 的初值在 flash 里的位置 | 以为 `.data` 的初值本来就在 RAM |
| `_estack` 与 RAM 顶端 | 栈的起点，必须在真实 RAM 之内 | 换芯片不改链接脚本：复位即 HardFault |
