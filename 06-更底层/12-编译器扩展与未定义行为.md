语言标准规定的是「任何编译器都必须做到什么」。编译器厂商在这条底线之上各自加了一批能力：
用属性描述对齐与段，用 `#pragma` 控制布局与诊断，用内建函数把编译器自己的判断借给程序。
这些能力都不在标准里，一旦写进源码，这份源码就与某一套编译器绑定。本章讲它们分别是什么、
怎样用一层薄薄的宏把差异隔离掉，以及它们与标准之间那条最容易被误解的界线：**未定义行为**。

未定义行为常被当成「拿到错误结果」的同义词，实际比这更宽：标准对它不提任何要求，
编译器于是可以把「不会发生」当作已知条件反过来推理。同一个 `x + 1 > x`，
在 `-O0` 上老老实实做一次加法再比较，在 `-O2` 上直接变成常量 `1`；
越界的一次读在 `-O0` 上读到的是相邻的栈内容，在 `-O2` 上这次读可能整条被删掉。
同一份源码在两档优化下给出不同答案，不是编译器有错，而是程序本身落在了标准不保证的地带。

本章的目标是让这两类问题各归其位：扩展的部分给出了一层可以直接照抄的隔离写法，
未定义行为的部分给出了「`-O0` 与 `-O2` 各编一遍」这种立刻能做的判断，
以及一套能把错误指到具体哪一行上的运行时检查工具。
遇到「换优化等级就出错」，该查的是未定义行为；遇到「换编译器就编译不过」，该查的是扩展。

# 第 1 节 扩展是什么

**扩展是标准之外、某一套编译器额外提供的能力。** 它们不被标准要求，
因此别的编译器可以完全不认；它们也不是随意堆上去的，每一条背后都有一个标准不肯承诺的现实。

## 1.1 标准为什么不把这些写进去

标准要同时容纳两类完全不同的机器。

| 现实差异 | 标准的选择 | 后果 |
|---|---|---|
| 有的平台 `char` 是有符号、有的是无符号 | 写成实现定义 | 需要确定时得自己判断 |
| 对齐要求随平台变化，x86 宽松、ARM 严格 | 只规定「不得减少对齐」 | 想强制对齐只能靠扩展 |
| 硬件寄存器有固定地址 | 标准里根本没有地址这个概念 | 内存映射 I/O 只能用扩展或指针转换 |
| 段、flash、DMA 区这些概念 | 不属于语言 | 只能用属性与链接脚本安排 |
| 优化器的自由度 | 把落在灰区的行为交给实现 | 于是有了未定义行为 |

标准能做的只有一件事：**把不承诺的部分明确标出来**。剩下的空白，
或者留给了实现定义（`sizeof(int)`），或者留给了未指定行为（函数参数的求值顺序），
或者干脆留给了未定义行为（越界、溢出、空指针解引用）。
扩展就是编译器在这些空白上自己订立的一套约定。

> [!IMPORTANT]
> **扩展是双向的**：它在你的平台上解决问题，同时把你的源码绑到这套编译器上。
> 因此使用扩展的第一原则不是「能不能用」，而是「差异有没有被关在一个地方」。

## 1.2 三类扩展

这些能力按形态分成三类，三类的隔离办法并不相同。

| 类别 | 形态 | 典型成员 | 差异有多大 |
|---|---|---|---|
| **属性** | 修饰声明的一段语法 | `__attribute__((packed))`、`__declspec(align(64))` | 最大，两套语法完全不通用 |
| **`#pragma`** | 一行预处理指令 | `#pragma once`、`#pragma pack`、`#pragma GCC diagnostic` | 中等，写法一致但名字与参数各写各的 |
| **内建函数** | 名字以 `__builtin_` 开头的函数 | `__builtin_expect`、`__builtin_add_overflow` | 中等，多数在 MSVC 上有能力相同但名字不同的对应件 |

还有一类常被单独提出来：**关键字扩展**，例如 `__int64`、`__typeof__`、`__forceinline`、
`__declspec(noreturn)`。它们的用法与属性或内建函数重合，因此归入上面三类，不构成独立的第四类。

## 1.3 扩展的三种命运

三类扩展并不是并列的三种技术，它们各自走向了不同的结局。看清这一点，
就能判断手上这条扩展值不值得依赖。

| 命运 | 例子 | 判断依据 |
|---|---|---|
| **进了标准** | `long long`、`inline`、`[[nodiscard]]`、C23 的 `typeof` 与 `unreachable` | 现在写标准写法即可，扩展写法是包袱 |
| **成了事实标准** | `#pragma once`、`__attribute__((packed))`、`__declspec(dllexport)` | 主流编译器都认，但标准不保证 |
| **始终是一家之言** | `__attribute__((cleanup))`、`__declspec(allocate)`、GCC 的语句表达式 | 换编译器就要重写 |

`#pragma once` 是事实标准里最典型的一个。它不在标准里，但 GCC、Clang、MSVC 都支持；
C23 引入 `#embed` 与 `__has_include` 之后，标准才慢慢补上这一块。

> [!TIP]
> **判断一条扩展能不能放心用，看它在第二列还是第三列。**
> 在第二列，把它关进一个头文件即可；在第三列，写之前先确认这个项目会不会换编译器。

# 第 2 节 属性

属性是加在声明上的一小段语法，作用是告诉编译器「这条声明有额外的情况」。
GCC 与 Clang 用 `__attribute__((...))`，MSVC 用 `__declspec(...)`，
同一件事在两边的写法往往毫无相似之处。

## 2.1 同一件事的两种写法

`实测数据`

| 用途 | GCC / Clang | MSVC |
|---|---|---|
| 强制对齐 | `__attribute__((aligned(64)))` | `__declspec(align(64))` |
| 紧凑布局 | `__attribute__((packed))` | 无（用 `#pragma pack`） |
| 不内联 | `__attribute__((noinline))` | `__declspec(noinline)` |
| 声明不返回 | `__attribute__((noreturn))` | `__declspec(noreturn)` |
| 标记弃用 | `__attribute__((deprecated))` | `__declspec(deprecated)` |
| 导出符号 | `__attribute__((visibility("default")))` | `__declspec(dllexport)` |
| 放进指定段 | `__attribute__((section(".name")))` | `__declspec(allocate(".name"))` |
| 强制内联 | `__attribute__((always_inline))` | `__forceinline` |
| 弱符号 | `__attribute__((weak))` | 无直接对应（要在链接器命令行上做） |
| 启动时调用 | `__attribute__((constructor))` | 无直接对应（要写进 `.CRT$XCU` 段） |

**一个属性在两边都写不出来的，才是真正需要隔离层的地方**，例如弱符号与构造函数。
`weak` 与 `constructor` 在 MSVC 侧要绕到链接器与 CRT 段，本章不做展开，
它们的机制见《06-更底层/06-符号与链接属性.md》第 4 节与《06-更底层/08-CRT 与程序启动.md》第 2 节。

## 2.2 布局类属性：`packed` 与 `aligned`

布局类属性改的是内存里的字节排布，因此它影响 ABI：两段代码必须对同一份结构体有完全一致的认识，
才能互相传值。下面这份程序把两种布局一次打印出来。

`C`

```c
/* ext_portable.c   编译：gcc -std=c23 ext_portable.c -o ext_portable.exe
 *                  MSVC：cl /nologo /std:c17 /utf-8 ext_portable.c
 * 同一份源码用两套编译器各编一遍，验证隔离层是否有效。 */
#include <stdio.h>
#include <stdint.h>
#include <stddef.h>

/* 隔离层：三套编译器各走一支，正文里只出现下面这四个宏 */
#if defined(_MSC_VER)
#  define ALIGNED(n)    __declspec(align(n))
#  define NOINLINE      __declspec(noinline)
#  define DEPRECATED    __declspec(deprecated)
#  define PACK_BEGIN    __pragma(pack(push, 1))
#  define PACK_END      __pragma(pack(pop))
#elif defined(__GNUC__) || defined(__clang__)
#  define ALIGNED(n)    __attribute__((aligned(n)))
#  define NOINLINE      __attribute__((noinline))
#  define DEPRECATED    __attribute__((deprecated))
#  define PACK_BEGIN    _Pragma("pack(push, 1)")
#  define PACK_END      _Pragma("pack(pop)")
#else
#  error "未知编译器：请为它补一支"
#endif

PACK_BEGIN
struct wire_header {          /* 线上报文的头部：必须紧凑排列 */
    uint8_t  type;
    uint32_t seq;
    uint16_t len;
};
PACK_END

struct loose_header {         /* 同样的成员，不加紧凑排列 */
    uint8_t  type;
    uint32_t seq;
    uint16_t len;
};

ALIGNED(64) static int g_line[16];   /* 对齐到缓存行 */

NOINLINE static int never_inlined(int x) { return x * 3 + 1; }

int main(void)
{
    printf("编译器标识：");
#if defined(_MSC_VER)
    printf("_MSC_VER = %d\n", _MSC_VER);
#elif defined(__GNUC__)
    printf("__GNUC__ = %d.%d.%d\n", __GNUC__, __GNUC_MINOR__, __GNUC_PATCHLEVEL__);
#endif

    printf("packed   : sizeof = %2zu  type@%zu seq@%zu len@%zu\n",
           sizeof(struct wire_header),
           offsetof(struct wire_header, type),
           offsetof(struct wire_header, seq),
           offsetof(struct wire_header, len));
    printf("未 packed: sizeof = %2zu  type@%zu seq@%zu len@%zu\n",
           sizeof(struct loose_header),
           offsetof(struct loose_header, type),
           offsetof(struct loose_header, seq),
           offsetof(struct loose_header, len));

    printf("g_line 地址 %% 64 = %llu\n",
           (unsigned long long)((uintptr_t)g_line % 64));
    printf("never_inlined(7) = %d\n", never_inlined(7));
    return 0;
}
```

同一份源码编两遍，两边的输出逐字相同：

`实测数据`
`Text`

```text
$ gcc -std=c23 -Wall ext_portable.c -o ext_portable_gcc.exe && ./ext_portable_gcc.exe
编译器标识：__GNUC__ = 15.2.0
packed   : sizeof =  7  type@0 seq@1 len@5
未 packed: sizeof = 12  type@0 seq@4 len@8
g_line 地址 % 64 = 0
never_inlined(7) = 22

> cl /nologo /std:c17 /utf-8 ext_portable.c && ext_portable.exe
编译器标识：_MSC_VER = 1944
packed   : sizeof =  7  type@0 seq@1 len@5
未 packed: sizeof = 12  type@0 seq@4 len@8
g_line 地址 % 64 = 0
never_inlined(7) = 22
```

**12 与 7 这两个数说的是同一件事的两面**：不加紧凑排列时，`seq` 要落在 4 的倍数上，
于是 `type` 后面补 3 个字节、`len` 后面再补 2 个字节；加了之后成员一个挨一个，
代价是 `seq` 变成非对齐访问。对齐的硬件代价与各平台的规则见
《06-更底层/02-对齐、填充与缓存.md》第 2 节。

## 2.3 行为类属性

行为类属性不改布局，它们改的是编译器对这个名字的处理方式，因此不影响 ABI，
换编译器时也不会造成两边数据对不上。

| 属性 | 作用 | 少了它会怎样 |
|---|---|---|
| `noreturn` | 声明这个函数不会返回 | 调用点后面会被塞进多余代码，还可能收到「缺少 return」的警告 |
| `noinline` | 禁止内联 | 函数被内联进调用者，调试时断点位置对不上 |
| `always_inline` | 强制内联 | 小函数在 `-O0` 下也变成一次调用 |
| `deprecated` | 用到就警告 | 旧接口被悄悄调用，没人提醒 |
| `warn_unused_result` | 丢弃返回值就警告 | `fread` 这类函数的返回值被无声丢弃 |
| `used` | 挡住编译器的丢弃 | 只被汇编引用的符号被优化掉 |
| `section` | 把符号放进指定段 | 链接脚本里为它准备的规则落空 |

这几个属性在真实项目里的分工很清楚：`noreturn` 与 `always_inline` 让生成的代码更准，
`deprecated` 与 `warn_unused_result` 让错误在编译期暴露，`used` 与 `section` 服务于链接脚本。
`used` 挡不住链接器的 `--gc-sections`，那要靠 `KEEP`，这一条在
《06-更底层/06-符号与链接属性.md》第 5.2 小节里有实测的数字。

## 2.4 写错了会怎样：属性语法不通用

把 GCC 的属性语法直接交给 MSVC，报错发生在**结构体名字那一行**，
信息里不会出现 `attribute` 这个词：

`C`

```c
/* ext_attribute_msvc.c   只编译：gcc -std=c23 -c ext_attribute_msvc.c -o ext_attribute_msvc.o
 * GCC 侧编得过；把同一份文件交给 MSVC 会报下面那几条错。 */
struct __attribute__((packed)) bad_wire {
    unsigned char  type;
    unsigned int   seq;
};

int main(void)
{
    return (int)sizeof(struct bad_wire);
}
```

`实测数据`
`Text`

```text
$ cl /nologo /std:c17 /utf-8 ext_attribute_msvc.c
ext_attribute_msvc.c(3): error C2061: 语法错误: 标识符“bad_wire”
ext_attribute_msvc.c(3): error C2059: 语法错误:“;”
ext_attribute_msvc.c(3): error C2449: 在文件范围内找到“{”(是否缺少函数头?)
ext_attribute_msvc.c(6): error C2059: 语法错误:“}”
```

反方向更隐蔽。GCC 认 `__declspec` 这个拼写，但只认一部分：

`C`

```c
/* declspec_partial.c   编译：gcc -std=c23 declspec_partial.c -o declspec_partial.exe
 * 逐个试 __declspec 的几种形式，看 GCC 收哪些、忽略哪些。 */
#include <stdio.h>
#include <stddef.h>

struct with_declspec_align {
    char c;
    __declspec(align(64)) int x;      /* 想让 x 落在 64 字节边界上 */
};

struct with_attribute_align {
    char c;
    __attribute__((aligned(64))) int x;
};

__declspec(noinline)    static int f_noinline(int v)    { return v + 1; }
__declspec(deprecated)  static int f_deprecated(void)   { return 2; }

int main(void)
{
    printf("declspec(align)   : sizeof = %2zu  offsetof(x) = %zu\n",
           sizeof(struct with_declspec_align),
           offsetof(struct with_declspec_align, x));
    printf("attribute(aligned): sizeof = %2zu  offsetof(x) = %zu\n",
           sizeof(struct with_attribute_align),
           offsetof(struct with_attribute_align, x));
    printf("noinline  = %d, deprecated = %d\n", f_noinline(1), f_deprecated());
    return 0;
}
```

`实测数据`
`Text`

```text
$ gcc -std=c23 declspec_partial.c -o declspec_partial.exe
declspec_partial.c:8:5: warning: 'align' attribute directive ignored [-Wattributes]
    8 |     __declspec(align(64)) int x;
      |     ^~~~~~~~~~
declspec_partial.c:27:5: warning: 'f_deprecated' is deprecated [-Wdeprecated-declarations]
declspec(align)   : sizeof =  8  offsetof(x) = 4
attribute(aligned): sizeof = 128  offsetof(x) = 64
noinline  = 2, deprecated = 2
```

**`noinline` 与 `deprecated` 生效了，`align` 只给了一句警告就被丢掉**：
`sizeof` 从 128 掉回 8，`offsetof` 从 64 掉回 4。同一份源码在 MSVC 上得到的是另一半结果：

`实测数据`

| 编译器的处理 | `sizeof` | `offsetof(x)` |
|---|---|---|
| GCC 15.2.0 读 `__declspec(align(64))` | 8 | 4（**忽略，只给警告**） |
| MSVC 19.44 读 `__declspec(align(64))` | 128 | 64 |
| MSVC 19.51 读 `__declspec(align(64))` | 128 | 64 |
| GCC 15.2.0 读 `__attribute__((aligned(64)))` | 128 | 64 |

> [!CAUTION]
> **这条警告很容易被淹没在编译输出里。** 布局类的属性被忽略之后，
> 编译、链接、运行全部正常，只有在协议解析、DMA 描述符、共享内存这些对字节位置敏感的地方才会出错，
> 而且错的是「数据不对」这类最难查的症状。布局类属性务必在两种编译器上各验一次
> `sizeof` 与 `offsetof`。

# 第 3 节 `#pragma`

`#pragma` 是标准留给实现的一条出口：**标准规定它的语法，但不规定它的意思**。
写法在《04-语法/14-预处理器.md》第 8 节已经讲过，另一面是跨编译器时 `#pragma` 靠什么站稳。

## 3.1 不认识的杂注怎么处置

标准要求实现忽略不认识的 `#pragma`，因此**一条没人认得的杂注不会让编译失败**，
它只是什么也不做。两套编译器都会提醒一句：

`C`

```c
/* pragma_unknown.c   编译：gcc -std=c23 -Wall -Wunknown-pragmas pragma_unknown.c -o pragma_unknown.exe
 *                     MSVC：cl /nologo /std:c17 /W4 /utf-8 pragma_unknown.c */
#include <stdio.h>

#pragma GCC optimize("O0")     /* GCC 认识 */
#pragma my_compiler magic 42   /* 谁也不认识 */

int main(void)
{
    printf("ok\n");
    return 0;
}
```

`实测数据`
`Text`

```text
$ gcc -std=c23 -Wall -Wunknown-pragmas pragma_unknown.c -o pragma_unknown.exe
pragma_unknown.c:4: warning: ignoring '#pragma my_compiler magic' [-Wunknown-pragmas]
    4 | #pragma my_compiler magic 42   /* 不认识 */
      |          ^~~~~~~~~~~

$ cl /nologo /std:c17 /W4 /utf-8 pragma_unknown.c
pragma_unknown.c(3): warning C4068: 未知的杂注“GCC”
pragma_unknown.c(4): warning C4068: 未知的杂注“my_compiler”
```

两份输出对着读能看出一个要点：**GCC 只对自己的那条杂注有反应，MSVC 把两条都当成未知**。
一条为 GCC 写的 `#pragma` 留在源码里，在 MSVC 上就是一句警告，而**警告容易被忽略**。
如果那条杂注恰好是 `#pragma pack` 这类改布局的，忽略之后就是第 2.4 小节那种静默的布局错误。

> [!TIP]
> **跨编译器项目里打开 `-Wunknown-pragmas` / `/W4`**，让「这条杂注在这儿没人认」当场说出来。
> GCC 上它包含在 `-Wall` 里，MSVC 的 `C4068` 要到 `/W4`。

## 3.2 诊断开关：一对 push 与 pop

最常用的 `#pragma` 是临时关掉一条警告。它必须成对出现，作用范围从 `push` 到 `pop`：

`C`

```c
/* pragma_diag.c   编译：gcc -std=c23 -Wall -Wextra pragma_diag.c -o pragma_diag.exe
 *                  MSVC：cl /nologo /std:c17 /W4 /utf-8 pragma_diag.c
 * 同一句会报警告的比较写两遍，中间那句夹在一对 push/pop 之间。 */
#include <stdio.h>

#if defined(_MSC_VER)
#  define DIAG_PUSH       __pragma(warning(push))
#  define DIAG_IGNORE     __pragma(warning(disable : 4018))   /* C4018：有符号/无符号不匹配 */
#  define DIAG_POP        __pragma(warning(pop))
#else
#  define DIAG_PUSH       _Pragma("GCC diagnostic push")
#  define DIAG_IGNORE     _Pragma("GCC diagnostic ignored \"-Wsign-compare\"")
#  define DIAG_POP        _Pragma("GCC diagnostic pop")
#endif

int main(void)
{
    int      x = -1;
    unsigned u = 1u;
    int      inside, outside;

DIAG_PUSH
DIAG_IGNORE
    inside = (x < u);         /* 这一段里的警告被压掉 */
DIAG_POP

    outside = (x < u);        /* 出了这一段，同样的警告照旧 */

    printf("%d %d\n", inside, outside);
    return 0;
}
```

`实测数据`
`Text`

```text
$ gcc -std=c23 -Wall -Wextra pragma_diag.c -o pragma_diag.exe
pragma_diag.c:27:18: warning: comparison of integer expressions of different signedness:
    'int' and 'unsigned int' [-Wsign-compare]
   27 |     outside = (x < u);        /* 出了这一段，同样的警告照旧 */

$ cl /nologo /std:c17 /W4 /utf-8 pragma_diag.c
pragma_diag.c(27): warning C4018: “<”: 有符号/无符号不匹配
```

**两边的输出都只剩第 27 行**，第 24 行被压掉了。运行结果是 `0 0`：
`(x < u)` 把 `x` 转成 `unsigned` 之后是 `4294967295 < 1`，两次都是假。

这里有一个容易被忽略的细节：**诊断的位置决定了它受不受压制**。
上面这份程序把变量定义为「未使用」时，警告会在函数结束时才发出，
那时 `pop` 早已生效，压制就落空了——实测中 `-Wunused-variable` 与 MSVC 的 `C4189` 都是这种表现。
把范围写小、把 `pop` 写在警告真正发出的位置之前，才压得住。

## 3.3 紧凑布局与 ABI

`#pragma pack` 是 `#pragma` 里影响最深远的一条，因为它改的是内存布局，
而布局是 ABI 的一部分。

| 事实 | 后果 |
|---|---|
| `pack` 之后的 `sizeof` 与 `offsetof` 两边一致（第 2.2 小节的两边数字一致：7 与 0/1/5） | 布局类杂注**可以**跨编译器，前提是两边都认 |
| GCC 用 `__attribute__((packed))`、MSVC 只用 `#pragma pack` | 写法必须隔离，语义一致 |
| 紧凑之后成员可能非对齐 | 访问代价上升，Cortex-M3 上逐字节访问实测是 8 → 18 周期 |
| 布局变了，但**只在同一个编译单元里**变 | 头文件里加 `pack` 而不还原，会波及所有包含它的翻译单元 |

> [!WARNING]
> **`#pragma pack(push, 1)` 必须配一个 `#pragma pack(pop)`。**
> 少写 `pop` 时，后面所有结构体的布局都被改掉，包括系统头文件里的那些。
> 症状是随机的：某个库函数表现异常，或者结构体大小与对方对不上。
> 这类错误在源码里看不出来，只有在 `sizeof` 的实测数字上才露出马脚。

# 第 4 节 内建函数

内建函数（builtin）是编译器把自己的知识借给程序的一批名字，几乎全部以 `__builtin_` 开头。
它们与普通库函数的区别在于：**编译器知道它们是什么意思，可以内联展开，也可以直接对它们做推理**。
`__builtin_expect` 会被翻译成一条概率信息，`__builtin_unreachable()` 会被翻译成一句「这里到不了」的断言。

## 4.1 一张对照表

`实测数据`

| 内建函数 | 作用 | MSVC 上的对应件 |
|---|---|---|
| `__builtin_expect(e, c)` | 告诉编译器 `e == c` 的可能性 | 无（靠 `/O2` 的静态预测） |
| `__builtin_unreachable()` | 断言控制流到不了这里 | `__assume(0)` |
| `__builtin_trap()` | 立刻让程序停下来（不返回） | `__debugbreak()` / `__fastfail` |
| `__builtin_abort()` | 相当于 `abort()`，但不经过库 | `abort()` |
| `__builtin_add_overflow(a,b,&r)` | 相加并给出是否溢出 | 无（`_addcarry_u32` 等要手写） |
| `__builtin_mul_overflow` / `sub_overflow` | 同上，乘与减 | 无直接对应 |
| `__builtin_popcount(x)` | 数 1 的个数 | `__popcnt`（需要 CPU 支持） |
| `__builtin_clz(x)` / `ctz` | 前导零 / 末尾零个数 | `_BitScanReverse` / `_BitScanForward` |
| `__builtin_bswap32(x)` | 字节序翻转 | `_byteswap_ulong` |
| `__builtin_offsetof(T, m)` | 成员偏移 | `offsetof` 宏（C 里本来就是内建） |
| `__builtin_alloca(n)` | 栈上分配 | `_alloca` |

**这张表里最值得动手量的是前三个**，因为它们不是「多一个函数」，
而是把一条编译器内部的信息交给了程序，因此能改变生成的代码。

## 4.2 `__builtin_expect`：一条概率信息

它的两个参数是「表达式」与「期望的取值」，编译器只把它当成概率。
下面的对照把同一个循环写了三遍，只有判断外面套没套这一层。
两份源码各编一个目标文件，读 `.text` 段的大小：

`C`

```c
/* expect_off.c   只编译：gcc -std=c23 -O2 -c expect_off.c -o expect_off.o
 * 与 expect_on.c 只差判断外面有没有 __builtin_expect。 */
#include <stdio.h>

int find(const int *a, int n, int key)
{
    int hits = 0;
    for (int i = 0; i < n; i++)
        if (a[i] == key) { hits++; printf("命中 %d\n", i); }
    return hits;
}
```

`C`

```c
/* expect_on.c   只编译：gcc -std=c23 -O2 -c expect_on.c -o expect_on.o */
#include <stdio.h>

int find(const int *a, int n, int key)
{
    int hits = 0;
    for (int i = 0; i < n; i++)
        if (__builtin_expect(a[i] == key, 0)) { hits++; printf("命中 %d\n", i); }
    return hits;
}
```

`实测数据`
`Bash`

```bash
gcc -std=c23 -O2 -c expect_off.c -o expect_off.o
gcc -std=c23 -O2 -c expect_on.c  -o expect_on.o
objdump -h expect_off.o | grep "\.text"
objdump -h expect_on.o  | grep "\.text"
```

`实测数据`
`Text`

```text
expect_off.o  .text = 0x00000080     ← 128 字节
expect_on.o   .text = 0x00000070     ← 112 字节
```

代码布局也跟着变了。加提示的那一版把「命中」这一支挪到了函数的尾部，
循环体只剩一条比较与一条回跳：

`实测数据`
`Assembly`

```asm
; objdump -d --no-show-raw-insn expect_on.o     （只截了循环部分）
     a0:	cmp    %ebp,(%rdi,%rbx,4)
     a3:	je     c0 <find+0x40>          ; 命中才跳出去，是冷路径
     a5:	add    $0x1,%rbx
     a9:	cmp    %rbx,%rsi
     ac:	jne    a0 <find+0x20>          ; 热路径是笔直的一条
```

`Assembly`

```asm
; objdump -d --no-show-raw-insn expect_off.o    （只截了循环部分）
    29:	cmp    %ebp,(%rdi,%rbx,4)
    2c:	jne    20 <find+0x20>
    2e:	lea    0x0(%rip),%rcx        # 35 <find+0x35>
    35:	mov    %ebx,%edx
    37:	add    $0x1,%rbx
    3b:	call   40 <find+0x40>        ; printf 直接落在循环体里
```

> [!IMPORTANT]
> **`__builtin_expect` 只在编译器本来就拿不准的时候起作用。**
> 《04-语法/15-奇技淫巧与优化.md》第 7.3 小节给过一个简单情形：加不加提示，函数体逐条相同
> （那份记录的附录 A.8）。差别出现在「热路径能因此变成笔直一条」的形状里，
> 也就是循环里的罕见分支、错误处理这些位置——这正是 `unlikely()` 这类宏唯一被使用的地方。

## 4.3 `__builtin_unreachable`：一句不被检查的断言

它的意思是「控制流到不了这一行」，编译器可以据此推出结论。
下面的 `switch` 已经覆盖了枚举的全部取值，兜底那条返回因此是多余的：

`C`

```c
/* unreach_off.c   只编译：gcc -std=c23 -O2 -c unreach_off.c -o unreach_off.o
 * 与 unreach_on.c 只差最后那一行 __builtin_unreachable()。 */
enum color { RED = 0, GREEN = 1, BLUE = 2 };

const char *color_name(enum color c)
{
    switch (c) {
    case RED:   return "RED";
    case GREEN: return "GREEN";
    case BLUE:  return "BLUE";
    }
    return "unknown";
}
```

`C`

```c
/* unreach_on.c   只编译：gcc -std=c23 -O2 -c unreach_on.c -o unreach_on.o */
enum color { RED = 0, GREEN = 1, BLUE = 2 };

const char *color_name(enum color c)
{
    switch (c) {
    case RED:   return "RED";
    case GREEN: return "GREEN";
    case BLUE:  return "BLUE";
    }
    __builtin_unreachable();
}
```

`实测数据`
`Text`

```text
unreach_off.o  .text = 0x00000040     字符串 unknown 在目标文件里：在
unreach_on.o   .text = 0x00000030     字符串 unknown 在目标文件里：不在
```

`实测数据`
`Assembly`

```asm
; objdump -d --no-show-raw-insn unreach_on.o
0000000000000000 <color_name>:
   0:	lea    0x4(%rip),%rax        # b <color_name+0xb>
   7:	cmp    $0x1,%ecx
   a:	je     21 <color_name+0x21>
   c:	lea    0xa(%rip),%rax        # 1d <color_name+0x1d>
  13:	cmp    $0x2,%ecx
  16:	lea    0x0(%rip),%rdx        # 1d <color_name+0x1d>
  1d:	cmovne %rdx,%rax
  21:	ret
```

**兜底分支与那句字符串一起消失了**，函数从 64 字节降到 48 字节。
C23 把这件事收进了标准：`<stddef.h>` 里的 `unreachable()` 宏。

`文档`

> "An invocation of the function-like macro unreachable indicates that the particular
> flow control that leads to the invocation will never be taken; it receives no arguments
> and expands to a void expression. The program execution shall not reach such an invocation."
>
> —— N3220 §7.21.1

**标准用的词是 shall not**，也就是说这句断言的另一面是义务：
程序真的走到那里，行为就是未定义的（同节第 3 段：`If a macro invocation unreachable() is
reached during execution, the behavior is undefined.`）。

## 4.4 写错了会怎样：把断言写成事实

断言一旦不被检查，写错的代价就直接落在程序上。下面两个函数都声称「下标一定合法」，
一个用 `__builtin_unreachable`，一个用 `assert`：

`C`

```c
/* unreachable_abuse.c   编译：gcc -std=c23 -O2 unreachable_abuse.c -o unreachable_abuse.exe
 * 两种「断言下标合法」的写法：一个不会被检查，一个会。 */
#include <stdio.h>
#include <assert.h>

int pick_unchecked(int *a, int n, int i)     /* 用 __builtin_unreachable 断言 */
{
    if (i >= n)
        __builtin_unreachable();
    return a[i];
}

int pick_checked(int *a, int n, int i)       /* 用 assert 断言 */
{
    assert(i < n);
    return a[i];
}

int main(void)
{
    int a[4] = { 1, 2, 3, 4 };

    printf("合法下标：%d %d\n", pick_unchecked(a, 4, 2), pick_checked(a, 4, 2));
    printf("非法下标：%d（没有任何提示）\n", pick_unchecked(a, 4, 9));
    printf("非法下标：%d\n", pick_checked(a, 4, 9));   /* 这一行到不了 */
    return 0;
}
```

`实测数据`
`Assembly`

```asm
; objdump -d --no-show-raw-insn unreachable_abuse.o     （gcc 15.2.0 -O2）
0000000000000000 <pick_unchecked>:        ; 检查整条不见
   0:	movslq %r8d,%r8
   3:	mov    (%rcx,%r8,4),%eax
   7:	ret

0000000000000010 <pick_checked>:
  10:	sub    $0x28,%rsp
  14:	cmp    %edx,%r8d                    ; 真正的检查
  17:	jge    25 <pick_checked+0x15>
  19:	movslq %r8d,%r8
  1c:	mov    (%rcx,%r8,4),%eax
  20:	add    $0x28,%rsp
  24:	ret
  25:	lea    0x0(%rip),%rdx               ; 不满足时走 __assert_fail
```

同一个错误在两个平台上留下了两种现场：

`实测数据`

| 平台与编译命令 | 现场 |
|---|---|
| Windows，gcc 15.2.0 `-O2` | 退出码 **`0xC0000005`**（访问冲突）；崩溃前那两行 `printf` 的输出**全部丢失**（缓冲区没来得及刷新） |
| WSL Ubuntu，gcc 13.3.0 `-O2` | `main` 里第一句之后的代码被整段删掉，控制流落进后面的函数；同一行打印了 **28887 行**后段错误（连跑三次都是 28887 行） |

**第二次运行的三次计数完全相同**，这不是随机现象，而是编译器按「那里到不了」重排代码之后
必然的落点。`assert` 版本的表现则完全可预期：断言失败，打印一行诊断，`abort`。

> [!CAUTION]
> **`assert` 会在 `NDEBUG` 下消失，`__builtin_unreachable` 永远不会。**
> 把「运行时检查」写成 `__builtin_unreachable` 是两件事的混淆：
> 前者在发布版里被去掉时至少还有 `NDEBUG` 这个痕迹，
> 后者从编译那一刻起就改变了推理前提。要用它，先确认那条路径在**任何输入下**都到不了。

## 4.5 `__builtin_add_overflow`：溢出的正确答案

判断有符号加法是否溢出，用加法本身去判断是行不通的（`a + b` 一旦溢出，那次加法已经是 UB）。
内建函数把和与标志一起交出来：

`C`

```c
/* builtin_overflow.c   编译：gcc -std=c23 builtin_overflow.c -o builtin_overflow.exe
 * __builtin_add_overflow：一条内建函数同时给出和与「是否溢出」。 */
#include <stdio.h>
#include <limits.h>

int main(void)
{
    int a = INT_MAX, b = 1, sum = 0;

    if (__builtin_add_overflow(a, b, &sum))
        printf("内建函数：%d + %d 溢出，和不可用\n", a, b);
    else
        printf("内建函数：%d + %d = %d\n", a, b, sum);

    int manual = a + b;                 /* 这一句本身就已经是 UB */
    printf("手写加法：%d（无可用的溢出信息）\n", manual);

    /* 乘法同样有：__builtin_mul_overflow，还有 sub 版本 */
    long long prod = 0;
    printf("100000 * 100000 溢出吗：%d\n",
           __builtin_mul_overflow(100000, 100000, &prod));
    printf("100000 * 100000 = %lld\n", prod);
    return 0;
}
```

`实测数据`
`Text`

```text
内建函数：2147483647 + 1 溢出，和不可用
手写加法：-2147483648（无可用的溢出信息）
100000 * 100000 溢出吗：0
100000 * 100000 = 10000000000
```

第三次是「没有溢出」的那一面：`100000 * 100000` 放进 `long long` 里够宽，因此标志为 0。
**这一族函数的意义在于把「溢出」从一种状态变成了一条可读的返回值**，
而手写版本无论怎么写都绕不开「先做一次已经 UB 的加法」这个死结。

# 第 5 节 隔离

扩展本身不可怕，可怕的是它散落在业务代码里。隔离层的目标只有一个：
**让扩展只出现在一个头文件里，别处都写普通的名字。**

## 5.1 三个编译器宏

每套编译器都会定义一组标识自己的宏，条件编译就靠它们。

`实测数据`

| 宏 | 谁定义 | 常见取值 | 用来判断 |
|---|---|---|---|
| `_MSC_VER` | MSVC | `1944`（19.44）、`1951`（19.51） | 是不是 MSVC，以及哪一版 |
| `__GNUC__` | GCC 与「假装成 GCC」的编译器 | `15`（GCC 15.2.0） | 有没有 GCC 的扩展 |
| `__GNUC_MINOR__` / `__GNUC_PATCHLEVEL__` | 同上 | `2` / `0` | 精确版本 |
| `__clang__` | Clang | `1` | 是不是 Clang（它同时定义 `__GNUC__`） |
| `_MSC_FULL_VER` | MSVC | 完整版本号 | 需要区分补丁级时 |
| `__STDC_VERSION__` / `__cplusplus` | 都定义 | `202311L` / `201703L` | 语言版本，不是编译器品牌 |

**`__clang__` 必须排在 `__GNUC__` 前面判断**：Clang 为了兼容会一并定义 `__GNUC__` 与 `__GNUC_MINOR__`，
先判 `__GNUC__` 会把 Clang 误认成 GCC。

## 5.2 隔离层的写法

第 2.2 小节的 `ext_portable.c` 已经把骨架写出来了：三支 `#if` 各给一套宏定义，
`PACK_BEGIN` 与 `PACK_END` 分别展开成两套编译器各自的杂注，
最后一支用 `#error` 兜底。那个文件的完整内容就在第 2.2 小节，这里不重复。

四条写隔离层的经验：

| 做法 | 理由 |
|---|---|
| 每支都要给，最后留 `#else #error` | 换了编译器会当场编译失败，而不是静默走错分支 |
| 宏名用业务语义（`PACK_BEGIN`），不要用编译器名字 | 业务代码里不该出现 `__attribute__` |
| `#pragma` 想放进宏，只能用 `_Pragma` | `#pragma` 不能由宏展开产生，`_Pragma` 是标准给的替代 |
| 隔离层放在一个头文件里，随项目一起发布 | 否则每个用到扩展的文件都要抄一遍 |

## 5.3 已经变成标准的那一部分

属性语法本身已经进了标准。C++11 起用 `[[...]]`，C23 也把同一套属性语法收了进来：

`C++`

```cpp
/* attr_std.cpp   编译：g++ -std=c++17 -Wall attr_std.cpp -o attr_std.exe
 *                 MSVC：cl /nologo /std:c++17 /EHsc attr_std.cpp */
#include <cstdio>

[[nodiscard]] int compute(int x) { return x * 2; }

int main()
{
    compute(21);                 /* 返回值被丢掉：标准属性会让两套编译器都警告 */
    [[maybe_unused]] int v = 1;
    std::printf("ok\n");
    return 0;
}
```

`实测数据`
`Text`

```text
$ g++ -std=c++17 -Wall attr_std.cpp -o attr_std.exe
attr_std.cpp:9:12: warning: ignoring return value of 'int compute(int)',
    declared with attribute 'nodiscard' [-Wunused-result]

$ cl /nologo /std:c++17 /EHsc attr_std.cpp
attr_std.cpp(9): warning C4834: 放弃具有 [[nodiscard]] 属性的函数的返回值
```

**同一份源码、同一个属性、两套编译器各自的警告**，这就是「进了标准」的样子：
不再需要隔离层，也不再有第 2.4 小节那种被忽略的写法。

`文档`

> "The nodiscard attribute shall be applied to a function or to the definition of a
> structure, union, or enumeration type."
>
> —— N3220 §6.7.13.3

C++ 侧的同一属性在 N4659 §10.6.7（Nodiscard attribute）。哪些扩展已经走过这条路，
可以用一张表看全：

| 当年的扩展 | 现在写什么 | 依据 |
|---|---|---|
| `__int64` | `long long` | C99 起进标准 |
| `__typeof__` | C++ 的 `decltype`、C23 的 `typeof` | N3220 §6.7.2.5 |
| `__attribute__((noreturn))` | `[[noreturn]]` | C++11 / C23 |
| `__attribute__((warn_unused_result))` | `[[nodiscard]]` | N4659 §10.6.7 / N3220 §6.7.13.3 |
| `__builtin_unreachable()` | `unreachable()` | N3220 §7.21.1（在 `<stddef.h>` 里） |
| `#pragma once` | 仍无标准写法 | 包含保护仍是标准做法 |
| `__declspec(dllexport)` | 仍无标准写法 | 动态库导出不属于语言 |

> [!TIP]
> **选写法的顺序**：能用标准写法就用标准写法，退而求其次用两套编译器都认的事实标准，
> 只有当前两者都不存在时，才动隔离层。

## 5.4 隔离层盖不住的地方

有些差异没法用一个宏抹平，遇到它们要改的是设计，不是宏。

| 差异 | 为什么盖不住 | 怎么办 |
|---|---|---|
| 弱符号 | MSVC 没有对应属性，只能在链接器命令行上做 | 把「可覆盖的默认实现」改成注册函数指针 |
| 构造函数 | MSVC 靠 `.CRT$XCU` 段，GCC 靠属性 | 显式写一个 `init()` 并由启动代码调用 |
| 内建函数 | 名字与语义都不同，`__builtin_add_overflow` 在 MSVC 上没有对应件 | 各写一份实现，用同一个函数名包起来 |
| 内联汇编 | 语法完全不同（AT&T 与 Intel、约束写法） | 抽成单独的 `.s` 文件或彻底避免 |
| 结构体布局 | 属性写法不同，但语义相同（第 2.2 小节两边都是 7 字节） | 隔离宏即可，但**必须两边各验一次 `sizeof`** |

**最后一行是最容易被低估的。** 布局类扩展是唯一一类「写错了不报错，只把数据弄乱」的扩展，
而它恰恰又最容易跨过编译器边界：一份被 `pack` 过的结构体，
只要有一边忘了 `pack`，两边对同一个字节的解释就错开了。

# 第 6 节 未定义行为

与前面五节「标准之外多出来的东西」相对，未定义行为是标准之内那块**故意留空**的地方。
两者在写代码时的表现很像：都不报错，都可能换一个编译器就变样。

## 6.1 标准怎么说

`文档`

> "undefined behavior
> behavior, upon use of a nonportable or erroneous program construct or of erroneous data,
> for which this document imposes no requirements"
>
> —— N3220 §3.4.3

C++ 侧的措辞几乎一样：

`文档`

> "undefined behavior
> behavior for which this International Standard imposes no requirements"
>
> —— N4659 §3.27

「imposes no requirements」是这句话的全部要害：**标准对这段程序不提任何要求**，
于是编译器可以做任何事，包括把整段代码删掉。标准还特意说明，
未定义行为不只有一种触发方式：

`文档`

> "Undefined behavior is otherwise indicated in this document by the words
> 'undefined behavior' or by the omission of any explicit definition of behavior.
> There is no difference in emphasis among these three; they all describe
> 'behavior that is undefined'."
>
> —— N3220 §4/2

**「标准没有说」与「标准说了是 UB」是同一种东西。** 这一点解释了为什么很多 UB 在标准里
根本找不到「undefined」这个词：整数的位运算没有规定符号表示，于是有符号溢出就不在保证范围内；
指针的算术没有规定越界之后是什么，于是越界访问也不在。

> [!IMPORTANT]
> **UB 不是「结果随机」。** 它比随机更强：编译器有权假设它不会发生，
> 并据此删掉代码、改写分支、把整个函数折叠成一个常量。第 6.3 小节里 `c1` 在 `-O2` 下
> 只剩两条指令，就是这个过程的结果。

## 6.2 为什么标准要留出这块空地

原因有两个，一个来自硬件，一个来自优化。

| 来源 | 具体表现 |
|---|---|
| **硬件差异** | 有的机器整数用补码、有的用反码；有的机器对齐错会触发故障、有的只是慢一点；有符号溢出在有的机器上会陷入陷阱 |
| **优化自由** | 只要程序保证「不越界、不溢出」，编译器就能用更宽的整数运算、把循环向量化、把检查提到循环外 |

第二点是关键：**标准把「程序没有 UB」当作一张可以随便用的通行证交给了编译器**。
这张通行证换来的性能是真实的——第 6.3 到 6.7 小节的每一组对照里，
`-O2` 之所以能那么写，前提都是「那件事不会发生」。

## 6.3 第一组：有符号整数溢出

三处溢出都藏在「看起来显然成立」的判断里。

`C`

```c
/* ub_overflow.c   编译：gcc -std=c23 -O0 ub_overflow.c -o ub_overflow_O0.exe
 *                 （同一份源码换 -O2 再编一次，结果见正文）
 * 三处有符号整数溢出，都藏在「看起来显然成立」的判断里。 */
#include <stdio.h>
#include <limits.h>

int c1(int x) { if (x < 0) x = -x; return x >= 0; }        /* INT_MIN 取负溢出 */
int c2(int x) { int y = x * 2; return y / 2 == x; }        /* 乘 2 再除 2 */
int c3(int x) { int y = x + 1; return y > x; }             /* 加 1 之后比大小 */

int main(void)
{
    printf("c1(INT_MIN) = %d\n", c1(INT_MIN));
    printf("c2(INT_MAX) = %d\n", c2(INT_MAX));
    printf("c3(INT_MAX) = %d\n", c3(INT_MAX));
    return 0;
}
```

`实测数据`

| 函数 | `-O0` 的结果 | `-O2` 的结果 | `-O2 -fwrapv` 的结果 |
|---|---|---|---|
| `c1(INT_MIN)` | 0 | **1** | 0 |
| `c2(INT_MAX)` | 0 | **1** | 0 |
| `c3(INT_MAX)` | 0 | **1** | 0 |

**同一个二进制换一档优化，三个答案全部翻转。** `c1` 的反汇编把变化说透了：

`实测数据`
`Assembly`

```asm
; gcc -std=c23 -O0 -c ub_overflow.c     → objdump -d --no-show-raw-insn
0000000000000000 <c1>:                    ; 老老实实取负、再判断符号
   0:	push   %rbp
   4:	mov    %ecx,0x10(%rbp)
   7:	cmpl   $0x0,0x10(%rbp)
   b:	jns    10 <c1+0x10>
   d:	negl   0x10(%rbp)
  10:	mov    0x10(%rbp),%eax
  13:	not    %eax
  15:	shr    $0x1f,%eax
  18:	movzbl %al,%eax
  1c:	ret
```

`Assembly`

```asm
; gcc -std=c23 -O2 -c ub_overflow.c      → 同一个源文件
0000000000000000 <c1>:                    ; 整个函数变成一个常量
   0:	mov    $0x1,%eax
   5:	ret
```

`-O2` 的推理是：`x < 0` 时 `-x` 不会溢出，所以取负之后必定为正；`x >= 0` 时本来就为真。
两条路都通向 `return 1`，于是函数被折叠成 `return 1`，连参数都不读了。

> [!CAUTION]
> **`-fwrapv` 能把这一组变回 `-O0` 的结果**：它告诉编译器「有符号溢出按补码回绕，是定义好的」。
> 表中的第三列就是它。代价是编译器失去了「不会溢出」这条前提，
> 一些依赖它的优化（循环向量化、归纳变量化简）会退回去。

## 6.4 第二组：越界访问

`C`

```c
/* ub_bounds.c   编译：gcc -std=c23 -O0 ub_bounds.c -o ub_bounds_O0.exe
 *               （同一份源码换 -O2 再编一次，结果见正文） */
#include <stdio.h>
#include <stdlib.h>

int read_one_past(void)               /* 局部数组多读一个元素 */
{
    int a[4] = { 10, 20, 30, 40 };
    int s = 0;
    for (int i = 0; i <= 4; i++)
        s += a[i];
    return s;
}

int heap_one_past(void)               /* 堆上多读一个元素 */
{
    int *p = malloc(4 * sizeof *p);
    for (int i = 0; i < 4; i++)
        p[i] = i;
    int bad = p[4];
    free(p);
    return bad;
}

int main(void)
{
    printf("read_one_past() = %d\n", read_one_past());
    printf("heap_one_past() = %d\n", heap_one_past());
    return 0;
}
```

`实测数据`

| 函数 | `-O0` | `-O2` | 说明 |
|---|---|---|---|
| `read_one_past()` | **101** | **100** | 多读的那一个元素，两档读到的不是同一块内存 |
| `heap_one_past()` | 1869896820 | 1869896820 | 两次读的都是垃圾值；这个数换一次运行就变（另一次测到 1550148719） |

两次汇编的差别比数字更有说服力：

`实测数据`
`Assembly`

```asm
; gcc -std=c23 -O0 -c ub_bounds.c
0000000000000000 <read_one_past>:        ; 数组真的建在栈上，循环真的执行 5 次
   8:	movl   $0xa,-0x20(%rbp)          ; a[0] = 10
   f:	movl   $0x14,-0x1c(%rbp)         ; a[1] = 20
  16:	movl   $0x1e,-0x18(%rbp)         ; a[2] = 30
  1d:	movl   $0x28,-0x14(%rbp)         ; a[3] = 40
  32:	jmp    44
  34:	mov    -0x8(%rbp),%eax
  39:	mov    -0x20(%rbp,%rax,4),%eax   ; 下标 4 时读到相邻槽位
  40:	addl   $0x1,-0x8(%rbp)
  44:	cmpl   $0x4,-0x8(%rbp)
  48:	jle    34
```

`Assembly`

```asm
; gcc -std=c23 -O2 -c ub_bounds.c
0000000000000000 <read_one_past>:        ; 数组没了，循环也没了
   0:	sub    $0x18,%rsp
   4:	mov    0x10(%rsp),%eax           ; 读一个栈上未初始化的位置
   8:	add    $0x64,%eax                ; 加上常量 100
   b:	add    $0x18,%rsp
   f:	ret
```

`-O0` 的版本里数组确实存在，`a[4]` 读到了相邻槽位里的 1，于是 `100 + 1 = 101`。
`-O2` 的版本把数组整个消掉，剩下「读一个未初始化的栈位置再加 100」，
这次那个位置恰好是 0，于是结果是 100。**两次都不对**，只是错法不同。

编译器在 `-O2` 下提醒过一次：

`实测数据`
`Text`

```text
ub_bounds.c:11:15: warning: iteration 4 invokes undefined behavior [-Waggressive-loop-optimizations]
   11 |         s += a[i];
      |              ~^~~
ub_bounds.c:10:23: note: within this loop
   10 |     for (int i = 0; i <= 4; i++)
```

> [!WARNING]
> **`-Waggressive-loop-optimizations` 只在优化打开时才出现。** 它说的正是
> 「你的循环有一轮是 UB，我要按它不存在来处理」。看到这条警告不要去关掉它，
> 它是编译期能给出的最强提示之一。

堆上那一份两档结果相同，是因为越界读到的都是紧邻块的管理信息，
而两档的分配布局没有变。**数值相同不代表正确**：它换一次运行就会变
（同一份程序另一次运行读到 1550148719），这一处要靠 ASan 才抓得到（第 7.2 小节）。

## 6.5 第三组：空指针解引用

`C`

```c
/* ub_null.c   编译：gcc -std=c23 -O2 ub_null.c -o ub_null_O2.exe
 *             （同一份源码换 -O0 再编一次，汇编见正文） */
#include <stdio.h>

int probe(int *p)
{
    int v = *p;                       /* 无条件解引用：编译器据此认为 p 不是空指针 */
    if (p == NULL) return -1;         /* 上面已经是 UB，这一行成了死代码 */
    return v;
}

int main(void)
{
    int v = 7;
    printf("probe(&v)   = %d\n", probe(&v));
    printf("probe(NULL) = %d\n", probe(NULL));
    return 0;
}
```

`实测数据`

| 编译 | 运行结果 |
|---|---|
| `gcc -std=c23 -O0` | 退出码 **`0xC0000005`**（访问冲突），两行输出都来不及刷新 |
| `gcc -std=c23 -O2` | 退出码 **`0xC0000005`**，同样没有输出 |

两次都崩，**但崩的原因不同**。看 `probe` 的两种形态：

`实测数据`
`Assembly`

```asm
; -O0：判空这一行真的存在
0000000000000000 <probe>:
   0:	push   %rbp
   4:	mov    %ecx,0x10(%rbp)
   8:	mov    0x10(%rbp),%rax
   c:	mov    (%rax),%eax           ; 先解引用
   e:	mov    %eax,-0x4(%rbp)
  11:	cmpq   $0x0,0x10(%rbp)       ; 再判空
  16:	jne    1f
  18:	mov    $0xffffffff,%eax
  1c:	jmp    21
```

`Assembly`

```asm
; -O2：判空整条消失，函数只剩两次访存
0000000000000000 <probe>:
   0:	mov    (%rcx),%eax
   2:	ret
```

**`-O0` 上崩在那次解引用，`-O2` 上连「本来会返回 -1 的那条路」都不存在了。**
换句话说：写在解引用之后的判空，无论优化等级如何都不起作用；
而 `-O2` 还会把它从代码里删掉，让「这段代码有判空」这个印象彻底消失。

> [!IMPORTANT]
> **编译器认为地址 0 不可访问，这是一个可以关掉的假设。**
> Cortex-M 复位时正是从地址 0 取走栈顶与第一条指令的地址（STM32 上那里是 flash 的别名），
> 也就是说在裸机上地址 0 完全可能是一个合法地址。内核与裸机程序因此常开
> `-fno-delete-null-pointer-checks`，让编译器不要用「解引用过就非空」这条推理。

`待确认`

上面这条按 Cortex-M 的复位取向量行为写成，本机没有在真板上验证过「地址 0 可用于正常访存」；
向量表本身的位置与内容是实测过的，见《06-更底层/07-链接脚本与启动代码.md》第 2.4 小节。

## 6.6 第四组：移位

`C`

```c
/* ub_shift.c   编译：gcc -std=c23 -O0 ub_shift.c -o ub_shift_O0.exe
 *              （同一份源码换 -O2 再编一次，结果见正文）
 * 移位量达到或超过类型宽度是 UB，负数移位量也是 UB。 */
#include <stdio.h>

int shl_var(int n)                   /* 1 << 32：移位量等于宽度 */
{
    return 1 << n;
}

int shl_const(void)                  /* 编译期就能看出来的那一种 */
{
    return 1 << 32;
}

int main(void)
{
    printf("1 << 32（常量）  = %d\n", shl_const());
    printf("1 << 32（变量）  = %d\n", shl_var(32));
    printf("1 << 31（变量）  = %d\n", shl_var(31));
    return 0;
}
```

`实测数据`

| 表达式 | `-O0` | `-O2` |
|---|---|---|
| `1 << 32`（编译期常量） | 0 | 0 |
| `1 << 32`（运行期变量） | **1** | **0** |
| `1 << 31`（运行期变量） | -2147483648 | -2147483648 |

第二行是这一组的重点：**同一个表达式，两档给出 1 与 0。**
`-O0` 把它编成一条 `shl`，x86 的移位指令只取移位量的低 5 位，`32 & 31 == 0`，
于是「移 32 位」变成了「不移」；`-O2` 知道移位量越界属于 UB，
于是按照「它不会发生」处理，结果取 0。

`实测数据`
`Text`

```text
ub_shift.c:12:14: warning: left shift count >= width of type [-Wshift-count-overflow]
   12 |     return 1 << 32;
      |              ^~
```

常量那一行编译器给了警告，两档都取 0；变量那一行没有任何提示，两档结果不同。
**同一类错误，编译期能看出来的会被警告，看不出来的就只剩一个静默的差异。**

`待确认`

另一套指令集的规则也不同：ARM 的 `lsl` 在移位量大于等于位宽时得到 0，
因此同一个 `1 << 32` 在 x86 与 Cortex-M 上本来就是两个结果。
这一条引自 ARM 的指令说明，本机没有在真板上测过移位越界，故标 `待确认`；
它说明的正是标准不肯规定移位越界的原因：**同一个表达式在两块板子上不是同一件事**。

## 6.7 第五组：严格别名

`C`

```c
/* ub_alias.c   编译：gcc -std=c23 -O0 ub_alias.c -o ub_alias_O0.exe
 *              （同一份源码换 -O2 再编一次，结果见正文） */
#include <stdio.h>

static int poke(int *a, short *b)     /* 两个参数都指向同一个 int 对象 */
{
    *a = 1;
    *b = 2;                          /* 用 short 的别名写进去 */
    return *a;                       /* 编译器认为 b 动不了 a */
}

int main(void)
{
    int x = 0;
    printf("poke(&x, (short *)&x) = %d\n", poke(&x, (short *)&x));
    return 0;
}
```

`实测数据`

| 编译 | 输出 |
|---|---|
| `gcc -std=c23 -O0` | **2** |
| `gcc -std=c23 -O2` | **1** |
| `gcc -std=c23 -O2 -fwrapv` | 1（这个开关管不了别名） |
| `cl /std:c17 /O2`（MSVC 19.44） | **2** |

`-O0` 的 2 是内存里真实的值：先写 `x = 1`，再用 `short` 把低 16 位写成 2，于是 `x == 2`。
`-O2` 认为「`short` 类型的指针改不到 `int` 类型的对象」，
所以 `*a = 1` 之后 `*a` 一直是 1，不会再去内存里读一次，于是返回 1。

**同一份代码在 MSVC 的 `/O2` 下得到 2。** 这不是 MSVC 更保守，
而是它默认不做这种基于类型的别名优化（`/O2` 下它的反汇编里有两次真实的访存）。
用数据检验一下这个说法：

`实测数据`
`Assembly`

```asm
; cl /std:c17 /O2 之后 dumpbin /disasm:nobytes 的片段
  0000000140001019: mov         dword ptr [rsp+30h],1      ; *a = 1
  0000000140001021: mov         word  ptr [rsp+30h],ax     ; *b = 2
  000000014000102D: mov         edx,dword ptr [rsp+30h]    ; 重新读回 a 指向的内存
```

> [!CAUTION]
> **换编译器以后结果变对，不代表代码是对的。** 这一段仍然是别名违规，
> 只是 MSVC 这一版没有利用它。GCC 侧的开关是 `-fno-strict-aliasing`，
> 打开之后别名不再被利用——代价是编译器少了一大类优化。
> 合法写法（`memcpy` 与联合体）见《06-更底层/04-字节序与数据表示.md》第 2 节。

## 6.8 不是 UB，但同样会被优化掉

有一类现象与 UB 长得极像，性质却完全不同：**程序里没有任何未定义的东西，
编译器只是被允许假定某块内存不会被它看不见的东西改动。** 真板上的这一组是典型。

在 STM32F103C8（Cortex-M3）最小系统板上做过这样一组实验：程序在 `while (g_flag == 0) { }` 里等一个标志，
标志由调试器直接写内存置起。两个版本只差 `volatile` 这一个关键字，都开 `-O2`。

`实测`

| 版本 | 调试器写入 `0x20000020 = 1` 之后 | 结束时的 PC |
|---|---|---|
| 带 `volatile` | 读到了，跳出循环（等了 7,472,238 周期，约 0.93 s） | `0x0800049e`（循环之后） |
| 去掉 `volatile` | 完全没反应，结果变量仍是 0 | `0x0800032c`（**卡在循环里**） |

`实测`
`Assembly`

```asm
; 带 volatile：每次都真的去读
ldr.w r3, [r2, #2056]      ; 读寄存器
lsls  r3, r3, #31
bpl.n -6                   ; 为 0 就跳回去再读     ← 正确的轮询

; 去掉 volatile：只读一次
ldr.w r3, [r3, #2056]
lsls  r2, r3, #31
bmi.n +4
b.n   .                    ; ← 跳到自身：死循环，永远不再读寄存器
```

**去掉 `volatile` 的版本里没有 UB，编译器完全合规。** 它看到的循环体不修改标志，
循环里也没有任何东西能改它，于是把读操作提到了循环外面——把 `b.n .` 编成
「跳到自身」正是这种推理的产物。两组现象都是「程序卡住」，
但判断办法只有一条：

| 问题 | 结论 |
|---|---|
| 标准有没有要求编译器重新读这块内存 | 有 → 少了 `volatile`，属于**语义错误**，加回去即可 |
| 程序里有没有越界、溢出、空指针解引用 | 有 → 属于 **UB**，加 `volatile` 也救不了 |
| 改内存的那一方对编译器可见吗 | 不可见（中断、DMA、调试器、别的线程）→ 同样需要 `volatile` 或原子量 |

`volatile` 阻止了哪些优化、内存映射 I/O 该怎么写，见
《06-更底层/03-寄存器、位与 volatile.md》第 2 节；中断与原子量的部分见
《06-更底层/10-中断、并发与内存序.md》第 3 节。

## 6.9 边界表与几个能收回来的开关

`实测数据`

| 写法 | 性质 | 编译器可以拿它做什么 |
|---|---|---|
| 有符号整数溢出 | UB | 认定不发生，据此化简判断与循环 |
| 越界访问（读或写） | UB | 认定不发生，删掉循环与数组 |
| 空指针解引用 | UB | 认定指针非空，删掉后面的判空 |
| 移位量 ≥ 类型宽度或为负 | UB | 参照平台指令或直接折叠成常量 |
| 通过不兼容类型的指针访问对象 | UB | 认定两个指针不重叠，缓存其中一个的值 |
| 解引用未初始化的指针 | UB | 同上（不确定值） |
| 除以零 | UB | 认定不发生；x86 上会触发异常，ARM 上得到 0 |
| 求值顺序未指定（如 `f(i++, i++)`） | 未指定 / UB | 结果随实现与优化等级变化 |
| 读未初始化的自动变量 | 不确定值 | 可能读到寄存器里的旧值 |
| 无符号整数溢出 | **完全合法** | 按 2 的幂回绕，可以放心依赖 |
| 有符号右移负数 | 实现定义 | 算术右移（主流实现） |
| 指针与整数互转 | 实现定义 | 平台相关，嵌入式里常用 |
| 结构体的填充字节 | 不确定值 | 不要用 `memcmp` 比较含填充的结构体 |

把行为收回来的开关都集中在编译选项上，GCC 侧常用的是这四个：

`实测数据`

| 开关 | 作用 | 实测影响 |
|---|---|---|
| `-fwrapv` | 有符号溢出按补码回绕 | 6.3 小节三个答案从 1 回到 0 |
| `-fno-strict-aliasing` | 关掉基于类型的别名优化 | 6.7 小节从 1 回到 2 |
| `-fno-delete-null-pointer-checks` | 保留判空 | 6.5 小节里那行判空留下来 |
| `-ffast-math` | 反过来：**增加**假设，认定没有 NaN 与无穷 | 下一个小节 |

最后一个不属于「收回来」，它是「再交出去一点」，代价往往最大：

`C`

```c
/* fastmath.c   编译：gcc -std=c23 -O2 -ffast-math fastmath.c -o fastmath.exe
 *               对照：去掉 -ffast-math 再编一次 */
#include <stdio.h>
#include <math.h>

int main(void)
{
    double x = NAN;

    if (x != x)                    /* 判断是不是 NaN 的常用写法 */
        puts("x != x：是 NaN");
    else
        puts("x != x：不是 NaN");

    printf("isnan(x) = %d\n", isnan(x) != 0);
    return 0;
}
```

`实测数据`

| 编译 | `x != x` 的判断 | `isnan(x)` |
|---|---|---|
| `-O0` / `-O2` | 是 NaN | 1 |
| `-O2 -ffast-math` | **不是 NaN** | **1** |
| `-O2 -ffinite-math-only` | **不是 NaN** | **1** |

**同一个程序里两种写法给出了互相矛盾的两句话**：`-ffast-math` 认定「不会出现 NaN」，
于是把 `x != x` 折叠成假，而 `isnan` 是内建函数，仍然如实回答 1。
浮点代码里任何依赖 NaN、无穷、`-0.0` 的判断，在打开这个开关之后都要重新审一遍。

# 第 7 节 `-fsanitize` 家族

UB 的共同特征是「编译器不报错、程序有时看着还对」，因此排查手段只能是运行时检查。
GCC 与 Clang 把这类检查做成了编译开关：插桩代码在运行时盯着每一次访存、每一条算术指令。

## 7.1 先看清在哪台机器上能用

MinGW 只带编译器，不带这两套运行库，GCC 会在链接阶段直接说找不到：

`实测数据`
`Text`

```text
$ gcc -std=c23 -g -fsanitize=address san_heap.c -o san_heap.exe
<MinGW>/.../ld.exe: cannot find -lasan: No such file or directory
collect2.exe: error: ld returned 1 exit status

$ gcc -std=c23 -g -fsanitize=undefined san_ubsan.c -o san_ubsan.exe
<MinGW>/.../ld.exe: cannot find -lubsan: No such file or directory
collect2.exe: error: ld returned 1 exit status
```

**报错发生在链接，不在编译**：语法检查全过了，插桩代码也生成了，只是配不上运行库。
本机因此把这一节的实验放在 WSL 的 Ubuntu 里做，`libasan` 与 `libubsan` 随 gcc 一起安装。
两个环境的语言开关有一个差别要注意：

`实测数据`

| 环境 | 编译器 | 标准开关 |
|---|---|---|
| Windows（`<MinGW>`） | gcc 15.2.0 | `-std=c23` |
| WSL Ubuntu 24.04 | gcc 13.3.0 | `-std=c2x`（这一版还不认 `c23` 这个拼写） |

## 7.2 ASan 抓到的四类

地址检查器（AddressSanitizer，`-fsanitize=address`）在每次访存前后插桩，
并给每一块分配的内存加上「红区」。它最擅长的是**地址层面的越界与生存期错误**。

`C`

```c
/* san_heap.c   编译运行（Linux）：gcc -std=c2x -g -fsanitize=address san_heap.c -o san_heap && ./san_heap */
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *p = malloc(4 * sizeof *p);
    for (int i = 0; i < 4; i++)
        p[i] = i;
    printf("p[4] = %d\n", p[4]);      /* 堆越界读，读的是紧邻块的元数据区 */
    free(p);
    return 0;
}
```

`实测数据`
`Text`

```text
==1084==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x502000000020
READ of size 4 at 0x502000000020 thread T0
    #0 0x563c44e7b305 in main /mnt/k/.../san_heap.c:10
0x502000000020 is located 0 bytes after 16-byte region [0x502000000010,0x502000000020)
allocated by thread T0 here:
    #0 0x7f41e03d89c7 in malloc
    #1 0x563c44e7b25e in main /mnt/k/.../san_heap.c:7
SUMMARY: AddressSanitizer: heap-buffer-overflow /mnt/k/.../san_heap.c:10 in main
```

**报告里有三件事是 gdb 给不了的**：错误的类别（`heap-buffer-overflow`）、
越界的精确位置（距 16 字节块末尾 0 字节）、以及这块内存是谁分配的（同一文件第 7 行）。
同一套插桩还能抓到另外三类：

`实测数据`
`Text`

```text
# 释放后使用
==1092==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000010
READ of size 4 at 0x502000000010 thread T0
    #0 0x55b88fbb12e6 in main /mnt/k/.../san_uaf.c:10
freed by thread T0 here:
    #1 0x55b88fbb12af in main /mnt/k/.../san_uaf.c:9

# 内存泄漏（退出时由 LeakSanitizer 报告）
==1101==ERROR: LeakSanitizer: detected memory leaks
Direct leak of 1024 byte(s) in 1 object(s) allocated from:
    #1 0x55d1c3ca219e in main /mnt/k/.../san_leak.c:6

# 栈越界（报告里直接给出变量的字节范围）
==1110==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7f86d5800030
  This frame has 1 object(s):
    [32, 48) 'a' (line 6) <== Memory access at offset 48 overflows this variable
```

注意最后一份里的 `[32, 48) 'a'`：ASan 不仅说越界，还说越的是哪个变量、它的字节范围是多少。
**第 6.4 小节那个「-O0 得 101、-O2 得 100」的例子，在这里会直接变成一条错误报告。**

## 7.3 UBSan 抓到的四类

未定义行为检查器（UndefinedBehaviorSanitizer，`-fsanitize=undefined`）盯的是运算本身：
整数溢出、移位越界、空指针解引用、数组下标越界。

`C`

```c
/* san_ubsan.c   编译运行（Linux）：gcc -std=c2x -g -fsanitize=undefined san_ubsan.c -o san_ubsan && ./san_ubsan */
#include <stdio.h>
#include <limits.h>

int neg_abs(int x) { if (x < 0) x = -x; return x; }
int shl(int n)     { return 1 << n; }

int main(void)
{
    printf("neg_abs(INT_MIN) = %d\n", neg_abs(INT_MIN));   /* 取负溢出 */
    printf("shl(32)          = %d\n", shl(32));            /* 移位量越界 */
    return 0;
}
```

`实测数据`
`Text`

```text
san_ubsan.c:5:35: runtime error: negation of -2147483648 cannot be represented in type 'int';
    cast to an unsigned type to negate this value to itself
san_ubsan.c:6:31: runtime error: shift exponent 32 is too large for 32-bit type 'int'
neg_abs(INT_MIN) = -2147483648
shl(32)          = 1
```

**UBSan 默认只报告，不终止程序**：退出码是 0，两行结果照常算出来。
报告里的行号直接指到出错的那次运算，连是哪一种 UB 都写清了。

`实测数据`
`Text`

```text
# 空指针解引用（-fsanitize=null）：报告之后程序仍然崩，退出码 139（SIGSEGV）
san_null.c:6:9: runtime error: load of null pointer of type 'int'

# 数组下标越界（结构体内部的数组，边界在编译期已知）
san_intraobj.c:18:12: runtime error: index 4 out of bounds for type 'int [4]'
```

**`-fsanitize=null` 这一条尤其有用**：第 6.5 小节里那行被删掉的判空，
在开了插桩之后会带着行号报出来，不需要再从汇编去推。

## 7.4 两者一起上

`-fsanitize=address,undefined` 可以同时打开，这是开发期的推荐配置。
如果希望「报出来就停」，再加一个开关：

`实测数据`
`Text`

```text
$ gcc -std=c2x -g -fsanitize=undefined san_ubsan.c -o san_ubsan && ./san_ubsan; echo $?
... 两行 runtime error ...
0                          ← 默认：只报告

$ gcc -std=c2x -g -fsanitize=undefined -fno-sanitize-recover=all san_ubsan.c -o san_ubsan_stop
$ ./san_ubsan_stop; echo $?
1                          ← 报出来就终止
```

## 7.5 抓不到的那几类

插桩能看到的只有它被教过要看的东西。下面是实测过的盲区。

`实测数据`

| 错误 | ASan 单独 | UBSan 单独 | 说明 |
|---|---|---|---|
| 堆越界、栈越界、释放后使用、泄漏 | **报** | 不报 | 地址层面的事归 ASan |
| 有符号溢出、移位越界、空指针解引用 | 不报 | **报** | 运算层面的事归 UBSan |
| **结构体内部的越界** | **沉默** | 报（`index 4 out of bounds`） | 地址仍在同一个分配块里，ASan 的红区在块外 |
| **严格别名违规** | 沉默 | 沉默 | 两种插桩都不管别名 |
| **`__builtin_unreachable` 用错** | 沉默 | 沉默 | 它是给编译器的断言，不是运行时检查 |
| **未初始化读** | 沉默 | 沉默 | 要 MemorySanitizer，目前只有 Clang 有 |
| **数据竞争** | 沉默 | 沉默 | 要 `-fsanitize=thread`，而且与 ASan 不能同时开 |

结构体内部越界这一行的两头都验过。ASan 单独打开时，程序安静地跑完：
`last = -1`、退出码 0——越界写已经把 `last` 从 999 改成了 -1，
而地址始终落在同一个 `malloc` 块里，红区碰不到。加上 UBSan 之后才有那一行
`index 4 out of bounds for type 'int [4]'`。

别名违规那一行更彻底：

`实测数据`
`Text`

```text
$ gcc -std=c2x -O2 san_blind.c -o blind_plain && ./blind_plain
poke = 1                    ← 优化把第二次读消掉了

$ gcc -std=c2x -O2 -g -fsanitize=address,undefined san_blind.c -o blind_san && ./blind_san
poke = 1                    ← 插桩没有改变结论，也没有一句报告

$ gcc -std=c2x -O0 san_blind.c -o blind_O0 && ./blind_O0
poke = 2                    ← 只有关掉优化才是内存里的真值
```

**三种构建，两种答案，零条报告。** 遇到结果对不上又找不到越界与溢出时，
别名与 `__builtin_unreachable` 这两个方向要手工查。

数据竞争那一条在真板上有更直观的对照（同一块 STM32F103C8，主循环自增 20 万次，
同时 SysTick 每 1000 周期中断一次并在中断里自增同一个计数器）：

`实测`

| 版本 | 期望值 | 实测值 |
|---|---|---|
| 普通 `volatile` 计数器 | 201459 | **200000**（丢了 1459 次更新） |
| `__atomic_fetch_add`（`seq_cst`） | 202702 | **202702**（一次没丢） |

数据竞争不在 ASan 与 UBSan 的检查范围内（第 7.5 小节的盲区表里有一行），
要查它得换 `-fsanitize=thread`（WSL 里有 `libtsan`，实测能报出
`WARNING: ThreadSanitizer: data race`），或者按《06-更底层/10-中断、并发与内存序.md》第 3.2 小节的办法做临界区。

## 7.6 代价

插桩不是免费的。同一份「50 万轮分配、写入、读取、释放」的负载，在 WSL 里各跑三轮：

`实测数据`

| 构建 | 三次耗时 | 倍数 |
|---|---|---|
| `-O2` | 0.04 / 0.06 / 0.05 s | 1 |
| `-O2 -fsanitize=undefined` | 0.12 / 0.09 s | 约 2 |
| `-O2 -fsanitize=address` | 0.88 / 0.97 / 0.94 s | 约 18 |
| `-O2 -fsanitize=address,undefined` | 0.99 / 0.97 / 1.01 s | 约 20 |

体积的代价小一些，但方向一致：

`实测数据`

| 构建 | 文件大小 | `.text` |
|---|---|---|
| `-O2` | 16056 字节 | 1804 |
| `-O2 -fsanitize=undefined` | 16472 字节 | 2683 |
| `-O2 -fsanitize=address` | 25224 字节 | 2814 |
| `-O2 -fsanitize=address,undefined` | 26600 字节 | 4722 |

**ASan 慢在内存访问，UBSan 慢在算术密集处**，两者一起开大约是两者之和。
结论也很直接：**不要带着 sanitizer 发布**，把它当成测试期与调试期的必备配置。

# 第 8 节 速查表

`实测数据`

| 常用件 | 一句话用途 | 典型坑 |
|---|---|---|
| `__attribute__((aligned(n)))` | 强制对齐 | MSVC 上要写 `__declspec(align(n))`，写法不通用 |
| `__attribute__((packed))` | 紧凑布局 | 改 ABI；成员非对齐，Cortex-M3 上逐字节访问 8 → 18 周期 |
| `__declspec(align(n))` | MSVC 的强制对齐 | GCC 收下这个拼写却**忽略** `align`，只给一句警告 |
| `__attribute__((noreturn))` | 声明不返回 | 属性写错时调用点会多出无用的收尾代码 |
| `__attribute__((used))` | 挡住编译器的丢弃 | 挡不住链接器的 `--gc-sections`，那要靠 `KEEP` |
| `__attribute__((weak))` | 可被覆盖的默认实现 | MSVC 没有对应属性，隔离层盖不住 |
| `#pragma once` | 头文件只包含一次 | 事实标准，仍未进标准；符号链接的同一文件会被当成两份 |
| `#pragma pack(push,1)` / `pack(pop)` | 改局部布局 | 少写 `pop` 会污染后面所有结构体，包括系统头文件 |
| `#pragma GCC diagnostic push/ignored/pop` | 局部关警告 | 函数结束时才发出的警告不受压制（`-Wunused-variable`） |
| `#pragma warning(disable:4018)` | MSVC 的同一件事 | 用 `__pragma` 才能放进宏 |
| `_Pragma("...")` | 把杂注写进宏 | `#pragma` 不能由宏展开产生，只能用它 |
| `__builtin_expect(e, c)` | 分支概率提示 | 编译器本来就猜得准的地方完全没有效果 |
| `__builtin_unreachable()` | 断言控制流到不了 | 违反时无任何检查；实测两次运行分别落在 `0xC0000005` 与 28887 行重复输出上 |
| `unreachable()` | 上面那条的标准写法（C23） | 在 `<stddef.h>` 里，用法与内建函数一致 |
| `__builtin_add_overflow` | 加法与溢出标志一起给 | 手写判断必然要先做一次已经 UB 的加法 |
| `-fwrapv` | 有符号溢出按补码回绕 | 失去依赖「不会溢出」的那部分优化 |
| `-fno-strict-aliasing` | 关掉别名优化 | 6.7 小节的结果从 1 回到 2 |
| `-fno-delete-null-pointer-checks` | 保留判空推理 | 裸机上地址 0 合法时的必备开关 |
| `-ffast-math` | 增加假设，认定无 NaN | 同一个程序里 `x != x` 与 `isnan(x)` 给出矛盾答案 |
| `-Waggressive-loop-optimizations` | 提示循环里那一轮是 UB | 只在优化打开时出现，关掉它等于放弃提示 |
| `-fsanitize=address` | 抓越界、释放后使用、泄漏 | MinGW 上没有 `libasan`，要在 Linux 侧跑 |
| `-fsanitize=undefined` | 抓溢出、移位、空指针、下标 | 默认只报告不终止，要停止得加 `-fno-sanitize-recover=all` |
| `-fsanitize=thread` | 抓数据竞争 | 与 ASan 不能同时开 |
| `-fsanitize=address,undefined` | 开发期推荐配置 | 约 20 倍时间代价，不要带进发布版 |
| `_MSC_VER` / `__GNUC__` / `__clang__` | 三条分支的判据 | `__clang__` 必须排在 `__GNUC__` 前面判 |
