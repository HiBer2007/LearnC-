编译器把源码变成目标文件时，每一个名字都会在文件里留下一条记录：名字本身、它落在哪个段、
从段首算起偏移多少、它是本文件自己定义的还是需要别人提供。**链接器只看这些记录，不看源码。**
两段代码在语言层面长得一模一样，到了链接器那里可能一个是「我提供」、一个是「我需要」，
也可能一个别人看得见、一个别人看不见。链接期报出来的错几乎全部来自这条记录与预期不符。

语言层面的链接属性在《04-语法/11-作用域、生存期与链接.md》第 4.1 小节已经讲清楚了，
`static`、匿名命名空间、`const` 全局变量各自产生哪种链接也各有定论。
到了链接器这一侧，要回答的是另一批问题：一条记录长什么样、`nm` 的输出怎么读、两个翻译单元撞名时谁报错、
`__attribute__((weak))` 为什么能让芯片的向量表既能开箱可用又能被你替换、
一个静态库的成员什么时候会进可执行文件、一个动态库为什么必须把函数写进导出表。

这些机制在单片机上不是纸面知识。`A-教学素材/01-编译器/嵌入式/链接脚本与启动/startup_stm32f103xe.s`
里那张几百行的向量表，靠的就是弱符号：每个中断处理函数都有一个弱定义指向死循环，
你写了同名函数就覆盖它，没写就进死循环。弱定义生效与强定义覆盖这两种结果，
都能在 QEMU 里复现。

# 第 1 节 链接器眼里的符号

**源码里的名字到了目标文件里叫符号。** 一条符号记录至少包含四件事：
名字、它属于哪个段、段内偏移、以及它的绑定强度。

`T` `t` `D` `d` `B` `b` `R` `r` `U` `W` `w` 这些字母就是绑定强度与所属段的合并写法。

## 1.1 一条符号记录由什么组成

`nm` 是查看这张表最直接的工具。把下面这份程序编成目标文件，再读符号表。

`C`

```c
/* nm_marks.c   编译运行：gcc -std=c23 nm_marks.c -o nm_marks */
#include <stdio.h>

int          g_ext   = 1;      /* 外部链接：别的翻译单元也能用 */
static int   g_int   = 2;      /* 内部链接：只在本翻译单元可见 */
const int    g_cst   = 3;      /* C 里文件作用域 const 仍是外部链接 */
static const int g_icst = 4;   /* 加了 static 才是内部链接 */

int          f_ext(void) { return g_ext; }     /* 外部链接 */
static int   f_int(void) { return g_int; }     /* 内部链接 */

int main(void)
{
    printf("%d %d %d %d %d\n", f_ext(), f_int(), g_cst, g_icst, g_ext);
    return 0;
}
```

`Bash`

```bash
gcc -std=c23 -O0 -c nm_marks.c -o nm_marks.o
nm nm_marks.o
```

`实测数据`
`Text`

```text
0000000000000000 b .bss
0000000000000000 d .data
0000000000000000 p .pdata
0000000000000000 r .rdata
0000000000000000 r .rdata$zzz
0000000000000000 t .text
0000000000000000 r .xdata
                 U __main
                 U __mingw_printf
0000000000000000 T f_ext
000000000000000c t f_int
0000000000000000 R g_cst
0000000000000000 D g_ext
0000000000000004 r g_icst
0000000000000004 d g_int
0000000000000018 T main
```

前七行的名字就是段名本身，是 PE 目标文件为每个段列出的符号，
读符号表时可以整批滤掉；`U __mingw_printf` 是 MinGW 的 `printf` 实现，
源码里的 `printf` 被换成了它。真正对应源码的是后面九行。

**这份程序的运行结果：**

`实测数据`
`Text`

```text
1 2 3 4 1
```

这一列字母的含义是固定的，左边大写表示**外部链接**，小写表示**内部链接**。

`实测数据`

| 字母 | 含义 | 出现在哪个段 |
|---|---|---|
| `T` / `t` | 代码，函数 | `.text` |
| `D` / `d` | 有初值的可写数据 | `.data` |
| `B` / `b` | 无初值的可写数据 | `.bss` |
| `R` / `r` | 只读数据，含常量与字符串 | `.rdata`（ELF 上叫 `.rodata`） |
| `U` | 本文件**没定义**、需要别人提供 | —— |
| `W` / `w` | 弱符号（第 4 节） | —— |
| `A` | 绝对值，不落在任何段里（链接脚本里算出来的地址常是这种） | —— |

> [!IMPORTANT]
> **大写与小写的区别只有一件事：别的翻译单元能不能用这个名字。**
> 段名（`T` 与 `D` 的差别）说的是它放在哪个段里，与可见性无关。
> 链接器做符号解析时，真正关心的只有「谁提供」与「谁需要」。

`U __main` 这一行值得单独说一句。它是 MinGW 上的固定产物：
`main` 的代码里被插进了一次对 `__main` 的调用，用来在进入 `main` 之前跑全局对象的构造函数。
它的定义在 CRT 里，见《06-更底层/08-CRT 与程序启动.md》第 2 节。

## 1.2 未定义符号：链接的驱动力

`U` 那一行是链接器工作的理由。它表示「这个名字我用到了，但我这里没有」。
链接器的任务就是给每一条 `U` 找到一个定义，找到就把两边的地址对上，找不到就报错。

引用侧的样子很直白。

`C`

```c
/* nm_ref.c   只编译：gcc -std=c23 -c nm_ref.c -o nm_ref.o */
extern int g_ext;                 /* 声明：我不定义，只使用 */
int touch_ext(void) { return g_ext; }
```

`实测数据`
`Bash`

```bash
gcc -std=c23 -O0 -c nm_ref.c -o nm_ref.o
nm nm_ref.o
```

`实测数据`
`Text`

```text
0000000000000000 b .bss
0000000000000000 d .data
0000000000000000 p .pdata
0000000000000000 r .rdata$.refptr.g_ext
0000000000000000 r .rdata$zzz
0000000000000000 R .refptr.g_ext
0000000000000000 t .text
0000000000000000 r .xdata
                 U g_ext
0000000000000000 T touch_ext
```

**`extern` 这个关键字在目标文件里不留痕迹**，它只是让编译器相信这个名字存在，
于是生成一条 `U` 记录加一次取地址。链接期才有人管它对不对。

`.refptr.g_ext` 是 PE 目标特有的产物：64 位 Windows 上的数据寻址要走
一层指针表（伪重定位），因此多出一个指向 `g_ext` 的引用项。
ELF 目标上不会出现它。

> [!TIP]
> **判断一个链接错误属于哪一类，先看符号在不在。**
> `ld` 说 `undefined reference to 'xxx'`，说明没有任何目标文件提供 `xxx`；
> 说 `multiple definition of 'xxx'`，说明提供了不止一份。
> 两种错的查法完全不同：前者查「该链的库链了没有」，后者查「定义写在了哪个文件里」。

## 1.3 符号表在可执行文件里也留着

链接完成之后符号表通常并没有消失，只是大部分条目的地址已经是最终地址。
这既是调试器能按名字下断点的原因，也是发布前要 `strip` 的原因。

`Bash`

```bash
gcc -std=c23 -O0 nm_marks.c -o nm_marks.exe
nm nm_marks.exe | grep -E " g_ext| f_ext| g_int| g_cst| f_int"
```

`实测数据`
`Text`

```text
0000000140001440 T f_ext
000000014000144c t f_int
000000014000a000 R g_cst
0000000140009000 D g_ext
0000000140009004 d g_int
```

**内部链接的符号在可执行文件里同样保留**，小写字母照旧，只是它不会参与跨文件的解析。
`strip` 之后这些名字都会消失，见《03-构建工具链/04-符号与调试信息.md》第 10 节。

# 第 2 节 内部链接与外部链接

**内部链接的意思是：这个名字只对本翻译单元有效。** 别的翻译单元写同名符号，
两份互不干涉，链接器也不会认为它们冲突。外部链接则相反，全程序共享一个名字，
多写一份就是第 3 节的重复定义。

## 2.1 内外部链接在链接期的两种后果

把同一份 `static` 定义复制到两个翻译单元里，程序照样能链接；
去掉 `static`，立刻报重复定义。

`C`

```c
/* two_static_a.c   编译（只编这一份）：gcc -std=c23 -c two_static_a.c -o two_static_a.o */
#include <stdio.h>
static int counter = 10;              /* 内部链接：与 b 里的同名变量无关 */
int a_next(void) { return ++counter; }
```

`C`

```c
/* two_static_b.c   编译（只编这一份）：gcc -std=c23 -c two_static_b.c -o two_static_b.o */
#include <stdio.h>
static int counter = 20;              /* 同样的名字，互不干涉 */
int b_next(void) { return ++counter; }
```

`C`

```c
/* two_static_main.c   编译（只编这一份）：gcc -std=c23 -c two_static_main.c -o two_static_main.o */
#include <stdio.h>
int a_next(void);
int b_next(void);
int main(void)
{
    int x = a_next();          /* 分成三条语句：求值顺序就是书写顺序 */
    int y = b_next();
    int z = a_next();
    printf("%d %d %d\n", x, y, z);
    return 0;
}
```

`实测数据`
`Bash`

```bash
gcc -std=c23 two_static_main.c two_static_a.c two_static_b.c -o two_static.exe
./two_static.exe
```

`实测数据`
`Text`

```text
11 21 12
```

**两个 `counter` 各自独立计数。** 如果把它们前面的 `static` 去掉，
链接时会直接报第 3 节那种重复定义，因为两个外部链接的 `counter` 撞在同一个名字上。

把三个调用写进同一行还有一处可以观察：`printf("%d %d %d\n", a_next(), b_next(), a_next())`
在本机输出 `12 21 11`，与上一段的结果不同。
C 与 C++ 都不保证函数参数的求值顺序，见《04-语法/04-表达式与运算符.md》第 4.1 小节。
拆成分条语句之后结果就是确定的，这也是本节例子的写法。

`实测数据`
`Text`

```text
12 21 11
```

## 2.2 C++ 额外的两种内部链接

C++ 除了 `static`，还多两种产生内部链接的写法：命名空间作用域的 `const` 变量与匿名命名空间。
它们编出来的名字带修饰，符号表里一眼能认出来。

`C++`

```cpp
/* cpp_linkage.cpp   编译运行：g++ -std=c++17 cpp_linkage.cpp -o cpp_linkage */
#include <cstdio>

const int kCppConst = 3;          /* C++：命名空间作用域的 const 是内部链接 */
namespace {
    int anon_var = 5;             /* 匿名命名空间：内部链接 */
    int anon_fn() { return anon_var; }
}
int cpp_ext(void) { return kCppConst + anon_fn(); }

int main() { std::printf("%d\n", cpp_ext()); return 0; }
```

`实测数据`
`Bash`

```bash
g++ -std=c++17 -O0 -c cpp_linkage.cpp -o cpp_linkage.o
nm cpp_linkage.o
```

`实测数据`
`Text`

```text
                 U __main
000000000000000c T _Z7cpp_extv
0000000000000000 r _ZL9kCppConst
0000000000000000 t _ZN12_GLOBAL__N_1L7anon_fnEv
0000000000000000 d _ZN12_GLOBAL__N_1L8anon_varE
0000000000000022 T main
```

三个名字都是小写，都进不了别的翻译单元。匿名命名空间在修饰名里留下 `_GLOBAL__N_1`，
`L` 是「local」的标记。**C 与 C++ 在这里有一处真实分歧**：
C 里文件作用域的 `const int` 是外部链接（`R`），C++ 里是内部链接（`r`）。
上一节的 `nm_marks.o` 与这一节的 `cpp_linkage.o` 正好是一对对照，
机制见《04-语法/11-作用域、生存期与链接.md》第 5.1 小节。

> [!WARNING]
> **头文件里写 `const int kMax = 10;` 在 C 与 C++ 里后果不同。**
> C 里它是定义，被多个 `.c` 包含就会重复定义；
> C++ 里它是内部链接，每个翻译单元各有一份，能编过但会让每个单元都存一份副本。
> 两门语言里更稳的写法都是 `static const`（内部链接，语义明确）或 C++17 起的 `inline constexpr`。

## 2.3 内部链接挡不住的东西

内部链接只影响链接器怎么解析名字，不影响名字在运行期是否存在。
它做不到三件事：不能让符号在调试器里消失、不能省下空间（每个单元一份副本）、
也不能阻止别人把同样的逻辑再写一遍。

**它真正的作用是「把实现藏起来」**：改了这份 `static` 函数的实现，
别的目标文件不需要重新编译，因为它们从来没引用过这个名字。
这在大工程里是有价值的：头文件里少一个函数声明，依赖关系就少一条。

# 第 3 节 重复定义：链接期报错原文

**两个翻译单元各自定义了一个外部链接的同名变量或函数，链接器只能报错**，
因为它无法判断你想用哪一个。这是链接期最常见的错误之一，两种工具链的措辞不同。

## 3.1 GCC 路线：`multiple definition`

先给出这一组的完整构建命令，再分别看两个翻译单元。

`Bash`

```bash
gcc -std=c23 -c dup_a.c -o dup_a.o
gcc -std=c23 -c dup_b.c -o dup_b.o
gcc -std=c23 dup_main.c dup_a.o dup_b.o -o dup.exe      # 失败
```

`C`

```c
/* dup_a.c   编译（只编这一份）：gcc -std=c23 -c dup_a.c -o dup_a.o */
int g_dup = 1;
int a_side(void) { return g_dup; }
```

`C`

```c
/* dup_b.c   编译（只编这一份）：gcc -std=c23 -c dup_b.c -o dup_b.o */
int g_dup = 2;                    /* 与 dup_a.c 里的 g_dup 同名同类型 */
int b_side(void) { return g_dup; }
```

`C`

```c
/* dup_main.c   编译（只编这一份）：gcc -std=c23 -c dup_main.c -o dup_main.o */
#include <stdio.h>
int a_side(void);
int b_side(void);
int main(void) { printf("%d %d\n", a_side(), b_side()); return 0; }
```

`实测数据`
`Text`

```text
<MinGW>/.../ld.exe: dup_b.o:dup_b.c:(.data+0x0): multiple definition of `g_dup';
                  dup_a.o:dup_a.c:(.data+0x0): first defined here
collect2.exe: error: ld returned 1 exit status
```

**报错里带了两条信息**：冲突的名字 `g_dup`，以及两个定义各自的来源文件与段内偏移。
`(.data+0x0)` 说明它落在 `.data` 段的开头。措辞是「先在这里定义过」，
因此修的时候要删掉其中一份，或者在两份里都加上 `static`。

## 3.2 MSVC 路线：`LNK2005` 与 `LNK1169`

同一份代码交给 `cl.exe`，报错换成了错误码。

`Batch`

```bat
cl /nologo /std:c17 /utf-8 /c dup_a.c /Fo:dup_a_msvc.obj
cl /nologo /std:c17 /utf-8 /c dup_b.c /Fo:dup_b_msvc.obj
cl /nologo /std:c17 /utf-8 dup_main.c dup_a_msvc.obj dup_b_msvc.obj /Fe:dup_msvc.exe
```

`实测数据`
`Text`

```text
dup_b_msvc.obj : error LNK2005: g_dup 已经在 dup_a_msvc.obj 中定义
dup_msvc.exe : fatal error LNK1169: 找到一个或多个多重定义的符号
```

**`LNK2005` 是「符号重复定义」，`LNK1169` 是它的收尾。**
本机装的是中文版 VS，因此措辞是中文；错误码与英文版一致
（英文版的 `LNK2005` 措辞是 `already defined in ...`）。两套 `cl.exe` 都会报这两个码。

> [!TIP]
> **同一个名字在 C++ 里是否冲突，要看修饰后的名字。**
> `int f(int)` 与 `double f(double)` 是两个不同的符号，不算重复定义；
> 而 `int f(int)` 写在两个 `.cpp` 里就是重复定义，报错会带上修饰名而不是源码里的 `f`。
> 修饰规则见《06-更底层/05-ABI 与调用约定.md》第 5.1 小节。

## 3.3 一个来源最隐蔽的重复定义

C 与 C++ 里有一类重复定义不是手写的，而是头文件带来的：
在头文件里写函数的**定义**（不是声明），然后被多个 `.c` 包含。

`C`

```c
/* dup_header.h   被两个翻译单元包含的头文件（下面是节选） */
int helper(void) { return 42; }      /* 这不是声明，是定义 */
```

**每个包含它的翻译单元都会得到一个外部链接的 `helper`**，链接期就是 `multiple definition`。
正确写法是头文件里只留声明，定义放进一个 `.c` 文件；或者两门语言里都加 `static`
（变成内部链接，代价是每个单元一份副本）。

排查办法是去符号表里找同名条目，把每个目标文件的全局定义并排列出来。

`实测数据`
`Bash`

```bash
gcc -std=c23 -c dup_a.c -o dup_a.o
gcc -std=c23 -c dup_b.c -o dup_b.o
for f in dup_a.o dup_b.o; do echo "== $f"; nm "$f" | grep " T \| D \| B "; done
```

`实测数据`
`Text`

```text
== dup_a.o
0000000000000000 T a_side
0000000000000000 D g_dup
== dup_b.o
0000000000000000 T b_side
0000000000000000 D g_dup
```

**`g_dup` 在两个文件里都以 `D` 出现**，重复定义就在这里。
如果它是内部链接，字母会是小写的 `d`，两份也就不冲突了。

# 第 4 节 弱符号

**强符号只能有一个，弱符号可以有多个，而且强符号优先。**
这条规则解决了一个非常实际的工程问题：库想提供一个默认实现，同时允许用户替换它。

## 4.1 真启动文件里的弱符号

`A-教学素材/01-编译器/嵌入式/链接脚本与启动/startup_stm32f103xe.s` 是 STM32CubeMX 生成的真实启动文件。
它有 470 行，其中 200 多行在做同一件事：为每个中断处理函数提供一个指向 `Default_Handler` 的弱别名。
下面第一段是第 106 至 118 行（下面是节选）。

`Assembly`

```asm
/**
 * @brief  This is the code that gets called when the processor receives an
 *         unexpected interrupt.  This simply enters an infinite loop, preserving
 *         the system state for examination by a debugger.
 *
 * @param  None
 * @retval : None
*/
    .section .text.Default_Handler,"ax",%progbits
Default_Handler:
Infinite_Loop:
  b Infinite_Loop
  .size Default_Handler, .-Default_Handler
```

上面这段是第 106 至 118 行：**默认处理函数就是一个死循环**，芯片进了未处理的中断就停在这里，
现场保持不动，方便调试器接上去看。

下面这段是第 264 至 266 行与第 288 至 289 行（下面是节选），每个中断函数都是三行。

`Assembly`

```asm
  .weak NMI_Handler
  .thumb_set NMI_Handler,Default_Handler
  ...
  .weak SysTick_Handler
  .thumb_set SysTick_Handler,Default_Handler
```

**`.weak` 声明这个名字是弱符号，`.thumb_set` 让这个名字等于 `Default_Handler` 的地址。**
于是链接器看到的是：`SVC_Handler` 有一个弱定义（地址与 `Default_Handler` 相同），
如果程序里另外有一个强定义，就用强的那个。

`实测数据`
`Bash`

```bash
# 只汇编启动文件，看它给出的弱别名（不涉及任何用户代码）
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -c startup_stm32f103xe.s -o startup_only.o
arm-none-eabi-nm startup_only.o | grep -E " (SVC_Handler|SysTick_Handler|Default_Handler)$"
```

`实测数据`
`Text`

```text
00000000 T Default_Handler
00000000 W SVC_Handler
00000000 W SysTick_Handler
```

**所有弱别名与 `Default_Handler` 落在同一个偏移上**，这就是弱别名在符号表里的样子。
真正链接成可执行文件时，这些地址会被重定位到 flash 里的实际位置。

`实测数据`
`Bash`

```bash
# 链接之后再看一次地址（weak_main.c 的源码见下一小节）
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -nostartfiles --specs=nosys.specs \
  -T STM32F103XX_FLASH.ld startup_stm32f103xe.s weak_main.c -o no_user.elf
arm-none-eabi-nm no_user.elf | grep -E " (SVC_Handler|Default_Handler)$"
```

`实测数据`
`Text`

```text
080002e4 T Default_Handler
080002e4 W SVC_Handler
```

**`W` 与 `T` 仍然落在同一个地址上。**

## 4.2 覆盖实验：同一个程序，两个版本

`sh.h` 是 Cortex-M 侧的输出通道，走 semihosting（`bkpt 0xAB` + `SYS_WRITE0`），
在主机上退化成 `fputs`，因此同一份源码两边都能编。
这个头必须写在用到它的程序之前。

`C`

```c
/* sh.h   Cortex-M 侧的 semihosting 输出；主机上退化为 stdout */
#ifndef SH_H
#define SH_H

#include <stdint.h>

#if defined(__arm__)
static void sh_puts(const char *s)
{
    __asm__ volatile ("mov r1, %0\n\t"
                      "movs r0, #4\n\t"    /* 0x04 = SYS_WRITE0 */
                      "bkpt 0xAB"
                      : : "r"(s) : "r0", "r1", "memory");
}
#else
#include <stdio.h>
static void sh_puts(const char *s) { fputs(s, stdout); }
#endif

#endif
```

`Bash`

```bash
# 变体 A：不提供 SVC_Handler；变体 B：提供自己的
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -nostartfiles --specs=nosys.specs \
  -T STM32F103XX_FLASH.ld startup_stm32f103xe.s weak_main.c -o no_user.elf
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -nostartfiles --specs=nosys.specs \
  -T STM32F103XX_FLASH.ld startup_stm32f103xe.s weak_main.c svc_user.c -o user.elf
```

`C`

```c
/* weak_main.c   编译运行：gcc -std=c23 weak_main.c -o weak_main */
#include "sh.h"

void SystemInit(void) { }        /* 启动文件会调用它们，这里给空实现 */
void _init(void) { }

int main(void)
{
    sh_puts("main: before svc\r\n");
#if defined(__arm__)
    __asm__ volatile ("svc 0");          /* 触发 SVCall，跳向量表第 11 项 */
#endif
    sh_puts("main: back from svc\r\n");  /* 处理器返回后才会打印这一行 */
    return 0;
}
```

`C`

```c
/* svc_user.c   编译（只编这一份）：gcc -std=c23 -c svc_user.c -o svc_user.o */
#include "sh.h"

void SVC_Handler(void)           /* 与启动文件里的弱符号同名 */
{
    sh_puts("SVC_Handler: user handler ran\r\n");
}
```

**变体 A 的符号表与运行结果：**

`实测数据`
`Text`

```text
080002e4 T Default_Handler
080002e4 W SVC_Handler

--- 向量表 0x2C 处那一项（SVCall 的入口，小端存放）
 8000020 00000000 00000000 00000000 e5020008

--- QEMU 输出
main: before svc
qemu-system-arm: terminating on signal 15 from pid 3088 (timeout)
```

`0x080002e5` 就是 `Default_Handler` 的地址加上 Thumb 位（最低位 1 表示 Thumb 指令集）。
**`main` 只打出了第一行，第二行永远不出现**，因为处理器进了 `Infinite_Loop`。

**变体 B 的符号表与运行结果：**

`实测数据`
`Text`

```text
08000310 T Default_Handler
08000266 T SVC_Handler

--- 向量表 0x2C 处那一项
 8000020 00000000 00000000 00000000 67020008

--- QEMU 输出
main: before svc
SVC_Handler: user handler ran
main: back from svc
```

**同一份启动文件，一行都没改。** 用户提供了强定义，向量表里那一项就换成了新地址，
处理器返回之后 `main` 继续往下走。

真板上的同一件事：STM32F103C8 复位后向量表的头两个字是 `0x20005000`（栈顶）
与 `0x080002CD`（`Reset_Handler` 的地址加 Thumb 位），最低位同样是 1。
弱符号替换掉的是表里的**其他**项，头两项永远由启动文件钉死。

> [!IMPORTANT]
> **弱符号让「库给默认实现、用户按需替换」这件事不需要任何配置。**
> 向量表的每个中断入口都是一个弱别名，因此 CubeMX 生成的工程里可以只写你关心的那几个
> `xxx_IRQHandler`，其余中断照样有落脚点，不会因为缺少定义而链接失败。
> 这也是 `--gc-sections` 会误伤向量表的原因，见《06-更底层/07-链接脚本与启动代码.md》第 5 节。

## 4.3 覆盖失败：一个静默的错

C++ 里写同名函数**不会**覆盖 C 的弱符号，因为修饰后的名字不一样。
链接器不会报错，程序照样能编出来，只是你的处理函数永远不会被调用。

`C++`

```cpp
/* svc_cpp_bad.cpp   编译（只编这一份）：g++ -std=c++17 -c svc_cpp_bad.cpp -o svc_cpp_bad.o */
#include "sh.h"

void SVC_Handler(void)           /* 少了 extern "C"：名字会被修饰 */
{
    sh_puts("SVC_Handler: user handler ran\r\n");
}
```

`实测数据`
`Bash`

```bash
arm-none-eabi-g++ -x c weak_main.c -x none -mcpu=cortex-m3 -mthumb -nostartfiles \
  --specs=nosys.specs -T STM32F103XX_FLASH.ld startup_stm32f103xe.s svc_cpp_bad.cpp -o cpp_bad.elf
arm-none-eabi-nm cpp_bad.elf | grep -iE "SVC_Handler|_Z11SVC"
arm-none-eabi-objdump -s -j .isr_vector cpp_bad.elf | sed -n '7p'
```

`实测数据`
`Text`

```text
08000310 W SVC_Handler
08000266 T _Z11SVC_Handlerv

--- 向量表 0x2C 处那一项
 8000020 00000000 00000000 00000000 11030008

--- QEMU 输出
main: before svc
（停住，第二行不再出现）
```

**用户写的函数变成了 `_Z11SVC_Handlerv`，弱符号 `SVC_Handler` 仍然指向 `Default_Handler`。**
向量表里那一项是 `0x08000311`，正好是 `Default_Handler`。加上 `extern "C"` 之后：

`实测数据`
`Text`

```text
08000310 T Default_Handler
08000266 T SVC_Handler

--- 向量表 0x2C 处那一项
 8000020 00000000 00000000 00000000 67020008

--- QEMU 输出
main: before svc
SVC_Handler: user handler ran
main: back from svc
```

> [!CAUTION]
> **这一类错误是静默的：编译通过、链接通过、程序也能跑，只是中断处理函数不生效。**
> 硬件相关的函数一律写 `extern "C"`。判据很简单：`nm` 里看到 `_Z` 开头的名字，
> 就说明它没能参与 C 名字的解析。

同一件事还有一个更常见的版本：用 `g++` 去编译 `.c` 文件。
`g++` 会把 `.c` 当成 C++ 源文件，于是启动文件要的 `SystemInit` 变成了 `_Z11SystemInitv`。

`实测数据`
`Text`

```text
<工具链>/.../ld: /tmp/ccHj6PrJ.o: in function `Reset_Handler':
(.text.Reset_Handler+0x0): undefined reference to `SystemInit'
<工具链>/.../ld: <newlib>/libc/misc/init.c:40:(.text+0x1e): undefined reference to `_init'
collect2: error: ld returned 1 exit status
```

（上面抹掉了两条绝对路径，其余原样。）

**处理办法有三个**：`.c` 交给 `gcc` 编、给这几个函数加 `extern "C"`、
或者用 `-x c` 显式告诉 `g++` 这一份按 C 处理。

## 4.4 主机侧的弱符号

`__attribute__((weak))` 在 Windows 的 PE 目标上**能用，但边界与 ELF 不同**。下面这份程序在两个链接顺序下都打印 `2`，
说明强定义胜出与顺序无关。

`C`

```c
/* weak_pe.c   编译运行：gcc -std=c23 weak_pe.c weak_strong.c -o weak_pe */
#include <stdio.h>
__attribute__((weak)) int weak_fn(void) { return 1; }
int main(void) { printf("weak_fn() = %d\n", weak_fn()); return 0; }
```

`C`

```c
/* weak_strong.c   编译（只编这一份）：gcc -std=c23 -c weak_strong.c -o weak_strong.o */
int weak_fn(void) { return 2; }      /* 强定义，覆盖上面的弱定义 */
```

`实测数据`
`Text`

```text
--- 弱定义先链接
weak_fn() = 2
--- 强定义先链接
weak_fn() = 2

--- nm weak_pe.o 里的弱符号
0000000000000000 T .weak.weak_fn.main
                 w weak_fn
```

**小写 `w` 与 ELF 侧一致。** 弱符号在主机上的典型用途是「库提供可被替换的默认实现」，
以及让同一个头文件里的内联函数在多个目标文件里有多个副本而不冲突——
后者是 `inline` 与模板实例化的底层机制，见《06-更底层/05-ABI 与调用约定.md》第 5 节。

**但两边的边界并不相同，PE 上有一条容易撞的规则**：**只有弱定义、没有强定义时，
PE 链接器不会拿它去满足一个普通的未定义引用**。同三份源码在两边各跑一遍：

`实测数据`
`Text`

```text
情形                      ELF（gcc 13.3.0）                PE（MinGW gcc 15.2.0）
调用方 + 弱定义            链接成功，运行打印 provider = 1   undefined reference to 'provider'
调用方 + 什么都没有        undefined reference              undefined reference
弱引用（声明成 weak）+ 无定义  链接成功，运行时解析为 0        链接成功，运行时解析为 0
```

符号表里也能看出差别：ELF 的目标文件把弱定义记成 `W provider`，
PE 的目标文件则把它记成小写 `w provider`，**另外生成一个 `.weak.provider.` 别名放进 COMDAT**——
链接器只在「有别的定义来和它比强弱」时才用得上它，**单独一份弱定义不够**。

> [!IMPORTANT]
> **跨平台的写法是「弱定义 + 强定义成对出现」**（库里给默认实现、使用者按需覆盖），
> 这才是两边都成立的那种用法；**想表达「这个符号可能不存在」，要用弱引用**（声明处加 `weak`，
> 调用前判空），它在 PE 与 ELF 上的行为一致。

# 第 5 节 段、保留与别名

三个属性经常一起出现，各自解决一个问题：`section` 决定放哪，`used` 决定编译器丢不丢，
`alias` 决定有没有第二个名字。

## 5.1 `section`：把符号放进指定的段

链接脚本是按段名摆放内存的（见《06-更底层/07-链接脚本与启动代码.md》第 2 节），
因此「把某个变量放进一个专门的段」就等于「让链接脚本单独安排它的地址」。
嵌入式里最常见的两个用途是把频繁访问的数据搬进 RAM、把只读表放进 flash 的指定区域。

`C`

```c
/* attrs.c   编译运行：gcc -std=c23 attrs.c -o attrs */
#include <stdio.h>

/* 放进自定义段：段名是给链接脚本用的 */
__attribute__((section(".mysec"))) int  in_mysec = 0x11223344;
__attribute__((section(".mysec"))) int  also_mysec = 0x55667788;

/* 只被这段内联汇编引用，编译器看不出来，必须加 used */
__attribute__((used, section(".keepme"))) static const char msg[] = "keep me";

int real_target(void) { return 42; }
/* alias：给同一个地址再起一个名字 */
int alias_name(void) __attribute__((alias("real_target")));

int main(void)
{
    printf("%d %d %d %d\n", in_mysec, also_mysec, real_target(), alias_name());
    return 0;
}
```

`实测数据`
`Bash`

```bash
gcc -std=c23 -O0 -c attrs.c -o attrs.o
objdump -h attrs.o | grep -E "mysec|keepme"
nm attrs.o | grep -E "real_target|alias_name"
gcc -std=c23 -O0 attrs.o -o attrs.exe
objdump -h attrs.exe | grep -E "mysec|keepme"
./attrs.exe
```

`实测数据`
`Text`

```text
  3 .mysec        00000008  0000000000000000  0000000000000000  000001dc  2**2
  4 .keepme       00000008  0000000000000000  0000000000000000  000001e4  2**3

0000000000000000 T alias_name
0000000000000000 T real_target

  2 .mysec        00000008  000000014000a000  000000014000a000  00007c00  2**2
  4 .keepme       00000008  000000014000c000  000000014000c000  00008800  2**2

287454020 1432778632 42 42
```

**两个段在目标文件里就有，链接后仍然保留。**
`287454020` 与 `1432778632` 分别是 `0x11223344` 与 `0x55667788` 的十进制写法；
最后两个 `42` 说明 `alias_name` 与 `real_target` 是同一个函数。

## 5.2 `used` 挡的是编译器，不是链接器

符号被删除有两个独立的关卡。第一关在编译器里：看不到引用的 `static` 数据会被直接丢掉。
第二关在链接器里：`--gc-sections` 会把没有引用的段收走。**`used` 只过第一关。**

`C`

```c
/* used_demo.c   只编译，看编译器丢掉谁：gcc -std=c23 -O2 -c used_demo.c -o used_demo.o */
__attribute__((used, section(".rodata.keep"))) static const char kept[] = "KEEP-ME";
static const char dropped[] = "DROP-ME";     /* 没有任何人引用 */
int main(void) { return 0; }
```

`实测数据`
`Bash`

```bash
gcc -std=c23 -O2 -c used_demo.c -o used_demo.o
objdump -h used_demo.o | grep rodata
nm used_demo.o | grep -E "kept|dropped"

# 再让链接器回收一次
gcc -std=c23 -O0 -ffunction-sections -fdata-sections -Wl,--gc-sections used_demo.o -o used_demo_gc.exe
objdump -h used_demo_gc.exe | grep -E "rodata|keep"
strings used_demo_gc.exe | grep -c KEEP-ME
```

`实测数据`
`Text`

```text
--- 第一关：编译器（-O2，只编不链）
  6 .rodata.keep  00000008  0000000000000000  0000000000000000  00000178  2**3
0000000000000000 r kept
（dropped 连符号都没有留下来）

--- 第二关：链接器（--gc-sections）
（.rodata.keep 也没有了）
0                 ← 镜像里连 "KEEP-ME" 这个字符串都找不到

--- 对照：不加 --gc-sections 链接
  3 .rodata.keep  00000008  0000000140005000  0000000140005000  00002600  2**2
1                 ← 字符串还在
```

同一份代码在 Cortex-M 上是一模一样的结果：`-O2` 编出的 `.o` 里只剩带 `used` 的那一份，
链接时加上 `--gc-sections`，`.rodata.keep` 照样消失。

> [!WARNING]
> **「加了 `used` 就安全」是一个常见误解。**
> `used` 的语义是「告诉编译器这个符号可能被本翻译单元之外的东西引用，别丢」，
> 它没有要求链接器保留。真正能挡住链接器的是链接脚本里的 `KEEP`——
> 第 4 节那张向量表就是靠 `KEEP(*(.isr_vector))` 活下来的。
> GCC 的 `retain` 属性只在支持 GNU 或 FreeBSD OSABI 的 ELF 目标上生效，
> 本章用到的两个目标（MinGW 的 PE 与 `arm-none-eabi` 的裸机 ELF）都不在其中，
> 编译器直接忽略它。因此不要把它当作办法。

`实测数据`
`Text`

```text
retain_demo.c:2:1: warning: 'retain' attribute ignored [-Wattributes]
```


## 5.3 `alias`：一个地址两个名字

`alias` 让一个新名字与已有符号共用地址。它与弱符号组合起来可以做「改名不失兼容」：
新名字是强符号，旧名字是弱别名。

`C`

```c
/* alias_weak.c   编译（只编这一份）：gcc -std=c23 -c alias_weak.c -o alias_weak.o */
int new_api(int x) { return x * 2; }
int old_api(int x) __attribute__((alias("new_api")));      /* 旧名字指向新实现 */
```

> [!TIP]
> **`alias` 的目标必须是同一个翻译单元里的定义**，而且要实现已经存在。
> 想给别的库里的函数起别名做不到，那种场合要在链接脚本里用 `PROVIDE`，
> 见《06-更底层/07-链接脚本与启动代码.md》第 2.7 小节。

# 第 6 节 静态库与动态库

**库的形态决定了链接器什么时候能看到里面的符号。**
静态库是「一堆目标文件打成的包」，链接器按需拆包；动态库是一个独立模块，
链接期只看导出表，运行期再去加载。

## 6.1 静态库：成员粒度是目标文件

`ar` 打出来的 `.a` 只是把多个 `.o` 串在一起，外加一张索引表。
链接器处理它的方式是：**扫描到未解析的符号时，去库里找哪个成员能提供它，把那个成员整个拉进来。**
粒度是成员（也就是目标文件），不是符号。

先给出整组的构建命令。

`Bash`

```bash
gcc -std=c23 -O0 -c lib_used.c -o lib_used.o
gcc -std=c23 -O0 -c lib_unused.c -o lib_unused.o
ar rcs libdemo.a lib_used.o lib_unused.o
gcc -std=c23 -O0 lib_main.c libdemo.a -o lib_demo.exe      # 库放在引用者之后
./lib_demo.exe
```

`C`

```c
/* lib_used.c   编译（只编这一份）：gcc -std=c23 -c lib_used.c -o lib_used.o */
int lib_used(void) { return 100; }
```

`C`

```c
/* lib_unused.c   编译（只编这一份）：gcc -std=c23 -c lib_unused.c -o lib_unused.o */
#include <stdio.h>
int lib_unused(void) { return 200; }
__attribute__((constructor)) static void lib_unused_ctor(void) { puts("lib_unused: constructor ran"); }
```

`C`

```c
/* lib_main.c   编译（只编这一份）：gcc -std=c23 -c lib_main.c -o lib_main.o */
#include <stdio.h>
int lib_used(void);
int main(void) { printf("lib_used() = %d\n", lib_used()); return 0; }
```

`实测数据`
`Text`

```text
--- 链接静态库，运行结果
lib_used() = 100

--- 可执行文件里的符号（只找 lib_ 开头的）
0000000140001470 T lib_used

--- 对照：把两个 .o 直接写进命令行
lib_unused: constructor ran
lib_used() = 100
000000014000148b t lib_unused_ctor
0000000140001480 T lib_unused
0000000140001470 T lib_used
```

**`lib_unused.o` 整个成员都没有进可执行文件**，连它的构造函数一起被丢掉了。
这不是优化，而是静态库的语义：没被引用就不拆包。
要把整个库无条件拉进来，用 `-Wl,--whole-archive`。
构造函数被丢掉这件事在 C++ 里有一个很常见的后果，见《06-更底层/08-CRT 与程序启动.md》第 4 节。

## 6.2 顺序敏感：库必须放在引用者之后

链接器只做一趟扫描。扫到一个库时，它只解析**当前已经出现过**的未定义符号；
扫完之后才出现的 `U`，不会回头再去库里找。

`实测数据`
`Bash`

```bash
gcc -std=c23 -O0 lib_main.c libdemo.a -o order_ok.exe     # 对
gcc -std=c23 -O0 libdemo.a lib_main.c -o order_bad.exe    # 错
```

`实测数据`
`Text`

```text
<MinGW>/.../ld.exe: <临时目录>/ccQl7sc.o:lib_main.c:(.text+0xe): undefined reference to `lib_used'
collect2.exe: error: ld returned 1 exit status
```

**符号明明在库里，链接器却说找不到。** 这是「顺序敏感」的典型症状：
报错里的名字确实存在于某个库中，只是那个库出现得太早。
办法有三个：把库挪到引用者后面、把库名写两遍（`-ldemo -ldemo`），
或者用 `--start-group`/`--end-group` 让链接器反复扫描。

> [!TIP]
> **库里出现「没人引用的构造函数」，就要检查它所在的那个成员有没有被引用。**
> 一个成员里只要有一个符号被用到，整个成员都会被拉进来，构造函数就跟着进来了；
> 反过来，一个成员里全是没人引用的东西，它就一直在库文件里待着。
> 把「注册用的全局对象」单独放一个成员，是这个坑最常见的形状。

## 6.3 动态库：链接期只看导出表

动态库（Windows 的 `.dll`、Linux 的 `.so`）在链接期只提供一张表：
**哪些名字可以被外部使用**。表里没有的名字，哪怕它的代码就在文件里，外部也链接不到。

`Bash`

```bash
# 造一个最小 DLL：两个导出，一个不导出
gcc -shared -O0 mydll.c -o mydll.dll -Wl,--out-implib,libmydll.a
```

`C`

```c
/* mydll.c   只编译：gcc -std=c23 -c mydll.c -o mydll.o（链接成 DLL 的命令见上） */
__declspec(dllexport) int  dll_add(int a, int b) { return a + b; }
__declspec(dllexport) int  dll_answer = 42;
int dll_hidden(void) { return 7; }     /* 有代码、有符号，但没有导出 */
```

**`__declspec(dllexport)` 是 Windows 上的导出标记。**
GCC 在 MinGW 上也认它，等价写法是 `__attribute__((dllexport))`；
如果想让 GCC 与 MSVC 都能导，还要考虑 `.def` 文件或 `--export-all-symbols`，
那属于构建系统的取舍。

### 没导出会怎样

`Bash`

```bash
gcc -std=c23 use_hidden.c -o use_hidden.exe -L. -lmydll    # 链接失败
```

`C`

```c
/* use_hidden.c   只编译：gcc -std=c23 -c use_hidden.c -o use_hidden.o */
int dll_hidden(void);
int main(void) { return dll_hidden(); }
```

`实测数据`
`Text`

```text
<MinGW>/.../ld.exe: <临时目录>/cc64ibwj.o:use_hidden.c:(.text+0xe): undefined reference to `dll_hidden'
collect2.exe: error: ld returned 1 exit status
```

**报错措辞与「库里根本没有这个函数」完全一样。** 排查时先确认导出表里有没有这个名字，
再看是不是漏了导入库（MinGW 的 `libmydll.a`、MSVC 的 `.lib`）——
Windows 上链接动态库靠的是导入库，它只为导出表里的名字生成跳转桩。

### MSVC 侧的同一张表

同一件事在 MSVC 侧换一个工具，导出的写法一样，看表的命令不一样。

`C`

```c
/* dll_msvc.c   MSVC 侧的导出样本：两个导出、一个不导出
   编译：cl /nologo /std:c17 /utf-8 /LD dll_msvc.c /Fe:dll_msvc.dll /Fo:dll_msvc.obj */
__declspec(dllexport) int msvc_add(int a, int b) { return a + b; }
__declspec(dllexport) int msvc_answer = 42;
int msvc_hidden(void) { return 7; }     /* 有代码、有符号，但没有导出 */
```

`Batch`

```bat
cl /nologo /std:c17 /utf-8 /LD dll_msvc.c /Fe:dll_msvc.dll /Fo:dll_msvc.obj
dumpbin /exports dll_msvc.dll
```

`实测数据`
`Text`

```text
    00000000 characteristics
    FFFFFFFF time date stamp
        0.00 version
           1 ordinal base
           2 number of functions
           2 number of names

    ordinal hint RVA      name

          1    0 00001000 msvc_add
          2    1 00018000 msvc_answer
```

（上面是 `dumpbin` 输出的节选，省略了文件头与末尾的 Section summary。）

**同一个 DLL，`objdump -p` 与 `dumpbin /exports` 读的是同一张表**，
一个给地址（RVA），一个给序号。序号用于按序号导入，名字用于按名字导入。

### 真实的规模

一个真实的库导出多少东西，可以直接数。下面这份是某套 Qt 6 动态版里随应用分发的
`Qt6Core.dll`（随 STM32CubeProgrammer 一起装到本机的那一份）。

`Bash`

```bash
ls -l Qt6Core.dll
dumpbin /exports Qt6Core.dll | findstr /C:"ordinal base" /C:"number of"
dumpbin /dependents Qt6Core.dll
```

`实测数据`
`Text`

```text
文件：Qt6Core.dll  6,686,904 字节

           1 ordinal base
        6374 number of functions
        6374 number of names

导入表里出现的运行时：libgcc_s_seh-1.dll、libstdc++-6.dll、libwinpthread-1.dll、msvcrt.dll、KERNEL32.dll …
```

**6374 个导出**，这是 C++ 库的常态：类、成员函数、模板实例化、
`typeinfo` 都在导出表里，名字全是修饰名。这也解释了为什么 C++ 库的 ABI 兼容那么难做：
导出表里的名字与编译器、标准库版本绑得很紧。
同一份 `Qt6Core.dll` 换一个 Qt 版本、换一套编译器，导出的名字与数量都会变，
上面这组数字只是这一份文件的规模。

# 第 7 节 速查表

| 常用件 | 一句话用途 | 典型坑 |
|---|---|---|
| `nm` 大写字母 | 外部链接，别的翻译单元能用 | 与段名混淆，`T`/`D`/`B` 的差别不是可见性 |
| `nm` 小写字母 | 内部链接，只在本翻译单元有效 | 头文件里的 `static` 会让每个单元各存一份 |
| `nm` 的 `U` | 未定义，需要别人提供 | 报 `undefined reference` 时先看它在不在 |
| `nm` 的 `W` / `w` | 弱符号，可被强定义覆盖 | `_Z` 开头的名字不参与 C 名字解析 |
| `static` | 产生内部链接 | 用在头文件的函数定义上会复制出多份实现 |
| 匿名命名空间 | C++ 里产生内部链接 | 名字被修饰成 `_GLOBAL__N_1`，`grep` 时按原名找不到 |
| `multiple definition` | GCC 的重复定义报错 | 报错里带两个来源文件与段内偏移，按它定位 |
| `LNK2005` / `LNK1169` | MSVC 的重复定义报错 | 与 `LNK2019`（未解析外部符号）不是一回事 |
| `__attribute__((weak))` | 提供可被替换的默认实现 | C++ 里必须 `extern "C"` 才能覆盖 C 的弱符号 |
| `.weak` + `.thumb_set` | 汇编里造弱别名（向量表就是这么写的） | 用户写了同名函数却不生效，先查修饰名 |
| `__attribute__((section))` | 把符号放进指定段，交给链接脚本安排 | 链接脚本里没有对应规则时段会被放到别处 |
| `__attribute__((used))` | 挡住编译器丢弃 | **挡不住链接器的 `--gc-sections`**，那要靠 `KEEP` |
| `__attribute__((alias))` | 一个地址两个名字 | 目标必须在本翻译单元已定义 |
| `ar rcs lib.a a.o b.o` | 打静态库 | 库要放在引用者之后，否则报未定义 |
| `-Wl,--whole-archive` | 把库的所有成员都拉进来 | 体积变大，同一符号可能重复 |
| `objdump -p` / `dumpbin /exports` | 读导出表 | 符号表里有不等于导出表里有 |
| `__declspec(dllexport)` | Windows 上导出符号 | 忘了导出时报 `undefined reference`，与「函数不存在」措辞一致 |
| `strip` | 去掉符号表 | 调试信息与断点一起消失 |
