《06-更底层/03-寄存器、位与 volatile.md》章节讲的是「一个固定地址上的读写在硬件上意味着什么」。
要接着往下走，先得回答一个更前面的问题：**一个变量、一段代码、一次分配，究竟落在哪个地址上**。
这个问题在两句不同的话里有完全不同的答案——「在我的电脑上运行」与「在一颗单片机上运行」。

在桌面上，地址是操作系统与加载器给的：代码与常量在只读区、有初值的全局量在数据段、
无初值的在 `.bss`、函数调用时在栈上、`malloc` 出来的在堆上，
而且因为地址空间布局随机化，同一份程序两次运行的栈与堆地址并不相同。
在单片机上，没有操作系统也没有加载器：地址由链接脚本写死，
代码与常量在 flash、变量在 SRAM、栈从 SRAM 顶端往下长，
上电后第一件事是把 `.data` 的初值从 flash 搬到 SRAM。

本章把这两套地址空间并排摆出来：先用一份程序把桌面程序各段的地址打印出来，
再用交叉工具链把同一类变量在 Cortex-M 上的地址打印出来，
然后钻到栈里面看一个栈帧由什么组成、栈溢出在两边各是什么后果，
最后看堆——桌面上的分配器与裸机上的 `_sbrk` 各是怎么管那一段空间的。

# 第 1 节 进程地址空间：一个程序把六段都打印出来

## 1.1 六类对象，六个地址

先说清一件事：**「段」是链接器的概念，「区」是操作系统的概念**。
链接器把代码与数据分成 `.text`、`.rodata`、`.data`、`.bss` 这些段，
加载器再按权限把它们映射到进程地址空间里的几个区域。
写代码的人关心的是另一件事：**我写的这个东西落在哪一类里**。

下面这份程序把六类对象各取一个，把它们的地址打印出来。

`C`

```c
/* segments.c   编译：gcc -std=c23 -O0 segments.c -o segments.exe
   打印六类对象的地址：代码、只读数据、有初值的数据、无初值的数据、栈、堆 */
#include <stdio.h>
#include <stdlib.h>

int         g_init   = 0x11223344;   /* 有初值的全局：.data */
int         g_uninit;                /* 无初值的全局：.bss  */
const int   g_const  = 0x55667788;   /* 只读数据：.rodata  */
static int  s_static = 0x99;         /* 内部链接，仍在 .data */
const char  g_msg[]  = "hello";      /* 只读数据 */

void code_here(void) { }             /* 代码：.text */

int main(void)
{
    int  local   = 1;                /* 自动变量：栈 */
    static int s_local = 2;          /* 静态存储期：.data */
    int *heap1 = malloc(16);         /* 堆 */
    int *heap2 = malloc(16);

    printf("code_here = %p   .text\n",   (void *)code_here);
    printf("main      = %p   .text\n",   (void *)main);
    printf("g_const   = %p   .rodata\n", (void *)&g_const);
    printf("g_msg     = %p   .rodata\n", (void *)g_msg);
    printf("g_init    = %p   .data\n",   (void *)&g_init);
    printf("s_static  = %p   .data\n",   (void *)&s_static);
    printf("s_local   = %p   .data\n",   (void *)&s_local);
    printf("g_uninit  = %p   .bss\n",    (void *)&g_uninit);
    printf("&local    = %p   栈\n",      (void *)&local);
    printf("heap1     = %p   堆\n",      (void *)heap1);
    printf("heap2     = %p   堆\n",      (void *)heap2);
    free(heap1); free(heap2);
    return 0;
}
```

连续运行两次，把两次的输出并排看：

`实测数据`
`Text`

```text

code_here = 00007ff6e05c1440   .text        code_here = 00007ff6e05c1440   .text
main      = 00007ff6e05c1447   .text        main      = 00007ff6e05c1447   .text
g_const   = 00007ff6e05ca000   .rodata      g_const   = 00007ff6e05ca000   .rodata
g_msg     = 00007ff6e05ca004   .rodata      g_msg     = 00007ff6e05ca004   .rodata
g_init    = 00007ff6e05c9000   .data        g_init    = 00007ff6e05c9000   .data
s_static  = 00007ff6e05c9004   .data        s_static  = 00007ff6e05c9004   .data
s_local   = 00007ff6e05c9008   .data        s_local   = 00007ff6e05c9008   .data
g_uninit  = 00007ff6e05cd030   .bss         g_uninit  = 00007ff6e05cd030   .bss
&local    = 0000008ed55ff72c   栈           &local    = 0000008a7fbff9cc   栈
heap1     = 000001a4dd092420   堆           heap1     = 00000282ef8d2420   堆
heap2     = 000001a4dd092440   堆           heap2     = 00000282ef8d2440   堆
```

**两类地址，两种行为**：

| 对象 | 在哪个段／区 | 两次运行是否变化 | 谁决定地址 |
|---|---|---|---|
| 函数（`code_here`、`main`） | `.text` | 不变 | 链接器给相对位置，加载器给基址 |
| 只读数据（`g_const`、`g_msg`） | `.rodata` | 不变 | 同上 |
| 有初值的全局与静态变量 | `.data` | 不变 | 同上 |
| 无初值的全局与静态变量 | `.bss` | 不变 | 同上 |
| 自动变量 | 栈 | **变** | 操作系统给栈顶，调用深度决定偏移 |
| `malloc` 返回的地址 | 堆 | **变** | 分配器与操作系统的 ASLR |

**段与段的相对位置是固定的**：`g_const` 比 `g_init` 高 `0x1000`（一页），
`main` 比 `code_here` 高 7 字节（`code_here` 只有一条 `ret`），
`.bss` 紧跟在 `.data` 后面。**变化的是运行期给的基址**：
同一份可执行文件在这台机器上连续运行六次，模块基址都是 `0x7ff6e05c0000`
（换一个可执行文件、换一台机器都会不同），
而栈地址每次都不同（`0x497a1ff6bc`、`0x5c53bffb7c`、`0x800cbffc7c`……
六次六个值），堆地址同样每次都不同。
**同一次运行内所有段共享一个模块基址**，这就是 `nm` 的映像内偏移与程序打印的
运行地址之间只差一个常数的原因。

> [!IMPORTANT]
> **「变量在哪里」有两个层次：段（相对位置，链接期定死）与基址（绝对位置，加载期决定）。**
> 调试时看到地址对不上，先分清是哪一层变了——换了一次编译（段变了），
> 还是换了一次运行（基址变了）。

## 1.2 `size` 与 `nm` 看各段

上一节那张表是从程序里打印出来的，工具侧看同一件事用 `size` 与 `nm`。

`实测数据`
`Text`

```text
$ size segments.exe
   text	   data	    bss	    dec	    hex	filename
  36760	    288	   2976	  40024	   9c58	segments.exe

$ nm segments.exe | grep -E "g_const|g_init|g_msg|g_uninit|s_local|s_static|code_here|main"
0000000140001440 T code_here
000000014000a000 R g_const
0000000140009000 D g_init
000000014000a004 R g_msg
000000014000d030 B g_uninit
0000000140009008 d s_local.0
0000000140009004 d s_static
0000000140001447 T main
```

两边能对上：

| 从程序里打印 | 从 `nm` 读 | 段 |
|---|---|---|
| `code_here` = `...c1440` | `T code_here` @ `0x140001440` | `.text` |
| `g_const` = `...ca000` | `R g_const` @ `0x14000a000` | `.rodata` |
| `g_init` = `...c9000` | `D g_init` @ `0x140009000` | `.data` |
| `g_uninit` = `...cd030` | `B g_uninit` @ `0x14000d030` | `.bss` |

**`nm` 里的地址是「映像内偏移」，程序打印的是「运行时的绝对地址」**，
两者的差就是加载基址（这里是 `0x7ff6e05c0000 - 0x140000000`）。
把这一层看明白，段表、符号表、调试器里的地址就能互相对上了。

## 1.3 `.data` 的初值从哪来，`.bss` 为什么不占文件

一个反直觉的事实：**`.data` 里那个 `0x11223344` 一开始并不在内存里，它在文件里**。
链接器把有初值的可写数据同时记两个地址：运行地址（VMA）在可写内存，
装载地址（LMA）在文件（或裸机上的 flash）里。段表把这两列并排写出来。

`实测数据`
`Text`

```text
$ objdump -h segments.exe | sed -n '4,12p'
Idx Name          Size      VMA               LMA               File off  Algn
  0 .text         000073c0  0000000140001000  0000000140001000  00000600  2**4
  1 .data         00000100  0000000140009000  0000000140009000  00007a00  2**4
  2 .rdata        00000998  000000014000a000  000000014000a000  00007c00  2**4
  3 .pdata        00000480  000000014000b000  000000014000b000  00008600  2**2
  4 .xdata        00000430  000000014000c000  000000014000c000  00008c00  2**2
  5 .bss          00000b80  000000014000d000  000000014000d000  00000000  2**4
```

- **`.data` 有 `File off`**（`0x7a00`）：初值在文件里，加载时拷进内存；
- **`.bss` 的 `File off` 是 0**：它在文件里没有内容，只有长度，加载时清零。

在 Cortex-M 上这两件事变成：`.data` 的初值在 **flash** 里，由启动代码搬到 SRAM；
`.bss` 由启动代码清零。**这是同一套机制的两种落地方式**——
桌面靠加载器，裸机靠 `Reset_Handler`（第 7 章逐条讲它）。

`实测数据`
`Text`

```text
$ arm-none-eabi-objdump -h addr.elf | grep -A1 -E "^ *[0-9]+ \.(data|bss) +"
  8 .data         0000054c  20000000  0800198c  00003000  2**3
                  CONTENTS, ALLOC, LOAD, DATA
 11 .bss          000001d0  2000054c  08001ed8  0000354c  2**2
                  ALLOC
```

`.data` 的 VMA 是 `20000000`（SRAM），LMA 是 `0800198c`（flash）——**同一个段的两个地址**。
`.bss` 的 VMALMA 那一列写着 `08001ed8`，但属性里没有 `CONTENTS`：
它不需要在 flash 里占位置，只需要记下「从 `2000054c` 开始、长 `0x1d0` 字节，全部清零」。

> [!TIP]
> 查「一个变量到底在哪」，最短的路是 `nm` 看段归属（`D`/`B`/`R`），
> 再用 `objdump -h` 或 map 文件看那个段的两套地址。
> 判断「初值从哪来」，看 `.data` 的 `load address` 就够了。

## 1.4 小结

> [!NOTE]
> 进程地址空间里，代码与只读数据、可写数据、无初值数据分别落在不同段上，
> 段内偏移由链接器定死、基址由加载器给，因此段间相对位置固定而绝对地址会变；
> 栈与堆的地址每次都不同。`.data` 的初值随文件一起装载，
> `.bss` 只在文件里记长度、运行时清零——这两条到了裸机上就变成启动代码里的**搬运**与**清零**。

# 第 2 节 裸机地址空间：三个区加一个寄存器区

## 2.1 真板上的内存地图

桌面程序运行在操作系统搭好的沙盒里，裸机程序没有这层沙子。
STM32F103C8 这颗芯片上的地址空间是芯片设计时定死的，写进参考手册，
链接脚本只是把它抄一遍。本章用到的四个区如下。

`实测数据`

| 区 | 起始地址 | 大小 | 放什么 | 能不能写 |
|---|---|---|---|---|
| flash | `0x08000000` | 64 KiB | 向量表、代码、只读数据、`.data` 的初值 | 不能（要按扇区擦除） |
| SRAM | `0x20000000` | 20 KiB | `.data`、`.bss`、堆、栈 | 能 |
| 外设寄存器区 | `0x40000000` 起 | 按外设分 | GPIO、USART、定时器等外设寄存器 | 能，且读写有副作用 |
| 内核私有区（PPB） | `0xE0000000` 起 | — | SysTick、NVIC、SCB 这些内核里的东西 | 能 |

**这四行不是从手册抄来的结论，是在板子上读出来的**：复位向量的第一个字是 `0x20005000`，
正好是 `0x20000000` 加 20 KiB——栈顶就设在 SRAM 的最高地址；
第二个字是 `0x080002CD`，指向 flash 里的 `Reset_Handler`（最低位是 1，表示 Thumb 态）。

把整片擦掉再看，就更直白了：

`实测数据`
`Text`

```text
0x08000000: ffffffff ffffffff ffffffff ffffffff     ← 全片擦净
复位后：pc = 0xfffffffe   sp = 0xfffffffc
```

**擦掉的是向量表，于是复位时取到的「栈顶」是 `0xfffffffc`、「入口」是 `0xfffffffe`**，
两个地址都不在有效内存里，芯片直接进 HardFault。这一条解释了为什么向量表必须钉在 flash
最前面，而不是「放在代码后面比较整齐」（第 7 章会讲向量表的每一位是谁）。

## 2.2 在 QEMU 里把每个地址打印出来

桌面程序打印地址用 `printf`；裸机程序没有操作系统，输出要走 semihosting
（`bkpt 0xAB` 加 `SYS_WRITE0`，见《06-更底层/03-寄存器、位与 volatile.md》第 2.3 小节）。
下面这份程序在目标上把每一类对象的地址打出来。

`C`

```c
/* addr.c   交叉编译（Cortex-M3）：arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -c addr.c -o addr.o
   完整构建与运行（在 WSL 的 Ubuntu 里）：
     arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -nostartfiles --specs=nosys.specs \
       -T STM32F103C8_FLASH.ld startup_stm32f103xe.s addr.c -o addr.elf
     qemu-system-arm -M netduinoplus2 -kernel addr.elf -nographic \
       -semihosting-config enable=on,target=native
   这个文件在主机上只编译（目标专有的符号与地址在主机上没有意义） */
#include <stdint.h>
#include <stdlib.h>
#include <stdio.h>       /* 主机侧退化输出要用 fputs/stdout */

/* ---- 输出：目标上走 semihosting，主机上退化成 stdout ---- */
static void sh_puts(const char *s)
{
#if defined(__arm__)
    register uint32_t r0 __asm__("r0") = 0x04u;      /* SYS_WRITE0 */
    register const char *r1 __asm__("r1") = s;
    __asm__ volatile ("bkpt 0xAB" : : "r"(r0), "r"(r1) : "memory");
#else
    fputs(s, stdout);
#endif
}

static void sh_hex(uint32_t v)
{
    static const char h[] = "0123456789abcdef";
    char b[11];
    b[0] = '0'; b[1] = 'x';
    for (int i = 0; i < 8; ++i) b[2 + i] = h[(v >> (28 - 4 * i)) & 0xFu];
    b[10] = '\0';
    sh_puts(b);
}

static void row(const char *label, const volatile void *p, const char *note)
{
    sh_puts(label);
    sh_hex((uint32_t)(uintptr_t)p);
    sh_puts("  ");
    sh_puts(note);
    sh_puts("\r\n");
}

/* ---- 链接脚本给出的符号：它们的「值」就是地址 ---- */
extern uint32_t _sidata, _sdata, _edata, _ebss, _estack, _end;

volatile uint32_t g_data = 0x11112222u;   /* 有初值：.data */
volatile uint32_t g_bss;                  /* 无初值：.bss  */

/* 与 sysmem.c 同一套逻辑的 _sbrk：让 malloc 能用（第 5 节展开讲） */
static uint8_t *heap_end = NULL;
void *_sbrk(ptrdiff_t incr)
{
    const uint32_t stack_limit = (uint32_t)(uintptr_t)&_estack - 0x400u;   /* _Min_Stack_Size */
    if (heap_end == NULL) heap_end = (uint8_t *)&_end;
    if ((uint32_t)(uintptr_t)heap_end + incr > stack_limit) { return (void *)-1; }
    uint8_t *prev = heap_end;
    heap_end += incr;
    return prev;
}

void SystemInit(void) { }    /* 启动文件会调用它们 */
void _init(void) { }

int main(void)
{
    int  local = 0;
    void *h1 = malloc(16);
    void *h2 = malloc(16);

    row("_sidata = ", &_sidata, "flash（.data 的装载地址）");
    row("_sdata  = ", &_sdata,  "SRAM （.data 的运行地址）");
    row("_edata  = ", &_edata,  "SRAM");
    row("_ebss   = ", &_ebss,   "SRAM");
    row("_end    = ", &_end,    "SRAM （堆从这里往上长）");
    row("_estack = ", &_estack, "SRAM （MSP 初值）");
    row("&g_data = ", &g_data,  "SRAM");
    row("&g_bss  = ", &g_bss,   "SRAM");
    row("main    = ", (void *)main, "flash");
    row("&local  = ", &local,   "SRAM （栈）");
    row("h1      = ", h1,       "SRAM （堆）");
    row("h2      = ", h2,       "SRAM （堆）");
    for (;;) { }             /* 裸机上没有「退出」，跑完就停在这里 */
}
```

`实测数据`
`Text`

```text
_sidata = 0x0800198c  flash（.data 的装载地址）
_sdata  = 0x20000000  SRAM （.data 的运行地址）
_edata  = 0x2000054c  SRAM
_ebss   = 0x2000071c  SRAM
_end    = 0x20000720  SRAM （堆从这里往上长）
_estack = 0x20005000  SRAM （MSP 初值）
&g_data = 0x20000000  SRAM
&g_bss  = 0x200005a0  SRAM
main    = 0x080003f5  flash
&local  = 0x20004fec  SRAM （栈）
h1      = 0x20000728  SRAM （堆）
h2      = 0x20000740  SRAM （堆）
```

同一颗芯片上的地址空间被切成两簇，**每一簇里各段的顺序也一目了然**：

`Text`

```text
0x08000000 ┌──────────────────────────────┐  flash（64 KiB）
           │ .isr_vector   向量表          │  ← 复位时 CPU 从这里读栈顶与入口
           ├──────────────────────────────┤
           │ .text         代码            │
           ├──────────────────────────────┤
           │ .rodata       只读数据        │
           ├──────────────────────────────┤
           │ .data 的初值（← 上电后被搬走）│
           └──────────────────────────────┘
0x20000000 ┌──────────────────────────────┐  SRAM（20 KiB）
           │ .data         有初值的变量    │  ← 初值刚从 flash 搬过来
           ├──────────────────────────────┤
           │ .bss          无初值的变量    │  ← 刚被清零
           ├──────────────────────────────┤
           │ 堆            ↑ 向上长       │  _end = 0x20000720
           │                              │
           │ 栈            ↓ 向下长       │  _estack = 0x20005000
           └──────────────────────────────┘
```

**堆从 `_end` 往上长、栈从 `_estack` 往下长，两者在 20 KiB 里对向生长**——
中间没有任何硬件分隔，撞上之前谁也不知道。第 4、5 节分别从两头逼近这条边界。

## 2.4 外设寄存器区：同一句 C 代码，不同的去处

地址空间的第三个区从 `0x40000000` 开始，里面不是内存，是**外设的寄存器**。
在真板上读一次 GPIOA 的输入数据寄存器：

`实测数据`
`Text`

```text
在 STM32F103C8（Cortex-M3、HSI 8 MHz）上，调试器读 0x40010808（GPIOA_IDR）：
读到值，没有总线错误——这一段地址上挂着真实的外设寄存器
```

同一句 `*(volatile uint32_t *)0x40010808` 在 QEMU 的近似板上是另一回事：

`实测数据`
`Text`

```text
真板 F103C8           读到值，程序继续跑
QEMU netduinoplus2    执行到这一句之后不再有输出（卡住了）
```

QEMU 的 `netduinoplus2` 是 Cortex-M4 的近似板，`0x40010808` 在它的地址映射里
不是 GPIOA。**两个目标的差别不是编译器造成的，是地址映射不同**——
外设地址只在它自己的芯片上有意义（卡住的具体原因由默认异常处理函数的死循环推断，标 `待确认`）。

这一句在 C 里的写法与读内存变量完全一样：

`C`

```c
/* periph_read.c   读一个外设寄存器：地址随芯片变（下面是节选） */
#include <stdint.h>

#if defined(BOARD_F103C8)
#define GPIOA_IDR (*(volatile uint32_t *)0x40010808u)   /* F103C8：GPIOA 的输入寄存器 */
#else
#define GPIOA_IDR (*(volatile uint32_t *)0x40020000u)   /* 近似板（F4）的 GPIOA 在另一个地址 */
#endif

uint32_t read_pins(void) { return GPIOA_IDR; }
```

**同一个「GPIOA」，在 F103 上是 `0x40010800`，在 F4 系列上是 `0x40020000`。**
外设基址是芯片设计的一部分，换型号就要换地址——
用厂商头文件里的 `GPIOA` 而不是自己抄地址，图的就是这一点。

`实测数据`

| 外设 | F103 上的基址 | 常见偏移 | 在 QEMU 近似板上的地址 |
|---|---|---|---|
| GPIOA | `0x40010800` | `IDR` +0x08、`ODR` +0x0C、`BSRR` +0x10 | `0x40020000` |
| RCC | `0x40021000` | `APB2ENR` +0x18 | 同名外设地址不同 |
| USART2 | `0x40004400` | `SR` +0x00、`DR` +0x04 | `0x40004400`（恰好一致） |
| SysTick（内核，不在外设区） | `0xE000E010` | `CTRL`/`LOAD`/`VAL` | `0xE000E010` |

**内核私有区（`0xE0000000`）里的东西与芯片型号无关**，SysTick、NVIC、SCB 都在这里，
所以第 3 章用 SysTick 数周期这件事在真板与 QEMU 上都能做；
而外设寄存器区的地址与行为都随芯片变，涉及具体外设时序的结论只能标 `待确认`。

`待确认`

> 表里只有 GPIOA 的 `0x40010808` 是在真板上读过的（读到 `0`）；
> RCC、USART2 那两行取自芯片头文件与参考手册，没有在真板上逐个核对，
> QEMU 那一列则是 `netduinoplus2`（Cortex-M4 近似板）的实际映射。

## 2.5 写错了会怎样：内存大小抄错

到这里可以回答一个很常见的事故：**链接脚本里的内存大小与实际芯片不一致**。
素材里的 `STM32F103XX_FLASH.ld` 是给 F103xC（RAM 48 KiB、flash 256 KiB）的，
直接拿给 F103C8（RAM 20 KiB）用：

`实测数据`

| 项 | 用错脚本（RAM 48K） | 改成 20K 之后 |
|---|---|---|
| `_estack` | `0x2000C000`（**超出 20 KiB RAM**） | `0x20005000` |
| 复位后的现场 | `current mode: Handler HardFault`，`pc = 0x08000314` | 正常进 `main` |
| 结果 | **第一次压栈就越界**，任何测试都跑不起来 | `.data`/`.bss` 检查全部通过 |

**报错方式很隐蔽**：链接器不会抱怨——`0x2000C000` 是一个完全合法的地址，
只是这颗芯片上没有那块内存。程序在复位后第一条 `push` 指令上就进了 HardFault，
在没有调试器的情况下表现为「烧进去什么都不动」。
QEMU 近似板的 RAM 是 128 KiB，同样的脚本在 QEMU 里反而能跑——
**这也是「在 QEMU 里通过」不能替代真板验证的原因之一**。
链接脚本逐段怎么改是第 7 章的主题（《06-更底层/07-链接脚本与启动代码.md》第 5 节专门讲这类改错）。

> [!CAUTION]
> **裸机上没有 MMU 兜底。** 越界访问要么落到别的变量上（静默出错），
> 要么落到没有实现的地址上（HardFault）。第 4 节会看到前者，
> 2.5 这一组就是后者。

> [!NOTE]
> **小结**：裸机地址空间由芯片定死，链接脚本把它抄进工程：
> flash `0x08000000` 放向量表、代码与 `.data` 的初值，SRAM `0x20000000` 放变量与栈堆，
> 外设寄存器区从 `0x40000000` 开始，内核私有区在 `0xE0000000`。
> `objdump -h` 与 map 文件能把这些数字逐条核对出来，
> 而内存大小抄错的表现是复位后立刻 HardFault。

# 第 3 节 栈：一个栈帧由什么组成

## 3.1 x86-64 的栈帧：`-O0` 与 `-O2` 对照

栈帧是「一次函数调用占用的那块栈内存」。它由编译器布局，布局规则由 ABI 约束。
用一个有参数、有局部变量、有数组、有一次调用的函数来看。

`C`

```c
/* frame.c   编译（只看汇编）：gcc -std=c23 -O0 -S frame.c -o frame_O0.s
                             gcc -std=c23 -O2 -S frame.c -o frame_O2.s          */
int add3(int a, int b, int c) { return a + b + c; }

int frame_demo(int n)
{
    int x = n + 1;
    int y = x * 2;
    int arr[4] = { 1, 2, 3, 4 };
    return add3(x, y, arr[n & 3]);
}

int main(void) { return frame_demo(2); }
```

`-O0` 下 `frame_demo` 的帧：

`实测数据`
`Assembly`

```asm
frame_demo:
	pushq	%rbp
	movq	%rsp, %rbp
	subq	$64, %rsp                # 帧本体 64 字节
	movl	%ecx, 16(%rbp)           # 参数 n 从 ecx 存回栈上（影子空间）
	movl	16(%rbp), %eax
	addl	$1, %eax
	movl	%eax, -4(%rbp)           # 局部变量 x
	movl	-4(%rbp), %eax
	addl	%eax, %eax
	movl	%eax, -8(%rbp)           # 局部变量 y
	movl	$1, -32(%rbp)            # 数组 arr[0]～arr[3]：-32、-28、-24、-20
	movl	$2, -28(%rbp)
	movl	$3, -24(%rbp)
	movl	$4, -20(%rbp)
```

`-O2` 下同一个函数：

`实测数据`
`Assembly`

```asm
frame_demo:
	subq	$24, %rsp
	movabsq	$8589934593, %rax        # 一次把 {1, 2} 两个 int 装进 8 字节寄存器
	movl	%ecx, %edx
	movq	%rax, (%rsp)
	movabsq	$17179869187, %rax       # 再把 {3, 4} 装进去
	andl	$3, %edx
	movq	%rax, 8(%rsp)
	leal	3(%rcx,%rcx,2), %eax     # x + y 直接算成 3*n+3
	addl	(%rsp,%rdx,4), %eax
	addq	$24, %rsp
	ret
```

**同一份源码，两种帧**：

| 项 | `-O0` | `-O2` |
|---|---|---|
| 帧指针 | 用 `rbp`（`pushq %rbp` + `movq %rsp,%rbp`） | 不用 `rbp` |
| 帧大小 | `pushq` 8 字节 + `subq $64` = **72 字节** | `subq $24` = **24 字节** |
| 参数 `n` | 从 `ecx` 立刻存到 `16(%rbp)` | 一直留在 `ecx`/`edx` |
| 局部变量 | 每个都在栈上有地址（`-4`、`-8`） | 没有自己的地址 |
| 数组 | 4 个元素逐个写入栈 | 两条 `movabsq` 直接写 16 字节立即数 |
| 函数调用 | 真的 `call add3` | `leal` 把 `x + y` 算完，调用被内联掉 |

两点值得记住：

- **`-O0` 下每个变量都有地址，`-O2` 下多数变量只在寄存器里**。
  这就是为什么「在调试器里看不到某个变量」通常不是调试器的问题，
  而是那个变量根本没有内存地址。
- **帧大小由编译器定，不由源码行数定**。同一个函数，帧从 72 字节缩到 24 字节。
  算「栈够不够用」时不能只看变量声明了几个。

## 3.2 Cortex-M 的栈帧

同一件事在 Cortex-M 上换个样子。第 4 节那份递归程序的汇编开头是这样的：

`实测数据`
`Assembly`

```asm
080002fc <recurse>:
 80002fc:	b580      	push	{r7, lr}        # 8 字节：帧指针 + 返回地址
 80002fe:	b08c      	sub	sp, #48            # 再留 48 字节给局部变量
 8000300:	af00      	add	r7, sp, #0         # r7 当帧指针（-O0 专用）
 8000302:	2300      	movs	r3, #0
 8000304:	62fb      	str	r3, [r7, #44]
```

**每层递归占 8 + 48 = 56 字节**。Cortex-M 的 `push` 把返回地址也压进栈，
而 x86-64 的 `call` 会自己把返回地址压栈，所以两边「帧」的构成略有不同，
但套路一样：**返回地址、保存的寄存器、局部变量，三段拼在一起**。

| 帧里的东西 | x86-64（Windows x64） | Cortex-M（AAPCS，`-O0`） |
|---|---|---|
| 返回地址 | `call` 指令压栈 | `push {r7, lr}` 里的 `lr` |
| 帧指针 | `pushq %rbp` | `push {r7, lr}` 里的 `r7` |
| 参数 | 前 4 个进 `rcx`/`rdx`/`r8`/`r9`，多出的在栈上 | 前 4 个进 `r0`–`r3`，多出的在栈上 |
| 局部变量 | `subq $N, %rsp` 之后按偏移访问 | `sub sp, #N` 之后按偏移访问 |
| 谁负责复原栈 | 被调用者在返回前恢复（`addq`/`pop`） | 同样由被调用者恢复 |

参数寄存器的具体规则、结构体按值传递怎么摊开、软浮点与硬浮点的区别，
是《06-更底层/05-ABI 与调用约定.md》章节的内容，这里只要认得三件事：
**返回地址在栈上（或 `lr` 里）、局部变量在栈上、参数优先进寄存器**。

## 3.3 栈有多大，往哪边长

栈在两边都往**低地址**方向长：`push` 或 `sub sp` 让栈指针变小。
差别在容量与「谁定的容量」。

`实测数据`

| 目标 | 栈的起点 | 栈的大小 | 谁决定 |
|---|---|---|---|
| Windows x86-64 | 由系统给 | **2 MiB**（PE 头部的 stack reserve = `0x200000`） | 链接选项，默认 2 MiB |
| Linux x86-64 | 由系统给 | 8 MiB（`ulimit -s`） | 内核默认 |
| STM32F103C8 | `0x20005000` | **20 KiB 里的一部分**（`_Min_Stack_Size` = `0x400`） | 链接脚本 |

桌面上「栈有多大」平时不用管：2 MiB 用完之前，操作系统会先给一个段错误，
而且很多系统还能自动增长栈。**单片机上必须自己算**：
栈顶是 SRAM 顶端，栈底就是堆的上界，中间没有护栏。
链接脚本里的 `_Min_Stack_Size = 0x400` 只是一个「至少留 1 KiB」的声明，
真实占用由链接器检查——堆加栈装不下就报错。

## 3.4 小结

> [!NOTE]
> 一个栈帧由返回地址、保存的寄存器、局部变量三段组成，大小由编译器决定；
> `-O0` 下每个变量都有栈地址，`-O2` 下多数变量只在寄存器里，帧也小得多。
> 栈在桌面与裸机上都向低地址增长，区别在容量：桌面默认 2 MiB 且有护栏，
> 裸机是 SRAM 顶端往下的一段，大小写死在链接脚本里。

# 第 4 节 栈溢出：桌面崩溃，单片机上无声

## 4.1 x86-64：进程被操作系统终止

先看桌面上的表现。下面这份程序无限递归，每层在栈上放 64 字节。

`C`

```c
/* stack_overflow.c   编译：gcc -std=c23 -O0 stack_overflow.c -o stack_overflow.exe
   运行：stack_overflow.exe   （会被系统终止，退出码 0xC00000FD） */
#include <stdio.h>

static unsigned long long depth = 0;

static void recurse(void)
{
    volatile int pad[16];          /* 每层 64 字节，编译器删不掉 */
    pad[0] = (int)depth;
    ++depth;
    if (depth % 2000 == 0) { printf("递归 %llu 层\n", depth); fflush(stdout); }
    recurse();
}

int main(void)
{
    recurse();
    return 0;
}
```

`实测数据`
`Text`

```text
$ gcc -std=c23 -O0 -S stack_overflow.c -o so.s   # 看帧大小
recurse:
	pushq	%rbp
	movq	%rsp, %rbp
	subq	$96, %rsp         # 每层 96 + 8 = 104 字节

$ stack_overflow.exe
递归 2000 层
...
递归 18000 层
（进程终止）

$ echo %ERRORLEVEL%          （cmd 里的退出码）
-1073741571        # 即 0xC00000FD，STATUS_STACK_OVERFLOW
```

**为什么会停在 18000 到 20000 层之间**：PE 头部写明栈预留 2 MiB
（`dumpbin /headers` 里的 `200000 size of stack reserve`），
`2097152 ÷ 104 ≈ 20165`，与实测区间吻合。
**这里不需要算准**——重点是：桌面上栈用完时，操作系统会明确地终止进程，
给一个能查的错误码，而不是让程序带着被写坏的数据继续跑。

## 4.2 Cortex-M：全局变量被悄悄改写

同一件事在单片机上是另一副样子。下面这份程序在 SRAM 最低处放了一组「哨兵」，
然后无限递归，看会撞上什么。

`C`

```c
/* ovf.c   交叉编译（Cortex-M3）：arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -c ovf.c -o ovf.o
   完整构建与运行（在 WSL 的 Ubuntu 里，链接脚本是 F103C8 的 20 KiB RAM 版）：
     arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O0 -nostartfiles --specs=nosys.specs \
       -T STM32F103C8_FLASH.ld startup_stm32f103xe.s ovf.c -o ovf.elf
     qemu-system-arm -M netduinoplus2 -kernel ovf.elf -nographic \
       -semihosting-config enable=on,target=native */
#include <stdint.h>

static void sh_puts(const char *s)
{
#if defined(__arm__)
    register uint32_t r0 __asm__("r0") = 0x04u;
    register const char *r1 __asm__("r1") = s;
    __asm__ volatile ("bkpt 0xAB" : : "r"(r0), "r"(r1) : "memory");
#else
    (void)s;
#endif
}
static void sh_hex(uint32_t v)
{
    static const char h[] = "0123456789abcdef";
    char b[9];
    for (int i = 0; i < 8; ++i) b[i] = h[(v >> (28 - 4 * i)) & 0xFu];
    b[8] = '\0'; sh_puts("0x"); sh_puts(b);
}
static void sh_dec(uint32_t v)
{
    char b[12]; int i = 11; b[i--] = '\0';
    if (!v) b[i--] = '0';
    while (v) { b[i--] = (char)('0' + v % 10u); v /= 10u; }
    sh_puts(&b[i + 1]);
}

extern uint32_t _sdata, _estack;

volatile uint32_t g_guard[64] = { 0 };     /* 256 字节哨兵，落在 SRAM 最低处 */
static uint32_t depth = 0;

static void recurse(void)
{
    volatile uint32_t pad[8];              /* 每层在栈上写 32 字节 */
    for (int i = 0; i < 8; ++i) pad[i] = depth;

    /* 栈指针已经进到 SRAM 最低的 256 字节时，回头看看哨兵还在不在 */
    if ((uint32_t)(uintptr_t)&pad[0] < (uint32_t)(uintptr_t)&_sdata + 0x100u) {
        uint32_t broken = 0, first = 0;
        for (uint32_t i = 0; i < 64; ++i)
            if (g_guard[i] != 0xA5A50000u + i) { if (!broken) first = i; ++broken; }
        sh_puts("递归 "); sh_dec(depth); sh_puts(" 层，栈指针已经到 ");
        sh_hex((uint32_t)(uintptr_t)&pad[0]); sh_puts("\r\n");
        sh_puts("g_guard[] 被改写 "); sh_dec(broken); sh_puts(" 个字；g_guard[");
        sh_dec(first); sh_puts("] 期望 "); sh_hex(0xA5A50000u + first);
        sh_puts("，实际 "); sh_hex(g_guard[first]); sh_puts("\r\n");
        for (;;) { }                        /* 停在这里，不再递归下去 */
    }
    ++depth;
    recurse();
}

void SystemInit(void) { }
void _init(void) { }

int main(void)
{
    for (uint32_t i = 0; i < 64; ++i) g_guard[i] = 0xA5A50000u + i;
    sh_puts("MSP 初值 "); sh_hex((uint32_t)(uintptr_t)&_estack);
    sh_puts("，.data 起点 "); sh_hex((uint32_t)(uintptr_t)&_sdata);
    sh_puts("，相距 20 KiB\r\n");
    recurse();
    return 0;
}
```

`Text`

```text

    -semihosting-config enable=on,target=native

递归 360 层，栈指针已经到 0x200000f8
```

**没有任何异常，程序继续跑了下去。** 360 层乘以每层 56 字节正好约 20 KiB，
栈指针一路走到 `0x200000f8`，也就是 SRAM 的最底部，
把 256 字节哨兵数组末尾的两个字改成了 `0x00000168`（递归层数）。
如果程序没有自己检查，它会带着这些被改过的全局变量继续运行——
**这就是「跑飞」的典型来源**：一个变量莫名其妙变成别的值，没有报错，没有崩溃点。

## 4.3 为什么单片机上没人拦

桌面上的「护栏页」是 MMU 提供的：操作系统在栈下面留一页不映射，
栈一旦越界就触发缺页异常，进程被终止。
**Cortex-M3 有 MPU（内存保护单元），但默认不启用**，
而且 MPU 的作用是按区域设权限，不能像 MMU 那样给每一层调用单独开一个栈。
因此裸机上的栈溢出只有一个后果：**写到栈底下面的东西上去**。

栈底下是什么，取决于内存布局。这一章的例子是 `.data`/`.bss`；
如果栈顶被链接脚本设到了 SRAM 之外，那就是 2.5 节那种「第一次压栈就 HardFault」。
两种表现完全不同，但根因是同一个：**内存没有护栏，布局是人定的**。

## 4.4 怎么防

栈溢出没法「遇到再修」，只能事先算。三件事按顺序做：

1. **量出每个函数的栈用量**。GCC 有一个不太为人知的选项 `-fstack-usage`，
   编译时给每个函数生成一行记录（`.su` 文件）：

   `实测数据`
   `Text`

   ```text
   $ arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O0 -fstack-usage -c su.c
   $ cat su_O0.su
   su.c:4:5:small	16	static
   su.c:6:5:medium	56	static
   su.c:13:5:big	536	static
   su.c:20:12:recurse	16	static
   su.c:21:5:deep	16	static

   $ arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -fstack-usage -c su.c
   $ cat su_O2.su
   su.c:4:5:small	0	static
   su.c:6:5:medium	32	static
   su.c:13:5:big	512	static
   su.c:21:5:deep	0	static
   ```

   **同一个函数在两个优化等级下用量不同**（`medium` 从 56 降到 32，`small` 从 16 降到 0），
   所以这份表要按实际发布的编译选项生成。带 `volatile int buf[128]` 的 `big` 是 536 字节，
   **一次调用就吃掉 20 KiB SRAM 的 2.6%**——大数组放局部变量在单片机上是危险动作。

2. **把调用链加起来乘最坏情况**。`-fstack-usage` 给的是单个函数，
   实际占用是「当前调用链上所有函数之和」，再加上中断嵌套
   （中断服务函数会在当前栈上继续压栈）。嵌入式项目里常见的做法是
   留出与最坏调用链等量的余量，并把 `_Min_Stack_Size` 写成实际值而不是默认的 `0x400`。

3. **留一个能发现问题的哨兵**。4.2 那份程序里的 `g_guard[]` 就是最简单的栈哨兵：
   在栈底放一段有特征值的内存，定期检查。RTOS 的任务栈检查用的是同一个思路，
   只不过哨兵值固定成 `0xA5A5A5A5` 之类的魔数。

> [!CAUTION]
> **不要用「加大栈」来掩盖栈溢出。** 20 KiB 的 SRAM 里栈、堆、
> 全局变量是同一个池子：栈多占 4 KiB，堆和 `.bss` 就少 4 KiB。
> 真正要修的是那个 536 字节的局部数组（改成 `static` 或全局），而不是把栈顶往上挪。

# 第 5 节 堆：从 `_end` 往上

## 5.1 桌面上的堆：分配粒度

`malloc` 返回的不是「刚好那么多字节」，分配器有自己的最小块与对齐要求。
连续申请几种大小，看地址间隔：

`C`

```c
/* heap_probe.c   编译：gcc -std=c23 -O2 heap_probe.c -o heap_probe.exe
   运行：heap_probe.exe                                                      */
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    size_t sizes[] = { 1, 8, 16, 17, 32, 1000, 4096 };
    void *prev = NULL;
    printf("%8s  %-20s %s\n", "请求", "返回地址", "与上一次的间隔");
    for (unsigned i = 0; i < sizeof sizes / sizeof sizes[0]; ++i) {
        void *p = malloc(sizes[i]);
        printf("%8zu  %-20p", sizes[i], p);
        if (prev) printf(" %td 字节", (char *)p - (char *)prev);
        printf("\n");
        prev = p;
    }
    char *a = (char *)malloc(1);
    char *b = (char *)malloc(1);
    a[0] = 'X'; b[0] = 'Y';
    printf("\n两次 malloc(1) 的间隔：%td 字节，写入后读回：%c %c\n", b - a, a[0], b[0]);
    return 0;
}
```

`实测数据`
`Text`

```text
      请求  返回地址             与上一次的间隔
       1  1fc4fba2420
       8  1fc4fba2440          32 字节
      16  1fc4fba2460          32 字节
      17  1fc4fba2480          32 字节
      32  1fc4fba24a0          32 字节
    1000  1fc4fba24d0          48 字节
    4096  1fc4fba81b0          23776 字节

两次 malloc(1) 的间隔：32 字节，写入后读回：X Y
```

三件事读得出来：

- **小于等于 32 字节的请求，间隔都是 32 字节**：分配器按 16 字节对齐切块，
  再加上自己的一份头信息，所以 `malloc(1)` 实际吃掉 32 字节；
- **`malloc(1000)` 的间隔是 48 字节**（相对上一块），说明它占了 1024 字节的整数倍；
- **`malloc(4096)` 之后地址跳了 23776 字节**：分配器手上没有这么大的连续块了，
  向操作系统要了一块新的（Windows 上是 `HeapAlloc` 背后的虚拟内存保留，
  Linux 上是 `brk` 或 `mmap`）。

**「申请 1 字节，实际占用 32 字节」这件事在小内存设备上是决定性的**：
在 20 KiB SRAM 的单片机上，频繁申请小块内存很快就把堆切碎。
嵌入式的普遍建议是**干脆不用动态分配**，需要什么在编译期定好。

## 5.2 裸机的堆：`sysmem.c` 里的 `_sbrk`

裸机上没有操作系统可以要内存，`malloc` 最后落到 `_sbrk` 这个函数上。
CubeMX 生成的工程里它长这样（`A-教学素材/01-编译器/嵌入式/内存布局与中断/sysmem.c`，
**原样引用，下面是节选**）：

`C`

```c
/**
 * @brief _sbrk() allocates memory to the newlib heap and is used by malloc
 *        and others from the C library
 *
 * @verbatim
 * ############################################################################
 * #  .data  #  .bss  #       newlib heap       #          MSP stack          #
 * #         #        #                         # Reserved by _Min_Stack_Size #
 * ############################################################################
 * ^-- RAM start      ^-- _end                             _estack, RAM end --^
 * @endverbatim
 *
 * This implementation starts allocating at the '_end' linker symbol
 * The '_Min_Stack_Size' linker symbol reserves a memory for the MSP stack
 * The implementation considers '_estack' linker symbol to be RAM end
 */

static uint8_t *__sbrk_heap_end = NULL;   /* 文件里这一行在函数之前，堆的水位线 */

void *_sbrk(ptrdiff_t incr)
{
  extern uint8_t _end; /* Symbol defined in the linker script */
  extern uint8_t _estack; /* Symbol defined in the linker script */
  extern uint32_t _Min_Stack_Size; /* Symbol defined in the linker script */
  const uint32_t stack_limit = (uint32_t)(uintptr_t)&_estack - (uint32_t)&_Min_Stack_Size;
  const uint8_t *max_heap = (uint8_t *)stack_limit;
  uint8_t *prev_heap_end;

  /* Initialize heap end at first call */
  if (NULL == __sbrk_heap_end)
  {
    __sbrk_heap_end = &_end;
  }

  /* Protect heap from growing into the reserved MSP stack */
  if (__sbrk_heap_end + incr > max_heap)
  {
    errno = ENOMEM;
    return (void *)-1;
  }

  prev_heap_end = __sbrk_heap_end;
  __sbrk_heap_end += incr;

  return (void *)prev_heap_end;
}
```

**整段逻辑就是三个链接脚本符号**：

| 符号 | 在 F103C8 上的值 | 用途 |
|---|---|---|
| `_end` | `0x20000720` | 堆的起点，`.bss` 结束之后 |
| `_estack` | `0x20005000` | SRAM 末端，栈顶 |
| `_Min_Stack_Size` | `0x400` | 为栈保留的量（声明性） |

`_sbrk` 把堆顶从 `_end` 往上推，**推到 `_estack - _Min_Stack_Size` 就返回 `-1`**，
`malloc` 于是返回 `NULL`。整个机制里没有操作系统、没有页表，
只有一根会检查边界的指针——而边界是从链接脚本读来的两个常量。

第 2.2 小节那份 `addr.c` 里的 `_sbrk` 就是这套逻辑的最小复刻（少了 `errno` 与
`__PICOLIBC__` 分支），所以那里 `malloc` 能返回真实地址 `0x20000728`。
分配器的完整用法在《07-标准库/A-05-工具与其它：stdlib 与杂项.md》第 1 节，
这里只关心它的边界在哪。

## 5.3 堆用完会怎样

把堆一路推到边界，看到的是「分配失败」而不是「崩溃」。

`C`

```c
/* heap.c   交叉编译（Cortex-M3）：arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -c heap.c -o heap.o
   完整构建与运行：
     arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O0 -nostartfiles --specs=nosys.specs \
       -T STM32F103C8_FLASH.ld startup_stm32f103xe.s heap.c -o heap.elf
     qemu-system-arm -M netduinoplus2 -kernel heap.elf -nographic \
       -semihosting-config enable=on,target=native */
#include <stdint.h>
#include <stdlib.h>

static void sh_puts(const char *s)
{
#if defined(__arm__)
    register uint32_t r0 __asm__("r0") = 0x04u;
    register const char *r1 __asm__("r1") = s;
    __asm__ volatile ("bkpt 0xAB" : : "r"(r0), "r"(r1) : "memory");
#else
    (void)s;
#endif
}
static void sh_hex(uint32_t v)
{
    static const char h[] = "0123456789abcdef";
    char b[9];
    for (int i = 0; i < 8; ++i) b[i] = h[(v >> (28 - 4 * i)) & 0xFu];
    b[8] = '\0'; sh_puts("0x"); sh_puts(b);
}
static void sh_dec(uint32_t v)
{
    char b[12]; int i = 11; b[i--] = '\0';
    if (!v) b[i--] = '0';
    while (v) { b[i--] = (char)('0' + v % 10u); v /= 10u; }
    sh_puts(&b[i + 1]);
}

extern uint32_t _end, _estack;

/* 与 sysmem.c 同一套逻辑，把保留的栈大小写死成 0x400 */
static uint8_t *heap_end = NULL;
void *_sbrk(ptrdiff_t incr)
{
    const uint32_t limit = (uint32_t)(uintptr_t)&_estack - 0x400u;
    if (heap_end == NULL) heap_end = (uint8_t *)&_end;
    if ((uint32_t)(uintptr_t)heap_end + incr > limit) { return (void *)-1; }
    uint8_t *prev = heap_end;
    heap_end += incr;
    return prev;
}

void SystemInit(void) { }
void _init(void) { }

int main(void)
{
    uint32_t ok = 0;
    void *last = NULL;
    sh_puts("_end = "); sh_hex((uint32_t)(uintptr_t)&_end);
    sh_puts("，_estack = "); sh_hex((uint32_t)(uintptr_t)&_estack);
    sh_puts("，为栈保留 0x400\r\n");
    for (;;) {
        void *p = malloc(256);
        if (!p) break;
        last = p; ++ok;
    }
    sh_puts("malloc(256) 成功 "); sh_dec(ok);
    sh_puts(" 次，最后一次给到 "); sh_hex((uint32_t)(uintptr_t)last); sh_puts("\r\n");
    for (;;) { }
}
```

`实测数据`
`Text`

```text
$ qemu-system-arm -M netduinoplus2 -kernel heap.elf -nographic \
    -semihosting-config enable=on,target=native
_end = 0x200006c0，_estack = 0x20005000，为栈保留 0x400
malloc(256) 成功 55 次，最后一次给到 0x20003e78
```

**55 次 `malloc(256)` 之后堆就到头了**：`0x20003e78` 再往上就是
`0x20005000 - 0x400 = 0x20004c00` 这条线。这时 `malloc` 返回 `NULL`，
`_sbrk` 里那一行 `errno = ENOMEM` 就是唯一的事故记录。
**在单片机上，`malloc` 的返回值必须检查**——桌面上内存耗尽很罕见，
20 KiB 的设备上它是一件必然会发生的事。

`实测数据`

| 项 | Windows x86-64 | STM32F103C8 |
|---|---|---|
| 堆的起点 | 由分配器决定，运行期变化 | `_end`，固定值（本例 `0x200006c0`） |
| 向上生长的边界 | 虚拟内存上限 | `_estack - _Min_Stack_Size`（本例 `0x20004c00`） |
| 最小分配粒度 | 32 字节 | 由 newlib 的分配器决定，本例约 272 字节/次 |
| 耗尽时 | `malloc` 返回 `NULL` | `malloc` 返回 `NULL`，`errno = ENOMEM` |
| 碎片化的代价 | 有虚拟内存兜底 | 直接吃掉有限的 SRAM |

> [!NOTE]
> **小结**：堆在桌面上由分配器与操作系统共同管理，最小块远大于请求字节数；
> 在裸机上 `malloc` 一路落到 `_sbrk`，而 `_sbrk` 只看三个链接脚本符号：
> 从 `_end` 往上推，推到 `_estack - _Min_Stack_Size` 就返回失败。
> 栈与堆在同一段 SRAM 里对向生长，中间没有硬件隔离——
> 栈溢出改的是堆或全局变量，堆耗尽只是让 `malloc` 返回 `NULL`。
