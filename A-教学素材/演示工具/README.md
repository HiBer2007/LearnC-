# 演示工具（框架说明）

本目录下的演示程序共用同一个框架：**界面进程负责画与收命令，运算进程负责推进算法**，
两者之间用共享内存传状态、用环回 TCP 传命令。搜索演示按这套框架写成，
数据结构板块的演示照同一套接口做，核心代码不必重写。

框架本身只有一份：`_common/VisualCore.cs`。每个演示自己的代码放在各自目录下，
编译时把两份一起交给编译器。

## 为什么分成两个进程

界面与算法分开之后，各自按自己的节奏走，谁也不等谁。

| 谁 | 管什么 | 节奏 |
|---|---|---|
| 界面进程（默认身份） | 画元素、收鼠标与按钮、把命令发出去 | 固定约 60 帧每秒，与算法快慢无关 |
| 运算进程（`--worker`） | 推进算法、按 sps 限速、把状态写进共享内存 | 自己按时钟推进；不限速时一直推进 |

这样分有三处实际好处。

**一、不限速一档确实能达到全速。** 界面按 60 帧每秒刷新，算法在另一个进程里全速推进，
不会因为界面重绘而慢下来。同一台机器上实测的对照数据见
《搜索演示/README.md》的「实测数据」一节。

**二、界面上显示的 sps 是算法的真实速度。** 如果两者在同一个线程里，
显示的速率里会掺进重绘耗时，那个数字说明不了算法有多快。
分开之后，运算进程用自己的步数与时钟算 sps，界面只负责显示。

**三、界面不会被算法拖住。** 运算进程每一片最多推进 12 毫秒就回来处理命令，
因此暂停、单步在任何速率下都能立刻生效。

### 两者之间传什么

| 内容 | 走哪条路 | 说明 |
|---|---|---|
| 每元素的状态与数值 | **共享内存** | 运算进程写，界面进程按帧读；只在序号变化时读一遍 |
| 命令（装载、配置、速率、运行、暂停、单步、重置、回放、场景同步、退出） | **环回 TCP** | 一行一条，参数用空格分开 |
| 统计小消息（STAT） | **环回 TCP** | 运算进程每 100 毫秒回一条，界面进程用它确认命令已生效 |

共享内存的布局是定长的，两个进程各自算一遍偏移，不靠序列化：

60     int32             1           固定种子
64     int32             1           演示自定义 A

> [!IMPORTANT]
> **每元素的状态与数值走共享内存，命令与统计走 TCP。**
> 把每步的状态也塞进消息里传，不限速这一档会立刻被 IPC 拖死；
> 反过来，把命令写进共享内存则要自己处理竞争与丢失。

### 为什么不用命名管道

一开始命令通道用的是 `NamedPipeServerStream`。同一台机器上实测，
管道里的数据会被攒批：运算进程写出的 `READY` 行，界面进程要过几秒才读到，
命令也因此延迟好几秒才生效。用最小程序单独验证过，命名管道本身能通，
是这套程序里的用法触发了这个问题。

换成环回 TCP（`TcpListener` + `TcpClient`，两端都设 `NoDelay`）之后，
`READY` 在 19 毫秒发出、121 毫秒读到，命令即时生效。

`实测数据`
`Text`

```text
命名管道   READY 于 19 ms 写出，界面进程在 4533 ms 才读到；此后每一条命令都延迟数秒
环回 TCP   READY 于 19 ms 写出，界面进程在 121 ms 读到；命令与统计都在毫秒级往返
```

### 进程怎么退出

| 情形 | 谁先动 | 结果 |
|---|---|---|
| 关掉界面窗口 | 界面进程发 `QUIT` | 运算进程退出；界面最多等 1.5 秒，超时就强制结束 |
| 界面进程崩了 | 连接断开 | 运算进程的读循环结束，自行退出 |
| 运算进程崩了 | 界面进程发现连接断开或进程已退出 | 状态栏写明原因；点「开始」会重新拉起一个 |

**不留孤儿进程**：运算进程还会每隔约一秒检查父进程是否还在，
父进程没了就退出。关窗之后 `Get-Process` 查不到残留进程，见搜索演示的实测记录。

## 怎么编

核心不是独立程序，要和某个演示的 `.cs` 一起编译。

### 方式一：用 .NET Framework 自带的编译器

`PowerShell`

```powershell
cd A-教学素材/演示工具/搜索演示
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe /nologo /target:winexe `
  /out:SearchDemo.exe /r:System.Windows.Forms.dll /r:System.Drawing.dll `
  ..\_common\VisualCore.cs SearchDemo.cs
```

### 方式二：用 dotnet SDK

`PowerShell`

```powershell
cd A-教学素材/演示工具/搜索演示
dotnet build -c Release
```

`SearchDemo.csproj` 里用一行把核心带进来：

`XML`

```xml
<ItemGroup>
  <Compile Include="..\_common\VisualCore.cs" />
</ItemGroup>
```

**源码一律按 C# 5 写**：.NET Framework 自带的 `csc.exe` 只支持到 C# 5，
不用字符串内插、空条件运算符、表达式体成员这类写法，两种编法才能编同一份源码。

### 窗口尺寸

窗口不做 DPI 自动缩放（`AutoScaleMode` 为 `None`），尺寸与字体都按像素给定，
因此在 100%、125%、150% 三档缩放下**文字不会因为缩放而溢出**，
代价是高缩放档下整体由系统拉伸，边缘略糊。

窗口尺寸按内容算：宽度是画布加控制面板加边距，高度取左右两列里更高的那一列
（左列是画布、图例、提示行，右列是控制面板），再加上底部 26 像素的署名条。
**最小尺寸就设成这个内容尺寸**，因此窗口不可能缩到把面板或画布切掉的状态。

**控件高度按字体度量算，不写死常数**：中文字形走字体回退，比西文更高，
早先把标签高度写成 18 像素，状态行的字底边就被切掉了（`LineHeight` 现在按实测字高加 4 像素算）。

## 怎么加一个新演示

1. 建目录 `A-教学素材/演示工具/<演示名>/`，名字用中文，与搜索演示并列。
2. 写 `XxxDemo.cs`，里面实现三个类型：
   - `IVisualEngine`：算法本体。核心只要求它能配置、能重置、能推进一步、能把状态摊成快照。
   - `IVisualScene`：场景与绘制。命中测试、画法、元素上写什么、工具怎么落笔、撤销，都在这里。
   - `IVisualDemo`：把上面两个造出来，给出下拉里的名字、状态栏文案与自测。
3. 入口三行：

   `C#`

   ```csharp
   [STAThread]
   private static int Main(string[] args)
   {
       XxxDemo demo = new XxxDemo();
       return VisualCoreMain.Run(args, demo, delegate { return new VisualFormBase(demo); });
   }
   ```

4. 需要演示专用的按钮时，继承 `VisualFormBase`，重写 `BuildExtraControls`，
   在给定的行号往下加控件，返回新的行号。
5. 建 `.csproj`，照搜索演示那份写，只改 `AssemblyName` 与 `Compile Include`。
6. 自测：实现 `IVisualDemo.RunSelfTest`，用 `SelfTestHost.Check` 打断言。
   `--selftest` 一律在同一个进程中运行，不开窗口，也不启动子进程。
7. README 照《搜索演示/README.md》的骨架写：目录、怎么编、怎么跑、界面怎么用、
   算法或结构说明、实测数据、主题与配色、授权与署名。
8. 颜色只挑语义色槽，不写死色值；要区分状态就同时给一个形状或纹理线索
   （`AddState` / `AddMarker` 的第三个参数是色槽，第四个是线索）。
   署名条与主题切换由基类窗口建好，新演示不必自己写。

**元素的排布方式由场景决定，核心不假设是方格。** 每个元素只有三个字节
（状态、标记、标签）与六个整数属性；方格、树节点、桶、并查集的父指针，
都可以用这套记录表达。

### 速率语义

单位是 **sps**（每秒推进多少步）。滑块是对数刻度，从 0.5 步每秒到不限速，
另有 0.5、1、10、100、1k、10k、不限速七个预设按钮。

| 档位 | 运算进程怎么推进 |
|---|---|
| 有限 sps | 按「目标 sps × 这一片经过的时间」发步数配额，不足一步的余量留到下一片 |
| 不限速 | 每一片推进到用掉时间预算（约 12 毫秒）为止，不等任何一帧 |

实测 sps 由运算进程用真实经过的时间与步数算出，界面只显示这个数。

### 时间线

暂停、继续、单步、重置、**回放到第 n 步**。回放依赖引擎的确定性：
重置之后连续推进 n 步，得到的状态与当初第 n 步时相同。
数据结构演示用它观察结构的生成过程。

### 工具与刷子

场景给出一组 `ToolDescriptor`，界面外壳据此生成单选按钮、刷子尺寸与刷子值控件。
左键落笔、按住拖动连续生效，右键在场景里表示「擦除」（搜索演示的「地形代价」工具
把它解释成「把该格的代价循环加一」）。一次拖动开始与结束会通知场景，
场景在这两处记快照、压撤销栈。

## 主题与配色

### 怎么切

界面右侧面板的「主题」下拉有三个选项：**浅色**、**深色**、**跟随系统**（默认）。
命令行也能指定，启动时生效：

`PowerShell`

```powershell
.\SearchDemo.exe --theme light
.\SearchDemo.exe --theme dark
.\SearchDemo.exe --theme auto
```

选择只记在本进程里，**不写注册表，也不落磁盘**：下次启动仍按 `--theme` 或系统设置来。

「跟随系统」读的是当前用户的一项设置：

`Text`

```text
HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize
    AppsUseLightTheme    REG_DWORD    1 = 浅色，0 = 深色
```

`实测数据`
`Text`

```text
本机实测：该键存在，AppsUseLightTheme = 0（类型 REG_DWORD，读出来是 Int32），
同一键下还有 SystemUsesLightTheme = 0 与 ColorPrevalence = 0。
因此本机 --theme auto 解析为深色。
```

读不到这个键时按浅色处理，不抛异常。

### 对比度

块上的小字（代价、`g`、`h`、`f`、访问次序）与块底色，**两套主题下都不低于 4.5:1**。
比值按 WCAG 的相对亮度公式算：`(L1 + 0.05) / (L2 + 0.05)`，
其中 `L = 0.2126R + 0.7152G + 0.0722B`，每个通道先做 `c <= 0.03928 ? c/12.92 : ((c+0.055)/1.055)^2.4`。

`实测数据`

### 状态用颜色区分，最终路径用折线

**这是作者 2026-10-02 的决定**：状态**只用填充色区分**，
不加叉、角点、三角、圆、加粗边框、斜线纹理这类形状或纹理线索；
唯一保留的图形元素是**最终路径的折线**。

| 状态 | 表示方式 |
|---|---|
| 空地、地形各档、墙、起点、终点、待访问、已访问、当前展开 | **只靠填充色**（色值见上一节的两套色表） |
| 当前展开要更醒目 | 用**更亮的颜色**（浅色主题 `#FF6D00`，深色主题 `#FF8F00`），不加边框 |
| 最终路径 | **折线**，按格心连成，每一段只许横或只许竖 |

图例也跟着简化：只有**色块 + 名称**，不再画形状。

`CueKind` 这套线索机制仍留在核心里（默认 `None`），将来的演示若需要可以直接用，
搜索演示不用它。

#### 折线压在别的颜色上还看得清吗

折线会跨过空地、地形、已访问、墙这些不同底色，**单色做不到在每种底色上都清楚**，
因此折线画两遍：先粗一圈**描边色**，再压上**主色**。两色里总有一色与底色分得开。

| 主题 | 主色 | 描边色 | 画出来的总宽 |
|---|---|---|---|
| 浅色 | `#6A1B9A`（与路径块填充同色） | `#C0C0C0`（中灰） | 3 像素 |
| 深色 | `#CE93D8`（与路径块填充同色） | `#1B1B1B`（深灰） | 3 像素 |

**描边不用接近白的高亮色**：白色描边在浅色主题下会把整条折线渲染成一条白线，
路径的颜色反而看不出来。两套主题都用中性色，靠对比度表选值。

**主色取路径块的填充色**：折线压在路径块上时只剩描边那两道细边，
格上的数字不会被一条宽带子拦腰截断；压在别的填充色上时主色自己就够醒目。

**总宽压在 4 像素以内**：描边 3.0 像素、主色 1.8 像素，露出来的描边每侧不到 1 像素。
早先用的是描边 4.0 加主色 2.6，画出来约 6 像素，压在 20 像素的格子上占掉三分之一。

图形元素按 **≥ 3:1** 判（低于文字那档）。下表给的是「主色与描边色里**较高的那一个**」与底色的对比度：

`实测数据`

|---|---|---|
| 空地 | 9.39:1 | 7.99:1 |
| 地形 2-9 | 7.39:1 | 6.25:1 |
| 墙 | 6.32:1 | 11.72:1 |

| 已访问 | 5.37:1 | 3.38:1 |

#### 格上数字压在折线上怎么读

数字与折线占用的是同一块像素：折线从格心穿过，而数字正好画在格心。
把数字放在折线之后画**还不够**——GDI 画字带抗锯齿，深色数字压在折线的深色描边上，
笔画会被那道描边「切开」，看上去是一团影子。

做法是：路径格上的数字先按上下各 1 像素、用**与路径块同色**画两遍，
把压在字上的那两道细描边在字的位置让开，再把数字本身画上去。
数字因此始终完整，折线在字的两侧照常连着。
只对路径格做（最多几十个格子），每帧多出的绘制量可以忽略。

格上数字用 **Consolas 11 像素粗体**：11 像素的字笔画只有一两个像素宽，
不加粗时笔画芯部的实色像素太少，压在描边上仍然发糊。

> [!IMPORTANT]
> **墙只用纯色填充，不加斜纹，也不加边框。**
> 曾经给墙加过斜纹，结果深色模式下把格子上的数字盖住了，等于用纹理换掉了信息；
> 边框也属于形状线索，按「状态只用颜色区分」的要求一并去掉。

### 标题栏（非客户区）

WinForms 没有给标题栏设深浅的属性，只能走 DWM 互操作。属性号在历史上换过：
Windows 10 1809 到 1903 用 **19**，1909 起用 **20**（`DWMWA_USE_IMMERSIVE_DARK_MODE`）。
程序不猜：先设 20，再用 `DwmGetWindowAttribute` **读回来**，读到的值与设进去的一致就用 20，
否则再试 19。

`实测数据`
`Text`

```text
本机（Windows 11 build 22631）实测，palettecheck 打印的一行：
  dwm attr20 readback=1 attr19 readback=1
即：设 20 之后读回 20 得到 1，设 19 之后读回 19 也得到 1。
两个号在本机都被接受，程序采用 20。浅色主题下 titlebar=0，深色主题下 titlebar=1。

截图取样（窗口 1362x879，标题栏在图像顶部）：
  浅色：y=4..16 处像素约 #F5F2F0，标题栏区域平均亮度 242.5
  深色：y=4..16 处像素约 #21201F，标题栏区域平均亮度 31.8
```

切换主题时立即重设一次属性并重绘，不需要重启程序。

**系统菜单与最大化、最小化按钮**由系统绘制：深色标题栏生效后，
最小化与最大化按钮跟着变成深色样式；左上角图标点开的**系统菜单**
也由 DWM 一并接管。这一项**随系统版本而变**，换一台机器可能不同，读者以自己的机器为准。

### 控件颜色怎么接管

WinForms 的 `ForeColor` 是环境属性，但**不保证每个控件都跟随**，
因此每个控件的两个颜色都由 `ThemePalette` 显式赋值，一个都不留默认值。

| 控件 | 处理 |
|---|---|
| `Label`、`Panel`、`GroupBox` | 底色用 `Surface`，字色用 `PanelText`；标签用实色而不是透明，漏掉的控件才查得出来 |
| `ComboBox` | 另外设 `FlatStyle = Flat`——`DropDownList` 只有平铺样式才认 `BackColor` |
| `Button` | 另外设 `UseVisualStyleBackColor = false` 与 `FlatStyle = Flat`：默认按钮由视觉样式绘制，会**忽略** `BackColor` |
| `NumericUpDown`、`TextBox` | 连同内部的 `UpDownEdit`、`UpDownButtons` 一起显式赋值 |
| `RadioButton`、`CheckBox` | 与标签同样处理 |
| 滑块 | **不用 `TrackBar`**，改用自绘的 `FlatSlider`，原因见下 |
| 撤销按钮 | 放在「工具」分组的最后一行，不与单选钮挤在一起；**始终可点**（置灰文字由系统画，颜色不跟主题走），没有可撤销的操作时用状态行说明 |
| `ToolTip` | 它是独立窗口，不跟着父控件继承，单独赋值 |
| 消息框 | 系统绘制，**改不了**。本演示不使用消息框，出错信息一律写在状态栏上 |

**为什么不用 `TrackBar`**：它的 `ForeColor` 是空实现——
赋任何值读回来都还是 `WindowText`（黑色），深色主题下滑块的刻度与文字就是黑的。
本机实测过「直接赋值」「先底色后字色」「建句柄后赋值」三种顺序，读回来都不变。
因此换成自绘的 `FlatSlider`：轨道、已选段、滑块、刻度全部按主题画，
并且支持鼠标拖动、左右方向键、`Home` 与 `End`。

`实测数据`
`Text`

```text
自绘滑块之前：TrackBar fore=#000000 back=#252525 contrast=1.37  ← 不合格
换成 FlatSlider 之后：FlatSlider fore=#E8E8E8 back=#252525 contrast=12.51  ← 合格
```

### `--palettecheck`：用对比度机器复验

`PowerShell`

```powershell
.\SearchDemo.exe --palettecheck
```

它**只创建窗体对象，不显示窗口，也不起运算进程**，然后：

1. 两种主题各建一次窗体，递归遍历全部控件；
2. 对每个控件算（`ForeColor`，`BackColor`）的对比度；
3. **低于 4.5:1 的列为不合格**，逐行打出来；
4. 另外把 DWM 标题栏的两个属性号各设一次并读回，打印读到的值；
5. 有任何不合格就以**退出码 1** 结束，全部合格退出码 0。

这样「深色下文字发黑」这类组合（对比度接近 1）会直接暴露，不必等人看出来。

`实测数据`
`Text`

```text
palettecheck 只建窗体对象，不显示窗口，也不起运算进程
theme=light controls=73 titlebar=0 attr=20
  dwm attr20 readback=1 attr19 readback=1
  ok   SignatureBar   fore=#1A1A1A back=#FAFAFA contrast=16.67
  ok   Label          fore=#1A1A1A back=#FAFAFA contrast=16.67  [Written By HiBer20…]
  ok   GridCanvas     fore=#1A1A1A back=#F4F4F4 contrast=15.82
  ...（每个控件一行，共 72 行）
theme=light checked=72 low_contrast=0
theme=dark controls=73 titlebar=1 attr=20
  dwm attr20 readback=1 attr19 readback=1
  ok   SignatureBar   fore=#E8E8E8 back=#252525 contrast=12.51
  ok   GridCanvas     fore=#E8E8E8 back=#1B1B1B contrast=14.06
  ...（每个控件一行，共 72 行）
theme=dark checked=72 low_contrast=0
palettecheck result=PASS (全部控件的对比度都不低于 4.5:1)
退出码 0
```

控件这一侧最低的对比度是 12.51:1。

### `--layoutcheck`：排版与连线也用机器判

`PowerShell`

```powershell
.\SearchDemo.exe --layoutcheck
```

它同样只建窗体对象、不显示窗口，逐条判下面四件事，任何一条不通过就非零退出：

| 判什么 | 怎么判 |
|---|---|
| 折线不出现斜段 | 从路径点列生成**实际画出去**的线段，逐段断言「水平或垂直」；四方向与八方向各验证一次 |
| 格上标注放得下 | 五种「元素上标」模式逐一验证，测量最宽的一处文字，与格子边长比较 |
| 图例排版 | 色块右缘与文字左缘至少隔 4 像素；同一行的项共用一条基线；整项换行 |
| 控件 | 不越出父容器、同级不重叠、同一种按钮不重复出现；按钮宽度放得下文字 |

`实测数据`
`Text`

```text
layoutcheck 只建窗体对象，不显示窗口，也不起运算进程
theme=light layout
  note 图例：项数 10，行数 1，行高 23，色块间距 8
  note 折线[四方向] 共 74 段，其中 0 处斜走拆成了 L 形
  note 折线[四方向]：全部线段都是水平或垂直（路径代价 167000，长度 74）
  note 折线[八方向] 共 76 段，其中 32 处斜走拆成了 L 形
  note 折线[八方向]：全部线段都是水平或垂直（路径代价 140880，长度 44）
  note 格上标注：格子 20 像素，字体 Consolas 11 Pixel（行高 13），最宽的一处 [104] 需 18 像素，放不下的格子数 0
theme=dark layout
  （同上）
layoutcheck result=PASS
退出码 0
```

**这套检查抓到的真问题**（都不是靠眼睛看出来的）：状态行文字被标签高度切掉、
面板在窗口缩小时滑到署名条下面、`Label [主题]` 压住 `同进程` 单选钮、
`撤销 Ctrl+Z` 按钮在同一个容器里出现了两个、按钮文字宽度不足。

> [!WARNING]
> **.NET Framework 的 `TextRenderer.MeasureText` 测出来的宽度带一段与字数无关的余量**
> （约 7 像素），而空串又测得 0，因此「减掉空串宽度」这个常见做法在这里无效。
> 等宽字体改用**两次度量之差**求字符宽度：`测("00") - 测("0")` 就是单个字符的宽度，
> 再乘字数。用带余量的数去判「放不放得下」会误报一大片。

## 出错时怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
| 状态栏写「运算进程未连接」 | 运算进程没起来或已退出 | 点「开始」会重新拉起一个，并把当前场景发过去 |
| 状态栏写「读运算进程的消息失败：…」 | 连接断了，界面读线程已退出 | 同上；这一行会带上异常类型与消息 |
| 界面不动、步数不涨 | 连接建立但数据不通 | 用 `--trace` 启动，两个进程的动作会写进 `%TEMP%\visualcore_trace.log` |

`--trace` 是诊断开关，正常使用不必带。
