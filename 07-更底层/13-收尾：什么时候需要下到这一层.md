前面十一篇讲的是这一层有什么。这一篇回答另一个问题：**什么时候真的需要下来。**
多数日常问题在语言与标准库那一层就能解决，只有少数症状是上层解释不了的——
它们有一个共同特征：源码看起来没问题，编译器也不报错，可程序的行为就是不对。

这些症状可以按现场分成五类：链接期报错、程序跑飞、数据不对、体积超、时序不对，
再加上一个横跨几类的「只有 `-O2` 出错」。每一类的第一步都不是打开反汇编，
而是**判断它属于哪一类**——判断对了，工具是现成的；判断错了，
在下层翻半天也找不到上层的一个笔误。

这一篇不引入新机制，它把前面十一篇按「症状 → 工具 → 机制」重排一遍：
拿到一个现象时先判断它属于哪一类，再到对应的那一篇去找原因。
正因为不引入新东西，它可以当作整个板块的索引来用——
每一个结论都指回真正讲它的那一节，而不是在本篇里重讲一遍。

# 第 1 节 症状 → 工具

分类的依据是**错误发生的时刻**：链接期、运行期、还是事后看指标。
时刻决定了现场还在不在，也就决定了能用什么工具。

| 症状 | 发生的时刻 | 现场还在吗 |
|---|---|---|
| 链接期报错 | 构建时 | 完整，报错原文就是现场 |
| 程序跑飞 | 运行中崩溃 | 崩溃现场可能还在（核心转储或调试器在线） |
| 数据不对 | 运行中，无崩溃 | 要靠断言、插桩或调试器重建 |
| 体积超 | 构建后看产物 | 完整，`size` 与 `nm` 随时可查 |
| 时序不对 | 运行中，程序本身正确 | 要靠测量，且测量本身会扰动 |

## 1.1 链接期报错：三种错，三条路

链接错误的信息量最大，因为它把「谁提供、谁需要」摆在了台面上。
三种常见错的措辞完全不同，处理办法也不同。

**第一种：符号没人提供。** 声明写了，定义没链进来。

`C`

```c
/* link_missing.c   只编译：gcc -std=c23 -c link_missing.c -o link_missing.o
 * 链接它才会报未定义符号：gcc link_missing.o -o link_missing.exe */
#include <stdio.h>

int helper(int x);            /* 只有声明，没有定义 */

int main(void)
{
    printf("%d\n", helper(3));
    return 0;
}
```

`实测数据`
`Text`

```text
$ gcc link_missing.o -o link_missing.exe
<MinGW>/.../ld.exe: link_missing.o:link_missing.c:(.text+0x13): undefined reference to `helper'
collect2.exe: error: ld returned 1 exit status

$ cl /nologo /std:c17 /utf-8 link_missing.c
link_missing.obj : error LNK2019: 无法解析的外部符号 helper，函数 main 中引用了该符号
link_missing.exe : fatal error LNK1120: 1 个无法解析的外部命令
```

两份报错给了同样的三件事：**名字**（`helper`）、**谁在用**（`main`，还带段内偏移 `0x13`）、
**错在哪一步**（链接，不是编译）。接下来要查的只有一件事：这个名字该由谁提供。

**第二种：符号提供了不止一份。**

`C`

```c
/* link_dup_a.c   只编译：gcc -std=c23 -c link_dup_a.c -o link_dup_a.o */
int g_shared = 1;             /* 定义 */
int helper(int x) { return x + g_shared; }
```

`C`

```c
/* link_dup_b.c   只编译：gcc -std=c23 -c link_dup_b.c -o link_dup_b.o */
int g_shared = 2;             /* 同一个名字的第二个定义 */
int helper(int x);
int main(void) { return helper(1) + g_shared; }
```

`实测数据`
`Text`

```text
$ gcc link_dup_a.o link_dup_b.o -o link_dup.exe
<MinGW>/.../ld.exe: link_dup_b.o:link_dup_b.c:(.data+0x0): multiple definition of `g_shared';
    link_dup_a.o:link_dup_a.c:(.data+0x0): first defined here
collect2.exe: error: ld returned 1 exit status

$ cl /nologo /std:c17 /utf-8 link_dup_a.c link_dup_b.c
link_dup_b.obj : error LNK2005: g_shared 已经在 link_dup_a.obj 中定义
link_dup_a.exe : fatal error LNK1169: 找到一个或多个多重定义的符号
```

**报错里带两个来源文件与段内偏移**，这句话值得记住：它意味着不必猜是谁重复了，
按它给的 `段+偏移` 找过去就行。

**第三种：库在，但导出表里没有。** 这种错误的措辞与第一种完全相同，
只是原因藏在动态库的导出表里。

`实测数据`

| 报错 | 含义 | 先查什么 |
|---|---|---|
| `undefined reference to 'x'` | 没有任何目标文件提供 `x` | 源文件加进构建了吗；库的顺序对吗 |
| `multiple definition of 'x'` | 提供了两份以上 | 定义是不是写在头文件里了 |
| `LNK2019` | MSVC 的未解析外部符号 | 与 GCC 的 `undefined reference` 同类 |
| `LNK2005` + `LNK1169` | MSVC 的重复定义 | 与 GCC 的 `multiple definition` 同类 |
| `undefined reference` 且库里确实有这个函数 | **导出表里没有它** | `objdump -p` / `dumpbin /exports` 读导出表 |

**在哪一章**：符号形状与绑定强度见《07-更底层/06-符号与链接属性.md》第 1 与第 3 节；
静态库的顺序敏感与动态库的导出表见同章第 6 节；
名字修饰（C++ 里 `helper` 为什么长得不像 `helper`）见
《07-更底层/05-ABI 与调用约定.md》第 5 节。

## 1.2 程序跑飞：先拿到崩溃位置

「跑飞」指程序没有按预期路径继续，通常表现为崩溃、卡死或者复位。
应用侧最常见的是访问冲突，嵌入式侧最常见的是 HardFault。

`C`

```c
/* crash_demo.c   编译：gcc -std=c23 -g crash_demo.c -o crash_demo
 * 一个会跑飞的程序：把空指针当成记录指针用。 */
#include <stdio.h>
#include <stdlib.h>

struct record {
    int  id;
    char name[16];
};

static int read_id(struct record *r)
{
    return r->id;                  /* r 为 NULL 时在这里出事 */
}

int main(int argc, char **argv)
{
    struct record *r = NULL;
    if (argc > 100)                /* 命令行永远给不到 100 个参数 */
        r = malloc(sizeof *r);

    printf("%d\n", read_id(r));    /* 于是这里收到一个空指针 */
    free(r);
    return 0;
}
```

先看它自己留下了什么：

`实测数据`
`Bash`

```bash
$ gcc -std=c23 -g crash_demo.c -o crash_demo && ./crash_demo; echo "退出码 $?"
Segmentation fault
退出码 139
```

**光有退出码还不够。** 让它进调试器，一条批处理命令就能拿到调用栈：

`实测数据`
`Bash`

```bash
gdb -batch -ex run -ex "bt" -ex "info registers rip" ./crash_demo
```

`实测数据`
`Text`

```text
Program received signal SIGSEGV, Segmentation fault.
0x0000555555555199 in read_id (r=0x0) at crash_demo.c:13
13	    return r->id;                  /* r 为 NULL 时在这里出事 */
#0  0x0000555555555199 in read_id (r=0x0) at crash_demo.c:13
#1  0x00005555555551d8 in main (argc=1, argv=0x7fffffffde38) at crash_demo.c:22
rip            0x555555555199      0x555555555199 <read_id+16>
```

**这份输出里最有价值的是括号里的 `r=0x0`。** 它把「崩在哪一行」与「为什么崩」一起给出了：
参数是空指针，因此下一层不必再查。`.c:13` 也说明 `-g` 不能省——
没有调试信息时这里只有地址。

Windows 侧的现场是另一种形态：

`实测数据`

| 平台 | 现场 | 说明 |
|---|---|---|
| Linux / WSL | `Segmentation fault`，退出码 **139** | 信号 11 |
| Windows | 退出码 **`0xC0000005`** | 访问冲突；控制台里看不到信号名 |
| Windows，输出被缓冲时 | **崩溃前的 `printf` 全部丢失** | 缓冲区没机会刷新 |

最后一行是排查时最容易上当的地方：**打印调试法在崩溃面前会丢现场**。
`crash_demo` 里那一行 `printf` 的输出在 Windows 上就消失了。
这一点在《02-调试器/01-原理与使用.md》第 3.1 小节有专门的实测。

嵌入式侧的「跑飞」有自己的形态。在 STM32F103C8（Cortex-M3）最小系统板上实测过这样一个病例：

`实测`

| 项 | 现场 |
|---|---|
| 起因 | 链接脚本照抄了 F103xC 的版本（RAM 48K），而板子是 C8（RAM 20K） |
| `_estack` 算出来 | `0x2000C000`，**超出 20 KiB RAM** |
| 复位后现场 | `current mode: Handler HardFault`，`pc = 0x08000314` |
| 结果 | 第一次压栈就越界，连 `main` 都进不去 |

**「连 `main` 都进不去」是嵌入式特有的症状**：应用侧的崩溃至少还有调用栈，
裸机侧的崩溃可能发生在栈指针被用之前，那时连 `main` 都没开始执行。
判断这一类的办法见《07-更底层/07-链接脚本与启动代码.md》第 5 节。

**在哪一章**：崩溃现场与退出码见《02-调试器/01-原理与使用.md》第 10.1 小节；
HardFault 与栈溢出的机制见《07-更底层/01-对象在哪里：栈、堆与静态区.md》第 2 与第 4 节；
链接脚本与 `_estack` 见《07-更底层/07-链接脚本与启动代码.md》第 2 节。

## 1.3 数据不对：三种来源，三种工具

数据不对时没有任何现成的现场，这是它比崩溃难查的原因。
按来源分，它只有三种可能，每种对应一件工具。

| 来源 | 表现 | 工具 |
|---|---|---|
| **读到了不该读的地方** | 值随机、换优化等级就变 | ASan（地址层面）、UBSan 的 `bounds`（下标层面） |
| **被不该动的人改了** | 值在某个时刻突变 | 数据断点（watchpoint） |
| **编译器按别的假设生成了代码** | 换编译器或换优化等级就变 | `-O0` 对照、`-fno-strict-aliasing`、`volatile` |

第一种有一个「静默」的典型：**越界写在结构体内部**，地址仍在同一个 `malloc` 块里，
ASan 的红区在块外，于是它一声不响，只有 UBSan 的下标检查能报出来。

`C`

```c
/* san_intraobj.c   编译运行（Linux）：gcc -std=c2x -g -O2 -fsanitize=address,undefined san_intraobj.c -o san_intraobj && ./san_intraobj
 * 越界写在结构体内部：地址仍在同一个 malloc 块里。 */
#include <stdio.h>
#include <stdlib.h>

struct row {
    int cell[4];
    int last;                  /* 紧跟在数组后面 */
};

int main(void)
{
    struct row *r = malloc(sizeof *r);
    for (int i = 0; i < 4; i++)
        r->cell[i] = i;
    r->last = 999;

    r->cell[4] = -1;           /* 越界写：落在 last 上 */
    printf("last = %d\n", r->last);

    free(r);
    return 0;
}
```

`实测数据`
`Text`

```text
# 只开 ASan：程序安静跑完，最后打印 last = -1（越界写已经改掉了它）
last = -1
退出码 0

# 加上 UBSan：一行报告指出是哪一次下标
san_intraobj.c:18:12: runtime error: index 4 out of bounds for type 'int [4]'
```

同一份源码、同一个越界写：地址检查器沉默，运算检查器报错。
**选工具之前先判断错误属于哪一类**，这一步比工具本身重要。

第二种要用数据断点。它的用法与实测在
《02-调试器/01-原理与使用.md》第 3.3 小节：程序停在「谁写了这个地址」的那一刻，
比排查一百行打印都快。

第三种是最容易被误判成「硬件坏了」的一类，它的判断办法很直接：
**换一档优化再编一遍**。

`实测数据`

| 同一份源码 | `-O0` | `-O2` |
|---|---|---|
| 越界多读一个元素 | 101 | 100 |
| 严格别名写同一个对象 | 2 | 1 |
| `x + 1 > x`（`x` 为 `INT_MAX`） | 0 | 1 |

三组都来自《07-更底层/12-编译器扩展与未定义行为.md》第 6 节，那里有完整的汇编对照。

**在哪一章**：地址与下标的插桩见《07-更底层/12-编译器扩展与未定义行为.md》第 7 节；
数据断点见《02-调试器/01-原理与使用.md》第 8.4 小节；
中断改内存与 `volatile` 的边界见《07-更底层/12-编译器扩展与未定义行为.md》第 6.8 小节。

## 1.4 体积超：先分清看的是哪个数字

体积问题有一个前置陷阱：**看错指标**。文件大小与真正加载的部分常常不是一回事。

`C++`

```cpp
/* size_demo.cpp   编译：g++ -std=c++17 -O2 size_demo.cpp -o size_demo.exe
 * 同一个程序，换优化与链接开关各量一次体积。
 * 注意：-fno-exceptions 与源码里的 try/catch 不能共存，因此用条件编译隔开。 */
#include <cstdio>
#include <string>
#include <vector>

#if defined(__cpp_exceptions) || defined(__EXCEPTIONS) || defined(_CPPUNWIND)
#  include <stdexcept>
#  define HAS_EXCEPTIONS 1
#endif

struct shape {
    virtual ~shape() = default;
    virtual double area() const = 0;
};

struct square : shape {
    double side;
    explicit square(double s) : side(s) {}
    double area() const override { return side * side; }
};

struct circle : shape {
    double r;
    explicit circle(double v) : r(v) {}
    double area() const override { return 3.14159265358979 * r * r; }
};

/* 下面这些函数没人调用：用来观察 --gc-sections 能不能把它们丢掉 */
static double unused_one(double x) { return x * 1.5 + 2.5; }
static double unused_two(double x) { return unused_one(x) / 3.0; }
static int    unused_three(int n) { int s = 0; for (int i = 0; i < n; i++) s += i * i; return s; }
static void   unused_four(void) { std::printf("never\n"); }
static double unused_five(double x) { return unused_two(x) + unused_three(10); }

static double total(const std::vector<shape *> &v)
{
    double s = 0;
    for (shape *p : v)
        s += p->area();
    return s;
}

int main(int argc, char **argv)
{
    std::vector<std::string> names{ "square", "circle" };
    std::vector<shape *> shapes;
    square q(2.0);
    circle c(1.0);
    shapes.push_back(&q);
    shapes.push_back(&c);

#ifdef HAS_EXCEPTIONS
    try {
        if (argc > 100)
            throw std::runtime_error("参数太多");
        std::printf("%s %s %f\n", names[0].c_str(), names[1].c_str(), total(shapes));
    } catch (const std::exception &e) {
        std::printf("异常：%s\n", e.what());
    }
#else
    std::printf("%s %s %f\n", names[0].c_str(), names[1].c_str(), total(shapes));
#endif
    return 0;
}
```

七种构建各量一次，其中 `-Os` 那一行要多看一眼：

`实测数据`

| 构建 | 文件大小 | `.text` | `.data` |
|---|---|---|---|
| `-O2` | 19056 | 7516 | 968 |
| `-Os` | **23392** | **6794** | 976 |
| `-O2 -ffunction-sections -fdata-sections -Wl,--gc-sections` | 18952 | 7508 | 960 |
| `-O2 -fno-rtti` | 18888 | 7503 | 920 |
| `-O2 -fno-exceptions -fno-rtti` | 17264 | **4634** | 768 |
| `-O2 -s`（strip） | **14648** | 7516 | 968 |
| `-O2 -static` | **985048** | —— | —— |

三个数字要分开读：

- **`-Os` 的文件反而更大**（23392 对 19056），但它的 `.text` 确实更小（6794 对 7516）。
  大出来的部分是**页对齐填充**：`-Os` 版里 `.text` 结束的位置把 `.rodata` 推到了下一个 4 KiB 边界，
  `readelf -S` 里两个版本的节偏移一看就明白。
- **`-s` 只删符号表**：`.text` 一个字节都没变，文件小了 4 KB 多，调试信息与断点一起消失。
- **`-static` 涨到 985 KB**：静态链接把运行库整段拉进产物。
  嵌入式侧对应的选择是「要不要带 `printf` 这种重量级库函数」。

嵌入式侧看的是同一件事的另一面：**flash 里真正被烧进去的字节数**。
同一份固件在四个优化档下的占用：

`实测`

| 优化 | text（flash） | data | bss（RAM） | 合计 |
|---|---|---|---|---|
| `-O0` | 3564 | 8 | 1728 | 5300 |
| `-O1` | 2644 | 8 | 1720 | 4372 |
| `-O2` | 2520 | 8 | 1720 | 4248 |
| `-Os` | **2368** | 8 | 1720 | **4096** |

**flash 侧省了 34%，RAM 侧几乎不动**——省下来的是代码，不是数据。
这条结论在别处也成立：想省 RAM 要动的是数据结构与栈，不是优化等级。

MSVC 侧的同一件事要看段而不是文件大小，因为一个 154 KB 的 exe 里绝大部分是固定内容：

`实测数据`

| 构建 | 文件大小 | `.text` 虚拟大小 |
|---|---|---|
| `cl /O2` | 157696 | 98384（`0x18050`） |
| `cl /O1` | 157696 | 98720（`0x181A0`） |

**文件大小完全相同，段大小不同**：这一对数字说明「看文件大小判断优化效果」在小程序上无效。

**在哪一章**：段与 `size` 见《07-更底层/01-对象在哪里：栈、堆与静态区.md》第 1 节；
对齐与填充见《07-更底层/02-对齐、填充与缓存.md》第 2 节；
C++ 的虚表、RTTI 与异常的体积代价见《07-更底层/09-C++ 对象布局与它的硬件代价.md》第 6 节；
优化等级与体积的取舍见《03-构建工具链/05-优化等级.md》第 4.6 小节。

## 1.5 时序不对：测量本身也要设计

时序问题的特点是「程序逻辑没错，快慢不对」。它有两个方向：
绝对速度不够，或者时间抖动太大。

`C`

```c
/* time_demo.c   编译：gcc -std=c2x -O2 time_demo.c -o time_O2（-O0 版换输出名）
 * 同一份计算，带参数运行会往循环里插 200 行打印。 */
#include <stdio.h>

#define N 500000000

int main(int argc, char **argv)
{
    long long acc = 0;
    for (int i = 0; i < N; i++) {
        acc += i % 7;
        if (argc > 1 && (i % 2500000) == 0)     /* 打开这个开关：循环里多一次打印 */
            printf("i = %d\n", i);
    }
    printf("acc = %lld\n", acc);
    return 0;
}
```

同一台机器上各跑五轮，掐表用的是 `date +%s.%N`：

`实测数据`

| 构建 | 五轮耗时（秒） | 极差 |
|---|---|---|
| `-O0` | 0.754 / 0.760 / 0.753 / 0.753 / 0.758 | 0.007（约 1%） |
| `-O2` | 0.388 / 0.395 / 0.352 / 0.401 / 0.370 | 0.049（约 14%） |
| `-O3` | 0.257 / 0.262 / 0.259 / 0.263 / 0.259 | 0.006（约 2%） |
| `-O2`，循环里插 200 行打印 | 0.400 / 0.417 / 0.427 / 0.401 / 0.422 | 0.027（约 7%） |

三件事值得记下来：

- **优化等级带来的差距是真实且巨大的**：0.754 秒到 0.257 秒，接近三倍。
- **抖动也同样真实**：`-O2` 那一行极差 14%，说明有缓存与调度在干扰。
  比较两个版本时要跑多轮看极差，不要用单次结果下结论。
- **打印的代价不只在打印本身**：200 行输出只把 0.37 秒推到 0.42 秒，
  但循环里多了一个判断，热点路径的形状变了。高频路径上的打印是排查手段里代价最大的一种。

真板上的对照正好相反：**没有缓存与调度，数字可复现**。
同一次测量里，中断延迟（写 `NVIC_ISPR` 到进 ISR 第一条指令）触发 64 次，
最小值与最大值都是 **21 个周期**（8 MHz 下 2.6 µs）。几个常用操作的周期数：

`实测`

| 操作 | 周期数 | 折合时间 |
|---|---|---|
| `volatile` 读一次外设寄存器 | 9 | 1.125 µs |
| 对齐的 32 位访问 | 8 | 1.00 µs |
| 同一个字逐字节拼起来 | 18 | 2.25 µs |
| 空函数调用（`-O2`，`noinline`） | 8 | 1.00 µs |
| 关中断再开（`cpsid i` / `cpsie i`） | 6 | 0.75 µs |

**「无缓存」的另一面是数字可信**：应用侧要跑很多轮取最小值，
单片机上一次测量就足够，这也是嵌入式里敢直接用周期计数做结论的原因。

**在哪一章**：`volatile` 与寄存器访问的代价见《07-更底层/03-寄存器、位与 volatile.md》第 1 与第 2 节；
缓存与伪共享见《07-更底层/02-对齐、填充与缓存.md》第 3 节；
调用开销与参数传递见《07-更底层/05-ABI 与调用约定.md》第 2 节；
中断延迟与临界区见《07-更底层/10-中断、并发与内存序.md》第 3 节。

## 1.6 只有 `-O2` 出错

这一条不是第六类症状，而是前面几类里最值得单独记住的一种形态：
**同一份源码，`-O0` 正常，`-O2` 出错。** 它几乎总是指向同一批原因。

`实测数据`

| 现象 | 真实原因 | 第一步怎么办 | 在哪一章 |
|---|---|---|---|
| 换 `-O2` 后判断结果翻转 | 有符号溢出等 UB 被当成前提 | 加 `-fwrapv` 试一次；开 UBSan | 《07-更底层/12-编译器扩展与未定义行为.md》第 6.3 小节 |
| 换 `-O2` 后数组读到别的值 | 越界访问让循环被改写 | 开 ASan 与 UBSan | 《07-更底层/12-编译器扩展与未定义行为.md》第 6.4 小节 |
| 轮询循环不再退出 | 缺 `volatile`（不是 UB） | 查这块内存谁会改；补 `volatile` | 《07-更底层/03-寄存器、位与 volatile.md》第 2 节 |
| 两个指针指向同一处却读不到新值 | 严格别名 | 加 `-fno-strict-aliasing` 试一次 | 《07-更底层/12-编译器扩展与未定义行为.md》第 6.7 小节 |
| 判空代码被跳过 | 解引用之后才判空 | 把判空提到解引用之前 | 《07-更底层/12-编译器扩展与未定义行为.md》第 6.5 小节 |
| 浮点比较结果自相矛盾 | `-ffast-math` 一类开关 | 去掉该开关再编一次 | 《07-更底层/12-编译器扩展与未定义行为.md》第 6.9 小节 |

**第一步为什么是「换一档优化」而不是「读汇编」**：换档只要一条命令，
而且结果立刻能证明问题属于哪一类。读了半小时汇编才发现是上层一个越界，代价太大。

> [!TIP]
> **二分定位的三种切法**，按代价从小到大：
> 换优化等级（`-O0` / `-O1` / `-O2` / `-Og`）；
> 加开关试（`-fwrapv`、`-fno-strict-aliasing`、`-fno-delete-null-pointer-checks`）；
> 把可疑文件单独编成 `-O0` 再链接进来。三种都只是定位手段，不是修法。

# 第 2 节 嵌入式读者的一条最短路径

这一节给出一条读法：**假设你的目标是给一块 STM32 写一个能用的外设驱动**，
从「对象放在哪里」一路读到「没有内核时那些接口由谁提供」。这七个名字在
《07-更底层/00-导读：什么叫更底层.md》第 5.3 小节出现过一次，本节把每一步要解决的问题补上。

| 顺序 | 读哪一篇 | 解决的问题 | 读完之后能回答 |
|---|---|---|---|
| 1 | `01-对象在哪里：栈、堆与静态区` | 地址空间长什么样 | flash、SRAM、外设寄存器区各在哪一段；栈顶是谁定的 |
| 2 | `02-对齐、填充与缓存` | 寄存器映射与结构体布局 | 为什么寄存器结构体要用 `volatile` 成员、`packed` 的代价是多少 |
| 3 | `03-寄存器、位与 volatile` | 怎么读写寄存器 | `*(volatile uint32_t *)0x4001080C` 的每一部分为什么必须有；少了 `volatile` 会怎样 |
| 4 | `04-字节序与数据表示` | 多字节数据怎么摆 | 一个 32 位寄存器拆成四个字节时，谁在前；类型双关怎么写才合法 |
| 5 | `07-链接脚本与启动代码` | 程序怎么从复位走到 `main` | 向量表为什么在 flash 最前面、`.data` 怎么搬到 RAM、`_estack` 从哪来 |
| 6 | `10-中断、并发与内存序` | 中断与主循环怎么配合 | 中断里的变量主循环为什么看不见、临界区怎么写、为什么需要屏障 |
| 7 | `11-系统调用：程序与内核的边界` | 那些标准库接口在裸机上由谁提供 | `printf` 为什么一个字都不打印、`_write`/`_sbrk` 这些桩函数是谁写的、semihosting 怎么成了打印通道 |

前四篇是一条线：**地址 → 布局 → 寄存器 → 数据表示**。
它对应写一个驱动的全过程——先知道寄存器在哪，再决定用什么类型去访问它，
然后用 `volatile` 保证每次访问都真的发生，最后处理寄存器里的数据。

第五、六篇是另一条线：**启动 → 中断**。
一个驱动要真正跑起来，前面必须有正确的向量表与内存搬运；
要真正稳下来，后面必须有正确的临界区与内存序。

**第七篇收尾**：驱动跑起来了，可它一旦要打印、要 `malloc`，那些接口在裸机上就没有人实现——
`_write`、`_sbrk` 这些桩函数正是「没有内核时的系统调用」，而 semihosting 是把打印接到调试器上的另一条通道。

```mermaid

    B --> C["用什么类型访问它"]

    D --> E["数据怎么解读"]
    E --> F["中断怎么进来"]
    F --> G["中断与主循环怎么共享数据"]
```

# 第 3 节 什么时候不必下到这一层

这一层的能力很强，代价也很明确：读汇编要时间，改链接脚本要重新验证整个内存布局，
而这两件事都容易把注意力从真正的问题上带走。下面四条标准用来判断「该不该下来」。

## 3.1 标准一：上层有没有做同一件事的工具

**同一个错误，上层有工具能抓，就不必自己读汇编。** 最典型的例子是下标越界。
标准库给了 `at()`，编译器给了 `_GLIBCXX_ASSERTIONS`，两者都会做下标检查——
它们的代价，用同一份「1024 个元素、反复遍历」的负载量一次：

`实测数据`

| 构建 | 三次耗时（秒） |
|---|---|
| `-O2`，`v[i]` | 0.025 / 0.027 / 0.028 |
| `-O2`，`v.at(i)` | 0.027 / 0.024 / 0.024 |
| `-O2`，`v[i]` + `-D_GLIBCXX_ASSERTIONS` | 0.026 / 0.024 / —— |
| `-O0`，`v[i]` | 0.306 / 0.290 |
| `-O0`，`v.at(i)` | 0.651 / 0.651 / 0.646 |

**在 `-O2` 下三者的区间完全重叠，量不出差别**——检查被提到了循环外面，
或者与内存访问的开销相比可以忽略。只有关掉优化才看得出 2.2 倍的差距。

> [!TIP]
> **这条实测的用法**：抓越界的第一步是打开标准库自带的下标检查，
> 而不是学会读 `movslq` 与 `cmp`。检查的成本在优化打开后往往测不出来，
> 而它抓到的错误，读汇编要读很久才能看出来。

## 3.2 标准二：症状能不能在上一层复现

**能写出最小复现，就不要读产物。** 判断顺序是：

| 顺序 | 做法 | 什么时候够用 |
|---|---|---|
| 1 | 写一个十行的最小复现 | 大多数逻辑错误 |
| 2 | 打开 `-Wall -Wextra` 与 `/W4` | 类型不匹配、未使用、可疑写法 |
| 3 | 打开 `assert` 与 sanitizer | 越界、溢出、空指针、竞争 |
| 4 | 进调试器看调用栈与变量 | 崩溃与数据被改 |
| 5 | 读反汇编 | 前面四步都排除了，才轮到它 |

前四步都在语言与工具层，只有第五步属于「下到这一层」。
**顺序不能颠倒**：先读汇编再回头发现是一个 `-Wall` 就能报出来的笔误，是最常见的浪费。

## 3.3 标准三：问题是设计问题还是机制问题

有些症状看起来在底层，实际在设计层。

`实测数据`

| 症状 | 底层的解释 | 更该先做的 |
|---|---|---|
| 固件超过 flash 容量 | 段布局与优化等级 | 先看 `nm --size-sort` 里最大的几个符号：通常是一个被链进来的库函数 |
| RAM 不够用 | 栈与堆的分配 | 先看数据结构：一个没用到的缓冲区常常就是答案 |
| 时间抖动大 | 缓存与调度 | 先看算法与分配：循环里的 `malloc` 比缓存行对齐更致命 |
| 换个编译器就崩 | ABI 与 UB | 先看有没有依赖 UB 或布局假设的代码（第 12 章） |

**这四条的共同点**：底层的解释都成立，但改底层不是最短路径。
真相在「哪一个符号占了这么大」这类问题上，`nm` 比链接脚本快得多。

## 3.4 标准四：有没有标准件直接给答案

语言与标准库已经把一部分「以前必须下到这一层」的事收了上来：

`实测数据`

| 需求 | 以前的做法 | 现在写什么 |
|---|---|---|
| 保证对齐 | 手写填充数组 | `alignas(64)` |
| 抓越界 | 手工插检查 | `at()`、`-D_GLIBCXX_ASSERTIONS` |
| 抓溢出 | 手写判断 | `__builtin_add_overflow` 家族，或宽类型再判范围 |
| 抓空指针 | 手工加断言 | `-fsanitize=null`、`assert` |
| 原子访问 | 手写临界区 | `std::atomic`、`_Atomic` |
| 编译期检查 | 运行时断言 | `static_assert` |
| 标记可疑调用 | 注释提醒 | `[[nodiscard]]` |

**这张表里的每一行，都把一件底层的事变成了一行上层代码。**

## 3.5 反过来：什么时候必须下来

四条标准划出的是「不必」的边界，边界之外有四件事是上层解决不了的：

| 必须下来的情形 | 为什么上层解决不了 | 去哪一章 |
|---|---|---|
| 程序根本没进 `main`，或复位后立刻 HardFault | 这时还没有 C 的运行环境 | 第 7 章 |
| 链接脚本、内存布局、向量表位置 | 语言里没有「地址空间」这个概念 | 第 7 章 |
| 中断改了内存而主循环看不见 | 编译器看不见中断 | 第 3 章、第 10 章 |
| 换编译器/优化等级才出错，且已排除上层原因 | 需要看优化器用了哪条假设 | 第 12 章 |
| 两段代码之间的二进制接口对不上 | ABI 不在语言里 | 第 5 章 |
| 对象布局决定的大小与偏移 | 布局是实现细节 | 第 9 章 |

> [!IMPORTANT]
> **判断标准只有一条：这个问题的答案，语言与标准库有没有规定？**
> 规定了，就在上层解决；没规定，才轮到这一层。
> 本章第 1 节的每一行「在哪一章」，都是按这条标准分出来的。

# 第 4 节 一页速查：全板块十四篇

`实测数据`

# 第 5 节 速查表

`实测数据`

| 常用件 | 一句话用途 | 典型坑 |
|---|---|---|
| `size 产物` | 看 `text`/`data`/`bss` 三段 | 文件大小含符号表与对齐填充，判断占用要看段 |
| `nm 产物` | 看符号与绑定 | 小写是内部链接；C++ 名字是修饰名 |
| `nm --size-sort -S` | 按大小排符号 | 最大的往往是意外链进来的库函数 |
| `objdump -d` | 反汇编 | 要配 `--no-show-raw-insn` 才好读；`-S` 可以混排源码 |
| `objdump -h` | 看段布局 | 与 `readelf -S` 的偏移一起看才能发现页对齐填充 |
| `objdump -p` | 看动态库的导出表 | 符号表里有不等于导出表里有 |
| `readelf -S` | 看节的偏移与大小 | 判断「文件大而段不大」的必用工具 |
| `dumpbin /exports` | MSVC 侧的导出表 | 与 `objdump -p` 读的是同一张表 |
| `dumpbin /headers` | 看 PE 的段虚拟大小 | 小程序的 exe 文件大小几乎固定，只有段大小有区别 |
| `gdb -batch -ex run -ex bt` | 批处理拿到崩溃调用栈 | 没有 `-g` 就只有地址 |
| `-g` | 生成调试信息 | 与优化不冲突，但优化会让行号跳跃 |
| `-Wall -Wextra` / `/W4` | 打开警告 | `-Waggressive-loop-optimizations` 只在优化打开时出现 |
| `assert` | 运行时断言 | `NDEBUG` 下会被去掉 |
| `-fsanitize=address` | 抓越界、释放后使用、泄漏 | MinGW 上没有 `libasan`，要在 Linux 侧跑 |
| `-fsanitize=undefined` | 抓溢出、移位、空指针、下标 | 默认只报告；结构体内部越界只有它能抓 |
| `-fsanitize=address,undefined` | 开发期推荐配置 | 约 20 倍时间代价 |
| `-fwrapv` / `-fno-strict-aliasing` | 把两类 UB 变回定义行为 | 只用于定位，不要长期开着发布 |
| `-O0` 与 `-O2` 各编一遍 | 判断问题是否属于 UB | 最便宜的第一步二分 |
| `-Os` | 减小代码体积 | 文件可能反而更大（页对齐），要看 `.text` |
| `-ffunction-sections -fdata-sections -Wl,--gc-sections` | 丢掉没人用的函数与数据 | 没有 `KEEP` 时会被误删的中断向量表 |
| `-fno-exceptions -fno-rtti` | 去掉 C++ 的两大运行时开销 | 源码里用了 `try` 就编不过 |
| `strip` / `-s` | 去掉符号表 | 文件变小，段不变，调试信息一起消失 |
| `volatile` | 让每次访问都真的发生 | 不是原子，也不保证顺序（第 10 章） |
| `alignas` / `_Alignas` | 标准写法的对齐 | 与 `__declspec(align)` 混用时注意哪一套生效 |
| `std::atomic` / `_Atomic` | 原子访问与内存序 | 在 MCU 上是 `ldrex`/`strex` 加屏障，有周期代价 |
| `at()` / `-D_GLIBCXX_ASSERTIONS` | 标准库自带的下标检查 | 只在违反时才付代价，`-O2` 下常常测不出差别 |
| 链接脚本的 `LENGTH` | 声明 RAM 与 flash 的大小 | 写大了不会报错，复位后立刻 HardFault |
| `mww` / `mdw`（OpenOCD） | 直接读写目标内存 | 调试器同一时刻只能被一个进程占用 |
