《07-更底层/10-中断、并发与内存序.md》章节讲的是硬件可以在任意两条指令之间插进来。
本章讲方向相反的另一件事：**程序自己把控制权交给内核**。
中断是硬件打断程序，系统调用是程序主动请求内核；两者都是态切换，发起方却正好相反。

桌面程序与裸机程序之间那些差别——`printf` 能不能打出字、`malloc` 能不能拿到内存、
程序走到最后谁替它收尾——最后都落在同一处：**有没有一个内核可以请求**。
桌面上的程序碰不到屏幕、磁盘和网卡，它只能提出请求，由内核替它完成；
裸机上没有内核，标准库的同一批接口下面就必须有人补上一组桩函数。

本章把这条边界从头走一遍。x86-64 那一侧看 `syscall` 指令与真实反汇编，
再用 `strace` 数清楚一次 `printf` 到底走了几次系统调用；
Windows 那一侧顺着 `WriteFile` 往下读到 `ntdll` 里那段 `mov r10, rcx` 加 `syscall`；
最后回到裸机，在真板上演示同一份源码只换一个链接选项，
一边一个字都打不出来，一边正常输出。数字来自三处：WSL Ubuntu 里的 `strace` 与 `objdump`、
本机 Windows 上的 `dumpbin`，以及一块 STM32F103C8 上的实测；这一层看不到的地方一律标 `待确认`。

# 第 1 节 特权级与态切换

## 1.1 一条 `printf` 里藏着的两次世界切换

桌面上的程序写不出一个字到屏幕上。它调用 `printf`，`printf` 把字符塞进一块缓冲区，
缓冲区满了以后调用 `write`，而 `write` 里的那条指令会让 CPU 切换到另一个世界——
内核。字符真正出现在终端上，是内核里的驱动做的。

这件事在源码里完全看不见：`printf("hi\n")` 与 `x = x + 1` 长得一样，都是普通函数调用。
但两者的代价差两个数量级，原因就在「要不要切换」。
下面这份程序把同一个循环做两遍：一遍只调本文件里的函数，一遍每次都调 `getpid()`，
后者的返回值只能来自内核。

`C`

```c
/* WSL Ubuntu 侧（x86-64 Linux 专用，Windows 上缺 clock_gettime64 链接不过）：
   syscost.c —— 态切换的代价
   同一个循环里做两件事：一次普通函数调用，一次 getpid()（一次真正的态切换）。
   用 clock_gettime 的单调时钟计时，两边各做 1000 万次。
   gcc -O2 -std=c2x syscost.c -o syscost */
#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <time.h>
#include <unistd.h>

static long g_sink;

__attribute__((noinline)) static long local_call(long x)
{
    return x + 1;
}

static double now_sec(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec + (double)ts.tv_nsec / 1e9;
}

int main(void)
{
    const long N = 10000000;
    double t0, t1;

    t0 = now_sec();
    for (long i = 0; i < N; ++i) {
        g_sink += local_call(i);
    }
    t1 = now_sec();
    printf("普通函数调用   %ld 次：%.3f s（每次 %.2f ns）\n", N, t1 - t0, (t1 - t0) / N * 1e9);

    /* getpid 每次都要进内核：返回值的唯一来源是内核里的进程表 */
    t0 = now_sec();
    for (long i = 0; i < N; ++i) {
        g_sink += getpid();
    }
    t1 = now_sec();
    printf("getpid 系统调用 %ld 次：%.3f s（每次 %.2f ns）\n", N, t1 - t0, (t1 - t0) / N * 1e9);
    return 0;
}
```

`实测数据`
`Bash`

```bash
$ ./syscost
普通函数调用   10000000 次：0.003 s（每次 0.26 ns）
getpid 系统调用 10000000 次：0.456 s（每次 45.56 ns）
$ ./syscost
普通函数调用   10000000 次：0.003 s（每次 0.27 ns）
getpid 系统调用 10000000 次：0.453 s（每次 45.33 ns）
```

**同一个循环，换成进内核的那一次，每次多花约 45 ns（约 170 倍）。**
`getpid()` 没有被 libc 缓存，这一点可以再确认一次：

`实测数据`
`Bash`

```bash
$ strace -c -e trace=getpid ./syscost_small     # 把循环次数改成 100 再编一份
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.000889           8       100           getpid
------ ----------- ----------- --------- --------- ----------------
100.00    0.000889           8       100           total
```

循环 100 次，内核里就真的发生了 100 次 `getpid`。
45 ns 里做的事不少：保存用户态的现场、换到内核栈、按系统调用号查表、
执行、把结果写回寄存器、再切回来。

## 1.2 Cortex-M：只有 Handler 与 Thread 两种态

Cortex-M 没有「用户态程序请求内核」这套东西，它只有两个**执行态**：

| 态 | 什么时候在里面 | 栈用哪个 | 权限 |
|---|---|---|---|
| **Thread** | 复位之后、`main` 与主循环 | 默认 MSP，可以切到 PSP | 默认特权级 |
| **Handler** | 任何一个异常或中断的服务函数里 | MSP | 特权级 |

硬件在异常进入时自动换成 Handler 态，退出时自动换回 Thread 态——
也就是第 10 章讲的那套压栈与 `EXC_RETURN` 机制。**这个切换是硬件做的，没有软件入口。**
想知道当前在哪个态，读 `xPSR` 的低 9 位（IPSR）就够了。

`实测数据`
`Text`

```text
# 真板（STM32F103C8）停住时，OpenOCD 打印的现场
[stm32f1x.cpu] halted due to debug-request, current mode: Thread
xPSR: 0xa1000000 pc: 0x08006bc6 msp: 0x20004ff8      ← 主循环 for(;;) 里
[stm32f1x.cpu] halted due to debug-request, current mode: Handler HardFault
xPSR: 0x21000003 pc: 0x080002b4 msp: 0x20004fd0      ← 越界写之后的 HardFault
```

| 现场 | `xPSR` | IPSR（bit 8:0） | 态 |
|---|---|---|---|
| 主循环里的 `for(;;)` | `0xa1000000` | 0 | Thread |
| 越界写之后 | `0x21000003` | 3（HardFault） | Handler |

两次都停在同一条 `for(;;)` 循环上，唯一的区别是第二次的 IPSR 变成了 3。
`0x21000003` 与 `0xa1000000` 的差别还说明了一件事：
进入 Handler 时，`xPSR` 里的标志位被清掉了（`0xa1` 里的 N、C 位不见了），
只有 T 位（bit 24，Thumb）与 IPSR 留着。

Thread 态默认跑在**特权级**，程序可以直接写 `NVIC`、`SYST_RVR`、`DWT` 这些内核寄存器——
第 10 章测中断延迟时就是这么做的（`*(volatile uint32_t *)0xE000E100u = ...`），
程序全程在 Thread 态，没有任何人拦它。Cortex-M 只在 `CONTROL` 寄存器的 `nPRIV` 位置 1 之后，
Thread 态才降为非特权级；那时访问内核寄存器会触发故障，这才是「用户态」。
**常见的裸机固件全程特权级，所以「进内核」这件事在 Cortex-M 上根本不存在。**

## 1.3 x86-64：ring 0 与 ring 3

x86 的特权级叫 **ring**，一共有四个（0 到 3），现代系统只用了两个：

| ring | 谁在跑 | 不能做什么 |
|---|---|---|
| **0** | 内核 | —— |
| **3** | 普通程序 | 不能执行 `in`/`out` 等特权指令，不能改页表基址，不能关中断，不能碰别的进程的地址空间 |

从 ring 3 到 ring 0 的切换由 `syscall` 指令发起（第 2 节详述），
硬件在这一刻做的事与 Cortex-M 的异常进入很像：
把返回地址与标志位存到寄存器里，从内核预先登记的入口地址开始执行，
栈也从用户栈换成内核栈。区别在于**方向与发起方**：

| | 中断 / 异常 | 系统调用 |
|---|---|---|
| 谁发起 | 硬件（外设、定时器、错误） | **程序自己**（一条指令） |
| 什么时候发生 | 任意两条指令之间，不可预期 | 程序说了算，位置固定 |
| 入口地址从哪来 | 向量表 | 内核在启动时写进一个专用寄存器 |
| Cortex-M 上的对应物 | 异常进入 → Handler 态 | **没有**（裸机全程特权级） |
| x86-64 上的对应物 | 中断 → ring 0 | `syscall` → ring 0 |

第 10 章那句「中断随时可能在任意两条指令之间插进来」说的是左列；
右列是程序主动排好的，所以调用点固定、可预期，代价也可预估（上表测得的 45 ns）。

## 1.4 哪些操作必须进内核

判断标准一句话：**这件事需要碰「不属于这个程序」的东西吗。**
需要，就必须由内核代办。

| 事情 | 为什么必须进内核 | 对应的系统调用（x86-64 号） |
|---|---|---|
| 往终端、文件、管道写字 | 设备与文件系统状态由内核维护 | `write`（1） |
| 申请内存 | 地址空间布局由内核决定 | `brk`（12）、`mmap`（9） |
| 起进程、起线程、结束进程 | 调度器是内核的一部分 | `clone`、`exit_group`（231） |
| 读时间 | 时钟源与「墙上时间」由内核统一 | `clock_gettime`（228） |
| 打开文件、读目录 | 文件系统只有内核看得见 | `openat`（257）、`read`（0） |
| 进程间通信、网络 | 另一端可能根本不在本机 | `socket`、`pipe2` |

反过来，**不需要进内核的事情也有一张表**，它们在裸机上同样是免费的：

| 事情 | 桌面上要进内核吗 | 裸机上怎么做 |
|---|---|---|
| 读写自己进程里的内存 | 不要 | 同样是普通指令 |
| 算术、分支、函数调用 | 不要 | 一样 |
| 读写外设寄存器 | 要（驱动在内核里） | **直接写固定地址**，不需要内核 |
| 拿一个精确的周期数 | 要（`clock_gettime`） | `DWT->CYCCNT`，一条 `ldr` |
| 知道「现在几点」 | 要 | 没有 RTC 就没有，只能自己定一个基准 |

**最后三行是嵌入式侧的关键**：裸机程序对外设的全部操作都是普通的内存访问，
既没有态切换，也没有权限检查。代价是没有任何人替它兜底——
第 10 章与本章第 5 节里的故障都是这么来的。

> [!IMPORTANT]
> **「必须进内核」的清单就是「裸机上必须自己实现」的清单。**
> 桌面程序靠内核完成的那几件事，到了裸机上要么由库桩顶替，要么由程序员自己写。
> 第 5 节把这批桩逐个列出来。

# 第 2 节 x86-64 怎么发一次系统调用

## 2.1 `syscall` 指令与寄存器约定

一条系统调用只需要三样东西：**一个号**（要做什么）、**几个参数**、**一条指令**。
x86-64 的约定如下（这是 ABI，不是标准）：

| 用途 | 寄存器 |
|---|---|
| 系统调用号 | `rax` |
| 第 1 到第 3 个参数 | `rdi`、`rsi`、`rdx` |
| 第 4 到第 6 个参数 | `r10`、`r8`、`r9` |
| 返回值 | `rax` |
| 被 `syscall` 破坏 | `rcx`（存返回地址）、`r11`（存 `RFLAGS`） |

与普通函数调用（《07-更底层/05-ABI 与调用约定.md》第 1 节）只差两处：
第 4 个参数从 `rcx` 改成了 **`r10`**，而且 `rcx` 会被指令本身覆盖。
这两点正是第 2.5 小节的错误来源。

系统调用号写在头文件里，是内核与用户态之间的编号约定：

`文档`

> "#define __NR_read 0"
> "#define __NR_write 1"
> "#define __NR_open 2"
> "#define __NR_close 3"
> "#define __NR_mmap 9"
> "#define __NR_brk 12"
> "#define __NR_getpid 39"
> "#define __NR_exit 60"
> "#define __NR_clock_gettime 228"
> "#define __NR_exit_group 231"
> "#define __NR_openat 257"
>
> —— `/usr/include/x86_64-linux-gnu/asm/unistd_64.h`

`文档`

> "#define __NR_exit 1"
> "#define __NR_read 3"
> "#define __NR_write 4"
> "#define __NR_open 5"
> "#define __NR_close 6"
> "#define __NR_getpid 20"
> "#define __NR_brk 45"
> "#define __NR_mmap 90"
> "#define __NR_clock_gettime 265"
>
> —— `/usr/include/x86_64-linux-gnu/asm/unistd_32.h`

**两张表的号完全对不上**：64 位的 `write` 是 1，32 位的是 4；
64 位的 `brk` 是 12，32 位的是 45。号是内核接口的一部分，
换架构、换位数就得换表，这一点在第 2.3 小节会再看到一次。

## 2.2 真实反汇编：直接发一次 `write`

下面这份程序不调用 libc 的 `write`，而是自己把号与参数放进寄存器，直接执行 `syscall`。

`C`

```c
/* WSL Ubuntu 侧（x86-64 Linux 专用，在 WSL 里编译运行）：
   raw_write.c —— 直接发一次 write，不经过 libc
   gcc -O2 -std=c2x raw_write.c -o raw_write */
/* 不用 libc 的 write()，直接用 syscall 指令发一次 write(1, "hi\n", 3) */
static const char msg[] = "hi\n";

int main(void)
{
    long ret;
    /* rax = 1（write）、rdi = 1（stdout）、rsi = 缓冲区、rdx = 长度 */
    __asm__ volatile ("syscall"
                      : "=a"(ret)
                      : "a"(1L), "D"(1L), "S"(msg), "d"(sizeof msg - 1)
                      : "rcx", "r11", "memory");
    return ret == (long)(sizeof msg - 1) ? 0 : 1;
}
```

`实测数据`
`Bash`

```bash
$ ./raw_write
hi
$ strace -e trace=write ./raw_write
write(1, "hi\n", 3)                     = 3
```

`strace` 看到的与 libc 版本一模一样，因为它看的是内核收到的东西。
下面是这段内联汇编编出来的机器码：

`实测数据`
`Assembly`

```asm
0000000000001040 <main>:
    1040:	f3 0f 1e fa          	endbr64
    1044:	b8 01 00 00 00       	mov    $0x1,%eax        ; rax = 1，write 的号
    1049:	48 8d 35 b4 0f 00 00 	lea    0xfb4(%rip),%rsi  ; rsi = 缓冲区
    1050:	ba 03 00 00 00       	mov    $0x3,%edx        ; rdx = 3
    1055:	48 89 c7             	mov    %rax,%rdi        ; rdi = 1（fd）
    1058:	0f 05                	syscall
    105a:	48 83 f8 03          	cmp    $0x3,%rax        ; 返回值就是 rax
    105e:	0f 95 c0             	setne  %al
    1061:	0f b6 c0             	movzbl %al,%eax
    1064:	c3                   	ret
```

编译器把 `"a"(1L)` 与 `"D"(1L)` 合并成了一条 `mov %rax,%rdi`，
`syscall` 之前四个寄存器各就各位，之后紧跟着一条比较——这就是全部。

## 2.3 32 位的 `int 0x80` 差在哪

32 位 x86 没有 `syscall` 指令可用（那是 64 位才有的），进内核走的是软中断 `int 0x80`。
寄存器约定也换了一整套：

| | 32 位 `int 0x80` | 64 位 `syscall` |
|---|---|---|
| 号放哪 | `eax` | `rax` |
| 参数 | `ebx`、`ecx`、`edx`、`esi`、`edi`、`ebp` | `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9` |
| 返回值 | `eax` | `rax` |
| 号表 | `unistd_32.h` | `unistd_64.h` |
| `write` 的号 | **4** | **1** |

`C`

```c
/* WSL Ubuntu 侧（32 位 x86 Linux 专用，需要 gcc-multilib）：
   raw32_write.c —— 同样的 write，换成 int 0x80
   gcc -m32 -O2 -std=c2x raw32_write.c -o raw32_write */
/* 32 位 x86 没有 syscall 指令可用：走 int 0x80，参数寄存器也换了一套 */
static const char msg[] = "hi from int 0x80\n";

int main(void)
{
    long ret;
    /* eax = 4（__NR_write）、ebx = 1、ecx = 缓冲区、edx = 长度 */
    __asm__ volatile ("int $0x80"
                      : "=a"(ret)
                      : "a"(4L), "b"(1L), "c"(msg), "d"(sizeof msg - 1)
                      : "memory");
    return ret == (long)(sizeof msg - 1) ? 0 : 1;
}
```

`Bash`

$ file raw32_write | cut -c1-80

$ strace -e trace=write ./raw32_write

`实测数据`
`Assembly`

    1050:	e8 58 01 00 00       	call   11ad <__x86.get_pc_thunk.ax>

    105a:	53                   	push   %ebx
    105b:	ba 11 00 00 00       	mov    $0x11,%edx       ; edx = 17
    1060:	bb 01 00 00 00       	mov    $0x1,%ebx        ; ebx = 1（fd）
    1065:	8d 88 2c e0 ff ff    	lea    -0x1fd4(%eax),%ecx

    1072:	83 f8 11             	cmp    $0x11,%eax

两边的程序都打印成功，`strace` 看到的也是同一次 `write`；
**内核只认号与寄存器，不认那条指令叫什么名字。**
`int 0x80` 在 64 位内核上仍能跑，但走的是兼容路径：
它只按 32 位规则解释寄存器，参数里的指针也被截断到 32 位。
64 位程序用 `int 0x80` 发一个带指针的系统调用，地址会被截掉高 32 位——
这条路径的实测在 32 位程序上做，`待确认` 64 位程序误用的具体后果。

## 2.4 内核给负数，`errno` 为什么是正数

内核里没有 `errno` 这个东西。它的约定更简单：**成功时把结果放在 `rax`，
失败时把「负的错误码」放在 `rax`。** 下面这份程序让同一个失败的请求走两条路：
一条是自己发的 `syscall`，一条是 libc 的 `open`。

`C`

```c
/* WSL Ubuntu 侧（x86-64 Linux 专用，在 WSL 里编译运行）：
   raw_errno.c —— 内核的负返回值怎么变成 errno
   gcc -O2 -std=c2x raw_errno.c -o raw_errno */
/* 同一个失败的内核请求，走两条路：裸 syscall 与 glibc 包装 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

/* openat(AT_FDCWD, path, O_RDONLY, 0)：rax = 257，第 4 个参数走 r10 */
static long raw_openat(const char *path)
{
    register long r10 __asm__("r10") = 0;
    long ret;
    __asm__ volatile ("syscall"
                      : "=a"(ret)
                      : "a"(257L), "D"(-100L), "S"(path), "d"(0L), "r"(r10)
                      : "rcx", "r11", "memory");
    return ret;
}

int main(void)
{
    const char *path = "/no/such/file";

    long raw = raw_openat(path);
    printf("裸 syscall 的返回值      ：%ld（0x%016lx）\n", raw, (unsigned long)raw);

    errno = 0;
    int fd = open(path, O_RDONLY);
    printf("glibc open 的返回值      ：%d\n", fd);
    printf("同一时刻的 errno         ：%d（%s）\n", errno, strerror(errno));
    printf("ENOENT 的数值            ：%d\n", ENOENT);
    return 0;
}
```

`实测数据`
`Bash`

```bash
$ ./raw_errno
裸 syscall 的返回值      ：-2（0xfffffffffffffffe）
glibc open 的返回值      ：-1
同一时刻的 errno         ：2（No such file or directory）
ENOENT 的数值            ：2
```

同一个失败，**内核交出来的是 `-2`，`errno` 里躺着的是 `2`**。
把这一步做掉的代码在 libc 里，只有几条指令：

`实测数据`
`Assembly`

```asm
0000000000448de0 <__libc_write>:              # gcc -static 之后的 libc
  448ded:	b8 01 00 00 00       	mov    $0x1,%eax
  448df2:	0f 05                	syscall
  448df4:	48 3d 00 f0 ff ff    	cmp    $0xfffffffffffff000,%rax
  448dfa:	77 54                	ja     448e50 <__libc_write+0x70>   # 落在这一区间就是错误
  448dfc:	c3                   	ret
  ...
  448e50:	48 c7 c2 c0 ff ff ff 	mov    $0xffffffffffffffc0,%rdx
  448e57:	f7 d8                	neg    %eax
```

判据是 **`rax` 落在 `-4095` 到 `-1` 之间**（无符号看就是大于 `0xfffffffffffff000`）。
落进去，libc 就把 `rax` 取负写进 `errno`，再把返回值改成 `-1` 交出来。
由此可以推出三条使用规则：

| 规则 | 原因 |
|---|---|
| 失败之后才能读 `errno` | 成功的调用不会去动它，读到的可能是上一次留下的值 |
| 成功的调用**不会**把 `errno` 清零 | 所以判断成败要看返回值，不能看 `errno` |
| `strerror(errno)` 拿到的是那串英文 | 它按错误码查一张表，表在 libc 里 |

> [!WARNING]
> **`errno` 不是全局变量那么简单。** 它通常是「线程局部的」，
> 每个线程各有一份；在裸机上用 newlib 时，它背后还会牵出一整套可重入机器——
> 第 5.3 小节会给出这一行赋值在真板固件里的体积代价。

## 2.5 写错了会怎样：参数进错寄存器

寄存器约定是硬性的，写错不会有任何编译期提示。下面两个程序各错一处。

第一处错：把文件描述符与缓冲区放反。内核按位置解释寄存器：
`rdi` 就是 `fd`，`rsi` 就是缓冲区指针。

`C`

```c
/* WSL Ubuntu 侧（在 WSL 里编译运行，Windows 上编不过）：
   raw_write_swap.c
   gcc -O2 -std=c2x raw_write_swap.c -o raw_write_swap */
/* 故意把 fd 与缓冲区放反：rdi 放了缓冲区地址，rsi 放了 1 */
static const char msg[] = "hi\n";

int main(void)
{
    long ret;
    __asm__ volatile ("syscall"          /* 内核按 rdi=fd 解释，于是 fd = 一个地址 */
                      : "=a"(ret)
                      : "a"(1L), "D"((long)msg), "S"(1L), "d"(sizeof msg - 1)
                      : "rcx", "r11", "memory");
    return (int)ret;
}
```

`实测数据`
`Bash`

```bash
$ ./raw_write_swap; echo "退出码 $?"
退出码 247
$ strace -e trace=write ./raw_write_swap
write(254033924, 0x1, 3)                = -1 EBADF (Bad file descriptor)
```

`strace` 把那个被当成 `fd` 的地址原样打印了出来（`254033924`，就是 `msg` 的地址），
返回 `-1 EBADF`，程序一个字也没输出。**内核不会检查「这个 fd 看起来像不像指针」**，
它只查这个号在进程的文件表里有没有对应项。

第二处错更隐蔽：4 个及以上参数时，第 4 个参数必须走 `r10`，
放进 `rcx` 会被 `syscall` 指令本身覆盖掉——而内核读的是 `r10`。

`C`

```c
/* WSL Ubuntu 侧（在 WSL 里编译运行，Windows 上编不过）：
   raw_open_mode.c
   gcc -O2 -std=c2x raw_open_mode.c -o raw_open_mode */
/* 4 个参数的 syscall：第 4 个参数必须走 r10。放进 rcx 会怎样。 */
#include <fcntl.h>
#include <stdio.h>
#include <sys/stat.h>
#include <unistd.h>

#define FLAGS (O_CREAT | O_WRONLY | O_TRUNC)

/* 正确：mode 走 r10 */
static long openat_r10(const char *path, long mode)
{
    register long r10 __asm__("r10") = mode;
    long ret;
    __asm__ volatile ("syscall"
                      : "=a"(ret)
                      : "a"(257L), "D"(-100L), "S"(path), "d"((long)FLAGS), "r"(r10)
                      : "rcx", "r11", "memory");
    return ret;
}

/* 错误：mode 放进 rcx。syscall 指令会把 rcx 覆盖成返回地址，内核读的是 r10。 */
static long openat_rcx(const char *path, long mode)
{
    register long r10 __asm__("r10") = 0777;   /* 模拟上一个调用留在 r10 里的值 */
    long ret;
    __asm__ volatile ("mov %[m], %%rcx\n\tsyscall"
                      : "=a"(ret)
                      : "a"(257L), "D"(-100L), "S"(path), "d"((long)FLAGS),
                        "r"(r10), [m] "r"(mode)
                      : "rcx", "r11", "memory");
    return ret;
}

static void report(const char *tag, const char *path)
{
    struct stat st;
    if (stat(path, &st) != 0) {
        printf("%s：stat 失败\n", tag);
        return;
    }
    printf("%s -> 实际权限位 0%03o\n", tag, (unsigned)(st.st_mode & 07777));
}

int main(void)
{
    remove("/tmp/mode_ok");
    remove("/tmp/mode_bad");

    openat_r10("/tmp/mode_ok", 0600);
    report("正确（mode 走 r10，请求 0600）", "/tmp/mode_ok");

    openat_rcx("/tmp/mode_bad", 0600);
    report("写错（mode 走 rcx，请求 0600）", "/tmp/mode_bad");
    return 0;
}
```

`实测数据`
`Bash`

```bash
$ ./raw_open_mode
正确（mode 走 r10，请求 0600） -> 实际权限位 0600
写错（mode 走 rcx，请求 0600） -> 实际权限位 0755
$ ls -l /tmp/mode_ok /tmp/mode_bad
-rwxr-xr-x 1 root root 0 /tmp/mode_bad
-rw------- 1 root root 0 /tmp/mode_ok
```

两个调用都返回了有效的文件描述符，都建出了文件，**没有一个报错**。
写错的那一次，请求的是 `0600`，实际建出来的是 `0755`——
内核读到的 `mode` 是 `r10` 里残留的 `0777`，再被进程的 `umask`（`022`）削掉两位。
这类错误不会当场崩，它会把一个权限边界悄悄放宽。

> [!CAUTION]
> **内联汇编里的寄存器约束写错，编译器不会有任何提示。**
> `"r"(x)` 只保证 `x` 在一个通用寄存器里，不保证是哪一个；
> 需要指定寄存器就用 `register long r10 __asm__("r10") = x;` 这种带寄存器名的写法，
> 并且把 `syscall` 会破坏的 `rcx`、`r11` 放进 clobber 列表。
> 少了 clobber 列表，编译器可能把还需要的值留在 `rcx` 里，后果与上面一样隐蔽。

这份程序打印 20000 行（前一万行 5 字节、后一万行 6 字节），一共 110000 字节；
110000 除以 4096 得到 26.86，所以是 27 次：**26 次满块 4096 字节，最后一次 3504 字节**，
`26 × 4096 + 3504 = 110000`。缓冲区大小是 4096，这个数与流的类型有关，
下一小节说明它从哪来。

## 3.2 缓冲决定次数与时刻

把「两次 `printf`、中间等 2 秒」写成一个程序，就能看清缓冲到底改变了什么。

`C`

```c
/* WSL Ubuntu 侧（在 WSL 里编译运行；需要真正的伪终端才看得到第三种情况）：
   hi_two.c
   gcc -O2 -std=c2x hi_two.c -o hi_two */
/* 两次 printf，中间等 2 秒：看 write 到底发生几次、什么时候发生 */
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("hi\n");
    sleep(2);
    printf("bye\n");
    return 0;
}
```

`实测数据`
`Bash`

```bash
# 1. 输出重定向到文件：全缓冲，两次 printf 合成一次 write，发生在程序结束时
$ strace -tt -e trace=write ./hi_two > /dev/null
16:40:21.215633 write(1, "hi\nbye\n", 7) = 7

# 2. 同一件事写到 stderr：不缓冲，两次 write 相隔 2 秒
$ strace -tt -e trace=write ./hi_two_err 2>/dev/null
16:40:21.228940 write(2, "hi\n", 3)     = 3
16:40:23.232334 write(2, "bye\n", 4)    = 4

# 3. 输出接在伪终端上：行缓冲，遇到 \n 就刷，同样相隔 2 秒
$ strace -f -tt -e trace=write -o t3.txt python3 -c "import pty; pty.spawn(['./hi_two'])"
476   16:40:23.317527 write(1, "hi\n", 3) = 3
476   16:40:25.318876 write(1, "bye\n", 4) = 4
```

三种情况的差别全在「什么时候刷」：

| stdout 连到哪 | 缓冲策略 | 两次 `printf` 的结果 |
|---|---|---|
| 文件、管道 | 全缓冲（4096 字节） | 合成一次 `write`，在缓冲区满或 `exit` 时才发 |
| 终端 | 行缓冲 | 每个 `\n` 触发一次 `write` |
| 程序自己 `setvbuf` 成 `_IONBF` | 不缓冲 | 每次 `printf` 都发一次 `write` |
| stderr | 标准规定不缓冲 | 每次输出立刻发一次 `write` |

这三行解释了写这类程序时最常见的两个现象。
**「加了 `printf` 调试，程序崩了但什么都没打出来」**：缓冲区里的字还没刷，
进程就死了，那些字跟着内存一起消失——`stderr` 与 `fflush` 是两种解法。
**「`printf` 打点让程序变慢」**：如果输出接在终端上，每一行都是一次 45 ns 起的内核往返；
重定向到文件反而更快，因为攒成 4096 字节才进一次内核。

> [!TIP]
> 判断一个程序的输出走哪条路，不必猜：`strace -tt -e trace=write` 会同时给出**时刻**与**长度**。
> 分散的小 `write` 说明是不缓冲或行缓冲，成批的 4096 说明是全缓冲。

已经进过三十几次内核了**；而裸机程序从复位向量到 `main`，
一次都没有离开过 Thread 态（《07-更底层/07-链接脚本与启动代码.md》第 3 节）。

# 第 4 节 Windows 这一侧

## 4.1 `WriteFile` 的三层

Windows 没有把系统调用直接交给程序。程序调用的是 `WriteFile`，
这个名字在三个 DLL 里各有一份，一层转一层：

`Text`

```
   你自己的代码
        │  WriteFile(handle, buf, len, &written, NULL)
        ▼
   kernel32.dll 的 WriteFile：一条跳转指令，跳到导入表里的槽位
        │
        ▼
   KernelBase.dll 的 WriteFile：检查参数、决定同步还是异步
        │
        ▼
   ntdll.dll 的 NtWriteFile：mov r10, rcx / mov eax, 8 / syscall
        │
        ▼

```

这条链子的每一段都能在二进制里看到。第一段，`kernel32` 导出的 `WriteFile`：

`实测数据`

```

序号 1612、提示值 `64B`、RVA `00020A90`。`kernel32` 的映像基址是 `0x180000000`，
所以这个名字指向 `0x180020A90`，那里的内容是：

```

`kernel32` 同时从两个地方取名字：`WriteFile` 来自一个 `api-ms-win-*` 名字，
`NtWriteFile` 直接来自 `ntdll.dll`。
那个 `api-ms-win-core-file-l1-1-0.dll` 在磁盘上并不存在：

`实测数据`

$ powershell -c "Test-Path C:\Windows\System32\KernelBase.dll"

第二段，`KernelBase` 里确实有这个名字，并且它从 `ntdll` 取 `NtWriteFile`：

`实测数据`
`Text`

```text
$ dumpbin /exports C:\Windows\System32\KernelBase.dll | findstr WriteFile
       1943  796 0002B630 WriteFile
$ dumpbin /imports C:\Windows\System32\KernelBase.dll | findstr NtWriteFile

```

`待确认`

> `api-ms-win-*` 是「API 集」的虚拟名字，由装载器映射到真正实现的 DLL
> （`api-ms-win-core-file-l1-1-0` 对应 `KernelBase`）。
> 本机实测到的只有两件事：这个名字在磁盘上不存在，而 `KernelBase` 导出同名函数。
> 「槽位 `0x180084628` 指向的就是 `KernelBase!WriteFile`」这一步没有在本机用调试器验证过，
> 因此标 `待确认`。

**为什么要有这一层**：`kernel32` 这一类 DLL 是「稳定名字」，
程序只跟它链接；真正的实现可以在每个 Windows 版本里换地方，
只要这些跳转跟着改就行。Linux 侧没有对应物，`libc` 自己就是实现，
系统调用号由内核固定（第 2.1 小节）。两种做法的取舍不同：
Windows 把兼容放在用户态的一层 DLL 上，Linux 把兼容放在内核的系统调用表上。

## 4.2 `NtWriteFile` 的桩里就是 `syscall`

`ntdll` 的导出表给出 `NtWriteFile` 的位置：

`实测数据`
`Text`

```text
$ dumpbin /exports C:\Windows\System32\ntdll.dll | findstr NtWriteFile
        683  2A2 000A0D40 NtWriteFile
        684  2A3 000A0FA0 NtWriteFileGather
$ dumpbin /headers C:\Windows\System32\ntdll.dll | findstr "image base"
       180000000 image base (0000000180000000 to 0000000180216FFF)
```

RVA `0xA0D40` 加上基址 `0x180000000`，就是 `0x1800A0D40`。
把这个地址前后的反汇编拿出来：

`实测数据`
`Assembly`

```asm
  00000001800A0D20: mov         r10,rcx                  ← 同一张表里的另一个 Nt* 调用
  00000001800A0D23: mov         eax,7
  00000001800A0D28: test        byte ptr [000000007FFE0308h],1
  00000001800A0D30: jne         00000001800A0D35
  00000001800A0D32: syscall
  00000001800A0D34: ret
  00000001800A0D35: int         2Eh
  00000001800A0D37: ret
  00000001800A0D40: mov         r10,rcx                  ← NtWriteFile 从这里开始
  00000001800A0D43: mov         eax,8                    ← NtWriteFile 的系统调用号 = 8
  00000001800A0D48: test        byte ptr [000000007FFE0308h],1
  00000001800A0D50: jne         00000001800A0D55
  00000001800A0D52: syscall
  00000001800A0D54: ret
  00000001800A0D55: int         2Eh
  00000001800A0D57: ret
```

这段桩只有七条指令，与 Linux 的 libc 包装是同一件事：
**把参数摆好、把号放进 `rax`、执行 `syscall`。**
三处细节值得单独看：

| 指令 | 含义 |
|---|---|
| `mov r10, rcx` | Windows 的第 1 个参数在 `rcx`，而 `syscall` 要求第 4 个参数在 `r10`；`Nt*` 的签名与内核约定一致，所以把这一个搬过去 |
| `mov eax, 8` | `NtWriteFile` 在**这台机器这个版本**上的号是 8；它不保证跨版本稳定，所以程序不直接用它 |
| `test byte ptr [7FFE0308h],1` | 一个共享只读页里的标志位，为 1 时改走老的 `int 2Eh`，为 0 时走 `syscall` |

最后那条标志位可以直接读出来。这个页面在用户态是可读的，
下面这个 Windows 程序就是普通 `gcc` 编出来读一个字节：

`C`

```c
/* kuser.c   编译：gcc -O2 -std=c23 kuser.c -o kuser.exe
   ntdll 的 Nt* 桩里有一句 test byte ptr [7FFE0308h],1：
   这个字节决定走 syscall 还是老的 int 2Eh。该页面用户态可读（KUSER_SHARED_DATA）。 */
#include <stdint.h>
#include <stdio.h>

int main(void)
{
    const volatile unsigned char *flag = (const volatile unsigned char *)0x7FFE0308ull;
    printf("0x7FFE0308 = %u\n", (unsigned)*flag);
    return 0;
}
```

`实测数据`
`Bash`

```bash
$ ./kuser.exe
0x7FFE0308 = 0
```

读到 0，所以本机走的是 `syscall` 那条分支，`int 2Eh` 是留给老系统的退路。
**这就是 Windows 与 Linux 在这一层最接近的地方**：
两边的用户态都要经过一小段「摆寄存器 + 一条指令」的代码，
区别只是这段代码住在哪个 DLL、号是谁定的。

## 4.3 与 Linux 的对照

`实测数据`
`Text`

| | Linux（x86-64） | Windows（x86-64） |
|---|---|---|
| 指令 | `syscall` | `syscall`（可用 `int 2Eh` 退路） |
| 号在哪个寄存器 | `rax` | `rax` |
| `write` 的号 | 1（`__NR_write`） | 8（`NtWriteFile`） |
| 号的稳定性 | 内核接口，长期固定 | 随版本变化，程序不直接用 |
| 谁填号 | libc 的包装函数 | `ntdll` 的桩 |
| 名字在哪一层 | `write` → libc → `syscall` | `WriteFile` → `KernelBase` → `NtWriteFile` → `syscall` |
| 错误怎么回 | 负数返回值 → `errno` | `NTSTATUS` → `SetLastError` 的 `Win32` 错误码 |
| 参数顺序 | `rdi` `rsi` `rdx` `r10` `r8` `r9` | `rcx` `rdx` `r8` `r9` + 栈 |
| 谁做参数搬运 | 库函数内部完成 | `Nt*` 桩里那句 `mov r10, rcx` |

两边的第 5 行是最容易混的地方：**系统调用的参数约定与普通函数的参数约定不一定相同。**
x86-64 上 Linux 两套都是 `rdi` 打头，所以 `r10` 这个例外格外容易忘（第 2.5 小节）；
Windows 的普通函数用 `rcx` 打头，而内核约定用 `r10` 收第 4 个参数，
于是每个 `Nt*` 桩里都要有一条 `mov r10, rcx`。

> [!NOTE]
> **小结**：这一节看到的三层，作用是「让程序不必知道系统调用号」。
> 号是内核的实现细节，名字与签名才是给程序用的接口。
> 裸机上没有这一层，所以第 5 节的桩函数直接把名字与内核的对应关系暴露了出来。

## 5.2 真板上的对照：同一份源码，两种 `--specs`

下面这份程序是本章裸机侧的主程序。它把每一步的结果都写进 `g_result`，
调试器读内存就能看到全部答案，同时 `printf` 写到哪儿也一目了然。

`C`

```c
/* Cortex-M 侧（在 WSL 里交叉编译，QEMU 或真板上跑）：
   hello.c —— 同一份源码，只改 --specs 就看两种桩的差别
   arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -g -nostartfiles \
     --specs=nosys.specs -T STM32F103C8_FLASH.ld startup_stm32f103xe.s hello.c -o hello_nosys.elf
   arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -g -nostartfiles \
     --specs=rdimon.specs -T STM32F103C8_FLASH.ld startup_stm32f103xe.s hello.c -o hello_rdimon.elf
   结果全部写进 g_result，调试器用 mdw 一次读完；rdimon 那一版还会把字打出来。 */
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

/* -nostartfiles 把 crt0 挡在外面，这两个符号得自己给（一行空函数） */
void SystemInit(void) { }
void _init(void) { }

/* rdimon 的 crt0 才会调它，而 crt0 被 -nostartfiles 挡住了，于是自己声明成弱符号：
   链接了 librdimon 就调到它，链接 nosys 时它是 0，什么都不发生。 */
extern void initialise_monitor_handles(void) __attribute__((weak));

volatile unsigned g_result[8] = { 0x5A5A0000u, 0, 0, 0, 0, 0, 0, 0 };

int main(void)
{
    void *p;

    if (initialise_monitor_handles != NULL) {
        initialise_monitor_handles();     /* 打开 semihosting 的标准输出句柄 */
    }

    g_result[0] = 0x5A5A0001u;                             /* 已经进了 main */
    g_result[1] = (unsigned)printf("hello from board\n");   /* printf 的返回值 */
    g_result[2] = (unsigned)fflush(stdout);                 /* 0 = 成功，EOF = 失败 */

    p = malloc(64);
    g_result[3] = (unsigned)(unsigned long)p;               /* malloc 给的地址 */
    if (p != NULL) {
        *(volatile unsigned *)p = 0xA5A5A5A5u;
        g_result[4] = *(volatile unsigned *)p;              /* 真的能读写才算数 */
    }
    g_result[5] = (unsigned)printf("second line\n");
    g_result[6] = (unsigned)time(NULL);                     /* 没有内核，问谁要时间 */
    g_result[7] = 0x5A5AFFFFu;                              /* 跑完了 */

    for (;;) {
    }
}
```

两个镜像编出来，各自烧进板子跑 2 秒，再用 `mdw` 读那 8 个字：

`PowerShell`

`hello_nosys` 那一轮，控制台自上而下什么都没有。

`实测数据`
`Text`

| 下标 | 记录什么 | `--specs=nosys.specs` | `--specs=rdimon.specs` |
|---|---|---|---|
| 0 | 进了 `main` | `0x5A5A0001` | `0x5A5A0001` |
| 1 | `printf` 的返回值 | **`0xFFFFFFFF`（-1）** | **`0x00000011`（17，正好是 17 个字符）** |
| 2 | `fflush` 的返回值 | 0 | 0 |
| 3 | `malloc(64)` 给的地址 | `0x20000C60` | `0x20000D18` |
| 4 | 写进去再读出来的值 | `0xA5A5A5A5` | `0xA5A5A5A5` |
| 5 | 第二次 `printf` 的返回值 | **`0xFFFFFFFF`（-1）** | **`0x0000000C`（12）** |
| 6 | `time(NULL)` | **`0xFFFFFFFF`（-1）** | **`0x6ABE1C01`（真实秒数）** |
| 7 | 跑完标记 | `0x5A5AFFFF` | `0x5A5AFFFF` |

三处结论都在表里：

| 现象 | 原因 |
|---|---|
| `printf` 返回 -1，控制台没有字 | `_write` 是那条五指令的桩，直接返回 -1 并置 `errno = ENOSYS` |
| `malloc` 两边**都**拿到了有效地址 | `libnosys.a` 的 `_sbrk` 是一个没有上界检查的分配器（第 5.3 小节），它不问内核，只看 RAM |
| `time(NULL)` 一边 -1 一边是真实秒数 | 时间必须来自内核；`rdimon` 把它转成了 semihosting 的时间调用 |

还有一个容易忽略的差别藏在下标 2 与 1 之间：
`nosys` 那一轮 `printf` 返回的是 -1，而不是「写进了缓冲区、稍后再失败」。
原因在 `_fstat`：它同样返回 -1，于是 newlib 无法确定这个流的块大小，
干脆把 `stdout` 设成**不缓冲**——每次 `printf` 都直接落到 `_write` 上，
错误当场就返回了。这条链子把「内核缺席」的影响一路传到了缓冲策略上。

`rdimon` 那一版还有两个必要条件，缺一个就不出字：

`实测数据`
`Text`

| 条件 | 少了会怎样 |
|---|---|
| `-nostartfiles` 必须保留 | 去掉它，`rdimon-crt0` 会参与链接，报 `undefined reference to '__end__'`（它要的符号名与 CubeMX 链接脚本给的 `_end` 不同），另外 `_init` 会重复定义 |
| 自己调一次 `initialise_monitor_handles()` | 桩函数不知道往哪个句柄写，结果是**一个字都不打印**，与 `nosys` 那一版看上去一样 |
| `arm semihosting enable` | 调试器不接管 `bkpt 0xAB`，同样什么都看不到 |

只有 `-nostartfiles` 与 `initialise_monitor_handles()` 容易漏，
因为前者的报错发生在链接期（看得见），后者是**静默的**：
程序照样跑完，`g_result` 也全部写对，就是没有输出。

> [!WARNING]
> **`printf` 在裸机上不打字时，先分清是桩的问题还是通道的问题。**
> 三种情况的现象完全一样：`nosys` 的 `_write` 返回 -1、
> `rdimon` 没调 `initialise_monitor_handles`、调试器没开 semihosting。
> 分辨办法是读 `printf` 的返回值：`-1` 说明桩失败了，
> 返回正数却没有字说明桩成功了、只是通道没打开。

## 5.3 `_sbrk`：裸机上的「brk 系统调用」

桌面上 `malloc` 要内存时，最终会请求内核扩展堆（`brk` 或 `mmap`）。
裸机上没有内核可问，这件事落在一个函数上：`_sbrk`。
**它要自己回答三个问题**：堆从现在哪里开始、往上能走到哪、走过头了怎么办。

`libnosys.a` 给的答案只回答了第一个：

`实测数据`
`Assembly`

```asm
08006af8 <_sbrk>:
 8006af8:	4a04      	ldr	r2, [pc, #16]	@ (8006b0c)   ; r2 = &heap_end
 8006afa:	4905      	ldr	r1, [pc, #20]	@ (8006b10)   ; r1 = &_end
 8006afc:	6813      	ldr	r3, [r2, #0]                 ; r3 = heap_end
 8006afe:	2b00      	cmp	r3, #0
 8006b00:	bf08      	it	eq
 8006b02:	460b      	moveq	r3, r1                       ; 第一次调用：heap_end = &_end
 8006b04:	4418      	add	r0, r3                       ; 返回值 = heap_end + incr
 8006b06:	6010      	str	r0, [r2, #0]                 ; heap_end 往后挪
 8006b08:	4618      	mov	r0, r3                       ; 返回挪之前的位置
 8006b0a:	4770      	bx	lr
```

这十条指令里唯一的比较是 `cmp r3, #0`，它只在判断「是不是第一次调用」；
**没有一条指令去看 RAM 到哪里结束，也没有一条去看栈在哪里**——
它从 `_end` 开始往上发地址，发到哪儿算哪儿。这正是第 5.4 小节的现场。

CubeMX 生成的工程里另有一个版本，写在
`A-教学素材/01-编译器/嵌入式/内存布局与中断/sysmem.c` 里（**只读引用，未做改动**）。
（下面是节选，第 54 到 80 行）

`C`

```c
void *_sbrk(ptrdiff_t incr)
{
  extern uint8_t _end; /* Symbol defined in the linker script */
  extern uint8_t _estack; /* Symbol defined in the linker script */
  extern uint32_t _Min_Stack_Size; /* Symbol defined in the linker script */
  const uint32_t stack_limit = (uint32_t)&_estack - (uint32_t)&_Min_Stack_Size;
  const uint8_t *max_heap = (uint8_t *)stack_limit;
  uint8_t *prev_heap_end;

  /* Initialize heap end at first call */
  if (NULL == __sbrk_heap_end)
  {
    __sbrk_heap_end = &_end;
  }

  /* Protect heap from growing into the reserved MSP stack */
  if (__sbrk_heap_end + incr > max_heap)
  {
    errno = ENOMEM;
    return (void *)-1;
  }

  prev_heap_end = __sbrk_heap_end;
  __sbrk_heap_end += incr;

  return (void *)prev_heap_end;
}
```

两个版本的差别就是那句 `if`：**上界取 `_estack - _Min_Stack_Size`**，
也就是「RAM 顶端往下让出链接脚本给栈预留的那一段」。
这两个符号都来自链接脚本（《07-更底层/07-链接脚本与启动代码.md》第 2.2 小节），
本机这块板子上是 `_estack = 0x20005000`、`_Min_Stack_Size = 0x400`，
于是堆的终点是 `0x20004C00`。

> [!IMPORTANT]
> **`_sbrk` 就是裸机上的 `brk`。** 桌面上的 `brk` 由内核维护、跨进程安全；
> 裸机上的 `_sbrk` 由程序员维护，边界要自己从链接脚本里算出来。
> 少写一句检查，等于把 `brk` 换成了一个不知道 RAM 有多大的版本。

## 5.4 写错了会怎样：堆越过 RAM 顶端

下面这份程序直接调用 `_sbrk`（不经过 `malloc`，这样每一步都看得见），
每次要 1 KiB，把交回来的地址记下来；最后往拿到的最后一块写一个字。
去掉边界检查只需一个宏。

`C`

```c
/* Cortex-M 侧（在 WSL 里交叉编译，QEMU 或真板上跑）：
   heap_probe.c —— 自己实现 _sbrk，验证裸机上的「brk 系统调用」
   arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -g -nostartfiles --specs=nosys.specs \
     -T STM32F103C8_FLASH.ld startup_stm32f103xe.s heap_probe.c -o heap_ok.elf
   arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -g -nostartfiles --specs=nosys.specs \
     -DNO_LIMIT_CHECK -T STM32F103C8_FLASH.ld startup_stm32f103xe.s heap_probe.c -o heap_bad.elf */
#include <errno.h>
#include <stddef.h>
#include <stdint.h>

void SystemInit(void) { }
void _init(void) { }

extern uint8_t _end;              /* 链接脚本给的堆起点：.bss 之后 */
extern uint8_t _estack;           /* 链接脚本给的 RAM 顶端 */
extern uint32_t _Min_Stack_Size;  /* 链接脚本给栈预留的字节数 */

volatile unsigned g_result[8] = { 0x5A5A0000u, 0, 0, 0, 0, 0, 0, 0 };
static uint8_t *heap_end;

/* 没有内核可问，只能自己在 RAM 里往上挪一个高水位标记。
   必须是一个真函数：newlib 的 malloc 会从库里面 call 它。 */
__attribute__((noinline))
void *_sbrk(ptrdiff_t incr)
{
    if (heap_end == NULL) {
        heap_end = &_end;
    }
#if defined(NO_LIMIT_CHECK)
    uint8_t *prev = heap_end;
    heap_end += incr;
    return prev;
#else
    const uint8_t *max_heap =
        (const uint8_t *)((uint32_t)&_estack - (uint32_t)&_Min_Stack_Size);
    if (heap_end + incr > max_heap) {
        errno = ENOMEM;
        return (void *)-1;
    }
    uint8_t *prev = heap_end;
    heap_end += incr;
    return prev;
#endif
}

int main(void)
{
    unsigned n = 0, last = 0, refused = 0;

    g_result[0] = (unsigned)(uintptr_t)&_end;
    g_result[1] = (unsigned)(uintptr_t)&_estack;
    g_result[2] = (unsigned)&_Min_Stack_Size;

    for (;;) {
        void *p = _sbrk(1024);
        if (p == (void *)-1) {
            refused = 1;
            break;
        }
        last = (unsigned)(uintptr_t)p;
        ++n;
        if (n >= 40) {          /* 保险：最多要 40 KiB，别真的跑飞 */
            break;
        }
    }
    g_result[3] = n;            /* 被接受了几次 1 KiB 的请求 */
    g_result[4] = last;         /* 最后交出去的那块地址 */
    g_result[5] = refused;      /* 1 = 触到边界被拒 */

    g_result[6] = 1;            /* 打算往最后那块写一个字 */
    *(volatile unsigned *)last = 0x600D600Du;
    g_result[7] = 0x600D600Du;  /* 写成功了才会到这里 */

    for (;;) {
    }
}
```

`实测数据`
`Text`

| 下标 | 记录什么 | 有边界检查 | 无边界检查（`-DNO_LIMIT_CHECK`） |
|---|---|---|---|
| 0 | `_end`（堆起点） | `0x200006E0` | `0x20000028` |
| 1 | `_estack`（RAM 顶端） | `0x20005000` | `0x20005000` |
| 2 | `_Min_Stack_Size` | `0x400` | `0x400` |
| 3 | 被接受的请求次数（每次 1 KiB） | **17** | **40（撞到程序里的 40 次上限，一次都没被拒）** |
| 4 | 最后交出去的地址 | `0x200046E0` | **`0x20009C28`** |
| 5 | 有没有被拒 | **1（第 18 次拒绝）** | **0** |
| 6 | 打算写 | 1 | 1 |
| 7 | 写成功 | `0x600D600D` | `0x600D600D` |

有检查的那一版，堆停在 `0x200046E0`，再加一块就会越过 `0x20005000 - 0x400 = 0x20004C00`，
于是第 18 次请求被拒，`errno` 被置成 `ENOMEM`。
没有检查的那一版，**一口气发出 40 块，最后一块落在 `0x20009C28`**——
比这块芯片 RAM 的顶端高出 `0x4C28`（约 19 KiB）。
更值得注意的是 `g_result[5] = 0`：它一次都没有表示过反对。

> [!CAUTION]
> **越界的那次写不会当场停住。** 真板上这一轮停在
> `current mode: Handler HardFault`，但故障寄存器里留下的是一组「不精确」的证据：
> `CFSR = 0x00000400`（`IMPRECISERR`，写缓冲延迟报告的总线错误）、
> `HFSR = 0x40000000`（升级成了 HardFault）、
> `BFAR = 0xE000EDF8`（**无效**：不精确故障不记录出错地址）。

出错的那条指令与真正被压栈的 PC 差两条，这正是「不精确」的含义：

`实测数据`
`Assembly`

```asm
 80002ec:	4b07      	ldr	r3, [pc, #28]	@ (800030c)     ; r3 = 0x600D600D
 80002ee:	61b2      	str	r2, [r6, #24]                  ; g_result[6] = 1
 80002f0:	602b      	str	r3, [r5, #0]                   ; ← 越界写：*last = 0x600D600D
 80002f2:	61f3      	str	r3, [r6, #28]                  ; g_result[7] = 0x600D600D（照常执行了）
 80002f4:	e7fe      	b.n	80002f4 <main+0x3c>            ; ← 压栈的 PC 停在这里
```

`0x08002F0` 那条存指令把数据交给写缓冲之后就「完成了」，
CPU 接着执行下面两条，走到 `for(;;)` 上；总线错误晚几个周期才报上来，
这时压栈的 PC 已经是 `0x08002F4`。
**故障地址没有留下来，出错的那条指令只能靠反汇编倒推。**

最后是 QEMU 与真板的差别，它正好说明「RAM 有多大」这件事在哪儿生效：

`实测数据`
`Text`

| 同一份 `heap_bad.elf` | 最后一块地址 | 写下去的结果 |
|---|---|---|
| QEMU `netduinoplus2`（RAM 128 KiB） | `0x20009C28` | 落在合法 RAM 里，**没有故障**，`g_result[7]` 与真板一样是 `0x600D600D` |
| 真板 STM32F103C8（RAM 20 KiB） | `0x20009C28` | 落在 RAM 之外 → **Handler HardFault** |

`g_result` 里那 8 个字在两台机器上完全一致，**故障只在真板上出现**。
QEMU 的近似板 RAM 是这块板子的六倍多，这个差别不会影响启动、周期数与竞争这类测量，
但一碰到「越界」就会露出来（《07-更底层/07-链接脚本与启动代码.md》第 1.5 小节也提过这一点）。

## 5.5 与第 7、8 章的接缝：CRT 要给的那些东西

第 7、8 两章讲的是「`main` 之前发生的事」：`Reset_Handler` 搬 `.data`、
清 `.bss`、调 `__libc_init_array`，然后才是 `main`；`main` 返回之后还有 `atexit` 与析构。
本章这几节看到的桩，正是同一批东西的另一半——**桌面上的这些步骤大多由内核与 CRT 一起完成，
裸机上全部要自己给**。

`实测数据`
`Text`

| 桌面上谁做 | 裸机上谁做 | 在哪一章 |
|---|---|---|
| 内核装载可执行文件、建立地址空间（`execve`、`mmap`） | 复位向量直接跳进 `Reset_Handler` | 《07-更底层/07-链接脚本与启动代码.md》第 3 节 |
| 动态链接器读 libc、做重定位 | 静态链接，没有这一步 | 《07-更底层/06-符号与链接属性.md》第 1 节 |
| 内核把参数放进栈（`argc`、`argv`、`envp`） | `main` 由启动文件直接调用，没有参数 | 《07-更底层/08-CRT 与程序启动.md》第 1 节 |
| CRT 搬 `.data`、清 `.bss` | 同一件事，写在 `Reset_Handler` 里 | 《07-更底层/07-链接脚本与启动代码.md》第 3 节 |
| CRT 调构造表（`__libc_init_array`） | 一样，但 `_init` 要自己给一个空函数 | 《07-更底层/08-CRT 与程序启动.md》第 2 节 |
| 内核在 `exit_group` 之后回收进程 | `_exit` 是 `b .`，只有复位能重来 | 本章第 5.1 小节 |
| 内核按 `atexit` 登记的逆序调用析构 | 只有走到 `exit()` 才会调用；`for(;;)` 结尾就永远不调 | 《07-更底层/08-CRT 与程序启动.md》第 4 节 |
| 内核提供时间与随机数 | `time()` 返回 -1，要自己接 SysTick 或 RTC | 本章第 5.2 小节 |

> [!IMPORTANT]
> **「有没有内核」这个问题，最后总能落到一张「谁来提供」的清单上。**
> 桌面上这张清单由内核与 CRT 填满，裸机上大部分格子是空的，
> 空着的格子要么由库桩顶替，要么由程序员补上——`sysmem.c` 就是补 `_sbrk` 那一格的产物。

| 故障寄存器 | `mdw 0xE000ED28 1`（CFSR）、`mdw 0xE000ED2C 1`（HFSR）、`mdw 0xE000ED38 1`（BFAR） |
| 压栈的 PC | 中断现场的 8 个字在 `msp` 处，PC 是第 7 个字：`mdw <msp+24> 1` |

真板侧的操作纪律有两条：**调试器同一时刻只能被一个进程占用**；
**只写 flash 主区，不碰 option bytes**（本章只用了 `flash write_image erase`）。

## A.3 本章 Cortex-M 侧程序的输出通道

`hello.c` 与 `heap_probe.c` 都**不用** semihosting 头文件：
前者靠 `rdimon` 的库输出，后者根本不打印——所有结果都写进 `g_result`，
用调试器的 `mdw` 直接读。这样两个镜像在 `nosys` 与 `rdimon` 下的行为可以放在一张表里比。
