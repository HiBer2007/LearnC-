记录「哪个地址对应源码哪一行」「变量叫什么名字、是什么类型」的信息。

# 第 1 节 符号是什么

## 1.1 一句话定义

> [!IMPORTANT]
> **符号（symbol）就是函数或变量的名字。**

**编译之后，`compute` 这个名字在机器码里已经不存在了，只剩一个地址。**
**符号表记录的是「名字 ↔ 地址」的对应关系。**

**查看这张表用 `nm`**：

`Bash`

```bash
nm app.exe
```

`实测数据`
`Text`

```text
$ nm calc.c.obj
0000000000000000 T add
0000000000000000 T factorial
0000000000000000 T sub
0000000000000000 T sum_array

$ nm main.c.obj
0000000000000000 T main
                 U add
                 U factorial
                 U __mingw_printf
                 U sub
                 U sum_array
```

**两相对照就是一个完整的例子**：`calc.c` **定义**了四个函数，
`main.c` **引用**它们，因此在自己这一侧显示为 `U`。
**链接器要做的事，就是把这些 `U` 与那些 `T` 接起来。**

这份对照取自仓库示例 `B-examples/03-build-toolchain/01-cmake-c`（`src/calc.c` 与 `src/main.c`），
复现方式见附录 B.1。

> [!TIP]
> 对**可执行文件**执行 `nm` 会列出大量运行库符号
> （MinGW 的启动代码有数百个）。
> **看自己的符号应当对目标文件执行 `nm`，或对输出做过滤。**

| 标记 | 含义 |
|---|---|
| `T` | 代码段里已定义的符号（函数） |
| `D` | 数据段里已初始化的全局变量 |
| `B` | 未初始化数据段里的全局变量 |
| `U` | **未定义**：这个目标文件引用了它，定义在别处 |

**`U` 是最有用的一栏**：它列出了「还欠着的」符号，
链接器就是靠它去找定义的。**链接错误多半与 `U` 有关。**

**这些内容在《01-编译器/01-编译与链接.md》第 2.4 小节有更详细的说明。**

## 1.2 符号的两种用途

| 用途 | 什么时候用 |
|---|---|
| **链接** | 把不同目标文件里的同名符号接起来 |
| **调试** | 让调试器能按名字下断点、看调用栈 |

**第一种是必需的**——没有符号，链接根本无法进行。
**所以发布版的可执行文件里也有符号表**，只是没有调试信息。

> [!IMPORTANT]
> **发布版并不是「一个符号都没有」。**
> `nm` 在发布版上照样能列出函数名，除非手工 `strip`。

# 第 2 节 两类信息

## 2.1 区分

**可执行文件里可能含有两类信息，用途不同。**

| | 符号表 | 调试信息 |
|---|---|---|
| 内容 | 名字 ↔ 地址 | 地址 ↔ 源码行、类型、变量 |
| 谁需要 | **链接器** | **调试器** |
| 是否必需 | **是**，链接阶段必需 | 否 |
| 发布版是否保留 | 通常保留 | 通常删除 |
| 生成方式 | 自动 | `-g`（GCC）/ `/Zi`（MSVC） |

**两类信息的有无，决定调试时能看到什么**：

`Text`

```text
只有符号表、没有调试信息：
    #0  0x401550 in ?? ()
    #1  0x4015a0 in ?? ()
    断点只能按地址下，不能按函数名

有调试信息：
    #0  compute (a=3, b=4) at calc.c:12
    #1  main () at main.c:8
```

> [!IMPORTANT]
> **差别就在这里**：只有符号表时，调试器认的是地址；
> 有调试信息时，才能把地址对应回源码。

## 2.2 `-g` 到底做了什么

**`-g` 让编译器把「源码与机器码的对照关系」写进目标文件**，具体包括：

| 记录什么 | 例子 |
|---|---|
| 函数名与地址 | `compute` 在 `0x401550` |
| 行号与地址 | `calc.c` 第 12 行从 `0x401568` 开始 |
| 变量名、类型、位置 | `a` 是 `int`，在栈偏移 `-4` |
| 结构体布局 | `Point` 有两个 `int`，各占 4 字节 |
| 类型定义 | `std::string` 的实际结构与成员 |

**后两项是体积的主要来源**：它不只记录你写的代码，
还记录**所有包含进来的头文件里的类型**。**量级见第 6 节。**

# 第 3 节 DWARF

## 3.1 它是什么

**DWARF 是调试信息的公开标准格式**，由 DWARF 标准委员会维护，
GCC 与 Clang 都使用它。

**名字的由来**：它是「Debugging With Attributed Record Formats」的缩写，
同时也是一语双关——DWARF 是 ELF 的「小矮人」（ELF 意为精灵）。

## 3.2 它嵌在文件里

**DWARF 不是一个独立文件**，而是以若干**段（section）**的形式
写在目标文件与可执行文件里。**用 `objdump -h` 可以看到这些段。**

`实测数据`

| 段名 | 大小（十六进制） | 大小（字节） | 内容 |
|---|---|---|---|
| `.debug_info` | `00011eaa` | **73,386** | **主要部分：类型、变量、函数** |
| `.debug_abbrev` | `00000c3f` | 3,135 | 信息的编码格式表 |
| `.debug_line` | `000011ba` | 4,538 | **行号与地址的对照** |
| `.debug_frame` | `00001340` | 4,928 | 调用栈展开信息 |
| `.debug_str` | `0000068f` | 1,679 | 字符串池 |
| `.debug_line_str` | `000005d0` | 1,488 | 行号信息用的字符串 |
| `.debug_rnglists` | `000002ef` | 751 | 地址范围列表 |
| `.debug_aranges` | `00000500` | 1,280 | 地址范围索引 |

**合计约 91,000 字节**，与第 6 节实测的「`-g` 增加 93,033 字节」吻合。

## 3.3 几个段的用途

**`.debug_line` 是最容易理解的一个**：它就是一张「地址 → 文件行号」的表，
调试器显示源码位置靠的就是查它。

`Text`

```text
0x401568  →  calc.c 第 12 行
0x401570  →  calc.c 第 12 行
0x401590  →  calc.c 第 13 行
```

**`.debug_frame` 记录「怎样从当前栈帧回到上一层」**，
调用栈能显示完整的函数链，靠的是它。

**`.debug_info` 最大，因为它记录所有类型与变量的描述。**
它之所以这么大，是因为包含了头文件里的所有类型定义。

## 3.4 调试等级的差别

GCC 的 `-g` 后面可以跟一个级别，级别决定记录多少内容：

| 参数 | 内容 |
|---|---|
| `-g0` | 不生成调试信息 |
| `-g1` | 最少，只有函数与行号 |
| `-g`（默认） | 包含变量与类型 |
| `-g3` | 额外包含宏定义 |

`文档`

> "Level 3 includes extra information, such as all the macro definitions
> present in the program. Some debuggers support macro expansion when you
> use -g3."
>
> —— GCC 手册 §3.11《Options for Debugging Your Program》

**嵌入式工程的工具链常用 `-g3`**，因为它需要调试宏。
**桌面工程用默认的 `-g` 就够。**

# 第 4 节 PDB

## 4.1 它是什么

**PDB 是微软的调试信息格式**，全称 Program Database，
由 MSVC 使用，文件扩展名 `.pdb`。

> [!IMPORTANT]
> **与 DWARF 最重要的差别：PDB 是一个独立文件。**

`Text`

```text
   MSVC 路线                          GCC 路线
   ─────────────                      ─────────────
   app.exe   ← 机器码 + 对 PDB 的引用    app.exe
   app.pdb   ← 调试信息                 ↑
                                       └─ 机器码 + DWARF 在同一个文件里
```

## 4.2 带来的实际后果

| 后果 | 说明 |
|---|---|
| **不能只复制 exe** | 少了 PDB 就没有调试信息 |
| **路径关系要对得上** | exe 里记录了 PDB 的位置，移动后可能找不到 |
| **PDB 可以单独归档** | 发布时 exe 不带调试信息，PDB 存在服务器上 |
| **调试信息与 exe 版本必须匹配** | 不匹配时调试器会拒绝加载 |

**第三条是 PDB 设计的价值所在**：
可以给用户一个干净的 exe，同时自己保留 PDB，
将来用户报告崩溃时用同一个 PDB 分析。

**这一点在《02-调试器/01-原理与使用.md》第 10 节讲内存转储时会再次用到。**

## 4.3 生成方式

`Bash`

```bash
cl /Zi /DEBUG app.c        # /Zi 生成 PDB，/DEBUG 让链接器也产出
```

| 参数 | 作用 |
|---|---|
| `/Zi` | 编译期把调试信息写进 PDB |
| `/Z7` | 把调试信息写进目标文件，**不生成 PDB** |
| `/DEBUG` | 链接期生成 PDB 并嵌入引用 |
| `/DEBUG:FASTLINK` | 只索引不复制，链接快但 PDB 依赖中间文件 |

**`/Z7` 与 `/Zi` 的区别值得记**：
`/Z7` 把调试信息留在各个 `.obj` 里，链接器再合并。
**好处是不依赖 PDB 文件，坏处是每个目标文件都变大、链接更慢。**

# 第 5 节 两种格式对照

## 5.1 对照表

| 维度 | DWARF | PDB |
|---|---|---|
| 标准 | **公开标准** | 微软私有，但格式已公开 |
| 维护者 | DWARF 委员会 | 微软 |
| 生成者 | GCC、Clang | MSVC |
| 存放 | **嵌在目标文件与可执行文件里** | **独立文件** |
| 读取者 | GDB、LLDB、部分工具 | Visual Studio 调试器、WinDbg、LLDB |
| 调试等级 | `-g` / `-g1` / `-g3` | `/Zi` / `/Z7` |
| 能否剥离 | 能，`strip` | 本身就是分离的 |

## 5.2 为什么不能混用

**这是《01-编译器/02-环境配置.md》第 1.1 小节讲过的核心约束**：

`Text`

```text
   gcc 编译  ──→  DWARF  ──→  GDB 能读                  Visual Studio 调试器读不了
   cl 编译   ──→  PDB    ──→  Visual Studio 调试器能读  GDB 读不了
```

**「用哪个编译器」与「用哪个调试器」必须配套。**

**唯一的例外是 LLDB**：它两种格式都支持，
因此 CodeLLDB 扩展既能调 GCC 产物也能调 MSVC 产物。

**这就是本教材给出三条调试路线的原因**，见
《02-调试器/00-本机环境与路线.md》第 1 节。

## 5.3 转换的可能性

| 想做的事 | 是否可行 |
|---|---|
| DWARF 转 PDB | 有工具（如 `pdbparse` 一类），但不完整、不可靠 |
| PDB 转 DWARF | 同上 |
| 同一份代码生成两套 | **可行**，编两遍即可 |

**建议不要指望转换**。需要两套调试信息时，
**用两种编译器各编译一遍**，这是最简便的做法。

# 第 6 节 体积代价

**调试信息不是免费的。** 用同一个探针在两条路线上各编一遍，
可以直接看到它占多少空间。

探针是一个只用到 `<vector>` 与 `<string>` 的小程序；
GCC 侧是 MinGW `g++` 15.2.0，MSVC 侧是 `cl` 19.51，
两侧都是 C++17 的 Debug 配置。**探针源码与完整数据见附录 B.3。**

## 6.1 GCC 路线

`实测数据`

| 配置 | 可执行文件 | 相对基准 |
|---|---|---|
| 不带 `-g` | 116,571 字节 | 1.00 |
| **带 `-g`** | **209,604 字节** | **1.80** |
| **带 `-g` 后 `strip`** | **48,128 字节** | **0.41** |

**`-g` 让文件变成 1.80 倍**，多出的 93,033 字节全部是 DWARF 段，
与第 3.2 小节列出的段大小合计吻合。

**`strip` 之后比「不带 `-g`」还小，这一条最值得注意。**
可执行文件里除了机器码还有符号表；`strip` 把符号表与调试信息一起删掉，
而「不带 `-g`」只是没有调试信息，**符号表仍然在**。
三种产物的关系因此是：
**只有机器码 < 机器码加符号表 < 机器码加符号表加 DWARF。**

**加了 `-O2` 之后体积反而下降**：优化把代码改短，
一部分调试信息也随之减少。这一组数据见附录 B.3。

## 6.2 MSVC 路线

`实测数据`

| 配置 | 可执行文件 | PDB | 合计 |
|---|---|---|---|
| 不带 `/Zi` | 163,328 字节 | 不生成 | 163,328 字节 |
| **带 `/Zi`** | **762,880 字节** | **7,770,112 字节** | **8,532,992 字节** |

**PDB 是可执行文件的 10.19 倍，两者合计是发布产物的 52 倍。**

**PDB 之所以这么大，是因为它不只记录行号，还记录所有类型定义**——
包括 `#include` 进来的每一个头文件里的每一个结构体、每一个模板实例化。
**探针只有十几行，却带进了整个标准库头文件的类型信息。**

> [!IMPORTANT]
> 带 `/Zi` 时**可执行文件本身也变大了**（163,328 → 762,880 字节）。
> `/Zi` 隐含启用了链接器的 `/DEBUG`，它会把调试段保留在 exe 里，
> 同时生成 PDB。**exe 里保留的是索引，PDB 里是完整信息。**

## 6.3 两点工程含义

**其一，发布版一定要去掉调试信息。**

| 平台 | 做法 |
|---|---|
| GCC | 发布时用 `strip`，或编译加 `-s` |
| MSVC | 发布时用 `/DEBUG:NONE`，或不加 `/Zi` |

**其二，但不要随手删掉 PDB。**

**正确做法是「分离保存」**：

`Text`

```text
   发给用户的          自己留档的
   ──────────          ──────────
   app.exe             app.exe（同一个）
                       app.pdb
                       app.exe 的源码版本号
```

**将来收到崩溃报告时，用留档的 PDB 就能还原出完整的调用栈。**

> [!WARNING]
> **PDB 删掉之后，崩溃报告里只剩一串地址，几乎无法分析。**
> 发给用户的 exe 可以不带调试信息，
> **自己留档的那一份必须与它一一对应**。

# 第 7 节 调试器怎样使用符号

## 7.1 下一次断点的完整过程

以 GDB 里 `break compute` 为例：

`Text`

```text
   你输入：break compute
        │
        ▼
   ① 在调试信息里查找名为 compute 的记录
        │      （查 .debug_info 段）
        ▼
   ② 得到它的地址，例如 0x401550
        │      （查 .debug_line 段验证对应源码行）
        ▼
   ③ 在该地址写入断点指令
        │      （x86 上是 INT3，一个字节 0xCC）
        ▼
   ④ 程序执行到该地址时触发异常，控制权交给调试器
        │
        ▼
   ⑤ 调试器查表：这个地址对应 calc.c 第 12 行
        │
        ▼
   ⑥ 显示源码、变量名与值
```

**第 ① 与第 ⑤ 步完全依赖调试信息。**
没有它，第 ① 步就失败，调试器只能显示地址。

## 7.2 单步执行的原理

**「单步」也依赖调试信息**（用于源码级单步）：

| 单步类型 | 依据 |
|---|---|
| 指令级单步 | CPU 的单步标志，与调试信息无关 |
| **源码级单步** | **查 `.debug_line`，找到下一行的起始地址** |

**这解释了一个现象**：优化过的代码单步时会「跳来跳去」，
因为源码行与机器码不再是一一对应——
一行可能被拆散、合并或删除。见第 7.4 小节。

## 7.3 查看变量

变量的值**不在调试信息里**，而在内存或寄存器里。
调试信息提供的是**「怎么找到它」**：

`Text`

```text
   a 是一个 int，位于当前栈帧基址减 4 的位置
   v 是一个 std::vector<int>，位于栈偏移 -32，
      它的元素在堆上，起始地址存在偏移 -32 处
```

**调试器按这个描述去内存里取值。**

**这也是为什么看 `std::vector` 需要「美化打印」**：
原始结构里有三个指针，直接看只能看到地址。
美化打印器知道怎么按这三个指针把元素读出来。

> [!TIP]
> 本教材的 `launch.json` 里有 `-enable-pretty-printing`，就是打开这个能力。
> 见《01-编译器/02-环境配置.md》第 5.4 小节。

## 7.4 优化对调试信息的破坏

**`-O2` 之后，源码行与机器码的对应关系不再是线性的**：

| 优化做的事 | 对调试的影响 |
|---|---|
| 变量被放进寄存器 | 调试器找不到它的内存位置 |
| 变量被完全消除 | 显示「已优化掉」 |
| 循环展开 | 一行对应多段代码 |
| 函数内联 | 调用栈里看不到那一层 |
| 代码重排 | 单步时顺序与源码不一致 |

**实测对照见《01-编译器/01-编译与链接.md》第 6.2 小节**，
那里给出了 `-O0` 与 `-O2` 的汇编对比。

**这也是 Debug 配置用 `-O0`、Release 用 `-O2` 的原因**：
两者的调试信息「可用程度」差别很大。

# 第 8 节 诊断：断点为什么是空心的

## 8.1 现象

在 VS Code 里下断点后，红点变成**空心灰点**，
悬停提示「未绑定断点」（Unverified breakpoint）。

## 8.2 含义

**「未绑定」的意思是：调试器还没能把这个断点落到某个具体地址上。**

**这是「还没」，不一定是「不能」**：

| 情况 | 说明 |
|---|---|
| 程序还没启动 | 正常现象，启动后自动绑定 |
| 符号还没加载 | 稍等，或检查符号路径 |
| **调试信息缺失** | 真的绑不上 |
| **调试信息与程序不匹配** | 绑到了错误位置，或绑不上 |
| 源码路径映射错误 | 调试器以为源码在别处 |

## 8.3 排查顺序

| 步骤 | 检查什么 |
|---|---|
| 1 | 编译时加 `-g` 了吗（GCC）或 `/Zi`（MSVC） |
| 2 | PDB 与 exe 是同一次编译的产物吗 |
| 3 | 调试器类型与编译器匹配吗（`cppdbg` 对 gcc，`cppvsdbg` 对 cl） |
| 4 | 源码路径对不对（`sourceFileMap` 是否需要） |
| 5 | 程序是否已经启动 |

**第 4 条在跨系统调试时最常见**：
Linux 上的源码路径与 Windows 上的不同，
需要 `sourceFileMap` 做映射。见《02-调试器/02-跨系统调试.md》第 3 节。

## 8.4 另一个相关现象

**调用栈里全是 `??` 和地址**：

`Text`

```text
#0  0x00007ff6a1b21550 in ?? ()
#1  0x00007ff6a1b215a0 in ?? ()
```

**含义与空心断点相同**：没有可用的调试信息。
**在调试系统库时也会看到**，那时需要符号服务器，见下一节。

# 第 9 节 符号服务器

## 9.1 问题

**Windows 系统 DLL（`kernel32.dll`、`ntdll.dll` 等）的 PDB 不在你机器上。**

调试到系统调用时，调用栈会显示成一串地址：

`Text`

```text
#5  0x00007ff8e1a21234 in ?? ()       ← 本来是 ntdll!NtWaitForSingleObject
```

**微软把这些 PDB 放在公开的符号服务器上。**

## 9.2 配置方法

**WinDbg**（在调试会话里执行）：

`Text`

```text
.sympath srv*<本地缓存目录>*https://msdl.microsoft.com/download/symbols
.reload
```

| 部分 | 含义 |
|---|---|
| `srv*` | 表示这是一个符号服务器路径 |
| `<本地缓存目录>` | 下载后缓存到哪 |
| URL | 服务器地址 |

**VS Code 的 `cppvsdbg`** 在 `launch.json` 里配置：

`JSONC`

```jsonc
"symbolSearchPath": "srv*<本地缓存目录>*https://msdl.microsoft.com/download/symbols"
```

**本教材的模板 T13 里有这条配置**，见
《01-编译器/02-环境配置.md》第 7 节。

## 9.3 必须配本地缓存

**不配缓存目录的后果**是每次调试都要重新下载，网络不通时还会长时间无响应；
符号路径没配好时，连 `!analyze -v` 都跑不完。

`实测数据`
`Text`

```text
未配置本地符号路径：!analyze -v 超时
配置本地符号路径后：正常完成
```

见《02-调试器/01-原理与使用.md》第 10 节。

> [!TIP]
> 缓存目录会持续增长，可能达到数 GB，**定期清理即可**。

## 9.4 Linux 侧的对应机制

**Linux 用 `debuginfod`**：

| 方面 | Windows | Linux |
|---|---|---|
| 服务 | 微软符号服务器 | `debuginfod` |
| 配置 | `.sympath` / `symbolSearchPath` | 环境变量 `DEBUGINFOD_URLS` |
| 缓存 | 手工指定目录 | `~/.cache/debuginfod_client/` |
| 本地包装 | 无 | `libc6-dbg` 等 `-dbg` 包 |

`文档`

> "elfutils debuginfod is a client/server in elfutils 0.178+ that
> automatically distributes elf/dwarf/source-code from servers to
> clients such as debuggers across HTTP."
>
> —— elfutils 官方页面《debuginfod》

**Ubuntu 上的常见做法**是装对应的调试包：

`Bash`

```bash
sudo apt install libc6-dbg          # C 运行库的调试符号
```

**装完之后 GDB 进入 `printf` 这类函数时，就能看到源码级信息。**

# 第 10 节 发布时的处理

## 10.1 三条原则

**其一，产物不带调试信息。**

**其二，调试信息单独归档，与产物一一对应。**

**其三，归档要记录「哪份源码、哪个编译器、什么选项」。**

## 10.2 具体做法

**GCC 路线**：

`Bash`

```bash
# 编译时生成，但发布前剥离
gcc -g app.c -o app
objcopy --only-keep-debug app app.debug    # 先把调试信息另存
strip app                                   # 再剥离
objcopy --add-gnu-debuglink=app.debug app   # 记录关联
```

**`--add-gnu-debuglink` 是关键**：它在 exe 里留下一个引用，
告诉调试器「调试信息在旁边的这个文件里」。

**MSVC 路线**：

`Bash`

```bash
cl /Zi app.c /link /DEBUG /PDB:app.pdb
# 发布时不带 .pdb，把它归档到符号服务器或版本库
```

**MSVC 不需要额外处理**，PDB 本来就是独立文件。

## 10.3 归档什么

| 归档项 | 为什么 |
|---|---|
| `.pdb` 或 `.debug` 文件 | 分析崩溃报告必需 |
| 对应的源码版本号 | PDB 只记录路径与行号，要看源码得有那一版 |
| 编译器的完整版本 | 不同版本的 PDB 格式可能不同 |
| 编译选项 | 复现构建需要 |

**只存 PDB 不存源码是不够的**——
将来要看具体代码，得有当时那一版的源码。

## 10.4 不要提交进版本库

**调试信息文件通常很大。**

`实测数据`
`Text`

```text
本章节探针的 PDB        7,770,112 字节
```

**真实工程的 PDB 常见数百 MB，应当放在制品库或符号服务器上，不要进 Git。**

**判断标准与《03-构建工具链/03-包管理.md》第 10.4 小节相同**：
**能由源码与编译命令重新生成的，就不该提交。**

# 附录 B 复现本章节实测

**环境**：Windows x64。GCC 侧为 MinGW `g++` 15.2.0（binutils 2.45），
MSVC 侧为 `cl` 19.51（Visual Studio 18 BuildTools）。
其余环境信息见 `README.md` 的「实测环境」一节。

## B.1 符号表的标记方式

**下面这份单文件源码一次就能看到 `T`、`D`、`B`、`U` 四种标记。**

`C`

```c
/* symbols.c    编译：gcc -std=c23 -c symbols.c -o symbols.obj */
#include <stdio.h>

int counter = 1;                            /* D：数据段里已初始化的全局变量 */
int total;                                  /* B：未初始化的全局变量 */

int add(int a, int b) { return a + b; }     /* T：本文件定义的函数 */
int sub(int a, int b) { return a - b; }     /* T */

int main(void) {
    total = add(1, 2) + sub(5, 3);
    printf("%d\n", total);                  /* printf 不在本文件定义，显示为 U */
    return 0;
}
```

`Bash`

```bash
gcc -std=c23 -c symbols.c -o symbols.obj
nm --extern-only symbols.obj
```

`实测数据`
`Text`

```text
                 U __main
                 U __mingw_printf
0000000000000000 T add
0000000000000000 D counter
0000000000000026 T main
0000000000000014 T sub
0000000000000000 B total
```

**`__main` 来自 MinGW 的启动代码，`__mingw_printf` 就是 `printf`**，
两者都不在本文件里定义，因此显示为 `U`。
`--extern-only` 只列出外部符号，把 `.text`、`.data` 这类段符号滤掉。

**这份探针是 C 代码**；同一份源码按 C++ 编译（`g++ -x c++ -c symbols.c`）时，
两个函数名会被修饰成 `_Z3addii`、`_Z3subii`，`nm` 的输出随之变化。
名字修饰的规则见《01-编译器/00-语言的实现.md》第 4.2 小节。

**第 1.1 小节那份两文件对照**取自示例 `B-examples/03-build-toolchain/01-cmake-c`：
`src/calc.c` 定义四个函数，`src/main.c` 引用它们。
把这两个源文件分别编译成目标文件，再各自执行 `nm --extern-only`，
就能看到一侧全是 `T`、另一侧出现 `U`。

## B.3 体积实测

**探针**（单文件，含 `<vector>` 与 `<string>`）：

`C++`

```cpp
/* probe.cpp    编译：g++ -std=c++17 -g probe.cpp -o a_g.exe */
#include <iostream>
#include <string>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 3, 4, 5};
    std::string s = "sum: ";
    int sum = 0;
    for (int x : v) {
        sum += x;
    }
    s += std::to_string(sum);
    std::cout << s << std::endl;
    return 0;
}
```

GCC 侧的四种配置：

`Bash`

```bash
g++ -std=c++17 probe.cpp -o a_nog.exe          # 不带 -g
g++ -std=c++17 -g probe.cpp -o a_g.exe         # 带 -g
g++ -std=c++17 -g -O2 probe.cpp -o a_g_o2.exe  # 带 -g -O2
cp a_g.exe a_stripped.exe && strip a_stripped.exe
ls -l *.exe
```

MSVC 侧（在「x64 Native Tools Command Prompt」中）：

`Batch`

```bat
cl /nologo /std:c++17 /EHsc /Fe:m_noZi.exe probe.cpp
cl /nologo /std:c++17 /EHsc /Zi /Fe:m_Zi.exe probe.cpp
dir m_*.exe m_*.pdb
```

**完整数据**：

`实测数据`

| 路线 | 配置 | 可执行文件 | PDB | 相对基准 |
|---|---|---|---|---|
| GCC | 不带 `-g` | 116,571 字节 | 不生成 | 1.00 |
| GCC | 带 `-g` | 209,604 字节 | 不生成 | **1.80** |
| GCC | 带 `-g -O2` | 162,228 字节 | 不生成 | 1.39 |
| GCC | 带 `-g` 后 `strip` | 48,128 字节 | 不生成 | **0.41** |
| MSVC | 不带 `/Zi` | 163,328 字节 | 不生成 | 1.00 |
| MSVC | 带 `/Zi` | 762,880 字节 | 7,770,112 字节 | **52.2**（含 PDB） |

**GCC 侧三种产物的层次**：

`Text`

```text
   strip 后      48,128 字节   只有机器码
   不带 -g      116,571 字节   机器码 + 符号表
   带 -g        209,604 字节   机器码 + 符号表 + DWARF
```

**「带 `-g`」与「不带 `-g`」两行之差是 93,033 字节，全部是 DWARF 段。**

**MSVC 侧的比例**：PDB 是 exe 的 10.19 倍（7,770,112 ÷ 762,880）；
两者合计 8,532,992 字节，是发布产物的 52.2 倍（8,532,992 ÷ 163,328）。

**同一份探针换一个 MinGW 发行版或改写源码，绝对字节数都会变**，
这组数字用于比较同一条路线内部的相对大小，正文引用的比例即取自这里。
