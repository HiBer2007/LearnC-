# 第 1 节 执行器在工具链中的位置

## 1.1 四个角色，各司其职

`Text`

```text
   你写的                 工具                   产出
   ─────────            ──────────            ──────────
   CMakeLists.txt  ──→  CMake          ──→   build.ninja
                        （生成器）             或 Makefile

   build.ninja     ──→  Ninja          ──→   调用编译器
   或 Makefile           （执行器）            产出 .o 与 .exe

   main.c          ──→  gcc            ──→   main.o
                        （编译器）

   main.o calc.o   ──→  gcc（链接）     ──→   app.exe
```

**关键点：CMake 与执行器是两层。**

| | CMake | Ninja / Make |
|---|---|---|
| 输入 | 人写的 `CMakeLists.txt` | 机器生成的构建文件 |
| 输出 | 构建文件 | 可执行文件 |
| 何时运行 | 改了 `CMakeLists.txt` 时 | 每次构建 |
| 是否调用编译器 | **否** | **是** |

**在构建目录里打开 `build.ninja`，开头两行是**：

`实测数据`
`Ninja`

```ninja
# CMAKE generated file: DO NOT EDIT!
# Generated by "Ninja" Generator, CMake Version 4.4
```

**这两行说明了两件事**：这个文件是 CMake 生成的，
以及它不该被人手工修改——每次重新配置都会被覆盖。

## 1.2 为什么需要执行器

CMake 完全可以直接调用编译器，为什么还要生成一个中间文件？

| 原因 | 说明 |
|---|---|
| **分工** | 生成器负责表达，执行器负责调度，各自简单 |
| **复用** | 执行器不关心语言，C、C++、Rust 都能用 |
| **效率** | 执行器可以做成极简、极快，见第 4 节 |
| **增量** | 执行器专门处理「哪些该重做」的判断 |

**这与 `03-构建工具链` 板块讲的工具链分层是同一件事**，
见《03-构建工具链/01-构建工具链.md》第 2 节。

# 第 2 节 依赖图

## 2.1 构建的本质是一张有向图

**构建系统做的全部事情，可以概括成一句话**：
维护一张「谁依赖谁」的图，然后按正确的顺序把过期的节点重新生成。

本章节示例工程的依赖图（取自生成的 `build.ninja`）：

`实测数据`
`Text`

```text
        src/main.c                       src/calc.c
        include/calc.h                   include/calc.h
              │                                │
              │ 编译                            │ 编译
              ▼                                ▼
   CMakeFiles/app.dir/src/main.c.obj   CMakeFiles/app.dir/src/calc.c.obj
              │                                │
              └───────────┬────────────────────┘
                          │ 链接
                          ▼
                     bin/app.exe
```

**每个箭头表示「右边变了，左边要重做」。**

## 2.2 图从哪来

**依赖关系不是执行器猜的，是被明确告知的。**
`CMakeLists.txt` 里写明了要编译哪些源文件：

`CMake`

```cmake
add_executable(app
    src/main.c
    src/calc.c
)
```

CMake 据此知道：`app.exe` 依赖这两个源文件编译出的 `.obj`。

**但头文件依赖不在 `CMakeLists.txt` 里。** 源文件中写了 `#include "calc.h"`，
依赖关系是**编译器发现的**，并写进一个 `.d` 文件告诉执行器。
`build.ninja` 里的对应行是：

`实测数据`
`Ninja`

```ninja
build CMakeFiles/app.dir/src/main.c.obj: C_COMPILER__app_unscanned_Debug C$:/.../src/main.c || cmake_object_order_depends_target_app
  DEP_FILE = CMakeFiles\app.dir\src\main.c.obj.d
  FLAGS = -g -std=gnu17 -g -Wall -Wextra -finput-charset=UTF-8 -fexec-charset=GBK
```

冒号左边是**输出**，右边依次是**用哪条规则**与**输入源码**；
`DEP_FILE` 指明头文件依赖从哪个文件读，`FLAGS` 是传给编译器的参数。
路径里的冒号写作 `$:`，因为 Ninja 用 `$` 作转义符——
这是机器生成文件的特点，人不用手写。

**`DEP_FILE` 这一行就是头文件依赖的来源。** CMake 在编译命令里加了
生成依赖文件的参数，把 `.d` 路径指向它；这条规则定义在 `CMakeFiles/rules.ninja` 里：

`实测数据`
`Ninja`

```ninja
rule C_COMPILER__app_unscanned_Debug
  depfile = $DEP_FILE
  deps = gcc
  command = ... gcc.exe $DEFINES $INCLUDES $FLAGS -MD -MT $out -MF $DEP_FILE -o $out -c $in
```

`-MD` 让它生成依赖文件，`-MT $out` 指定依赖文件里的目标名，
`-MF $DEP_FILE` 指定写到哪个路径；`depfile` 与 `deps = gcc`
则告诉 Ninja 去哪读这份依赖。**没有这一步，执行器就不知道头文件变了要重编。**

> [!TIP]
> 这一组参数由 CMake 生成，不由使用者手写。
> 不同生成器、不同版本、不同工具链的具体写法可能不同，
> 需要核实时查看 `build.ninja` 与 `CMakeFiles/rules.ninja`。

**换一套工具链，写法就会变**：STM32CubeMX 生成的 ARM 工具链文件里写的是
`-MMD -MP`，作用相同而来源不同（见附录 C.2）。
**读别人的文档时不要照着推断本机用了什么参数，以自己构建目录里的实际内容为准。**

## 2.3 拓扑排序

**依赖图决定了执行顺序**，规则很简单：

`Text`

```text
一个节点只有在它依赖的所有节点都完成之后，才能开始。
```

这个顺序由**拓扑排序**算出。它保证了不会出现
「先链接、后编译」这种错误顺序。

**同时依赖时谁先谁后无所谓**——
只要满足「被依赖的先做」，任意顺序都对。**这正是并行构建的基础**，见第 7 节。

# 第 3 节 Makefile

## 3.1 规则的写法

Makefile 的基本单位是**规则**：

`Makefile`

```makefile
目标: 依赖...
	命令
```

> [!WARNING]
> 命令前面必须是 Tab 字符，不能用空格。
> 这是 Make 的历史遗留要求，也是常见的入门障碍。

一个手写的小例子：

`Makefile`

```makefile
app.exe: main.o calc.o
	gcc main.o calc.o -o app.exe

main.o: main.c calc.h
	gcc -c main.c -o main.o

calc.o: calc.c calc.h
	gcc -c calc.c -o calc.o
```

`app.exe` 依赖两个 `.o`；
当任一 `.o` 比 `app.exe` 新时，执行下面那行命令重建 `app.exe`。

## 3.2 CMake 生成的 Makefile 长什么样

`cmake -G "MinGW Makefiles"` 生成的 `Makefile` 开头是：

`实测数据`
`Makefile`

```makefile
# CMAKE generated file: DO NOT EDIT!
# Generated by "MinGW Makefiles" Generator, CMake Version 4.4

# Default target executed when no arguments are given to make.
default_target: all
.PHONY : default_target

# Allow only one "make -f Makefile2" at a time, but pass parallelism.
.NOTPARALLEL:

# Disable implicit rules so canonical targets will work.
.SUFFIXES:
```

`.PHONY : default_target` 声明 `default_target` 不是文件，是纯动作；
`.NOTPARALLEL:` 限制某些目标不能并行。**最后一行尤其重要**：
`.SUFFIXES:` **清空内置规则后缀**，Make 内置了大量隐式规则
（看到 `.c` 就自动知道怎么编成 `.o`），CMake 把它们全部禁用，
是为了**完全控制每一条编译命令**，不让 Make 自作主张。

## 3.3 为什么不建议手写 Makefile

| 问题 | 说明 |
|---|---|
| 头文件依赖要手工维护 | 每加一个 `#include` 都要改 Makefile |
| 不可移植 | Windows 与 Linux 的命令行写法不同 |
| 没有跨平台条件判断 | 平台差异要靠 shell 脚本绕 |
| Tab 与空格 | 一个看不见的字符就能让整个文件失效 |

**手写 Makefile 适合很小的项目**，一旦超过十几个文件，
维护成本就会超过它的简单性带来的好处。

# 第 4 节 Ninja

## 4.1 设计取舍：把表达力让出去

**Ninja 把「表达力」交给生成它的程序，自己只按依赖图把命令跑起来。**

`文档`

> "Where other build systems are high-level languages, Ninja aims to be an assembler."
>
> "Ninja contains the barest functionality necessary to describe arbitrary
> dependency graphs. Its lack of syntax makes it impossible to express complex
> decisions."
>
> —— Ninja 手册，Philosophical overview

**「便于手写构建文件」也在手册里被列为非目标**，`build.ninja` 应当由别的程序生成。
落到语法上，Ninja 只有两种语句：

`Ninja`

```ninja
build 输出: 规则 输入...          # 构建语句
  变量 = 值                       # 变量赋值（缩进在 build 下面）
rule 规则名                       # 规则定义
  command = ...
```

**没有条件判断，没有循环，没有函数。**
因为这些都能在 CMake 阶段算完。

## 4.2 与 CMake 的分工

本章节示例的 `build.ninja` 里有三条构建语句：

`实测数据`
`Ninja`

```ninja
build CMakeFiles/app.dir/src/main.c.obj: C_COMPILER__app_unscanned_Debug C$:/.../src/main.c
  FLAGS = -g -std=gnu17 -g -Wall -Wextra -finput-charset=UTF-8 -fexec-charset=GBK

build CMakeFiles/app.dir/src/calc.c.obj: C_COMPILER__app_unscanned_Debug C$:/.../src/calc.c
  FLAGS = -g -std=gnu17 -g -Wall -Wextra -finput-charset=UTF-8 -fexec-charset=GBK

build bin/app.exe: C_EXECUTABLE_LINKER__app_Debug CMakeFiles/app.dir/src/main.c.obj CMakeFiles/app.dir/src/calc.c.obj
  FLAGS = -g
```

**这三条语句就是整张依赖图。** 前两条说明两个 `.obj` 各依赖自己的源文件；
第三条最值得看——`app.exe` 的输入是那两个 `.obj`，
所以「改了 `main.c` 之后要重新链接」这件事，
是从图上直接读出来的，不需要额外规则。

## 4.3 别名目标

`build.ninja` 末尾还有几行：

`实测数据`
`Ninja`

```ninja
build app: phony bin/app.exe
build app.exe: phony bin/app.exe
build all: phony bin/app.exe
```

**`phony` 表示「只是个名字，不产出文件」。**
这几行让你可以用 `ninja app`、`ninja all` 等简写来构建。
`make` 里的 `.PHONY` 是同一类东西。

## 4.4 为什么 Ninja 快

| 方面 | 说明 |
|---|---|
| **语法极简** | 解析开销小 |
| **不做表达** | 没有条件与循环，不需要求值 |
| **依赖检查优化** | 用 `stat` 批量查询，而非逐个 shell 调用 |
| **无 shell 开销** | 直接创建进程，不经过 `sh -c` |
| **只剩一件事** | 只负责调度与执行 |

**`Make` 的启动开销主要来自三处**：
解析 Makefile、求值变量与函数、以及大量 `$(shell ...)` 调用。

**实测对照见第 8 节。**

# 第 5 节 增量构建

## 5.1 判断依据：时间戳

执行器判断「要不要重做」的依据是**文件修改时间**：

`Text`

```text
   源文件 main.c          10:00
   目标文件 main.c.obj    10:05
   ─────────────────────────────
   main.c 比 .obj 旧    →  不重编

   改动后 main.c          10:10   ← 变新了
   目标文件 main.c.obj    10:05
   ─────────────────────────────
   main.c 比 .obj 新    →  重新编译
```

**规则是：目标的修改时间早于任一依赖，就重做。**

## 5.2 只做必要的部分

改一行 `main.c` 后重新构建：

`实测数据`
`Text`

```text
# 改一行 src/main.c 之后
[1/2] Building C object CMakeFiles/app.dir/src/main.c.obj
[2/2] Linking C executable bin\app.exe

# 紧接着再运行一次，无任何改动
ninja: no work to do.        # 用时 0.07 秒
```

**只做了两件事**：编译改动的那个文件，然后重新链接。`calc.c` **完全没有被编译**。
第二次运行时，执行器检查了一遍时间戳，发现没有过期的东西，直接退出。

## 5.3 改头文件的影响

若 `include/calc.h` 被 `main.c` 与 `calc.c` 同时包含：

`Text`

```text
   改动 calc.h
        │
        ▼
   calc.h 的时间变新
        │
        ├──→ main.c.obj 过期（它依赖 calc.h）  → 重编
        └──→ calc.c.obj 过期（它依赖 calc.h）  → 重编
                    │
                    ▼
             两者都变新 → app.exe 过期 → 重新链接
```

**这正是《01-编译器/01-编译与链接.md》第 3.2 小节讲的现象的底层机制。**

**头文件依赖从哪来**：编译时 CMake 传入的参数让 gcc 生成 `.d` 文件，
里面列出该源文件实际包含的头文件。执行器读这个文件补全依赖图。

> [!WARNING]
> **如果 `.d` 文件没生成**，执行器就不知道头文件的存在，
> 改了头文件不会触发重编。这是「改了没反应」的常见原因。

# 第 6 节 时间戳的失效场景

时间戳机制简单有效，但有几类明确的失效情况：
一旦判断出错，没有别的办法，只能删掉构建目录重新配置（见第 9.4 小节）。

## 6.1 改了却没重编

| 场景 | 原因 |
|---|---|
| 系统时间被调回过去 | 新文件的时间戳反而更旧 |
| 从压缩包解出源码 | 解压工具可能保留原始时间，比构建产物旧 |
| 切换 Git 分支 | 切换会更新文件时间，但若分支间文件相同则不变 |
| 网络文件系统时钟不同步 | 客户端与服务器时间有偏差 |
| `.d` 文件缺失 | 头文件依赖根本没进图 |

## 6.2 没改却重编

| 场景 | 原因 |
|---|---|
| 构建脚本每次都 touch 某文件 | 时间戳总在变新 |
| 生成的代码每次内容都不同 | 即使逻辑一样也算改动 |
| 用了 `ALWAYS` 之类的强制标记 | 明确要求每次都做 |

# 第 7 节 并行构建

## 7.1 为什么可以并行

**回到第 2.3 小节的拓扑排序**：
只要满足「被依赖的先做」，同层的节点**任意顺序都对**。

`Text`

```text
        main.c.obj        calc.c.obj
             │                 │
             └────────┬────────┘
                      ▼
                  app.exe
```

`main.c.obj` 与 `calc.c.obj` **互不依赖**，因此可以同时编译。

## 7.2 怎么开启

| 工具 | 参数 | 说明 |
|---|---|---|
| Ninja | `-j N` | **默认已经是并行**，自动取 CPU 核心数 |
| Make | `-j N` | **默认串行**，必须显式指定 |
| CMake 包装 | `cmake --build build -j N` | 转交给下层执行器 |

**这是 Ninja 与 Make 的一个重要差别。**
`cmake --build` 不加 `-j` 时，用的是下层执行器自己的默认值：

`文档`

> "Build in parallel using the given number of jobs. If <jobs> is omitted the
> native build tool's default number is used. The CMAKE_BUILD_PARALLEL_LEVEL
> environment variable specifies a default parallel level when this option
> is not given."
>
> —— `cmake --build` 的快速帮助（CMake 4.4.3）

**因此走 Ninja 时不必手工加 `-j`，走 Make 时要显式指定。**

## 7.3 并行的限度

**不是并行度越高越好**：

| 限制 | 说明 |
|---|---|
| 内存 | 每个编译进程都要占用内存，并行太多会耗尽 |
| 磁盘 | 大量同时读写会互相拖慢 |
| 依赖链 | 关键路径上的节点必须串行 |
| 链接阶段 | 通常只有一个链接动作，无法并行 |

**经验做法**：并行度取 CPU 核心数，或核心数的 1 到 2 倍。
内存较小的机器应取更小的值。

## 7.4 并行带来的问题

**并行构建会把输出顺序打乱**，报错信息可能交错。
排查时可以先改成串行（`-j 1`），让输出变清晰。

**另外**：若 `CMakeLists.txt` 里漏写了依赖关系，
串行时可能碰巧正常，并行时才暴露出来。
**并行构建因此也能当一种检查手段。**

# 第 8 节 实测对照

## 8.1 环境与对象

**环境**：Windows 11（16 核 / 24 逻辑处理器），CMake 4.4.3，Ninja 1.13.2，
MinGW `gcc` 15.2.0；构建对象为 `B-examples/03-CMake-C`，
含 2 个源文件与 1 个头文件。

## 8.2 结果

`实测数据`

| 阶段 | Ninja | MinGW Makefiles |
|---|---|---|
| 首次构建 | **0.28 秒** | **0.93 秒** |
| 增量构建（改 1 个源文件） | **0.28 秒** | **0.39 秒** |
| **产物大小** | **85,468 字节** | **85,468 字节** |

## 8.3 三点结论

**其一，Ninja 在首次构建上快约 3.3 倍**：0.28 秒对 0.93 秒。

**其二，增量构建的差距缩小，但 Ninja 仍占优**：0.28 秒对 0.39 秒。

**其三，也是最重要的一点：产物字节完全相同**，
两个生成器都产出 85,468 字节的 `app.exe`。
**这证明「用哪个执行器」不影响结果，只影响速度。**

> [!IMPORTANT]
> `Ninja` 与 `Make` 之间可以自由切换，
> 排查问题时换成另一个执行器不会改变行为。
> 但 `Make` 默认串行，切换时要注意并行度设置。

**本章节的实测对象规模很小，两者的绝对差距都在毫秒级。**
**在数千文件的大工程上，差距会被放大到分钟级。**

**配置阶段与无改动时的耗时、生成的构建文件行数见附录 C.1。**

# 第 9 节 排查构建问题

## 9.1 先分清是哪一层出的问题

`Text`

```text
   报错出现在 cmake -S . -B build      →  配置阶段，看 CMakeLists.txt
   报错出现在 cmake --build build      →  构建阶段，看源码与编译参数
```

**这与《03-构建工具链/01-构建工具链.md》第 3.8 小节讲的求值模型是同一件事。**

## 9.2 构建阶段的常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `ninja: no work to do.` 但代码没更新 | 时间戳判断出错 | 删除构建目录重新配置 |
| 改了头文件没重编 | `.d` 文件缺失或没被读到 | 检查构建目录里有没有 `.d`，以及 `DEP_FILE` 是否指向它 |
| `undefined reference` | 缺源文件或库 | 检查 `add_executable` 与 `target_link_libraries` |
| 找不到头文件 | 路径没传 | 检查 `target_include_directories` |
| 每次都全量重编 | 有文件时间戳总在变 | 找出被 touch 的文件 |
| 并行时报错、串行正常 | 依赖没写全 | 补全 `add_executable` 的源文件列表 |
| 输出信息交错难以阅读 | 并行构建 | 改 `-j 1` |
| 报错说缺某个 `.o` | 上一次构建被中断 | 重新构建，或删构建目录 |

## 9.3 查看实际执行的命令

**Ninja**：

`Bash`

```bash
ninja -C build -v             # 打印完整命令行
ninja -C build -t commands    # 只列出命令，不执行
ninja -C build -t targets     # 列出所有目标
```

**Make**：

`Bash`

```bash
make -C build VERBOSE=1       # CMake 生成的 Makefile 支持这个变量
```

**更简便的办法**：打开 `CMAKE_EXPORT_COMPILE_COMMANDS` 后，
构建目录里会生成 `compile_commands.json`，
**逐条记录每个源文件的完整编译命令**。

## 9.4 清理与重建

| 目的 | 命令 |
|---|---|
| 重新构建全部 | `cmake --build build --clean-first` |
| 重新配置 | `cmake -S . -B build --fresh` |
| 彻底重来 | 删除 `build/` 目录后重新配置 |

**删除构建目录是排查构建问题的第一步。**
它把所有缓存状态清空，代价只是一次全量构建。

# 第 10 节 术语表

| 术语 | 英文 | 含义 |
|---|---|---|
| 构建执行器 | Build executor | 按依赖图调用编译器的程序，如 Ninja、Make |
| 构建文件 | Build file | 执行器的输入，由生成器产出 |
| 规则 | Rule | 一条「如何从输入得到输出」的模板 |
| 目标 | Target | 构建产物的名字，如 `app.exe` |
| 依赖 | Dependency | 目标所依赖的输入 |
| 依赖图 | Dependency graph | 所有目标与依赖构成的有向图 |
| 拓扑排序 | Topological sort | 由依赖图得出合法执行顺序的算法 |
| 增量构建 | Incremental build | 只重做时间戳过期的部分 |
| 全量构建 | Clean build | 从零重建全部 |
| 伪目标 | Phony target | 只作为名字、不产出文件的目标 |
| 隐式规则 | Implicit rule | Make 内置的「看到后缀就知道怎么做」的规则 |
| 关键路径 | Critical path | 依赖图里最长的那条链，决定最短构建时间 |
| 并行构建 | Parallel build | 同时执行互不依赖的节点 |

## C.2 依赖参数的两种写法

桌面 CMake 配 Ninja 时，`-MD -MT -MF` 这一组参数由 CMake 自动注入。
换一套工具链就可能换成别的写法。STM32CubeMX 生成的 ARM 工具链文件里，
依赖参数是手写的（见 `A-教学素材/07-CubeMX编译链路/gcc-arm-none-eabi.cmake` 第 28 行）：

`实测数据`
`CMake`

```cmake
set(CMAKE_ASM_FLAGS "${CMAKE_C_FLAGS} -x assembler-with-cpp -MMD -MP")
```

| 场景 | 参数 | 谁写的 |
|---|---|---|
| 桌面 CMake + Ninja | `-MD -MT -MF` | **CMake 自动注入** |
| CubeMX 生成的 ARM 工具链文件 | `-MMD -MP` | **工具链文件里手写** |

**两者作用相同，都是生成依赖文件**，只是写法与使用场景不同。
