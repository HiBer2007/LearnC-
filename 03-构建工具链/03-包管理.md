# 第 1 章 为什么需要包管理

## 1.1 把库源码复制进仓库的问题

初学者常见的做法是把第三方源码整个复制进项目：

```
project/
├── src/
├── include/
└── third_party/
    ├── json/          ← 复制的
    ├── zlib/          ← 复制的
    └── fmt/           ← 复制的
```

**四种代价**：

| 代价 | 说明 |
|---|---|
| **仓库膨胀** | 第三方代码往往比自己的代码多几十倍 |
| **更新困难** | 想升级版本，要手工对比替换 |
| **安全漏洞** | 上游修了漏洞，你不知道 |
| **许可混乱** | 第三方代码各有各的许可证，容易被忽略 |

**最后一条尤其容易出问题**：把 GPL 代码复制进闭源项目，
会带来法律后果。详见[版权与许可说明.md](../版权与许可说明.md)。

## 1.2 包管理要解决的问题

| 问题 | 包管理器的做法 |
|---|---|
| 去哪里拿 | 从官方源或指定仓库下载 |
| 拿哪个版本 | 按版本约束解析 |
| 依赖的依赖怎么办 | **递归解析**，一并装上 |
| 编译参数怎么给 | 通过 CMake 配置文件自动传递 |
| 换平台怎么办 | 按 triplet（目标平台）分别构建 |

**「依赖的依赖」是最容易被低估的一点。**
你只声明要用 `cpr`，但 `cpr` 自己依赖 `curl` 与 `zlib`，
包管理器要能把这些一并解析出来。

# 第 2 章 四种获取方式

## 2.1 总览

```
   ┌───────────────────────────────────────────────────────────┐
   │  ① find_package                                           │
   │     找【已经装好】的库                                      │
   │     库从哪来：系统包管理器、手工编译安装、vcpkg 预装          │
   ├───────────────────────────────────────────────────────────┤
   │  ② FetchContent                                           │
   │     配置阶段从【源码仓库】下载并一起编译                      │
   │     适合：库很小、想固定到某个提交                           │
   ├───────────────────────────────────────────────────────────┤
   │  ③ vcpkg                                                  │
   │     独立包管理器，用 manifest 声明依赖                       │
   │     适合：依赖较多、需要统一版本与跨平台                      │
   ├───────────────────────────────────────────────────────────┤
   │  ④ Conan                                                  │
   │     独立包管理器，功能更强、配置更复杂                        │
   │     适合：需要二进制缓存、多配置矩阵                          │
   └───────────────────────────────────────────────────────────┘
```

## 2.2 一个常见的组合

**真实做法往往是组合使用**：

```cmake
# 依赖由 vcpkg 提供（通过工具链文件接入）
find_package(nlohmann_json CONFIG REQUIRED)
find_package(yaml-cpp REQUIRED)

# 自己仓库里的子模块，源码就在本地
add_subdirectory(nbtcpp EXCLUDE_FROM_ALL)

# 很小的纯头文件库，直接下载
FetchContent_Declare(xxhash GIT_REPOSITORY ... GIT_TAG ...)
FetchContent_MakeAvailable(xxhash)
```

**判断依据**：

| 库的情况 | 用哪种 |
|---|---|
| 大、编译慢、多项目共用 | `find_package` + vcpkg |
| 就在自己仓库里 | `add_subdirectory` |
| 小、纯头文件、想固定版本 | `FetchContent` |
| 需要细粒度控制二进制 | Conan |

# 第 3 章 `find_package`

## 3.1 基本用法

```cmake
find_package(ZLIB REQUIRED)
find_package(nlohmann_json CONFIG REQUIRED)
find_package(Qt6 REQUIRED COMPONENTS Widgets Network Core)
```

| 部分 | 含义 |
|---|---|
| `ZLIB` | 包名 |
| `REQUIRED` | **找不到就报错**停止配置；不加则只是设置一个变量 |
| `CONFIG` | 指定查找模式，见 3.2 节 |
| `COMPONENTS` | 只要求该包的部分组件 |

## 3.2 两种查找模式

**这是 `find_package` 最容易混淆的地方。**

| | MODULE 模式 | CONFIG 模式 |
|---|---|---|
| 找什么文件 | `FindXXX.cmake` | `xxx-config.cmake` 或 `XXXConfig.cmake` |
| 谁提供 | **CMake 自带**，或项目自己写 | **库的安装过程生成** |
| 位置 | `<CMake>/share/cmake-<版本>/Modules/` | 库的安装目录下 |
| 是否精确 | 靠模式匹配猜路径与库名 | 库自己声明的，**准确** |
| 覆盖范围 | 只覆盖常见库 | 每个支持 CMake 的库都有 |

**默认行为**：不写模式时，**先试 MODULE，失败再试 CONFIG**。

**为什么推荐显式写 `CONFIG`**：

```cmake
find_package(nlohmann_json CONFIG REQUIRED)    # 明确要求用库自己提供的配置
```

因为 MODULE 模式依赖 CMake 自带的 `FindXXX.cmake` 脚本去**猜**，
而 `CONFIG` 模式是库自己给出的准确信息——
包括它需要哪些编译定义、链接哪些子库。

**本教材案例工程的用法**（`NeoServerUpdateModpack/CMakeLists.txt`，**原文**）：

```cmake
find_package(nlohmann_json CONFIG REQUIRED)
find_package(Lua REQUIRED)
find_package(ZLIB REQUIRED)
find_package(libzippp CONFIG REQUIRED)
find_package(cpr CONFIG REQUIRED)
```

**可以看到两种模式混用**：`Lua` 与 `ZLIB` 用 MODULE 模式
（这两个比较老，CMake 自带查找脚本），其余用 CONFIG。

## 3.3 找到之后怎么用

```cmake
find_package(ZLIB REQUIRED)

add_executable(app main.c)
target_link_libraries(app PRIVATE ZLIB::ZLIB)
```

**注意 `ZLIB::ZLIB` 这个写法**——带 `::` 的名字是**导入目标**。

**为什么用它而不是用变量**：老式写法是

```cmake
include_directories(${ZLIB_INCLUDE_DIRS})    # 旧式
target_link_libraries(app ${ZLIB_LIBRARIES})
```

**这类变量可能不存在**，或者只包含库文件而漏掉编译定义。
**导入目标把「头文件路径 + 库文件 + 编译选项 + 依赖的依赖」
打包在一起**，链接它一个就够了。

**这与《03-构建工具链/01-构建工具链.md》第 4.4 节讲的
`PUBLIC` / `PRIVATE` 传递是同一套机制。**

## 3.4 找不到时报什么错

```
CMake Error at CMakeLists.txt:12 (find_package):
  By not providing "FindZLIB.cmake" in CMAKE_MODULE_PATH this project has
  asked CMake to find a package configuration file provided by "ZLIB", but
  CMake did not find one.
```

**排查顺序**：

| 步骤 | 做法 |
|---|---|
| 1 | 确认库**确实装了**，而不只是下载了源码 |
| 2 | 确认 `CMAKE_PREFIX_PATH` 含库的安装位置 |
| 3 | 确认模式写对（有的库只提供 CONFIG） |
| 4 | 打印变量看看：`message(STATUS "CMAKE_PREFIX_PATH=${CMAKE_PREFIX_PATH}")` |

**`CMAKE_PREFIX_PATH` 是最常用的手段**：把库的安装根目录告诉 CMake。

# 第 4 章 `FetchContent`

## 4.1 用法

```cmake
include(FetchContent)

FetchContent_Declare(
    googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        v1.14.0
)

FetchContent_MakeAvailable(googletest)
```

**它做了什么**：

```
   配置阶段
       │
       ├── 从 Git 克隆到 build/_deps/ 下
       ├── 把该目录当作 add_subdirectory 引入
       └── 于是它的 target 就可以直接链接
```

**注意 `GIT_TAG` 是关键**。写分支名（如 `main`）会让构建结果
随上游变化，无法复现。**应当写具体的标签或提交哈希。**

## 4.2 适合与不适合

| 适合 | 理由 |
|---|---|
| 纯头文件库 | 没有编译负担 |
| 很小的库 | 编译几秒钟 |
| 想固定在某个提交 | 不受上游变动影响 |
| 不想额外装包管理器 | 只要有 Git 就行 |

| 不适合 | 理由 |
|---|---|
| 大库（如 Qt、LLVM） | 每次新构建目录都要重新编译，几十分钟起 |
| 需要多项目共享 | 每个项目各编译一份，浪费磁盘与时间 |
| 网络受限环境 | 配置阶段必须能访问 Git 仓库 |

**注意 `FetchContent` 是「每次配置都下载」还是「只下一次」**：
CMake 会把内容放在构建目录里，
**删掉构建目录就会重新下载**。

## 4.3 与 `ExternalProject` 的区别

CMake 里还有一个 `ExternalProject_Add`，两者差别值得说明：

| | `FetchContent` | `ExternalProject_Add` |
|---|---|---|
| 下载时机 | **配置阶段** | 构建阶段 |
| 能否直接链接它的 target | **能** | 不能，需手工指定路径 |
| 适用 | 想当普通依赖用 | 想在构建时才准备（如工具链） |

**绝大多数场景用 `FetchContent`**，
`ExternalProject_Add` 主要用于「构建过程中才需要的工具」。

# 第 5 章 vcpkg

## 5.1 它是什么

**vcpkg 是微软开源的 C/C++ 包管理器**，与 CMake 集成紧密。

**核心特点**：

| 特点 | 说明 |
|---|---|
| 清单模式 | 依赖写在 `vcpkg.json` 里，随仓库走 |
| 源码构建 | 从源码编译，因此能适配你的编译器与运行库设置 |
| 三元组（triplet） | 按目标平台分别构建，如 `x64-windows` |
| 与 CMake 集成 | 通过一个**工具链文件**接入，几乎不需要改 `CMakeLists.txt` |

## 5.2 清单文件

**真实案例**：本教材案例工程的 `vcpkg.json`（**原文**）：

```json
{
  "$schema": "https://raw.githubusercontent.com/microsoft/vcpkg/master/scripts/vcpkg-configuration.schema.json",
  "name": "neoserver-update-modpack",
  "version": "1.0.0",
  "description": "NeoServer 更新整合包管理工具",
  "dependencies": [
    "cmark-gfm",
    "cpr",
    "libzippp",
    "lua",
    "nlohmann-json",
    "spdlog",
    "tomlplusplus",
    "yaml-cpp",
    "webview2",
    "zlib"
  ]
}
```

**十个依赖，一个文件声明完。**

**注意这里没有写「cpr 依赖 curl」这类信息**——
vcpkg 会从自己的端口定义里**递归解析**出完整的依赖树。

**版本约束的写法**：默认不指定版本时，vcpkg 用它的基线版本。
要固定版本用 `overrides`：

```json
{
  "dependencies": [ "fmt" ],
  "overrides": [
    { "name": "fmt", "version": "10.2.1" }
  ]
}
```

## 5.3 接进 CMake

**关键在一个工具链文件**。在 `CMakePresets.json` 里（**原文的做法**）：

```json
"cacheVariables": {
  "CMAKE_TOOLCHAIN_FILE": "<vcpkg>/scripts/buildsystems/vcpkg.cmake"
}
```

> **路径说明**：原文里写的是本机的绝对路径，
> 此处替换为占位符 `<vcpkg>`，指 vcpkg 的安装根目录。

**这个工具链文件做了什么**：

```
   配置阶段启动
       │
       ▼
   读 vcpkg.json ──→ 解析依赖树
       │
       ▼
   检查 vcpkg_installed/ 里是否已装
       │  缺少的
       ▼
   下载并编译依赖 ──→ 装到 vcpkg_installed/<triplet>/
       │
       ▼
   把安装目录加进 CMAKE_PREFIX_PATH
       │
       ▼
   于是 find_package 就能找到它们
```

**这就是为什么 `CMakeLists.txt` 里不需要写任何 vcpkg 相关的东西**——
接入点在工具链文件，不在工程文件。

## 5.4 构建后的目录

**实测**：案例工程构建后的 `vcpkg_installed/` 结构：

```
vcpkg_installed/
├── vcpkg/                     vcpkg 自身的记录
└── x64-windows/               ← triplet 名
    ├── info/
    ├── updates/
    ├── compiler-file-hash-cache.json
    ├── manifest-info.json
    ├── status
    └── vcpkg-running.lock
```

**`x64-windows` 就是 triplet**：它同时编码了架构（x64）与目标平台（windows）。
换 32 位就是 `x86-windows`，换静态运行库就是 `x64-windows-static`。

**为什么这个目录在工程里而不在系统里**：
清单模式下 vcpkg 把依赖装到**构建目录旁边**，
因此不同工程可以用不同版本的同一个库，互不干扰。

> **注意**：`vcpkg_installed/` 与 `build/` 一样属于构建产物，
> **不应提交进版本库**，应当写进 `.gitignore`。

## 5.5 常用命令

```bash
vcpkg install                 # 按当前目录的 vcpkg.json 安装依赖
vcpkg list                    # 列出已安装的包
vcpkg search <名字>            # 搜索可用的包
vcpkg x-update-baseline       # 更新基线版本
```

**版本信息**（**实测**，本机）：

```
vcpkg package management program version 2026-05-27-d5b6777d666efc1a7f491babfcdab37794c1ae3e
```

**vcpkg 是滚动发布的**，没有语义化的版本号，
而是用日期加提交哈希标识。**这意味著「升级 vcpkg」就等于「换基线」**，
依赖的版本可能一并变化。

# 第 6 章 Conan

## 6.1 它是什么

**Conan 是另一个 C/C++ 包管理器**，出现早于 vcpkg，
设计上更强调**二进制缓存**与**多配置矩阵**。

| 方面 | Conan | vcpkg |
|---|---|---|
| 主要分发形式 | 二进制包为主 | 源码构建为主 |
| 配置文件 | `conanfile.txt` / `conanfile.py` | `vcpkg.json` |
| 私有仓库 | 支持自建服务器 | 相对简单 |
| 多配置 | **配置矩阵更灵活** | triplet 机制 |
| 学习成本 | 较高 | 较低 |
| 与 CMake 集成 | 生成工具链文件 | 提供工具链文件 |

## 6.2 配置文件

**真实案例**：同一工程的 `conanfile.txt`（**原文**）：

```ini
[requires]
qt/5.15.14
nlohmann_json/3.11.3

[generators]
CMakeToolchain
CMakeDeps

[options]
qt:shared=True
qt:with_network=True
qt:with_widgets=True
```

| 段 | 含义 |
|---|---|
| `[requires]` | 依赖与版本，`包名/版本` |
| `[generators]` | **生成什么给 CMake 用** |
| `[options]` | 传给具体包的构建选项 |

**两个 generator 的作用**：

| 生成器 | 产出 | 用途 |
|---|---|---|
| `CMakeToolchain` | 工具链文件 | 告诉 CMake 用哪个编译器、什么配置 |
| `CMakeDeps` | `xxx-config.cmake` 文件 | **让 `find_package` 能找到这些依赖** |

**这正是 Conan 与 CMake 的接合点**：
Conan 生成一批 `xxx-config.cmake`，
于是 `CMakeLists.txt` 里照常用 `find_package`，不需要知道 Conan 的存在。

> **注意**：这与 vcpkg 的思路相同——
> **都在工具链层面接入，不侵入 `CMakeLists.txt`**。
> 这是成熟的包管理器普遍采用的做法。

## 6.3 使用流程

```bash
conan install . --output-folder=build --build=missing
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake
cmake --build build
```

**注意 `--build=missing`**：表示「二进制包缺失时从源码构建」。
不加这个参数，找不到预编译包就会直接失败。

# 第 7 章 怎么选

## 7.1 对照表

| 维度 | `find_package` | `FetchContent` | vcpkg | Conan |
|---|---|---|---|---|
| 需要额外工具 | 否 | 否（要 Git） | **是** | **是** |
| 依赖写在工程里 | 否 | 是 | **是** | **是** |
| 自动解析传递依赖 | 否 | 部分 | **是** | **是** |
| 二进制缓存 | — | 否 | 有限 | **强** |
| 首次构建耗时 | 无 | 中 | 高 | 低（有缓存时） |
| 跨平台一致性 | 靠系统 | 好 | **好** | **好** |
| 学习成本 | 低 | 低 | 中 | 较高 |

## 7.2 建议

| 你的情况 | 建议 |
|---|---|
| 只用系统自带的几个库 | 直接 `find_package` |
| 依赖少、都很小 | `FetchContent` |
| 依赖十个以上、要跨平台 | **vcpkg** |
| 团队已有 Conan 服务器 | Conan |
| 只是学习 CMake | 先用 `find_package` 加系统库 |

**给初学者的一句话**：先不要引入包管理器。
用 `find_package` 找系统已装的库，
**把 CMake 本身学好之后**再考虑 vcpkg。

## 7.3 不要同时用两个

**真实工程里同时存在 `vcpkg.json` 与 `conanfile.txt` 是常见现象**，
但那通常是历史遗留。

**同一个构建里同时用两套包管理器会出问题**：

| 问题 | 说明 |
|---|---|
| 同一个库被装两份 | 版本可能不一致 |
| 符号冲突 | 两个来源的同一个库同时链接 |
| 排查困难 | 出错时不知道是哪一套提供的 |

**应当选定一套**，另一套的配置保留但不用。

# 第 8 章 真实案例的依赖组织

## 8.1 工程概况

本教材案例工程 `NeoServerUpdateModpack` 的依赖分三类：

| 类别 | 数量 | 获取方式 |
|---|---|---|
| 第三方库 | 10 个 | vcpkg 清单 |
| 独立子模块（链接仓库） | 7 个 | `add_subdirectory` |
| 内部模块 | 27 个 | `add_subdirectory` |

## 8.2 `CMakeLists.txt` 里的三类写法

**第一类，第三方库**——用 `find_package`（**原文**）：

```cmake
find_package(Qt6 REQUIRED COMPONENTS Widgets Network Core)
find_package(nlohmann_json REQUIRED)
find_package(yaml-cpp REQUIRED)
find_package(tomlplusplus REQUIRED)
find_package(spdlog REQUIRED)
find_package(libzippp REQUIRED)
```

**第二类，仓库内的子模块**——用 `add_subdirectory`（**原文**）：

```cmake
add_subdirectory(nbtcpp EXCLUDE_FROM_ALL)
add_subdirectory(modules/CommonLoggerCPP)
add_subdirectory(modules/HiBerGUILibCPP)
add_subdirectory(modules/NeoCore)
add_subdirectory(modules/NeoWorkspace)
add_subdirectory(modules/NeoBuild)
```

**注意 `EXCLUDE_FROM_ALL`**：表示「这个子目录的目标不纳入默认构建」，
只有被别处链接时才编译。**对可选组件很有用。**

**第三类，平台相关**——条件判断（**原文**）：

```cmake
if(WIN32)
    add_subdirectory(modules/HiBerCommonInstaller)
endif()
```

## 8.3 预设文件里的关键设置

**实测**：该工程的 `CMakePresets.json`（version 6）里有三个预设：
`msvc`、`msvc-release`、`installer-static`。

每个预设都设置了同一组关键变量（**原文的做法**）：

```json
"cacheVariables": {
  "CMAKE_BUILD_TYPE": "Debug",
  "CMAKE_TOOLCHAIN_FILE": "<vcpkg>/scripts/buildsystems/vcpkg.cmake",
  "CMAKE_PREFIX_PATH": "<Qt>/6.11.1/msvc2022_64",
  "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
}
```

| 变量 | 作用 |
|---|---|
| `CMAKE_TOOLCHAIN_FILE` | **接入 vcpkg**，依赖从此而来 |
| `CMAKE_PREFIX_PATH` | 指向 Qt 的安装位置（Qt 不由 vcpkg 提供） |
| `CMAKE_EXPORT_COMPILE_COMMANDS` | 产出 `compile_commands.json` 给智能感知用 |

**这说明了第 2.2 节讲的组合方式**：
**大部分依赖走 vcpkg，Qt 单独用 `CMAKE_PREFIX_PATH` 指明。**

**为什么 Qt 不交给 vcpkg**：Qt 体积大、编译耗时长，
官方提供预编译包，用现成的更快。

## 8.4 静态运行库的写法

`installer-static` 预设里有一行值得注意（**原文**）：

```json
"CMAKE_MSVC_RUNTIME_LIBRARY": "MultiThreaded"
```

**这是把 MSVC 的 C 运行库静态链接进产物**，
好处是发布时不需要额外的运行库 DLL。

**这就是 triplet 与运行库设置的关联**：
vcpkg 的 `x64-windows-static` 三元组做的事是同一件，
但 Qt 不在 vcpkg 里，因此需要手工对齐设置。

> **对齐很重要**：若 vcpkg 提供的库是静态运行库，
> 而你的代码是动态运行库，链接时会报运行库不匹配。
> **两边必须一致。**

# 第 9 章 常见问题

## 9.1 找不到包

| 现象 | 原因 | 处理 |
|---|---|---|
| `Could not find a package configuration file` | 库没装，或不在搜索路径 | 装库，或设置 `CMAKE_PREFIX_PATH` |
| 装了却找不到 | 装到了非标准位置 | 显式指定 `CMAKE_PREFIX_PATH` |
| vcpkg 装了但没用上 | 没设 `CMAKE_TOOLCHAIN_FILE` | 在 preset 或命令行里设上 |
| Conan 装了但没用上 | 没设 conan 生成的工具链 | 加 `-DCMAKE_TOOLCHAIN_FILE=...` |

## 9.2 版本冲突

| 现象 | 原因 |
|---|---|
| 链接时报符号重复定义 | 同一个库被两个来源提供 |
| 运行时崩溃、行为异常 | 编译期与运行期的库版本不一致 |
| `LNK2038` 运行库不匹配 | 静态与动态运行库混用 |

**排查方法**：打印实际链接了哪些库

```cmake
get_target_property(LIBS app LINK_LIBRARIES)
message(STATUS "链接库: ${LIBS}")
```

## 9.3 vcpkg 构建很慢

**首次使用 vcpkg 会很慢**，因为它要从源码编译所有依赖。
本教材案例工程的十个依赖，首次构建需要较长时间。

**这是「源码构建」这一设计选择的必然代价**，换来的是
「能适配你的编译器与运行库设置」。

**缓解手段**：

| 手段 | 说明 |
|---|---|
| 用二进制缓存 | vcpkg 支持本地或远程二进制缓存 |
| 减少依赖 | 只声明真正需要的 |
| 复用 `vcpkg_installed` | 不要每次都删构建目录 |

## 9.4 提交了什么不该提交的

**容易误提交的目录**：

```
build/
vcpkg_installed/
_deps/                   ← FetchContent 下载的内容
conan/                   ← Conan 生成的工具链与配置
```

**这些都应当写进 `.gitignore`。**
它们的共同点是：**都能由配置文件重新生成**。

**判断标准**：一个文件能否从仓库里的其他文件推导出来。
能推导的就不该提交。
