真实工程很少只用自己的代码。JSON 解析、压缩、日志、图形界面——
这些轮子不该重造，但**把第三方库的源码复制进仓库同样不是办法**。

这些可复用的代码就是**库**；把库文件、头文件、版本信息与依赖声明打成一个整体，
再由工具自动取用，这套机制叫作**包管理**。

CMake 生态里获取与使用第三方依赖有四种方式，适用场景各不相同。

# 第 1 节 库与包管理

## 1.1 什么是库

**库是一批已经写好、可以被别的程序复用的代码。**

JSON 解析、数据压缩、日志输出、图形界面，这些事情都有人做过，
而且做得比临时拼凑的可靠。把它们拿来用，而不是每次从头再写一遍，
这就是库存在的理由。

**对使用者而言，一个库由两部分构成。**

| 部分 | 交给谁 | 里面是什么 |
|---|---|---|
| **头文件** | 编译器 | 有哪些函数，参数与返回值各是什么类型 |
| **库文件** | 链接器 | 这些函数的机器码 |

**两部分缺一不可**：只有头文件，链接时会报「未定义的引用」；
只有库文件，编译器连函数名都不知道。

**同一份库源码可以做成两种库文件**，区别只在代码被送进程序的时机。

| 形态 | 可执行文件里留下什么 | 谁把代码送进去 | 什么时候 |
|---|---|---|---|
| **静态库** | 用到的函数的**副本** | 链接器 | 链接时 |
| **动态库** | 一个**引用**（库名与符号名） | 加载器 | 程序启动时 |

> [!IMPORTANT]
> **静态与动态的差别不在源码，只在产物。**
> 同一个 `mymath.c`，既可以打成静态库，也可以打成动态库，区别只是命令不同。
> 本节后面逐项对照的那些差别，全部由这一处不同派生出来。

## 1.2 一个最小的库

**下面的库只提供一个加法函数，以及一个返回版本号的函数。**

`C`

```c
/* mymath.h —— 库对外的声明，使用者 #include 的就是它 */
#ifndef MYMATH_H
#define MYMATH_H

int add(int a, int b);          /* 库提供的功能 */
int lib_version(void);          /* 库的版本，用来观察「换库」的效果 */

#endif
```

`C`

```c
/* mymath.c —— 库的实现，打成静态库或动态库用的都是这一份 */
#include "mymath.h"

int add(int a, int b)
{
    return a + b;
}

int lib_version(void)
{
    return 1;                   /* 换库时改的就是这一行 */
}
```

`C`

```c
/* main.c —— 使用这个库的程序 */
#include <stdio.h>
#include "mymath.h"

int main(void)
{
    printf("add(2, 3) = %d\n", add(2, 3));
    printf("lib_version() = %d\n", lib_version());
    return 0;
}
```

**这三份文件用 C++ 编译器也能直接编译**，它们没有用到 C 与 C++ 写法不同的地方。

**打成两种库文件，各需要一组命令。** 下面是 Windows 侧（MinGW 的 `gcc`）：

`Bash`

```bash
# 静态库：先编出目标文件，再用 ar 打包
gcc -c mymath.c -o mymath.o
ar rcs libmymath.a mymath.o

# 动态库：直接由源码生成，同时要求生成导入库
gcc -shared -o mymath.dll mymath.c -Wl,--out-implib,libmymath.dll.a

# 链接成程序
gcc main.c libmymath.a -o app_static.exe            # 静态链接
gcc main.c -L. -lmymath -o app_dynamic.exe          # 动态链接
```

Linux 侧的命令：

`Bash`

```bash
gcc -c mymath.c -o mymath.o
ar rcs libmymath.a mymath.o

gcc -shared -fPIC -o libmymath.so mymath.c

gcc main.c libmymath.a -o app_static                # 静态链接
gcc main.c -L. -lmymath -o app_dynamic              # 动态链接

LD_LIBRARY_PATH=. ./app_dynamic     # 运行时到当前目录去找 libmymath.so
```

**`-fPIC` 要求生成位置无关的代码**，即库里的代码不假定自己会被放在哪个地址。
本节这个库只有函数，去掉它也能编过；库一旦引用全局变量，去掉它链接就会失败，
报错与复现命令见附录 B.4。

**两个程序的输出完全一样。**

`实测数据`
`Text`

```text
$ ./app_static
add(2, 3) = 5
lib_version() = 1

$ LD_LIBRARY_PATH=. ./app_dynamic
add(2, 3) = 5
lib_version() = 1
```

## 1.3 静态库与动态库的区别

### 文件形式

**同一个库，在不同工具链下产出的文件不同。**

`实测数据`

| 工具链 | 静态库 | 动态库 | 附加产物 |
|---|---|---|---|
| Windows + MinGW `gcc` | `libmymath.a`（990 字节） | `mymath.dll`（36,519 字节） | 导入库 `libmymath.dll.a`（2,114 字节） |
| Windows + MSVC | `mymath.lib`（930 字节） | `mymath.dll`（103,424 字节） | 导入库 `mymath.lib`（1,846 字节），另有 `mymath.exp`（796 字节） |
| Linux + `gcc` | `libmymath.a`（1,500 字节） | `libmymath.so`（15,144 字节） | 无 |

**Linux 的库名有约定**：一律以 `lib` 开头，因此链接时写 `-lmymath`，
链接器去找的就是 `libmymath.a` 与 `libmymath.so`。Windows 没有这个约定。

**在 Windows 上链接一个动态库需要两个文件**：运行时用的 `.dll`，
与链接时用的**导入库**。Linux 上没有这一层，
一个 `.so` 同时充当链接时的输入与运行时的依赖。
**导入库里不是库的实现**，核心是一张表：哪个符号在哪个 DLL 里。
链接器读这张表，把「我需要 `mymath.dll` 里的 `add`」写进可执行文件。

**MSVC 的静态库与导入库同名**，都是 `.lib`，只能靠所在目录区分；
MinGW 用 `.a` 与 `.dll.a` 把两者分开。

**Windows 上还有一条与编译器有关的规则。**

`实测数据`
`Text`

```text
$ cl /LD mymath.c /Fe:noexp.dll        # 源码里没有 __declspec(dllexport)
noexp.dll
（链接成功，退出码 0，但没有生成导入库）

$ dumpbin /exports noexp.dll
（输出里没有 exports 段，也就是一个符号都没有导出）
```

**MSVC 生成 DLL 时必须显式声明导出**（`__declspec(dllexport)`），
否则 DLL 里一个符号都不导出——链接不会报错，但别人无法链接它。
**MinGW 的 `gcc` 默认导出全部符号**，同一个 `mymath.c` 不加任何修饰也能用。

### 链接时机与更新方式

**静态链接发生在链接的那一刻。** 链接器把用到的函数从 `libmymath.a` 里取出来，
**复制**进 `app_static.exe`；此后这个 exe 与 `libmymath.a` 再无关系。

**动态链接发生在程序启动的那一刻。** 可执行文件里只留下一句
「我需要 `mymath.dll` 里的 `add`」，加载器在启动时把它找出来、映射进地址空间。

**这个区别可以直接看到**：把 `lib_version` 的返回值由 1 改成 2，
用第 1.2 小节里那两条生成库的命令重编 `libmymath.a` 与 `mymath.dll`，
**不重新链接程序**，再运行一次。

`实测数据`
`Text`

```text
（库为版本 1）
app_static.exe      add(2, 3) = 5      lib_version() = 1
app_dynamic.exe     add(2, 3) = 5      lib_version() = 1

（只改库、只重编库，两个程序都没有重新链接）
app_static.exe      add(2, 3) = 5      lib_version() = 1     ← 没有变
app_dynamic.exe     add(2, 3) = 5      lib_version() = 2     ← 跟着变了
```

**静态链接的程序里装的是副本，副本不会自己更新**，
要让它用上新的库，必须重新链接一次；重新链接之后它也输出 2。

**动态链接的程序每次启动都重新去 `.dll` / `.so` 里取**，因此换库之后不用动它。

> [!WARNING]
> **动态链接的程序每次启动都用当前那一份库。**
> 只换库、不重编程序，程序的行为就跟着变了。
> 若新旧库的函数名相同而参数或返回类型变了，链接期不会有任何提示。

### 可执行文件的体积

**「静态链接会大很多」这句话要看用掉了库的多少。**
为了把差值放大到看得见，先把库做成一个体积可观的版本。

`C`

```c
/* biglib.h */
#ifndef BIGLIB_H
#define BIGLIB_H

unsigned long big_sum(void);

#endif
```

`C`

```c
/* biglib.c —— 库里放一张 8 MiB 的只读表
   静态库：gcc -c biglib.c -o biglib.o && ar rcs libbiglib.a biglib.o
   动态库：gcc -shared -fPIC -o libbiglib.so biglib.c */
#include "biglib.h"

const unsigned char big_table[8 * 1024 * 1024] = { 1 };

unsigned long big_sum(void)
{
    unsigned long sum = 0;
    for (unsigned long i = 0; i < sizeof big_table; i += 4096)
        sum += big_table[i];        /* 每页读一个字节，把整张表都触进内存 */
    return sum;
}
```

`实测数据`

| 库 | 工具链 | 静态链接的程序 | 动态链接的程序 | 差 |
|---|---|---|---|---|
| 只有一个加法 | Windows + MinGW | `app_static.exe` 81,199 字节 | `app_dynamic.exe` 80,309 字节 | 890 |
| 只有一个加法 | Linux + `gcc` | `app_static` 16,056 字节 | `app_dynamic` 16,024 字节 | 32 |
| 8 MiB 只读表 | Windows + MinGW | `mem_a_static.exe` 8,469,738 字节 | `mem_a_dynamic.exe` 81,096 字节 | 8,388,642 |
| 8 MiB 只读表 | Linux + `gcc` | `mem_a_static` 8,404,800 字节 | `mem_a_dynamic` 16,120 字节 | 8,388,680 |

**前两行与后两行的对比说明了全部问题。**

小库那一行只差 890 字节，因为可执行文件的体积主要由启动代码与 C 运行库占据，
一个只有几行的库在其中看不出来。**换成 8 MiB 的库，差值就是 8 MiB**，
它约等于库自身的大小（`libbiglib.a` 为 8,389,668 字节）。

> [!IMPORTANT]
> **静态链接带来的体积增量，等于「你用掉的那部分库」。**
> 只用了一个函数的库，增量是几百字节；整个用上的库，增量就是整个库。

### 缺了库会怎样

**静态链接的程序不依赖库文件，拷到别处照样运行。**
**动态链接的程序必须能找到它依赖的那些库**，找不到就起不来。

`实测数据`
`Text`

```text
Windows：把 mymath.dll 从程序所在目录移走
  > app_dynamic.exe
  （没有任何输出）
  退出码 -1073741515

Linux：把 libmymath.so 移走
  $ LD_LIBRARY_PATH=. ./app_dynamic
  ./app_dynamic: error while loading shared libraries: libmymath.so: cannot open shared object file: No such file or directory
  退出码 127
```

**两个平台的表现在这里很不一样。** Linux 的加载器把原因直接写在标准错误上；
Windows 的加载器什么都不输出，只留下一个退出码。
`-1073741515` 是 `0xC0000135` 的有符号写法，
这个值在 MinGW-w64 的 `ntstatus.h` 里定义为 `STATUS_DLL_NOT_FOUND`。

**同一个目录下的 `app_static.exe` 在两种情况下都照常运行。**

**程序依赖哪些动态库可以直接问系统。**

`实测数据`
`Text`

```text
$ ldd app_static               # 只列与本例有关的一行
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6

$ ldd app_dynamic
	libmymath.so => ./libmymath.so
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
```

> [!TIP]
> **发布 Windows 程序时，`.dll` 要和 `.exe` 放在一起**，或者改用静态链接。
> 见《01-编译器/01-编译与链接.md》第 3.1 小节。

### 内存占用

**静态链接的程序，每个 exe 里都有一份库的副本，运行时各占一份物理内存。**
**动态链接的库在物理内存里只有一份，用到它的进程共用这一份。**

**要量出这一点，需要两个条件。**
一是两个**不同**的可执行文件——同一个 exe 运行两遍，
它自己的映像页也会被两个进程共享，看不出差别；
二是一个能区分「独占」与「共享」的内存指标。

Linux 的 `/proc/<pid>/smaps_rollup` 提供两个这样的指标。

| 指标 | 含义 |
|---|---|
| **Rss** | 这个进程映射进来的物理页，**共享的页在每个进程里各算一次** |
| **Pss** | 共享的页按**共享它的进程数**平摊，同一份库因此不会重复计入 |

**同时启动两个程序，读它们各自的这两个值。**

`实测数据`
`Text`

```text
静态链接（mem_a_static 与 mem_b_static，两个不同的 exe，各带一份 8 MiB 的库）
  进程 1   Rss=9800 kB   Pss=8380 kB
  进程 2   Rss=9908 kB   Pss=8379 kB
  合计     Rss=19708 kB  Pss=16759 kB

动态链接（mem_a_dynamic 与 mem_b_dynamic，两个程序共用同一个 libbiglib.so）
  进程 1   Rss=9872 kB   Pss=4297 kB
  进程 2   Rss=9864 kB   Pss=4299 kB
  合计     Rss=19736 kB  Pss=8596 kB
```

**两组的 Rss 合计几乎一样**（19,708 与 19,736 kB），
因为 Rss 把共享的页在每个进程里都记了一遍，看不出谁与谁共享。

**Pss 合计则相差约一倍**：静态那一组是 16,759 kB，约等于两份 8 MiB 的表；
动态那一组是 8,596 kB，约等于一份。

**映射关系也对得上**：两个动态链接的进程里，`libbiglib.so` 各段的设备号与 inode
完全相同（都是 `00:57` 与 `7599824373790684`），说明它们映射的是同一个文件；
两个静态链接的程序各自映射自己的 exe，inode 不同。

**这一组数字在 Linux 上量**，因为需要 `Pss` 这个指标。
Windows 的 `WorkingSet64` 与 `PrivateMemorySize64` 都不区分共享的映射页与独占的页：
同一组程序在 Windows 上量到的合计工作集是 24,911,872 与 25,063,424 字节，看不出差别。

### 六项对照

> [!NOTE]
> | 对比项 | 静态库 | 动态库 |
> |---|---|---|
> | 文件形式 | Windows 上是 `.lib`（MSVC）或 `.a`（MinGW），Linux 上是 `.a` | Windows 上是 `.dll`，Linux 上是 `.so` |
> | 链接时机 | 链接时把用到的代码复制进可执行文件 | 程序启动时由加载器装入 |
> | 可执行文件体积 | 含一份副本，增量约等于用掉的那部分库 | 只有导入表与少量引用 |
> | 依赖关系 | 不依赖 `.dll` / `.so`，拷走就能运行 | 缺库就起不来：Windows 退出码 `0xC0000135`，Linux 报 `cannot open shared object file` |
> | 更新方式 | 换了库必须重新链接 | 换掉库文件即可，程序不用动 |
> | 内存占用 | 每个 exe 一份，两个程序占两份 | 物理内存里一份，多进程共用 |

## 1.4 什么是包管理

**光有一个库文件还不够用。** 一个能拿来就用的库，至少带四样东西。

| 东西 | 少了它会怎样 |
|---|---|
| **头文件** | 编译器不知道有哪些函数、参数是什么类型 |
| **库文件** | 链接器找不到函数的实现 |
| **版本信息** | 不知道手上这份是哪一个版本，出了问题无法复现 |
| **依赖声明** | 不知道它自己还需要哪些别的库 |

**把这四样打成一个整体，就是「包」（package）；
获取包、解析它的依赖、把它装到合适位置供工程使用，这一整套机制就是包管理。**

**包管理要保证的核心是「可复现」**：今天能编过的工程，换一台机器、
换一个月再编一次，应当得到同样的依赖版本。为此它要同时处理四件事——
从哪里取、取哪个版本、这个版本又依赖谁、以及那些依赖各自还依赖谁。

**其中「依赖的依赖」最容易被低估。** 你只声明要用 `cpr`，
但 `cpr` 自己依赖 `curl` 与 `zlib`，这两者又各有自己的依赖。
手工处理这棵树很快会失控，因此**传递依赖由工具递归解析**，
写依赖的人只需要声明直接用到的那几个。
包管理器要应对的完整问题清单见第 2 节。

**C/C++ 还多一层麻烦**：同一个库在不同平台上要分别编译，下一小节说明原因。

### 包管理器与构建系统的分工

**两者做的是两件事。**

| 工具 | 负责 | 不负责 |
|---|---|---|
| **构建系统生成器**（CMake） | 描述这个工程由哪些目标组成、各自怎么编译 | 下载第三方库 |
| **构建执行器**（Ninja、Make） | 按依赖关系真正调用编译器 | 决定依赖从哪里来 |
| **包管理器**（vcpkg、Conan） | 下载、解析依赖、构建并安装 | 编译你自己的代码 |

**两者的接合点是一批配置文件。** 包管理器把依赖装好之后，
会在安装目录里放一批 `xxx-config.cmake`；CMake 的 `find_package` 读这些文件，
就知道头文件在哪、要链接哪个库文件、以及这个库自己还依赖谁。

**因此工程的 `CMakeLists.txt` 里看不到 `vcpkg` 或 `Conan` 的字样**，
接入点在工具链文件与那些配置文件中。
见《03-构建工具链/01-构建工具链.md》第 2.5 小节。

### 与把库源码复制进仓库的对比

| | 把库源码复制进仓库 | 用包管理器 |
|---|---|---|
| 仓库里放什么 | 第三方的全部源码 | 一份依赖声明 |
| 传递依赖 | 自己看出来、自己去找 | 工具递归解析 |
| 构建结果可复现 | 取决于当时复制了哪一份 | 由版本号与基线固定 |

**把第三方源码整个复制进项目的问题，见第 2 节。**

## 1.5 C/C++ 的包管理为什么更麻烦

### 一、没有统一的 ABI

**多数语言的包管理只需要处理版本与依赖**，语言本身对平台差异的暴露有限。
**C/C++ 不一样：它编译出来的是机器码**，
机器码绑定了一整套由平台与编译器共同决定的约定：

| 约定 | 由谁决定 |
|---|---|
| 数据模型（`long` 是 4 字节还是 8 字节） | 平台 |
| 调用约定（参数放寄存器还是栈） | 平台与编译器 |
| 名字修饰（符号在目标文件里叫什么） | 编译器 |
| 结构体的布局与填充 | 平台与编译器 |
| 导出规则（DLL 里哪些符号对外可见） | 编译器 |

**这一整套就是 ABI**，完整说明见《01-编译器/00-语言的实现.md》第 5 节。

**因此同一个库，换一套编译器或换一套运行库设置，往往要重新编译一份。**
vcpkg 默认从源码构建、并按 triplet 分目录存放，正是因为这个原因：
`x64-windows` 与 `x64-windows-static` 是两份独立的产物，不能互换。

**导出规则的差别在第 1.3 小节已经出现过**：
MSVC 要写 `__declspec(dllexport)`，MinGW 默认导出全部符号。
同一份源码，两个编译器给出的产物能不能被别人链接，答案不一样。

### 二、头文件与库文件要分别找到

**一个包要在三个不同的时刻各被找到一次。**

| 时刻 | 要找什么 | 谁来指定 |
|---|---|---|
| 编译时 | 头文件 | `-I`，或 CMake 的 `target_include_directories` |
| 链接时 | 库文件或导入库 | `-L` 与 `-l`，或 `target_link_libraries` |
| 运行时 | `.dll` / `.so` | 系统的库搜索路径 |

**三次的搜索位置各不相同**，而且前两次找不到在构建期就报错，
**第三次找不到要到运行期才暴露**——第 1.3 小节里那个退出码 `0xC0000135`
就是这么来的。

### 三、与构建系统耦合

**C/C++ 没有官方指定的构建系统**，因此包管理器必须迁就工程实际用的那一套。

**CMake 生态的接合点是 `find_package`**：包管理器负责把依赖装好、
并生成 `xxx-config.cmake`，工程的 `CMakeLists.txt` 只写 `find_package`。
**分工看起来干净，代价是两边都要对**：库没有提供配置文件，`find_package` 就找不到它；
`CMAKE_PREFIX_PATH` 没有指对，装了也找不到。
第 4 节与第 10 节讲的都是这一类问题。

# 第 2 节 为什么需要包管理

## 2.1 把库源码复制进仓库的问题

初学者常见的做法是把第三方源码整个复制进项目：

`Text`

```text
project/
├── src/
├── include/
└── third_party/
    ├── json/          ← 复制的
    ├── zlib/          ← 复制的
    └── fmt/           ← 复制的
```

**四种代价**：

| 代价 | 说明 |
|---|---|
| **仓库膨胀** | 第三方代码往往比自己的代码多几十倍 |
| **更新困难** | 想升级版本，要手工对比替换 |
| **安全漏洞** | 上游修了漏洞，你不知道 |
| **许可混乱** | 第三方代码各有各的许可证，容易被忽略 |

**最后一条尤其容易出问题**：把 GPL 代码复制进闭源项目，
会带来法律后果。详见[版权与许可说明.md](../版权与许可说明.md)。

## 2.2 包管理要解决的问题

| 问题 | 包管理器的做法 |
|---|---|
| 去哪里拿 | 从官方源或指定仓库下载 |
| 拿哪个版本 | 按版本约束解析 |
| 依赖的依赖怎么办 | **递归解析**，一并装上 |
| 编译参数怎么给 | 通过 CMake 配置文件自动传递 |
| 换平台怎么办 | 按 triplet（目标平台）分别构建 |

**「依赖的依赖」是最容易被低估的一点。**
你只声明要用 `cpr`，但 `cpr` 自己依赖 `curl` 与 `zlib`，
包管理器要能把这些一并解析出来。

# 第 3 节 四种获取方式

## 3.1 总览

`Text`

```text
   ┌───────────────────────────────────────────────────────────┐
   │  ① find_package                                           │
   │     找【已经装好】的库                                     │
   │     库从哪来：系统包管理器、手工编译安装、vcpkg 预装         │
   ├───────────────────────────────────────────────────────────┤
   │  ② FetchContent                                           │
   │     配置阶段从【源码仓库】下载并一起编译                    │
   │     适合：库很小、想固定到某个提交                          │
   ├───────────────────────────────────────────────────────────┤
   │  ③ vcpkg                                                  │
   │     独立包管理器，用 manifest 声明依赖                      │
   │     适合：依赖较多、需要统一版本与跨平台                    │
   ├───────────────────────────────────────────────────────────┤
   │  ④ Conan                                                  │
   │     独立包管理器，功能更强、配置更复杂                      │
   │     适合：需要二进制缓存、多配置矩阵                        │
   └───────────────────────────────────────────────────────────┘
```

## 3.2 一个常见的组合

**真实做法往往是组合使用**：

`CMake`

```cmake
# 依赖由 vcpkg 提供（通过工具链文件接入）
find_package(nlohmann_json CONFIG REQUIRED)
find_package(yaml-cpp REQUIRED)

# 自己仓库里的子模块，源码就在本地
add_subdirectory(nbtcpp EXCLUDE_FROM_ALL)

# 很小的纯头文件库，直接下载
FetchContent_Declare(xxhash GIT_REPOSITORY ... GIT_TAG ...)
FetchContent_MakeAvailable(xxhash)
```

**判断依据**：

| 库的情况 | 用哪种 |
|---|---|
| 大、编译慢、多项目共用 | `find_package` + vcpkg |
| 就在自己仓库里 | `add_subdirectory` |
| 小、纯头文件、想固定版本 | `FetchContent` |
| 需要细粒度控制二进制 | Conan |

# 第 4 节 `find_package`

## 4.1 基本用法

`CMake`

```cmake
find_package(ZLIB REQUIRED)
find_package(nlohmann_json CONFIG REQUIRED)
find_package(Qt6 REQUIRED COMPONENTS Widgets Network Core)
```

| 部分 | 含义 |
|---|---|
| `ZLIB` | 包名 |
| `REQUIRED` | **找不到就报错**停止配置；不加则只是设置一个变量 |
| `CONFIG` | 指定查找模式，见 4.2 小节 |
| `COMPONENTS` | 只要求该包的部分组件 |

## 4.2 两种查找模式

**这是 `find_package` 最容易混淆的地方。**

| | MODULE 模式 | CONFIG 模式 |
|---|---|---|
| 找什么文件 | `FindXXX.cmake` | `xxx-config.cmake` 或 `XXXConfig.cmake` |
| 谁提供 | **CMake 自带**，或项目自己写 | **库的安装过程生成** |
| 位置 | `<CMake>/share/cmake-<版本>/Modules/` | 库的安装目录下 |
| 是否精确 | 靠模式匹配猜路径与库名 | 库自己声明的，**准确** |
| 覆盖范围 | 只覆盖常见库 | 每个支持 CMake 的库都有 |

**默认行为**：不写模式时，**先试 MODULE，失败再试 CONFIG**。

**为什么推荐显式写 `CONFIG`**：

`CMake`

```cmake
find_package(nlohmann_json CONFIG REQUIRED)    # 明确要求用库自己提供的配置
```

因为 MODULE 模式依赖 CMake 自带的 `FindXXX.cmake` 脚本去**猜**，
而 `CONFIG` 模式是库自己给出的准确信息——
包括它需要哪些编译定义、链接哪些子库。

**本教材案例工程的用法**（`NeoServerUpdateModpack/CMakeLists.txt`，**原文**）：

`CMake`

```cmake
find_package(nlohmann_json CONFIG REQUIRED)
find_package(Lua REQUIRED)
find_package(ZLIB REQUIRED)
find_package(libzippp CONFIG REQUIRED)
find_package(cpr CONFIG REQUIRED)
```

**这里两种模式混用**：`Lua` 与 `ZLIB` 用 MODULE 模式
（这两个比较老，CMake 自带查找脚本），其余用 CONFIG。

## 4.3 找到之后怎么用

`CMake`

```cmake
find_package(ZLIB REQUIRED)

add_executable(app main.c)
target_link_libraries(app PRIVATE ZLIB::ZLIB)
```

**带 `::` 的名字是导入目标。**

**为什么用它而不是用变量**：老式写法是

`CMake`

```cmake
include_directories(${ZLIB_INCLUDE_DIRS})    # 旧式
target_link_libraries(app ${ZLIB_LIBRARIES})
```

**这类变量可能不存在**，或者只包含库文件而漏掉编译定义。

> [!IMPORTANT]
> **导入目标把「头文件路径 + 库文件 + 编译选项 + 依赖的依赖」打包在一起**，
> 链接它一个就够了。这与《03-构建工具链/01-构建工具链.md》第 4.4 小节讲的
> `PUBLIC` / `PRIVATE` 传递是同一套机制。

## 4.4 找不到时报什么错

`Text`

```text
CMake Error at CMakeLists.txt:12 (find_package):
  By not providing "FindZLIB.cmake" in CMAKE_MODULE_PATH this project has
  asked CMake to find a package configuration file provided by "ZLIB", but
  CMake did not find one.
```

**排查顺序**：

| 步骤 | 做法 |
|---|---|
| 1 | 确认库**确实装了**，而不只是下载了源码 |
| 2 | 确认 `CMAKE_PREFIX_PATH` 含库的安装位置 |
| 3 | 确认模式写对（有的库只提供 CONFIG） |
| 4 | 打印变量看看：`message(STATUS "CMAKE_PREFIX_PATH=${CMAKE_PREFIX_PATH}")` |

**`CMAKE_PREFIX_PATH` 是最常用的手段**：把库的安装根目录告诉 CMake。

# 第 5 节 `FetchContent`

## 5.1 用法

`CMake`

```cmake
include(FetchContent)

FetchContent_Declare(
    googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG        v1.14.0
)

FetchContent_MakeAvailable(googletest)
```

**它做了什么**：

`Text`

```text
   配置阶段
       │
       ├── 从 Git 克隆到 build/_deps/ 下
       ├── 把该目录当作 add_subdirectory 引入
       └── 于是它的 target 就可以直接链接
```

> [!WARNING]
> **`GIT_TAG` 必须写具体的标签或提交哈希。**
> 写分支名（如 `main`）会让构建结果随上游变化，无法复现。

## 5.2 适合与不适合

| 适合 | 理由 |
|---|---|
| 纯头文件库 | 没有编译负担 |
| 很小的库 | 编译几秒钟 |
| 想固定在某个提交 | 不受上游变动影响 |
| 不想额外装包管理器 | 只要有 Git 就行 |

| 不适合 | 理由 |
|---|---|
| 大库（如 Qt、LLVM） | 每次新构建目录都要重新编译，几十分钟起 |
| 需要多项目共享 | 每个项目各编译一份，浪费磁盘与时间 |
| 网络受限环境 | 配置阶段必须能访问 Git 仓库 |

**`FetchContent` 下载的内容放在构建目录里，删掉构建目录就会重新下载。**

## 5.3 与 `ExternalProject` 的区别

CMake 里还有一个 `ExternalProject_Add`，两者的差别在于：

| | `FetchContent` | `ExternalProject_Add` |
|---|---|---|
| 下载时机 | **配置阶段** | 构建阶段 |
| 能否直接链接它的 target | **能** | 不能，需手工指定路径 |
| 适用 | 想当普通依赖用 | 想在构建时才准备（如工具链） |

**绝大多数场景用 `FetchContent`**，
`ExternalProject_Add` 主要用于「构建过程中才需要的工具」。

# 第 6 节 vcpkg

## 6.1 它是什么

**vcpkg 是微软开源的 C/C++ 包管理器**，与 CMake 集成紧密。

**核心特点**：

| 特点 | 说明 |
|---|---|
| 清单模式 | 依赖写在 `vcpkg.json` 里，随仓库走 |
| 源码构建 | 从源码编译，因此能适配你的编译器与运行库设置 |
| 三元组（triplet） | 按目标平台分别构建，如 `x64-windows` |
| 与 CMake 集成 | 通过一个**工具链文件**接入，几乎不需要改 `CMakeLists.txt` |

## 6.2 清单文件

**真实案例**：本教材案例工程的 `vcpkg.json`（**原文**）：

`JSON`

```json
{
  "$schema": "https://raw.githubusercontent.com/microsoft/vcpkg/master/scripts/vcpkg-configuration.schema.json",
  "name": "neoserver-update-modpack",
  "version": "1.0.0",
  "description": "NeoServer 更新整合包管理工具",
  "dependencies": [
    "cmark-gfm",
    "cpr",
    "libzippp",
    "lua",
    "nlohmann-json",
    "spdlog",
    "tomlplusplus",
    "yaml-cpp",
    "webview2",
    "zlib"
  ]
}
```

**十个依赖，一个文件声明完。**

**这里没有写「cpr 依赖 curl」这类信息**——
vcpkg 会从自己的端口定义里**递归解析**出完整的依赖树。

**版本约束的写法**：默认不指定版本时，vcpkg 用它的基线版本。
要固定版本用 `overrides`：

`JSON`

```json
{
  "dependencies": [ "fmt" ],
  "overrides": [
    { "name": "fmt", "version": "10.2.1" }
  ]
}
```

## 6.3 接进 CMake

**关键在一个工具链文件**。在 `CMakePresets.json` 里（**原文的做法**）：

`JSON`

```json
"cacheVariables": {
  "CMAKE_TOOLCHAIN_FILE": "<vcpkg>/scripts/buildsystems/vcpkg.cmake"
}
```

原文里写的是本机的绝对路径，此处替换为占位符 `<vcpkg>`，
指 vcpkg 的安装根目录。

**这个工具链文件做了什么**：

`Text`

```text
   配置阶段启动
       │
       ▼
   读 vcpkg.json ──→ 解析依赖树
       │
       ▼
   检查 vcpkg_installed/ 里是否已装
       │  缺少的
       ▼
   下载并编译依赖 ──→ 装到 vcpkg_installed/<triplet>/
       │
       ▼
   把安装目录加进 CMAKE_PREFIX_PATH
       │
       ▼
   于是 find_package 就能找到它们
```

> [!IMPORTANT]
> **`CMakeLists.txt` 里不需要写任何 vcpkg 相关的东西**——
> 接入点在工具链文件，不在工程文件。

## 6.4 构建后的目录

案例工程构建后的 `vcpkg_installed/` 结构：

`实测数据`
`Text`

```text
vcpkg_installed/
├── vcpkg/                     构建过程的记录与状态
└── x64-windows/               ← triplet 名
    ├── bin/                   运行库（.dll）
    ├── include/               头文件
    ├── lib/                   导入库与静态库
    └── share/                 CMake 配置文件（供 find_package 使用）
```

**完整的目录清单见附录 B。**

**要接入 CMake，关键在 `x64-windows/share/`**——
那里放着各个库提供的 `xxx-config.cmake`，
`find_package` 正是靠它找到这些依赖。

**`x64-windows` 就是 triplet**：它同时编码了架构（x64）与目标平台（windows）。
换 32 位就是 `x86-windows`，换静态运行库就是 `x64-windows-static`。

**为什么这个目录在工程里而不在系统里**：
清单模式下 vcpkg 把依赖装到**构建目录旁边**，
因此不同工程可以用不同版本的同一个库，互不干扰。

> [!TIP]
> `vcpkg_installed/` 与 `build/` 一样属于构建产物，
> **不应提交进版本库**，应当写进 `.gitignore`。

## 6.5 常用命令

`Bash`

```bash
vcpkg install                 # 按当前目录的 vcpkg.json 安装依赖
vcpkg list                    # 列出已安装的包
vcpkg search <名字>            # 搜索可用的包
vcpkg x-update-baseline       # 更新基线版本
```

**vcpkg 是滚动发布的**，没有语义化的版本号，
而是用日期加提交哈希标识（本机版本见附录 B）。
**因此「升级 vcpkg」就等于「换基线」**，
依赖的版本可能一并变化。

# 第 7 节 Conan

## 7.1 它是什么

**Conan 是另一个 C/C++ 包管理器**，出现早于 vcpkg，
设计上更强调**二进制缓存**与**多配置矩阵**。

| 方面 | Conan | vcpkg |
|---|---|---|
| 主要分发形式 | 二进制包为主 | 源码构建为主 |
| 配置文件 | `conanfile.txt` / `conanfile.py` | `vcpkg.json` |
| 私有仓库 | 支持自建服务器 | 相对简单 |
| 多配置 | **配置矩阵更灵活** | triplet 机制 |
| 学习成本 | 较高 | 较低 |
| 与 CMake 集成 | 生成工具链文件 | 提供工具链文件 |

## 7.2 配置文件

**真实案例**：同一工程的 `conanfile.txt`（**原文**）：

`INI`

```ini
[requires]
qt/5.15.14
nlohmann_json/3.11.3

[generators]
CMakeToolchain
CMakeDeps

[options]
qt:shared=True
qt:with_network=True
qt:with_widgets=True
```

| 段 | 含义 |
|---|---|
| `[requires]` | 依赖与版本，`包名/版本` |
| `[generators]` | **生成什么给 CMake 用** |
| `[options]` | 传给具体包的构建选项 |

**两个 generator 的作用**：

| 生成器 | 产出 | 用途 |
|---|---|---|
| `CMakeToolchain` | 工具链文件 | 告诉 CMake 用哪个编译器、什么配置 |
| `CMakeDeps` | `xxx-config.cmake` 文件 | **让 `find_package` 能找到这些依赖** |

**这正是 Conan 与 CMake 的接合点**：
Conan 生成一批 `xxx-config.cmake`，
于是 `CMakeLists.txt` 里照常用 `find_package`，不需要知道 Conan 的存在。

> [!IMPORTANT]
> Conan 与 vcpkg 的思路相同——**都在工具链层面接入，不侵入 `CMakeLists.txt`**。
> 这是成熟的包管理器普遍采用的做法。

## 7.3 使用流程

`Bash`

```bash
conan install . --output-folder=build --build=missing
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake
cmake --build build
```

`--build=missing` 表示「二进制包缺失时从源码构建」；
不加这个参数，找不到预编译包就会直接失败。

# 第 8 节 怎么选

## 8.1 对照表

| 维度 | `find_package` | `FetchContent` | vcpkg | Conan |
|---|---|---|---|---|
| 需要额外工具 | 否 | 否（要 Git） | **是** | **是** |
| 依赖写在工程里 | 否 | 是 | **是** | **是** |
| 自动解析传递依赖 | 否 | 部分 | **是** | **是** |
| 二进制缓存 | — | 否 | 有限 | **强** |
| 首次构建耗时 | 无 | 中 | 高 | 低（有缓存时） |
| 跨平台一致性 | 靠系统 | 好 | **好** | **好** |
| 学习成本 | 低 | 低 | 中 | 较高 |

## 8.2 建议

| 你的情况 | 建议 |
|---|---|
| 只用系统自带的几个库 | 直接 `find_package` |
| 依赖少、都很小 | `FetchContent` |
| 依赖十个以上、要跨平台 | **vcpkg** |
| 团队已有 Conan 服务器 | Conan |
| 只是学习 CMake | 先用 `find_package` 加系统库 |

**初学者不必急于引入包管理器**：先用 `find_package` 找系统已装的库，
**把 CMake 本身学好之后**再考虑 vcpkg。

## 8.3 不要同时用两个

**真实工程里同时存在 `vcpkg.json` 与 `conanfile.txt` 是常见现象**，
但那通常是历史遗留。

**同一个构建里同时用两套包管理器会出问题**：

| 问题 | 说明 |
|---|---|
| 同一个库被装两份 | 版本可能不一致 |
| 符号冲突 | 两个来源的同一个库同时链接 |
| 排查困难 | 出错时不知道是哪一套提供的 |

**应当选定一套**，另一套的配置保留但不用。

# 第 9 节 真实案例的依赖组织

## 9.1 工程概况

本教材案例工程 `NeoServerUpdateModpack` 的依赖分三类：

| 类别 | 数量 | 获取方式 |
|---|---|---|
| 第三方库 | 10 个 | vcpkg 清单 |
| 独立子模块（链接仓库） | 7 个 | `add_subdirectory` |
| 内部模块 | 27 个 | `add_subdirectory` |

## 9.2 `CMakeLists.txt` 里的三类写法

**第一类，第三方库**——用 `find_package`（**原文**）：

`CMake`

```cmake
find_package(Qt6 REQUIRED COMPONENTS Widgets Network Core)
find_package(nlohmann_json REQUIRED)
find_package(yaml-cpp REQUIRED)
find_package(tomlplusplus REQUIRED)
find_package(spdlog REQUIRED)
find_package(libzippp REQUIRED)
```

**第二类，仓库内的子模块**——用 `add_subdirectory`（**原文**）：

`CMake`

```cmake
add_subdirectory(nbtcpp EXCLUDE_FROM_ALL)
add_subdirectory(modules/CommonLoggerCPP)
add_subdirectory(modules/HiBerGUILibCPP)
add_subdirectory(modules/NeoCore)
add_subdirectory(modules/NeoWorkspace)
add_subdirectory(modules/NeoBuild)
```

`EXCLUDE_FROM_ALL` 表示「这个子目录的目标不纳入默认构建」，
只有被别处链接时才编译，**对可选组件很有用**。

**第三类，平台相关**——条件判断（**原文**）：

`CMake`

```cmake
if(WIN32)
    add_subdirectory(modules/HiBerCommonInstaller)
endif()
```

## 9.3 预设文件里的关键设置

该工程的 `CMakePresets.json`（version 6）定义了 `msvc`、`msvc-release`、
`installer-static` 三个预设，每个预设都设置了同一组关键变量（**原文的做法**）：

`JSON`

```json
"cacheVariables": {
  "CMAKE_BUILD_TYPE": "Debug",
  "CMAKE_TOOLCHAIN_FILE": "<vcpkg>/scripts/buildsystems/vcpkg.cmake",
  "CMAKE_PREFIX_PATH": "<Qt>/6.11.1/msvc2022_64",
  "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
}
```

| 变量 | 作用 |
|---|---|
| `CMAKE_TOOLCHAIN_FILE` | **接入 vcpkg**，依赖从此而来 |
| `CMAKE_PREFIX_PATH` | 指向 Qt 的安装位置（Qt 不由 vcpkg 提供） |
| `CMAKE_EXPORT_COMPILE_COMMANDS` | 产出 `compile_commands.json` 给智能感知用 |

**这说明了第 3.2 小节讲的组合方式**：
**大部分依赖走 vcpkg，Qt 单独用 `CMAKE_PREFIX_PATH` 指明。**

**为什么 Qt 不交给 vcpkg**：Qt 体积大、编译耗时长，
官方提供预编译包，用现成的更快。

## 9.4 静态运行库的写法

`installer-static` 预设里有一行运行库设置（**原文**）：

`JSON`

```json
"CMAKE_MSVC_RUNTIME_LIBRARY": "MultiThreaded"
```

**这是把 MSVC 的 C 运行库静态链接进产物**，
好处是发布时不需要额外的运行库 DLL。

**这就是 triplet 与运行库设置的关联**：
vcpkg 的 `x64-windows-static` 三元组做的事是同一件，
但 Qt 不在 vcpkg 里，因此需要手工对齐设置。

> [!WARNING]
> **两边的运行库必须一致。** 若 vcpkg 提供的库是静态运行库，
> 而你的代码是动态运行库，链接时会报运行库不匹配。

# 第 10 节 常见问题

## 10.1 找不到包

| 现象 | 原因 | 处理 |
|---|---|---|
| `Could not find a package configuration file` | 库没装，或不在搜索路径 | 装库，或设置 `CMAKE_PREFIX_PATH` |
| 装了却找不到 | 装到了非标准位置 | 显式指定 `CMAKE_PREFIX_PATH` |
| vcpkg 装了但没用上 | 没设 `CMAKE_TOOLCHAIN_FILE` | 在 preset 或命令行里设上 |
| Conan 装了但没用上 | 没设 conan 生成的工具链 | 加 `-DCMAKE_TOOLCHAIN_FILE=...` |

## 10.2 版本冲突

| 现象 | 原因 |
|---|---|
| 链接时报符号重复定义 | 同一个库被两个来源提供 |
| 运行时崩溃、行为异常 | 编译期与运行期的库版本不一致 |
| `LNK2038` 运行库不匹配 | 静态与动态运行库混用 |

**排查方法**：打印实际链接了哪些库

`CMake`

```cmake
get_target_property(LIBS app LINK_LIBRARIES)
message(STATUS "链接库: ${LIBS}")
```

## 10.3 vcpkg 构建很慢

**首次使用 vcpkg 会很慢**，因为它要从源码编译所有依赖。
本教材案例工程的十个依赖，首次构建需要较长时间。

**这是「源码构建」这一设计选择的必然代价**，换来的是
「能适配你的编译器与运行库设置」。

**缓解手段**：

| 手段 | 说明 |
|---|---|
| 用二进制缓存 | vcpkg 支持本地或远程二进制缓存 |
| 减少依赖 | 只声明真正需要的 |
| 复用 `vcpkg_installed` | 不要每次都删构建目录 |

## 10.4 提交了什么不该提交的

**容易误提交的目录**：

`Text`

```text
build/
vcpkg_installed/
_deps/                   ← FetchContent 下载的内容
conan/                   ← Conan 生成的工具链与配置
```

**这些都应当写进 `.gitignore`。**
它们的共同点是：**都能由配置文件重新生成**。

**判断标准**：一个文件能否从仓库里的其他文件推导出来。
能推导的就不该提交。

# 术语表

| 术语 | 英文 | 含义 |
|---|---|---|
| **库** | Library | 已经写好、可以被别的程序复用的代码集合 |
| **静态库** | Static library | 链接时把用到的代码复制进可执行文件的库 |
| **动态库** | Dynamic library、Shared library | 程序启动时由加载器装入的库；Windows 上是 `.dll`，Linux 上是 `.so` |
| **导入库** | Import library | 链接动态库时用的小文件，本身没有代码，只记录哪个符号在哪个 DLL 里 |
| **包** | Package | 库文件、头文件、版本信息与依赖声明打成的整体 |
| 包管理 | Package management | 获取、构建、集成第三方依赖的机制 |
| 包管理器 | Package manager | 下载、解析依赖并安装包的工具，如 vcpkg、Conan |
| 清单 | Manifest | 声明依赖的文件，如 `vcpkg.json` |
| 传递依赖 | Transitive dependency | 依赖的依赖 |
| 三元组 | Triplet | vcpkg 里描述目标平台的标识，如 `x64-windows` |
| 导入目标 | Imported target | 库提供的、带 `::` 的目标，承载用法要求 |
| MODULE 模式 | Module mode | 用 `FindXXX.cmake` 查找包 |
| CONFIG 模式 | Config mode | 用包自己提供的 `xxx-config.cmake` 查找 |
| 工具链文件 | Toolchain file | 在配置前加载的脚本，用于指定编译器与依赖来源 |
| 二进制缓存 | Binary cache | 保存已编译依赖，避免重复构建 |
| 基线 | Baseline | vcpkg 中一组固定的依赖版本 |

## B.3 库与链接的复现命令

**源码**：`mymath.h`、`mymath.c`、`main.c` 见第 1.2 小节，
`biglib.h`、`biglib.c` 见第 1.3 小节。测量内存用的两个程序如下，
它们只有一处输出不同，因而是两个不同的可执行文件；
`mem_b.c` 与 `mem_a.c` 只差输出前缀与文件名，这里只列后者。

`C`

```c
/* mem_a.c —— 编译：gcc mem_a.c libbiglib.a -o mem_a_static
              gcc mem_a.c -L. -lbiglib -o mem_a_dynamic */
#include <stdio.h>
#include <unistd.h>
#include "biglib.h"

int main(void)
{
    printf("A: big_sum() = %lu\n", big_sum());
    fflush(stdout);
    sleep(20);              /* 留出时间，让脚本去读 /proc/<pid>/smaps_rollup */
    return 0;
}
```

**构建与运行**（Linux 侧）：

`Bash`

```bash
gcc -c mymath.c -o mymath.o
ar rcs libmymath.a mymath.o
gcc -shared -fPIC -o libmymath.so mymath.c
gcc main.c libmymath.a -o app_static
gcc main.c -L. -lmymath -o app_dynamic
LD_LIBRARY_PATH=. ./app_dynamic

# 体积差值与内存测量用的那一组
gcc -c biglib.c -o biglib.o
ar rcs libbiglib.a biglib.o
gcc -shared -fPIC -o libbiglib.so biglib.c
gcc mem_a.c libbiglib.a -o mem_a_static
gcc mem_a.c -L. -lbiglib -o mem_a_dynamic
```

**内存测量**：同时启动两个程序，三秒后读各自的 `smaps_rollup`。

`Bash`

```bash
./mem_a_static & p1=$!
./mem_b_static & p2=$!
sleep 3
for p in $p1 $p2; do
    grep -E '^(Rss|Pss):' /proc/$p/smaps_rollup
done
grep libbiglib /proc/$p1/maps      # 两个进程的设备号与 inode 相同
kill $p1 $p2
```

**库里有全局数据时，`gcc -shared` 不带 `-fPIC` 会链接失败。**
