# 第 1 节 为什么需要构建工具

## 1.1 编译器的局限

《01-编译器/01-编译与链接.md》讲过，
`gcc` 的完整流程是「预处理 → 编译 → 汇编 → 链接」。
但真正动手时会立刻遇到一个限制：

`Bash`

```bash
gcc src/main.c -o app        # 可以
gcc src/ -o app              # 不行：gcc 不接受目录
```

**编译器一次只处理你明确给它的文件。**

单文件程序无所谓，一个命令就够了。但真实工程是这样的：

`Text`

```text
project/
├── src/         30 个 .c 文件
├── include/     40 个 .h 文件
├── third_party/ 3 个外部库
└── tests/       12 个测试程序
```

要构建它，必须自己回答一系列问题：

| 问题 | 手工做会怎样 |
|---|---|
| 哪些文件需要编译 | 靠人记住 |
| 编译顺序是什么 | 靠人排出依赖关系 |
| 哪个文件改了 | 靠人盯着，或全部重编 |
| 头文件改了要重编谁 | 基本靠全部重编 |
| 库要按什么顺序链接 | 靠反复试错 |
| 换一台机器怎么构建 | 命令全部重写 |

**这些问题与「程序要实现什么功能」毫无关系。** 它们纯粹是组织问题。
构建工具就是为了把这类组织工作自动化。

## 1.2 一个真实的例子

本教材的示例工程 `B-examples/03-CMake-C` 只有 3 个源文件，
手工构建完全可行：

`Bash`

```bash
gcc -c src/main.c -I include -o main.o
gcc -c src/calc.c -I include -o calc.o
gcc main.o calc.o -o app.exe
```

**这条命令链在三个文件时还算清楚，到三十个文件时就无法维护了。**
而且它至少有三个隐患：

1. **改了 `calc.h` 之后要重编两个 `.c`**，靠人记
2. **`-I include` 这样的参数要重复写**，漏一处就报「找不到头文件」
3. **换到 Linux 上要用另一套参数**，Windows 上的命令全部作废

## 1.3 构建工具要解决的四个问题

| 问题 | 术语 | 解决方式 |
|---|---|---|
| **描述**：怎样把工程结构写下来 | 构建描述 | 用一份声明式文件（`CMakeLists.txt`） |
| **依赖**：谁依赖谁、按什么顺序做 | 依赖图 | 工具自动推出，不靠人排 |
| **增量**：只重做必要的部分 | 增量构建 | 比较文件时间戳 |
| **可移植**：换平台不用重写 | 跨平台 | 生成平台本地的构建文件 |

**第四点常常被低估。** 同一个 `CMakeLists.txt` 可以在 Windows 上生成
Ninja 文件、在 Linux 上生成 Makefile、在 macOS 上生成 Xcode 工程——
这是「构建系统生成器」这一类工具存在的全部理由。

# 第 2 节 工具链的层次

## 2.1 一张分层图

构建不是一个程序完成的，而是**四层工具接力**：

`Text`

```text
   ┌──────────────────────────────────────────────────┐
   │  ④ 包管理器                                        │
   │     vcpkg / Conan / FetchContent                  │
   │     负责：把第三方库下载并编译好                     │
   └───────────────────────┬──────────────────────────┘
                           │ 提供库
   ┌───────────────────────▼──────────────────────────┐
   │  ③ 构建执行器                                      │
   │     Ninja / GNU Make / MSBuild                    │
   │     负责：按依赖图逐个执行命令，只做必要的部分         │
   └───────────────────────▲──────────────────────────┘
                           │ 读构建文件
   ┌───────────────────────┴──────────────────────────┐
   │  ② 构建系统生成器                                   │
   │     CMake / Meson / Bazel                         │
   │     负责：把工程描述翻译成某个执行器能读的构建文件      │
   └───────────────────────▲──────────────────────────┘
                           │ 读 CMakeLists.txt
   ┌───────────────────────┴──────────────────────────┐
   │  ① 编译器与链接器                                   │
   │     gcc / g++ / clang / cl.exe + ld               │
   │     负责：真正的翻译与合并                          │
   └──────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **CMake 自己不做任何编译。**
> 它读 `CMakeLists.txt`，产出一份 `build.ninja` 或 `Makefile`，
> 然后由 Ninja 或 Make 去调用编译器。这三者的分工必须分清。

## 2.2 第一层：编译器与链接器

这一层在《01-编译器/01-编译与链接.md》已经讲过，此处只补充**它们如何被别的工具调用**。

编译器接收的参数有两类：

| 类别 | 例子 | 说明 |
|---|---|---|
| **输入输出** | `-c src/main.c -o main.o` | 处理哪个文件、产出什么 |
| **行为控制** | `-I include`、`-O2`、`-g`、`-DDEBUG` | 去哪里找头文件、怎么优化、是否生成调试信息 |

**构建工具的主要工作，就是替你拼出正确的参数组合。**
你在 `CMakeLists.txt` 里写的 `target_include_directories(...)`，
最终就是变成命令行上的 `-I`。

**验证方法**：设置 `CMAKE_EXPORT_COMPILE_COMMANDS ON` 后，
构建目录里会生成 `compile_commands.json`，
里面**逐条记录了每个源文件实际用的完整命令**。
这是排查「参数到底传没传对」的最直接手段。

## 2.3 第二层：构建系统生成器

这一层目前事实上的标准是 **CMake**。

| 工具 | 特点 | 现状 |
|---|---|---|
| **CMake** | 跨平台、生态最大、被绝大多数开源库采用 | **事实标准** |
| Meson | 语法更简洁，用 Python 写 | 增长中，生态小于 CMake |
| Bazel | 谷歌出品，适合超大单体仓库 | 学习成本高 |
| Autotools | 历史悠久，`configure` / `make` 那一套 | 老旧项目仍在用 |
| 手写 Makefile | 直接写执行器的输入 | 小项目可行，不可移植 |

**为什么 CMake 能成为标准**：不是因为它语法优雅——恰恰相反，
它的语法常被批评。真正的原因是**用的人多**：
绝大多数第三方库提供的都是 `CMakeLists.txt` 或 `*.cmake` 配置文件。
**生态一旦形成，后来者只能跟随。**

## 2.4 第三层：构建执行器

| 工具 | 输入文件 | 特点 |
|---|---|---|
| **GNU Make** | `Makefile` | 历史悠久，几乎无处不在 |
| **Ninja** | `build.ninja` | **专注于快**，文件由工具生成，不适合手写 |
| **MSBuild** | `*.vcxproj` | Visual Studio 自己的构建系统 |
| Xcode Build | `*.xcodeproj` | 苹果平台 |

**Ninja 的设计取舍**：它的构建文件**不是给人写的**，
语法很简单，甚至不提供条件判断与循环。

`文档`

> "Where other build systems are high-level languages, Ninja aims to be an assembler."
> "convenient syntax for writing build files by hand.
> _You should generate your ninja files using another program_."
> "build-time decision-making ability such as conditionals or search paths.
> _Making decisions is slow._"
>
> —— Ninja Manual，Introduction: Philosophical overview / Design goals

**人的精力应该花在写 `CMakeLists.txt` 上，`build.ninja` 是给机器读的。**

**这正是 CMake 与 Ninja 分工的原因**：
一个负责表达（给人读），一个负责执行（给机器读）。

## 2.5 第四层：包管理器

第三方库（如 zlib、Qt）不应被复制进你的仓库，
而应由包管理器下载并编译。CMake 生态里常见三种方式：

| 方式 | 说明 | 适用 |
|---|---|---|
| **`find_package`** | 找**系统里已安装**的库 | 库已由系统或包管理器装好 |
| **`FetchContent`** | 构建时从 Git 下载源码并一起编译 | 库很小、想固定版本 |
| **vcpkg / Conan** | 独立的包管理器，与 CMake 集成 | 依赖较多、需要统一版本 |

**本教材的真实案例**：`NeoServerUpdateModpack` 用的是 **vcpkg** 清单模式，
依赖写在 `vcpkg.json` 里，`CMakeLists.txt` 通过
`CMAKE_TOOLCHAIN_FILE` 指向 vcpkg 的集成脚本。

## 2.6 常见误解

| 误解 | 事实 |
|---|---|
| 「CMake 是编译器」 | CMake **从不编译任何东西**，它只生成构建文件 |
| 「`CMakeLists.txt` 是配置文件」 | 它是一门编程语言写的程序，见第 3 节 |
| 「装了 CMake 就不需要 Make/Ninja」 | 两者都要有，缺了执行器 CMake 无法工作 |
| 「CMake 生成的 `Makefile` 可以手改」 | 每次重新配置都会被覆盖，改了没有意义 |
| 「用 CMake 就不用管编译器参数了」 | 参数还是要给，只是从命令行搬到了 `CMakeLists.txt` |

# 第 3 节 CMake 是一门语言

## 3.1 一个普遍存在的误解

多数人第一次见到 `CMakeLists.txt` 时会把它读成一份**配置文件**，
类似 `.ini` 或 `.json`——一堆键值对，声明一下源文件在哪、输出叫什么。

**这个理解会导致一系列判断失误**：

- 以为命令的顺序可以随意调整
- 以为变量就是文本替换
- 以为看到 `if()` 就是「条件配置项」
- 遇到报错时不知道该从哪里找原因

> [!IMPORTANT]
> **`CMakeLists.txt` 是一个程序**，用一门叫 CMake 的语言写成。
> CMake 读它的过程叫**配置（configure）**，等价于「运行这个程序」。

**这个区别不是措辞问题，它决定了很多具体行为。**

## 3.2 证据一：它有变量

`CMake`

```cmake
set(MY_NAME "app")
set(MY_SOURCES src/main.c src/calc.c)

message(STATUS "工程名：${MY_NAME}")
add_executable(${MY_NAME} ${MY_SOURCES})
```

- `set()` 是**赋值**
- `${}` 是**取值**
- 变量可以被重新赋值

**配置文件里没有「赋值」这个概念**，只有「设置某一项的值」。
CMake 的 `set()` 是真正的赋值语句。

**一个容易忽略的细节**：`set()` 赋的值默认是**字符串**，
但 CMake 的字符串可以含分号，而含分号的字符串会被当作**列表**：

`CMake`

```cmake
set(LIST_A "x;y;z")     # 这是 3 个元素的列表
set(LIST_B x y z)       # 这也是 3 个元素的列表，写法更常见
```

**`${LIST_A}` 展开后是 `x;y;z`**，而 CMake 内部把它当作三个元素。
这是 CMake 列表的实现方式，也是很多「参数个数不对」报错的根源。

## 3.3 证据二：它有作用域

`实测数据`
`CMake`

```cmake
# scope.cmake    运行：cmake -P scope.cmake
set(VAR "outer")

function(my_func)
    set(VAR "inner")      # 只在这个函数内有效
    message(STATUS "函数内：${VAR}")
endfunction()

my_func()
message(STATUS "函数外：${VAR}")
```

**输出**（`cmake -P` 会给 `message(STATUS ...)` 的每一行加上 `-- ` 前缀，此处省略）：

`Text`

```text
函数内：inner
函数外：outer
```

**函数有自己的作用域，且默认不向外传递变量。**
这与配置文件的行为完全不同——配置文件没有嵌套的求值环境。

**目录也有作用域**：

`CMake`

```cmake
# 顶层 CMakeLists.txt
set(TOP_VAR "top")
add_subdirectory(sub)      # 进入子目录
```

`CMake`

```cmake
# sub/CMakeLists.txt
message(STATUS "${TOP_VAR}")   # 能读到，子目录继承父目录的变量
set(SUB_VAR "sub")             # 但父目录读不到 SUB_VAR
```

**子目录能读父目录的变量，反之不行。** 这是 CMake 作用域的基本规则。

## 3.4 证据三：它有函数与宏

`CMake`

```cmake
function(add_warning_flags target)
    target_compile_options(${target} PRIVATE -Wall -Wextra)
endfunction()

add_warning_flags(app)
```

**这是抽象与复用**——把一组操作打包成一个名字。
配置文件里没有这种东西。

**`function` 与 `macro` 的区别，恰恰体现了语言的求值规则**：

| | `function` | `macro` |
|---|---|---|
| 参数 | 真正的参数，有自己的作用域 | **文本替换**，没有新作用域 |
| `return()` | 返回调用处 | **从调用者的位置返回** |
| 变量修改 | 不影响调用者 | **影响调用者** |

**宏是文本替换**这一点与 C 的宏类似，
也意味着宏里的 `${}` 会在**调用者的上下文**里求值。
不理解这一条，宏的行为会显得莫名其妙。

## 3.5 证据四：它有控制流

`CMake`

```cmake
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    message(STATUS "调试构建")
elseif(CMAKE_BUILD_TYPE STREQUAL "Release")
    message(STATUS "发布构建")
else()
    message(WARNING "未指定构建类型")
endif()

foreach(src ${SOURCES})
    message(STATUS "源文件：${src}")
endforeach()

while(NOT DONE)
    # ...
endwhile()
```

**`if()` 不是「配置项开关」**，而是一条真正的条件语句。
它的条件在**配置阶段**求值，决定后面哪些命令会被执行。

**`if()` 的求值规则比较特别**：

`CMake`

```cmake
if(VAR)              # VAR 的值为真（非空、非 0、非 FALSE 等）
if(NOT VAR)          # 取反
if(DEFINED VAR)      # 变量是否已定义（不关心它的值）
if(VAR STREQUAL "x") # 字符串比较
if(EXISTS path)      # 路径是否存在
if(TARGET app)       # 某个 target 是否已定义
if(CMAKE_CXX_COMPILER_ID STREQUAL "GNU")   # 判断编译器家族
```

**`if(VAR)` 与 `if(${VAR})` 的区别**：
前者判断「变量 VAR 的值是否为真」，后者先把值展开再判断。
当 VAR 的值是另一个变量名或含特殊字符时，两者结果不同。
**推荐用 `if(VAR)` 这种不展开的写法**，CMake 官方文档也是这个建议。

## 3.6 证据五：它有列表这种数据结构

`CMake`

```cmake
set(FRUITS apple banana cherry)

list(LENGTH FRUITS n)             # n = 3
list(APPEND FRUITS date)          # 追加一个
list(REMOVE_ITEM FRUITS banana)   # 删掉一个
list(SORT FRUITS)                 # 排序

foreach(f ${FRUITS})
    message(STATUS "${f}")
endforeach()
```

**`list()` 是一个完整的列表操作函数族**：追加、删除、排序、查找、取子列表。
配置文件不会有「对某个列表排序」这种操作。

## 3.7 它是一门什么样的语言

**在 `<CMake>` 的安装目录下就能看到语言本身的文档，与编译器、链接器的文档并列。**

`实测数据`
`Text`

```text
<CMake>/doc/cmake/html/manual/cmake-language.7.html
<CMake>/doc/cmake/html/manual/cmake-commands.7.html
<CMake>/doc/cmake/html/manual/cmake-variables.7.html
```

**CMake 官方把它分成三份手册**：语言、命令、变量。
这与「C 语言规范 + 标准库」的组织方式完全一致。

把它与常见语言对照：

| 方面 | CMake | 说明 |
|---|---|---|
| 程序单位 | `CMakeLists.txt` | 相当于一个源文件 |
| 语句 | 命令，形如 `名字(参数...)` | 括号里的就是参数，用空白分隔 |
| 注释 | `#` 到行尾 | 与 shell 相同 |
| 变量 | `set()` / `${}` | 弱类型，本质是字符串 |
| 数据结构 | 字符串与列表 | 列表用分号分隔 |
| 控制流 | `if` / `foreach` / `while` / `break` / `continue` | 完整 |
| 函数 | `function()` / `macro()` | 有作用域差异 |
| 模块 | `include()` / `find_package()` | 相当于导入 |
| 作用域 | 函数、目录、缓存三级 | 见 3.8 小节 |

**它是一门领域特定语言（DSL）**——为「描述构建过程」这一件事而设计，
不打算用来写通用程序。

> [!IMPORTANT]
> **是不是 DSL，不改变它是语言这个事实。**
> 判断标准不是「能不能写业务代码」，而是
> 「有没有变量、控制流、函数、作用域」——它全都有。

## 3.8 求值模型：两个阶段

**这是理解 CMake 最关键的一点。**

用 CMake 构建分两个阶段，**两者的职责完全不同**：

`Text`

```text
   阶段一：配置（configure）              阶段二：构建（build）
   ─────────────────────────            ─────────────────────────
   cmake -S . -B build                   cmake --build build
                                         （或直接 ninja -C build）

   运行 CMakeLists.txt
   求值所有变量、条件、循环
   检查编译器是否可用
   生成 build.ninja / Makefile    ──→    读 build.ninja
   生成 CMakeCache.txt                   按依赖顺序执行编译器命令
   生成 compile_commands.json            只重编改动过的文件

   做一次，慢（数秒到数十秒）              每次都做，快（只做必要的）
```

**为什么必须分清**：

| 现象 | 原因 |
|---|---|
| 改了 `CMakeLists.txt` 后必须重新配置 | 阶段一的程序变了 |
| 只改 `.c` 文件不必重新配置 | 阶段一的输出没变 |
| `message()` 只在配置阶段打印一次 | 它是阶段一的语句 |
| 构建时的报错来自编译器，不是 CMake | 阶段二由 Ninja 驱动 |
| 配置阶段报「找不到库」 | 阶段一在探测环境 |
| `CMakeCache.txt` 里的值改了不生效 | 缓存只在**首次**配置时写入 |

**`CMakeCache.txt` 有一条单独的规则**：
它保存首次配置时探测到的结果（编译器路径、库位置等）。
**之后每次配置都会复用缓存里的值**，除非用 `-D` 显式覆盖或删除该文件。

> [!TIP]
> **改了 `CMakeLists.txt` 却不生效，多数是缓存造成的**。
> 如果改动正好落在被缓存的值上，就不会生效；
> 删掉构建目录重新配置即可排除这一类问题。

## 3.9 为什么理解这一点很关键

**因为它决定了排查问题的方向。**

| 报错出现在 | 说明问题在 | 排查方向 |
|---|---|---|
| `cmake -S . -B build` | 阶段一 | `CMakeLists.txt` 的写法、环境探测 |
| `cmake --build build` | 阶段二 | 源码本身、编译器参数 |

**两者混在一起看，就会浪费大量时间。**
例如「找不到头文件」既可能是阶段一没配对 `include_directories`，
也可能是阶段二传参失败——分开看就一目了然。

**还有一层意义**：本教材后续遇到的工程（如 `NeoServerUpdateModpack`）
规模都不小，`CMakeLists.txt` 加起来上千行。
**把它们当代码读，才有可能读懂**；当配置文件读，只会越读越乱。

# 第 4 节 CMakeLists.txt 详解

## 4.1 一个真实的最小工程

以下取自本教材的 `B-examples/03-CMake-C`（**原文**，有删减）：

`CMake`

```cmake
cmake_minimum_required(VERSION 3.16)

project(app
    VERSION 1.0.0
    DESCRIPTION "CMake 多文件工程示例（C）"
    LANGUAGES C
)

set(CMAKE_C_STANDARD 17)
set(CMAKE_C_STANDARD_REQUIRED ON)

if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    set(CMAKE_BUILD_TYPE Debug CACHE STRING "构建类型" FORCE)
endif()

set(CMAKE_RUNTIME_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/bin")

add_executable(app
    src/main.c
    src/calc.c
)

target_include_directories(app
    PRIVATE "${CMAKE_CURRENT_SOURCE_DIR}/include"
)

if(MSVC)
    target_compile_options(app PRIVATE /source-charset:utf-8 /execution-charset:gbk /W4)
else()
    target_compile_options(app PRIVATE -g -Wall -Wextra -finput-charset=UTF-8 -fexec-charset=GBK)
endif()

set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

**这份文件已经用到了变量、条件、函数调用、作用域、列表**——
第 3 节列出的五项证据它占了四项。

## 4.2 逐行讲解

### `cmake_minimum_required(VERSION 3.16)`

**声明这份文件要求的最低 CMake 版本。**

它不只是版本检查。**它还决定了 CMake 用哪一套「策略」来解释这份文件**——
CMake 的行为会随版本变化，这一行告诉它「按 3.16 时代的规则来」。

**为什么必须有这一行**：没有它，CMake 会警告，
而且不同版本上的行为可能不一致。

**一条实际会遇到的版本差异**：CMake 4.x 起**不再支持低于 3.5 的版本声明**。
拿到旧工程时会报：

`实测数据`
`Text`

```text
Compatibility with CMake < 3.5 has been removed from CMake.
```

两种处理方式：

`Bash`

```bash
# 临时：用命令行参数放宽限制（不改动他人代码）
cmake -S . -B build "-DCMAKE_POLICY_VERSION_MINIMUM=3.5"
```

> [!WARNING]
> 等号后的值必须整体加引号。不加引号时 PowerShell 会把它拆成两个参数，
> CMake 会报 `Invalid CMAKE_POLICY_VERSION_MINIMUM value "3"`。

长期使用则应直接修改那一行版本号。

### `project(...)`

**声明工程名，并触发编译器探测。**

| 参数 | 作用 |
|---|---|
| 第一个位置参数 | 工程名，同时成为变量 `PROJECT_NAME` |
| `VERSION` | 版本号，拆成 `PROJECT_VERSION_MAJOR` 等变量 |
| `DESCRIPTION` | 描述文本 |
| `LANGUAGES` | **启用哪些语言**，决定去探测哪些编译器 |

**`LANGUAGES` 的作用常被忽略**：写 `C` 就只找 C 编译器；
写 `C CXX` 会同时找 C 与 C++ 编译器。
只写 `C` 时若代码里用了 C++，配置能过，构建时才报错。

**`project()` 必须出现在大多数其他命令之前**，
因为它建立了编译器相关的变量。

### `set(CMAKE_C_STANDARD 17)`

**设置 C 语言标准。**

| 变量 | 含义 |
|---|---|
| `CMAKE_C_STANDARD` | 期望的标准（11 / 17 / 23） |
| `CMAKE_C_STANDARD_REQUIRED` | 设 `ON` 表示**必须是这个版本**，不允许降级 |
| `CMAKE_C_EXTENSIONS` | 设 `OFF` 表示用 `-std=c17` 而不是 `-std=gnu17` |

**为什么要加上 `CMAKE_C_STANDARD_REQUIRED ON`**：
不加时，若编译器不支持指定标准，CMake 会**悄悄降级**到它能支持的最高版本。
加上之后会直接报错，问题暴露得更早。

### `if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)`

这一段处理的是**单配置生成器与多配置生成器的差异**：

| 生成器 | 例子 | `CMAKE_BUILD_TYPE` 的含义 |
|---|---|---|
| **单配置** | Ninja、MinGW Makefiles | **有用**，构建时只能用这一个类型 |
| **多配置** | Visual Studio、Xcode | **无效**，构建时用 `--config Debug` 指定 |

**多配置生成器下 `CMAKE_CONFIGURATION_TYPES` 有值**（如 `Debug;Release`），
所以这段条件是「只在单配置生成器且未指定类型时，默认设为 Debug」。

**`CACHE STRING "构建类型" FORCE` 三个部分分别表示**：
写入缓存、类型是字符串、帮助文本、强制覆盖已有的缓存值。

### `set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ...)`

**指定可执行文件输出到哪里。**

**路径里的 `CMAKE_BINARY_DIR` 指向构建目录**（即 `-B` 指定的那个），
而不是源码目录。**构建产物不应当写回源码目录**——
这也是 `B-examples/*/.gitignore` 里忽略 `build/` 的原因。

**多配置生成器会再套一层**，所以实际路径不同：

`Text`

```text
Ninja  → build/mingw/bin/app.exe
MSVC   → build/msvc/bin/Debug/app.exe
```

### `add_executable(app ...)` 与 `target_include_directories(...)`

**这两条是核心，涉及 CMake 最重要的概念：target。**

## 4.3 核心概念：target

**target 是 CMake 的枢纽。**

`Text`

```text
        add_executable(app src/main.c src/calc.c)
                          │
                          │  建立一个名为 app 的 target
                          ▼
   ┌──────────────────────────────────────────────┐
   │  target: app                                  │
   │  ├── 类型        : 可执行文件                   │
   │  ├── 源文件      : src/main.c src/calc.c       │
   │  ├── 头文件路径  : include/                    │
   │  ├── 编译选项    : -g -Wall -Wextra ...        │
   │  ├── 链接库      : （无）                       │
   │  └── 输出名      : app / app.exe               │
   └──────────────────────────────────────────────┘
                          │
        target_include_directories(app ...)
        target_compile_options(app ...)
        target_link_libraries(app ...)
                          │  都是往这个 target 上加属性
                          ▼
```

**target 有三种类型**：

| 命令 | 类型 | 说明 |
|---|---|---|
| `add_executable` | 可执行文件 | 最终产物 |
| `add_library` | 库 | 静态库 `.a` / `.lib`，或动态库 `.so` / `.dll` |
| `add_library(... INTERFACE)` | **接口库** | 不产出文件，只承载「用法要求」 |

**为什么 target 这么重要**：现代 CMake 的一切都挂在 target 上。

> [!IMPORTANT]
> **「以 target 为中心」是现代 CMake 与旧式写法的分界线。**

## 4.4 PUBLIC / PRIVATE / INTERFACE

这三个关键字是 CMake 里最容易混淆、也最能体现设计意图的地方。

**它们回答的是同一个问题：这条属性，谁需要知道？**

| 关键字 | 自己编译时用 | 使用者也要用 | 典型场景 |
|---|---|---|---|
| `PRIVATE` | 是 | 否 | 内部实现细节 |
| `PUBLIC` | 是 | 是 | 头文件里 `#include` 了它 |
| `INTERFACE` | 否 | 是 | 只有头文件，无需编译 |

**用一个具体例子说明**：

`CMake`

```cmake
# mylib 是个静态库
add_library(mylib STATIC mylib.c)

target_include_directories(mylib
    PUBLIC  include          # 使用者也要能找到这些头文件
    PRIVATE src/internal     # 只有 mylib.c 自己需要
)

target_link_libraries(mylib
    PUBLIC  m                # 使用者链接 mylib 时也要链接 m
    PRIVATE internal_helper  # 只是 mylib 内部用到
)
```

**判断口诀**：

- **头文件里 `#include` 了某个库 → `PUBLIC`**
- **只在 `.c` / `.cpp` 里用 → `PRIVATE`**
- **这个 target 本身不需要编译，只是转发要求 → `INTERFACE`**

> [!WARNING]
> `PRIVATE` 与 `PUBLIC` 写反不会立刻报错，但会在使用者那边
> 表现为「找不到头文件」或「链接错误」，
> **而错误现场离原因很远**，排查起来很费时间。

**对比旧式写法**：老工程常用

`CMake`

```cmake
include_directories(include)      # 影响此后所有 target，无差别
link_libraries(m)                 # 同上
```

**这类命令没有「谁需要」的概念**，一律全局生效。
后果是：任何 target 都能看到任何头文件，
**依赖关系变得不可见**，改一处容易连带影响别处。

## 4.5 常用命令速查

### 工程与 target

| 命令 | 作用 |
|---|---|
| `cmake_minimum_required(VERSION x.y)` | 声明最低版本与策略 |
| `project(名字 ...)` | 声明工程，探测编译器 |
| `add_executable(名 源文件...)` | 建立可执行文件 target |
| `add_library(名 [STATIC\|SHARED] 源文件...)` | 建立库 target |
| `add_subdirectory(目录)` | 引入子目录的 `CMakeLists.txt` |

### target 属性

| 命令 | 作用 |
|---|---|
| `target_include_directories` | 头文件搜索路径 |
| `target_compile_options` | 编译选项 |
| `target_compile_definitions` | 预处理宏定义（等价于 `-D`） |
| `target_link_libraries` | 要链接的库 |
| `target_sources` | 追加源文件 |
| `set_target_properties` | 设置其他属性（输出名、位置等） |

### 变量与流程

| 命令 | 作用 |
|---|---|
| `set(名 值...)` | 赋值 |
| `unset(名)` | 删除变量 |
| `option(名 "说明" 默认值)` | 定义一个开关选项 |
| `if` / `elseif` / `else` / `endif` | 条件 |
| `foreach` / `while` / `break` / `continue` | 循环 |
| `function` / `macro` / `endfunction` / `endmacro` | 定义可复用块 |
| `message([STATUS\|WARNING\|FATAL_ERROR] 文本)` | 输出信息 |
| `include(文件)` | 引入 `.cmake` 脚本 |
| `find_package(包名)` | 查找已安装的库 |

### 常用于调试的命令

| 命令 | 用途 |
|---|---|
| `message(STATUS "${变量名}")` | **打印变量值**，最常用的排查手段 |
| `message(FATAL_ERROR "...")` | 打印并终止配置，用于断言 |
| `get_cmake_property(_vars VARIABLES)` | 列出所有已定义变量 |
| `cmake --trace-expand` | 打印每条命令的求值结果 |

构建阶段看不到它的输出。

## 4.6 现代 CMake 与旧式写法

| 旧式（不推荐） | 现代（推荐） | 差别 |
|---|---|---|
| `include_directories()` | `target_include_directories()` | 后者指定作用对象 |
| `link_libraries()` | `target_link_libraries()` | 同上 |
| `add_definitions(-DX)` | `target_compile_definitions()` | 同上 |
| `set(CMAKE_CXX_FLAGS "-Wall")` | `target_compile_options()` | 前者全局，后者按 target |
| `file(GLOB ...)` 收集源文件 | **显式列出源文件** | 见下 |
| `CMAKE_CXX_FLAGS` 传 `-I` | `target_include_directories` | 后者能传递依赖 |

**关于 `file(GLOB)`**：它看起来很方便——

`CMake`

```cmake
file(GLOB SOURCES "src/*.c")     # 收集所有 .c
add_executable(app ${SOURCES})
```

但**不推荐**，原因有两个：

1. **新增文件后不会自动重新配置**，必须手工重新跑一次 `cmake`，
   否则新文件不会参与构建，且没有任何提示
2. 部分平台与工具链对通配符展开的支持不一致

**本教材示例工程的注释里明确写了这一点**（**原文**）：

> 多文件：源文件必须显式列出
> （MSYS2 从 2024-11 起禁用了通配符展开，别用 `file(GLOB *.c)`）

**`CMAKE_CXX_FLAGS` 之类的全局变量为什么也被列为旧式**：
它影响此后定义的所有 target，且**不会传递给使用者**。
用 `target_compile_options` 才能让依赖关系正确地传递下去。

## 4.7 多目录工程

真实工程通常按模块分目录，靠 `add_subdirectory` 串起来：

`Text`

```text
project/
├── CMakeLists.txt          顶层
├── src/
│   ├── CMakeLists.txt
│   └── *.c
└── libs/
    └── mathlib/
        ├── CMakeLists.txt
        └── mathlib.c
```

顶层：

`CMake`

```cmake
cmake_minimum_required(VERSION 3.16)
project(demo LANGUAGES C)

add_subdirectory(libs/mathlib)   # 先建立库 target
add_subdirectory(src)            # 再建立依赖它的可执行文件
```

`libs/mathlib/CMakeLists.txt`：

`CMake`

```cmake
add_library(mathlib STATIC mathlib.c)
target_include_directories(mathlib PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
```

`src/CMakeLists.txt`：

`CMake`

```cmake
add_executable(app main.c)
target_link_libraries(app PRIVATE mathlib)   # 头文件路径会自动带过来
```

**关键在于最后一行**：因为 `mathlib` 用 `PUBLIC` 声明了头文件路径，
使用者 `app` **不需要再写一遍 `target_include_directories`**。
这就是 target 属性传递的价值。

**顺序要求**：`add_subdirectory(libs/mathlib)` 必须在
`add_subdirectory(src)` **之前**，因为后者要用到前者的 target。
**这也印证了 CMakeLists.txt 是程序——语句有执行顺序。**

## 4.8 CMakePresets.json

`CMakePresets.json` 把常用的命令行参数固化下来，避免每次手敲。

本教材 `B-examples/03-CMake-C` 的配置（**原文**，节选）：

`JSON`

```json
{
  "version": 3,
  "cmakeMinimumRequired": { "major": 3, "minor": 21, "patch": 0 },
  "configurePresets": [
    {
      "name": "mingw-gdb",
      "displayName": "MinGW GCC + GDB (Ninja, Debug)",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/mingw",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_C_COMPILER": "gcc",
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
    }
  ]
}
```

用法：

`Bash`

```bash
cmake --preset mingw-gdb              # 配置
cmake --build --preset mingw-gdb      # 构建
```

| 字段 | 作用 |
|---|---|
| `generator` | 用哪个执行器（Ninja / Visual Studio ...） |
| `binaryDir` | 构建目录 |
| `cacheVariables` | 传给 `CMakeCache.txt` 的变量，等价于 `-D` |

**它的价值在于「把构建方式写进仓库」**：
换一台机器只要 `cmake --preset xxx`，不必问「你当初是怎么编的」。

## 4.9 常见报错解读

| 报错 | 阶段 | 原因 |
|---|---|---|
| `CMake Error: Could not find CMAKE_C_COMPILER` | 配置 | 编译器不在 PATH 中 |
| `Compatibility with CMake < 3.5 has been removed` | 配置 | 旧工程的版本声明过低 |
| `Invalid CMAKE_POLICY_VERSION_MINIMUM value "3"` | 配置 | 传参时等号后的值没加引号 |
| `Cannot find source file: src/x.c` | 配置 | `add_executable` 里的路径写错 |
| `undefined reference to 'xxx'` | **构建** | 链接阶段，函数声明了没定义 |
| `fatal error: xxx.h: No such file or directory` | **构建** | 头文件路径没传给编译器 |
| `Target "app" links to target "xxx" but the target was not found` | 配置 | `target_link_libraries` 里的 target 未定义 |
| `CMake Error: The current CMakeCache.txt is different...` | 配置 | 换过编译器或路径，需删除构建目录 |

**区分「配置」与「构建」两列，就是第 3.8 小节的直接应用。**

# 第 5 节 在 VS Code 中使用这些工具

## 5.1 CMake Tools 扩展做了什么

装了 CMake Tools 之后，构建过程被包在图形界面里：

| 界面元素 | 背后执行的动作 |
|---|---|
| 选择「工具包」（Kit） | 决定 `CMAKE_C_COMPILER` 等变量 |
| 状态栏的「配置」 | `cmake -S . -B build` |
| 状态栏的「生成」 | `cmake --build build` |
| 选择构建类型（Debug/Release） | 决定 `CMAKE_BUILD_TYPE` |
| 选择「变体」（Variant） | 同上，多配置生成器下用 `--config` |

**它没有引入新东西**，只是把第 3.8 小节那两个阶段做成了按钮。
**理解命令行之后，这个界面就只是快捷方式。**

## 5.2 与 `tasks.json` 的关系

两种方式都能构建，区别在于**谁来驱动**：

| | CMake Tools | `tasks.json` |
|---|---|---|
| 谁调用 cmake | 扩展 | 任务里写的命令 |
| 配置来源 | Kit + 变体 | 任务里写的参数 |
| 灵活性 | 受扩展的约定限制 | 完全自定义 |
| 适合 | 常规 CMake 工程 | 需要特殊参数或流程 |

**本教材的示例工程两种都提供了**：
`tasks.json` 里有显式的构建任务，`CMakePresets.json` 里也有预设。
读者可以对照两者，看清「界面上点一下」等价于哪条命令行。

## 5.3 本教材示例的构建路径

以 `B-examples/03-CMake-C` 为例：

`Text`

```text
   按 F5
     │
     ▼
   ① 读 .vscode/launch.json 的 preLaunchTask
     │
     ▼
   ② 执行 .vscode/tasks.json 里的构建任务
     │
     ├─ cmake --preset mingw-gdb          ← 配置阶段
     ├─ cmake --build --preset mingw-gdb  ← 构建阶段
     │
     ▼
   ③ 产物 build/mingw/bin/app.exe
     │
     ▼
   ④ 按 launch.json 的 program 字段启动 GDB 调试
```

**对照第 3.8 小节的两阶段图**，可以看到配置与构建是分开的两条命令。
**这也解释了为什么改了 `CMakeLists.txt` 后按 F5 会重新配置**——
`tasks.json` 里的配置任务每次都跑。

| 构建系统生成器 | Build system generator | 把描述翻译成执行器输入的工具，如 CMake |
| 构建执行器 | Build executor | 按依赖图执行命令的工具，如 Ninja、Make |
| 生成器 | Generator | CMake 里指具体用哪个执行器 |
| 配置 | Configure | CMake 求值 `CMakeLists.txt`、生成构建文件的过程 |
| 构建 | Build | 执行器调用编译器产出可执行文件的过程 |
| 增量构建 | Incremental build | 只重做必要的部分 |
| 全量构建 | Clean build | 从零重建全部 |
| 目标 | Target | CMake 里可执行文件或库的抽象，属性都挂在它上面 |
| 接口库 | INTERFACE library | 不产出文件、只承载「用法要求」的 target |
| 工具链文件 | Toolchain file | 描述编译器与目标平台的 `.cmake` 文件 |
| 交叉编译 | Cross compilation | 在 A 平台生成 B 平台的产物 |
| 预设 | Preset | `CMakePresets.json` 里固化的一组参数 |
| 符号 | Symbol | 函数或变量的名字 |
| 符号数据库 | Symbol database | 存放调试信息的文件，即 PDB 或 DWARF |
| 调试信息 | Debug information | 源码与机器码的对照信息，`-g` 生成 |
| 符号服务器 | Symbol server | 按需提供公开组件调试信息的服务 |
