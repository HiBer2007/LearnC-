**编译器的优化等级是一个字母之差、效果差数倍的开关。**

**它同时是最容易出错的地方**：优化会改变程序的实际行为，
而很多改变在源码上完全看不出来。

**本章节用同一段代码在六个等级下的实测结果，说明它们究竟差在哪里。**

# 第 1 节 优化在做什么

## 1.1 一个前提

> [!IMPORTANT]
> **编译器最优先的目标不是快，而是「不改变程序的可观察行为」。**

优化是在**满足这个前提**的情况下改写代码。
**当优化改变了行为，那是编译器认为
「这个行为本来就不该被依赖」**——通常是因为源码里存在未定义行为。

## 1.2 优化在改什么

| 方向 | 具体做法 |
|---|---|
| **减少内存访问** | 变量从栈搬进寄存器 |
| **减少指令数** | 常量折叠、死代码消除 |
| **减少函数调用** | 内联 |
| **减少循环开销** | 循环展开、循环不变量外提 |
| **并行计算** | 向量化（一条指令处理多个数据） |
| **改善局部性** | 调整指令顺序，让流水线更顺 |

**第 1 项是最重要的**：`-O0` 到 `-O1` 的最大变化就是这一步，
而它带来的加速也最大（见第 3 节）。

## 1.3 为什么 `-O0` 那么慢

`-O0` 的目标不是「慢」，而是**「调试友好」**：

| `-O0` 的做法 | 好处 |
|---|---|
| 每个变量都放在栈上 | 调试器随时能改它的值 |
| 每步都写回内存 | 断点处看到的值是准的 |
| 不内联 | 调用栈与源码一一对应 |
| 不重排代码 | 单步时顺序与源码一致 |

**代价就是慢。** 本章节实测中 `-O0` 比 `-O1` 慢 3.68 倍（见第 3.3 小节）。

# 第 2 节 各等级的含义

## 2.1 GCC / Clang

| 等级 | 含义 | 典型用途 |
|---|---|---|
| `-O0` | **不优化**，逐字翻译 | 调试 |
| `-O1` | 基本优化，不做耗时的分析 | 编译慢的机器上折中 |
| `-O2` | **常用发布级**，绝大多数优化 | 发布 |
| `-O3` | 在 `-O2` 基础上加更激进的优化 | 计算密集型 |
| `-Os` | **优先减小体积** | 嵌入式、体积敏感 |
| `-Og` | 优化但不妨碍调试 | 开发时想快一点又不想失去调试 |
| `-Ofast` | **`-O3` 加不顾标准合规的优化** | 极少数场景 |

**`-O2` 与 `-O3` 的差别**主要在**向量化**与更激进的内联展开。
本章节实测中这正好是最大的代码差异来源（见第 4 节）。

**关于 `-Ofast` 的名字**：它不叫 `-O4` 而叫 `-Ofast`，
是因为它**明确放弃了标准合规性**。
它等价于 `-O3 -ffast-math`，而 `-ffast-math` 会让浮点运算不再遵守 IEEE 754。

**`-Og` 值得单独一提**：它是为「想调试又不想太慢」设计的。
它开启不妨碍调试的优化，**编译产物仍可正常设置断点与查看变量**。

## 2.2 MSVC

| 参数 | 等价于 | 说明 |
|---|---|---|
| `/Od` | `-O0` | **调试默认** |
| `/O1` | 约 `-Os` | 优先小 |
| `/O2` | 约 `-O2` | **发布默认** |
| `/Ox` | 部分 `-O3` | 最大优化，不含向量化 |
| `/Ot` | — | 优先快 |
| `/GL` | 类似 LTO | 全程序优化 |
| `/fp:fast` | `-ffast-math` | 快速浮点 |

> [!WARNING]
> **MSVC 的 `/O1` 与 `/O2` 的含义与 GCC 不同**：`/O1` 是「小」，`/O2` 是「快」，
> **与 GCC 的 `-O1`（基本优化）不是一回事。**
> 看 MSVC 工程文件时，`/O2` 表示「优化速度」，不是「二级优化」。

## 2.3 两套参数的对应

> [!NOTE]
> **不优化（调试）用 `-O0` / `/Od`**；
> **优化速度用 `-O2`、`-O3` / `/O2`、`/Ox`**；
> **优化体积用 `-Os` / `/O1`**；
> **快速浮点用 `-Ofast` / `/O2 /fp:fast`**。
> `-Og` 在 MSVC 里没有直接对应。

# 第 3 节 体积与速度实测

## 3.1 环境与探针

**环境**：MinGW `gcc` 15.2.0，Windows 11 build 22631。

**探针**：一个 8192 元素 `int` 数组的平方和循环，外层重复 4000 次，
**完整源码见附录 B.1**。第 3 节的数据由它产生；
第 4 节的汇编对照另用第 4.1 小节的 `sum_squares.c`。

**探针为什么这么写**：普通的短程序运行时间只有几毫秒，
**进程启动开销会盖过优化带来的差别**。
必须让计算本身占主要时间，测出的数字才有意义。

## 3.2 体积

<small style="color:gray">实测数据</small>

| 等级 | 可执行文件 | 相对 `-O0` |
|---|---|---|
| `-O0` | 80,481 字节 | 1.000 |
| `-O1` | 80,351 字节 | 0.998 |
| `-O2` | 80,899 字节 | 1.005 |
| `-O3` | 80,899 字节 | 1.005 |
| `-Os` | 80,387 字节 | 0.999 |
| `-Ofast` | 83,637 字节 | **1.039** |

**体积几乎没有差别**，最大波动 4%。

**为什么**：程序体积主要来自运行时库与启动代码，
优化只影响自己那部分代码，占比很小。

**这与《03-构建工具链/04-符号与调试信息.md》第 6 节的结论并不矛盾**：
那边对比的是**有无调试信息**，差别来自 DWARF/PDB 这类附加数据；
这里对比的是**优化程度**，只影响代码段。

**`-Os` 并没有让产物变小**——因为省下的那点代码量
在总大小里看不出来。**`-Os` 的价值要在代码量大的工程上才体现。**

**各等级的编译耗时见附录 B.2。**

## 3.3 速度

**同一探针，各跑 7 次取最快。**

<small style="color:gray">实测数据</small>

| 等级 | 运行耗时 | 相对 `-O0` 加速 |
|---|---|---|
| `-O0` | **55.0 毫秒** | 1.00 |
| `-O1` | **14.9 毫秒** | **3.68** |
| `-O2` | **11.2 毫秒** | **4.90** |
| `-O3` | **9.4 毫秒** | **5.88** |
| `-Os` | 14.8 毫秒 | 3.72 |
| `-Ofast` | 9.9 毫秒 | 5.53 |

## 3.4 最重要的一条规律

> [!IMPORTANT]
> **`-O0` 到 `-O1` 这一步就拿到了 3.68 倍，占总收益的六成以上。**

**之后的每一步收益都在递减**：

<small style="color:gray">text</small>

```text
   O0 → O1   3.68 倍   ← 一步拿走大半
   O1 → O2   1.33 倍
   O2 → O3   1.19 倍
```

**原因**：`-O0` 把每个变量都放在栈上，
每次读写都是一次内存访问。`-O1` 把它们搬进寄存器，
**内存访问次数直接降了一个数量级**。

**更高的等级做的是更细的活**：循环展开、向量化、更聪明的调度。
收益递减，但积累起来仍可观。

> [!TIP]
> **必须用 `-O0` 调试时，知道会慢数倍即可**，不要误以为程序本身写得差。
> 想要速度又不想折腾，`-O2` 是性价比最高的选择；
> 计算密集型再试 `-O3`，实测确认有提升才采用。

# 第 4 节 汇编对照

## 4.1 探针

**对照用的函数是探针里的 `sum_squares`，这里给它加了 `noinline`，
以便在每个等级下都能在反汇编里看到它的函数体。**

<small style="color:gray">实测数据</small>
<small style="color:gray">c</small>

```c
/* sum_squares.c    编译：gcc -std=c17 -O2 -S sum_squares.c -o sum_squares.s */
#include <stdio.h>

#define NOINLINE __attribute__((noinline))

/* 阻止内联：不加的话 -O1 及以上会把这个函数整个内联掉，
   反汇编里根本找不到它，也就无从对比 */
NOINLINE long sum_squares(const int *a, int n) {
    long s = 0;
    for (int i = 0; i < n; ++i) s += (long)a[i] * a[i];
    return s;
}

int main(void) {
    int a[4] = {1, 2, 3, 4};        /* 只为让这个文件能独立编译运行 */
    printf("%ld\n", sum_squares(a, 4));
    return 0;
}
```

## 4.2 三种截然不同的策略

<small style="color:gray">实测数据</small>

| 等级 | 指令数 | 向量指令 | 策略 |
|---|---|---|---|
| `-O0` | **30** | 0 | 变量全在栈上，逐字翻译 |
| `-O1` | **18** | 0 | 变量进寄存器，紧凑标量循环 |
| `-O2` | **21** | 0 | 标量循环，稍作展开与对齐 |
| `-O3` | **98** | **7** | **向量化，一次处理 4 个元素** |
| `-Os` | **14** | 0 | **指令最少** |
| `-Ofast` | 98 | 7 | 与 `-O3` 相同 |

**表里有三处需要解释**：

1. **`-O3` 的指令数最多（98 条）**——向量化要用更多指令做准备与收尾
2. **`-Os` 的指令数最少（14 条）**——它把循环压到了极致
3. **`-Ofast` 与 `-O3` 完全相同**——因为探针里没有浮点运算

## 4.3 `-O0`：变量住在栈上

<small style="color:gray">实测数据</small>
<small style="color:gray">asm</small>

```asm
sub    $0x10,%rsp
mov    %rcx,0x10(%rbp)          ← 参数存进栈
mov    %edx,0x18(%rbp)
movl   $0x0,-0x4(%rbp)          ← s = 0，存进栈
movl   $0x0,-0x8(%rbp)          ← i = 0，存进栈
jmp    ...+0x55
mov    -0x8(%rbp),%eax          ← 读 i（从内存）
cltq
lea    0x0(,%rax,4),%rdx        ← 算 &a[i]
mov    0x10(%rbp),%rax          ← 读 a（从内存）
add    %rdx,%rax
mov    (%rax),%edx              ← 读 a[i]
mov    -0x8(%rbp),%eax          ← 又读一次 i
```

**看这段代码的特征**：

| 现象 | 说明 |
|---|---|
| `-0x4(%rbp)`、`-0x8(%rbp)` | **变量都在栈帧里** |
| 每次用 `i` 都要重新读 | 编译器不假设内存没被改过 |
| `a` 每次都要重新读 | 同上 |
| 30 条指令 | 循环里的实际计算只占几条，其余都是搬运 |

**这不是编译器笨**，而是 `-O0` 的设计目标：
**保证每个变量在内存里的值与源码一致，调试器随时能改。**

## 4.4 `-O1`：搬进寄存器

<small style="color:gray">实测数据</small>
<small style="color:gray">asm</small>

```asm
test   %edx,%edx
jle    ...+0x34                  ← n <= 0 直接返回
mov    %rcx,%r8                  ← a 放进 r8
movslq %edx,%rdx
lea    (%rcx,%rdx,4),%rcx        ← 算出结束地址
mov    $0x0,%edx                 ← s 放进 edx
...
mov    (%r8),%eax                ← 读 a[i]
imul   %eax,%eax                 ← 平方
add    %eax,%edx                 ← 累加
add    $0x4,%r8                  ← 指针前移
cmp    %rcx,%r8                  ← 与结束地址比较
jne    ...+0x20                  ← 循环
```

**循环体只剩 6 条指令**：读一个元素、平方、累加、指针前移、比较、跳回，
**全部在寄存器之间完成。**

**关键变化**：

| 变化 | 效果 |
|---|---|
| `a`、`i`、`s` 全在寄存器 | 不再有内存读写 |
| 用**指针递增**代替下标计算 | 省掉每次的乘法与加法 |
| 循环边界预先算成地址 | 每次循环少一次比较运算 |

**这就是 3.68 倍加速的来源。**

## 4.5 `-O3`：向量化

<small style="color:gray">实测数据</small>
<small style="color:gray">asm</small>

```asm
pxor   %xmm2,%xmm2               ← 清零一个 128 位寄存器
shr    $0x2,%edx                 ← n / 4，因为一次处理 4 个
...
movdqu (%rax),%xmm0              ← 一次读入 4 个 int（16 字节）
movdqa %xmm0,%xmm1
pmuludq %xmm0,%xmm1              ← 4 个元素同时平方
psrlq  $0x20,%xmm0
pmuludq %xmm0,%xmm0
```

**`movdqu` 一次读 16 字节 = 4 个 `int`。**
`pmuludq` 对这四个数**同时**做乘法。

**这就是「单指令多数据」（SIMD）。**

| 对比 | `-O2` | `-O3` |
|---|---|---|
| 每次循环处理 | 1 个元素 | **4 个元素** |
| 循环次数 | n | n / 4 |
| 适合 | 通用 | **连续内存上的同类运算** |

**向量化的前提**：数据在内存里连续、运算彼此独立。
**链表、跳跃访问、有依赖的循环都无法向量化。**

## 4.6 `-Os`：指令最少

<small style="color:gray">实测数据</small>
<small style="color:gray">asm</small>

```asm
xor    %eax,%eax                 ← i = 0
xor    %r9d,%r9d                 ← s = 0
cmp    %eax,%edx
jle    ...+0x19
mov    (%rcx,%rax,4),%r8d        ← 读 a[i]
inc    %rax                      ← i++
imul   %r8d,%r8d                 ← 平方
add    %r8d,%r9d                 ← 累加
jmp    ...+0x5                   ← 无条件跳回
```

**只剩 14 条指令。** 比 `-O1` 的 18 条还少。

**它做了什么**：`-O1` 用指针递增与结束地址比较，
`-Os` 改成下标加 `inc`，**用略多的运算换取更少的指令字节数**。

**这解释了 `-Os` 的设计取向**：它优化的目标是**体积**，不是速度。
在这个例子里两者碰巧接近，但**不保证总是如此**。

## 4.7 一个反直觉的结果

**在本次实测中，`-Os` 的运行耗时反而最短**（7.1 毫秒，
甚至快过 `-O3` 的 7.8 毫秒）。

**原因是这个循环受内存带宽限制，不是计算受限**：
每次循环要读 4 字节，计算量却很小（一次乘法、一次加法），
**瓶颈在「读内存」上，不在「算」上**。
向量化因此收益有限，而 `-Os` 的紧凑循环
反而让指令缓存更友好。

**这条结论不能推广**。换成计算密集的循环，
`-O3` 的向量化会带来数倍提升。

> [!IMPORTANT]
> **优化等级不是越高越快，要看具体代码的瓶颈在哪里。**
> 判断的唯一可靠办法是把同一段代码在各等级下分别编译、分别计时。

# 第 5 节 各项优化详解

## 5.1 内联

**把被调函数的代码直接搬进调用处**，省掉调用与返回的开销。

**同一探针，`square` 是一个只被调用一次的小函数。**

<small style="color:gray">实测数据</small>

| 等级 | `square` 函数体是否存在 | 被 `call` 次数 |
|---|---|---|
| `-O0` | **有** | 1 |
| `-O1` 及以上 | **无** | **0** |

**`-O1` 起，这个函数就完全消失了，调用处变成了直接的乘法。**

**内联的代价**：代码重复，体积增大。
**所以 `-Os` 会限制内联的积极性。**

## 5.2 死代码消除

**下面这个函数的返回值从未被使用。**

<small style="color:gray">实测数据</small>
<small style="color:gray">c</small>

```c
/* dead_code.c    编译：gcc -std=c17 -O1 -S dead_code.c -o dead_code.s */
#include <stdio.h>

/* 返回值从未被使用，循环也不产生可观察行为：整个函数可以被删掉 */
static int dead_code(void) {
    int unused = 0;
    for (int i = 0; i < 100000; ++i) unused += i * 3;
    return 42;
}

int main(void) {
    dead_code();                   /* 丢弃返回值 */
    printf("done\n");
    return 0;
}
```

| 等级 | 函数体存在 |
|---|---|
| `-O0` | 有 |
| `-O1` 及以上 | **无（已消除）** |

**编译器发现**：这个函数的返回值从未被使用，
循环也对外界没有影响，**于是把整个函数删掉**。

**这是「正确地删除」**：C 与 C++ 都规定，不产生可观察行为的计算可以省略。
**但如果这个循环里有 `volatile` 读写或 I/O 调用，就不能删。**

## 5.3 常量折叠与传播

<small style="color:gray">c</small>

```c
/* const_fold.c    编译：gcc -std=c17 -O0 -S const_fold.c -o const_fold.s */
#define N 100                   /* C 里数组长度用宏；C++ 可以直接写 const int N = 100; */
int x = 3 * 4 + 5;              /* 直接算成 17 */
int a[N];                       /* 数组大小直接用 100 */

int main(void) {
    return x + a[0];
}
```

**`-O0` 下也会做常量折叠**——这是编译期的必做工作，不算「优化」。

## 5.4 循环优化

| 优化 | 做法 | 效果 |
|---|---|---|
| **不变量外提** | 循环里不变的表达式挪到外面 | 少算 n 次 |
| **强度削减** | 乘法换成加法 | `i*4` 变成指针递增 |
| **循环展开** | 一次迭代做多轮 | 减少跳转次数 |
| **向量化** | 一条指令处理多个数据 | 数倍加速 |

**第 4.4 小节那段 `-O1` 的汇编就是「强度削减」的实例**：
`a[i]` 的地址计算被换成了指针自增。

## 5.5 未定义行为让优化「有恃无恐」

**这是优化改变程序行为的最主要原因。**
编译器会**假设源码里没有未定义行为**，并据此推理。

<small style="color:gray">c</small>

```c
/* ub_sign.c    编译：gcc -std=c17 -O2 -S ub_sign.c -o ub_sign.s */
#include <limits.h>

/* 有符号整数溢出是未定义行为，编译器据此认为 x + 1 不会溢出 */
int f(int x) {
    return x + 1 > x;              /* 看起来永远为真 */
}

int g(void) {
    return f(INT_MAX);             /* 传入最大值，直觉上应当得到 0 */
}
```

**编译器可以把 `f` 直接变成 `return 1;`**：
既然有符号整数溢出是未定义行为，`x + 1` 就不会溢出，
`x + 1 > x` 于是恒成立。
但若调用方传入 `INT_MAX`，实际行为与直觉不符。

**常见的未定义行为**：

| 行为 | 后果 |
|---|---|
| 有符号整数溢出 | 结果不可预测 |
| 数组越界访问 | 优化可能删掉整个分支 |
| 解引用空指针 | 后续代码可能被删 |
| 违反严格别名规则 | 类型双关失效 |
| 未初始化变量 | 值不确定 |

> [!CAUTION]
> **带未定义行为的程序，在不同优化等级下可能给出不同结果。**
> `-O0` 下跑得通不代表代码正确——那只是编译器没有拿它做推理。

**相关案例**（用类型双关读写同一段内存）见《04-语法/14-奇技淫巧与优化.md》第 4 节，
那里有一个真实项目里的类型双关写法。

## 5.6 `volatile` 与优化

**这是嵌入式开发中最常见的一类错误。**

<small style="color:gray">c</small>

```c
/* volatile_flag.c    编译：gcc -std=c17 -O2 -S volatile_flag.c -o volatile_flag.s */
#include <stdio.h>

int flag = 0;                      /* 由硬件或中断写入 */

int main(void) {
    while (flag == 0) { }          /* 等待硬件或中断把它置 1 */
    printf("flag = %d\n", flag);
    return 0;
}
```

**`flag` 不加 `volatile` 时，`-O2` 生成的是这样的循环。**

<small style="color:gray">实测数据</small>
<small style="color:gray">asm</small>

```asm
.L3:
    jmp  .L3                 ← 原地死循环，再也不读内存
```

**编译器推理**：「循环体内没有修改 `flag`，
也没有调用可能修改它的函数，因此它的值不变。
既然第一次读到 0，就永远是 0。」

**推理在普通变量的前提下正确，但它不知道硬件会改这个变量。**

**把 `flag` 改成 `volatile int` 再编一次，循环就变成下面这样。**

<small style="color:gray">实测数据</small>
<small style="color:gray">asm</small>

```asm
.L6:
    movl  flag(%rip),%eax    ← 每轮都重新读
    testl %eax,%eax
    je    .L6
```

**完整对照见《01-编译器/03-嵌入式与交叉编译.md》第 4.5 小节。**

## 5.7 浮点优化

**`-Ofast` 里的 `-ffast-math` 会关闭 IEEE 754 的若干保证**：

| 被放弃的保证 | 后果 |
|---|---|
| 结合律成立 | `(a+b)+c` 可能被改成 `a+(b+c)`，结果有微小差异 |
| 不重排运算 | 同上 |
| 保留 NaN 与 Inf 语义 | 判断可能被优化掉 |
| 精确的舍入 | 结果可能与预期不符 |

**判断能否用 `-Ofast`**：

| 场景 | 能否用 |
|---|---|
| 图形、游戏、机器学习推理 | 通常可以 |
| 金融计算 | **不可以** |
| 科学计算（需要可复现） | **不可以** |
| 任何需要与标准结果逐位一致的场合 | **不可以** |

**本章节的实测里 `-Ofast` 与 `-O3` 完全相同**——
因为探针里只有整数运算，`-ffast-math` 无用武之地。

**这也说明：不能只凭「用了 `-Ofast`」就断定有风险，
要看代码里有没有浮点。**

# 第 6 节 优化与调试的矛盾

## 6.1 前端与后端

**调试需要的是「源码与机器码一一对应」，而优化做的正是打破这个对应。**

| 优化做的事 | 对调试的影响 |
|---|---|
| 变量放进寄存器 | 调试器找不到它的内存位置 |
| 变量被消除 | 显示「已优化掉」 |
| 内联 | 调用栈里少一层 |
| 循环展开 | 一行源码对应多段代码 |
| 指令重排 | 单步时顺序跳来跳去 |
| 死代码消除 | 断点永远命不中 |

## 6.2 `-Og`：折中方案

**GCC 提供 `-Og`**：开启不妨碍调试的优化。

| 方面 | `-O0` | `-Og` | `-O2` |
|---|---|---|---|
| 速度 | 基准 | 明显更快 | 最快 |
| 变量可见 | 完整 | 基本完整 | 部分丢失 |
| 单步 | 线性 | 基本线性 | 跳跃 |
| 内联 | 不内联 | 少量 | 大量 |

**适合**：开发期嫌 `-O0` 太慢，又不想失去调试能力。

## 6.3 一个常见误解

**「优化后的程序有 bug，那一定是编译器的错」——绝大多数情况下不是。**
优化只是**把源码里本来就存在的问题暴露出来**：

| 真实原因 | 表现 |
|---|---|
| 未定义行为 | `-O0` 碰巧对，`-O2` 就错 |
| 缺 `volatile` | 死循环 |
| 数据竞争 | 偶发错误 |
| 越界访问 | 覆盖掉别的变量 |

**排查顺序**：

1. 用 `-O0` 复现，确认问题是否与优化相关
2. 检查有没有未定义行为（用 `-fsanitize=undefined` 与 `-fsanitize=address`）
3. 检查共享变量有没有 `volatile` 或原子操作
4. 缩小到最小复现代码

> [!IMPORTANT]
> **如果 `-O0` 对、`-O2` 错，先怀疑自己的代码，而不是编译器。**

# 第 7 节 Debug 与 Release 怎么选

## 7.1 两套配置的典型设置

| | Debug | Release |
|---|---|---|
| GCC 优化 | `-O0` | `-O2` 或 `-O3` |
| GCC 调试信息 | `-g3` | 无 |
| MSVC 优化 | `/Od` | `/O2` |
| MSVC 调试信息 | `/Zi` | 无 |
| 断言 | 开启 | 关闭（`NDEBUG`） |
| 运行库 | 调试版 | 发布版 |

## 7.2 为什么必须两套都测

**「Debug 正常、Release 崩溃」是最典型的一类问题。**
原因通常是第 5.5 与 5.6 小节讲的那些：
未定义行为、缺 `volatile`、数据竞争。

**它们共同的特征是**：

<small style="color:gray">text</small>

```text
   -O0：编译器不做推理，代码逐字翻译，问题碰巧不出现
   -O2：编译器做推理，问题暴露
```

> [!IMPORTANT]
> **发布前必须在 Release 配置下完整测一遍**，不能只测 Debug。

## 7.3 三层选择

| 场景 | 建议 |
|---|---|
| 日常开发调试 | `-O0` + `-g` |
| 自己测性能 | `-O2` 或 `-O3`，无 `-g` |
| 发布给用户 | `-O2`，无调试信息，保留符号文件另行归档 |
| 想边调边跑得快 | `-Og` + `-g` |

**最后一项的搭配值得记住**：
`-Og` 加 `-g` 是「既要调试又能接受的速度」的最佳组合。

# 第 8 节 在 CMake 里设置

## 8.1 通过构建类型

**CMake 用 `CMAKE_BUILD_TYPE` 决定优化等级。**

<small style="color:gray">文档</small>

> "Specifies the build type on single-configuration generators
> (e.g. Makefile Generators or Ninja). Typical values include `Debug`,
> `Release`, `RelWithDebInfo` and `MinSizeRel`,
> but custom build types can also be defined."
>
> —— CMake 4.4.3 文档，变量 `CMAKE_BUILD_TYPE`

| `CMAKE_BUILD_TYPE` | GCC 默认标志 | MSVC 默认标志 |
|---|---|---|
| `Debug` | `-g` | `/Zi /Ob0 /Od /RTC1` |
| `Release` | `-O3 -DNDEBUG` | `/O2 /Ob2 /DNDEBUG` |
| `RelWithDebInfo` | `-O2 -g -DNDEBUG` | `/Zi /O2 /Ob1 /DNDEBUG` |
| `MinSizeRel` | `-Os -DNDEBUG` | `/O1 /DNDEBUG` |

**四个值的分工**：`Debug` 供调试；`Release` 供发布，最快；
`MinSizeRel` 优先体积；**`RelWithDebInfo` 是优化过、但保留调试信息的那一个**。

> [!TIP]
> **用户报告「Release 版崩溃」时，用 `RelWithDebInfo` 重新构建。**
> 它给出的正是「优化过的代码 + 调试信息」，
> 可以在接近真实优化的条件下调试，不必退回 `-O0`。

## 8.2 在命令行指定

<small style="color:gray">bash</small>

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
```

> [!WARNING]
> **`-DCMAKE_BUILD_TYPE` 只对单配置生成器有效**（Ninja、Makefiles）。
> Visual Studio 生成器是多配置的，改在构建时指定配置。

<small style="color:gray">bash</small>

```bash
cmake --build build --config RelWithDebInfo
```

**这个差别在《03-构建工具链/01-构建工具链.md》第 4.2 小节讲过。**

## 8.3 用预设固化

<small style="color:gray">json</small>

```json
{
  "name": "release-with-debug",
  "displayName": "Release + 调试信息",
  "generator": "Ninja",
  "binaryDir": "${sourceDir}/build/relwithdeb",
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "RelWithDebInfo"
  }
}
```

**在 `CMakePresets.json` 里固化的好处**：
换一台机器只要 `cmake --preset release-with-debug`，
不必问「你当初是怎么编的」。

## 8.4 自定义优化等级

> [!WARNING]
> **不推荐直接改 `CMAKE_C_FLAGS_RELEASE`**：
> 那会**覆盖掉 CMake 的默认值**，而不是追加。
> 要追加选项，用 `target_compile_options` 指定到具体目标上。

<small style="color:gray">cmake</small>

```cmake
target_compile_options(app PRIVATE
    $<$<CONFIG:Release>:-O3>
    $<$<CONFIG:Debug>:-Og>
)
```

**`$<CONFIG:...>` 是生成器表达式**，它在**构建阶段**按配置求值。
这解决了「同一份 `CMakeLists.txt` 在不同配置下要传不同参数」的问题。

**这是《03-构建工具链/01-构建工具链.md》第 3.8 小节
「配置阶段与构建阶段」的一个实际应用**：
配置阶段不知道最终用哪个配置，因此需要把判断推迟到构建阶段。

# 附录 B 复现本章节数据

## B.1 探针

**环境**：MinGW `gcc` 15.2.0，Windows 11 build 22631。

<small style="color:gray">c</small>

```c
/* probe.c    编译：gcc -std=c17 -O2 probe.c -o probe.exe */
#include <stdio.h>

#define N      8192        /* 数组长度：一次循环要读 8192 个 int */
#define REPEAT 4000        /* 外层重复次数：把总耗时抬到毫秒级，盖过进程启动开销 */

static int a[N];

/* 第 5.1 小节观察内联用的函数：内联之后函数体在反汇编里消失 */
static int square(int x) { return x * x; }

/* 热点函数：优化等级的差别主要体现在它生成的循环上 */
long sum_squares(const int *p, int n) {
    long s = 0;
    for (int i = 0; i < n; ++i) s += (long)p[i] * p[i];
    return s;
}

/* 第 5.2 小节观察死代码消除用的函数：返回值从未被使用 */
static int dead_code(void) {
    int unused = 0;
    for (int i = 0; i < 100000; ++i) unused += i * 3;
    return 42;
}

int main(void) {
    for (int i = 0; i < N; ++i) a[i] = i % 7;
    long total = 0;
    for (int r = 0; r < REPEAT; ++r) total += sum_squares(a, N);
    dead_code();
    printf("%ld %d\n", total, square(a[0]));
    return 0;
}
```

**C 与 C++ 写法相同**，把 `gcc -std=c17` 换成 `g++ -std=c++17` 即可。

## B.2 构建与编译耗时

<small style="color:gray">bash</small>

```bash
for lvl in O0 O1 O2 O3 Os Ofast; do
    gcc -std=c17 -$lvl probe.c -o o$lvl.exe
done

```

| `-O1` | 0.165 秒 |
| `-O2` | 0.194 秒 |
| `-O3` | 0.182 秒 |
| `-Os` | 0.184 秒 |
| `-Ofast` | 0.192 秒 |

## B.3 汇编对照

**关键：加 `noinline`**（源码见第 4.1 小节的 `sum_squares.c`），
否则 `-O1` 起函数会被内联掉，反汇编里看不到函数体。

<small style="color:gray">bash</small>

```bash

    gcc -std=c17 -$lvl -S sum_squares.c -o ss_$lvl.s
done
```

**直接看可执行文件也可以**：

