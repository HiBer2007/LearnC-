# 第 1 节 为什么需要 Linux 环境

## 1.1 Windows 上 GDB 的两个限制

### 限制一：中文路径

GDB 在 Windows 上通过 MI 协议接收文件名时，按 **ANSI 代码页**（简体中文系统为 936）解释字节，
而 VS Code 发送的是 UTF-8。两者不一致时，GDB 找不到可执行文件，表现为：

- 弹出「选择要终止的会话」对话框，但没有可选内容
- 底部没有任何输出，像是按 F5 没反应

**这个限制只影响可执行文件路径，不影响源码路径**——断点、单步、查看变量都正常。

详细分析见《01-编译器/02-环境配置.md》第 9.13 小节。

### 限制二：不含 GNU/Linux 目标

这一点更根本，也更少被提及。

用 `gdb --configuration` 可以查看 Windows 版 GDB 的编译参数：

`实测数据`
`Text`

```text
configure --host=x86_64-w64-mingw32 --target=x86_64-w64-mingw32
          --enable-targets=x86_64-w64-mingw32
```

**目标只有 Windows。** 这带来一个直接后果：**Windows 的 GDB 无法调试 Linux 程序**，
哪怕是通过网络连接 Linux 上的 gdbserver 也不行。连接 Linux 侧 gdbserver 时的报错：

`实测数据`
`Text`

```text
warning: A handler for the OS ABI "GNU/Linux" is not built into this configuration of GDB.
Remote register badly formatted: T0506:0000000000000000;07:90deffffff7f0000;...
```

GDB 能连上，能读取远端的符号文件，但读不懂 Linux 进程的寄存器格式，随即中断。

> [!IMPORTANT]
> 这不是配置问题，无法通过任何设置绕过。要跨系统调试，
> 只能让**调试器本身运行在 Linux 上**。

## 1.2 由此得出的根本原则

> [!IMPORTANT]
> **调试器必须运行在目标程序所在的那一侧。**

| 做法 | 调试器在哪 | 是否可行 |
|---|---|---|
| Windows GDB → 本地 Windows 程序 | Windows | 可行 |
| Windows GDB → Linux gdbserver | Windows | **不可行** |
| Linux GDB → 本地 Linux 程序 | Linux | 可行 |
| `pipeTransport`：VS Code 经管道调用 Linux 侧 GDB | Linux | 可行 |
| Remote - WSL / Remote - SSH：整个 VS Code 后端在远端 | Linux | 可行 |

## 1.3 三种 Linux 环境

| 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **WSL** | 与 Windows 文件系统互通、启动快、VS Code 原生支持 | 不是真正的独立主机，网络模型特殊 | 日常开发、联合调试 |
| **虚拟机**（Hyper-V） | 是真正独立的主机，有独立 IP，贴近生产环境 | 占资源、需要安装系统 | 远程调试演练 |
| **远程真机 / 云主机** | 完全真实 | 需要额外资源 | 团队协作 |

**建议**：WSL 用于日常开发与联合调试，虚拟机用于远程调试演练。

## 1.4 本章节覆盖的四个场景

| 场景 | 节 | 说明 |
|---|---|---|
| 在 WSL 中开发与调试 | 第 2 节 | 最基础的一步 |
| 联合调试：Windows 客户端 + Linux 服务端 | 第 3 节 | 一个窗口同时调试两边 |
| 远程调试：调试远端主机上的程序 | 第 4 节 | SSH 通道、pipeTransport、gdbserver、Remote-SSH |
| 虚拟机环境 | 第 5 节 | 真实的远程目标 |

## 1.5 真实项目里的跨平台代码

**跨平台不是抽象概念，它就写在真实项目的源码里——用条件编译把两个平台分开。**

以下引自 `modules/NeoCore/src/plugin_loader.cpp`（**原文**，节选）：

`C++`

```cpp
static void* loadNativeLibrary(const std::string& path)
{
    int len = MultiByteToWideChar(CP_UTF8, 0, path.c_str(), -1, nullptr, 0);
    if (len <= 0) return nullptr;
    std::wstring wpath(len, L'\0');
    MultiByteToWideChar(CP_UTF8, 0, path.c_str(), -1, &wpath[0], len);
    void* handle = (void*)LoadLibraryW(wpath.c_str());
    if (!handle) {
        CLogger::Error("LoadLibrary failed for '{}': {}", path,
            getLastWindowsError());
    }
    return handle;
}

static void* getNativeProc(void* handle, const char* name)
{
    void* proc = (void*)GetProcAddress((HMODULE)handle, name);
    if (!proc) {
        CLogger::Error("GetProcAddress '{}' failed: {}", name,
            getLastWindowsError());
    }
    return proc;
}

static void* freeNativeLibrary(void* handle)
{
    if (handle) {
        FreeLibrary((HMODULE)handle);
    }
}

#define LOAD_LIBRARY(path)    loadNativeLibrary(path)
#define GET_PROC(handle, name) getNativeProc(handle, name)
#define FREE_LIBRARY(handle)  freeNativeLibrary(handle)

#else
#include <dlfcn.h>
```

### 两套 API，各写一遍

`#ifdef _WIN32` 分支用 Windows 的 `LoadLibraryW` / `GetProcAddress` / `FreeLibrary`；
`#else` 分支 `#include <dlfcn.h>`，用 Linux 的 `dlopen` / `dlsym` / `dlclose`。
**同一个功能，两套 API，各写一遍。**

### 宏把差异封装起来

`C++`

```cpp
#define LOAD_LIBRARY(path)    loadNativeLibrary(path)
```

**这个宏在 Windows 与 Linux 分支里被定义了两次**，实现不同，
但**名字与用法完全相同**。

于是上层代码只需要写：

`C++`

```cpp
void* handle = LOAD_LIBRARY(dllPath.c_str());
```

**平台差异被完全隔离开**，上层代码一个字都不用改。

### Windows 特有的编码转换

`C++`

```cpp
int len = MultiByteToWideChar(CP_UTF8, 0, path.c_str(), -1, nullptr, 0);
std::wstring wpath(len, L'\0');
MultiByteToWideChar(CP_UTF8, 0, path.c_str(), -1, &wpath[0], len);
void* handle = (void*)LoadLibraryW(wpath.c_str());
```

**两个平台的路径类型不同**：

| 平台 | 路径类型 | 说明 |
|---|---|---|
| Linux | `char*`（字节串） | UTF-8 直接用 |
| **Windows** | `wchar_t*`（宽字符） | **必须显式转换** |

而 Windows 上还有 `LoadLibraryA`（接受 `char*`），
它按**系统 ANSI 代码页**解释，**中文路径下会失败**。

这与第 1.1 小节的 GDB 限制同源：都是编码约定不一致。

### 项目里的一处错误写法

同一个项目里，另一处加载 DLL 的代码写成了：

`C++`

```cpp
std::wstring widePath(dllPath.begin(), dllPath.end());   // 逐字节加宽
handle = LoadLibraryW(widePath.c_str());
```

**这是错的**。逐字节加宽只对 ASCII 有效，中文路径必然失败。
下面这个程序把两种写法的差别打印出来：

`C++`

```cpp
/* widen.cpp    编译：g++ -std=c++17 widen.cpp -o widen    （Windows 侧） */
#include <windows.h>

#include <cstdio>
#include <string>

int main() {
    /* 「插件」的 UTF-8 字节：E6 8F 92 E4 BB B6，共 6 个 */
    std::string utf8 = "\xe6\x8f\x92\xe4\xbb\xb6";

    /* 错误写法：逐字节加宽，只对 ASCII 有效 */
    std::wstring wrong(utf8.begin(), utf8.end());

    /* 正确写法：先按 UTF-8 解码，再转成宽字符 */
    int len = MultiByteToWideChar(CP_UTF8, 0, utf8.c_str(), -1, nullptr, 0);
    std::wstring right(len, L'\0');
    MultiByteToWideChar(CP_UTF8, 0, utf8.c_str(), -1, &right[0], len);

    std::printf("UTF-8 字节数   = %d\n", (int)utf8.size());
    std::printf("错误写法码元数 = %d\n", (int)wrong.size());
    std::printf("正确写法码元数 = %d（含结尾的 0）\n", (int)right.size());
    return 0;
}
```

这里只给出 C++ 版本：出问题的那处写法属于 `std::wstring`，C 没有对应的库类型。

`实测数据`

| 量 | 值 | 说明 |
|---|---|---|
| UTF-8 字节数 | 6 | 「插件」占 6 个字节 |
| 逐字节加宽的码元数 | 6 | 6 个乱码码元，不能当路径使用 |
| `MultiByteToWideChar` 的码元数 | 3 | 2 个汉字与结尾的 `L'\0'` |

详细分析见《01-编译器/02-环境配置.md》第 9.6 小节与《04-语法/10-字符串.md》第 5 节。

### 为什么必须有 Linux 环境

| 观察 | 含义 |
|---|---|
| 同一份代码要写两套实现 | 跨平台是真实的开发成本，不是抽象概念 |
| 编码差异造成真实 bug | 平台差异会变成难以排查的故障 |
| **只有在两个平台上都跑过，才能确认代码正确** | 这就是第 3 节「联合调试」的价值 |

代码里有 `#ifdef _WIN32`，只在 Windows 上测试就不够——`#else` 分支从未被执行过。
**Linux 环境（WSL 或虚拟机）正是为了跑那另一半。**

# 第 2 节 搭建 WSL 环境

## 2.1 WSL 是什么

WSL（Windows Subsystem for Linux）让 Windows 直接运行 Linux 内核。
它不是虚拟机软件，而是 Windows 的一个功能组件。

**优点**：

- 与 Windows 文件系统双向互通：Windows 的 `K:\` 在 WSL 中是 `/mnt/k/`
- 启动快（秒级），资源占用低于虚拟机
- VS Code 有原生的 WSL 支持

WSL 里的**文件路径是 Linux 风格**，因此**不存在中文路径导致的 GDB 问题**——
Linux 下 GDB 原生使用 UTF-8。这是用 WSL 做 C/C++ 调试的一个实际好处。

## 2.2 检查与安装

### 检查现状

`PowerShell`

```powershell
wsl --version          # 查看 WSL 版本与内核版本
wsl --status           # 查看默认版本
wsl -l -v              # 列出已安装的发行版及其状态
```

`wsl -l -v` 的输出形如：

`Text`

```text
  NAME            STATE           VERSION
* Ubuntu          Running         2
```

行首的 `*` 表示默认发行版。**若没有任何发行版带 `*`，直接执行 `wsl` 会报错**：

`Text`

```text
Wsl/Service/CreateInstance/GetDefaultDistro/WSL_E_DEFAULT_DISTRO_NOT_FOUND
```

设置默认发行版：

`PowerShell`

```powershell
wsl --set-default <发行版名>
```

### 安装 WSL 本体

以**管理员身份**打开 PowerShell：

`PowerShell`

```powershell
wsl --install
```

该命令会启用所需功能并安装 WSL。**完成后需要重启计算机。**

> [!TIP]
> 网络访问微软商店较慢时，`wsl --install` 与 `wsl --update` 都可能长时间无响应
> （见附录 A.2）。此时改用第 2.3 小节的离线方式安装发行版，
> 并用手工下载的 MSI 升级 WSL 本体。

### 升级 WSL 本体

WSL 的版本会随 Windows 更新自动升级，但往往滞后。手工升级的方法：

1. 打开 <https://github.com/microsoft/WSL/releases>
2. 找到最新的**正式版**（标记为 Pre-release 的不要用）
3. 下载 `wsl.<版本号>.0.x64.msi`，是 **x64** 而不是 arm64
4. 以管理员身份运行该 MSI

也可以在管理员 PowerShell 中尝试：

`PowerShell`

```powershell
wsl --update
```

> [!TIP]
> `wsl --update` 走的是微软商店通道，网络不畅时改用上面的 MSI 方式。
> 升级 WSL 本体不会影响已安装的发行版。

## 2.3 安装发行版

### 方式一：在线安装

`PowerShell`

```powershell
wsl --install -d Ubuntu
```

查看可安装的发行版列表：

`PowerShell`

```powershell
wsl --list --online
```

### 方式二：从本地镜像导入（推荐给网络受限的环境）

Ubuntu 官方提供 WSL 专用的根文件系统镜像，体积远小于完整 ISO：

`Text`

```text
https://releases.ubuntu.com/24.04.5/ubuntu-24.04.5-wsl-amd64.wsl
```

该文件约 370 MB。下载后导入：

`PowerShell`

```powershell
# 语法：wsl --import <发行版名> <安装位置> <镜像文件>
wsl --import Ubuntu D:\WSL\Ubuntu "<下载目录>\ubuntu-24.04.5-wsl-amd64.wsl"
```

**参数说明**：

| 参数 | 说明 |
|---|---|
| `<发行版名>` | 自定义的名字，之后用 `wsl -d <名字>` 使用 |
| `<安装位置>` | 存放虚拟磁盘的目录，建议选空间充足的盘 |
| `<镜像文件>` | 下载的 `.wsl` 文件 |

**该文件实际是 tar.gz 打包的根文件系统**，因此 `wsl --import` 可以直接使用，
导入后发行版的默认用户是 `root`。导入耗时见附录 A.2。

> [!WARNING]
> `wsl --install --from-file` 是较新版本 WSL 才支持的命令。
> 本教材编写时使用的 2.1.5.0 **不支持**，只能用 `wsl --import`。

### 导入后设置默认用户

`wsl --import` 得到的发行版默认以 `root` 登录。若要改为普通用户：

`PowerShell`

```powershell
# 先在发行版内创建用户
wsl -d Ubuntu -- useradd -m -s /bin/bash -G sudo student
wsl -d Ubuntu -- passwd student
```

然后在发行版内写入 `/etc/wsl.conf`：

`INI`

```ini
[user]
default=student
```

最后重启该发行版使其生效：

`PowerShell`

```powershell
wsl --terminate Ubuntu
```

### 若下载缓慢：更换软件源

官方源 `archive.ubuntu.com` 在部分网络下很慢，换用国内镜像可以明显加快下载：

`实测数据`

| 镜像 | 下载速度 |
|---|---|
| `mirrors.huaweicloud.com` | 约 2.9 MB/s |
| `mirrors.ustc.edu.cn` | 约 2.4 MB/s |

```ini
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg

Types: deb

Suites: noble-security
Components: main restricted universe multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
```

其中 `noble` 是 Ubuntu 24.04 的代号，其他版本需换成对应代号。

然后执行 `sudo apt-get update`。

> [!WARNING]
> 镜像可能同步不及时，出现 `Hash Sum mismatch` 错误，此时换一个镜像即可。
> 本工作区在华为云镜像上遇到过（见附录 A.2）。

### 启用 SSH 服务

WSL 默认不启用 systemd，因此 `sshd` 不会自动启动。手工启动：

`Bash`

```bash
sudo service ssh start
```

若要让 systemd 生效，在 `/etc/wsl.conf` 中写入：

`INI`

```ini
[boot]
systemd=true
```

然后 `wsl --terminate <发行版名>` 重启发行版。

启用 systemd 后可以用 `systemctl` 管理服务，代价是启动时间略有增加。

## 2.5 验证

`Bash`

```bash
gcc --version
gdb --version
cmake --version
```

编译并调试一个测试程序：

`Bash`

```bash
cat > /tmp/t.c <<'EOF'
#include <stdio.h>
int add(int a, int b) { return a + b; }
int main(void) { printf("%d\n", add(2, 3)); return 0; }
```

> 在 Windows 上通过命令行调用 GDB 时，**`-ex` 对含空格的命令不可靠**：
> 含空格的参数会被按空格拆开，多余部分被当成待调试的文件名。
> **解决办法是把命令写进脚本文件，用 `-x 文件名` 执行**（详见第 6.9 小节）。
> 这不影响 VS Code 中的调试，那里使用 MI 协议而非命令行。

# 第 3 节 联合调试

## 3.1 什么是联合调试

**联合调试**指**同时调试两个（或多个）相互通信的程序**，观察数据如何在它们之间流动。

典型场景：

- Windows 上的客户端 ↔ Linux 上的服务端
- 一个进程的多个协作模块
- 两个通过管道或共享内存通信的程序

与单程序调试的区别在于：断点分布在**不同的调试会话**中，需要让它们协调起来。

## 3.2 联合调试的两种形态

| 形态 | 做法 | 适用 |
|---|---|---|
| **同一窗口** | 用 `pipeTransport` 让远端程序也接入当前 VS Code 窗口 | 程序之间有紧密的调用/数据关系 |
| **两个窗口** | 用 Remote - WSL / Remote - SSH 各开一个窗口 | 两端相对独立，或需要在远端编辑代码 |

## 3.3 pipeTransport：让远端程序接入本地窗口

### 原理

`pipeTransport` 是 cpptools 提供的一种机制。

`文档`

> "Pipe transport allows communication through a pipe program to a remote shell.
> For example, `ssh` on Linux."
>
> —— VS Code Docs，Pipe transport
> （<https://code.visualstudio.com/docs/cpp/pipe-transport>）

它的工作方式是：

1. VS Code 不直接启动 GDB，而是启动 `pipeProgram` 指定的程序（如 `wsl.exe`）
2. 通过 `pipeArgs` 让该程序在远端启动 `debuggerPath` 指定的 GDB
3. VS Code 与远端 GDB 之间通过**标准输入输出这条管道**交换 MI 协议文本

因此：**GDB 运行在远端**，符合第 1.2 小节的原则。

`Text`

```text
┌──────────────────┐   MI 文本   ┌──────────┐   启动   ┌──────────────┐
│  VS Code (Win)   │ ←────────→ │ wsl.exe  │ ───────→ │ Linux 侧 GDB │
└──────────────────┘   管道      └──────────┘          └──────────────┘
                                                              │
                                                              ↓ 调试
                                                      ┌──────────────┐
                                                      │ Linux 程序    │
                                                      └──────────────┘
```

### 配置

`JSONC`

```jsonc
{
  "name": "Linux 服务端 (WSL)",
  "type": "cppdbg",
  "request": "launch",

  // 注意：路径必须是【Linux 侧】路径
  "program": "/mnt/k/<工作区>/server",
  "cwd": "/mnt/k/<工作区>",

  "MIMode": "gdb",

  // 把 GDB 报告的 Linux 路径映射回 Windows 路径，
  // 否则 VS Code 定位不到源文件，断点会显示为「未验证」
  "sourceFileMap": {
    "/mnt/k/": "K:\\"
  },

  "pipeTransport": {
    "pipeCwd": "${workspaceFolder}",
    "pipeProgram": "wsl.exe",
    "pipeArgs": ["-d", "<发行版名>", "--"],
    "debuggerPath": "/usr/bin/gdb",
    "quoteArgs": false
  },

  "setupCommands": [
    { "text": "-enable-pretty-printing", "ignoreFailures": true },
    { "text": "set pagination off", "ignoreFailures": true }
  ]
}
```

### 字段说明

| 字段 | 说明 |
|---|---|
| `program` | **Linux 侧**的可执行文件路径。Windows 的 `K:\` 在 WSL 中对应 `/mnt/k/` |
| `cwd` | 程序的工作目录，同样用 Linux 路径 |
| `sourceFileMap` | 路径映射表。左边是 GDB 报告的路径，右边是 Windows 上的路径 |
| `pipeProgram` | 用于建立管道的程序，WSL 场景固定为 `wsl.exe` |
| `pipeArgs` | 传给 `pipeProgram` 的参数。`-d <发行版名>` 指定发行版，`--` 之后是远端要执行的命令 |
| `debuggerPath` | **远端** GDB 的路径，WSL 中通常是 `/usr/bin/gdb` |
| `quoteArgs` | 是否给参数加引号。WSL 场景建议设为 `false`，避免参数被多加一层引号 |

### 关于 sourceFileMap

GDB 在 Linux 侧报告的文件名形如 `/mnt/k/项目/server.c`，
而 VS Code 认为源文件在 `K:\项目\server.c`。不做映射时：

- 断点可以设置成功，但显示为空心圆（未验证）
- 程序停下来时 VS Code 找不到对应源文件

映射写法是把**公共前缀**对应起来：

`JSONC`

```jsonc
"sourceFileMap": { "/mnt/k/": "K:\\" }
```

> [!WARNING]
> 映射的左右两侧都是目录前缀，必须以分隔符结尾，否则可能匹配到错误的路径。

## 3.4 复合启动：一次拉起多个会话

VS Code 的 `compounds` 可以把多个调试配置组合起来，一次全部启动，
见 VS Code 文档 [Configure debugging in Visual Studio Code](https://code.visualstudio.com/docs/debugtest/debugging-configuration)：

`JSONC`

```jsonc
"compounds": [
  {
    "name": "联合调试: 客户端 + 服务端",
    "configurations": [
      "Linux 服务端 (WSL)",
      "Windows 客户端"
    ],
    "stopAll": true
  }
]
```

| 字段 | 说明 |
|---|---|
| `configurations` | 要一起启动的配置名列表，名字必须与 `configurations` 中的 `name` 完全一致 |
| `stopAll` | 停止其中一个时是否一并停止其他会话 |

**使用方式**：在「运行和调试」面板顶部的下拉框中选择该复合项，然后按 F5。

**时序问题**：`compounds` 会**并行**启动各成员，因此可能出现「客户端已经发起连接，服务端还没开始监听」的情况。
本示例的客户端会因此报连接失败。处理办法：

- 在客户端 `main` 的第一个断点处停一下，等服务端就绪后再继续
- 或让客户端自带重试逻辑（生产环境通常都会这么做）

客户端与服务端的启动次序不确定，这是联合调试中常见的现象。

# 第 4 节 SSH 通道与远程调试

## 4.0 为什么 SSH 值得单独用一节

**SSH 不只是一个「远程登录」工具，它是一条通道。**

一旦这条通道建立，下列四件事可以**共用同一条连接、同一套认证、同一份配置**：

| 用途 | 做法 | 对应工具 |
|---|---|---|
| **编辑** | VS Code 后端跑在远端，本地只做界面 | Remote - SSH |
| **传输** | 上传下载文件 | `scp`、`sftp`、`rsync` |
| **执行** | 在远端编译、运行、查看日志 | `ssh <主机> <命令>` |
| **调试** | 用远端 GDB 调试远端程序 | `pipeTransport` + `ssh` |

**这带来的实际好处**：

- 不必在远端单独开一个常驻的调试服务器（不同于 gdbserver 方案）
- 不必为每件事单独配置认证——一次配好密钥，四件事都能用
- 路径、权限、环境在四件事之间完全一致，不会出现「能传文件但不能调试」这类割裂

> [!IMPORTANT]
> 上述四项已在本工作区逐一验证通过（完整记录见第 4.4 小节与附录 A.4）。

## 4.1 建立 SSH 通道

### 服务端（远端 Linux）

安装并启动：

`Bash`

```bash
sudo apt-get install -y openssh-server
sudo service ssh start
```

WSL 默认不启用 systemd，因此 `sshd` 不会开机自启，需要手工启动，
或按第 2.4 小节启用 systemd。

确认监听：

`Bash`

```bash
ss -tlnp | grep sshd
```

### 客户端（Windows）

Windows 10/11 自带 OpenSSH 客户端，无需安装：

`PowerShell`

```powershell
ssh -V
```

若提示找不到命令，在「设置 → 应用 → 可选功能」中添加「OpenSSH 客户端」。

### 生成密钥并安装到远端

`PowerShell`

```powershell
# 生成专用密钥（-N "" 表示不设密码，便于自动化）
ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\myserver -N ""

# 把公钥内容追加到远端的 authorized_keys
type $env:USERPROFILE\.ssh\myserver.pub | ssh user@host "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

> [!TIP]
> Windows 上没有 `ssh-copy-id`（那是 Linux 的工具），
> 因此用上面的管道写法手工安装公钥。

### 用配置文件管理多个主机

编辑 `%USERPROFILE%\.ssh\config`：

`INI`

```ini
Host myserver
    HostName 192.168.1.100
    User student
    Port 22
    IdentityFile ~/.ssh/myserver
    ServerAliveInterval 30
```

配好之后，所有的 `ssh`、`scp`、`sftp` 命令都可以直接用别名：

`PowerShell`

```powershell
ssh myserver
scp file.txt myserver:~/
```

| 字段 | 说明 |
|---|---|
| `Host` | 别名，自己起的名字 |
| `HostName` | 实际地址或域名 |
| `User` | 登录用户名 |
| `Port` | SSH 端口，默认 22 |
| `IdentityFile` | 使用的私钥路径 |
| `ServerAliveInterval` | 每 30 秒发一次心跳，防止连接被闲置断开 |

> [!IMPORTANT]
> `pipeTransport` 中可以直接使用这个别名，不必再写地址与密钥参数。
> 这让调试配置与其它 SSH 用途保持一致。

## 4.2 四种用途的配置

### 用途一：编辑（Remote - SSH）

见第 4.8 小节。

### 用途二：传输文件

`PowerShell`

```powershell
# 上传
scp .\main.cpp myserver:~/project/

# 下载
scp myserver:~/project/build/app.exe .\build\

# 整个目录（-r）
scp -r .\src myserver:~/project/

# 交互式传输（适合浏览与挑选）
sftp myserver
```

用别名之后不必再写 `-i`、`-P`、`-o` 等参数。

> [!TIP]
> `rsync` 更适合大量文件或增量同步，但 Windows 默认不带，
> 需要在 WSL 中执行或另行安装。日常小规模传输用 `scp` 即可。

### 用途三：执行命令

`PowerShell`

```powershell
# 单条命令
ssh myserver "uname -a"

# 带管道的复合命令
ssh myserver "cd ~/project && make -j4 && ./app"

# 把本地脚本送到远端执行
ssh myserver "bash -s" < .\build.sh
```

> [!WARNING]
> `ssh host "命令"` 中的命令由**远端的 shell** 解释，
> 因此引号的处理容易出错。复杂命令建议先写成脚本文件再执行。

### 用途四：调试（pipeTransport + ssh）

配置方式与 WSL 场景几乎一致，只把 `wsl.exe` 换成 `ssh`：

`JSONC`

```jsonc
{
  "name": "远端程序 (SSH 管道)",
  "type": "cppdbg",
  "request": "launch",

  // 远端路径
  "program": "/home/student/project/build/app",
  "cwd": "/home/student/project",

  "MIMode": "gdb",

  // 若远端路径与本地不同，需要映射
  "sourceFileMap": {
    "/home/student/project": "${workspaceFolder}"
  },

  "pipeTransport": {
    "pipeCwd": "${workspaceFolder}",
    "pipeProgram": "ssh",
    // 直接使用 ~/.ssh/config 里配好的别名；
    // 若未配置别名，则写成 ["-i", "<私钥路径>", "-p", "<端口>", "user@host"]
    "pipeArgs": ["myserver"],
    "debuggerPath": "/usr/bin/gdb",
    "quoteArgs": false
  },

  "preLaunchTask": "构建: 远端 (ssh + make)"
}
```

### 对应的构建任务

用同一条 SSH 通道在远端编译：

`JSONC`

```jsonc
{
  "label": "构建: 远端 (ssh + make)",
  "type": "process",
  "command": "ssh",
  "args": [
    "myserver",
    "cd ~/project && cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug && cmake --build build -j"
  ],
  "problemMatcher": "$gcc",
  "presentation": { "reveal": "always", "panel": "shared", "clear": true }
}
```

这样就形成了完整闭环，**全程只用一条 SSH 通道**：

`Text`

```text
编辑（Remote-SSH 或本地编辑后 scp）
   ↓
构建（ssh 执行 cmake/make）
   ↓
调试（pipeTransport 经 ssh 驱动远端 gdb）
```

### 字段对照：WSL 与 SSH

两者只有 `pipeProgram` 与 `pipeArgs` 不同，其余完全一致：

| 字段 | WSL 场景 | SSH 场景 |
|---|---|---|
| `pipeProgram` | `wsl.exe` | `ssh` |
| `pipeArgs` | `["-d", "Ubuntu", "--"]` | `["myserver"]` |
| `debuggerPath` | `/usr/bin/gdb` | `/usr/bin/gdb` |
| `program` | `/mnt/k/...` | `/home/student/...` |
| `sourceFileMap` | `{"/mnt/k/": "K:\\"}` | `{"/home/student/project": "${workspaceFolder}"}` |

**理解这一点之后，WSL 与远程主机在配置上就没有本质区别了。**

## 4.3 SSH 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `Connection refused` | 服务未启动或地址/端口不对 | 远端 `ss -tlnp \| grep sshd` 确认 |
| `Permission denied (publickey)` | 公钥未装好或权限不对 | 检查 `~/.ssh/authorized_keys` 权限应为 600 |
| `Host key verification failed` | 主机指纹变了 | 删除 `known_hosts` 中对应行 |
| 连接一段时间后断开 | 空闲超时 | `ServerAliveInterval 30` |
| 每次都提示确认指纹 | 未记录 | 首次连接输入 `yes`，或用 `StrictHostKeyChecking=accept-new` |
| `~` 展开成了本地路径 | 引号问题 | `scp` 的远端路径加引号：`"myserver:~/dir"` |

### WSL 场景的地址问题

WSL 的 `localhost` 端口转发并不可靠：

`实测数据`

| 服务 | 绑定 | Windows 经 `127.0.0.1` | Windows 经 WSL 实际地址 |
|---|---|---|---|
| 测试用 Python 服务 | `0.0.0.0:39999` | 可连 | 拒绝 |
| `gdbserver` | `0.0.0.0:2345` | 拒绝 | 可连 |
| `sshd` | `0.0.0.0:2222` | 拒绝 | 可连 |

**连接 WSL 中的服务时，若 `127.0.0.1` 被拒，改用 WSL 的实际地址。**

取得地址：

`PowerShell`

```powershell
wsl -d <发行版名> -- ip -4 addr show eth0
```

> [!WARNING]
> WSL 的地址在重启后会变。**不要把 IP 写死在配置里**——
> 写进 `~/.ssh/config` 的 `HostName` 也一样会失效。
> 若连接 WSL 频繁，可以考虑在 Windows 侧写一个每次自动更新配置的脚本。

> [!TIP]
> 使用 `pipeTransport` 时**不涉及 IP**，因为它走的是标准输入输出管道，
> 由 `wsl.exe` 或 `ssh` 自行完成连接。这是 `pipeTransport` 相比 gdbserver 的一个实际便利。

## 4.5 远程调试的几种方式对比

| | 联合调试 | 远程调试 |
|---|---|---|
| 关注点 | 多个程序之间的数据流动 | 程序在远端运行，本地只管调试 |
| 会话数 | 通常两个以上 | 通常一个 |
| 典型场景 | 客户端/服务端联调 | 调试服务器上的程序、调试嵌入式设备 |

两者的底层机制是相通的：都把调试器放在目标程序那一侧。

| 方式 | 原理 | 优点 | 限制 |
|---|---|---|---|
| **Remote - SSH** | VS Code 后端整个跑在远端 | 最完整，编辑/终端/调试一体 | 需要 SSH 环境 |
| **pipeTransport + ssh** | 本地 VS Code，远端只跑 GDB | 界面在本地，响应更跟手 | 远端路径需映射 |
| **Remote - WSL** | VS Code 后端跑在 WSL 里 | 配置最简单 | 只能连 WSL |
| **gdbserver** | 远端只跑一个小程序 | 资源占用最小，适合嵌入式 | **Windows 的 GDB 用不了**，见下 |

**选择建议**：

| 情况 | 推荐 |
|---|---|
| 远端代码量大、需要频繁编辑 | Remote - SSH |
| 代码在本地，只是要在远端跑 | `pipeTransport` + `ssh` |
| 调试 WSL | `pipeTransport` + `wsl.exe` 或 Remote - WSL |
| 目标资源极度受限（嵌入式） | gdbserver（但需 Linux 侧调试器） |

## 4.6 关于 gdbserver 的重要限制

gdbserver 是 GDB 的远程调试服务端，在被调试的机器上运行：

`Bash`

```bash
# 在远端启动，监听 2345 端口
gdbserver :2345 ./程序
```

本地 GDB 连接它：

`Text`

```text
(gdb) target remote <远端地址>:2345
```

**但在 Windows 上这条路线走不通**：原因见第 1.1 小节，
Windows 版 GDB 不含 GNU/Linux 目标支持。连接后的表现与第 1.1 小节的报错相同——
能连上，能读取远端的符号，但读不懂寄存器格式，随即中断。

**可行的替代方案**：

| 方案 | 做法 |
|---|---|
| 用 `pipeTransport` | 让 GDB 在远端运行，通过管道通信（**推荐**） |
| 用 Remote - SSH | 让 VS Code 后端与 GDB 都跑在远端 |
| 在 WSL 中调试 | 同上，管道程序换成 `wsl.exe` |
| 使用交叉调试器 | 安装支持多目标的 GDB，如 `gdb-multiarch` |

`待确认`

支持多目标的 GDB（如 `gdb-multiarch`）在 Windows 上能否直接用于调试 Linux 目标，本教材尚未验证。

> [!IMPORTANT]
> 远端与本地**都是 Linux** 时，gdbserver 方式是可行的。本教材在 WSL 中验证过：
> Linux 侧 GDB 连接 Linux 侧 gdbserver，断点、调用栈、变量全部正常（见附录 A.1）。

## 4.8 Remote - SSH

### 安装

`PowerShell`

```powershell
code --install-extension ms-vscode-remote.remote-ssh
code --install-extension ms-vscode-remote.remote-ssh-edit
```

### 连接

`F1` → `Remote-SSH: Connect to Host` → 选择 `~/.ssh/config` 中配好的别名。

连接成功后，在远端安装 C/C++ 扩展，即可像本地一样调试。

### 连接后的调试配置

通过 Remote - SSH 连接后，`launch.json` 中的路径与调试器路径都要用**远端路径**。

`JSONC`

```jsonc
{
  "name": "远端程序 (SSH)",
  "type": "cppdbg",
  "request": "launch",

  // 以下都是【远端】路径
  "program": "/home/student/project/build/app",
  "cwd": "/home/student/project",

  "MIMode": "gdb",
  "miDebuggerPath": "/usr/bin/gdb",   // 远端 GDB，不是 Windows 的

  "setupCommands": [
    { "text": "-enable-pretty-printing", "ignoreFailures": true },
    { "text": "set pagination off", "ignoreFailures": true }
  ]
}
```

由于整个 VS Code 后端都运行在远端，**不存在路径映射问题**，也**不需要 `sourceFileMap`**。

### 附加到 gdbserver

若要调试一个已经在运行的程序（例如由脚本启动的服务），可以用 gdbserver + 附加：

`Bash`

```bash
# 在远端启动程序，等待调试器接入
gdbserver :2345 ./app
```

然后在**同样运行在远端**的 VS Code 中使用：

`JSONC`

```jsonc
{
  "name": "附加到远端 gdbserver",
  "type": "cppdbg",
  "request": "launch",
  "program": "/home/student/project/app",
  "MIMode": "gdb",
  "miDebuggerPath": "/usr/bin/gdb",

  // gdbserver 的地址。与 gdbserver 同机时用 127.0.0.1
  "miDebuggerServerAddress": "127.0.0.1:2345",

  "setupCommands": [
    { "text": "-enable-pretty-printing", "ignoreFailures": true },
    { "text": "set pagination off", "ignoreFailures": true }
  ]
}
```

> [!IMPORTANT]
> `miDebuggerServerAddress` 这一配置**只在调试器与 gdbserver 处于同类系统时可用**。
> 用 Windows 的 GDB 连接 Linux 的 gdbserver 会失败（见第 4.6 小节）。
> 上述配置的前提是「VS Code 通过 Remote - SSH 运行在远端」，此时 GDB 也是 Linux 版，因此可用。

# 第 5 节 虚拟机环境

## 5.1 为什么还需要虚拟机

WSL 已经能满足大部分需求，但虚拟机有两个不可替代的用途：

1. **真实的远程调试目标**。虚拟机拥有独立 IP，从 Windows 访问它的方式与访问一台真实服务器完全相同，
   这正是 Remote-SSH 与 gdbserver 的典型使用场景。
2. **完整的系统环境**。可以自由试验 systemd、网络配置、防火墙等 WSL 中受限的部分。

## 5.2 前置条件

| 项目 | 要求 |
|---|---|
| Windows 版本 | 专业版、企业版或教育版（家庭版需另外启用 Hyper-V） |
| CPU | 支持并已在 BIOS 中启用虚拟化 |
| 权限 | **创建虚拟机需要管理员权限** |
| 镜像 | Ubuntu Server 或 Desktop 的 ISO 文件 |

检查 Hyper-V 是否可用：

`PowerShell`

```powershell
Get-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All |
    Select-Object FeatureName, State
```

若 `State` 不是 `Enabled`，以管理员身份执行（**需要重启**）：

`PowerShell`

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All -All
```

## 5.3 创建虚拟机

本工作区提供了脚本 `工具\创建Ubuntu虚拟机.ps1`。

**以管理员身份**运行：

`PowerShell`

```powershell
pwsh -File "工具\创建Ubuntu虚拟机.ps1"
```

脚本会依次完成：权限检查 → Hyper-V 检查 → 镜像检查 → 创建虚拟机 → 配置内存与处理器
→ 挂载镜像 → 设置启动顺序 → 启动虚拟机。

### 可调参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `-VMName` | `Ubuntu-Debug` | 虚拟机名称 |
| `-MemoryGB` | `8` | 启动内存，同时启用动态内存 |
| `-CPUCount` | `4` | 虚拟处理器数量 |
| `-DiskGB` | `60` | 虚拟磁盘大小 |
| `-IsoPath` | `K:\系统镜像\ubuntu-24.04.5-live-server-amd64.iso` | 安装镜像路径 |

例如创建一台更小的虚拟机：

`PowerShell`

```powershell
pwsh -File "工具\创建Ubuntu虚拟机.ps1" -VMName Ubuntu-Test -MemoryGB 4 -CPUCount 2
```

脚本可以重复运行：若同名虚拟机已存在，它会跳过创建而不是报错。

### 连接虚拟机控制台

创建后虚拟机自动启动，但需要打开控制台才能看到安装界面：

- 打开「Hyper-V 管理器」，双击虚拟机，点击「连接」
- 或直接运行 `vmconnect.exe localhost Ubuntu-Debug`

## 5.4 安装系统时的选项

| 步骤 | 选择 |
|---|---|
| 安装类型 | **Ubuntu Server**（不要选 minimized 版本） |
| 网络 | 若自动获取到地址则直接继续 |
| 存储 | 使用整块磁盘，**不要**启用 LVM 加密 |
| SSH | **务必勾选 `Install OpenSSH server`** |
| 用户 | 创建一个普通用户，例如 `student` |

勾选 OpenSSH server 是关键一步：Remote-SSH 与远程调试都依赖它。
装完再补装虽然可行，但不如安装时一并勾选来得简便。

## 5.5 安装后的配置

### 取得虚拟机的地址

`PowerShell`

```powershell
Get-VMNetworkAdapter -VMName Ubuntu-Debug |
    Select-Object -ExpandProperty IPAddresses
```

也可以在虚拟机控制台中执行 `ip -4 addr show` 查看。

> [!WARNING]
> 使用「默认交换机」时，虚拟机地址由 DHCP 分配，**重启后可能变化**。
> 若需要固定地址，在虚拟机内配置静态 IP，或在 Hyper-V 中改用内部交换机并自行配置 NAT。

### 从 Windows 连接

`PowerShell`

```powershell
ssh student@<虚拟机地址>
```

首次连接会提示确认主机指纹，输入 `yes` 后输入密码。

### 安装工具链

与 WSL 中相同（见第 2.4 小节）：

`Bash`

```bash
sudo apt-get update
sudo apt-get install -y build-essential gcc g++ gdb gdbserver make cmake ninja-build git
```

### 用 VS Code 连接

`F1` → `Remote-SSH: Connect to Host`，输入 `student@<虚拟机地址>`。

连接后在远端安装 C/C++ 扩展，即可开始调试。

# 第 6 节 排错

## 6.1 `wsl` 命令报 `WSL_E_DEFAULT_DISTRO_NOT_FOUND`

**原因**：没有设置默认发行版。

**解决**：

`PowerShell`

```powershell
wsl -l -v                          # 查看有哪些发行版
wsl --set-default <发行版名>        # 设置默认
```

## 6.2 某个发行版一启动就报错

**现象**：

`实测数据`
`Text`

```text
无法将磁盘"C:\...\ext4.vhdx"附加到 WSL2：系统找不到指定的文件。
Error code: Wsl/Service/CreateInstance/MountVhd/HCS/ERROR_FILE_NOT_FOUND
```

**原因**：该发行版的虚拟磁盘文件已被删除，但登记信息仍在。

**解决**：取消注册这个已损坏的发行版。

`PowerShell`

```powershell
wsl --unregister <发行版名>
```

> [!CAUTION]
> 这会删除该发行版中的**全部数据**。若其中有需要保留的内容，
> 先用 `wsl --export <发行版名> <备份文件.tar>` 导出。
> 对于已经无法启动的发行版，通常已无数据可保留。

## 6.3 `wsl --install` 或 `wsl --update` 长时间无响应

**原因**：走的是微软商店通道，网络不通畅时会一直等待。

**解决**：

- 安装发行版：改用第 2.3 小节的离线导入方式
- 升级 WSL 本体：从 GitHub 下载 MSI 手工安装

## 6.4 apt 报 `Hash Sum mismatch`

**原因**：镜像同步不及时，索引与实际的包文件不一致。

**解决**：换一个镜像源。

## 6.5 apt 报 `NO_PUBKEY`

**原因**：缺少仓库的签名密钥。

**解决**：安装对应的 keyring 包，或从仓库官网下载公钥导入。

> [!TIP]
> 若连 `gpg` 都没有，会陷入「要装密钥得先有 gpg、要装 gpg 得先能 apt」的循环。
> 这种情况下重新安装一个干净的发行版通常比修复更快。

## 6.6 断点显示为空心圆（未验证）

**原因**：源文件路径映射不正确。

**解决**：

1. 在调试控制台执行 `-file-list-exec-source-files`（MI 命令），或
   在 GDB 中执行 `info sources`，查看 GDB 报告的**真实路径**
2. 按该路径配置 `sourceFileMap`

## 6.7 `pipeTransport` 连接失败

依次检查：

| 检查项 | 方法 |
|---|---|
| 发行版名是否正确 | `wsl -l -v` |
| `debuggerPath` 是否存在 | `wsl -d <发行版名> -- ls -l /usr/bin/gdb` |
| `program` 是否为 Linux 路径 | 应当是 `/mnt/...` 而非 `K:\...` |
| 程序是否已编译 | 先手工执行一次构建任务 |

## 6.8 Windows GDB 连不上 Linux 的 gdbserver

**这不是配置问题。** 见第 4.6 小节：Windows 版 GDB 不含 GNU/Linux 目标支持。

**解决**：改用 `pipeTransport` 或 Remote - SSH / Remote - WSL。

## 6.9 命令行调用 GDB 时 `-ex` 参数失效

**现象**：

`实测数据`
`Text`

```text
$ gdb --batch -ex "set pagination off" -ex "print 1+1" -ex quit
Excess command line arguments ignored. (1+1)
pagination: No such file or directory.
K:\.../off: No such file or directory.
Argument required (expression to compute).
```

**原因**：GDB 把含空格的 `-ex` 参数按空格拆开，多余的部分被当作命令行参数（即待调试的文件名）。

**解决**：把命令写进脚本文件，用 `-x` 执行：

`Text`

```text
# 写成 commands.gdb
set pagination off
print 1+1
quit
```

`PowerShell`

```powershell
gdb --batch -x commands.gdb
```

# 第 7 节 术语对照

| 术语 | 英文 | 含义 |
|---|---|---|
| WSL | Windows Subsystem for Linux | Windows 的 Linux 子系统 |
| 发行版 | Distribution / Distro | 具体的 Linux 系统，如 Ubuntu |
| 管道传输 | pipeTransport | cpptools 中通过管道在远端运行调试器的机制 |
| 复合启动 | compounds | VS Code 中一次启动多个调试会话的配置 |
| 远程调试 | Remote Debugging | 调试运行在另一台机器上的程序 |
| 联合调试 | Joint Debugging | 同时调试多个相互通信的程序 |
| 路径映射 | sourceFileMap | 把调试器报告的路径转换为本地路径 |
| MI | Machine Interface | GDB 供程序调用的文本协议，VS Code 使用它 |
| 根文件系统 | rootfs | 打包好的 Linux 文件系统，可用于导入 WSL |
