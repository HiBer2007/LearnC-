## 一、环境概况

### 三条调试路线

| | 编译器 | 调试器 | VS Code 调试类型 | 本工作区是否可用 |
|---|---|---|---|---|
| 路线 A | MinGW GCC 15.2.0 | GDB 16.3 | `cppdbg` | **不可用**，原因见下 |
| 路线 B | MSVC cl.exe 19.44（VS2022） | VS2022 调试器（与 Visual Studio 同一引擎） | `cppvsdbg` | **可用** |
| 路线 C | 两者均可 | LLDB（CodeLLDB 扩展自带） | `lldb` | **可用** |

> **路线 A 的两种解法**
>
> 路线 A 不可用的原因是中文路径（见下）。若确实需要使用 GDB，有两条路：
>
> | 解法 | 做法 | 代价 |
> |---|---|---|
> | 把工程移到全英文路径 | 例如 `D:\cpp-course` | 需要迁移工程，但配置无需改动 |
> | **改用 Linux 环境（WSL）** | 见《02-调试器/02-跨系统调试.md》 | 需要搭建 WSL，之后不再受中文路径限制 |
>
> 后者更为彻底：Linux 下 GDB 原生使用 UTF-8，中文路径不构成问题。
> 而且 WSL 还支持**联合调试**与**远程调试**，这是 Windows 侧难以做到的。

> **关于路线 A 不可用的原因（重要）**
>
> 工程所在路径中含中文时（本工作区即是如此）。
> GDB 在 Windows 上经 MI 协议接收文件名时期望 ANSI 代码页（936）字节，
> 而 VS Code 发送的是 UTF-8 字节，两者不一致，导致 GDB **无法打开可执行文件**，
> 调试完全无法启动。该问题无法通过任何配置项解决。
>
> 表现：按 F5 后提示 `Program path ... is missing or invalid`（但文件确实存在），
> 或弹出空的"选择要终止的调试会话"列表后无反应。
>
> 完整的原理、实测数据与解决方案见《01-编译器/02-环境配置.md》第 1 章第 2 节
> 与第 9 章第 13 节。
>
> **结论**：在本工作区中请使用**路线 B** 或**路线 C**。
> 把整个工作区移到全英文路径后，路线 A 即可恢复可用。

> **说明**：编译器与调试信息格式的对应关系不可混用。GDB 只识别 gcc/clang 产出的
> DWARF 调试信息，VS2022 调试器只识别 MSVC 产出的 PDB 调试信息。
> LLDB 是例外，两者都支持。

### 三类资源

| 目录 | 内容 | 使用方式 |
|---|---|---|
| （工作区根） | 单文件 playground | 放入 `.c` / `.cpp` 文件后，按 F5 即可调试 |

## 二、快速开始

### 场景 1 · 单文件调试（最常用）

1. 在工作区任意位置新建一个 `.c` 或 `.cpp` 文件。
2. 在行号左侧单击，设置断点。
3. 按 `F5`，在列表中选择以下配置之一：

   | 配置 | 适用范围 |
   |---|---|
   | `GDB · C 单文件 (gcc)` | C 语言，使用 gcc 编译并由 GDB 调试 |
   | `GDB · C++ 单文件 (g++)` | C++，使用 g++ 编译并由 GDB 调试 |
   | `VS2022 · 单文件 (cl · C 与 C++)` | C 或 C++，使用 cl 编译并由 VS2022 调试器调试 |

编译与启动调试均由配置自动完成。

> **注意**：两个单文件配置针对的都是当前打开的文件。
> 调试前需确认活动编辑器中为 `.c` / `.cpp` 文件，而非 `.h` 或 `CMakeLists.txt`。

> **注意**：编译 C++ 文件时必须选择 g++ 对应的配置。
> 使用 `gcc` 编译 `.cpp` 文件不会链接 `libstdc++`，
> 会出现大量 `undefined reference to std::cout` 报错。

### 场景 2 · 运行examples

需先单独打开对应的示例文件夹，再按 F5：

```
文件 → 打开文件夹 → 选中  B-examples\03-CMake-C
```

设置断点后按 F5：

| 配置 | 构建产物 |
|---|---|
| `GDB · CMake 工程 (MinGW gcc)` | `build/mingw/bin/app.exe` |
| `VS2022 · CMake 工程 (MSVC cl)` | `build/msvc/bin/Debug/app.exe` |

配置将自动完成「CMake 配置 → 编译 → 启动调试」全过程。

> **说明**：为什么必须单独打开
> VS Code 只识别工作区根目录下的 `.vscode`。
> 若在根工作区中直接打开 `03-CMake-C\src\main.c` 并按 F5，
> 实际使用的是根目录的「单文件」配置。该配置会把 `main.c` 作为单文件单独编译，
> 而 `main.c` 中调用了 `calc.c` 内的函数，因此会出现链接失败：
>
> ```
> undefined reference to `add'
> ```
>
> 该现象并非配置错误，而是打开方式不正确所致。

### 场景 3 · 自行练习配置

将 `C-空模板\` 中的任一模板复制到其他位置，按其中的 `配置步骤.md` 操作：

```powershell
Copy-Item -Recurse "C-空模板\01-C-单文件" "我的练习\01"
```

若配置过程中遇到问题，可参考 `B-examples\` 中对应示例的 `.vscode`。

## 三、常用快捷键

| 按键 | 作用 |
|---|---|
| `F5` | 开始 / 继续调试 |
| `F9` | 在当前行切换断点 |
| `F10` | 单步跳过（不进入函数） |
| `F11` | 单步进入（进入函数内部） |
| `Shift+F11` | 从当前函数跳出 |
| `Shift+F5` | 停止调试 |
| `Ctrl+Shift+Y` | 打开「调试控制台」（可输入 gdb / VS 调试器命令） |

左侧「运行和调试」面板包含「变量 / 监视 / 调用堆栈 / 断点」四个页签。

三种常用操作如下：

| 操作 | 方法 |
|---|---|
| 查看变量的值 | 将鼠标悬停在变量上，或将该变量添加到「监视」面板 |
| 修改变量的值 | 在「变量」面板中双击该值，修改后按回车（修改会实际影响程序运行） |
| 设置条件断点 | 右键单击断点 → `编辑断点` → 填写条件表达式 |

## 四、命令行用法（不启动 VS Code 时）

```powershell
# ---- 单文件 ----
# GDB 路线（C）
gcc -std=gnu17 -g -O0 -Wall -Wextra 你的文件.c -o build\single\gcc\a.exe
gdb build\single\gcc\a.exe

# GDB 路线（C++）—— 注意是 g++
g++ -std=gnu++17 -g -O0 -Wall -Wextra 你的文件.cpp -o build\single\gcc\a.exe

# VS2022 路线
pwsh -File .vscode\tools\build-msvc.ps1 -Source 你的文件.c -Output build\single\msvc\a.exe

# ---- CMake 工程（在示例文件夹里执行）----
cmake --preset mingw-gdb    ; cmake --build --preset mingw-gdb      # MinGW + GDB
cmake --preset msvc-vs2022  ; cmake --build --preset msvc-debug     # MSVC
```

| 组件 | 版本 | 位置 | 备注 |
|---|---|---|---|
| **PowerShell 7（`pwsh`）** | **7.6.3** | `C:\Program Files\PowerShell\7\pwsh.exe` | 原本已安装。**构建任务脚本由它执行**，必需项 |
| GCC / G++ | 15.2.0 | `<MinGW>\bin` | 原本已安装，已在 PATH 中 |
| GDB | 16.3 | `<MinGW>\bin\gdb.exe` | 原本已安装，已在 PATH 中 |
| CMake | 4.4.3 | `<CMake>\bin` | 新安装（winget），已加入机器级 PATH |
| Ninja | 1.13.2 | `<MinGW>\bin\ninja.exe` | 新安装（winget），按 MSYS2 惯例放入 mingw 目录 |
| MSVC cl.exe | 19.44 | `<VS>\VC\Tools\MSVC\<版本号>` | 复用已有的 VS2022 |
| VS Code 扩展 | — | — | 复用已有的 `ms-vscode.cpptools`、`ms-vscode.cmake-tools` |

> **关于 PowerShell 7**
>
> 本工作区的构建任务与脚本一律以 **PowerShell 7（`pwsh`）** 为准，
> 不使用 `cmd.exe`，也不使用 Windows PowerShell 5.1（`powershell.exe`）。
>
> 原因：`cmd.exe` 按当前代码页逐字节解析批处理文件，中文注释会被误读为控制字符；
> 其参数转义规则与 VS Code 的任务传参机制不兼容，会导致任务启动失败。
> Windows PowerShell 5.1 读取无 BOM 的 UTF-8 脚本时按 ANSI 解析，中文会变为乱码。
>
> 详细说明与实测记录见《01-编译器/02-环境配置.md》第 3 章步骤 1、第 9 章第 4 节。
>
> **唯一的例外**：`build-msvc.ps1` 内部会调用一次 `cmd.exe` 来执行 `vcvars64.bat`。
> 该文件是批处理脚本，必须由 `cmd` 解释，无法替代；调用被限制在这一处，不影响其余部分。

> **注意**：CMake 4.x 的重要变化
> 自 CMake 4.0 起，移除对 `cmake_minimum_required(VERSION < 3.5)` 的兼容。
> 网络上较早的教程中，CMakeLists.txt 常写有 `VERSION 2.8` / `3.0`，此类文件会直接报错。
> 本工作区的工程均使用 `VERSION 3.16`，不受影响。
> 遇到旧工程时，参见「七、常见问题 → 第 9 条」。

## 七、常见问题

### 1. 断点停在声明行时，变量显示的是垃圾值

该现象并非缺陷，而是最常见的误解之一。例如：

```c
int arr[N] = {10, 20, 30};   /* ← 断点打在这一行 */
```

断点触发时查看 `arr`，会看到一组无意义的数字，甚至出现
`Cannot access memory at address ...` 报错。原因是该行尚未执行：
断点停在「即将执行」的位置，初始化表达式尚未运算。

> **说明**：正确做法是将断点设置在下一行，或在断点触发后按一次 `F10`（单步跳过），
> 待初始化完成后再查看变量。

> **说明**：同理，对于 `std::vector<Student> list = {...}` 这类带构造函数的对象，
> 在声明行暂停时展开查看会报错，按一次 `F10` 即可恢复。

### 2. 调试控制台里 gdb 报 `No such file or directory`

```
warning: 2  <工作区>\xxx.c: No such file or directory
```

该现象已知，不影响调试。原因是：GDB 在 Windows 上通过 ANSI 码页（CP936）打开文件，
而 gcc 将 UTF-8 编码的路径写入调试信息，二者不一致，因此 GDB 自身无法打开源码文件。

该问题仅影响 GDB 的 `list` 命令。VS Code 通过 GDB 的 MI 接口通信，
MI 会以 UTF-8 正确返回绝对路径，源码文件由 VS Code 自行读取；
因此断点、单步、查看变量、源码高亮等功能均正常。

（已实测确认：中文目录名与中文文件名下的断点均可正常命中。）

### 3. 在根工作区调 CMake 示例，报 `undefined reference to ...`

该现象由打开方式不正确引起，参见「二、场景 2」的说明。
CMake 工程需单独打开其所在文件夹，不能使用根工作区的配置进行调试。

### 4. 按 F5 提示找不到 cmake / ninja

正常情况下不会出现该提示（配置中已作兜底处理）。若确实出现，重启 VS Code 即可解决：
新安装的软件需要等待 VS Code 重新读取 PATH 环境变量。

### 5. 智能感知（补全、波浪线）用的是哪套编译器？

默认使用 MinGW GCC（根目录）或 g++（C++ 示例）。
如需更换，按 `Ctrl+Shift+P`，执行 `C/C++: Select IntelliSense Configuration`。

### 6. 升级 Visual Studio 之后智能感知报错

`c_cpp_properties.json` 中 MSVC 的 `compilerPath` 带有工具集版本号：

```
<VS>\VC\Tools\MSVC\<版本号>\bin\Hostx64\x64\cl.exe
```

VS 大版本升级后，该版本号会发生变化。可查看 `VC\Tools\MSVC\` 下的新版本号并相应修改。
（仅影响智能感知，不影响编译和调试。）

### 7. 「单文件」配置能编译多个 .c 文件吗？

不能。该配置只编译当前打开的一个文件。多文件工程请使用 CMake 路线
（参考 `B-examples\03-CMake-C\`）。

### 8. 程序里用 scanf 能正常输入吗？

可以。两条路线均将程序的标准输入连接到 VS Code 的集成终端
（`cppdbg` 通过 `"externalConsole": false` 实现，`cppvsdbg` 通过 `"console": "integratedTerminal"` 实现）。

### 9. 导入的旧工程报 `Compatibility with CMake < 3.5 has been removed`

CMake 4.x 不再接受 `cmake_minimum_required(VERSION 2.8)` / `(VERSION 3.0)` 这类旧写法：

```
CMake Error at CMakeLists.txt:1 (cmake_minimum_required):
  Compatibility with CMake < 3.5 has been removed from CMake.
  ...
  Or, add -DCMAKE_POLICY_VERSION_MINIMUM=3.5 to try configuring anyway.
```

以下两种方法可任选其一（均已实测）：

**方法一 · 临时兼容，不修改原有代码**

```powershell
# 注意：等号后的部分必须整体加引号。
# 不加引号时 PowerShell 会拆分为 "-D...=3" 与 ".5" 两个参数，
# CMake 将报 Invalid CMAKE_POLICY_VERSION_MINIMUM value "3"
cmake -S . -B build "-DCMAKE_POLICY_VERSION_MINIMUM=3.5"
```

若不便于书写引号，可使用环境变量：

```powershell
$env:CMAKE_POLICY_VERSION_MINIMUM = "3.5"
cmake -S . -B build
Remove-Item Env:\CMAKE_POLICY_VERSION_MINIMUM   # 用完清掉，免得影响别的工程
```

**方法二 · 修改一行配置，推荐长期使用**

将旧工程的 `CMakeLists.txt` 第一行改为：

```cmake
cmake_minimum_required(VERSION 3.16)
```

> **注意**：在未指定 `-G` 参数而直接执行 `cmake -S . -B build` 时，
> CMake 4.4.3 会自动选择最新版本的 Visual Studio；本机为 VS2026 BuildTools，
> 而非通常使用的 VS2022。本工作区的预设均显式指定了生成器，不受影响。

### 10. MSVC 路线报 `D8003 缺少源文件名`

该报错源于 `.cmd` 批处理的常见问题：`/Fo:"...\dir\"` 结尾处的 `\"` 会被 CRT 参数解析器
视为转义引号，从而使其后的源文件参数被整体忽略。

本工作区使用 PowerShell 脚本（`build-msvc.ps1`），并统一使用正斜杠，已规避该问题。
若需自行编写 `.cmd` 文件，应将反斜杠改为 `/`，或去掉结尾处的反斜杠。

### 11. 程序输出的中文显示为乱码

现象为 `printf("中文")` 输出后显示成 `涓枃` 一类「看着像汉字但完全不对」的字符。

**原因**：gcc 与 MSVC 默认都把字符串常量按 UTF-8 写入 exe，
而中文 Windows 的控制台按 CP936（GBK）解释字节流。

**本工作区已修复**：全部编译配置中都显式指定了字符集：

| 编译器 | 参数 |
|---|---|
| gcc / g++ | `-finput-charset=UTF-8 -fexec-charset=GBK` |
| MSVC cl.exe | `/source-charset:utf-8 /execution-charset:gbk`（**不能写 `/utf-8`**） |

自行新建工程时若需复制编译参数，注意不要遗漏这两项。
完整的字节级实测对照见《01-编译器/02-环境配置.md》第 9 章第 6 节。
