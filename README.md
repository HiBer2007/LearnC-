# C/C++ 编译与调试教材

本教材面向**从零开始学 C/C++** 的读者，重点回答两类问题：

- **代码是怎样变成程序的**，以及为什么这个过程不能省略
- **程序出错时怎样查出原因**，而不只是靠打印

全部结论均经过实际验证，并标注了依据。

## 用 AI 读这套教材

仓库根目录带一份 **`AGENTS.md`**。用 AI 工具把本仓库当作工作区打开时，
它会被当作工作区说明读进去，作用是把三件事交代清楚：

| 交代什么 | 内容 |
|---|---|
| **这是什么** | 仓库里的 `.md` 是**教材正文**，每个技术结论都带依据标注（`实测数据` / `文档` / `待确认`），并明写限制与不确定之处 |
| **怎么使用** | 先在 `AGENTS.md` 第四节的内容索引里定位到篇与节，再读**整节**；回答时把出处写到节——《路径》第 N 节 |
| **回答的界限** | **只依据仓库内容作答**；仓库没覆盖的就说「本教材未涉及」，不用外部知识补全；标了 `待确认` 或写明**存疑**的内容，不许说成确定的 |

**因此你可以这样用它**：让它按节讲某个主题、让它指出这句话出自哪一节、
让它把某段实测的输出与结论对上。**它与教材正文冲突时，以正文为准。**

## 全教材通用的约定

### 事实与判断：本书里的两类内容

**这套教材里有两类内容，读法不同。**

| 类别 | 是什么 | 怎么对待 |
|---|---|---|
| **事实** | 命令的真实输出、标准条文、组件自身的定义 | **可以核对**。按标注区分：`实测数据` 是在本文所述环境中执行过的，`文档` 引自官方资料，`待确认` 尚未验证，**存疑**表示随环境而变、给不出统一答案 |
| **判断** | 讲什么、按什么顺序讲、怎么取舍、下什么结论，以及像《00-写在最初/02-AI时代要学什么.md》那样通篇议论的文字 | **请自己判断**。它们是作者的选择，不是唯一答案，也不代表标准或行业的共识 |

**文中的「应该」「必须」「值得」多为作者的建议。**
语言与标准真正规定的事情，会给出条文出处；其余是作者认为合理的做法。

**作者不认为自己的取舍适用于所有场合。**
同一件事换一个团队、换一套约束，合理的做法可能完全不同——
书中把理由与代价一并写出，正是为了让读者有能力做出不同的选择。

### 结论的依据怎么标

文中每个技术结论都标了依据，**标注是表格或代码块上方的一行行内代码**：

`Text`

```
实测数据    在编写环境中实际执行并验证过，输出可复现
文档        引自标准或官方资料，原文以引用块给出
待确认      有合理推断但未验证，或依赖外部条件
```

**这三种标注只出现在被标注的对象正上方**，不写在句子中间。
写法就是普通的行内代码，如 `` `实测数据` ``、`` `文档` ``、`` `待确认` ``。

**另有一类内容不标注、而是用正文写明「存疑」**：它的结论**随环境而变**
（图形界面里的操作、依赖读者所装扩展与版本的步骤、随发行版与内核变化的网络行为等），
教材给不出统一答案，只能说明**变的是什么、为什么定不下来、读者应以什么为准**。
遇到这类内容，请以自己机器上的实际结果为准。

### 提示与注意事项

按后果轻重分五级，靠左侧色线区分：

| 写法 | 颜色 | 表示 |
|---|---|---|
| `> [!IMPORTANT]` | 紫 | **结论**、要点、本质概括 |
| `> [!NOTE]` | 蓝 | **小结**、回顾 |
| `> [!TIP]` | 绿 | **提示**、做法建议 |
| `> [!WARNING]` | 黄 | **警告**、可能出错 |
| `> [!CAUTION]` | 红 | **严重后果**（未定义行为、数据损坏、安全问题） |

### 代码块的语言

**GitHub 与 VS Code 的预览都不在代码块头部显示语言**，
因此每个代码块上方也有一行标明语言的标注：

`Markdown`

````markdown
`C`

```c
/* width.c    编译：gcc -std=c23 width.c -o width */
#include <stdio.h>
int main(void) { return 0; }
```
````

**标签用行内代码写，语言名用标准写法**：
`C`、`C++`、`PowerShell`、`Bash`、`Text`、`CMake`、`JSON`、`JSONC`、
`Assembly`、`Ninja`、`Linker Script`、`INI`、`Markdown`、`Makefile`、
`Batch`、`.gitignore`。

> [!TIP]
> **为什么用行内代码而不是 `<small style="color:gray">`**：
> GitHub 会过滤掉 HTML 的 `style` 属性，灰色与字号都不会生效；
> 而行内代码的底色是 GitHub 自己的样式表给的，**在 GitHub 与 VS Code 上都能渲染**。

**文中的实测代码一律写成完整单文件**，带 `#include` 与 `int main`，
首行注释写明文件名与编译命令，读者可以直接复制去跑。

### 路径的写法

教材面向任意一台 Windows 计算机，因此**不出现某一台机器的具体安装路径**。
文中一律使用下列占位符：

| 占位符 | 含义 | 常见形式 |
|---|---|---|
| `<MinGW>` | MinGW-w64 的安装目录 | `C:\mingw64` |
| `<CMake>` | CMake 的安装目录 | `C:\Program Files\CMake` |
| `<VS>` | Visual Studio 的安装目录 | `C:\Program Files\Microsoft Visual Studio\2022\Community` |
| `<版本号>` | 带版本号的目录中的那一段数字 | 如 `14.44.35207` |
| `<工作区>` | 你在 VS Code 中打开的文件夹 | 任意位置 |
| `<发行版名>` | WSL 发行版的名字 | `Ubuntu` |
| `<WSL地址>` | WSL 的虚拟网卡地址 | `192.168.x.x` |

**各程序的实际路径怎么找**：见[01-编译器/02-环境配置](01-编译器/02-环境配置.md)第 3 节。

### 引用文档的写法

文中引用其他文档时写作 `《01-编译器/01-编译与链接.md》`，
路径**相对于本教材的根目录**。

**讲清引用的层级**，教材用四个固定的称呼：

| 层级 | 称呼 | 例子 |
|---|---|---|
| 顶层文件夹 | **板块** | `04-语法` |
| 一个 `.md` 文件 | **章节** | `01-一些基础概念.md` |
| 文件内的 `#` 标题 | **节** | `# 第 1 节 语法糖` |
| 文件内的 `##` 标题 | **小节** | `## 1.1 一句话定义` |

因此写「见《03-构建工具链/01-构建工具链.md》第 3.8 小节」。

**已规划但尚未编写的章节**，引用时写成 `【待补：10-并发与并行/】`。

## 本教材的四个立足点

### 一、用真实代码讲，不用玩具代码

教材中的例子取自**实际运行的项目**，而不是为教学编写的片段。
真实代码里有历史包袱、平台差异、为绕开某个问题而写的怪代码——
**这些恰恰构成了实际开发的绝大部分难度**。

源文件收录在 [`A-教学素材/`](A-教学素材/)，可对照阅读。

### 二、说清「为什么」，不只给结论

例如：

- 不只说「要加 `-g`」，而是说明调试信息里存了什么、不加会怎样
- 不只说「任务要这样写」，而是说明为什么另一种写法会失败
- 不只说「用 `volatile`」，而是给出优化前后的汇编对照

**讲一个语法点时，先找出它是不是另一件事的「语法糖」**，
再说明糖纸下面是什么。这样它的性质就是推出来的，不用逐条背。
写法见[04-语法/01-一些基础概念](04-语法/01-一些基础概念.md)第 1 节。

### 三、数据与结论分开摆

**主线只留讲清一件事所必需的数据**，
完整的实测数据、复现命令与源码放到该章节的附录。

数据用**行内代码**标注，与正文区分开，读者顺着正文能连续读完。

### 四、区分「实测」与「文档」

教材中的每个技术结论都标明了依据。
凡未实际验证的，一律注明「待确认」，不冒充已验证的事实。

## 各板块的理论与实操比例

**这套教材的各部分不是同一种写法。比例由题目本身决定，不是编写上的偏轻偏重。**

| 板块 | 偏重 | 为什么 |
|---|---|---|
| `01-编译器` | **动手** | 装环境、把程序编出来、烧进板子，这些事只有做一遍才算会；原理集中在《01-编译器/00-语言的实现.md》与《01-编译器/01-编译与链接.md》两篇 |
| `02-调试器` | **动手** | 调试是手上的功夫：快捷键、命令行、附加进程、看崩溃现场，讲得再细也不如自己跑一次 |
| `03-构建工具链` | **动手** | 构建描述是配出来的，不是推出来的；重点在「这样配会怎样」 |
| `04-语法` | **机制** | 规则为什么是这样、哪些地方 C 与 C++ 分岔，靠推理与对比 |
| `05-类与面向对象` | **机制** | 抽象手段的设计意图，要在概念之间对照才看得清 |
| `06-更底层` | **机制** | 标准与硬件交界的地方，只有机制能解释现象 |
| `07-标准库` | **机制与用法并重** | 库是拿来用的，但实现定义、未定义与失效规则必须讲清 |
| `08-一些散落的算法` | **机制与用法并重** | 解法是拿来用的，但每条解法在什么前提下成立、代价落在哪必须讲清；每章都从真实问题起步，落到能跑的代码与实测 |
| `09-高阶数据结构` | **机制与用法并重** | 容器是拿来用的，但结构为什么这样设计、代价落在哪必须讲清；推进路线固定为需求 → 模型 → 接口 → 实现 → 代价 |

**后续板块按同一标准**：题目偏动手就写步骤，偏机制就讲原理。

**由此有三条读法**：

1. **不要在动手的章节里找完整的语言规则**——那里只给够用的原理，
   其余指路到机制章节，指路会写到《路径》第 N 节。
2. **不要在机制的章节里找逐步操作**——那里给结论与理由，
   操作在动手的章节与 `B-examples/`、`C-templates/` 里。
3. **两边的依据同样严格**——操作步骤与机制结论都按同一套标注，
   说「做过的」就必须真做过，说不准的就写「待确认」或「存疑」。

**这不是编排上的失衡，而是把力气花在题目真正难的地方。**
嵌入式与构建这类题目，难在环境、版本与工具链之间的配合，不在概念；
语言与底层这类题目，难在机制与边界，不在敲命令。

### 怎么读这些数字

| 标注 | 含义 |
|---|---|
| 实测数据 | 在上述环境中**真的执行过**，输出可复现；给出的复现步骤能重跑 |
| 文档 | 来自官方文档、组件自身定义或权威资料 |
| 待确认 | 有合理推断但**未验证**，或依赖外部条件 |

**「实测数据」不代表「在所有环境下都成立」。**
例如 `sizeof(long)`，**在 Windows 上测是 4，在 Linux 上测就是 8**——
两个都是实测，差别来自平台而非编译器。
见《04-语法/02-数据类型与类型系统.md》第 2.6 小节。

**遇到与本文数字不符的情况，先核对上表**，
再检查是否有文中已说明的前提没有满足。
