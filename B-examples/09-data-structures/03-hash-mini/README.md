# 示例 `09-data-structures/03-hash-mini` · 链地址法与开放寻址（纯命令行）

两版从零写起的哈希表，**接口完全一样**：`insert`、`contains`、`erase`。
差别只在冲突怎么办——链地址法把冲突的键挂成一条链，开放寻址按线性探测往后找空槽。
项目让两者使用同一份 1000 个键（全是 10 的倍数）与同一套查找，
把桶数的增长、探测的步数、墓碑的积累、重整之后的回落都列在同一张表里。

主线是**哈希只决定快慢，不决定对错**。项目里有一个哈希开关，三档分别是混合、
只看低 8 位、永远返回 0。三档下 1000 个键全部找得到、命中次数一模一样，
变的只是比较次数：链地址法从 1505 次涨到 500500 次，开放寻址从 1447 次涨到 500500 次。
这一栏数字正是「哈希函数的质量决定一切」的依据。

第二件主线是删除。链地址法删一个键就是摘一个节点，用「指向指针的指针」
把「删头节点」和「删中间节点」写成同一段代码。开放寻址不能这样：
把槽直接清空会让探测序列从这里断掉，后面那些键就再也找不到了。
项目保留了那个写错的版本（`erase_clearing_slot`），
在同一张表上演示「找到 300 个」与「找到 193 个」的差别。

报告里另有一处对照：查一个不在表里的键要一路走到空槽，一路上每个墓碑都要走过，
但墓碑不会让它提前停下、也不会让它变长——占用变成墓碑，走过的格数还是那些。
墓碑真正占的是位置：插入要绕过它们才能找到空槽，负载因子把它们算在内，表会更早地长大。
这一段是控制实验：两张表容量相同、键数相同，只有一张留着 700 个墓碑，
各插 300 个新键的探测次数是 765 对 393。

核心库另带 19 项自测，覆盖两版的语义一致、坏哈希下的正确性、
负载因子上限、素数桶数、墓碑与「直接清空」的差别。

## 这个项目要解决什么问题

哈希表的形状由两件事决定：桶数组如何增长、冲突的键放在哪里。项目把这两件事各做成一段输出。

桶数组那一段打印的是「插入第几个键时加桶」：第 2、14、30、60、128、258、522 个键，
桶数依次长到 13、29、59、127、257、521、1049。桶数每次都取下一个素数，
负载因子在加桶之前压在 0.5 上下，最后一次加桶之后是 0.953。
加桶一共 7 次，再哈希重新放置了 1007 个元素——这就是「平均 O(1)」里那个「平均」的代价。

冲突那一段把两版放在一起：链地址法最终 1049 个桶、最长的一条链 5 个节点；
开放寻址最终容量 2048、插入 1000 个键共探测 2768 次、查找 1000 次共探测 1447 次。
两者的命中结果逐位一致，差别只在探测与链表指针这两种代价上。

坏哈希那一段针对「哈希函数写得太随意」这一情形：同一份键、同一套查找，
把哈希换成「永远返回 0」，链地址法的比较次数从 1505 涨到 500500，
开放寻址的探测次数从 1447 涨到 500500，而命中次数始终是 1000。

删除那一段对照的是两种删法。开放寻址里把槽清空会让探测提前停下，
项目用 `erase_clearing_slot()` 把这个错误做法保留下来：同样的表、同样的删法，
留墓碑的那张还能找到 300 个键，直接清空的那张只找到 193 个。

## 做完能掌握什么

- 会写出链地址法与开放寻址两版哈希表，并能说清「冲突的代价放在哪」
- 会在插入之前判断负载因子，并按素数序列给桶数组加桶
- 会写再哈希：只改链、不重新分配节点，因此指针与引用仍然有效
- 会说清开放寻址为什么必须留墓碑，并能演示直接清空会丢键
- 会用「比较次数」与「探测次数」测出坏哈希的代价，而不是凭感觉
- 会写一个把键的每一位都混合开的哈希函数，而不是把字段相加
- 会把核心逻辑与界面分开：`hmini` 命名空间不认识 `std::cout`

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `hash_mini.hpp` 的 `HashKind` | 哈希开关：同一份数据换一个函数，正确性不变、探测次数变 |
| `hash_mini.cpp` 的 `hash_key()` | 乘法与移位交替，让键的每一位都影响低位——取桶号用的就是低位 |
| `hash_mini.cpp` 的 `ChainedHash::insert()` | 先判断「插进去会不会超上限」，超了先加桶再插 |
| `hash_mini.cpp` 的 `ChainedHash::rehash()` | 只改链、不重新分配节点，因此指针与引用仍然有效 |
| `hash_mini.cpp` 的 `ChainedHash::erase()` | `Node** link`：删头节点与删中间节点写成同一段代码 |
| `hash_mini.cpp` 的 `OpenHash::find_slot()` | 空槽停下、墓碑继续——这一行决定了墓碑为什么必须有 |
| `hash_mini.cpp` 的 `OpenHash::insert()` | 记下第一个墓碑但还要往后确认键不在，最后落在墓碑上 |
| `hash_mini.cpp` 的 `OpenHash::erase_clearing_slot()` | 故意写错的删除，只用来演示「探测序列断掉」 |
| `hash_mini.cpp` 的 `OpenHash::grow()` | 再哈希时墓碑一并消失：容量不变时它就是一次重整 |
| `main_cli.cpp` 的 `to_console_encoding()` | 全项目唯一的编码转换点 |

## 已知问题

- 键只支持 `int`，哈希与判等都写死在 `int` 上；换成字符串键要另写一对，
  并保证「判等为真则哈希相同」这一条
- 开放寻址的 `insert()` 在表满时返回 `false`，与「键已经存在」返回的 `false` 分不开；
  正常路径下不会走到（负载上限挡住了），但接口上没有把这两种情况分开
- 开放寻址用的是线性探测，没有做二次探测或双重哈希；
  步长固定为 1 时容易聚成一片，这正是报告里「平均 2.77 次」里包含的代价
- 链地址法的节点是逐个 `new` 出来的，没有做节点池；
  报告里的数字只有计数，不含分配器开销
- 墓碑只在「负载因子超上限」与显式调用 `rehash_clean()` 时清，
  没有按墓碑比例自动触发重整
- `erase_clearing_slot()` 是故意写错的实现，留在头文件里只为演示，
  正常代码里不要调用
- 计数是全局的，多线程下不安全；教学示例固定单线程使用
