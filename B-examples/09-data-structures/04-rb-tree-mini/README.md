# 示例 `09-data-structures/04-rb-tree-mini` · 红黑树的插入与删除（纯命令行）

一棵从零写起的红黑树，插入与删除都按 CLRS 的四情形改法写全，另配两件减少排错时间的工具：
**不变式校验器**与**带颜色的按层打印**。校验器逐条检查四条不变式、
搜索树性质、父指针一致性与「走一遍数出来的节点数」，每改一次就校验一遍；
打印按中序名次排位置，因此左子树总在左边，每个节点前面带 `B:` 或 `R:`，
可以直接看出是否出现连续两个红节点。

两处实现上的决定先说明：**空叶子合成一个黑哨兵**，于是叔叔与兄弟永远不是空指针，
删除修复少一半分支；**节点带父指针**，于是迭代器的 `++` 与 `--` 都是常数时间，
代价是每个节点多 8 字节。

报告里有三处对照构成主线。第一处：插入 11 个键的固定顺序一次旋转都不用
（该顺序是完美二叉树的层序，始终没有出现双红），
换成 1 到 8 依次插入就要旋转 4 次——**同一批键，插入顺序决定修复的工作量**。
第二处：随机插删 2000 次，每一步都与 `std::set` 比对，不一致 0 次，
校验 2000 次，不变量被破坏 0 次。第三处：同样的 1000 个键，
有序插入时朴素搜索树的高为 1000、红黑树为 17；打乱插入时分别为 22 与 12。

核心库另带 20 项自测，其中第 17 项把「朴素树退化成链」与「红黑树有高度上界」
放在一起比，第 19 项验「旋转不改中序」。

## 这个项目要解决什么问题

红黑树有两个公认的难点：插入修复要分情况，删除修复更难。项目把这两处难点都做成可检查的。

插入那一段打印的是「每插一个键之后的节点数、树高、黑高度、旋转次数、染色次数与校验结果」。
用 11 个键的固定顺序插进去，旋转次数一直是 0，染色 11 次——
这个顺序恰好是完美二叉树的层序，父亲的兄弟（叔叔）总是红的，
走的全是「父叔染黑、祖父染红」的情形 1，一次旋转都不需要。
换成 1 到 8 依次插入，旋转次数升到 4 次，走的是情形 2 与情形 3。
两段对照，可以看出「分情况」分的是什么。

删除那一段从同一棵树里删掉 5、30、60、50、15，每删一个都校验一次。
先删 5 触发一次旋转，后面几次是纯染色或直接摘掉。删除修复看的是兄弟的颜色与
兄弟两个孩子的颜色，四情形里只有「兄弟与两个孩子都黑」那一种需要继续往上推。

校验器与打印是两件工具。校验器返回的不只是一个布尔值，还给出「是哪一条被破坏了」，
自测第 13 项单独核对了它算出的黑高度与 `black_height()` 一致。
打印把颜色一起打出来，`B:30` 与 `R:10` 的区别在树形图里可以直接分辨，
自测第 6 项检查每个键都在图里、且两种颜色字母都出现过。

## 做完能掌握什么

- 会写出完整的红黑树插入与删除，并能说出每一处在恢复哪一条不变式
- 会写不变式校验器：红孩子必须黑、黑高度相同、搜索树性质、父指针一致性
- 会把颜色一起打印出来，用肉眼快速定位「连着两个红」这类错误
- 会解释空叶子哨兵为什么能让删除修复少一半分支
- 会写带父指针的中序迭代器：`++` 三步、`--` 镜像、`--end()` 是最大的键
- 会用「树高」与「最深比较次数」测出平衡与退化的差别，而不是靠计时
- 会把核心逻辑与界面分开：`rbmini` 命名空间不认识 `std::cout`

| 阶段 | 目标 | 做什么 | 验收标准 |

| **阶段 2** | 读懂插入修复 | 把 `insert_fixup()` 里情形 3 的两行染色对调 | 自测第 4 项立刻报出「红节点的孩子是红的」 |
| **阶段 3** | 加一个只读接口 | 加 `int rank(int key)`：返回键的中序名次，用子树大小 | 自测通过；旋转之后名次仍然正确（旋转要重算子树信息） |
| **阶段 4** | 换一种平衡树 | 照同一套校验器写一棵 AVL，比较两者的树高与旋转次数 | 两个自测都通过；AVL 树高更小、旋转更多 |

阶段 2 是重点：改坏之后无须猜测，校验器会指出坏在哪一条上。

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `rb_tree_mini.cpp` 的 `RbTree::RbTree()` | 黑哨兵 `nil_`：左右与父都指向自己，所有空叶子共用它 |
| `rb_tree_mini.cpp` 的 `rotate_left()` | 三处链接成对更新，漏一处就出现「孩子认父、父不认孩子」 |
| `rb_tree_mini.cpp` 的 `insert()` | 新节点一定染红：染黑会直接破坏「黑节点数相同」 |
| `rb_tree_mini.cpp` 的 `insert_fixup()` | 情形 1 是唯一需要继续往上的一种，另两种在本层收尾 |
| `rb_tree_mini.cpp` 的 `erase()` | 两个孩子时先与后继交换位置，转成「最多一个孩子」 |
| `rb_tree_mini.cpp` 的 `erase_fixup()` | 判断依据是兄弟的颜色与兄弟两个孩子的颜色，四种情形 |
| `rb_tree_mini.cpp` 的 `walk_check()` | 校验器在回程里把黑高度返回上来，父子两层的黑高度不等就报错 |
| `rb_tree_mini.cpp` 的 `to_levels()` | 位置按中序名次排，因此一行就是一层，左子树总在左边 |
| `rb_tree_mini.cpp` 的 `Iterator::operator++` | 三步：右子树最左、往上找「我是左孩子」、到 end() |
| `rb_tree_mini.cpp` 的 `worst_lookup()` | 查全部键取最坏一次的比较次数，这就是最深那个键的深度 |
| `main_cli.cpp` 的 `to_console_encoding()` | 全项目唯一的编码转换点 |

## 已知问题

- 只支持 `int` 键，比较写死在 `<` 上；换成别的键类型要另写一份
- 节点带父指针，每个节点比不带多 8 字节；报告里没有统计节点字节数，
  那属于 `A-07` 的内容
- 校验器是递归的，走的是整棵树；在调试构建里每一步都校验会慢下来，
  发布构建里应当关掉（项目里没有做「只在 Debug 下开」的开关）
- 删除修复的四种情形里没有实现「兄弟为空」的分支，
  因为空叶子哨兵让兄弟永远不是空指针；换成 `nullptr` 表示空叶子时要补上
- 迭代器的 `--begin()` 是未定义行为，项目不加检查
- `PlainBst` 只用来做退化对照，只有插入、查找与树高，
  它递归析构 1000 层深的链，换成十万个键会有栈溢出的风险
- 报告里的随机序列来自固定种子的线性同余发生器，
  换一个种子之后「插入成功 739 次」这类数字会跟着变
