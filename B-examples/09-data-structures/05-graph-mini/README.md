# 示例 `09-data-structures/05-graph-mini` · 图的三种存法（纯命令行）

邻接表、邻接矩阵（位图）、边表，三种存法各自实现**同一套回调式遍历接口**：
`for_each_neighbor(v, f)`。四个算法（广度优先、深度优先、连通块标号、拓扑排序）
写成模板，只调用这个接口，因此**换存法不用改算法一个字**。
报告把这件事做成了可核对的输出：同一份模板在三种存法上各实例化一次，
BFS 序列、DFS 序列、连通块标号、邻居访问次数四组结果逐位相同。

另一件被量出来的是「什么时候该用哪种」。同一张稀疏图（200 个点、300 条无向边）上：
查 300 条边各一次，邻接表检查了 849 个位置、矩阵 300 个、边表 90000 个；
取所有点的邻居各一次，邻接表 600 个位置、矩阵 40000 个、边表 120000 个。
矩阵查一条边只要算一个下标再取一位，与图的密度无关；
但取邻居要扫一整行，`V²` 在稀疏图上就贵了。这一行数字就是选择的依据。

报告的邻居序列另外定死了一条约定：**三种存法的邻居都按编号升序回调**。
顺序定死了，三种存法给出的遍历序列才可能逐位相同；
邻接表、矩阵、边表的邻居列表并排打印，可以直接核对。

核心库另带 19 项自测，覆盖三种存法的 `has_edge` 对全部 144 个点对一致、
位图矩阵跨 `uint64` 边界的那一格、有向只存一侧、孤立点的连通块、
有环图上的拓扑排序返回空表。

## 这个项目要解决什么问题

图的形状与遍历是两件事。存法只负责回答「谁能查到谁」，遍历只用到这个接口。
项目里四个算法**一处都没有出现存法的类型名**，因此同一份 `bfs_order` 模板
在三种存法上编出来的实例，给出的序列逐位相同。

第一段把三种存法摆在一起：12 个点、18 条无向边，度数之和都是 36，
内存字节数分别是 432（邻接表）、24（位图矩阵）、288（边表）。
矩阵的 24 字节与边数无关，它只由点数决定——这是它的优点，也是它在大图上的缺点。
各点的邻居列表三行并排打印，逐位相同。

第二段是「换存法不改算法」的证据：BFS 与 DFS 序列各三行、连通块标号三行，
每一组后面都跟着「三者逐位相同：是」；邻居访问次数三行都是 36，等于 2 倍边数。
拓扑排序另拿一张 8 个点、10 条边的有向无环图来跑，长度等于点数。

第四段把「选哪种」量成计数。查边这一项，矩阵每条边只要 1 个位置，
邻接表平均 2.8 个（要扫 `from` 的邻居数组），边表要扫全表；
取邻居这一项反过来，邻接表正好 2 倍边数 600 个位置，矩阵要扫 `V²` 40000 个格子，
边表要扫 `V × 2E` 120000 次。**稠密小图查边用矩阵，稀疏图取邻居用邻接表。**

## 做完能掌握什么

- 会写出邻接表、位图邻接矩阵、边表三种存法，并能说清各自的代价在哪
- 会设计回调式遍历接口，让算法不必知道底下是哪种存法
- 会用显式栈写深度优先，避免链状图把递归深度顶到点数
- 会按「块里最小的顶点编号」给连通块命名，让三种存法的结果可比
- 会把「查边」与「取邻居」的操作次数分别量出来，据此选存法
- 会处理有向与无向的差别：只存一侧、字节数与访问次数各减半
- 会把核心逻辑与界面分开：`gmini` 命名空间不认识 `std::cout`

## 阶段推进

| 阶段 | 目标 | 做什么 | 怎么验收 |

| **阶段 3** | 加带权支持 | 给邻接表加 `for_each_weighted_neighbor`，写一个求最短路的过程 | 新自测通过；报告里每边字节数会变 |
| **阶段 4** | 换一个规模 | 把 `kSparseVertices` 改成 2000，观察矩阵与邻接表的操作次数比 | 矩阵的 `V²` 项涨到 400 万，邻接表仍是 2 倍边数 |

阶段 2 是重点：新存法只实现那成员函数就能套上四个算法，
这就是回调式接口的价值；如果算法里出现了存法类型名，就说明接口漏了东西。

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `graph_mini.hpp` 的 `AdjList::add_undirected` | 无向图两个方向各存一次，漏一个方向反向就查不到 |
| `graph_mini.hpp` 的 `AdjList::for_each_neighbor` | 回调式接口：算法只认识这一个函数 |
| `graph_mini.hpp` 的 `AdjMatrix::set`／`get` | `index >> 6` 与 `index & 63`：除以 64 与取余 64 就是移位与掩码 |
| `graph_mini.hpp` 的 `EdgeList::has_edge` | 没有索引，只能扫全表；这就是边表很少直接当最终结构用的原因 |
| `graph_mini.hpp` 的 `dfs_order` | 显式栈加上「倒着压栈」，避免递归深度等于点数，也让顺序与存法无关 |
| `graph_mini.hpp` 的 `component_label` | 用块里最小的顶点编号当标号，三种存法的结果才可比 |
| `graph_mini.hpp` 的 `topological_order` | 入度数组加队列；走完还有剩下的点就是有环，返回空表 |
| `graph_mini.cpp` 的 `make_edges` | 固定种子的 LCG 加去重排序，报告里的图因此可以逐位复现 |
| `graph_mini.cpp` 的 `neighbors_dump` | 三种存法的邻居列表并排打印，顺序约定一眼可核 |
| `main_cli.cpp` 的 `to_console_encoding()` | 全项目唯一的编码转换点 |

## 已知问题

- 只支持无权图；带权要另写一套接口，`A-10` 给出过每边字节数的对照
- 三种存法都不做顶点编号的越界检查，传进 `n` 以外的编号是未定义行为
- 邻接矩阵的 `n²/64 + 1` 在 `n` 很大时会先算出溢出前的中间值，
  实际使用前应当先判 `n` 是否超过可行范围
- 连通块标号用「块里最小的顶点编号」，因此结果与插入顺序无关；
  但这也意味着标号不是连续的（块可能标成 0、2、3）
- `memory_bytes()` 报的是「按结构算出来的字节数」，不含分配器的头部与对齐填充；
  邻接表那一项在小图上被每个点的 `vector` 头部占去大半
- 深度优先用的是显式栈，因此序列与递归写法不同（递归写法会先走第一个邻居到底）
- `for_each_neighbor` 把回调按值接收，回调里若捕获大对象要留意拷贝；
  项目里的回调都是引用捕获的 lambda
- 计数是全局的，多线程下不安全；教学示例固定单线程使用
