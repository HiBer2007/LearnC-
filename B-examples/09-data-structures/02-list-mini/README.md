# 示例 `09-data-structures/02-list-mini` · 带哨兵的双向链表与 `splice`（纯命令行）

一条从零写起的双向链表：节点分两层（只有链接的 `NodeBase` 与带上元素的 `Node<T>`），
哨兵是一个内嵌的 `NodeBase` 成员，迭代器能把 `NodeBase*` 转回 `Node<T>*`，
因此 `begin()` 就是哨兵的 `next`、`end()` 就是哨兵自己、`--end()` 是最后一个元素。
它能直接进范围 `for`，五个迭代器类型别名齐备，`std::distance` 这类算法也能用。

主线是**插入删除只改指针、从不搬元素**。这条性质带来三件事：
迭代器稳定（别的节点连地址都不动）、`splice` 是常数时间（六处指针，与段长无关）、
移动构造等同于整条链接过来（一个元素都不构造）。报告把这三件事都测了出来：
`link_in` 与 `unlink` 各有几次、`splice` 改了几处指针、
元素构造与析构的增量是不是 0、原来的节点地址变了没有。

报告里另有一处细节：按段的 `splice` 虽然只改六处指针，
却还要走一遍数元素个数——那是为了维护常数时间的 `size()`，不是搬元素。
项目把「改指针次数」与「数元素步数」分成两列打印，这两列在段长 1000 时分别是 6 与 1000。

核心库另带 20 项自测，覆盖空链、反向遍历、`splice` 三种重载、自己 `splice` 自己、
`swap` 只换节点、以及「哨兵不构造元素」这一条。

## 这个项目要解决什么问题

链表的形状比动态数组简单，难的是三处决定：哨兵要不要、节点什么时候被析构、
`splice` 到底改了哪几个指针。项目把这三处各做成一段能看见的输出。

哨兵换掉的是边界特例。项目里的插入只有 `link_in` 一条路径，删除只有 `unlink` 一条路径，
空链插入、头部插入、尾部插入、删到空四种情形共用它们：报告最后一段打印的就是
「三次插入共走 `link_in` 3 次，三次删除共走 `unlink` 3 次」。
代价是一个节点的空间，换掉的却是四段「是不是第一个／最后一个」的判断。

哨兵还有一层与元素生命周期有关的性质：它是内嵌的 `NodeBase` 成员，不是 `Node<T>`，
因此创建一条空链既不分配节点、也不构造元素。报告第一段从 0 个元素递增到 10 个元素，
节点分配次数与元素构造次数始终相等，两列都从 0 起步。

`splice` 是链表独有的操作。项目提供三个重载（整条链、一个元素、一段），
三者在报告里的「改指针次数」都是 6——摘下来两处、接上去四处。
段长从 1 涨到 1000，这一列不动；动的是「数元素步数」那一列，
因为 `size()` 必须是常数时间，按段搬就必须先数一遍。
被搬走的节点地址在 `splice` 前后完全一样，这一点在报告里也有专门一列。

## 做完能掌握什么

- 会写出带哨兵的双向链表，并能说清哨兵为什么是 `NodeBase` 而不是 `Node<T>`
- 会写能进范围 `for` 的双向迭代器：五个类型别名、`++` 与 `--`、`--end()` 是最后一个元素
- 会解释插入删除只改指针带来的迭代器稳定性，并用节点地址验证它
- 会写出三个 `splice` 重载，并说清「改指针是常数时间」与「数元素个数是线性」的分工
- 会把 `clear()` 与析构写成「先记住下一个、再删当前」的顺序
- 会解释移动构造为什么可以一个元素都不构造
- 会把核心逻辑与界面分开：`lmini` 命名空间不认识 `std::cout`

| **阶段 3** | 加一个接口 | 加 `void reverse()`：反复把元素搬到头部，逐次改指针 | 新自测通过；元素构造与析构次数都不变 |

阶段 3 是重点：`reverse` 若写成「交换两个节点的值」，元素构造次数会增加，
迭代器稳定性也会消失；两种写法的差别由自测给出。

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `list_mini.hpp` 的 `NodeBase` 与 `Node<T>` | 哨兵只用到前一半，因此它不构造元素 |
| `list_mini.hpp` 的 `transfer()` | 六处指针：先摘下来两处、再接到新位置四处；段长不进这一层 |
| `list_mini.hpp` 的 `link_in()` 与 `unlink()` | 私有插入与删除路径，边界情形不再各写一遍 |
| `list_mini.hpp` 的 `splice(pos, other, first, last)` | 改指针之外还要数一遍元素个数，为的是常数时间的 `size()` |
| `list_mini.hpp` 的 `begin() const` 与 `sentinel_node()` | 常量成员函数把哨兵交给迭代器的那一处 `const_cast`，改动不了任何节点 |
| `list_mini.hpp` 的 `create_node()` | 先构造元素再入链：构造抛异常时链还是完整的 |
| `list_mini.hpp` 的 `adopt()` | 移动构造与移动赋值共用：整链接过来，元素零构造 |
| `list_mini.cpp` 的 `count_moved()` | 用「值 + 节点地址」的日志核对迭代器稳定性 |
| `list_mini.cpp` 的 `probe_range()` | 三种 `splice` 各一个探针，表里的数字全是它们的增量 |
| `main_cli.cpp` 的 `to_console_encoding()` | 全项目唯一的编码转换点 |

## 已知问题

- `pop_back()` 与 `erase()` 用在空链上是未定义行为，项目不加检查，与标准库一致
- `splice(pos, other, first, last)` 在「`pos` 落在 `[first, last)` 之内且两条链是同一条」时
  什么都不做；标准把这种情况定为未定义行为，项目选择不动而不是给出错误结果
- `swap()` 换的是挂在两个哨兵上的节点段，因此它只对「同一种 `List<T>`」成立；
  与 `std::swap` 的默认实现相比，它不会构造或析构任何元素
- `ListIterator` 的转换构造函数允许 `iterator` 转 `const_iterator`，
  反向转换被 `enable_if` 挡住；但没有实现 `std::iterator_traits` 的特化
- 计数是全局的，多线程下不安全；教学示例固定单线程使用
- 报告里不打印节点地址，只打印「地址变了没有」——地址每次运行都不同，属于不可复现的量
- 表里的「数元素步数」统计的是 `count_range()` 走过的步数；
  别的接口（例如 `std::distance`）自己走的路不计入这个数
