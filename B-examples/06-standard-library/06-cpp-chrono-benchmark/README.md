# 示例 `06-standard-library/06-cpp-chrono-benchmark` · `<chrono>` 小基准：预热、多次测量、分位数与 `atomic` 计数（命令行）

这个示例做一个能报数的小基准工具：用 `steady_clock` 给三段纯计算计时，
先预热若干轮把结果丢掉，再正式测若干轮，最后给出最小值、最大值、中位数、P90、P99、均值与标准差。

它要回答的是「一次测量为什么不可信」。工具对每个用例同时给出**只测一次**的数值与**多次测量**的分位数，
并排在同一张表里。同一段代码在不同的时刻测，结果可以差出几倍；只报一个数，
读者无法判断那是「通常的快慢」还是「碰巧的一次」。分位数把这两件事分开：
最小值说明最好能到多少，中位数说明通常是多少，P90、P99 说明最坏的一成、百分之一有多坏。

三段被测计算分别是累加平方、试除数素数、方阵相乘。它们都用 `std::atomic<long long>` 记下自己跑了多少次迭代，
报表里打出这个计数——有了它才能确认计时区间里真的发生了计算，而不是被编译器优化掉。
工具没有图形界面：结果是一张表，命令行里看最合适。

## 这个项目要解决什么问题

随手写一个 `auto t = clock(); f(); clock() - t;` 得到的是一个数，不是结论。
这个数受四件事影响：时钟的分辨率、代码与数据是否已经在缓存里、机器上同时跑着什么、
以及被测代码本身是否稳定。这个示例把这四件事都摊开：

- 时钟：不用 `system_clock`。它是对过时的墙上时间，对时或夏令时调整会让它跳一下，
  两次读数相减可能出现负值。用单调的 `steady_clock`。
- 缓存：第一轮要把代码与数据带进缓存、把页换进来，它比后面每一轮都慢，因此先预热若干轮并把结果丢掉。
- 环境：机器上同时跑着别的进程，频率也在变，因此测多轮并报分位数，而不是报一个数。
- 代码：被测的三段计算都用 `atomic` 计数器报出自己跑了多少次，报表里能核对。

## 做完能掌握什么

- 会用 `steady_clock` 做差得到 `duration<double, std::milli>`，并说清为什么不用 `system_clock`
- 会写「预热 + 重复」的测量框架，并把单次测量与多次测量的分位数并排放出来
- 会算最小值、最大值、中位数、P90、P99、均值与标准差，并说清 P90 的定位规则
- 会用 `std::atomic<long long>` 的 `fetch_add` 统计迭代次数，并知道原子操作本身也有开销，
  因此要批量记账而不是逐次加
- 会把界面与逻辑分开：`core` 不认识 `std::cout`，报表以字符串交出去

| **阶段 3** | 加一个被测函数 | 在 `all_cases()` 里加一项（例如斐波那契递归），实现对应的 `Body`，并补一条自测核对迭代计数 | 新用例出现在表里；`--case` 能只跑它；自测项数增加且全通过 |

两次的「最小」与「中位」都在同一水平（`matrix-multiply` 分别是 0.979 / 1.003 与 0.985 / 0.998），
差别集中在「单次」与「最大」上。这正是只报一个数时会误导人的地方：
拿第一次运行的「单次」1.074 与第二次运行的「中位」0.998 相比，会得出「变快了 7%」的结论，
而两者的实际差别只是这几次采样落在分布的哪一段。

`--selftest` 只跑自测，输出就是上面「== 自测 ==」那一段，进程退出码为 0；
有任何一项不符时行首写成 `[失败]`，末行写成「N 项中 M 项通过，K 项失败」，退出码为 1。
自测**不断言任何耗时数值**，只断言统计量的结构与 `atomic` 计数器的数值，
因此换机器、换优化等级都会照常通过。

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `benchmark.cpp` 的 `measure_once` | 计时区间只包住 `item.body(...)` 一行；`now()` 取在体外，避免把测量本身算进去 |
| `benchmark.cpp` 的 `measure_case` | 顺序固定为「先测一次 → 预热若干轮并丢掉 → 正式测若干轮」；每轮之间把计数器清零，`iterations` 才是单轮的次数 |
| `benchmark.cpp` 的 `percentile` | 排序后按 `ceil(p/100 × n)` 向上取整定位；样本数少时 P99 会等于最大值，属预期 |
| `benchmark.cpp` 的 `probe_clocks` | 连续读两个时钟各 1000 次，去重后数不同值的个数；本机两者相同，因此选 `steady_clock` 的理由只能是单调性 |
| `benchmark.cpp` 的 `sum_of_squares` | 内层按 256 一段，段尾一次性 `fetch_add` 这一段的次数：逐次原子加会让计时测的是原子操作 |
| `benchmark.cpp` 的 `matrix_multiply` | 每次调用都重新分配三个方阵，分配行为本身就是方差的一个来源，报表里如实呈现 |
| `benchmark.cpp` 的 `make_report` | 三段文本都在这里拼好，调用方只负责打印；界面与逻辑因此分开 |

## 已知问题

- 全部数字来自 Debug 构建（`-g -O0`）。Release 下 `sum_of_squares` 这类循环会被优化得很不一样，
  数字不能跨优化等级比较
- 单次测量的方差主要来自内存分配与调度，而不是被测计算本身。要测纯计算，应把缓冲区移到计时区间外，
  但那会让「一轮」的含义变化，因此这里保留原样并在报表里说明
- 时钟分辨率探测只做了 1000 次连续读取。这个长度下本机的 `steady_clock` 与 `system_clock`
  分不出高下；要比较分辨率需要更长的读取序列
- `--repeat` 的上限是 1000，`--warmups` 的上限是 100。超过上限时报错退出，不会静默截断
- 迭代次数的上限是 `long long`，`matrix_multiply` 的阶数超过约 2 × 10^6 时会溢出；
  当前用例的阶数是 64，离得很远
