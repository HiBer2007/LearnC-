# 示例 `08-algorithms/04-search` · 查找：从线性到索引

一个把「查找」从线性一路测到索引的命令行程序。它把线性查找（含哨兵写法）、
二分的三种边界写法、插值查找、手写哈希索引放在各自的表上各查一遍，逐项数出比较次数、
边界判断次数、探查槽数与装载因子。

报告里的每个数字都由计数器产出，重跑逐位相同：数据在源码里就地构造，
查询按固定次序发出，没有一处依赖时钟、地址或随机种子。耗时刻意拆到 `--timing` 里，
默认运行不打一个时间数字——`0.000 ms` 与贴着时钟分辨率的结果都不适合当作结论。

六段输出各管一件事：线性与哨兵的对照、二分三种边界的比较次数、有重复值时三种写法
各自返回哪一个位置、插值查找在均匀分布与极端偏斜分布上的分岔、同一批键上哈希索引与
「排序后二分」的建索引代价与查询代价、以及所有查询的步数直方图。核心库另带 29 项自测，
每一项都拿暴力查找、恒等式或边界输入当尺子。

## 这个项目要解决什么问题

查找的第一课是「一个循环找过去」，第二课是「排好序就能折半」，第三课是
「键值可以直接算出地址」。三课的差别不在代码长短，而在代价：比了几次、探了几个槽、
建索引花了多少。项目把这三课的代价逐项测出来。

第一段测线性查找的两种写法。普通写法每轮判断两次——下标有没有越界、这个元素是不是
目标值；哨兵写法把目标值写进末尾多出来的一格，循环里只剩一次元素判断。未命中时
普通写法做了 2049 次判断（1024 次元素比较加 1025 次下标判断），哨兵写法 1025 次，
全是元素比较。代价是哨兵写法要求表可写、末尾多留一格，而且未命中时要比到哨兵本身。

第二段把二分的三种边界写法放在同一张 1000 个元素的表上。闭区间 `[lo, hi]`、
半开区间 `[lo, hi)`、下界三种写法给出同样的答案，比较次数却差出一截：命中首位时
分别比了 18、20、11 次。差别来自每轮比几次——闭区间与半开区间要判断「小于」与
「大于」两个方向，下界只判断「mid 这一格该不该被排除」，因此每轮只比一次。
三种写法的循环不变式写在报告第二段开头。

第三段把表换成有重复值的那种：每 50 个位置放同一个值。查值 500 时，闭区间返回 280、
半开区间返回 250、下界返回 250，三个下标上的值都等于 500，只有下界保证是第一次出现的
位置。「找到」这件事在有重复值时必须补上半句：找到的是哪一个。

第四段是插值查找。它不取中点，而是按值的比例估计位置。均匀分布上它一两次就命中，
二分要 9 到 10 次；换成 2 的幂那种极端偏斜的分布，查 2^40 时它比了 41 次，二分只要 7 次。
原因是值域的上半段里只落着 2^62 一个键，插值的估计位置几乎不动，每轮只把区间缩短一格。

第五段用同一批 4096 个键建两种索引：手写的开放寻址哈希表与排序后的二分。
哈希命中平均探查 1.43 次、未命中 2.50 次，二分每次要 13.00 次比较；建索引的代价反过来
——哈希插入 4096 个键共探查 5882 次，排序要比较 58132 次。同一节的最后用 64 个
同余键演示坏散列函数：它们全部落在 0 号槽上，插入合计探查 2080 次（等于 64 × 65 / 2），
换成 64 位混合散列只要 81 次。

第六段把所有查询的步数做成直方图，并把表长与装载因子列出来。线性查找在 2000 次查询上
的平均步数是 750.75，二分下界是 9.98，哈希命中是 1.43。这三个数放在一起，
就是「为什么要有索引」的全部理由。

## 做完能掌握什么

- 会写线性查找的两种写法，并能说清哨兵省下的是哪一类判断、代价又是什么
- 会写二分的三种边界写法，并各自说出循环不变式与终止条件
- 会用「每轮比几次」解释三种写法比较次数的差别，而不是只看步数
- 会说清有重复值时三种写法各自返回哪一个位置，以及为什么只有下界给出「第一个」
- 会判断插值查找在什么分布下有效、在什么分布下退化成 O(n)
- 会手写开放寻址的哈希索引，并测出插入与查找各自的探查次数
- 会用装载因子与期望探查次数核对实测值，而不是只报一个平均数
- 会说清「排序后二分」与「哈希索引」在建立代价与查询代价上的分工
- 会把查找代价做成直方图，用分布而不是单个平均数看一个查找策略

五、同一批键：哈希索引与「排序后二分」的对照
  键集：4096 个互不相同的键，由固定种子的 Lehmer 生成器产出
        （递推式 x ← 48271 × x mod 2147483647；前 4096 个建索引，后 2048 个当作不在表里的键）
  建索引的代价：
    哈希索引   表长 8192（2 的幂），装载因子 0.500，插入 4096 个键共探查 5882 次，平均 1.44 次，最坏 15 次
    排序后二分 先排一次序：比较 58132 次（std::sort，比较次数随标准库实现而变），此后不再有额外结构
  查找 4096 次，每次一个键：
    查询类别          写法          查询数    平均步数    最坏步数    平均比较    最坏比较
    在表里的键        哈希索引      2048      1.43        10          1.43        10
                      排序后二分    2048      12.00       13          13.00       14
    不在表里的键      哈希索引      2048      2.50        19          1.50        18
                      排序后二分    2048      12.00       13          13.00       14
  哈希的「步数」是探查过的槽数，「比较」只发生在槽里有键的时候：
    未命中时最后探到的是一个空槽，那一次不算键比较，因此未命中的平均比较比平均步数少 1
    装载因子 0.500 的线性探查期望值（近似公式）：命中 1.500 次探查，未命中 2.500 次探查
    实测命中平均 1.43 次、未命中平均 2.50 次，与期望值吻合
  哈希用一次乘法把查找压到常数级，代价是表长翻倍、建表要 O(n) 次探查；

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `search_lab.cpp` 的 `linear_sentinel` | 哨兵在末尾兜底，循环里只剩元素比较，「上界判断」一栏因此归零 |
| `search_lab.cpp` 的 `binary_closed` | 闭区间用带符号下标：`hi = mid − 1` 会取到 −1，用无符号会绕成最大值 |
| `search_lab.cpp` 的 `lower_bound_probe` | 每轮只比一次，收尾那次判断「找到的位置上是不是目标值」 |
| `search_lab.cpp` 的 `interpolation_search` | 区间守卫单独计数；两端重合时直接收工，挡住插值公式的除以 0 |
| `search_lab.hpp` 的 `SearchStats` | 步数、元素比较、边界判断三个量分开记，报告的每一列都能追到某个计数器 |
| `search_lab.cpp` 的 `mix64` | 64 位混合：一次乘法加两次移位；换掉它就能看到坏散列函数的后果 |
| `search_lab.cpp` 的 `HashIndex::find` | 探到空槽就说明键不在表里；空槽那一次不算键比较 |
| `search_lab.cpp` 的 `histogram_block` | 取值不超过 12 就逐值一列，超过就合并成十档，两种表格同一段代码 |
| `search_lab.cpp` 的 `display_width` | 表格按显示宽度对齐：CJK 算 2 列，否则中文列会参差 |
| `main_cli.cpp` 的 `to_console_encoding` | 全项目唯一的编码转换点：控制台是 65001 就原样输出，是 936 就转 GBK |

## 已知问题

- 报告里线性那一节用 1024 个元素、二分那一节用 1000 个元素，两节的比较次数不能跨节横比；
  第六段的直方图统一用 1000 个元素的那张表
- 第五段里 `std::sort` 的比较次数随标准库实现而变（本机 libstdc++ 是 58132 次），
  报告里那一行已经注明；换一个标准库，这个数与正文里的对照会一起变
- `HashIndex` 只支持插入与查找：没有删除（开放寻址的删除要打墓碑标记），也没有扩容，
  表长在构造时就定死；`insert` 不检查重复键，重复插入会让表里出现两份
- 装载因子固定不超过 0.5，因为表长取的是不小于 2n 的 2 的幂；期望探查次数那两个数
  来自线性探查的经典近似公式，只在散列接近随机时成立
- 插值查找要求键互不相同、且值的分布与位置大致成比例；表里有重复值时实现不会出错
  （区间守卫与两端重合的处理挡住了除以 0），但比较次数不再有保证
- 二分与插值都假定表已经升序：表没排好序时两者不会报错，只会给出没有意义的结果
- 计时数字随机器、编译器与优化等级变化，程序只打印不断言；正文给的是区间，
  两次运行都打印校验和，避免整段循环在 `-O2` 下被优化掉却不自知
