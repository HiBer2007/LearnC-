# 示例 `08-algorithms/05-sort-compare` · 比较排序：比较次数、搬移次数、递归深度与稳定性

一个把排序算法的代价逐项数出来的命令行程序。插入排序、归并排序、快速排序的两版
（朴素取首元素与三数取中）、堆排序各跑一遍，每一次元素之间的比较、每一次把元素写回数组
都记一笔；四类输入形态（随机、已排序、逆序、大量重复）各给一组数，对照表里每格是
「比较次数 / 搬移次数」。内省排序作为第六行出现，它把三数取中版加了一条深度限值，
超限就改走堆排序。

递归深度在这份报告里与比较次数地位相同，也是一等结构量。快排的退化因此有两条证据：
朴素取首元素版在已排序输入上跑到 1000 层、比较 499500 次，三数取中版在同一个输入上
只到 10 层、比较 9520 次；而换到大量重复的输入，三数取中版自己也退到 111 层，
轮到内省排序把它压回 19 层。

稳定性用带 key 的记录验，不靠记忆下结论。每组输入 200 条记录，key 取 0 到 4，
每条记着自己在输入里的原始下标；排完之后同一个 key 的记录若仍按原始下标递增，
这一组就算稳定。六种排序各跑 64 组，报告直接打出保持稳定的组数与判定。

## 这个项目要解决什么问题

排序算法的说法很多，能数出来的很少。项目先把计数口径定死，再让六种排序在同一批输入上
各跑一遍：比较次数只数元素与元素之间的比较，下标比较不算；搬移次数按元素被写进数组计，
写临时变量不算，两个下标相同的交换也不算；一次交换按三次搬移记（暂存一次、两次回写）。
口径写在报告第一段，读者可以逐条对照实现。

插入排序的表现最能说明「输入形态」这四个字的分量。同一份代码，在已排序输入上比较 999 次、
搬移 0 次——内层循环一次都没进，元素根本没被挪动过；在逆序输入上比较 499500 次、
搬移 500499 次，两个数都到了 n²/2 的量级。随机输入落在中间：比较 243570 次、
搬移 243565 次，两个数几乎相等，因为随机输入下每次比较几乎都跟着一次挪动。

归并排序的代价落在搬移上。它的四列搬移次数完全相同（都是 19952 次），一行都不差：
合并这一步不看输入是否已经有序，它只跟 n 有关。每次合并要把整段先写进缓冲区、
再写回原数组，两笔都算搬移，这就是那 19952 次的来路。

快速排序的两版放在一起看，差别只有挑 pivot 那一处。已排序输入上，首元素版每一趟都把
pivot 留在区间最左边，左边空、右边只少一个元素，于是递归深度跟着元素个数一起长到 1000 层，
比较次数正好是 n × (n - 1) / 2；三数取中版在同一个输入上深度 10 层、比较 9520 次。
规模翻倍时，首元素版的比较次数涨到四倍，三数取中版只涨两倍出头。

三数取中并不是万灵药。换到大量重复的输入，它自己也退到 111 层、比较 55740 次，
比首元素版的 52746 次还多。把输入换成全部相同的 1000 个 7 更彻底：两版都是 1000 层，
三数取中版因为每趟多花三次比较，反而成了更贵的那个（502497 次对 499500 次）。
三个候选一样大时，中位数与第一个元素没有区别。

内省排序补的就是这一块。给三数取中版加一条 2 × floor(log2 n) 层的深度限值，超限就
整段交给堆排序：四类输入里有 2 类真的触到了限值，合计切换 15 次；大量重复那一列从
55740 次、111 层压到 19743 次、19 层。切堆排序而不是归并排序，理由是堆排序最坏
O(n log n)、原地、不用额外缓冲区，而且实现里用的是迭代版下沉，切过去之后递归栈不再变深。

## 做完能掌握什么

- 会为一次排序过程定义四项结构量（比较次数、搬移次数、递归深度、切换次数），并让实现严格按口径记账
- 会解释插入排序在近乎有序的数据上为什么几乎不搬东西，并把这件事落到一行 `if (j != i)` 上
- 会算出归并排序的搬移次数为什么与输入形态无关，为什么它是 2 × n × 层数 的量级
- 会写出 Lomuto 划分，并能数出它每趟恰好做区间长度减一次比较
- 会用三数取中挡住已排序与逆序输入，并能说出它在大量重复与全部相同的输入上为什么失效
- 会写迭代版下沉的堆排序，并说清它当兜底的三个理由：最坏 O(n log n)、原地、不占递归栈
- 会实现内省排序：深度预算每层减一，归零就换堆排序
- 会用带 key 的记录把稳定性验出来，并知道这个判定的方向是不对称的

## 阶段推进

| 阶段 | 目标 | 做什么 | 怎么验收 |

| **阶段 1** | 跑通命令行版 | 配置、编译，运行 `build\mingw\bin\app_cli.exe` | 看到六段项目输出与「29 项中 29 项通过，全部通过」 |

| **阶段 3** | 让三数取中在重复元素上也站得住 | 把 `partition_lomuto` 换成三路划分：小于、等于、大于各成一段 | 报告「大量重复」那一列的两个快排版数字都比改之前小，深度回到限值以内 |
| **阶段 4** | 换一档深度限值 | 把 `intro_sort` 的限值从 `depth_limit_for(a.size())` 改成 4 | 报告第二段内省排序那一行的比较次数明显变大，自测第 16 项转为不符——限值调小是拿比较次数换深度，这笔账在报告里能看见 |

阶段 3 是重点：三路划分改完之后，报告第二段的「大量重复」列会立刻给出改动的效果，
不必另写测试程序。

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `sort_compare.cpp` 的 `less_than` / `put` / `swap_at` | 三个计数工具：比较、写入、交换各只在一处记账，排序代码里不会漏记 |
| `sort_compare.cpp` 的 `insertion_range` | `if (j != i)` 让已排序输入的搬移次数落在 0 上：位置没变就不回写 |
| `sort_compare.cpp` 的 `merge_range` | 相等时先取左半边，归并排序的稳定性就靠这一行；先写进缓冲区再写回，搬移因此是两倍 |
| `sort_compare.cpp` 的 `partition_lomuto` | 比较次数恰好是区间长度减一；`swap_at` 跳过自交换，已排序输入上因此一次都不搬 |
| `sort_compare.cpp` 的 `median3_index` | 三次比较把中位数换到 mid 上，再换到区间头上，复用同一套 Lomuto |
| `sort_compare.cpp` 的 `sift_down_range` | 迭代版下沉：堆排序不占递归栈，切过来之后深度不会接着长 |
| `sort_compare.cpp` 的 `intro_range` | 深度预算每层减一，归零就让 `heap_sort_range` 整段接管 |
| `sort_compare.cpp` 的 `Lcg` | 自带的线性同余发生器：`std::uniform_int_distribution` 的输出随实现而变，报告不能依赖它 |
| `sort_compare.cpp` 的 `first_stability_violation` | 同 key 的记录排完之后是挨着的，逐段看 origin 是否递增即可 |
| `sort_compare.cpp` 的 `display_width` | 表格按显示宽度对齐：CJK 与全角标点算 2 列，否则中文列会参差 |
| `main_cli.cpp` 的 `to_console_encoding` | 全项目唯一的编码转换点：控制台是 65001 就原样输出，是 936 就转 GBK |
| `sort_compare.hpp` 的 `Stats` | 四项结构量集中在一个结构里，报告与自测读的是同一份数 |

## 已知问题

- 报告给的是具体输入上的结构量，不是渐近界：换一个 n、换一个种子，数字就变。
  大 O 记号要靠这些数字自己推，程序不替读者推
- 两个快排版都用 Lomuto 划分（单指针），不是 Hoare 划分。Hoare 划分与三路划分在重复元素多的
  输入上分得更均匀，本示例没有实现这两版，也没有给出它们的数字，阶段 3 把三路划分留作练习
- 归并排序每次合并都要把整段写回原数组，搬移次数因此是 2 × n × 层数 的量级；
  用两块缓冲区来回倒可以省掉一半写回，本示例没有做这个优化
- 「大量重复」的取值是 0 到 9 十个，不是全部相同。全部相同的那一种更极端，
  报告第四段单独给了两行，但没有做成第五列
- 深度按调用层数数，不是从栈指针测出来的字节数。换编译器、换优化等级，真实栈用量会变，
  这里的数字不变
- 报告里没有时间。比较次数相同的两种排序，实际耗时仍可能不同（缓存命中、分支预测），
  要比较耗时得另开计时实验，并且要留意 `-O2` 之下计数代码被优化掉的风险
- 逆序输入的构造是 (n - i) × 3，值域随 n 变化；拿它与随机输入比数值大小没有意义，
  比的是结构量
- 稳定性那一节每组 200 条记录、64 组输入。判定为不稳定，一组反例就够；
  判定为稳定只是「这 64 组里没出错」，不是数学证明
- 内省排序的深度限值取 2 × floor(log2 n)。限值取小了切换频繁、比较次数上升
  （报告第四段给出限值压到 4 的那一行：比较次数从 9520 涨到 13046），
  取大了兜底来得太晚，这个取舍由读者按场景定
