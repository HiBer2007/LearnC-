# 示例 `08-algorithms/03-varargs` · 不定参数：从 printf 到可变模板

一个把「个数不定的实参」这件事从 C 讲到 C++ 的命令行程序。第一段用 `va_list` 手写两个函数，
一个把一串 `int` 加起来，一个认得 `%d`、`%s`、`%f` 的极简格式化函数。第二段把默认实参提升
摆到台面上：`float` 进省略号之前已经变成 `double`，比 `int` 窄的整型已经变成 `int`，
读的时候用错宽度就是未定义行为。第三段换成 C++ 的写法：可变参数模板与 C++17 的折叠表达式。
第四段拿 `std::initializer_list` 做对照，用会记账的元素类型数出拷贝与移动各发生了几次。

报告里的每个数字都来自计数器：`va_start` 与 `va_arg` 被调用了多少次、格式串里消耗实参的
转换说明有几个、模板函数进了几次、元素被拷了几次、移了几次。重跑逐位相同，一个都不是估的。
地址、时钟、随机数一个都不出现。

第二段那三行读数是**未定义行为**，写出来是为了让人看见它长什么样：本机 `g++ 16.2.0`（x64）
上读到的位模式逐位记在报告里。换编译器、换平台、换优化等级都可能得到别的数。程序用它们说明
「为什么不能这么写」，自测里只把这几个读数当成现场记录核对一遍，不靠它们得出结论。

## 这个项目要解决什么问题

`printf` 的用法很常见，难的是它为什么能这么用，以及照它的样子自己写一个要注意什么。
项目把这些问题拆成五段可以逐行核对的输出。

第一件是「个数从哪里来」。`sum_ints(count, ...)` 的个数由调用方单独传进来，函数完全照它读：
同一批实参 `1 2 3 4`，`count` 传 2 得 3、传 3 得 6、传 4 得 10。传少了，多出来的实参被忽略；
传多了就是未定义行为。`format_small` 换一种办法定位实参：个数由格式串里的转换说明决定，
`%d` 取一个 `int`、`%f` 取一个 `double`、`%s` 取一个 `const char *`，`%%` 输出一个百分号
且不消耗实参。报告里每个格式串后面都跟着「消耗实参的转换说明几个、`va_arg` 调用几次」，
两列始终相等。

第二件是类型。这一段的结论和不少资料写的不一样：**直接传 `float`、用 `va_arg(ap, double)` 读，
并不是未定义行为**。匹配省略号的实参先做默认实参提升，`float` 在进入函数之前就已经是 `double`，
所以「传 1.5f」与「先 `static_cast<double>` 再传」读出来的位模式都是 `3FF8000000000000`。
真正会出事的是读的类型与实际传的类型不一致，报告里给了三行本机读数：

- 绕开提升之后按 `double` 读：传 `1.5f` 与 `7`，读到的位模式是 `0000000000000007`，
  也就是同一个调用里第二个实参那 8 字节被当成 `double` 解释的结果
- 传 `1.1f`（提升后是 `3FF19999A0000000`）按 `int` 读：只取低 4 字节，读到 `A0000000`
- 传 `1` 按 `long long` 读：多读 4 字节，本机那 4 字节恰好是全零，于是读出来「对」

第三行是最值得记住的一行：未定义行为不保证看得出来，只保证不用保证。

> [!CAUTION]
> 第二段那三行是未定义行为在本机上的样子，不是可以依赖的结果。
> 同样的代码换编译器、换平台、换优化等级都可能读出别的数，甚至直接崩。
> 程序把它们打印出来只为了说明「为什么不能这么写」。

第三件是 C++ 的写法。同样是 4 个实参求和，递归展开的写法要两个同名的函数模板
（一个基线、一个递归），整包进去要进 4 次函数；C++17 的折叠表达式一个模板就够，
`return (0 + ... + args);` 整包只进 1 次。两者结果相同，模板重载个数与进入函数的次数
都数在报告第三段里。同一个 `sum_all` 还能吃下 `int` 与 `double` 混着写：
`sum_all(1, 2.5, 3)` 是 `6.5`。异构类型的渲染交给 `print_all`，`bool` 打 `true`／`false`，
其余按自己的规则进流。

第四件是 `std::initializer_list` 的对照。用一个拷贝构造与移动构造都记账的 `Counter`，
三条对照各自有数：

| 对照项 | `va_list` | 可变参数模板 | `initializer_list` |
|---|---|---|---|
| 元素拷贝与移动 | 0／0，不构造对象 | 0／0，形参直接构造 | 右值列表 0／0；左值列表 3／0；传入已有列表 0／0 |
| 能不能接受不同类型 | 能，但读的时候不做类型检查 | 能，每个实参一个类型 | 不能，一个列表只有一种元素类型 |
| 个数什么时候定下来 | 运行期，是调用方传进去的值 | 编译期，个数不同就是不同的实例 | 调用点，大括号里写几个就是几个 |

「能不能接受不同类型」这一条在命令行版里只演示了合法的那一半：`int` 放进 `long long`
列表算加宽，`sum_il({1, 2, 3})` 照常编过。混进 `double` 就编不过：把 `sum_il({1, 2.5})`
写进一个小文件单独编译（`g++ -std=c++17 -c`），GCC 16.2.0 给的原话是：

## 做完能掌握什么

- 会写出配对的 `va_start`／`va_arg`／`va_end`，并说清为什么个数必须由调用方另传
- 会手写一个认 `%d`、`%s`、`%f`、`%%` 的格式化函数，并知道 `%s` 遇到整数会发生什么
- 会说清默认实参提升把 `float` 变成 `double`、把比 `int` 窄的整型变成 `int`，
  并知道「传 `float` 按 `double` 读」为什么不是未定义行为
- 会指出 `va_arg` 的类型与实际实参不一致时是未定义行为，并知道这类读数不可当结论用
- 会写 C++17 的折叠表达式求和，并说清它比 C++11 的递归展开省了什么
- 会用 `if constexpr` 给异构实参各写一条渲染规则
- 会数出 `initializer_list` 在右值、左值、传入已有列表三种情形下各拷贝了几次
- 会说清这三种写法各自把「个数」定在什么时刻

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `varargs_lab.cpp` 的 `sum_ints` | 三件套各占一行；循环次数就是 `va_arg` 的调用次数，个数由参数说了算 |
| `varargs_lab.cpp` 的 `format_small` | 边走格式串边取实参：认不出来的说明原样输出且不消耗实参 |
| `varargs_lab.cpp` 的 `read_double_arg` | 按 `double` 读；调用点直接传 `float` 时提升已经替它做完了转换 |
| `varargs_lab.cpp` 的 `read_double_bypassing_promotion` | 只有让调用点「以为形参是 `float`」，4 字节的 `float` 才真的按 4 字节进参数区 |
| `varargs_lab.cpp` 的 `bits_of` 四个重载 | 位模式用 `memcpy` 取，宽度由类型自己定，不猜 |
| `varargs_lab.hpp` 的 `sum_all` | `return (0 + ... + args);`：二元右折叠，空包与异构都能用 |
| `varargs_lab.hpp` 的 `sum_rec` 两个重载 | C++11 的写法：基线一个、递归一个，整包要进 N 次函数 |

## 已知问题

- 报告第二段那三行 UB 读数绑在本机这套参数传递约定上（Windows x64）。自测第 16 至 18 项
  断言的正是这三行的位模式：本机两套工具链（MinGW-w64 的 `g++ 16.2.0` 与 cl 19.44）读数相同，
  但换到 Linux（System V 的约定）或别的 ABI 就可能不同，届时这三条自测会失败。
  这不是代码坏了，而是这三条断言本来就只对本机成立，换平台时用本机重测的数替换即可；
  本次没有在 Linux 或虚拟机上跑过这一版，跨平台的对照数据一条都没有
- 绕开提升那一处用 `reinterpret_cast` 换了一个函数指针类型再调用，用不兼容的函数类型调用
  本身也是未定义行为。它存在的唯一目的是让 4 字节的 `float` 真的进参数区。
  `-Wall -Wextra` 会因此报 `-Wcast-function-type`，代码里用 `#pragma GCC diagnostic` 就地关掉，
  并注明了原因
- 反方向的写法（`va_arg(ap, float)` 去读一个 `double`）GCC 直接拦住：
  编译期给 `warning: 'float' is promoted to 'double' when passed through '...'`，
  并提示 `if this code is reached, the program will abort`；本机实测把这一版跑起来，
  进程以非法指令终止，退出码 `0xC000001D`（`0xC000001D` 是 Windows 的
  `STATUS_ILLEGAL_INSTRUCTION`）。因此程序里没有这一版，只在源码注释与这里记下它的下场
- `format_small` 只认 `%d`、`%s`、`%f` 与 `%%`，不支持宽度与精度：`%.3f` 会被当成认不出来的
  说明原样输出。这一点与 `printf` 不同，`printf` 会照它的规则处理
- `%s` 遇到非字符串实参（例如整数）会把这个整数当成地址去解引用，是未定义行为，程序里不演示
- 计数用的是全局变量，多线程下不安全；教学示例固定单线程使用
- 报告第四段的 `kept` 是局部变量，底层数组与它同生共死；`initializer_list` 一旦跨出这个
  生存期（例如把它当返回值带出去）就悬垂，这一条见
  《08-一些散落的算法/03-不定参数：从 printf 到可变模板.md》章节
- `sum_all` 与 `sum_rec` 的返回类型由实参自己决定：`sum_all(1, 2.5, 3)` 返回 `double`，
  `sum_all(1, 2)` 返回 `int`。两者结果相同这一条只在整型实参上验过（自测第 22 项）
- 「模板重载个数」是读自源码的常量（递归展开 2、折叠 1），不是运行期数出来的；
  报告第三段的另外两列（进入函数次数与结果）才是计数器与实算的结果
