# 示例 `08-algorithms/10-string-match` · 字符串匹配：朴素、KMP 与 Rabin–Karp，以及按字节还是按码点

一个把字符串匹配拆开看的命令行程序：同一段文本分别交给朴素匹配、KMP 与 Rabin–Karp，
各自数出比较次数、失配表取值、哈希命中次数与碰撞次数；同一段中文文本再按字节与按码点各跑一遍，
给出两种口径下的匹配位置。报告里的每个数字都由计数器数出来，重跑逐位相同，一个都不是估的。

三种算法回答同一个问题：模式在文本里出现在哪些位置，差别在代价怎么算。朴素匹配把每个对齐位置
都比一遍，最坏输入要比较 (n − m + 1) × m 次；KMP 先花一遍比较建出失配表，匹配阶段文本下标不再
回退；Rabin–Karp 用滚动哈希先筛一遍，只有哈希相等的窗口才逐字符复核。三者并排放在报告里，
可以看出失配表不是白拿的，也可以看出复核这一步不能省。

中文那一段处理的是另一种问题。一段 UTF-8 文本既可以按字节读，也可以先解码再按码点读，
两种读法给出的位置单位不同；用 `substr` 按字节切出来的「模式」在字符层面根本不存在，
按字节却能找到位置，而且位置可能落在某个字符的中间。程序把这两类位置一并列出，
逐处指出它是不是字符边界。

## 这个项目要解决什么问题

第一个问题是朴素匹配的代价上界到底是多少。报告第一段的 (2) 组用 32 个 `'a'` 找 `"aaab"`：
29 个对齐位置每个都比满 4 次，比较次数 116，恰好等于 (n − m + 1) × m。教科书里写的上界
`n × m` = 128 多算了 12 次，那 12 次来自最后 m − 1 = 3 个对齐位置——它们根本不足一个模式长，
实现到 n − m 就停了。把同一形状放大到 512 个 `'a'` 找 63 个 `'a'` 加一个 `'b'`，
比较次数 28736 = 449 × 64，而这段文本里模式一次都没出现。

第二个问题是 KMP 省下来的到底是什么。报告第二段把失配表的构建比较次数与匹配阶段的比较次数
分开数：`"aaab"` 的失配表是 0 1 2 0，构建只比了 5 次，匹配比了 61 次，合计 66 次，朴素是
116 次，差别只有 1.76 倍。放大版上差距拉开到 26.46 倍（1086 对 28736），因为 m 变大了：
朴素每换一个对齐位置就要从头比一遍模式，KMP 只回退模式，文本下标一直往前走。
报告里还能看到 `"the"` 那一组合计 45 次、朴素 45 次——典型文本上失配表并没有赚回成本。

第三个问题是 Rabin–Karp 里「哈希相等」与「字符串相等」的距离。报告第三段的 (1) 组在 43 字节
英文里找 `"the"`：41 个窗口，从头算哈希 2 次（模式一次、首个窗口一次），此后 40 次都是 O(1)
滚动；如果不滚动、每个窗口都从头乘一遍，要 123 次乘法。命中 2 次、复核 2 次、碰撞 0 次。
(2) 组把模数压到 8，用 6 字节文本 `"baaabc"` 找 `"abc"`：4 个窗口的哈希依次是 2 1 2 2，
命中 3 次、复核 3 次、碰撞 2 次，真正的匹配只有偏移 3 那一处。两处碰撞的窗口分别是
`"baa"` 与 `"aab"`，哈希都与模式相同，复核把它们挡了回去。(3) 组让进制与模数都等于 31，
`b mod q` 变成 0，哈希退化成只看窗口最后一个字符：34 个窗口里 12 个以 `'c'` 结尾，
全部命中，12 次复核全部失败，匹配 0 处，而答案依旧是对的——复核这一步保住了正确性。

第四个问题是中文文本的两种读法。报告第四段用的文本是 44 字节、20 个码点，模式 `"字符串"`
是 9 字节、3 个码点。按字节匹配给出位置 0 与 21，按码点匹配给出 0 与 7，两种口径各记一个位置，
换算要对齐字符边界，不能靠乘法。真正的麻烦在模式本身：取文本的第 1 到第 3 个字节得到的片段
`AD 97 E7`，按字节搜索在偏移 1 与 22 两处命中，而这两处都落在某个字符的内部——偏移 1 在
第 0 个字符里，偏移 22 在第 7 个字符里；这段片段按 UTF-8 解码在第一个字节就失败，
码点口径里根本不存在这个模式。

## 做完能掌握什么

- 会说出朴素匹配比较次数的两个上界 (n − m + 1) × m 与 n × m 差在哪里
- 会手算一个模式的失配表，并用它解释匹配阶段为什么不用回退文本下标
- 会用「构建 + 匹配」两段比较次数评价 KMP，而不是只看匹配那一段
- 会写滚动哈希的更新式，并说清「从头算」「滚动」「逐窗重算」三种代价的差别
- 会解释哈希命中之后为什么必须逐字符复核，并能用小模数造出一次碰撞
- 会说明进制与模数有公因子时哈希退化成什么样，以及为什么答案仍然正确
- 会在字节与码点两种口径之间换算位置，并判断一处位置是否落在字符边界上
- 会指出用 `substr` 按字节切出来的模式为什么在字符层面不成立

## 已知问题

- 码点口径只做了朴素与 KMP 两版，没有做 Rabin–Karp 的码点版；哈希那一段全部按字节跑
- 哈希的乘法先抬到 64 位再取模，模数超过 2 的 32 次方时中间积会溢出；报告里用到的最大模数是 1000003
- (1) 组碰撞 0 次是「模数够大、文本够短」的结果，不是「不会碰撞」的证明；
  窗口足够多时大模数同样会碰
- 「合法 UTF-8 模式不会命中在非字符边界上」这条只对合法 UTF-8 成立；
  用 `substr` 按字节切出来的片段不受这条保护，正是报告第四段演示的那一类
- 报告里的位置都从 0 起算；`byte_offset` 末尾补了一个哨兵，`is_boundary` 把 `bytes.size()`
  也算作边界，方便定位文本末尾的子串
- 文本与模式都写在源码里，改文本要改代码重编；程序不读外部文件，也不接受命令行传入的模式
- 自测里的伪随机文本来自固定种子的线性同余发生器，换种子会换数据，结果依旧可复现
- 报告里没有任何耗时数字，全部是结构量；要比较三种算法的运行时间，得自己另加计时
