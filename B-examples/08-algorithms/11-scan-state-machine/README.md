# 示例 `08-algorithms/11-scan-state-machine` · 扫描与状态机：一个状态机的三种写法

一个把状态机拆开看的命令行程序：同一台剥 JSON 注释的状态机，分别写成 switch、
二维转移表与函数指针表三种形态，对同一份输入给出逐位相同的输出，各自数出扫描步数、
状态转移次数与走到过的表格格子。报告里的每个数字都由计数器产出，重跑逐位相同。

程序要办的事很小：把 JSONC 文本里的注释换成空格。难点在「哪两个斜杠才算注释开头」。
朴素做法直接查找两条斜杠再删到行尾，会把 `"https://example.com"` 里的斜杠当成注释，
网址连同后面的真注释一起被删掉；状态机做法只维护「在不在字符串里」与一个转义状态，
逐字节走一遍就绕开了这个错误，不预读、不回退。

注释换成空格而不是删掉，是为了让处理前后的字节数相同、行列号不变。报告里打印了
处理前后的长度、行数与同一处标记的行列号，也给出朴素做法之后标记跑到了哪一行。
末尾单个反斜杠那一段说明：扫描器只看当前字节，越界保护本来就不需要写。

## 这个项目要解决什么问题

三件事各用一段输出钉住。

第一件是「同一台机器可以有三种写法」。状态机一旦写成转移表，它就是一串数据；
写成 switch 或者一组处理函数，它就是一串代码。项目把三种写法放在一起：先穷举
63 个 (状态, 输入类) 组合比对转移，再让三者跑同一份输入比对输出与结构量。
三种写法的差别不在运行结果，而在改动成本：加一个状态，表驱动只要加一行，
switch 要加一个 case，函数指针表要加一个函数加一个数组项；加一个要单独处理的
输入字符，三种写法都要在 9 处转移描述里各补一条。

第二件是「先查找再删除」错在哪。`strip_comments_naive` 走的是最自然的思路：
找块注释起点删到终点，再找行注释起点删到行尾。它在主样例上把
`https://example.com/docs//index.html` 从第一个 `//` 处截断，输出从 390 字节
掉到 148 字节，行数也从 9 行变成 8 行。状态机做法对这同一份输入给出 390 字节的
输出，网址一个字节没动，被换掉的 190 个字节全部落在注释里。

第三件是「换掉而不是删掉」。注释里的字节换成空格之后，输出与输入等长，
块注释跨的那两行也照旧占两行，因此标记 `@@` 的行列号在处理前后都是第 8 行第 14 列；
朴素做法删掉字节之后，同一个标记跑到了第 7 行。报告第四段把这些数字并排摆出来。

## 做完能掌握什么

- 会写出状态机的四个零件，并能把一台机器的转移写成一张二维表
- 会用 switch、转移表、函数指针表三种写法实现同一台机器，并说明各自的改动成本
- 会解释「查找并删除」为什么处理不了字符串里的注释符号
- 会写出逐字节扫描的剥注释器：只维护在不在字符串里、是哪种引号、有没有转义
- 会说明为什么注释要换成空格而不是删掉，以及位置信息对报错有什么用
- 会指出预读式写法里 `i + 1 < n` 这一行挡掉的是哪种输入
- 会把扫描器的步数、转移次数、被替换字节数记下来，作为可复现的结构量

找不到就说明读表的方式错了。

## 已知问题

- 扫描器按字节走，不按 Unicode 码点走：主样例 390 字节里，一个汉字算三步。
  要在码点层面工作，得先解码再扫描，位置换算也跟着变成码点与字节两套
- `copy_with_escape` 不带保护的那一版依赖 C++ 对 `s[s.size()]` 返回结尾空字符的保证
  （读它是良定义的），因此演示才没有踩到未定义行为；输入换成 `const char*` 时，
  这一次读取就越过了缓冲区末尾，属于未定义行为
- 注释换成空格后行尾会留下成片的空格：报告里用竖线把行夹起来才看得见，
  正文与 README 里的行尾空格会被编辑器或 Git 处理掉，抄的时候要留意
- 只认 `\n` 作换行：CRLF 文本里 `\r` 会被当成普通字节，落在注释里就换成空格，
  长度与行列号仍然不变，但行尾会多一个空格
- 未闭合的字符串与未闭合的块注释都不报错：扫描器只管剥注释，语法检查不在范围内，
  它只会停在对应的状态上（例如「双引号转义」或「块注释」）
- 单引号串按字符串处理，JSON 本身只有双引号；保留它是为了说明「引号类型」也是状态的一部分
- 旧稿 A4 的 `reserve` 耗时对照不在本示例里：本示例的输出全部是可逐位复现的结构量，
  计时数字不适合放进 `实测数据` 块，因此不设 `--timing`
