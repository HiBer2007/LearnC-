# 示例 `08-algorithms/06-sort-noncompare` · 计数、基数与桶排序：不比较也能排

一个把三种非比较排序摆在一起对照的命令行程序。计数排序、基数排序（LSD）与桶排序
各自怎么把键换算成下标，各自的前提是什么，代价落在哪一列，报告逐列给出。
报告里的每个数字都由计数器数出来：元素被读了几次、写了几次、桶内比较了几次、
辅助数组有几个、占多少槽、多少字节、分配了几次，重跑逐位相同，一个都不是估的。

三种排序都把「比较」这件事从主循环里拿掉了，代价换成了别的东西。计数排序用一段
与键域等宽的计数数组换掉比较，键域一宽空间就跟着涨；基数排序把键拆成定长的数位，
一趟只看一个数位，键域再宽也不怕，代价是趟数；桶排序先把键分进若干个桶，
桶内仍要靠比较收尾，键的分布因此直接写进了它的代价公式。

报告用两处退化把这两条边界摆出来。一批 16 个键从 [0, 31] 整体加到 [1000000, ...] 之后，
元素一个没多、计数数组从 32 槽变成 1048576 槽。64 个键从均匀分布换成全部挤进同一个桶
并且逆序之后，桶内比较从 163 次变成 2016 次，后者正好是 n(n − 1) / 2。
稳定性那一段拿同一批 12 条记录做两趟排序：先按次键、再按主键，两趟都用稳定版
得到「主键优先、次键次之」的次序，两趟都换成不稳定版就只剩主键还对。

## 这个项目要解决什么问题

「不比较也能排」这句话本身没有信息量，有用的是它换来了什么、又付出了什么。
项目把三笔账并排放在报告第一段：同样 32 个键，计数排序读 64 次写 32 次、
辅助 8136 字节；基数排序读 128 次写 64 次、辅助 2304 字节；桶排序读 138 次写 91 次、
辅助 264 字节，另外还有 50 次桶内比较。读写的次数、空间的字节数、比较的次数
三列各不相同，没有一种在三列上都占优。

第二段回答「各自的前提是什么」。计数排序要求整数键，而且键域上下界已知、宽度可控，
它的空间只由键域决定，与元素个数无关——把同一批 16 个键整体加 1000000，
计数数组就从 32 槽涨到 1048576 槽，落进去的键至多 16 个，其余全是空槽。
桶排序对键域没有要求，却要求键的分布接近均匀：64 个键均匀撒在 [0, 999] 上、
分 8 个桶时，桶内比较 163 次；换成全部落进第 0 个桶并且严格递减，
插入排序就退化成 n(n − 1) / 2 = 2016 次。同一份代码、同一批规模，
差别只在键怎么分布。

第三段是多关键字排序。一批记录有主键和次键，要按「主键优先、次键次之」排，
做法是先按次键排一趟、再按主键排一趟——这正是 LSD 基数排序的思路。
项目把同一趟排序写成两个版本：稳定版的落点在各段内从前往后走，
不稳定版的落点从后往前。两版排出来的数组都按主键有序，
但只有稳定版保住第一趟排好的次键次序。报告把 12 条记录的两种结果并排打印，
每一步都能对上：做法 B 的每一条记录都还在，只是同一主键的那几段被翻了过来。

## 做完能掌握什么

- 会说出三种非比较排序各自把「比较」换成了什么，以及换来的代价落在哪一列
- 会写出稳定的计数排序，并能指出「前缀和给起点、取值与落点同向」这两件事缺一不可
- 会用一次不稳定的写法把同一段代码变成不稳定的，并解释稳定性丢在哪一行
- 会按最大键算出 LSD 基数排序的趟数，并说清为什么每一趟都必须稳定
- 会写出桶排序的两遍分发骨架，并把桶内排序的比较次数单独记下来
- 会构造退化输入：键域远大于元素个数的计数排序、分布极偏的桶排序
- 会用「先次键、后主键」的两趟稳定排序完成多关键字排序，并知道它比打包成一个键强在哪
- 会把结构量集中在一个 `SortStats` 里，让报告与自测读同一份数

## 阶段推进

| 阶段 | 目标 | 做什么 | 怎么验收 |
|---|---|---|---|
| **阶段 1** | 跑通命令行版 | 配置、编译，运行 `build\mingw\bin\app_cli.exe` | 看到四段项目输出与「31 项中 31 项通过，全部通过」 |
| **阶段 2** | 看懂两版落点方式的差别 | 读 `counting_sort_impl` 的 `if (stability == ...)` 两个分支 | 能说清报告第三段做法 B 的那几段次序是在哪一行被翻过来的 |
| **阶段 3** | 把不稳定版改回稳定版 | 把不稳定分支的前缀和改成起点、落点改成 `count[key]++` | 自测第 26 项从「次键乱了」变成满足有序性 |
| **阶段 4** | 换一个基数 | 把 `radix_sort_lsd` 的 `base` 从 256 改成 16，趟数改成按 4 位算 | 报告第四段的趟数从 2 变成 3，结果仍与 `std::stable_sort` 相同 |

阶段 3 是重点：把落点方向改回去之后，报告第三段的两列会立刻变成一样，
不必等到别处出错才发现稳定性丢了。

## 已知问题

- 三种排序都要求每个键落在调用方给出的键域之内。越界的键会算出越界的下标，
  这是调用方的责任，代码里不做检查：计数排序会越界写计数数组，桶排序会算出越界的桶号。
  Debug 版下 MinGW 的 libstdc++ 带边界断言，会直接停下；Release 版与 MSVC 下不会
- `Key` 固定是 `unsigned int`。要排 64 位键就得改这个别名，并同时改
  `radix_sort_lsd` 里 `base` 与 `shift` 的推进方式；趟数上限现在是 4
- `bucket_of` 用一次乘法加一次除法算桶号，键域宽度乘以桶数超过 `std::size_t` 时会回绕。
  演示里的量级离这个边界很远
- 报告里的「辅助字节」按「槽数 × 元素宽度」算，不含 `std::vector` 自身的对象头，
  也不含桶排序里那几个桶的对象开销；换一个分配器，真实的字节数会变
- 桶排序的桶内用的是插入排序。换别的排序会改变「桶内比较」这一列，
  但不会改变结论：分布偏斜时最满的那个桶决定了总的代价
- 报告第三段只有主键与次键两列。三列及以上照样是「从最低位一路排到最高位」，
  但要把每一趟的中间结果都留一份，辅助空间会成倍上涨
- 演示数据由固定种子的线性同余发生器就地构造，不读外部文件。
  换一个种子，桶排序那几列会变，计数排序与基数排序的读写次数不变
