# 示例 `08-algorithms/01-recursion` · 递归：三件套、三种错法与三种改法

一个把递归拆开看的命令行程序：三件套（基线、推进、合并）各是什么，三种常见错法
各自错在哪，递归改迭代的三种手法怎么落到代码上。报告里的每个数字都由计数器数出来：
节点数、叶子数、树高、每层节点数、push 与 pop 次数、迭代次数、移动次数，
重跑逐位相同，一个都不是估的。

程序把递归树当成一等对象对待。同一棵树，可以交给调用栈走，也可以搬到堆上的
`std::vector` 里走（显式栈），还可以把中间结果放进参数（累加器），
或者把「走到哪一步」也写进帧里（状态机）。三种改法在报告里各自给出结构量，
可以逐列对照：节点数不变，树高变了，迭代次数变了。

三种错法不能真跑——它们不收敛——因此改用显式栈模拟，并给出步数预算。
报告里写的是「走满 20000 步仍未命中基线」，而不是某一次崩溃的记录。

## 这个项目要解决什么问题

递归的写法很短，短到容易跳过三件套里的任何一件。项目把三件套各用一段输出钉住。

第一件是基线。基线只有一个条件，写错一个等号就会变成不收敛的递归。
报告第三段用显式栈模拟两版错法：基线写成 `n == 1` 的那版从 0 出发越走越远，
推进写成 `n + 1` 的那版从 10 出发越走越远，两版都在 20000 步预算内一次基线都没碰到，
而正确版走 fib(15) 只用 1973 步，第 8 步就命中第一个基线。

第二件是推进。推进必须让规模靠近基线，`sum_to` 每次把 n 减一，
`fib_naive` 每次把 n 减一或减二，两者都能收敛。

第三件是合并。合并错最隐蔽：递归树的形状、节点数、层数全部正确，答案却是错的。
`sum_drop_level(100)` 与 `sum_to(100)` 都是 101 个节点、100 层，
前者返回 0，后者返回 5050，差别只在「本层的 n 有没有加上去」这一行。

改法那一段给出三种写法的结构量。显式栈版的 push 次数与递归版的节点数逐位相同
（fib(20) 都是 21891），栈最深 20 帧等于树高加一；累加器版把层数从 100 降到 100 次迭代
（写成尾递归不等于编译器会折叠它）；状态机版的移动序列与递归版逐位相同，
每一步都经过合法性检查。

## 做完能掌握什么

- 会说出三件套各自的作用，并能指出一段递归代码里哪一行属于哪一件
- 会数一棵递归树的节点数、叶子数、树高与每层节点数，并用恒等式自我检查
- 会解释为什么「节点数 = 2 × 叶子数 − 1」对满二叉递归树成立
- 会用显式栈把递归改成迭代，并能说清帧里为什么需要 `phase`
- 会写累加器版，并知道尾递归在 C++ 里不保证被优化成循环
- 会用状态机版处理「一趟只走一步」的场景
- 会在真跑之前先把不收敛的版本改成带预算的模拟，而不是让它去爆栈

## 已知问题

- 错法那一节的「不收敛」是**模拟**出来的结论：真跑那两版会一直递归到栈溢出，
  崩溃点随编译器与优化等级变化，不适合当作可复现的数字，因此改用带预算的显式栈模拟
- `run_with_budget` 一次只找第一个基线，不走完整棵树；要拿整棵树的节点数看第二段
- 累加器版的「层数」是计数器数出来的调用层数，不是从栈指针测出来的字节数；
  换一个编译器、换一个优化等级，真实栈用量会变，这里的数字不变
- 报告只覆盖 `int` 规模的 n；`fib_tree_stats` 的节点数按 n 指数增长，
  n 超过 30 之后运行时间会明显变长
- 汉诺塔状态机版在每帧里存了四个 `int`，帧比递归版大；
  状态机的价值在于可以随时暂停与单步，不在于省内存
