# 示例 `08-algorithms/09-greedy-dp` · 贪心与动态规划：同一道题的两条路

一个把贪心与动态规划摆在一起对照的命令行程序。同一道零钱兑换题分别用贪心与 DP
各解一次，两边各挑出哪些硬币、各用多少枚、差多少，全部打出来；贪心的反例
（面额 `{1, 3, 4}` 凑 6，贪心 3 枚、最优 2 枚）与贪心成立的例子（面额成倍数关系）
并排给出，再用 3840 个组合的穷举扫描说明「什么时候能贪」。

第二段换成最长上升子序列，同一道题写四种实现、三族状态定义：以下标结尾、
以值结尾、以长度做下标。四种实现必须给出同一个长度，代价却不一样，报告里
逐列给出状态槽位、用到的格子、转移次数与比较次数。第三段把 0/1 背包的二维表
改成滚动数组，字节数一律用 `sizeof` 现算，并解释内层循环为什么必须反过来。

报告里的每个数字都由计数器数出来：贪心步数、面额探查次数、状态数、转移次数、
比较次数、字节数，重跑逐位相同，一个都不是估的。凑不出的金额、方向写反的内层
循环这类边界也各给一个数，不留空白。

## 这个项目要解决什么问题

贪心写起来比 DP 短得多，短到容易忘记问一句「这样取真的最优吗」。项目把这个问题
做成三组可以逐行对照的输出。面额 `{1, 3, 4}` 凑 6，贪心每次取不超过剩余的最大面额，
挑出 4 + 1 + 1 共 3 枚；DP 给出 3 + 3 共 2 枚，差 1 枚。面额成倍数关系时结论反过来：
`{1, 2, 4, 8}` 凑 15 与 `{1, 3, 9, 27}` 凑 40，两边都是 4 枚。穷举扫描给出这条界线
的位置：面额含 1、其余面额从 2 到 8 里取，一共 128 组、金额扫 1 到 30，3840 个组合里
贪心失手 518 个；而其中每个面额都是前一个整数倍的 14 组、420 个组合，失手 0 个。
倍数关系是充分条件不是必要条件，`{1, 5, 10, 25}` 不成倍数，金额 1 到 100 上贪心
处处最优。

第二段回答「状态定义是什么、换了会怎样」。最长上升子序列的三种定义各写一遍：
`dp[i]` 是以 `a[i]` 结尾的长度，`f[v]` 是以值 `v` 结尾的长度，`tails[len]` 是长度为
`len` 的上升子序列里最小的结尾值。三种定义必须给出同一个长度，程序用四种实现
把它们钉住：20 个元素的序列 A 上四种实现都是 6，200 个元素的序列 B 上都是 21；
连暴力枚举每条子序列的独立实现也核对过。代价则完全不同：序列 B 上定义一要
19900 次转移，定义三只有 200 次。同一套「以值结尾」的定义换个实现，朴素扫描
9987 次、树状数组 1382 次，而序列 A 的值域只有 9，两者几乎持平（77 对 76）。

第三段把 0/1 背包的二维表改成滚动数组。60 件物品、容量 1000：二维表 61 行 ×
1001 列，状态 61061 格，数据 244244 字节加 61 个行控制块 1464 字节，合计 245708 字节；
滚动数组 1001 格、4004 字节加 24 字节，合计 4028 字节。两者相差 61.0 倍，而 61
正好是行数，滚动数组省掉的就是这一维。内层循环的方向是这一段的重点：二维表
从小到大与从大到小都得到 661，因为读写的是不同的行；滚动数组从大到小是 661，
从小到大却变成 17000，这个数等于「每件物品可以拿任意多次」的独立实现算出的答案。

## 做完能掌握什么

- 会写出零钱兑换的贪心与 DP 两种解法，并能说出贪心在哪一步做出了不可撤销的选择
- 会自己构造贪心的反例，并用 DP 或者穷举扫描把反例找出来
- 会说出「面额成倍数关系」是贪心成立的充分条件，并能举出不成倍数也成立的例子
- 会为同一道题写出三族状态定义，并说清每一族的状态是什么、转移是什么
- 会用状态数、转移次数、比较次数三个量比较不同定义的代价，而不是只说一句「O(n²)」
- 会用暴力枚举给 DP 做交叉验证，而不是只信自己的实现
- 会把二维 DP 改成滚动数组，并用 `sizeof` 算出前后的字节数
- 会解释 0/1 背包的滚动数组为什么必须逆序枚举容量，以及正序枚举算出的是什么

| `greedy_dp.cpp` 的 `greedy_change` | 面额先排成降序，之后每一步都是「取不超过剩余的最大面额」，步数与探查次数都在这里数 |
| `greedy_dp.cpp` 的 `dp_change` | 状态是金额，哨兵值比任何可行解都大；`from` 数组记下最后用的那枚面额，用来回溯 |
| `greedy_dp.cpp` 的 `min_coins_memo` | 带记忆的递归，与 `dp_change` 是两条独立代码路径，自测用它交叉验证 |
| `greedy_dp.cpp` 的 `scan_greedy_systems` | 面额组按位掩码从小到大穷举，「第一处失败」才有确定的先后 |
| `greedy_dp.cpp` 的 `lis_end_at_index` | 定义一：状态是下标，双重循环把每一对下标都试一遍 |
| `greedy_dp.cpp` 的 `lis_by_value_naive` | 定义二：状态是值，每个元素扫一遍比它小的值 |
| `greedy_dp.cpp` 的 `MaxBit` | 定义二换个实现：树状数组维护前缀最大值，查询与更新把循环步数报出来 |
| `greedy_dp.cpp` 的 `lis_by_length` | 定义三：状态是长度，二分找第一个不小于当前值的位置 |
| `greedy_dp.cpp` 的 `lis_bruteforce` | 暴力枚举每条子序列，只用来给三种定义做交叉验证 |
| `greedy_dp.cpp` 的 `knapsack_2d_impl` | 二维表：`forward` 只决定内层从哪头走，两种写法读写的都是上一行 |
| `greedy_dp.cpp` 的 `knapsack_rolling` | 内层从大到小：`dp[j - w]` 读到的还是上一件物品的结果 |
| `greedy_dp.cpp` 的 `knapsack_unbounded` | 完全背包的独立实现：按容量递推，用来核对正序滚动数组算出的数 |
| `greedy_dp.cpp` 的 `table_bytes_2d` | 字节数一律 `sizeof` 现算，函数名就是算式，没有写死的 4 与 24 |
| `greedy_dp.cpp` 的 `ratio_text` | 比值只用整数算，输出一位小数，避免浮点格式带来的不可复现 |
| `main_cli.cpp` 的 `to_console_encoding` | 全项目唯一的编码转换点：控制台是 65001 就原样输出，是 936 就转 GBK |

## 已知问题

- 背包那两段字节数是按表格形状与 `sizeof` 算出来的，不是运行时测到的峰值：
  优化器完全可以把二维表化简成滚动数组，而源码里那张表仍然写着 61 行。
  这个数字描述的是源码里的表格，不是某一时刻真实占住的内存
- 行控制块的大小随标准库实现与目标平台变化，程序用 `sizeof` 现算，
  README 里的 24 与 1464 来自 64 位 MinGW-w64；换成 32 位目标会跟着变小
- 贪心扫描按位掩码穷举面额组，`max_denom` 每加一，组数就翻一倍；
  报告用的是 8，再往上跑会明显变慢
- 「面额成倍数关系」是充分条件，报告只给出了「成倍数则贪心一定最优」的实测，
  没有给出判定任意面额组是否可行的通用算法，那属于另一套理论
- 三种状态定义都在 `int` 值域上跑；值域很大时，「以值结尾」那两族的
  状态槽位会跟着值域涨，此时它反而不如另外两族
- 序列 A、B 都是写死的固定序列，不含随机数，因此数字稳定，
  也意味着它们代表不了别的分布
- 表格按显示宽度对齐，把 CJK 与全角标点算作 2 列；显示字体不满足这一假设时
  中文列会参差
- `lis_bruteforce` 的枚举量按 2 的幂增长，报告只把前 18 个元素交给它
