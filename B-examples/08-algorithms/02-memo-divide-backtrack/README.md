# 示例 `08-algorithms/02-memo-divide-backtrack` · 记忆化、分治与回溯

一个用计数器回答「同一道题为什么值得换个写法」的命令行程序。网格路径数与最长公共子序列各写三遍
——朴素递归、记忆化（自顶向下）、自底向上（递推），归并式分治在二分与三分两种分法下
各数一遍合并代价，N 皇后在三种剪枝档位下各走一遍搜索树。报告里的每个数字都由计数器数出来：
函数调用次数、真正算过的子问题个数、命中缓存的次数、合并阶段的比较与搬移次数、
搜索树节点数、放置与撤销次数，重跑逐位相同，一个都不是估的。

程序把「不重复子问题」当成记忆化有效性的直接证据。同一个 12 × 12 的网格，朴素递归要走
5408311 个递归树节点，记忆化只算 168 个子问题，两个数字并排出现在同一张表里，
相差 32192.3 倍；状态表里还有一个格子从头到尾没被问过，因为走到边界就返回了。

分治那一段把合并代价摊开：三分把递归层数从 12 压到 8，搬移少了 33324 次，
可三路归并每输出一个元素都要在三个候选里挑，比较次数反而涨到二分的 123.6%。
层数省下的那一头，抵不过每次合并多出来的那一头。

回溯那一段是一次账目核对：放置多少次就必须撤销多少次，搜索树节点数恰好等于放置次数加一，
候选总数等于放置次数加上被剪掉的候选数。三个档位的剪枝前后各有一行，节点数从 55987
降到 1957，再降到 153，而真正的解一个都没漏。

## 这个项目要解决什么问题

记忆化的说法通常是「把算过的存起来」，可用处有多大，要看递归树上有多少节点是重复的。
项目把这两个数直接摆到一起：网格路径数的朴素递归满足「节点数 = 2 × 答案 − 1」，
12 × 12 的答案 2704156 对应 5408311 个节点；而不同子问题只有 `(m + 1) × (n + 1) − 1 = 168` 个。
记忆化以后函数照样被进入 289 次，其中 168 次真的算，121 次从表里直接取。
三个数字合起来说明一件事：省下来的不是「计算」，是「重复的计算」。

三种写法在报告里各有各的代价。朴素递归 5408311 次函数调用、不占表；
记忆化 289 次调用、占 169 个格子；自底向上一次函数调用都没有，直接按行填 144 次加法。
最长公共子序列那三行是同一个模式的另一个例子，实算次数随串的内容变化
（38、46、103），因为碰到相同字符时这一步斜着走，跳过的子问题不必再问。

分治那一段回答的是「切几份才划算」。把区间切成三份，递归层数从 12 降到 8，
元素参与归并的轮数少了，4096 个元素的搬移次数从 98304 降到 64980。
代价出在合并：段数越多，每输出一个元素要在越多候选里挑最小的，比较次数从 43943 涨到 54334。
同一份数据、同一个答案、同一个逆序对数，两种分法的比较与搬移此消彼长，
合并阶段的开销决定分治划不划算。

回溯那一段把搜索过程记成一本账。放下一个皇后算一次选择，返回时把它拿掉算一次撤销，
两个数必须相等：6 皇后搜索的 153 个节点里，放置 152 次、撤销 152 次，节点数等于放置次数加一。
剪枝的前后差异同样落在节点数上：完全不剪枝 55987 个节点、叶子 46656 个，
只要求列不重复 1957 个节点、叶子 720 个（就是全部排列），再加上两条对角线 153 个节点、
叶子 4 个，这 4 个才是真正的解。

## 做完能掌握什么

- 会把一个递推式写成三种写法，并说出三者各自的调用次数与内存代价
- 会数一棵递归树的节点数，并说清它与「不重复子问题个数」为什么差着数量级
- 会在记忆化里分清「算过一次」与「问过一次」，并把命中缓存的次数记下来
- 会用自底向上的填表顺序把递归消掉，并说清边界那一行为什么可以直接写 1
- 会写归并式分治，并把合并阶段的比较次数与搬移次数分成两个计数器
- 会用实测数据说明三分为什么不比二分快：层数省得有限，每层却更贵
- 会写选择—撤销成对出现的回溯骨架，并检查两个计数器是否配平
- 会用公式（`Σ n^k`、`Σ n!/(n−k)!`）核对搜索树的结构量，而不是凭印象说「剪枝很有效」

## 代码里哪几处是要点

| 位置 | 要点 |
|---|---|
| `memo_lab.cpp` 的 `grid_naive_impl` | 基线 `m == 0 \|\| n == 0` 与两个递归调用，一棵二叉树，节点数按指数增长 |
| `memo_lab.cpp` 的 `grid_memo_impl` | 表里存 −1 表示没算过；`slot >= 0` 这一行就是「问过一次」与「算过一次」的分界 |
| `memo_lab.cpp` 的 `grid_bottom_up` | 第一行与第一列整体写成 1，剩下 `m × n` 个格子各做一次加法，没有函数调用 |
| `memo_lab.cpp` 的 `lcs_bottom_up` | 从右下角倒着填，每个格子只依赖右、下、右下三个格子，比较次数恰好是串长之积 |
| `memo_lab.cpp` 的 `merge_three` | 三段归并共用一个挑选循环，二路归并时第三段为空，两条路径用同一段代码 |
| `memo_lab.cpp` 的 `merge_three` 逆序对那几行 | 从后面的段取元素时，前面各段剩下的元素全都比它大，个数就是剩下的长度 |
| `memo_lab.cpp` 的 `sort_rec` | 二分与三分只差切点与递归次数，合并那一步共用；长度 2 时三分的第一段为空，归并照样走完 |

## 已知问题

- 「访问节点数」「递归层数」都是计数器数出来的调用次数，不是从栈指针测出来的字节数；
  换编译器、换优化等级，运行时间与真实栈用量会变，这些计数不变
- 完全不剪枝那一档只在报告与自测里跑到 n = 6：节点数是 `Σ n^k`，n = 9 时到四亿，
  真跑一遍要几秒；报告里那一行是 n = 6 的实测值
- 三分的切点在长度 2 时让第一段为空（`cut1 == begin`），归并照样走完，
  因此三分在小规模上的比较次数略高于「三段一样长」的理想值；长度 3 起切点才真正分成三份
- 逆序对计数与排序共用同一趟归并，报告里的比较次数是两者共同的开销，
  没有把「只排序」与「顺便数逆序对」分开计时
- 报告第二段的数据是固定种子构造的，不是真实数据分布；换一份数据，
  比较次数会变，三分与二分之间的差距也会变，这里给的是这一份数据上的结论
- `merge_sort_counted` 每层都要一个与输入等长的缓冲区，没有做原地归并；
  三分与二分的缓冲区大小相同，差别只在层数与每层代价
- `binomial` 用 `long long` 连乘，n 大到 60 以上就有溢出的风险；
  报告里最大的组合数是 `C(24, 12) = 2704156`，离上限很远
- 网格路径数用 `long long` 存，m + n 大到 60 以上同样有溢出的风险；
  12 × 12 的 2704156 与朴素递归的 5408311 次调用都在安全范围内
