# 配置步骤 · 空模板 09（RAII 与异常）

本模板是**分阶段的整体演练**，也是这五个模板里最难的一个：成品是一个资源管理小库
——文件句柄的 RAII 包装 `FileGuard`，加上一个用异常报告失败的复制函数 `copy_file`，
外面套三个驱动：命令行版 `app_cli.exe`、Win32 界面版 `app_gui_win32.exe` 与 Qt 界面版 `app_gui_qt.exe`（默认不构建）。
每个阶段结束时两个程序都能编译、能运行。怎么复制模板、怎么打开、遇到问题查哪里，
见 [`../README.md`](../README.md)，本文件不重复。

---

## 成品形态

做完 4 个阶段之后，这个小库具备：

| 能力 | 由哪一阶段提供 |
|---|---|
| 构造即拿到资源，拿不到就抛异常（对象不存在，也就不留下半成品） | 阶段 1 |
| 析构即释放，恰好一次，且不抛异常 | 阶段 1 |
| 句柄可读可写，出错抛异常；`close()` 幂等，可以安全地调用两次 | 阶段 1 |
| 拷贝被显式禁掉：管着资源的类不允许复制 | 阶段 2 |
| 移动转移所有权，源对象变成「空」，可以放进标准容器 | 阶段 3 |
| 复制文件：先做会失败的、再做不会失败的；中途失败不留半成品、资源全收回 | 阶段 4 |

命令行版按阶段打印日志与两个计数器；界面版把同一套操作搬到窗口上，
点「制造失败」就能看到「失败之后 live 没有变大」。

## 阶段 1 · 构造、析构、读写、关闭

**要做什么**（都在 `src/file_guard.cpp`）

- 1-1 构造函数：按模式 `fopen`，失败抛 `std::runtime_error`，成功打印「打开」并计数
- 1-2 析构函数：调用 `close()`，让 `live_count_` 自减
- 1-3 `valid()`
- 1-4 `close()`：幂等（已经关过就直接返回），打印「关闭」并计数
- 1-5 `read()`：读失败抛异常
- 1-6 `write()`：写的字节数不足时抛异常

**验收标准**

`Text`

```text
=== 阶段 1：三条路径 ===
[正常路径]
  打开 raii_a.tmp
  关闭 raii_a.tmp
[提前返回]
  打开 raii_b.tmp
  提前返回
  关闭 raii_b.tmp
[异常路径]
  打开 raii_c.tmp
  关闭 raii_c.tmp
  捕获：写到一半失败了
  live = 0, close = 3
```

注意「异常路径」里的顺序：**「关闭」出现在「捕获」之前**。栈展开先清理局部对象，
然后才轮到 `catch`（《04-语法/13-异常.md》第 2.1 小节）。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 一条「打开」都没有 | 构造函数还是占位版本 |
| 有「打开」没有「关闭」 | 析构函数没有调用 `close()` |
| `live` 不是 0 | 析构里忘了 `--live_count_`，或构造函数抛异常时也把计数加上了（抛异常时对象不存在，不该加） |
| `close = 6` | `close()` 不幂等，同一个句柄被关了两次 |
| 析构里抛出了异常，程序直接 `terminate` | 析构函数必须 `noexcept`；它默认就是，除非你显式写成 `noexcept(false)` |

## 阶段 2 · 拷贝必须禁掉

**要做什么**

- 2-1 在 `include/file_guard.hpp` 里显式写上两行 `= delete`（拷贝构造与拷贝赋值）

**验收标准**

- 取消 `main_cli.cpp` 顶部两条 `static_assert` 的注释后能编过
- 取消 `stage2()` 里 `FileGuard copy = original;` 那行的注释后**必须编译失败**

`实测数据`
`Text`

```text
骨架（未写 = delete）：
  error: use of deleted function 'constexpr FileGuard::FileGuard(const FileGuard&)'
写完 = delete 之后：
  error: use of deleted function 'FileGuard::FileGuard(const FileGuard&)'
```

两行报错的区别只有类名前面那个 `constexpr`：不写 `= delete` 时，编译器是**隐式删除**
拷贝构造（因为本类声明了移动操作），隐式生成的那一份是 `constexpr` 的；
显式写出来之后，这条声明就是你自己给的，编译器不再替它加 `constexpr`。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| 那行拷贝语句编译通过了 | `= delete` 没写对，或者写成了 `= default` |
| 报错关键词不是 `use of deleted function` | 检查是不是把 `= delete` 写到了移动操作上 |

> [!IMPORTANT]
> 判据只有一条：**这个类管着资源吗。** 管着，就不要让编译器生成拷贝。
> 两个对象拿着同一个句柄，析构时会关同一个文件两次——这与浅拷贝导致的双重释放是同一件事，
> 只是资源从内存换成了文件句柄。

## 阶段 3 · 移动转移所有权

**要做什么**

- 3-1 移动构造：接管句柄与路径，把源对象置空，并补上 `noexcept`
- 3-2 移动赋值：处理自赋值，先释放自己的资源，再接管，返回 `*this`

**验收标准**

`Text`

```text
=== 阶段 3：移动转移所有权 ===
  打开 raii_d.tmp
  移动之后：a.valid() = false, b.valid() = true
  live = 2
  关闭 raii_d.tmp
  作用域结束：live = 0, close = 4
  打开 raii_e.tmp
  打开 raii_f.tmp
  容器里 2 个句柄，live = 2
  关闭 raii_e.tmp
  关闭 raii_f.tmp
  清空容器后：live = 0, close = 6
```

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `a.valid() = true` | 移动之后没有把源对象置空。两块对象都拿着同一个句柄，析构时会关两次 |
| `live = 2` 之后 `close` 只加了一 | 被移动走的对象仍算活着，说明 `live_count_` 的加减与句柄的实际归属不一致 |
| 容器那一段编译失败，报 `use of deleted function` | 移动构造没声明，容器扩容时只能拷贝，而拷贝是删掉的 |
| 取消 `static_assert(std::is_nothrow_move_constructible<...>)` 的注释后编不过 | 移动构造没标 `noexcept`。标准容器只在移动不抛时才优先用它（《04-语法/13-异常.md》第 4 节） |

## 阶段 4 · 异常安全

**要做什么**

- 4-1 实现 `copy_file`：先打开源文件（会失败的一步放前面），再打开目标文件，
  按 8 字节一块复制；`fail_after >= 0` 时写到该字节数之后抛异常；
  中途失败要**先关闭再 `std::remove`**，把半成品删掉，然后把异常继续抛出去

**验收标准**

`Text`

```text
=== 阶段 4：异常安全 ===
  打开 raii_src.tmp
  关闭 raii_src.tmp
[正常复制]
  打开 raii_src.tmp
  打开 raii_dst.tmp
  关闭 raii_dst.tmp
  关闭 raii_src.tmp
  复制成功，校验 dst 的内容：  打开 raii_dst.tmp
0123456789abcdefghijklmn  关闭 raii_dst.tmp

[源文件不存在]
  抛出异常：打不开文件：raii_no_such.tmp
[中途注入失败：写入 8 字节之后出错]
  打开 raii_src.tmp
  打开 raii_dst.tmp
  关闭 raii_dst.tmp
  关闭 raii_src.tmp
  抛出异常：写入失败（练习用）
  失败之后 dst 还存在吗：否
  live = 0, close = 12

=== 收尾 ===
  live = 0（所有句柄都应当被释放）
```

> [!NOTE]
> 「复制成功，校验 dst 的内容：」这一行后面紧跟着打开与关闭的日志，
> 是校验函数自己打开文件造成的，属于正常现象。

**怎么自查**

| 你看到的 | 说明 |
|---|---|
| `[源文件不存在]` 那一段打印「不该走到这里」 | 打开源文件失败时没有抛异常 |
| 注入失败后 `dst 还存在吗：是` | 半成品没有删掉。注意 Windows 上不能删除还开着的文件，要先 `close()` 再 `std::remove` |
| 注入失败后 `dst 还存在吗：是`，且 `close` 计数比期望多一 | 你在 `catch` 里关了一次，析构时又关了一次——说明 `close()` 还不幂等，回到阶段 1 |
| 最后 `live` 不是 0 | 有句柄没有归还，检查 `copy_file` 里是不是自己手写了 `fclose`（不该有） |
| 程序直接崩在 `std::terminate` | `noexcept` 的函数里抛出了异常。检查析构函数与移动操作里有没有会抛的调用 |

## 界面部分怎么用

界面版是同一个核心模块的第二个驱动，有 Win32 与 Qt 两份实现，业务逻辑都只在 `core` 里。

### 两份界面：Win32 与 Qt

同一个窗口有两份实现，业务逻辑都只在 `core` 里，两份界面只负责调用它：

| 文件 | 界面库 | 产物 | 默认是否构建 |
|---|---|---|---|
| `src/main_gui_win32.cpp` | Win32 API + GDI | `app_gui_win32.exe` | 构建（零第三方依赖） |
| `src/main_gui_qt.cpp` | Qt Widgets | `app_gui_qt.exe` | **不构建**，需要显式打开 |

两份界面里的 TODO 是**同一批**，编号也一致（界面连接 1、2a、2b……）。
**做一份即可**，另一份留作对照：同一件事在消息映射里怎么写、在信号槽里怎么写。

**Qt 版怎么打开**

Qt 版用的是**官方安装器的动态版 Qt**，配置时指向那一套 Qt 的**套件目录**：

`PowerShell`

```powershell
# 套件目录要指到编译器那一层，例如 <Qt>/6.11.1/mingw_64
cmake --preset mingw-gdb -DWITH_QT=ON -DQT_ROOT=<Qt 的套件目录>
cmake --build --preset mingw-gdb
build\mingw\bin\app_gui_qt.exe
```

- `WITH_QT` 默认为 `OFF`：没有 Qt 时，`core`、`app_cli` 与 `app_gui_win32` 照常构建；
- Qt 的位置也可以放在环境变量 `QT_ROOT` 里，此时配置命令不必再写 `-DQT_ROOT`；
- 定位 Qt 与工具链匹配检查都交给仓库根目录 `工具/获取依赖/qt-dynamic.cmake`，
  **工程里不写死任何本机路径**；
- 模板若已被复制到仓库之外，Qt 版需要自行 `find_package(Qt6 COMPONENTS Widgets REQUIRED)`。

**运行时怎么部署**

构建完成后会自动调用 `windeployqt`，把 Qt 的 DLL 与 `platforms\qwindows.dll` 拷到 exe 旁边，
随后再把编这个 exe 的那套 MinGW 运行时 DLL 拷过去：

`Text`

```text
Qt6Core.dll  Qt6Gui.dll  Qt6Widgets.dll  platforms\qwindows.dll
libgcc_s_seh-1.dll  libstdc++-6.dll  libwinpthread-1.dll
```

- 后三个是 **MinGW 运行时**。Qt 自己的 DLL 也依赖它们，因此必须与 exe 放在一起，
  而且**必须与编译器同源**——不同 GCC 版本的 `libstdc++-6.dll` 混用会出怪问题；
- 工程同时给 Qt 目标加了 `-static-libgcc -static-libstdc++`：exe 本身不再依赖
  `libgcc_s_seh-1.dll` 与 `libstdc++-6.dll`，但 Qt 的 DLL 仍然需要，所以照拷；
- 目标机器仍需要对应的编译器运行库：MSVC 构建要装 Visual C++ 运行库；
  MinGW 构建的这三个 DLL 已经拷在 exe 旁边；
- **判据：把 exe 连同这些 DLL 拷到一个没有 Qt、`PATH` 里也没有 Qt 与 MinGW 的目录，
  双击能起窗口，才算部署完成。**
- 部署产物全部落在 `build\` 里，已被仓库 `.gitignore` 覆盖，**不要提交 DLL**。

> [!TIP]
> 只练语言部分时保持 `WITH_QT=OFF`，用 Win32 版或命令行版即可，不必装 Qt。

**怎么跑**

`PowerShell`

```powershell
cmake --build --preset mingw-gdb
build\mingw\bin\app_gui_win32.exe
```

在 VS Code 里调试它时，`program` 指向 `build/mingw/bin/app_gui_win32.exe`
（MSVC 生成器则是 `build/msvc/bin/Debug/app_gui_win32.exe`）。

**怎么自查**

| 操作 | 应当看到 | 没看到说明 |
|---|---|---|
| 点「打开」 | 日志出现「打开 raii_gui.tmp」，状态栏 `live = 1` | 打开分支没写，或没有调用 `refresh` |
| 点「写入一行」 | 日志每次多一行，`live` 不变 | 写入分支没写，或没有处理异常 |
| 点「制造失败」 | 日志出现异常消息，`live` **与点击前相同** | 失败分支没写，或者你在 `catch` 里漏了清理；若 `live` 变大，说明构造失败的对象被算进了计数 |
| 点「关闭」 | `live` 回到 0，`close` 加一，日志出现「关闭 raii_gui.tmp」 | 关闭分支没写，或没有把指针置空（下次点「打开」会重复打开） |
| 直接关窗口 | 进程正常退出，不残留句柄 | `WM_DESTROY` 里的 `delete` 被改坏了 |

> [!TIP]
> 界面版没有控制台窗口，看不到「打开」「关闭」这两行日志——它们由核心模块打印。
> 想在界面版里看到，就把断点打在 `FileGuard::close()` 上，
> 或者先用命令行版跑一遍，两个驱动用的是同一份实现。
