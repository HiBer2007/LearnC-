**写 C 与 C++ 的时候，用到的名字可以分成两堆。**

一堆是语言本身的：`int`、`for`、`struct`、`return`，编译器必须认识它们，
换个编译器也还是这些。另一堆是库里的：`printf`、`malloc`、`strlen`、`time`，
它们既不是关键字，也不是语法，只是**某个已经写好的函数的名字**。

**这一堆东西才是日常写代码时用得最多的部分。**
一份普通的 C 程序里，自己写的函数可能只有十来个，库里调用的却有几十处。

`06-标准库` 板块讲的就是这一堆。它被分成两段：A 段讲 C 标准库，
B 段讲 C++ 标准库。分段的理由很简单——**C++ 的标准库几乎全量包含了 C 的那一套**，
先把 C 这半边讲清楚，B 段就只需要讲「C++ 多出来的是什么、为什么更好用」。

本章节是 A 段的第一篇，它本身不教任何一个函数怎么用。
它要解决的是另外几件事：**这些 `<xxx.h>` 是谁规定的、为什么这样分、
遇到一个不认识的函数该去哪儿查、查的时候该看什么、
以及为什么有些函数用起来处处别扭**。

最后一件尤其重要。`gets` 已经被标准删掉了，`strncpy` 不保证在末尾补 0，
`atoi` 转换失败时一声不吭，`rand` 的低位随机性很差——
这些都不是「写法错了」，而是这几十年里标准为了兼容一直没动它们。
把它们当成历史包袱看待，比当成自己的失误去自责有用得多。

读完本章节，再看后面 A-01 到 A-05 的具体内容时，
遇到一个函数就会知道：**先看它的返回值，再看它的错误处理，
最后看标准有没有把某件事交给实现去决定。**

# 第 1 节 标准库是标准的一部分

## 1.1 库不是语言

**`printf` 不是一个语法结构。** 验证办法如下：
把 `<stdio.h>` 去掉，自己写一行声明，程序照样编译、照样链接、照样运行。

`实测数据`
`C`

```c
/* lib_not_lang.c    编译：gcc -std=c23 lib_not_lang.c -o lib_not_lang */
/* 故意一个头文件都不包含：库函数自己声明就能用 */

int printf(const char *format, ...);        /* 这两行就是 <stdio.h> 里的一小部分内容 */
int puts(const char *s);

int main(void) {
    /* 能取到地址，说明它就是普通函数，不是语言内置的语法 */
    int (*p)(const char *, ...) = printf;
    p("不包含 <stdio.h>，printf 照样能调用\n");
    puts("头文件只提供声明，实现在 C 运行库里");
    return 0;
}
```

`实测数据`
`Bash`

```bash
gcc -std=c23 lib_not_lang.c -o lib_not_lang && ./lib_not_lang
# 不包含 <stdio.h>，printf 照样能调用
# 头文件只提供声明，实现在 C 运行库里
```

**这行得通的原因**在于编译与链接是两件事。
编译时编译器只需要知道「`printf` 是一个接受格式串、返回 `int` 的函数」，
这条信息来自声明；链接时再去 C 运行库里找真正的那段代码。
`<stdio.h>` 提供的就是那批声明，它不提供实现。
（编译与链接的分工见《01-编译器/01-编译与链接.md》第 2 节。）

> [!IMPORTANT]
> **语言规定语法与语义，标准库规定一批现成的函数、类型与宏。**
> 两者写在同一份标准里，但是两回事：
> **库可以自己声明着用，语言的关键字不行。**

## 1.2 它在标准里的位置

C 标准的主体分成几大块：环境、语言、库、附录。
**库是第 7 章**，标题就叫「库」。

`文档`

> "Each library function is declared in a header, whose contents are made
> available by the #include preprocessing directive. The header declares a
> set of related functions, plus any types and additional macros needed to
> facilitate the use of such related functions."
>
> —— N3220 §7.1.2/1

`文档`

> "The standard headers are
> <assert.h> <complex.h> <ctype.h> <errno.h> <fenv.h> <float.h>
> <inttypes.h> <iso646.h> <limits.h> <locale.h> <math.h> <setjmp.h>
> <signal.h> <stdalign.h> <stdarg.h> <stdatomic.h> <stdbit.h> <stdbool.h>
> <stdckdint.h> <stddef.h> <stdint.h> <stdio.h> <stdlib.h> <stdnoreturn.h>
> <string.h> <tgmath.h> <threads.h> <time.h> <uchar.h> <wchar.h> <wctype.h>"
>
> —— N3220 §7.1.2/3

**一共 31 个头文件**，这就是 C23 标准库的全部入口。
其中 `<complex.h>`、`<stdatomic.h>`、`<threads.h>` 是**条件特性**，
实现可以不支持（§7.1.2 脚注 215）。

**每个头对应的章节号就是它的编号沿革**：`<stdio.h>` 在 §7.23，
`<stdlib.h>` 在 §7.24，`<string.h>` 在 §7.26，`<time.h>` 在 §7.29。
查标准时按这个编号定位最快。

`文档`

> "Standard headers may be included in any order; each may be included more
> than once in a given scope, with no effect different from being included
> only once, except that the effect of including <assert.h> depends on the
> definition of NDEBUG."
>
> —— N3220 §7.1.2/5

这句话的实践含义是：**标准头自己带包含保护**，
自己写的头文件则需要自己加（写法见《04-语法/14-预处理器.md》第 3 节）。

## 1.3 库里的名字可能是函数，也可能是宏

`<stdio.h>` 里有 `printf` 这样的函数名，也有 `EOF`、`BUFSIZ` 这样的宏。
**麻烦的是第三种情况：标准允许把一个函数同时实现成宏。**

`文档`

> "Any function declared in a header may be additionally implemented as a
> function-like macro defined in the header, so if a library function is
> declared explicitly when its header is included, one of the techniques
> shown later in the next subclause can be used to ensure the declaration is
> not affected by such a macro."
>
> —— N3220 §7.1.4/1

**`stdout` 就是这种情况的实例**。它看起来像一个 `FILE *` 类型的变量，
但在本机的 `<stdio.h>` 里它是这样定义的：

`实测数据`
`C`

```c
/* 从 gcc -E -dM -include stdio.h 的输出里摘出来的几行 */
#define stdout (__acrt_iob_func(1))
#define stderr (__acrt_iob_func(2))
#define stdin  (__acrt_iob_func(0))
#define EOF (-1)
#define BUFSIZ 512
#define FOPEN_MAX 20
```

**因此不能对它取地址**：

`实测数据`
`C`

```c
/* stdout_addr.c    编译：gcc -std=c23 stdout_addr.c -o stdout_addr （失败） */
#include <stdio.h>
int main(void) { FILE *p = &stdout; (void)p; return 0; }
```

`实测数据`
`Text`

```text
stdout_addr.c:2:28: error: lvalue required as unary '&' operand
    2 | int main(void) { FILE *p = &stdout; (void)p; return 0; }
      |                            ^
```

**同一段代码在别的实现上可能编得过**（那里的 `stdout` 是一个真变量），
这正是「标准允许两种做法」带来的差异。
要判断某个名字在本机是宏还是变量，用 `gcc -E -dM` 查一次即可，方法见第 3.1 小节。

> [!TIP]
> **写代码时不必刻意区分函数与宏**，标准要求宏实现也遵守函数的一切约定，
> 包括「每个参数只求值一次」（§7.1.4/1）。
> 需要区分的只有两种情况：**取地址**，以及**用 `#undef` 把它还原成真函数**。

`实测数据`

| 写法 | 结果 |
|---|---|
| `printf("%d", 1)` | 正常，是函数还是宏都无所谓 |
| `int (*p)(const char *, ...) = printf;` | 正常，标准明文允许对库函数取地址 |
| `FILE *p = &stdout;` | **编不过**，本机的 `stdout` 是宏 |
| `#undef stdout` | 把宏撤掉，露出背后的函数或变量（本机露出的是函数调用，仍然不能取地址） |

# 第 2 节 `<xxx.h>` 是怎么划分的

## 2.1 标准自己的分组

31 个头文件不是随手切的，它们按用途成组。按这套划分查，
就能大致判断「要找什么，去哪个头」。

`实测数据`

| 用途 | 头文件 | 里面有什么 |
|---|---|---|
| **输入输出** | `<stdio.h>` | `printf`、`scanf`、`fopen`、`FILE`、`EOF` |
| **字符串与内存** | `<string.h>` | `strlen`、`strcpy`、`memcpy`、`memcmp` |
| **数字转换与内存分配** | `<stdlib.h>` | `atoi`、`strtol`、`malloc`、`qsort`、`exit` |
| **字符分类** | `<ctype.h>` | `isdigit`、`isspace`、`toupper` |
| **数学** | `<math.h>`、`<tgmath.h>` | `sqrt`、`pow`、`fmod`、`isnan` |
| **时间** | `<time.h>` | `time`、`clock`、`strftime`、`timespec_get` |
| **错误** | `<errno.h>` | `errno`、`EDOM`、`EILSEQ`、`ERANGE` |
| **类型特征** | `<limits.h>`、`<float.h>`、`<stdint.h>`、`<inttypes.h>` | `INT_MAX`、`DBL_MAX`、`int32_t`、`PRIu64` |
| **本机信息** | `<locale.h>`、`<stddef.h>`、`<stdbool.h>` | `setlocale`、`size_t`、`NULL`、`bool` |
| **工具** | `<assert.h>`、`<stdarg.h>`、`<setjmp.h>`、`<signal.h>` | `assert`、`va_list`、`setjmp`、`signal` |
| **宽字符与 Unicode** | `<wchar.h>`、`<wctype.h>`、`<uchar.h>` | `wprintf`、`iswspace`、`char32_t` |
| **复数、原子、线程、位操作** | `<complex.h>`、`<stdatomic.h>`、`<threads.h>`、`<stdbit.h>` | 条件特性，后两个是 C11 与 C23 新增 |

**本板块不去覆盖这张表里的每一项。** 常用的几个头会讲透，
冷门的用一张表带过，分工见第 2.4 小节。

## 2.2 划分的依据

**这套划分是按「数据结构 + 操作」来的，不是按「谁调用谁」来的。**
分成这么几类：

- **一个头 = 一类对象**：`<stdio.h>` 是流，`<string.h>` 是字节序列，
  `<time.h>` 是时间值。同名头里的函数都围着这一类对象转；
- **一个头 = 一类操作**：`<ctype.h>` 全是判断与转换单个字符的，
  `<stdlib.h>` 是「其余都归它」的那个筐；
- **一个头 = 一组常量**：`<limits.h>`、`<float.h>` 里一个函数都没有，
  全是宏。

**判断一个函数归哪儿，有一个简单的经验**：
取决于它需不需要某个头的类型。`qsort` 要收函数指针，函数指针谁都能写，
于是它落进了 `<stdlib.h>`；`memcpy` 收 `void *`，也落进了 `<string.h>` 这个筐。

## 2.3 这套划分今天的问题

**它是 1970 年代的设计，按当时的模块划分，几十年没大改。**
今天用起来别扭的地方至少有这些：

| 现象 | 举例 | 为什么别扭 |
|---|---|---|
| **同一个头里混着两个层次** | `<stdlib.h>` 里既有 `atoi`（文本转数字），又有 `malloc`（内存分配），还有 `qsort`（排序） | 三者毫无关系，只是「别的头都放不下」 |
| **同一个功能分在两头** | `printf` 在 `<stdio.h>`，`atoi` 在 `<stdlib.h>`；`strtod` 在 `<stdlib.h>`，`snprintf` 在 `<stdio.h>` | 数字与文本互转要同时记两个头 |
| **名字与归属不一致** | `strdup` 是字符串操作，在 C23 里才进 `<string.h>`；在此之前它是 POSIX 的 | 同一个函数换个平台就换个头 |
| **按用途该在一起的分开了** | 处理一行文本要 `<stdio.h>` + `<string.h>` + `<stdlib.h>` + `<ctype.h>` | 一个任务横跨四个头 |
| **一个头里塞了太多** | `<stdlib.h>` 在 C23 里超过 60 个名字 | 想找那个名字得翻很久 |

**这不是「标准写错了」，而是「标准不能推翻自己」。**
删一个函数、挪一个头，会让几十年的老代码编不过。
C 标准选择的路线是**只加不改**——`gets` 被删掉是极少数的例外（见第 5.1 小节）。

> [!IMPORTANT]
> **按用途找头文件，不要按记忆找。**
> 记不住 `strtol` 在哪儿是正常的；知道「数字与文本互转在 `<stdlib.h>` 与 `<stdio.h>`」
> 这条线索，再查一遍，比背下来可靠。

# 第 3 节 怎么查

**标准库的用法不该靠背。** 常用的十几个函数用久了自然记得，
剩下的靠查。要掌握的是三件事：**去哪儿查、查什么、看到什么算看懂了**。

## 3.1 先查本机的头文件

**最权威的第一手资料就在本机**：编译器自带的那批头文件。
它们与所用的编译器、平台完全对应，不会出现版本对不上的问题。

**第一步是找到它们在哪。**

`实测数据`
`Bash`

```bash
gcc -std=c23 -print-file-name=include      # gcc 自己那批头（stddef.h、stdarg.h 等）
gcc -std=c23 -print-sysroot                # 系统头文件那一侧的根
```

`实测数据`
`Text`

```text
<MinGW>/lib/gcc/x86_64-w64-mingw32/15.2.0/include
<MinGW>/x86_64-w64-mingw32/include
```

两个目录都要看：`<stddef.h>` 这类编译器自带的在第一个，
`<stdio.h>`、`<string.h>` 这些平台相关的在第二个。

**第二步是查明这个头到底拉进了什么。** `gcc -E -H` 会打印出包含链。

`实测数据`
`C`

```c
/* inc.c    只用来观察头文件拉进了哪些文件：gcc -std=c23 -E -H inc.c */
#include <stdio.h>
```

`实测数据`
`Bash`

```bash
gcc -std=c23 -E -H inc.c | head -12
```

`实测数据`
`Text`

```text
# 1 "inc.c"
# 1 "<MinGW>/x86_64-w64-mingw32/include/stdio.h" 1 3
# 1 "<MinGW>/x86_64-w64-mingw32/include/corecrt_stdio_config.h" 1 3
# 1 "<MinGW>/x86_64-w64-mingw32/include/corecrt.h" 1 3
# 1 "<MinGW>/x86_64-w64-mingw32/include/_mingw.h" 1 3
...
```

**一行 `#include <stdio.h>` 实际拉进了四个以上的文件。**
读头文件时不必从头读，直接搜函数名更快。

**第三步是问「本机到底有没有这个东西」。** 函数在不在、头在不在，
都能在编译之前问清楚。C23 给了两个手段：`__has_include` 与每个头的版本宏。

`实测数据`
`C`

```c
/* header_check.c    编译：gcc -std=c23 header_check.c -o header_check */
#include <stdio.h>

/* __has_include 是 C23 起的预处理运算符：头文件在不在，编之前就能问 */
#if __has_include(<stdbit.h>)
#  include <stdbit.h>
#  define HAS_STDBIT 1
#else
#  define HAS_STDBIT 0
#endif

int main(void) {
    printf("有 <stdbit.h> 吗：%d\n", HAS_STDBIT);
    /* C23 给每个标准头配了一个版本宏，值是 202311L */
#ifdef __STDC_VERSION_STDIO_H__
    printf("<stdio.h> 的版本宏 = %ld\n", (long)__STDC_VERSION_STDIO_H__);
#else
    printf("<stdio.h> 没有版本宏\n");
#endif
    return 0;
}
```

`实测数据`
`Text`

```text
MinGW gcc 15.2.0：      有 <stdbit.h> 吗：0     <stdio.h> 没有版本宏
Ubuntu gcc 13.3.0：     有 <stdbit.h> 吗：1     <stdio.h> 没有版本宏
```

**同一个头在两边一个有一个没有**，而这与编译器版本谁新谁旧无关——
`<stdbit.h>` 是新标准的东西，是否提供取决于实现跟进的进度
（本机 Linux 侧的这个头可用，用法见《06-标准库/A-03-数值、数学与随机.md》第 6 节）。

`文档`

> "Some standard headers define or declare identifiers that had not been
> present in previous versions of this document. To allow implementations
> and users to adapt to that situation, they also define a version macro for
> feature test of the form __STDC_VERSION_XXXX_H__ which expands to 202311L."
>
> —— N3220 §7.1.2/6

**本机的两个头都没有定义这个版本宏**，因此「用版本宏判断新接口有没有」
这件事在本机还做不到，只能用 `__has_include` 判断头，用 `#ifdef` 判断单个名字。

## 3.2 手册页与在线资料

**Linux 上最方便的是 `man`。** 库函数在手册的第 3 节。

`实测数据`
`Bash`

```bash
man 3 printf | head -20
```

`实测数据`
`Text`

```text
PRINTF(3)                  Linux Programmer's Manual                 PRINTF(3)

NAME
       printf, fprintf, dprintf, sprintf, snprintf, vprintf, vfprintf,
       vdprintf, vsprintf, vsnprintf - formatted output conversion

SYNOPSIS
       #include <stdio.h>

       int printf(const char *format, ...);
...
```

**手册页写的是这个实现的行为，不是标准的规定**，两者有差别时以标准为准。
它的好处是快：`man 3 strtol` 一屏就能看到参数、返回值与 `errno` 的说明。

**Windows 侧的 MinGW 不带手册页**，可用的替代有三类：

| 渠道 | 适合查什么 | 注意 |
|---|---|---|
| 本机头文件 | 声明的准确形态、宏与函数的区别 | 只有声明，没有行为说明 |
| cppreference（`<https://en.cppreference.com/w/c>`） | 行为、返回值、示例、C 与 C++ 的差异 | 它描述的是标准，不针对某个实现 |
| man7.org（`<https://man7.org/linux/man-pages/>`） | Linux 上的实际行为、`errno` 取值 | 是 Linux 手册，Windows 上可能不同 |
| 标准草案 | 规定本身、实现定义的部分 | 正文长，按章节号定位 |

## 3.3 标准草案怎么读

**C 的正式标准要买，草案是免费的**，两者差异极小。
本教材引用的是 C23 草案 **N3220**，C++ 侧引用 C++17 最终草案 **N4659**。

**引用时写草案的章节号**，形如 `§7.23.6.1`。这个编号不是页码，
而是「第 7 章（库）第 23 节（`<stdio.h>`）第 6 小节（格式化输入输出）第 1 条（`fprintf`）」。
看到 `§7.26.2.5` 就知道是 `<string.h>` 里的复制类函数。

**每一条条文内部还有编号**，引用到具体那一条时要写出来：

`文档`

> "The printf function returns the number of characters transmitted, or a
> negative value if an output or encoding error occurred."
>
> —— N3220 §7.23.6.1/3

**末尾的 `/3` 就是条文序号**。同一个函数分「Synopsis（原型）、
Description（做什么）、Returns（返回什么）」三块，编号连续排下来。
查返回值时直接跳到 Returns 那一段。

> [!TIP]
> **不要用 ISO 正式版的页码去对草案**，两者排版不同。
> 也不要在网上抄别人写的章节号——不同版本的编号变过，
> 唯一可靠的做法是打开草案，按章节目录定位。

## 3.4 查的时候看什么

**一个库函数的完整信息有四项，缺一项就不算查到。**

| 看什么 | 为什么 | 例子 |
|---|---|---|
| **原型** | 参数类型与返回类型决定怎么调用，也决定要不要做类型转换 | `size_t strlen(const char *s)` 收的是 `const char *`，传 `char *` 不用转换 |
| **返回值** | 用返回值做判断，比事后猜有用得多 | `fopen` 失败返回 `NULL`；`fread` 返回的是「项数」而不是字节数 |
| **出错时怎么办** | 有的设 `errno`，有的返回特殊值，有的干脆不说 | `strtol` 溢出时返回极值并设 `errno = ERANGE`；`atoi` 什么都不说 |
| **实现定义的部分** | 标准把选择权交给实现，换个平台就变 | `%p` 打印成什么样、`long` 有多宽、`ftell` 在文本模式下返回什么 |

**前三项在手册页与标准里都写得很清楚。第四项最容易被忽略**，
它正是第 4 节的主题。

# 第 4 节 实现定义与未定义在库里的表现

## 4.1 三个术语

标准里有三个词，含义不同，混起来会误判。

`文档`

> "implementation-defined behavior
> unspecified behavior where each implementation documents how the choice is made"
>
> —— N3220 §3.5.1/1

`文档`

> "undefined behavior
> behavior, upon use of a nonportable or erroneous program construct or of
> erroneous data, for which this document imposes no requirements"
>
> —— N3220 §3.5.3/1

`文档`

> "unspecified behavior
> behavior, that results from the use of an unspecified value, or other
> behavior upon which this document provides two or more possibilities and
> imposes no further requirements on which is chosen in any instance"
>
> —— N3220 §3.5.4/1

**用一句话区分**：

- **实现定义**：标准说「这件事由实现决定」，但要求实现**写下来告诉用户**。
  因此它是稳定的、可查的，换平台要重新确认；
- **未指定**：标准给了几个选项，不要求实现说明选哪个。
  多数情况下不影响正确性，但会让输出顺序、求值顺序之类的东西不可预测；
- **未定义**：标准什么都没说。**程序怎么写都是它自己的事**，
  可能正常、可能乱码、可能崩，编译器也不必警告。

> [!CAUTION]
> **未定义行为的危险不在「一定会崩」，而在「这一次没崩」。**
> 本机跑通、连续跑通一年的代码，换个编译器或换个优化等级就可能出事，
> 而且没有任何提示。第 5 节与 A-02 会给出两个实例。

## 4.2 库里哪些是「实现说了算」

**库里的实现定义部分非常多，而且大多是日常会碰到的。**
下面这个程序一次打印出常见的那几个。

`实测数据`
`C`

```c
/* impl_defined.c    编译：gcc -std=c23 impl_defined.c -o impl_defined */
#include <stdio.h>
#include <limits.h>
#include <float.h>

int main(void) {
    /* 语言版本：标准里规定好的宏 */
    printf("__STDC_VERSION__       = %ld\n", (long)__STDC_VERSION__);

    /* 整数类型的宽度：标准只规定了最小值，具体多宽由实现定 */
    printf("sizeof(long)           = %zu\n", sizeof(long));
    printf("LONG_MAX               = %ld\n", LONG_MAX);
    printf("CHAR_MIN / CHAR_MAX    = %d / %d\n", CHAR_MIN, CHAR_MAX);

    /* 浮点：FLT_EVAL_METHOD 就是典型的实现定义 */
    printf("FLT_RADIX              = %d\n", FLT_RADIX);
    printf("FLT_EVAL_METHOD        = %d\n", FLT_EVAL_METHOD);

    /* 指针的打印形态：%p 输出成什么样，标准没有规定 */
    int x = 0;
    printf("sizeof(void*)          = %zu\n", sizeof(void *));
    printf("%%p 打印本机地址        = %p\n", (void *)&x);
    return 0;
}
```

`实测数据`

| 项目 | Windows 侧（MinGW gcc 15.2.0） | Linux 侧（Ubuntu gcc 13.3.0） |
|---|---|---|
| `__STDC_VERSION__` | 202311 | 202000（该版本最高只认到 `-std=c2x`） |
| `sizeof(long)` | 4 | 8 |
| `LONG_MAX` | 2147483647 | 9223372036854775807 |
| `CHAR_MIN` / `CHAR_MAX` | -128 / 127 | -128 / 127 |
| `FLT_RADIX` / `FLT_EVAL_METHOD` | 2 / 0 | 2 / 0 |
| `%p` 打印本机地址 | `0000000c945ff9bc` | `0x7ffe376c4274` |

**同一份源码，两边都编得过，但第 3 行的数字差了 4294967296 倍。**
`long` 的宽度就是最典型的一类实现定义：
标准只要求它「至少 32 位」，剩下的交给实现。
把 64 位平台上跑得好好的代码搬到 Windows 上，
凡是假设了 `long` 能装下指针或大整数的地方都会出问题。
需要确定宽度时用 `<stdint.h>` 的 `int32_t`、`uint64_t`（见 A-03）。

**`%p` 那一行也值得注意**：同一个空地址、同一段打印代码，
Windows 侧给出 16 位十六进制补零，Linux 侧给出带 `0x` 前缀的形式。
标准对 `%p` 的输出形态没有任何要求，因此**不要把 `%p` 的结果拿去解析或比较**。

## 4.3 哪些内容不能依赖

**另一些地方，标准直接写了「这是未定义行为」。** 库里的典型例子有三个，
它们共同的特点是：**在本机往往看不出问题**。

`文档`

> "The memcpy function copies n characters from the object pointed to by s2
> into the object pointed to by s1. If copying takes place between objects
> that overlap, the behavior is undefined."
>
> —— N3220 §7.26.2.1/2

**重叠时 `memcpy` 会怎样，标准把答案留成了「未定义」。**
本机把常见的重叠情形试了一遍：

`实测数据`

| 试了什么 | 结果 |
|---|---|
| 40 种重叠距离乘 7 种长度，共 280 组 | `memcpy` 与 `memmove` 的结果逐字节相同，0 组有差异 |
| 同一批用例换上 MSVC 19.44 与 glibc 13.3 | 同样 0 组有差异 |

这正是未定义行为最麻烦的形态：**看起来完全正常**。
详细数据与正确写法见《06-标准库/A-02-字符串与内存：string.h.md》第 4.1 小节。

**第二个例子是格式串与参数类型不匹配。**

`实测数据`
`C`

```c
/* printf_wrong.c    编译：gcc -std=c23 -Wall -Wextra printf_wrong.c -o printf_wrong */
#include <stdio.h>

int main(void) {
    /* 格式串说「我要一个 int」，实际给的是 double：类型不匹配 */
    printf("把 double 按 %d 打印：[%d]\n", 3.14);
    return 0;
}
```

`实测数据`
`Text`

```text
printf_wrong.c:6:27: warning: format '%d' expects argument of type 'int',
but argument 2 has type 'double' [-Wformat=]
把 double 按 1374389535 打印：[1038570368]
```

**编译器给了警告，程序照跑，输出是垃圾**，
而且同一个程序再跑一次这两个数字还会变。

**第三个例子是越界访问。** 库不检查与库函数配套的数组长度：
`strcpy` 不知道目标有多大，`memcpy` 不知道源有多长。
越界的后果见《06-标准库/A-02-字符串与内存：string.h.md》第 4.3 小节。

## 4.4 「本机能跑通」不是判据

**一句实用的话：编译器不警告，不代表写对了；今天跑得对，不代表明天还对。**

判断一段代码可不可靠，看的是它有没有踩到标准划出的那几类线。
清单不长，日常遇到的就这么几条：

| 线 | 判据 | 怎么做 |
|---|---|---|
| 目标缓冲区够不够 | 长度算过没有 | 用 `snprintf`、带宽度、先算长度 |
| 有没有重叠 | 两块内存会不会碰头 | 会重叠就用 `memmove` |
| 类型对不对得上 | 格式串与实参类型是否一一对应 | 打开 `-Wall -Wextra` |
| 返回值查了没有 | 失败路径走得到吗 | `fopen`/`malloc`/`scanf` 的返回值都要看 |
| 有没有依赖实现定义 | 换平台还成立吗 | 需要确定宽度就用 `<stdint.h>` |

**开警告是最便宜的防线。** `-Wall -Wextra` 能拦下格式串不匹配、
返回值没用、隐式声明这一类问题，代价只有一行编译选项。

# 第 5 节 哪些坑是设计遗留

**这一节列的四件事，每一件都会让初学者以为是自己写错了。**
它们不是——它们是标准在几十年的兼容压力下留下的形状。

## 5.1 `gets`：已经被删掉

`gets` 从标准输入读一行，**不检查目标缓冲区有多长**。
这个函数在 C11 里被删除，C23 里当然也没有。

`文档`

> "Major changes in the third edition (__STDC_VERSION__ 201112L) included:
> ...
> — removed the gets function (<stdio.h>)"
>
> —— N3220 §M.4

**但本机仍然编得过。** 因为运行库里还留着这个符号，只是编译器会给警告：

`实测数据`
`C`

```c
/* legacy_gets.c    编译：gcc -std=c23 legacy_gets.c -o legacy_gets */
#include <stdio.h>

int main(void) {
    char buf[16];
    gets(buf);              /* C11 起从标准里删除，C23 里更没有 */
    puts(buf);
    return 0;
}
```

`实测数据`
`Text`

```text
legacy_gets.c:6:5: warning: call to 'gets' declared with attribute warning:
Using gets() is always unsafe - use fgets() instead [-Wattribute-warning]
```

**加上 `-Werror` 就编不过了**，这也是把警告当错误用的一条理由：

`实测数据`
`Text`

```text
legacy_gets.c:6:5: error: call to 'gets' declared with attribute warning:
Using gets() is always unsafe - use fgets() instead [-Werror=attribute-warning]
```

**「能编过」与「标准里有」是两件事。** 依赖已被删除的函数，
等于把代码绑在某一个实现上。替代品是 `fgets`，用法见
《06-标准库/A-01-输入输出：stdio.md》第 3.4 小节。

## 5.2 `strncpy`：不保证结尾的 0

**这个函数的签名写着「带长度，安全」，实际行为与名字给人的印象不符。**
标准自己的脚注把话说得很清楚：

`文档`

> "Thus, if there is no null character in the first n characters of the
> array pointed to by s2, the result will not be null-terminated."
>
> —— N3220 §7.26.2.5 脚注 361

**名字里的 `n` 限制的是「写多少」，不是「结果是不是一个字符串」。**
源字符串比 `n` 长时，它照样写满 `n` 个字节，一个结尾的 0 都不补。
后果是这段内存**不能当字符串用**，而它看起来完全正常。
详细的实测与正确写法见《06-标准库/A-02-字符串与内存：string.h.md》第 2.3 小节。

**这个函数是历史遗留**：它最早用在固定长度的文件名字段里，
那种场景下写满、不补 0 是刻意的行为。
后来被当成「安全的 strcpy」到处使用，问题就来了。

## 5.3 `rand`：标准自己承认它弱

`rand` 是 `<stdlib.h>` 里唯一的随机数函数。
**标准没有承诺它的随机质量**，还在注释里直说了：

`文档`

> "There are no guarantees as to the quality of the random sequence produced
> and some implementations are known to produce sequences with distressingly
> non-random low-order bits. Applications with particular requirements
> should use a generator that is known to be sufficient for their needs."
>
> —— N3220 §7.24.2.1/4

**典型的症状是低位几乎不随机**：连续取 `rand() % 2` 可能得到
一长串交替的 0 与 1。用它做模拟、抽奖、洗牌都会出问题。
可复现且质量可靠的随机数应当取自 C++ 的 `<random>`
（《06-标准库/B-05-数值.md》章节）或平台提供的生成器。
`rand` 的分布实测见《06-标准库/A-03-数值、数学与随机.md》第 5 节。

## 5.4 `atoi`：出错了也不说

`atoi` 把字符串转成 `int`。**它没有返回值之外的错误通道**：

`文档`

> "The atoi, atol, and atoll functions convert the initial portion of the
> string pointed to by nptr to int, long int, and long long int
> representation, respectively. Except for the behavior on error, they are
> equivalent to
> atoi: (int)strtol(nptr, nullptr, 10)"
>
> —— N3220 §7.24.1.2/2

**「Except for the behavior on error」这几个字是全部关键**：
出错时它和 `strtol` 不一样，而标准没说它会怎样。
同一个程序在两个平台上跑出来的结果如下。

`实测数据`

| 调用 | Windows 侧（MinGW gcc 15.2.0） | Linux 侧（Ubuntu gcc 13.3.0） |
|---|---|---|
| `atoi("abc")` | 0 | 0 |
| `atoi("99999999999999999999")` | 1661992959 | -1 |
| 调用之后的 `errno` | 0（被 `atoi` 清掉了） | 34（ERANGE） |

**同一个函数、同一段输入，两边给出的错误信息完全对不上。**
数据与 `strtol` 的用法见《06-标准库/A-02-字符串与内存：string.h.md》第 5 节。

**需要判断「转换成功了吗」的时候只能用 `strtol`**，它给了两个出口：
`endptr` 给出已转换的字符数，`errno` 说明有没有溢出。

## 5.5 为什么会留下这些

**标准的两条底线互相打架**：

- 要**改正错误**，就得删函数、改行为；
- 要**不破坏已有代码**，就什么都不能动。

**C 标准选择的是后者**，理由是已有代码的量级太大：
一个被全世界用了三十年的头文件，改动一次要牵动无数项目。
因此它的通行做法是**只加不改**，把不好用的东西留在原地，
另外加一个新的（`gets` 对应 `fgets`，`strncpy` 对应 `strlcpy`／`snprintf`）。

**理解这一点之后，看待这些函数的态度会变**：
它们不是「设计得差」，而是「当年合理，今天不合适，又不能删」。
遇到它们时，知道该绕开哪一个、用哪个替代，就够了。

> [!NOTE]
> **本节的四件事在后面的章节里都会重新出现，并且给出实际运行得到的数据与替代写法**：
> `gets` 与 `strncpy` 在 A-01、A-02，`atoi` 在 A-02 与 A-05，`rand` 在 A-03。

# 第 6 节 A 段与 B 段的关系

## 6.1 C++ 里这些东西一个不少

**C++ 标准库把 C 的库整个包含了进来，只多了一层名字空间的包装。**
每个 C 头在 C++ 里都有一个对应的 `<cxxxx>` 版本：

`实测数据`
`C++`

```cpp
/* c_and_cpp_headers.cpp    编译：g++ -std=c++17 c_and_cpp_headers.cpp -o c_and_cpp_headers */
#include <cstdio>       /* 对应 <stdio.h> */
#include <cstring>      /* 对应 <string.h> */
#include <cstdlib>      /* 对应 <stdlib.h> */

int main() {
    char buf[32];
    std::strcpy(buf, "hello");
    std::printf("%s，长度 %zu\n", buf, std::strlen(buf));   /* 加 std:: 前缀 */
    std::printf("%d\n", std::atoi("42"));
    return 0;
}
```

`实测数据`
`Bash`

```bash
g++ -std=c++17 c_and_cpp_headers.cpp -o c_and_cpp_headers && ./c_and_cpp_headers
# hello，长度 5
# 42
```

**规则只有三条**：

| 写法 | 名字在哪个命名空间 | 备注 |
|---|---|---|
| `#include <cstdio>` + `std::printf` | `std::` | 标准保证的写法 |
| `#include <cstdio>` + `printf` | 也可能在全局 | 标准不保证，实践中的实现都提供 |
| `#include <stdio.h>` + `printf` | 全局 | 与 C 完全一样，C++ 也支持 |

**因此读 A 段的代码时不必切换思路**：把 `#include <stdio.h>` 换成
`#include <cstdio>`、把 `printf` 换成 `std::printf`，就是 C++ 里的等价写法。
B 段的每一章都会给出这种逐项对照。

## 6.2 同一件事的两种写法

**下面这十七行代码做的是同一件事**：从标准输入读一行，
按逗号切成字段，逐条打印。

`实测数据`
`C`

```c
/* split_c.c    编译：gcc -std=c23 split_c.c -o split_c
 * 用法：split_c.exe < split_input.txt
 */
#include <stdio.h>
#include <string.h>

int main(void) {
    char line[128];
    if (!fgets(line, sizeof line, stdin)) return 0;

    line[strcspn(line, "\r\n")] = '\0';        /* 去掉行尾的换行 */

    int fields = 0;
    for (char *t = strtok(line, ","); t; t = strtok(NULL, ",")) {
        printf("第 %d 个字段：[%s]\n", ++fields, t);
    }
    printf("共 %d 个字段\n", fields);
    return 0;
}
```

`实测数据`
`C++`

```cpp
/* split_cpp.cpp    编译：g++ -std=c++17 split_cpp.cpp -o split_cpp
 * 用法：split_cpp.exe < split_input.txt
 */
#include <iostream>
#include <sstream>
#include <string>

    std::string line;

    std::string field;
```

`实测数据`
`Text`

```text
输入：苹果,3.50,2,2026-09-30

C 版与 C++ 版的输出完全相同：
第 1 个字段：[苹果]
第 2 个字段：[3.50]
第 3 个字段：[2]
第 4 个字段：[2026-09-30]
共 4 个字段
```

**差别不在输出，在代价与风险**：

| 维度 | C 版（`char[]` + `strtok`） | C++ 版（`std::string` + `istringstream`） |
|---|---|---|
| 缓冲区 | 自己定 128 字节，行长了就截断 | 自动增长，多长都行 |
| 输入被改写 | `strtok` 把逗号改成 `\0`，原串报废 | 原串不动 |
| 能嵌套用吗 | 不能，内层会冲掉外层的状态 | 每个流各自独立 |
| 编译出来的东西 | 小 | 大一些（要链接 `std::string`、流设施） |
| 出错时的表现 | 静默截断、静默越界 | 抛异常或置流状态位 |

**两边都值得会。** 写一小段解析、或者在没有 C++ 运行库的环境里，
C 版更直接；做正式的数据处理，C++ 版的省心程度高得多。

# 第 7 节 速查表

**这一张表是本章节的用法索引**：遇到一个问题时，
先看第一列知道「该去哪儿查」，再看第三列避开常见的坑。

`实测数据`

| 要做的事 | 去哪儿 | 典型的坑 |
|---|---|---|
| 找一个函数在哪一个头 | 第 2.1 小节的表；查不到就 `grep` 本机头文件目录 | 不要凭记忆猜，`strtol` 与 `snprintf` 不在同一个头 |
| 查一个函数的准确原型 | 本机头文件（`gcc -E -H` 找路径） | 头文件里只有声明，行为要另查 |
| 查行为、返回值、错误处理 | `man 3 函数名`（Linux）或 cppreference | 手册页写的是某个实现的行为，不等于标准 |
| 查标准怎么规定的 | N3220 草案，按 `§7.23.6.1/3` 这样的编号定位 | 不要用 ISO 正式版的页码去对草案 |
| 判断某个头/名字本机有没有 | `__has_include`、`#ifdef` | 版本宏 `__STDC_VERSION_XXXX_H__` 本机没提供 |
| 判断某件事是不是实现定义 | 查 `§J.3`（实现定义行为清单）或本机实测 | 实现定义的东西换平台就变，`long` 的宽度是典型 |
| 判断某段代码踩没踩未定义 | 查 `§J.2`（未定义行为清单） | 「本机跑得通」不是判据 |
| 打开最有用的一组警告 | `-Wall -Wextra`（再加 `-Werror` 更狠） | 格式串不匹配、返回值没用都能拦下来 |
| 找已被删除或过时的函数 | 查 `§M`（修改历史）与 `§7.33`（未来库方向） | `gets` 已删除；`strtok` 仍在但没有可重入保证 |

# 术语表

| 术语 | 一句话解释 |
|---|---|
| **标准库** | 标准第 7 章规定的那批函数、类型与宏，通过 31 个头文件使用 |
| **头文件** | 声明库函数、类型与宏的文件，用 `#include` 取用；不提供实现 |
| **实现定义行为** | 标准交给实现选择，但要求实现写明的行为 |
| **未指定行为** | 标准给了几个选项，不要求实现说明选了哪个 |
| **未定义行为** | 标准不做任何要求的行为；可能正常，也可能崩，且不必给出诊断 |
| **保留标识符** | 标准留给自己用的名字，程序不得占用（见 §7.1.3） |
| **未来库方向** | §7.33，列出标准打算将来启用的名字，用到这些名字的程序不算错 |
| **条件特性** | `<complex.h>`、`<stdatomic.h>`、`<threads.h>`，实现可以不提供 |
| **CRT（C 运行库）** | 提供库函数实现的运行期代码，与编译器、平台绑定 |
